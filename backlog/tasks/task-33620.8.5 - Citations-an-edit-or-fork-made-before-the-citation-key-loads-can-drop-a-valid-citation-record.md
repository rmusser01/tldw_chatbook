## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in the TASK-33620.8 review (2026-10-30). Since TASK-33620.8 the app composes the citation repository without reading the keyring and loads the fingerprint key on first use. Until then the repository's codec is missing. In that window, the owner transition that runs when a message is edited marks a valid citation owner as a body mismatch for good, and linking a fork's owner fails with fingerprint_key_unavailable. Today the deferred startup reconcile (when records exist) and the Console count reader load the key before a user can realistically edit or fork, so the record survives by ordering alone. A change to that ordering, or a fast edit right after launch, would silently drop a record the key could have verified.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 An edit to a cited message made before the key has been loaded keeps its citation record when the key is available
- [ ] #2 Forking a cited message before the key has been loaded links the fork's citation owner when the key is available
- [ ] #3 The key is loaded off the UI loop, never inside the edit or fork database transaction
- [ ] #4 A test pins both cases with the key still pending at the start of the edit or fork
