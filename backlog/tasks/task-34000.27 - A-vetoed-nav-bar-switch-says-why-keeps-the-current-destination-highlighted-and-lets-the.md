## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: when Library has to refuse leaving (for example, a note title with a trailing space cannot be saved), clicking another destination in the nav bar does nothing visible. The nav bar then frames the clicked destination (⌃2 Console) while Library stays on screen, so the user believes either that the app froze or that they are already on Console. Worse, after the user fixes the problem, clicking ⌃2 Console again still does nothing, because the bar thinks Console is already active. The button looks broken for the rest of the visit. First-timers and keyboard users have no way to tell why.

Severity: the journey rated this P2. The live re-repro raised it to P1 because the retry click is swallowed. The finding title, summary and ACs all carry that escalation.

Observed (verified at 160x45, golden profile):
- 16-veto-t7: with the editor reporting "Title begins or ends with whitespace — remove it to save.", clicking ⌃2 Console leaves Library on screen while the nav bar frames "⌃2 Console". Nothing on screen responds to the click; only the log says "Navigation to chat vetoed by the outgoing screen's pending-work flush".
- 18-retry-console: after the title is fixed ("Saved 00:40"), clicking ⌃2 Console again still leaves Library on screen with Console framed.

Verified cause (origin/dev 2d34cbf80d):
- The veto branch in `app_navigation.py:533-538` (`if flush_result is False:`) only logs and returns False. It neither tells the user nor rolls back the nav bar's optimistic highlight.
- The navigation-failure path already does both: `_notify_navigation_failure` (:684) calls `MainNavigationBar.restore_active` (UI/Navigation/main_navigation.py:1217), whose docstring records this exact swallowed-retry trap (task-2720).
- The flush-timeout (:539) and flush-failure branches next to the veto do notify the user, but they also return without restoring the highlight. That gap is code-traced only, not reproduced.
- On the Library side, `LibraryScreen.flush_pending_work` (UI/Screens/library_screen.py:11109) notifies prompt and skill vetoes (task-449, TASK-2702) but not Notes vetoes. Its comment assumes the Notes banner is enough, but nothing ties that banner to the nav-bar click.

Suggested direction (the review's refined fix):
- In the app_navigation veto branch, call `restore_active` with the current route.
- Show the outgoing screen's veto message.
- Have `LibraryScreen.flush_pending_work` notify Notes validation vetoes with the field and the reason.
- Give the timeout and failure branches the same highlight rollback.

Owning-task note: TASK-2702 (Done) made the unsaved-prompt nav veto speak, and TASK-2720 made the failure path roll back the highlight. Neither covers the generic veto branch or Notes vetoes. Finding N-25 (the in-screen leave-veto toast names a 'Discard new note' button that is not there and blames the title for every veto) is a separate review finding about that toast's wording. This task covers the nav-bar path; reuse the corrected wording, do not fork it.
