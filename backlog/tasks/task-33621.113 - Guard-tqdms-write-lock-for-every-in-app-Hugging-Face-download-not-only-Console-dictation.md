## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The root cause in TASK-33621.21 is app-wide. Inside the running app, sys.stderr is Textual's capture with fileno() == -1; the first tqdm bar (built even when progress bars are disabled) creates a multiprocessing lock, which on macOS starts CPython's resource tracker, raises 'ValueError: bad value(s) in fds_to_keep', and leaves tqdm's class lock held. The guard, allow_tqdm_without_stderr_descriptor(), runs only at the start of a dictation attempt. A download from another feature first (embeddings, TTS models, media transcription, Models screen installs) can still fail that way and wedge every later download in the process, Dictate's included until its guard repairs the lock.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Every Hugging Face download in the app now gets tqdm's thread-only write lock, whichever feature downloads first.

Choke point. The entry points are many and mostly inside third-party loaders (sentence-transformers in RAG and Evals, transformers `from_pretrained` in Embeddings_Lib, Chunking and OCR, faster-whisper/NeMo/parakeet-mlx/Qwen in transcription_service, Kokoro's `hf_hub_download`, Chatterbox/Higgs), and `fd_protection.protect_file_descriptors` covers only some of them. All of them build tqdm's lock through `tqdm.std`, so that import is the one choke point: guarding call sites would miss the next new one.

Change. `tldw_chatbook/__init__.py`, beside the existing progress-bar settings: `_arm_tqdm_write_lock()` sets `TqdmDefaultWriteLock.mp_lock = None` (tqdm's own fallback when a multiprocessing lock cannot be built) immediately if `tqdm.std` is already imported, otherwise through a meta-path finder that wraps `tqdm.std`'s loader and decides the lock as that module finishes executing, then retires. It is the same arming pattern as the tiktoken armer above it, but asks the other finders directly instead of removing itself from `sys.meta_path`. It imports nothing (only `sys`), so no module joins `import tldw_chatbook`, the boot import census or the ui-ready census, and tqdm is never imported by it. A lock tqdm already decided is left alone. `Utils/model_download_guard.py` and its dictation call are unchanged: it remains the repair for a lock wedged by an unguarded build.

Tests (`Tests/Utils/test_app_wide_tqdm_lock.py`, fresh interpreters)
- AC#1: first launch with the spawn start method, `import tldw_chatbook`, a running Textual app (stderr fileno -1 asserted), and a real `hf_hub_download` from a loopback hub on a worker thread, with the dictation guard module never loaded. Dev: `ValueError: bad value(s) in fds_to_keep` and tqdm's class lock held (checked from the main thread, which never touched it; an earlier draft probed from a new thread, which can reuse the dead thread's id and read True on dev -- the trap in lessons-testing-evidence). Branch: the file arrives, the lock is free.

- Mutations, restored by edit: the decision made a no-op (all 3 red, `fds_to_keep` again); the already-imported branch skipped (only the tqdm-first case red).
