## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Moonshot (Kimi) setup ends with '✓ Provider — moonshot' and 'Start chatting', but every reply in a saved chat is generated and billed, then thrown away. The turn shows 'Provider continuation could not be persisted; retry or recover the interrupted run.' A recovery panel then falsely warns that delivery status is unknown and that a retry may send a duplicate request, and the composer stays blocked until the user discards the reply. The run record proves the provider answered: 'Model response completed' is logged 5 ms before the error. Temporary chats with the same model reply normally, and Anthropic and llama.cpp work, so the fault is in the persistent branch.

All four models Moonshot currently lists return reasoning content even on plain replies, so the provider adapter always builds a "complete" continuation checkpoint. Storing that checkpoint fails at a precondition somewhere between the controller's dispatch-recovery state and the chat store, and no current test drives that path; the store-level test for it passes. Six different continuation-error exits share one message, so nothing says which precondition failed.

This is the newly found P0 gap-02: roadmap item N6 and SF1 step 7 in §5 of Docs/superpowers/qa/first-run-wizard-ux-review-2026-10-02/README.md. No backlog task covers it. Coordination: this is not the TRACE_PROVENANCE pause that open PR #2975 fixes, and TASK-33662 only fixes Retry and Discard after a relaunch. Starting points on dev are the persistent path in Chat/console_chat_store.py (around lines 21040–21175) and the continuation handling in Agents/agent_runtime.py (around lines 1442–1456 and 2192–2235).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** Every saved-chat Moonshot reply failed because the durable dispatch row and the provider continuation describe the same endpoint in two formats. The repository compared them for equality, so terminal settlement always conflicted. That comparison is fixed. In addition, the optional reasoning checkpoint can no longer cost the user the reply, and every continuation-error exit now names its precondition.

**Root cause (AC#2).** `resolve_console_destination` records a credential-free origin in the dispatch row (`https://api.moonshot.ai`). The continuation carries its full base URL (`https://api.moonshot.ai/v1`). `ConsoleDispatchRepository._continuation_matches_destination` compared them with `==`, so `settle_with_assistant` returned CONFLICT. The store then marked dispatch recovery needed and raised "terminal settlement failed", and the runtime reported "Provider continuation could not be persisted". The same comparison gates the tool-batch handoff, so any saved-chat tool continuation conflicted too. The store and controller tests passed only because they hand-built a destination identity that already carried `/v1`.

How it was found: AC#3's diagnostics went in first. A live repro on the instrumented build (`homes/g3-moon1/.../tldw_cli_app.log`, 18:31:56) logged `reason=final_persist_failed store_failure=terminal_settlement_failed` with no "terminal settlement failed" warning, so settlement had returned early. The live DB showed matching message versions, and `resolved_destination_json` held `endpoint_identity: "https://api.moonshot.ai"`.

**Changes**
- Fix (`Chat/console_dispatch_repository.py`, `Chat/console_library_destination.py`): a new `console_endpoint_identity(base_url)` returns the identity the resolver records; the resolver now uses the same helper. The match compares that identity, and an identity recorded as the exact URL still matches. A different origin, port or scheme still conflicts.
- Fallback (AC#2; `Agents/agent_runtime.py`, `Chat/console_chat_store.py`): suppose a tool-free first final checkpoint (reasoning kept only for replay) fails, and the store wrote nothing (codes in `UNWRITTEN_STORE_FAILURES`). The loop then keeps the delivered reply as an ordinary reply and traces `model_error` "Reasoning not preserved for replay" with the codes. The store no longer flags recovery for that rolled-back atomic settlement, so the ordinary completion path settles the turn. Tool-run checkpoints, post-commit failures and unrecognised failures still fail closed. A mutation check (re-adding the recovery flag) turned the pilot fallback test RED, so the store change is load-bearing. `console_chat_store.py` is +2 lines (22336 against a budget of 22344); no ratchet row was raised.
- Diagnostics (AC#3): each of the 21 `continuation_error` call sites passes its own reason code (20 fixed codes, plus one site that passes one of six shape codes from `_first_final_continuation_problem`), recorded in the error step's `field_states["continuation_error"]` and logged. The compound context/shape checks were split (`_first_final_continuation_problem`). `persist_continuation` logs the event type, the error and cause class names, and the store's precondition as a code. The new module `Chat/provider_continuation_diagnostics.py` maps the store's fixed failure sentences to codes, so exception text is never logged (ADR-029). A test parses the store source and fails if a new failure sentence on the persist path has no code. The diagnostic inventory was re-pinned (agent_runtime 12 to 15 calls, all reviewed as metadata-only) and the rows were added to `REVIEWED_METADATA_ONLY_DIAGNOSTICS`.
- Smoke matrix (AC#4): `Tests/UI/test_console_moonshot_reasoning_reply.py` is a Console pilot built on the real ChatScreen, controller, store, runtime and gateway, with a file-backed DB. The adapter returns the real `MoonshotResponse` from `_moonshot_turn_response`; only the HTTP call is replaced. `SMOKE_MATRIX` covers kimi-k2.6, kimi-k2.7-code, kimi-k2.7-code-highspeed and kimi-k3, with an OpenAI control. Each row sends in a saved chat, then in a Temporary chat (through the real "Send without capture" button), and asserts the two views are equal. It then sends a second saved turn and asserts the first reply's reasoning checkpoint is replayed. The repo had no provider smoke matrix before. I did not extend the opt-in paid live harness: it appends messages with `persist=True` without a durable dispatch row, so it could not have caught this defect.
- Docs: `Docs/User_Guide/console.md` (Moonshot section) and a lesson in `backlog/docs/lessons-testing-evidence.md` on building fixture values with the producer.
