## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Moonshot (Kimi) setup ends with '✓ Provider — moonshot' and 'Start chatting', but every reply in a saved chat is generated and billed, then thrown away. The turn shows 'Provider continuation could not be persisted; retry or recover the interrupted run.' A recovery panel then falsely warns that delivery status is unknown and that a retry may send a duplicate request, and the composer stays blocked until the user discards the reply. The run record proves the provider answered: 'Model response completed' is logged 5 ms before the error. Temporary chats with the same model reply normally, and Anthropic and llama.cpp work, so the fault is in the persistent branch.

All four models Moonshot currently lists return reasoning content even on plain replies, so the provider adapter always builds a "complete" continuation checkpoint. Storing that checkpoint fails at a precondition somewhere between the controller's dispatch-recovery state and the chat store, and no current test drives that path; the store-level test for it passes. Six different continuation-error exits share one message, so nothing says which precondition failed.

This is the newly found P0 gap-02: roadmap item N6 and SF1 step 7 in §5 of Docs/superpowers/qa/first-run-wizard-ux-review-2026-10-02/README.md. No backlog task covers it. Coordination: this is not the TRACE_PROVENANCE pause that open PR #2975 fixes, and TASK-33662 only fixes Retry and Discard after a relaunch. Starting points on dev are the persistent path in Chat/console_chat_store.py (around lines 21040–21175) and the continuation handling in Agents/agent_runtime.py (around lines 1442–1456 and 2192–2235).
<!-- SECTION:DESCRIPTION:END -->
