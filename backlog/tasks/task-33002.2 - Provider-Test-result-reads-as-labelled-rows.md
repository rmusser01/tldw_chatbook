## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The Provider Test result is now five labelled rows, one fact each, drawn as lines in the existing `#settings-provider-test-result` Static. There is no `" | "` dump and no `model=`, `api_key_source=` or `configuration=` spelling anywhere.

**Approach**
- `SettingsScreen._provider_test_rows(readiness, *, display_name, model, endpoint, dirty, evidence, checking)` is the one pure function (spec §5; P5 can reuse it). The rows it returns:
  - **Config:** "<Provider> is configured", or "<Provider> is not ready: <reason>. <recovery>".
  - **Key:** "saved in config", "entered here, not saved yet", "from env var NAME [(draft)]", "missing (NAME is not set)", "not required" or the Claude-subscription state. A present key adds "· present, not verified", or "accepted by a generation test" when the evidence says so. The value is never shown.
  - **Endpoint:** `safe_endpoint_display(endpoint)` with "(draft)", then the model-listing outcome: checking, reached, unavailable, or "model listing failed (<category>) — <next step>". Per ruling 11 the listing outcome rides here, so the spec's five labels stay fixed.
  - **Model:** the model, or "not set — choose a default model", plus "listed by the server" or "not listed by the server — pick a listed model" after a reachable listing.
  - **Generation:** read from `evidence.generation`.
- **Order:** the failing row leads (AC#2), in this priority: Config not ready, then the listing unreachable, then no model, then generation failed. Otherwise the rows run Config, Key, Endpoint, Model, Generation.
- **Rendering:** `_build_provider_readiness_findings` renders `f"{label:<12}{text}"` lines, runs `redact_secret_text` over them, and builds the toast:
  - Config blocked or no model: the old "Configuration check blocked: …" (the Config text now uses the display name).
  - Failed listing: "Model listing failed (connection refused) — start the server or check the URL; generation not tested."
  - Reachable: "Configuration check complete: … Model listing reached; generation not tested." Generation is stated once (the rider).
  - Unavailable listing, and cloud without a probe: unchanged. The cloud toast is still pinned exactly.
- **Rebuilt, not appended:** `_provider_readiness_test_report(*, checking, probe)` rebuilds the rows from the one current evidence value. It uses the store's evidence for the draft identity, or the settled probe when the draft has no identity. The action sets the in-flight rows after `begin()` (`checking=True`), and `_apply_provider_endpoint_probe_outcome` rebuilds the rows and toast after settle.
  - `probes_when_passing`, `_provider_exact_evidence_copy` and the worker's detail/summary parameters are gone.
  - The probe-exception fallback is now a fixed line, "Configuration check could not finish; run it again.", because rebuilding the rows could raise again inside the worker.
- **TASK-486 (absorbed):** the Endpoint row goes through `safe_endpoint_display`, which drops user info, query and fragment. `_mask_url_userinfo` and `_provider_endpoint_summary` had no other callers and are deleted, so there is one redaction path.
- **Found while verifying:** Settings Overview's "Last connection test" row embedded the whole result. It now shows the leading row via `_provider_test_headline` ("Endpoint: http://… · model listing failed …").
- **Markup:** the result Static renders with `markup=False`, so IPv6 `[::1]` endpoints and the recovery copy's `[api_settings.x]` print literally.

**Rulings**
- Row order: fixed order unless something fails, and then the failing row leads. The alternative, a Config row that carries the probe failure, would put two facts in one row.
- An endpoint with user info shows "invalid endpoint". That is `safe_endpoint_display`'s answer, and the endpoint contract rejects user info.
- Pins go through `screen._provider_display_name(...)` or display names that TASK-33002.5 does not change (OpenAI, Ollama, Anthropic), per ruling 15.
