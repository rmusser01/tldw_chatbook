## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: the note editor's feedback is often wrong about what just happened, and the note lifecycle has gaps at both ends. A keyboard user (Sam) who changes their mind is told something failed and is left one Enter from Delete. A power user (Alex) re-filing ten notes pays about 120 keystrokes. A stress tester (Riley) is sent looking for a button that is not there. A first-timer (Jordan) reads backlinks that belong to a different note. A note with sensitive content can never be purged. Each has a workaround, hence P2. Causes are at origin/dev 2d34cbf80d.

N-12, cancelling an export is reported as a failure, and focus lands on Delete. The steps are Info > Export Markdown > Enter, then Esc in the file dialog. The status line then reads 'Saved · Export failed — choose another destination and try again. · Next: Review the error, then keep editing.' and Info repeats 'Export failed — …'. At the same moment, a toast says 'Note export cancelled.' and focus sits on '┃ Delete ┃' with the footer 'enter delete note'. Verified cause: a dismissed dialog (no selected path) is finished as success=False with a failure next-action (UI/Screens/library_screen.py:21136-21144). The verifier found the focus jump has a second cause: while the export runs, the button that started it is disabled, so focus falls through to Delete. This also happens after a successful export or a Copy. The finding was lowered to P2 because Delete still opens a confirm with Cancel focused. Suggested direction: treat no path as a cancellation with no failure copy and one quiet signal. After any outcome, return focus to the button that started the operation.

N-14, select mode can only export, and 'Select all N shown' miscounts. Existing task TASK-32635 owns bulk delete: confirm or undo, the count, lasting-sync handling, and matching Media's select grammar. This task covers only the remainder. With about 13 rows visible, the strip reads '20 selected   Done   Select all 100 shown   Clear   Export selected'. In the journey, pressing 'Select all 100 shown' produced '26 selected'. Verified cause: the label falls back to the flat row list when no tree projection exists (Widgets/Library/library_notes_canvas.py:1838-1846). The handler instead builds a fresh projection and selects the note rows in it (UI/Screens/library_screen.py:30120-30140). Space does nothing in select mode, so each row costs Enter+Down, and Export is the only bulk action. Suggested direction: compute the label from the ids actually rendered ('Select all 20 loaded'). Let Space toggle the focused row, copying Media's priority binding. Add an 'Actions…' chooser with Move to folder and Add/Remove keyword. Delete is left to TASK-32635.

N-25, the leave-veto toast names a button that is not on screen. On an existing note whose title has a trailing space, Esc shows the toast 'Can't leave yet — fix the title or press Discard new note.' The status reads 'Title begins or ends with whitespace — remove it to save.', and the word 'Discard' appears nowhere on screen. A duplicate-keyword veto gets the same title-blaming sentence. Verified cause: _library_note_editor_exit_veto_message (UI/Screens/library_screen.py:909-921) returns one fixed string for every validation veto. That string was the copy TASK-32133 AC#1 (Done) required, and this finding refines it now that the veto carries its own field and reason. Suggested direction: build the toast from the veto's field and reason, and mention 'Discard new note' only while that control is visible.

N-26, a new note's Info shows another note's backlinks, or never resolves. After the user opened a note that 'Index — start here' links to and then pressed n, the fresh note ('VB2 second note', 0 words) showed 'Linked from (1)  Index — start here'. On a fresh Blank note opened directly, Info stays at 'Linked from — checking…' until the note is reopened from the list. Code-traced cause, not separately verified: the create path (UI/Screens/library_screen.py:30847-30882) never resets the backlink facts and never runs the backlink lookup. Only the open path does (UI/Library_Modules/library_notes_controller.py:3452-3468), and the default status is 'loading' (UI/Library_Modules/library_notes_state.py:524). Suggested direction: reset per-note facts in one place, used by both create and open. A brand-new note has no inbound links and should show that as a settled fact. Its location fact should be reset too.

N-29, 'Recently deleted' can never delete permanently, and lists only the newest 20. The view says 'Deleted notes stay here until you restore them. Restore puts a note back where it was; nothing is removed for good from here.' Restore is the only action, while Media Trash offers 'Delete forever'. The verifier found only the newest 20 deleted notes are listed, with no pager. This revisits a recorded ruling: TASK-32144 (Done) fixed 'no permanent delete' and a single 20-row page. An owner ruling is therefore needed before the permanent-delete half is built. Suggested direction: 'Delete forever' on key x, as in Media, with an ADR-055 Pattern B confirm naming the title. It needs a hard-delete path that also removes the note's search index entries, keywords, folder memberships, versions and sync-log rows. Notes bound to a lasting-sync root are refused, or the user is warned first. Add an ADR-067 pager.

Review finding(s): N-12, N-14, N-25, N-26, N-29. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Acceptance Criteria

- [ ] #3 (N-14) The select-mode 'Select all' label states exactly how many notes it will select, and pressing it selects that many. This holds after returning from Export and with a filter applied
