## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-33620.15.1.3 stopped the Console Environment panel from building a whole turn configuration to find its workspace root. Each refresh still reads the root twice on the UI loop: once in request_refresh, and again when _land's stale-scope guard checks the scope it was just given. Each read is a Change Review consent lookup, a SELECT on the workspace registry database.

Measured live on 2026-10-22 (isolated profiles, Anthropic claude-haiku-4-5, 235x52; host load 30-43 on 14 cores, so 2-3x oversubscribed). Each refresh over 50 ms was these two reads and nothing else, for example 64.5 + 47.8 ms in a 113.1 ms rail open. In 3 of 9 rail opens the refresh held the loop for more than 100 ms (102.1, 103.4 and 113.1 ms). At run completion it reached 59.4 ms. The capability read took 0.0-0.1 ms and there was no lock wait, so the time was the database read itself: median 1.07 ms, p90 42.3 ms, max 64.5 ms (n=38). At load 5-9 on 2026-10-20 the same refreshes stayed under 34 ms. Evidence: uxrev/evidence/bd5/LENV (aggregate.txt).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: the Environment panel no longer reads its workspace root on the UI loop for any automatic refresh, and its landings never read it there. The stale-scope guard still drops a landing whose root changed in the app at any point before it lands, now from an in-memory scope stamp instead of a database read. Each root read is a Change Review consent lookup, a SELECT on the workspace registry database.

Approach (`tldw_chatbook/UI/Console_Modules/environment.py`):
- The automatic refreshes (rail open, run completion and focus regain through `request_refresh()`, and the 10 s `poll_tick`) read the root on a worker (`ROOT_WORKER_GROUP`, through `read_root_off_loop`, which runs the read as a finite local worker so the worker's registry connection is retired again) and continue on the UI loop with the answer (`_root_read`). Within one scope, reads rank by issue order: an older read answered after a newer one acts on the newer answer. The rail guard is applied again when the answer arrives.
- An explicit Refresh press (`force_net=True`) keeps ONE read on the UI loop, because its acknowledgment (`pending_ack_tiers`, TASK-31664) is decided against the root at the press and the screen reads it right after the call. AC#1 allows one; measured live at 1.3-2.3 ms in a bound workspace.
- Stale-scope guard (AC#2), with no UI-loop read. Each gather worker takes the screen's scope stamp, then re-reads the root after gathering. `_land` drops a landing whose scope differs from that read, from the newest root any refresh determined (`_observed_root`), or whose scope stamp has moved since the worker took it.
- The scope stamp (review follow-up, 2026-10-27). `Console_Modules/wiring.py::environment_scope_stamp` names everything the root accessor reads, from memory: the chat controller, the active session, and `session_change_review_admission_stamp` (in `Chat/console_turn_context.py`: the session's workspace, the registry's `mutation_generation`, which consent service answers, and its new `admission_revision`). `ChangeReviewConsentService.admission_revision` moves on a consent toggle, a root finishing or failing preparation, readiness discarded or a ready root rescheduled, and shutdown; never on a read, including the first read that only schedules preparation. Live it cost 0.003 ms median and 0.872 ms max per read on the UI loop (n=113).
- Why the stamp: the first version covered only a change seen by the worker's re-check or by a later refresh. Review reproduced the hop between the re-check and the landing on the UI loop: with the root changed to another folder, or consent revoked, in that hop, the old root painted and, for a local landing, its deferred `gh` fetch was issued for the abandoned folder. Both now drop.
- A root answer whose stamp moved before it reached the UI loop is read again, once, rather than acted on (the unbound landing is made from that answer). An answer overtaken twice is left to the next refresh. Under a moved stamp, an older read taken under the current stamp outranks a newer overtaken one. An unreadable stamp falls back to the root comparisons, so it can never stop the panel landing.
- Not covered: a change made outside the app in that hop (another process writing the registry, a bound folder removed on disk, the global `TLDW_CHANGE_REVIEW_ENABLED` capability) moves no stamp. The next refresh corrects it, as it does a change made just after a landing. This is the same in-process contract the registry's own caches keep (`mutation_generation`).
- First design (one read kept on the loop at dispatch, only the guard's read moved into the worker) met AC#1 as written but not AC#3: at load 36-47 that one read still held a rail open 104.5 ms and two poll ticks 145-146 ms, with 2-14 ms of thread CPU (evidence P16/designI). Lessons entry in lessons-live-verification.md; the hop gap has its own entry in lessons-console-wiring.md.
