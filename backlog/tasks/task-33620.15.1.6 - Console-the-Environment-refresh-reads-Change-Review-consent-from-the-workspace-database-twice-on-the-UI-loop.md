## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-33620.15.1.3 stopped the Console Environment panel from building a whole turn configuration to find its workspace root. Each refresh still reads the root twice on the UI loop: once in request_refresh, and again when _land's stale-scope guard checks the scope it was just given. Each read is a Change Review consent lookup, a SELECT on the workspace registry database.

Measured live on 2026-10-22 (isolated profiles, Anthropic claude-haiku-4-5, 235x52; host load 30-43 on 14 cores, so 2-3x oversubscribed). Each refresh over 50 ms was these two reads and nothing else, for example 64.5 + 47.8 ms in a 113.1 ms rail open. In 3 of 9 rail opens the refresh held the loop for more than 100 ms (102.1, 103.4 and 113.1 ms). At run completion it reached 59.4 ms. The capability read took 0.0-0.1 ms and there was no lock wait, so the time was the database read itself: median 1.07 ms, p90 42.3 ms, max 64.5 ms (n=38). At load 5-9 on 2026-10-20 the same refreshes stayed under 34 ms. Evidence: uxrev/evidence/bd5/LENV (aggregate.txt).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: the Environment panel no longer reads its workspace root on the UI loop for any automatic refresh, and its landings never read it there. Each root read is a Change Review consent lookup, a SELECT on the workspace registry database.

Approach (`tldw_chatbook/UI/Console_Modules/environment.py`):
- The automatic refreshes (rail open, run completion and focus regain through `request_refresh()`, and the 10 s `poll_tick`) read the root on a worker (`ROOT_WORKER_GROUP`, through `read_root_off_loop`, which runs the read as a finite local worker so the worker's registry connection is retired again) and continue on the UI loop with the answer (`_root_read`). Reads are numbered in issue order: an older read answered after a newer one acts on the newer answer. The rail guard is applied again when the answer arrives.
- An explicit Refresh press (`force_net=True`) keeps ONE read on the UI loop, because its acknowledgment (`pending_ack_tiers`, TASK-31664) is decided against the root at the press and the screen reads it right after the call. AC#1 allows one; measured live at 2.3 ms in the bound workspace.
- The stale-scope guard (AC#2) no longer reads on the UI loop. Each gather worker re-reads the root after gathering; `_land` drops a landing whose scope differs from that read, or from the newest root any refresh determined (`_observed_root`). The synchronous unbound landing is checked against the read that chose it.
- One edge moved: a root change made after the worker's re-read and before the landing reaches the UI loop, with no refresh observing it in between, now lands the old root's freshly gathered data until the next refresh, which is what a change made just after a landing always did. Once any refresh has seen the new root, an old landing is dropped.
- First design (one read kept on the loop at dispatch, only the guard's read moved into the worker) met AC#1 as written but not AC#3: at load 36-47 that one read still held a rail open 104.5 ms and two poll ticks 145-146 ms, with 2-14 ms of thread CPU (evidence P16/designI). Lessons entry added in lessons-live-verification.md.
