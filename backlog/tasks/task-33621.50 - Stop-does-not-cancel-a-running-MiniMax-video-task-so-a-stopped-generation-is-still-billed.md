## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in PR #3006's live check (2026-10-04, real MiniMax). Pressing Stop about 40 s into a /generate-video run logged 'MiniMax remote task cancel failed; local stop still honored (error_type=HTTPStatusError)'. The app stops locally, but the remote task is not cancelled, so the generation is probably billed in full. Docs/User_Guide/console/video.md says a queued MiniMax task 'is cancelled remotely and does not bill to completion'. The adapter's docstring says a task already running cannot be cancelled. Whether MiniMax offers any cancel for a queued or running task, and whether the request the adapter sends is right, is unverified.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: MiniMax does offer cancellation, and the adapter's request was already right; what was wrong is that Stop never said what happened. Stop now reports MiniMax's answer, and a refused cancel says plainly that the task keeps running and may still be billed.

AC#1, measured (2026-10-30, api.minimax.io, repo-root key, pure-httpx probe sending the adapter's exact DELETE /v2/video_generation/{id}, Bearer + Content-Type: application/json, no body; docs: https://platform.minimax.io/docs/api-reference/video-generation-v2-delete). Accepted ~1 s after submit and right after a poll read status=running: 200 {action: cancelled, status: cancelled}, and the task's usage stayed empty. Refused 43 s into running: 400 bad_request_error 'task in current status can not be cancelled or deleted (2013)'. That task kept running, succeeded at ~93 s and was billed (usage output_seconds=4). A DELETE on a cancelled task gives the same 400/2013. A DELETE on a succeeded task gives 200 {action: deleted}. The docs say running cannot be cancelled, but in practice a task that has just started is cancellable, and the API reports both stages as 'running'. That 400 is the incident's HTTPStatusError. Live spend was one 4 s clip in the probe and one 5 s clip in the app check, about $0.72; the other runs were cancelled at no charge.

Approach:
- New VideoGenerationCancelled(VideoGenerationError) carries remote_cancel = cancelled | refused | unconfirmed. MiniMax's _cancel_task classifies the DELETE answer: refused = 400 with code 2013; a 'deleted' record or any other error = unconfirmed, so a cancel is never claimed unless MiniMax confirmed one. It logs the HTTP status and error code: closed values, never the key.
- The Console's generate and regenerate handlers catch the cancellation before the failure handler and post the outcome row (helpers video_stopped_text and video_generating_text in Chat/console_generate_video.py). The cost confirm and the 'Generating video' row say Stop cancels only until MiniMax starts rendering.
- Docs/User_Guide/console/video.md is rewritten to match. The diagnostic registry and inventory are updated after review; every new field is a closed value.

Tests: Tests/Video_Generation/fixtures/minimax_cancel_recorded_2026-10-30.json holds the recorded bodies verbatim (CDN URL redacted). Four adapter tests in test_minimax_adapter.py replay them through the real fetch_json over MockTransport and pin the request (method, URL, headers, empty body). Tests/UI/test_console_video_stop_outcome.py drives the real app Stop button, controller, store, adapter and fetch_json; it is tail-appended to the UI PR gate census. All new tests failed on origin/dev 1eaa6a9429: 'Video generation failed (VideoGenerationError)', no billing caveat, no typed cancel. The only exception is the failure control, which passes on both, as it should. Six mutants of the fix were each caught.

Live (real app, isolated profile, real MiniMax key; evidence in the session's tools/evidence/bd5/U21/live): the cost confirm showed the caveat. Stop about 0.3 s after Generate gave 'Video generation stopped. MiniMax cancelled the remote task, so it is not billed.' (log: cancel confirmed). Stop about 54 s in gave '...MiniMax had already started rendering and refused to cancel. The remote task keeps running and may still be billed.' (log: http_status=400, error_code=2013).
