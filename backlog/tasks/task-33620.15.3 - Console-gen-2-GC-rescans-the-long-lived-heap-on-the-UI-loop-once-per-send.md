## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by live profiling on 2026-10-10 (160x45, Anthropic haiku through the review proxy, 56 sends over 10 launches; a PYTHONPATH-only probe timed every UI-loop callback of 10 ms or more, timed every collection per thread with `gc.callbacks`, and sampled the main thread every 4 ms). After a Console send is accepted, the longest UI-loop blocks are Textual screen updates, and 54% of that time is Python's generation-2 collection on the main thread: about 70 ms per send window, with single pauses of 23-65 ms at up to 16 turns and 78-122 ms at 31-46 turns (max 266-324 ms).

ADR-198 freezes the heap only at `_ui_ready` and after the screen pre-import. Every gen-2 pass therefore rescans everything the Console built after boot (about 590 widgets at about 50 turns, the transcript, the stores), and one runs about once per send. Within a launch the pauses grew with every send (36 ms on the first, 121 ms by the fifth). Worker-thread gen-2 passes (52-87 ms) hold the GIL as well.

Counterfactual on the same data: removing the main-thread collections alone takes the median longest loop callback after acceptance from 95 to 72 ms, and the sends with a block of 100 ms or more from 15/30 to 6/30. Together with moving the config projection's I/O off the loop (TASK-33620.15.4) it is 48 ms.

The risk to design for: `gc.freeze()` moves objects to the permanent generation, and frozen objects that later become unreachable cyclic garbage are never collected. Textual widgets are cyclic, so a conversation switch, a transcript trim or a recompose can leak whatever was frozen while it was live.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Main-thread gen-2 GC time in the send window (Enter to the provider call) drops against origin/dev, measured live with paired, interleaved sends in a chat of 30 or more turns
- [ ] #2 In the same live pairs, the longest UI-loop callback in the send window does not regress, and sends with a callback of 100 ms or more do not increase
- [ ] #3 Memory stays bounded: across 20 or more conversation switches and 10 or more run cycles, the permanent generation, the tracked-object count and RSS show no unbounded growth against origin/dev (measured)
- [ ] #4 Re-freezing never runs inside a send window or within a quiet period after user input; the collector is never disabled and CPython's default thresholds are kept (ADR-198 rules)
- [ ] #5 Deterministic tests pin the re-freeze points (a conversation painted, a run settled) and that nothing runs while a send is in flight or input is recent
- [ ] #6 A deterministic leak test shows that widgets frozen while live and removed later are reclaimed (their weakrefs die) by the bounded compaction, with a negative control
- [ ] #7 ADR-198 is amended with the idle re-freeze policy and its leak bound; the ADR-097 UI-ready module census and the boot CSS budget are unchanged or improved
