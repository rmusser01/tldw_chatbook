## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-33620.15.57's live round b1 (2026-11-06, dev 2684e5453f against the fix, 36 blocks). With the host at least 15% idle, the fix's first sends ran less generation-2 time on the UI loop between Enter and the provider POST than dev's (median 6.7 ms against 15.4). At 0% idle, though, the fix's four largest totals were 95-170 ms of wall time and 36-50 ms of CPU, each from two passes. In the same blocks, dev and the revert ran one pass, or two in one dev launch, for 9-28 ms of CPU. The fix's Enter to POST in those 16 loaded blocks was still a paired median 108 ms sooner than dev's. A likely cause, not measured: the warm-up's completion now re-freezes as the warm-up ends, so what the next 2 s allocate stays unfrozen until the first reply's maintenance. Dev's timer froze it at +2 s. The b1 probe did not count unfrozen objects, so this is unattributed. TASK-33620.15.57's review recomputed the same span over every generation: below 15% idle, the fix's four largest main-thread GC totals were 154, 162, 169 and 344 ms, against maxima of 134 (dev) and 139 (revert), and paired fix-minus-dev differences were +64 to +268 ms in 5 of 36 blocks. The paired median (-1.8 ms) does not show this tail, so the tail is what this task must settle.
