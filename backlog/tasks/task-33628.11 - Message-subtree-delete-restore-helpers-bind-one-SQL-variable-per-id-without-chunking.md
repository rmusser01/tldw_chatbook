## Description

<!-- SECTION:DESCRIPTION:BEGIN -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**AC#1 (verified; boundary test added).** PR #2965 already batches the three id-list helpers through `CharactersRAGDB._bounded_id_batches` (min(500, the connection's live `SQLITE_LIMIT_VARIABLE_NUMBER`)): the delete-proof capture inside `soft_delete_message_subtree`, `get_message_tombstones`, and `restore_message_subtree`'s version read (its writes are one row per statement). New `Tests/DB/test_message_subtree_delete_bounds.py::test_delete_and_restore_bind_ids_within_the_variable_limit` runs delete -> tombstone read -> Undo with the limit set to 16, at exactly 16 ids and at 17. Teeth, proved out of tree by monkeypatching `_bounded_id_batches` to yield one batch: the 17-id case and #2965's store-level `test_flat_delete_and_undo_past_the_sqlite_variable_limit` both fail with `sqlite3.OperationalError: too many SQL variables`; the 16-id case passes.

Sweep of the other delete/restore/tombstone paths found no unchunked per-id list: `soft_delete_message_subtree` binds its seeds as one JSON array (`json_each`); `_attach_chat_delete_base_hashes` and the restore UPDATEs are per row; the store's edit purge and sync projection go through `get_message_tombstones`; `RecoveredMessageReferences.release` pages by 200 and `message_references_exist` by `_MESSAGE_LOOKUP_BATCH`; the voice-pair locator probe binds two ids.

**AC#2.** The edit-invalidated descendants CTE in `_update_message_uncoordinated` (content edit without `preserve_descendants`, both the proof SELECT and the UPDATE) had an indexable `conversation_id = ?` in its seed and recursive steps. With no `sqlite_stat1` the planner chose `idx_messages_conversation_id_id` for both, scanning the whole conversation once per descendant. Unary `+` on both terms (as #2965 did in `soft_delete_message_subtree`) moves every step to `SEARCH ... USING INDEX idx_messages_variants_by_parent (parent_message_id=?)`; the predicate and its conversation scope are unchanged. Editing the second message of a 3,000-message chain (2,998 descendants tombstoned): 12.99 s on dev, 0.15 s here (in-memory DB, one run each).

Pin: `test_edit_descendants_delete_searches_children_by_parent_without_statistics` asserts `sqlite_stat1` is absent, a non-empty plan, exactly two row-reaching steps per statement, each `SEARCH ... USING INDEX idx_messages_variants_by_parent (parent_message_id=?)`, and the conversation index absent from them. RED on dev code (fix reverted with `git apply -R`): `SEARCH messages USING INDEX idx_messages_conversation_id_id (conversation_id=?)`. The planner picks `idx_messages_variants_by_parent` over the equivalent `idx_msgs_parent`; its census row in `scripts/index_plan_pin_census.tsv` moves from pre-convention to plan-pinned (`scripts/check_index_plan_pins.py`: OK). A scope test keeps a malformed cross-conversation child live, and a preserve_descendants test keeps the tail.

No schema change, no new index. Related suites (resume/rewind/trace/canvas/search-projection/delete persistence): 114 failures on both dev code and this branch, identical names (environment: `RecoveryRequired: raw_source_selection_changed`, hooks unavailable, canvas disabled); zero branch-only failures.

Files: `tldw_chatbook/DB/ChaChaNotes_DB.py`, `Tests/DB/test_message_subtree_delete_bounds.py`, `scripts/index_plan_pin_census.tsv`.

**Review follow-ups (checkpoint review).** AC#2 was reworded. Its old text ("uses the indexable conversation-scoped step") came from the description's wording; #2965 (`0598cabe69`) made `soft_delete_message_subtree`'s conversation term NON-indexable (unary `+`) so a parent index drives every step, and this change does the same. The criterion now states the shape the plan pin asserts. Kept as is: the pin names `idx_messages_variants_by_parent` exactly, although `idx_msgs_parent` also leads with `parent_message_id`. The census row marks that one index plan-pinned, and a test that accepted either index would no longer back that row; a planner tie-break flip on another SQLite build would fail loudly and is a one-line fix.
