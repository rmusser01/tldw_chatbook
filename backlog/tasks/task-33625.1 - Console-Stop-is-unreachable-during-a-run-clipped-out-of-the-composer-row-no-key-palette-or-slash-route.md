## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** While a run is active, the expanded composer never paints Stop at any width. Live checks at 80x24, 120x40, 160x45 and 235x52 with a slow proxy all showed the row ending `Queue  Dictate  Redir`, with `Stop` appearing 0 times on screen. Stopping a runaway, wrong or expensive agent run (which may be executing tools) is the core recovery action on a live work surface, and DESIGN says to "make cancellation available". The User Guide (`Docs/User_Guide/console/chat-basics.md:325`) says Stop appears "between Send and Mic", which is false.

**Verified mechanism.** The action row has a fixed budget of 33 cells (`BASE_ACTIONS_WIDTH` 25 plus Send width 14 minus 6) in `tldw_chatbook/Widgets/Console/console_composer_bar.py`. Send (14), the gap (2) and Dictate (11) use 27 of them. That leaves 6 cells for Redirect (10 cells), which is cut to `Redir`, and 0 for Stop (6 cells). Stop is composed last, so clipping always removes it first.

Keyboard access is also broken:
- Tab reaches the clipped Stop, but it shows no visible focus.
- Enter on it does not stop the run, because `ChatScreen.on_key` sends Enter from any composer descendant to the send path (log: `phase=ui_action status=not_dispatched`).
- There is no stop key binding. Esc, Esc and Ctrl+C do not stop a run.
- Ctrl+P "stop" lists nothing relevant, and there is no `/stop` command (`/emergency-stop` only holds new runs).
- The `stop` WorkbenchAction is filtered out of the header by `TOP_ACTION_IDS`.

The only working route is undocumented: collapse the composer, and the strip then shows `Composer hidden - Generating ... Stop`. The idle-style `Send disabled: …` text also sits next to a button labelled `Queue`.

**Severity / prior art.** P0. This is a **REGRESSION of TASK-28227 (Done)**. Its AC#5 says "Plain Stop ... behaves exactly as today", and it added Redirect "next to Stop (visibility synced with Stop)" (commit 42d9b7b737) without budgeting for it. It also breaks the contract of TASK-1680 (Done): the row is width-bounded, carries Send/Stop/Mic, and new actions must not grow it. Verdicts: live PARTIAL, code CONFIRMED, skeptic CONFIRMED.

**Suggested direction.**
- Make the row budget run-aware and derive it from the controls actually shown.
- Place Stop first after the draft, or swap it into Send's slot while running, with warning styling, so clipping can never remove it.
- Budget Redirect explicitly, or drop Dictate while running.
- Stop the composer Enter capture from swallowing Enter on a focused composer Button.
- Add a stop route for the viewed tab's run: a key shown in the footer only while running, a palette command, and `/stop`.
- Say "Type to queue" instead of the Send-disabled reason while running.
- Fix chat-basics.md.

The cross-region width-priority model belongs to the Theme 5 umbrella task. This task only guarantees Stop and Redirect inside the composer row.

TASK-33625.1 — Implementation Notes

Stop is reachable again while a run is active. The composer's action row had a fixed 33-cell budget (Send + gap + Dictate + Stop), and TASK-28227 showed Redirect beside Stop without adding Redirect to it. So Redirect was cut to "Redir" and Stop got 0 cells at every width.

Changes:
- Row budget (`console_composer_bar.py`):
  - Redirect has its own cells (`REDIRECT_ACTION_WIDTH`). They are reserved only where the draft keeps its minimum width and the widest reason text still fits (`_redirect_fits`, about 150+ columns). They stay reserved while idle, as Stop's always were, so Send and Dictate never move when a run starts or ends.
  - Narrower rows keep Send/Dictate/Stop, and Redirect is reached through /redirect or the palette.
- Focus: a Tab-focused Stop now shows the shared focus style (`_console.tcss`). A pressed, disabled or hidden composer button hands focus to the draft (`ComposerControlButton`).
- Keyboard routes, in the new `UI/Console_Modules/composer_run_controls.py`:
  - Ctrl+G, shown first in the footer and only while `stop_available`;
  - `/stop`, which clears itself from the draft;
  - "Console: Stop this tab's run" and "Redirect this tab's run" in the palette.
- The Redirect button handler moved into the same module.
- Reason text (`build_console_disabled_reason`) names the queue state: "Type to queue", "Queue opens once this turn is accepted", "Queue full — manage it to make room". The queue state arrives as `queue_blocked_reason`, so it no longer masks a real setup or attachment blocker, nor links to the wizard.
- The User Guide (chat-basics.md, console.md, agent-runs-and-tools.md) now says where Stop, Redirect and Ctrl+G actually are.
- `chat_screen.py` only wires these in: 25435 → 25415 lines, 762 methods unchanged.

Tests: Tests/UI/test_console_composer_run_controls.py covers geometry at 80/120/160/235 columns, Tab to Stop then Enter/Space, the footer key, /stop, the palette and the reason text. It fails on 857b3dd7d0 ('Stop falls outside the (80, 24) screen: Region(x=83…)') and passes on the branch. Live checks passed at 80x24 and 235x52: clicking Stop, Tab then Enter, Ctrl+G, /stop and the palette each stopped a run.

Trade-offs and follow-ups:
- Redirect is hidden below about 150 columns; showing it at narrower widths is left to the owner.
- A stop during the pre-provider "Connecting tools…" phase leaves the next prompt refused as "Unsent turn needs attention". This is a pre-existing controller defect that also reproduces on dev; follow-up recommended.

TASK-33622.2 — Implementation Notes

A focused composer-bar button now handles its own keys. Before, `ChatScreen._should_capture_console_input` treated every composer descendant as the draft (apart from TASK-15704's three-id allowlist), so Enter on Menu, Dictate or Redirect went down the paid send path.

Changes:
- Key routing (`route_composer_control_key` in the new `UI/Console_Modules/composer_run_controls.py`):
  - Enter and Space fall through to the focused button's own bindings; `ComposerControlButton` binds Space.
  - Plain typing is dropped.
  - Paging and undo/redo keep their composer-wide routing.
- The TASK-15704 allowlist is gone, so every button follows one rule.
- Only the draft paints a caret (`draft_has_focus`). The caret cell is still reserved while focus is anywhere in the composer, so tabbing onto a button never resizes the bar.
- Focus handling: when the key-routing change went in, it exposed a focus leak that the old capture had hidden. Textual focuses a Button on mouse-down and passes a disabled button's focus to a sibling, so after clicking Send the next prompt was dropped and its Space started dictation. Now `ComposerControlButton`:
  - presses on click without taking focus;
  - hands focus to the draft synchronously when it is disabled or hidden;
  - and Redirect hands focus back when pressed.
- New palette entries, each checked against the menu's own availability rules (`run_composer_menu_action`): Open composer menu, Attach file…, Save as Chatbook, Impersonate, Improve current draft….

Tests: in Tests/UI/test_console_composer_run_controls.py, all on the real ChatScreen and failing on 857b3dd7d0 ('Enter on the focused Menu did not open the Composer actions menu', 'draft still paints its caret while Menu holds focus', 'Enter on the focused Redirect did not run Redirect'):
- Enter on Menu (focus lands on the first item), Composer ▾, Expand, Send, Dictate, Queue, Redirect and the collapsed Stop;
- keys never edit the draft, and there is no caret while a button has focus;
- click or Enter on Send, then typing;
- Menu click then Escape then typing, Dictate click, Enter on ✕;
- undo passthrough;
- the palette entries.

Live at 235x52: Enter on the Tab-focused Menu opened Composer actions and logged no send stage; the palette's "Open composer menu" works.

Trade-off: while a button has focus, the draft placeholder renders brighter (#e1e1e1) than when the draft has focus. This is cosmetic.
