## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The idle heap re-freeze and its compaction (TASK-33620.15.3) freeze the heap only after a full collection really ran, judged by CPython's generation-2 pass count moving across the gc.collect(2) call. If a worker thread's generation-2 pass finishes between the before and after reads while the UI thread's own call was skipped, the count still moves, and a compaction whose collection never ran is recorded as done: frozen garbage is frozen again and stays until the next compaction. The damage is bounded (the next compaction reclaims it) and was never observed live, but the check proves only that some pass completed, not that this call's pass ran.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: the idle refreezer now accepts a re-freeze or compaction only when its own gc.collect(2) ran a full pass on the calling thread. Before this, the process-wide generation-2 pass count could move because another thread's pass finished.

Measured first (3.12.11, pure-CPython probe): a worker thread's gen-2 pass was held at its start hook while the UI thread called gc.collect(2). The call returned 0 and no callback fired on the UI thread. The pass count still went 0 -> 1 once the worker finished before the after-read, so the old check booked a collection that never ran.

Approach: `_collect_in_full` (Utils/ui_responsiveness.py) calls `_full_pass_ran_here()`. That function installs a `gc.callbacks` watcher for the duration of one `gc.collect(2)` and accepts the call only if a generation-2 "start" and "stop" fire on `threading.get_ident()` of the caller. The watcher is installed per call, not permanently, so young collections pay nothing. The retry loop (5 tries, 2 ms apart) and the CollectorBusy semantics are unchanged. The collector is never disabled and its thresholds are untouched; the new test asserts both.

Tests (Tests/Performance/test_gc_idle_refreeze.py): `test_a_worker_threads_pass_ending_inside_a_skipped_call_is_not_booked[refreeze|compaction]`. A real worker thread's full pass is held open and finishes inside every gc.collect call, so each call is skipped. The maintenance must report busy: nothing is frozen in the refreeze arm, and the compaction stays owed in the compaction arm. Negative control: the pass count moved across every call. RED on the pre-fix code: 'refreeze' / 'compact' was booked over 1 skipped call. The `counting_collector` fake now fires gc.callbacks the way a real pass does.

Docs: ADR-198 amendment paragraph; lessons-testing-evidence follow-up to the TASK-33620.15.3 gc.collect lesson (the pass-count check it recommended is process-wide).
