## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`chat_with_kobold` posts KoboldAI's native payload to whatever URL is saved for KoboldCpp. Dev's endpoint contract reads a typed server root such as `http://localhost:5001` as the OpenAI-style `/v1/chat/completions` (TASK-35010/35832; the owner's NO-1 ruling of 2026-10-20, pinned by `Tests/UI/test_settings_saved_lists_follow_file.py:670-674`). Since TASK-36516 and TASK-38964 (both Done, 2026-11-05), the wizard and Settings refuse such an endpoint rather than save it. The refusal line reads "KoboldCpp needs its native /api/v1/generate address. For an OpenAI-compatible server, choose Custom instead." (`KOBOLDCPP_NATIVE_ROUTE_REFUSAL` and `koboldcpp_route_refusal`, Provider_Contract/provider_endpoint_contract.py:691-721). Nothing unusable is saved any more. But a user who typed the bare address must retype the full route by hand, and the refusal does not show it.

**Owner ruling 2026-11-28: add a one-press fix; keep the refusal.** When the refusal fires for a typed KoboldCpp root, the refusal line offers one action, "Use http://<host>:<port>/api/v1/generate", in first-run setup and in Settings. The route comes from `koboldcpp_native_endpoint` (provider_endpoint_contract.py:724-745), which the model switcher already uses when it adopts a server (UI/Console_Modules/model_switcher.py:955-956). The endpoint is never rewritten silently: only the user's press changes it. The refusal, its copy and its pinned test stay as dev settled them. (This replaces the task's original outcome, a typed root silently saved as the native route, which conflicted with that settled refusal.)

Where the refusal is shown today:
- Setup's Provider step: UI/Wizards/first_run_setup_state.py:393, first_run_provider_detection.py:393/:433 and first_run_provider_step.py:753-760.
- Settings ▸ Providers & Models, while typing: UI/Settings_Modules/providers_models_card.py:885, through `typed_endpoint_refusal` (Chat/provider_setup_persistence.py:280-304).

Live verification needs a real KoboldCpp server. None is on this machine as of the 2026-11-28 re-triage. KoboldCpp publishes macOS builds that run GGUF models such as the QA ones (not tried here). llama-server is not an honest stand-in, because it does not serve KoboldAI's native `/api/v1/generate` route that `chat_with_kobold` posts to. If no real KoboldCpp can be run, the live AC records that, and nothing mocks it.
