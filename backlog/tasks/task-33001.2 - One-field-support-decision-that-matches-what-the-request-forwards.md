## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
For Anthropic, the Console modal shows Min P, Seed, Presence and Frequency like supported fields (Widgets/Console/console_settings_modal.py:1976-2017). But PROVIDER_PARAM_MAP['anthropic'] carries none of them (Chat/Chat_Functions.py:281-300), and project_chat_handler_kwargs forwards only mapped keys, so the values are dropped with no warning (:1431-1435).

Root cause: _supported_console_settings_fields (Chat/console_chat_controller.py:774-802) starts from every field in FULL_MODEL_DEFAULT_FIELDS and gates only the reasoning and thinking fields. The projection exists three times, and the copies drift independently:
- The controller copy above.
- _supported_profile_fields (Chat/console_settings_defaults.py:344), which the model-default writer uses at :1237. Its docstring says it mirrors the controller.
- Settings' _model_profile_field_supported (UI/Screens/settings_screen.py:12596), which returns True for every sampler.

The spec names the single replacement supported_generation_fields(): the existing capability projection intersected with PROVIDER_PARAM_MAP. Watch the mapping trap: the Console request sends top_p under both 'topp' and 'maxp' (Chat/console_provider_gateway.py:5138-5139), and OpenAI's map carries only 'maxp'. A provider with no map entry must keep today's field set (TASK-30012 AC#3).

This task fixes the data. The one-line 'hidden for <provider>' summary in the Console modal is layout work outside this phase. Settings already shows 'Unavailable for <provider>' on unsupported model-profile rows (settings_screen.py:12602-12608), so the fix becomes visible there with no layout change.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- One decision: `supported_generation_fields(provider, model)` in Chat/console_provider_support.py returns the capability rules (moved verbatim from the controller: Moonshot/Z.ai model-gated reasoning, OpenAI/QwenCloud direct fields, Anthropic thinking with the model-gated fixed budget, local thinking by execution key) intersected with the provider's `PROVIDER_PARAM_MAP` entry. `GENERATION_FIELD_REQUEST_KEYS` there is the only field-to-request-key mapping; `top_p` counts under `topp` or `maxp`. A provider with no map entry (e.g. a manual key) keeps the capability answer unchanged. A `custom-ep:` registry id is not an execution key: `provider_config_key` mangles it to `custom_ep:<slug>`, which has no map entry, so the decision takes an optional `app_config` and, when the id names a registry entry (`entry_for`), decides it as the entry's `family_execution_key`, exactly as the gateway sends it; the rebase passes its config and the dashed identity (fix round 1; before that, an ollama-family endpoint offered Min P that its request drops, and llama_cpp/openai_compatible endpoints under-reported reasoning and thinking). The model-default writer already fails closed for registry entries, and Settings has no model-default rows for them. `FULL_MODEL_DEFAULT_FIELDS` is now derived from the table, so the field list is defined once too.
- Callers: the Console draft rebase (`rebase_console_settings_draft`), the model-default writer (`_build_locked_default_mutation`) and every Settings Providers & Models model-default row, through the draft-key adapter `_model_profile_field_supported(provider, draft_key, model)`. Deleted: the controller's `_supported_console_settings_fields`, the defaults module's `_supported_profile_fields` mirror, and Settings' provider-only gates (`_provider_supports_*`, their five key sets, and the sampler-always-True branch). The modal's tri-state `console_generation_control_support` stays until TASK-33006 (ruling R3).
- Settings (ruling R1): Top P, Min P, Top K, Seed, Presence and Frequency rows now have ids and are hidden and disabled when unsupported (temperature, max tokens and streaming are in all 29 maps); the summary line names every hidden row, e.g. "Hidden for Anthropic: Min P, Seed, Presence, Frequency, Reasoning, Summary, Verbosity." Rendered live at 211x44 on a scratch profile. Because Settings now shares the Console's rules, reasoning and thinking rows follow the model and the local wire rules: llama.cpp shows Reasoning and Think budget, Moonshot/Z.ai show Reasoning only for reasoning-capable models, QwenCloud shows Reasoning, Claude models that reject a fixed budget hide Think budget. This also fixes a silent drop: the old form reader blanked reasoning effort for every provider but OpenAI, so Moonshot/Z.ai reasoning edited in Settings was never saved and a saved value was popped by the next save. Pinned by a mounted test (fix round 1) that fails against the old reader. A "/" search for a hidden row (e.g. "seed" with Anthropic) never focuses it; its status line now says the row is hidden for this provider and model instead of "enable the option that controls it first".
