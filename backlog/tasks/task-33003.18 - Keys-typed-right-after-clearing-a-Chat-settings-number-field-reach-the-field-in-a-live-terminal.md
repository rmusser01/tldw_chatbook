## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
No key is lost, by the app or by tmux. Every key arrives; Textual runs them out of order when they arrive together. Closed without a code change.

Reproduction (211x44, scratch profile, tmux, Chat settings with focus in Temperature holding 0.7). `tmux send-keys BSpace BSpace 1 2 3` in one command leaves `0.71`, in 27 of 27 runs. In order it would leave `0123`. All three characters landed: they went in first ("0.7123") and the two Backspaces then deleted "23". The rider's own burst, eight Backspaces and `0.9` in one command, leaves an empty field in 32 of 32 runs by the same rule ("0.70.9", then eight deletions).

Where. Textual 8.2.8's key dispatch, with no project code on the path. `Input._on_key` inserts a printable key as soon as the Input receives it. A bound key (Backspace, Delete, End, Ctrl+U) acts only when its Key event has bubbled through every ancestor back to `App._on_key`, which runs the binding, and a key already waiting in the app's queue is forwarded to the Input before that. A bare `App` holding one `Input`, with no tldw_chatbook import, gives an empty field for the same eleven keys posted without yielding, at nesting depths 0, 3 and 8.

Pacing, live, load average 17 to 67, reordered runs of all runs:
- one `send-keys` command: 32 of 32
- one command per key, no sleep (7 to 9 ms apart): 13 of 27
- one command per key, a sleep of 5, 10, 30 or 100 ms: 0 of 102
- the Backspaces in one command, the text in the next: 0 of 35
- the Backspaces, a wait for the empty field, then the text: 0 of 11
The rider's "paced 100 ms apart, '.9' twice" did not reproduce at this head (27 of 27 runs kept every key). `.9` is what the reorder leaves when only the `0` gets ahead of the last Backspaces.

Not only the driver. The reorder needs two keys in the app's queue at once. tmux gives it that by writing one command's keys together; a person on a responsive app does not. A blocked UI loop does: in the bare app, five keys posted 100 ms apart left `0123` in 5 of 5 runs with the loop free and `0.71` in 5 of 5 with the loop blocked for 0.7 s. So typing through a freeze can apply an editing key late, in any Input of any Textual app. That is the framework's dispatch order, not this modal's handling, and this rider changes nothing for it.

AC#2 depends on the app dropping keys, and it drops none. Its measure holds for typing at a person's pace: every key was kept in the 102 paced runs above.

Lesson: backlog/docs/lessons-live-verification.md, under "A tmux key burst loses typed text, and an empty Input shows its placeholder". TASK-34100.8 had recorded the same dispatch order for End and Ctrl+U; this adds Backspace, the one command that tells a reorder from a loss, the pacing table and the blocked-loop case.
