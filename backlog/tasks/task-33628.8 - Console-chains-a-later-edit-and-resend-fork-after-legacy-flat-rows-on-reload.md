## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the TASK-33628.6 (PR #2965) review. In legacy flat data that also has a later first-message edit-and-resend fork (a USER root with its own replies), _chain_legacy_flat_roots chains that fork after the flat rows on reload, because the root set also includes assistant roots. The transcript then shows the fork as later messages of the flat chain. Since #2965, Delete persists exactly what the prompt counted, so deleting an earlier flat row now durably tombstones the misplaced fork as well. The prompt counts it and Undo restores it, but the fork was never part of that chain.

Status 2026-10-03, owner ruling 'Mark new forks': PR #2965 (TASK-33628.6) records a durable root_fork marker in messages.metadata_json on every new root-level fork. That covers edit-and-resend of the first message, and a prompt sent after /rewind to before the first message. Marked roots reload as their own branch, so display, the Delete count and the durable delete agree. Unmarked roots chain exactly as before.
What remains for this task:
- Forks created before the marker shipped are unmarked and keep the chained reading, so Delete on an earlier flat row also deletes them. The prompt counts them and Undo restores them.
- The marker is lost on another synced device, through export/import, and when an older build rewrites the row.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Outcome: residual accepted and recorded; no backfill, no code change.** No durable signature separates a pre-marker root fork from a legacy flat USER row whose reply came later through Resend, so a backfill could not mark only roots provably created as forks. Checked against every writer of a parentless USER row:

- **Row columns.** `create_sibling` (Edit & resend) and the durable send write a plain parentless USER row. No Console writer sets `variant_of` (the store, controller and dispatch repository never name it), and `variant_number`/`is_selected_variant`/`total_variants` take the same defaults on every row. `metadata_json` was NULL on forks until the marker.
- **Semantic revisions.** `console_trace_semantic_revisions` shipped 2026-08-30 (c78f641adf), five weeks after the flat-root repair that came with branching (a5a3e88ca2, 2026-07-23), so forks saved in between have no creation-time revision. Later forks carry no fork-only reason either: `add_message` writes `message_create` for a sibling as for any row, and the durable send writes `durable_turn_user_create` for an ordinary first prompt and a before-first send alike.
- **Timestamps.** A fork that was the first action after the upgrade has no earlier parent-linked row to date it against. Timestamp order is not proof anyway: another device's clock, sync, or an older build still writing flat rows.
- **Shape.** Rejected by the owner on #2965: an answered flat row has the same shape, and splitting it drops the earlier history after a Resend.

**Recorded.** `Docs/User_Guide/console/chat-basics.md` (Delete section, "Conversations saved before branching"). New first-message branches are marked and stay separate. An unmarked one reads as later messages of the old chain: one saved by an older version, or a copy that lost the local-only mark through sync, export/import, or an older build's rewrite. Delete on an older message then counts and removes it, and Undo restores it. Console does not guess.

**AC#2 stays unticked.** It holds for every marked fork: Edit & resend of the first message, a typed prompt sent before the first message, and (TASK-33628.12) a voice exchange sent there. For an unmarked pre-marker fork it cannot hold without the identification AC#1's first option asked for, which does not exist. Whether the accepted residual closes the task is the lead's or owner's call.

**AC#3.** #2965's real-store tests (real controller and store, real `ChatPersistenceService`, in-memory `CharactersRAGDB`) pin both readings. `test_marked_first_message_fork_reloads_as_its_own_root_branch`, `test_flat_delete_leaves_a_marked_first_message_fork_live[flat|fork]` and `test_a_new_first_message_edit_fork_is_marked_and_outlives_a_flat_delete[flat|fork]` pin the reload shape and a delete scope of 3 with the fork live. `test_an_unmarked_root_fork_keeps_the_chained_reading` pins the documented residual: chained, counted 7, tombstoned, restored by Undo. They pass on this branch.
