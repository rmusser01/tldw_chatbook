## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the TASK-33628.6 (PR #2965) review. In legacy flat data that also has a later first-message edit-and-resend fork (a USER root with its own replies), _chain_legacy_flat_roots chains that fork after the flat rows on reload, because the root set also includes assistant roots. The transcript then shows the fork as later messages of the flat chain. Since #2965, Delete persists exactly what the prompt counted, so deleting an earlier flat row now durably tombstones the misplaced fork as well. The prompt counts it and Undo restores it, but the fork was never part of that chain.

Status 2026-10-03, owner ruling 'Mark new forks': PR #2965 (TASK-33628.6) records a durable root_fork marker in messages.metadata_json on every new root-level fork. That covers edit-and-resend of the first message, and a prompt sent after /rewind to before the first message. Marked roots reload as their own branch, so display, the Delete count and the durable delete agree. Unmarked roots chain exactly as before.
What remains for this task:
- Forks created before the marker shipped are unmarked and keep the chained reading, so Delete on an earlier flat row also deletes them. The prompt counts them and Undo restores them.
- The marker is lost on another synced device, through export/import, and when an older build rewrites the row.
