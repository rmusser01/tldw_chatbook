## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Opening Switch model probes each local server's model listing (TASK-33005.5), and the shared evidence keeps the model ids the server returned. The rows ignore them: Ollama's rows come from the shipped `[providers]` list (gemma3:12b, gemma3:4b, gemma3:27b, … in the capture checkpoint's captures 06 and 12) and never show `qwen2.5:0.5b`, the one model the running server actually listed. A user who just started a server sees models it does not have and misses the one it does.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 After a probe lists a local server's models, that provider's switcher rows show the listed models, and models the server did not list are no longer offered as ready rows [At the probe's 100-model bound (MODEL_IDS_MAX_COUNT) the listing may be partial, so the catalog's and saved models stay after the listed ones.] [In Chat settings' pick mode, the models its own listings found stay after the listing (TASK-33006.19); since TASK-35190, on the chat's own provider such a listing replaces the provider's rows instead.]
- [x] #2 With no listing yet (not probed, refused, or timed out), the rows keep today's saved and cached models
- [x] #3 No new network request is made for this: the rows read the evidence the probe already recorded
- [x] #4 A test drives the real popover with a stubbed server listing one model that is not in the saved list
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A server's switcher rows are now the models its last listing returned. All in tldw_chatbook/Widgets/Console/console_model_popover.py:
- `_server_listing(readiness)` reads the model ids from the evidence the provider's readiness already carries (`ConsoleSettingsReadiness.evidence`, TASK-33005.11), when the listing answered (`endpoint == "reachable"`) and the connection is a server's own: a URL-based provider or a registry entry, the same test `_retries_in_place` uses. A cloud key check's listing is not taken for a catalog. `_models_for` returns it ahead of the cached catalog and the saved list, so every reader of a provider's models (READY rows, NEEDS SETUP rows under a query, Find's count, the typed-id check, the representative model) sees what the server listed. A listing that answered with no models is an empty list (its "no models reported" line). A listing at the probe's bound (`MODEL_IDS_MAX_COUNT`, 100: discovery stops there and the evidence holds no more) may stop short of what the server serves, so there the catalog's and saved models follow the listed ones (and the `served_models` below) instead of dropping out (round-1 review: 150 listed with a saved m120 gave 100 ids without it, and Find offered m120 as a typed id in no catalog). `_catalog_status_rows` says nothing about a catalog while the listing fills the rows.
- Why it reached no row before: `_offer_probes` hands the prober `refresh_readiness`, and the re-read readiness carried the listing only into the readiness word (`model_readiness_words`).
- AC#2: not probed, refused (`unreachable`), timed out (`unreachable`), listing unavailable or not yet tested: no listing, so the rows are today's catalog or saved models.
- AC#3: nothing new is sent; the popover still makes no network call (`test_the_switcher_widget_makes_no_network_call_itself` passes, and the new test asserts one request per local server, as before). `connection_probe.switcher_probe_target` was not reused: the popover may not import Console_Modules (that same test).
- Not changed: this chat's own model stays listed first when the server does not list it (ADR-020), with the readiness word for an unlisted model.
- `served_models` stay after the listing (Wave 6 integration review, round 1). They reach the rows from two places: Phase 8's detected-server path (the server's own listing, which agrees with this) and Chat settings' pick mode (TASK-33006.19: the models its listings found, kept only where a pick lands on the Endpoint that listed them). Pick mode's readiness is the configured connection's, so the first version, which returned the listing alone, dropped the models Test connection had just listed at a typed :9200 once the configured :9099's own listing was in the shared evidence, and the rows offered :9099's listing for picks landing on :9200. `_models_for` now appends them after the listing, deduped; each was listed by the endpoint a pick of it lands on (TASK-33006.19), so a saved model no server listed is still not offered, and AC#1 holds. Round 2: they are appended on `_models_for`'s shared exit, so they also follow a loaded catalog (with no listing, Change dropped them as soon as the catalog loader, which `open_model_picker` passes, had resolved the provider; base 116013aeab already did this), and at the bound they come before the catalog's and saved models, as they do under it (they came last). `_saved_models` no longer appends them.
