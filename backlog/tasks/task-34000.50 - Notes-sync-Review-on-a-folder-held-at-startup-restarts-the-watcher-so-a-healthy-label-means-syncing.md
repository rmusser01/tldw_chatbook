## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: a synced folder can show a healthy, dated status while nothing is syncing. This was found in the review of the TASK-32633 slice (N-03) and measured on the production runtime.

When the app starts with a folder already held ("Needs attention"), that folder is never leased and its watcher never starts. The held row's primary action is **Review**. Review reaches `runtime.check_root`, which leases and re-plans but does not start the watcher. If the review clears the hold, the row turns to "✓ Up to date as of HH:MM", yet the watcher is not running:
- a later disk edit is never seen;
- `schedule_hint` is refused;
- `note_changed` returns nothing.

Only **Check changes** (`request_sync_now`) starts the watcher.

So after delete, restart, Restore and Review, the folder reads healthy while carrying nothing in either direction. That is the same false-comfort failure as the review's N-02 and N-03 findings. The N-03 slice makes "held at startup" the normal result of deleting a synced note, so this path is now ordinary. The slice's fix covers the Restore path only; every other way of healing a startup-held root still needs this.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** Two halves, both in the runtime; the UI only projects. (1) `_ensure_lease` starts the watcher for every NEW persisted lease taken under open admission (`_watch_lease`): Review on a folder held at startup, Recovery, the released pass, Resume, a migration activation -- the invariant is enforced where leases are made, not at each caller. Declined for a provisional setup-review lease (activation starts the watcher itself once the root exists), for a root Pause is closing (`_closed_roots`), and unless the runtime status is `active` (a dead watcher is restarted only by a successful Check changes, as `test_failed_sync_now_check_does_not_restart_the_watcher` pins). `_start_watcher` keeps its own guards (closing, maintenance fence, admission, idempotent). (2) `NotesSyncRootRuntimeSnapshot.watching` is computed at READ time in `snapshot()` (and stamped on listener notifications) as "watcher task running AND root leased AND not blocked" -- the set the watcher polls -- via `dataclasses.replace`, so `_publish` stays the only construction site. A watcher start re-announces every root's last publication so a row that read "⚠ Sync stopped" is re-projected without a keypress (listeners publish only on change). `_project_root` wears `ROOT_STATUS_LABELS["not_watching"]` ("⚠ Sync stopped", next action Check changes) for an `up_to_date` root with `watching` False, after the runtime-status overlay (a `starting` runtime still reads "◌ Starting").

**Deviation from the brief.** The brief placed `watching = watcher_running and leased`; blocked roots are excluded too (the watcher does not poll them). Test 3 (Recovery on a startup-held root) is GREEN on base, not RED: `_resume_incomplete` leases a Recovery-held root at startup and the startup watcher runs for that lease, so only the block kept hints out; it is kept as a pin. The early-return (already-leased) branch does NOT start a watcher: three sandboxed pins (two `request_sync_now` failed-check tests, one hand-built conflict-runtime owner) refuse exactly that.
