## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during the TASK-41306..41320 follow-up burn-down (2026-11-17, merged as #3581..#3593). Checked on dev 97f8c58c0c; line numbers are that tree's, and paths are under `tldw_chatbook/` unless they start with `Tests/` or `backlog/`.

**Why.** TASK-41308 made the Console Inspector say `MCP: off · this profile's MCP settings file can't be used here` whenever the MCP store is unbound, which is the same predicate that drops MCP from the Send. The MCP hub, where the user configures servers, still shows them with no warning. Someone who adds a server there has no way to learn it will never reach the Console.

**Where.** The hub's rail and inspector (`UI/MCP_Modules/`) read the server list but not the store binding.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Change.** `MCPRail` takes `console_mcp_off_reason`. When it is non-empty, the rail shows `Console: MCP off · <reason>` under **Servers**. The widget is a `Static#mcp-rail-console-warning` with the existing `mcp-status-warning` class (amber, `$ds-status-warning`) and `markup=False`. The only layout rule is padding, in the rail's `BUNDLED_CSS`, regenerated by `build_css.py`. `MCPWorkbench.compose` passes `console_mcp_unavailable_reason(self._service())`: the same pure predicate and reason constant as the Inspector row, through the workbench's existing service lookup. The rail does no app lookup of its own. This matters for tests too: a harness `App` is not the app instance. Nothing shows when the store is bound, or for a non-stock (fake) service. Binding never changes after the store is built, so the reason is read when the workbench composes.
