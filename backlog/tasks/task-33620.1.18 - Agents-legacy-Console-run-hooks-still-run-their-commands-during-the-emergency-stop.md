## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The owner ruled on 2026-11-24 that during an emergency stop hook-v2 MCP and command actions don't run (TASK-33620.1.12 holds them at `HookEngine._deliver_current`). The Console's legacy run hooks (`[[hooks.hook]]`, `Agents/run_hooks.py`'s `RunHooksEngine`, built in `Chat/console_runtime.ensure_run_hooks`) are a separate engine: they still spawn their commands during a stop. These are the hooks the User Guide documents ("Run hooks"), so a user's PreToolUse guard, PostToolUse notifier or Stop script runs while everything else is held. Needs an owner call on the legacy fail directions: PreToolUse fails closed today, but UserPromptSubmit fails open after consent.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Folded into TASK-33620.1.12's branch (coordinator, 2026-11-24: the owner's ruling covers an agent run's hooks, run hooks included).

- **Choke point.** `run_hooks._run_hook`, the one function every run-hook command passes through on the engine's pool threads (awaited `fire`/`fire_async` and `notify` alike). It reads the stop with the shared `emergency_stop.current_emergency_stop()` (blocking, off the loop) before launch.
- **Failure semantics kept and pinned.** A held hook takes the engine's existing meaning of a refused launch (`HookLaunchRefused` without `skip`): a blocking event (PreToolUse, UserPromptSubmit) is denied with the stop's copy, any other event (PostToolUse, Stop, ApprovalRequested, SubagentStop) is skipped. So a held PreToolUse guard still refuses its tool, and a held UserPromptSubmit hook blocks rather than failing open (it fails open only after an execution failure, never on a refused launch). SessionEnd is not a run-hook event.
- **UserPromptSubmit finding.** It fires only for MANUAL Send and manual resend; queued, wake, goal and scheduled turns and sub-agent prompts never fire it. A path did exist: the Console's send gate reads the stop before a Send (and resend's gate before its replay), then the turn awaits its preparation before the hooks fire; a stop landing in that window used to let the hook run and, failing open, the prompt reach the provider. Both paths now re-read the stop off the loop (`console_automatic_submission.emergency_stop_turn_refusal`) right before the prompt hooks and refuse the turn with the stop's copy. The run-hook hold is the second layer (a held prompt hook blocks).
- **Logging.** One sanitized line per hold: run hooks `run-hooks: event=<event> session_id=... run_id=... hook=<fingerprint> held by the emergency stop (unreadable=<bool>)`; hook-v2 `hooks-v2: event=<event> handler=<id> held by the emergency stop (unreadable=<bool>)`; research `research: run <id> held by the emergency stop before <step> (unreadable=<bool>)`. Never the command, its arguments or the user's question. Inventory reviewed with `--statements` before `--write`.
- **Tests.** `Tests/Agents/test_run_hooks_emergency_stop.py` (12: PreToolUse fail-closed pin, UserPromptSubmit blocks not fail-open, four observer events skipped, notification skipped, directory/corrupt stop, unlocatable stop, after Clear, and the controller test that a Send admitted before the stop is refused before its UserPromptSubmit hook); `Tests/Chat/test_console_turn_resend.py::test_resend_is_refused_by_a_stop_that_lands_after_its_gate`. Mutations: no run-hook check (10 red), held blocking hook fails open (4), no controller check (1), both (11), no resend check (1), each log line removed (1-5 red).
- **Live.** Not demonstrable end to end: `[[hooks.hook]]` commands fail with RuntimeError before launch in the real app on origin/dev too, stop or no stop (TASK-33620.1.18.1, filed). The hold is covered by the engine and controller tests above.
