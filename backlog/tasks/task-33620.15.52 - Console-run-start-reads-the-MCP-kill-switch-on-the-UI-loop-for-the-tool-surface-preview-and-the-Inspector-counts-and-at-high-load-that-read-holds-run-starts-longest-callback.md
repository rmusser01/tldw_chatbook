## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-33620.15.38's live rounds (2026-11-05, origin/dev 29592ecc9b, Anthropic claude-haiku-4-5 via the review proxy, 160x45, a fresh isolated profile per launch, lean probe with exact timers on recovery_activation.selected_path and its callers). With the catalog fingerprint's reads moved off the loop (TASK-33620.15.38's first round; its continuation took the fingerprint off a live send altogether, see the notes), the same recovery-activation check still runs on the UI loop during run start through UnifiedMCPControlPlaneService.get_kill_switch, called by Agents/plain_chat_tool_surface.tool_kill_switch_engaged from ConsoleAgentBridge.light_surface_local_tools_available. Two callers: ConsoleAgentBridge.preview_tool_surface (preflight_tool_surface, from ConsoleCompactionPreflight's conversation-memory and capacity checks) and offered_builtin_tool_count (ConsoleChatController._publish_mcp_inspector_counts). Each read is a full writing MCP store scope (storage admission, generation witnesses). At load1 6.6-9.2 this read held run start's longest UI-loop callback in 3 of 3 first sends and 3 of 6 later sends on origin/dev (longest-callback medians 73 and 39 ms). At load1 ~115 the check from these callers held it in 2-3 of 8-10 later sends on both arms, 100-200 ms of wall on 7-17 ms of CPU, because the loop waits to be scheduled again after each syscall (lessons-live-verification, TASK-33620.15.1.6). Run start already reads the kill switch once for MCP and local tools (LocalKillSwitchRead, TASK-33620.15.1); these preview and Inspector reads are separate. Evidence: tools/evidence/bd5/R38/ (v2base, v2pair; kit2/r38check.py prints the callers).

## Implementation Notes

2026-11-05/06, TASK-33620.15.38 continuation (branch perf/task-33620.15.38-mcp-source-check): left filed there, not fixed. After that branch a live Console send takes no catalog fingerprint at all (it anchors instead), so these kill-switch reads are the recovery-activation checks left on the UI loop during run start, and now the most frequent holder of run start's longest callback. On that branch at load1 100-128 (lean probe, rounds v3pair + v5pair, origin/dev e8eeae7db9 and 2684e5453f), the check from these callers held run start's longest UI-loop callback in 4 of 7 first sends and 6 of 14 later sends (origin/dev: 2 of 7 and 2 of 14, while the fingerprint still held others). Almost all of it comes from UnifiedMCPControlPlaneService.get_kill_switch < tool_kill_switch_engaged < ConsoleAgentBridge.light_surface_local_tools_available (kit3/r38check.py prints the callers). The two callers need two different fixes. The Inspector counts (_publish_mcp_inspector_counts) run after the run's composition and could take the run's own decision (its LocalKillSwitchRead, read moments earlier by the same run start). The preview (preflight_tool_surface, from the compaction preflight) runs before run start's own read, so there is no current read to reuse. Moving it to a worker is the trade the owner held on TASK-33620.15.38 (a hop on a first send's path cost about 55 ms at low load). A kill-switch read proven current by the permission store's stamp, as TASK-33620.15.38's anchor proves a pending catalog, would be a new design and needs its own measurement. AC#1 at low load is not measured yet.
