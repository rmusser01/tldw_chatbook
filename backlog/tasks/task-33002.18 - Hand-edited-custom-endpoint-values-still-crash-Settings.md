## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This rider comes from the TASK-33002.12 hotfix review, which confirmed both cases with mounted tests. Both need a hand-edited `config.toml`, because the UI edit path rejects these values, and both crashed before TASK-33002.12:

1. An invalid `[custom_endpoints.<slug>] api_key_env` (for example `"gpu-key"`) whose variable is unset. Opening Settings then crashes with `ValueError: Environment variable is invalid.`, raised from `_validate_env_var` in the shared missing-key readiness helper.
2. A dangling `custom-ep:gone[/]` default. Overview opens, but opening Providers & Models crashes with `MarkupError` on `#settings-provider-endpoint-key`, which renders the unescaped `api_settings.custom_ep:gone[/].api_base_url`. The Test endpoint line has the same exposure.

A hand-edited config should degrade to an honest not-ready state, never kill the app.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- Done in the TASK-33002.12 fix round for Qodo #2876, in the same commit. That task's "Review round 2" notes describe the whole change.
- Case 1, invalid `api_key_env`:
  - `load_custom_endpoints` checks the name with `validate_env_var_reference`, the check the Edit form already used. It logs a warning that names only the slug.
  - The entry is kept, not dropped. A dropped entry would read "Endpoint not found", which hides the real problem and removes the row the user fixes it from.
  - `_custom_endpoint_missing_key_readiness` is shared by Settings, Console readiness, the gateway and agent routing. When no credential resolves and the declared name is invalid, it returns reason "Invalid provider settings". The recovery reads "The '<name>' endpoint's credential env var name is invalid. <naming rule> Fix it under Custom endpoints."
  - The naming rule is now one constant, `ENV_VAR_NAME_RULE_COPY`, shared with the Edit form.
  - A stored key on the entry still resolves, so that entry stays ready.
- AC#1 wording changed before ticking. The rider asked the state to name "the bad variable name"; it names the problem, not the value. A value that is not a valid env var name (for example `sk-proj-...`, which contains `-`) is often a key pasted into the name field, and Settings output gets screenshotted.
- Case 2, dangling `custom-ep:gone[/]`: `#settings-provider-endpoint-key`, the Endpoint row and the Test endpoint line read the registry (`custom_endpoints.<slug>.base_url`) through `_provider_registry_endpoint`, which escapes both the slug and the URL.
- RED, with the source unfixed and the final tests:
  - Four invalid names raised `ValueError: Environment variable is invalid.`; the ESC name raised `ValueError: Provider recovery is invalid.`
  - The Console seam raised the same ValueError, and the load test saw no warning.
  - The mounted invalid-env test died on that ValueError.
  - The mounted dangling-markup test died on `MarkupError: auto closing tag ('[/]') has nothing to close`.
- GREEN: all of these pass.
