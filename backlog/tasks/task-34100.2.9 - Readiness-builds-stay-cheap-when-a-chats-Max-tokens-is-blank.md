## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-34100.2's pre-merge review (M-3, 2026-11-12) measured a Console readiness build at 0.117 ms when the chat's Max tokens is blank, against 0.029 ms on base: four times the cost. A blank Max tokens means "inherit", and readiness finds the inherited value by rebuilding the pair's default Console session settings on every build (`default_reply_max_tokens` in `Chat/console_session_settings.py`, reached through `_reply_max_tokens`), with no memo. Readiness is built hundreds of times per Console screen switch (TASK-18909). That is why the catalog lookup beside it, `_catalog_capacity_inputs`, is already memoized per catalog and config generation.

The goal is that a blank Max tokens costs about what a set one does, without readiness ever judging a stale inherited value. One trap: Settings' Test Provider calls the same function with its unsaved draft config, so a memo keyed only by the saved config's generation would judge the draft by the saved value.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Building readiness for a chat whose Max tokens is blank costs no more than 1.5x the same build with Max tokens set, measured on one machine over many builds; both numbers, and base's, are recorded in the Implementation Notes
- [ ] #2 After a config save that changes the inherited value (a model default, the provider table's max_tokens or [chat_defaults]) or a model-catalog reload, the next readiness build judges the new value without a restart
- [ ] #3 Settings' Test Provider, which judges its unsaved draft, still judges the draft's inherited value, never a value memoized from the saved config
- [ ] #4 Every readiness word (header, switcher rows, Settings' Readiness row) is unchanged for the same inputs
- [ ] #5 A test counts the default-settings rebuilds across repeated readiness builds of one blank-Max-tokens pair with the config unchanged; it fails on the current code (one rebuild per build) and passes after the fix
- [ ] #6 A test saves a new inherited max_tokens between two readiness builds and asserts the second build reads it (a staleness control that passes before and after the fix)
