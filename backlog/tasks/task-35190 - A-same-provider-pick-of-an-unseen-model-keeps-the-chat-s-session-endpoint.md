## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in the TASK-33006.19 review, round 2 (2026-10-17). A chat can run on an Endpoint other than the configured URL, for example after a user applies a second local server to one chat (session 127.0.0.1:9200, config :9099). In Chat settings, picking a model on that same provider that the draft has not seen moves the chat to the configured URL: the controller's settings rebaser (`rebase_console_settings_draft`) starts an unseen target from its default chain, and with a clean endpoint draft it takes that chain's base URL, not the chat's session URL. For llama.cpp that base URL is None, and None here means the configured URL, not 'no endpoint': `default_console_session_settings` leaves it unset on purpose, and the configured endpoint is resolved later (the modal shows it through `_initial_base_url_for_provider`). A fix that reads None as 'no endpoint' is wrong. So even a saved-model pick on the same server lands on :9099. Since TASK-33006.19, pick mode offers a model that Test connection listed only while a pick of it stays on the endpoint that listed it, which is correct, but it means a listing at :9200 says '3 models listed' and then Change offers none of them except the current model. The only way to pick them today is to retype the Endpoint. TASK-33006.19's test_a_listing_is_offered_only_while_its_pick_keeps_the_listed_endpoint pins today's reset, so this task changes that test's expectation. The rebaser is not Chat settings' own. Switch model (Alt+M) picks through it too (`ConsoleModelPopover._rebase_to`, on the quick surface, `QUICK_MODEL_DEFAULT_FIELDS`), and a probe at the TASK-33006.19 head (2026-10-17) showed the same reset there: a llama.cpp chat on :9200 with a clean endpoint draft, picking an unseen same-provider model, got base_url None and no endpoint draft on both the full and the quick surface. So the fix belongs in the rebaser, and AC #4 says what Alt+M then does. The rebaser's other two callers do not take this path: the live commit (`ChatScreen._commit_console_settings_submission_live`) rebases a draft onto its own pair, and session adoption (`session.py`) replaces the rebased base_url with the configured one. Account for TASK-33005.12 too (Wave 6 integration review, 2026-10-18): a server's switcher rows are the models the last listing of the readiness's connection returned, and both Alt+M's and pick mode's readiness is the configured connection's (:9099). Once a same-provider pick keeps the session Endpoint (:9200), Alt+M would offer :9099's listing too, with :9099's readiness words, for picks that land on :9200, so the implementer must decide which listing those rows read.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
A pick of another model on the chat's own provider now keeps the chat's Endpoint on both surfaces, and Switch model's rows, readiness and probe on that provider read the server a pick lands on, not the configured one.

- Rebaser (the root, shared by Chat settings, pick mode's landing check and Alt+M): the endpoint choice moved out of `ConsoleChatController.rebase_console_settings_draft` into `rebased_endpoint` in tldw_chatbook/Chat/console_settings_apply.py, next to `remember_model_draft` (the controller had 2 lines of headroom; it shrinks 29,182 -> 29,150 and its ratchet row is lowered to match). A kept pair (the current or a remembered target) behaves exactly as before. An unseen pair takes the endpoint of the latest draft on its provider: the current draft when it is on that provider, else the most recently remembered one (`remember_model_draft` moves a re-remembered pair to the end since review round 1, so `model_drafts` runs in recency order). So a pick on the chat's own provider keeps the session URL (:9200) even after a pick of another provider in between, which matters for Alt+M: its draft is rebased on every highlight change, and with Find empty PREVIOUS (often another provider) is highlighted first. With the remembered-draft lookup removed, only the three detour cases fail. An unset URL keeps meaning the configured one: the default chain applies, never "no endpoint". A registry entry keeps its own URL (ADR-146). An endpoint edit still carries only on the full surface, so the quick surface's rule is unchanged. The other two rebaser callers are unaffected: the live commit rebases onto its own pair, and session adoption overwrites base_url.
- AC#3: a pick onto another provider has no draft on that provider to read, or only one remembered from this open, which holds that provider's own endpoint. So the session URL is never carried across providers.
- Listing decision (TASK-33005.12, controller note): rows read the listing of the server a pick lands on. `ConsoleModelPopover._listing` (tldw_chatbook/Widgets/Console/console_model_popover.py) feeds `_models_for` and `_catalog_status_rows`. Which server that is comes from one helper, `pick_base_url` (console_settings_apply.py), which calls `rebased_endpoint` itself, so the rebaser, the rows and the switcher's readiness cannot drift (review round 1). A provider with no draft reads the readiness's listing, as before. On the chat's own provider, and on one a draft remembers with an Endpoint (a pick of another provider in between), a Chat settings listing (`served_models`, already kept only where a pick lands, TASK-33006.19) is that provider's listing, so it replaces the configured server's listing and the catalog or saved models it left out (TASK-33005.12 AC#1). Without one, the readiness's listing counts only while the chat's Endpoint is the connection it listed. Otherwise there is no listing, and the rows are the catalog or saved models, as with no listing (TASK-33005.12 AC#2). `_with_known` keeps the 100-model bound rule for both listings. Pick mode now opens on the modal's snapshot (`_open_model_picker` passes `source`, the draft as the controls show it), so a typed Endpoint is known too.
- `ConsoleSettingsReadiness.connection` is set only while evidence for it is current. The first version of `_listing` relied on it, so with no evidence (`test_a_listing_at_this_chats_endpoint_replaces_a_loaded_catalog`) it fell back to catalog plus served. Reading `served_models` first fixed it.
- Readiness and probe (review round 1; model_switcher.py joined the references): `_switcher_sources` takes the draft a switcher opens on and resolves readiness, and plans its local probe, over an in-memory configuration in which each drafted provider's endpoint is where a pick on it lands (`pick_base_url` plus `with_provider_endpoint`, as R12 does for a detected server); Alt+M passes the chat's draft, pick mode the modal's snapshot (full surface). Before, both read the configured connection, so with :9099 down a llama.cpp chat on :9200 sat under NEEDS SETUP: Alt+M's Enter on model-b left the chat on model-a, and pick mode offered neither served-y nor model-b. The rebaser keeps the saved configuration, so a default it writes names no session endpoint. The detected-server path keeps its own endpoint (no draft passed). Because the popover's Ctrl+N gate reads the same resolver, the switcher's committer now checks Make default for new chats against the configured connection, which new chats use, as the popover's gate did before.
- Settings round trip (review round 1): a suspended Chat settings draft reopened with no remembered drafts, so a pick back on the chat's provider landed on the configured URL. `ChatScreen._open_console_settings` now seeds the reopened draft's `model_drafts` with the chat's own pair (no new method; chat_screen.py 24,346 -> 24,360 lines, under its 24,369 row).
- mypy (review round 1): `rebased_endpoint` narrows the bound endpoint draft explicitly, and the controller's `source` line narrows the remembered target, so the touched modules report 181 errors against fc5a596f31's 184, none new (the controller's three base union-attr errors on `remembered_target` are gone; console_settings_apply.py is clean). The controller's line count is unchanged (29,150).
