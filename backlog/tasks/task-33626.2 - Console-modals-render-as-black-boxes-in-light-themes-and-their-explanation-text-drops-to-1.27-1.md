## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
In any light theme, Console modals that hard-code 'border: tall gray; background: black' in their Python DEFAULT_CSS/BUNDLED_CSS show up as black boxes in an otherwise light UI. Body copy with no explicit colour inherits the light theme's dark foreground, so it becomes nearly invisible. The copy that disappears is the consequence text a user needs to choose between actions (for example, what Save and Edit & resend will each do).

**Verified behaviour (live on 64579cce2c, general.default_theme = "textual-light"):**
- Library search description ('Manual search for this send only…'): #1f1f1f on #000000, **1.27:1**. ConsoleLibrarySearchModal only overrides size, so it inherits the black frame from ConsoleRagSettingsModal.
- Edit Message consequence line ('Save keeps the edit in place; Edit & resend creates a new response branch…'): **1.27:1**, with a dark-navy (#001423) text area.
- Composer Menu: a dark-navy focused row inside a black frame, while the other rows are light-grey (#d8d8d8) slabs. Rewind's highlighted row is also dark navy in a black box.
- solarized_light: the description reads 4.71:1, but the modal is still a black box in a cream UI. textual-dark: 15.91:1, which is why dark-only checks miss this.
- From reading the code (not reproduced live), AutoSpeakConsentModal has a black frame and no colour rules, so its consent copy (Provider, Destination, 'Provider charges may apply.') would also render at about 1.27:1 in a light theme.
- The verifier counted 17 Widgets/Console files with `background: black`, plus the inherited Library search modal. The counter-example ConsoleAppearancePickerModal already uses `$ds-surface-panel` with a token border.

**Severity / prior art:** P1, triage NEW (live, code and skeptic all CONFIRMED). This extends review finding G4-58 (P3: about ten modal frame styles and 18 hard-coded black frames; the gray border measures 2.99:1 in textual-light), and this fix removes the black-frame part of G4-58. ADR-150 (design-token system) already requires semantic tokens. Related work: TASK-31264 (Done; light themes exposing hard-coded stock colours), TASK-31429 (Done; context-rail theme-aware colours), TASK-32864 (To Do; modal dismissal/confirmation pattern, which covers behaviour, not colour), TASK-33003.6 (To Do; boundary/focus contrast on the Settings/Chat-settings surfaces, which covers theme edge tokens, not Console modal frames). None of these covers this defect.

**Suggested direction:** Add one shared, token-based Console modal frame (theme panel surface plus a token border, as ConsoleAppearancePickerModal does) and move every literal-black Console modal onto it; subclasses inherit the fix. Replace `color: gray/red` with muted/error tokens. Give explanation and consequence copy an explicit token text colour so it cannot inherit a clash. Add a ratchet, in the spirit of ADR-150, that rejects colour keywords and hex literals in Widgets/Console CSS strings.

Evidence: qa/console-ux-review-2026-09-29/findings.md → GAP3-02 (and G4-58); qa/console-ux-review-2026-09-29/evidence/evidence__GAP3__18-light-library-search.png, evidence__GAP3__20-light-edit-message.png, evidence__GAP3__21-light-rewind.png, evidence__GAP3__69-light-composer-menu.png, evidence__GAP3__29-solarized-library-search.png.

Review finding ids: GAP3-02 — see qa/console-ux-review-2026-09-29/findings.md.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Every Console modal that hard-coded `border: tall gray; background: black` now takes its frame from the theme: `$panel` fill, `$tldw-boundary` edge (the guard-generated 3:1 boundary token from TASK-33003.6), and an explicit `$text` ink so copy cannot inherit a clash. Explanation copy that had no colour (`#console-edit-message-context`, `.console-rag-settings-status`, the AutoSpeak consent Statics) gets an explicit token; `gray`/`red`/`yellow`/`$warning` inks become `$text-muted`, `$text-error` and the AA-pinned `$text-warning`. ConsoleLibrarySearchModal inherits the fix from ConsoleRagSettingsModal. 17 files under `Widgets/Console`, plus the regenerated `widget_defaults_scoped.tcss` / `screen_css_scoped.tcss` (via `build_css.py`; `check_bundle_sync.py` green).

Decision: per-modal token rules rather than one shared frame class. Each modal's frame selector is already its own id rule inside its class CSS, so a shared class would have added a second rule for every frame to override; the ratchet below is what keeps the set from drifting back.

Tests (`Tests/UI/test_console_modal_theme_frames.py`):
- AC#4 ratchet: AST-reads every class-level CSS string in `Widgets/Console` and rejects named colour keywords, hex and `rgb()`/`hsl()` outside an (empty, documented) allow-list. On origin/dev 3efe8476ce it listed 52 declarations in 18 files. A detector self-test guards against a vacuous pass.
- AC#1-#3, #5: pushes the real modal classes (Edit Message, Library search, RAG settings, AutoSpeak consent, composer Menu, Rewind) onto an App loading the production stylesheets, under textual-dark, textual-light, paper_light, solarized_light and high_contrast_yellow_black at 235x52 and 80x24, and reads frame fill, edge, copy contrast and focused-row contrast from `render_strips()`. On origin/dev all 10 rendered cases fail (e.g. textual-light: frame #000000, copy #1F1F1F on #000000 = 1.27:1, focused row #001423 "dark slab"); 11/13 red, 13/13 green on the branch.
- Two node ids (the ratchet and the textual-light 80x24 case) are added to the PR fast lane (`scripts/ui_pr_gate_census.txt`, floor 1141 -> 1143 after rebasing onto dev's TASK-36611 entry).
