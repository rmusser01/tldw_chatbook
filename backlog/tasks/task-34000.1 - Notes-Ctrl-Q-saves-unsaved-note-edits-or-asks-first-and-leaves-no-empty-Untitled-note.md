## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: Ctrl+Q is the universal quit key, and in Library ▸ Notes it silently throws away whatever was typed since the last autosave. The note header meanwhile promises "Unsaved changes · Next: Keep editing; changes save automatically." This hits everyone. A first-timer types a last line and quits. A power user keeps typing and is never saved mid-burst. The stress tester finds a brand-new note reduced to an empty row. Four independent runs reproduced it (j1, j3, j6, B-static), and so did the refute-first verifier.

What was observed (160x45, golden profile):
- Verify capture 03: " VERIFYTAILN01" is typed at the end of "Ideas inbox" while the header reads "Unsaved changes · Next: Keep editing; changes save automatically." Ctrl+Q exits in under 3 s with no prompt. After relaunch the word is gone, and the DB row is still at its previous version.
- The verifier widened the scope: typing one character every 1.2 s never saves at all. The 2.0 s debounce re-arms on every keystroke, so Ctrl+Q loses everything typed since the last pause.
- New-note variant: Ctrl+N, type a title, Tab Tab, type a body, Ctrl+Q. After relaunch, capture 10 shows an empty "Untitled · now" row (Notes (122) became Notes (123)), and the typed title and body are gone. j6 saw the same thing: a note typed as "Riley new ctrlq" persisted as title "Untitled" with content "".

Verified cause (origin/dev 2d34cbf80d):
- The quit flow consults only `confirm_quit` / `prepare_for_quit` on the active screen (app_lifecycle.py:1869 via `quit_confirmation_screens`, Widgets/confirmation_dialog.py:174). LibraryScreen defines neither.
- `LibraryScreen.flush_pending_work` (UI/Screens/library_screen.py:11109) already flushes Folder files, the note session, and prompt and skill drafts. Only navigation awaits it (app_navigation.py:513).
- `on_unmount` (library_screen.py:9615, call at :9738) runs `_invalidate_library_note_autosave` (UI/Library_Modules/library_notes_controller.py:3697-3702), which cancels the pending save.
- The debounce (`_schedule_library_note_autosave`, library_screen.py:20738-20749; `LIBRARY_NOTES_AUTOSAVE_SECONDS = 2.0` at UI/Library_Modules/screen_constants.py:177) has no maximum wait.
- Not reproduced live, code-traced only: B-static found the same gap for dirty prompt and skill drafts, and for Folder files autosave (`LibraryFileNotesWorkspace.shutdown` stops its timer without saving, Widgets/Library/library_file_notes_workspace.py:2428).

Suggested direction (the review's refined fix; a direction, not a mandate):
- Add `LibraryScreen.confirm_quit()` that awaits `flush_pending_work()`.
- On a veto or failure, ask: 'Quit and discard unsaved changes to "<title>"? Keep editing · Discard and quit', with Keep editing focused.
- Have `prepare_for_quit()` run the untouched-blank-note cleanup.
- Add a ~10 s maximum wait to the 2 s autosave debounce.
- Add an architecture test: any Screen that defines `flush_pending_work` must also define `confirm_quit`.

Ownership: no existing task owns this. N-06 is a separate review finding about the same autosave lifecycle (opening a modal cancels the pending autosave and never re-arms it), with its own fix. This task covers quit, the debounce max-wait and the blank-note orphan only.

Review finding(s): N-01. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Ctrl+Q in Library now persists pending work through the app's existing quit seam, or asks first. It never exits silently past an edit it could not save.

**Approach** (reuses `quit_confirmation_screens` / `confirm_quit` / `prepare_for_quit`, following the TASK-33622.14 Roleplay precedent):
- `LibraryScreen.confirm_quit` / `prepare_for_quit` are thin lazy-import delegators into the new focused module `UI/Library_Modules/library_pending_work.py`. Lazy, so the module stays out of the Library preimport census. `library_screen.py` is over its size ratchet.
- `confirm_library_quit` awaits the same `flush_pending_work` that navigation awaits (Folder files, the Database note session, prompt and skill drafts). The wait is bounded by `NAVIGATION_FLUSH_TIMEOUT_SECONDS` and shielded, and the task is retained, as navigation's is. A clean flush quits with no prompt.
- A veto, an exception or a timeout asks through `confirm_quit_discarding_edits`, which uses the `await_quit_prompt` choke point. The prompt reads 'Quit and discard unsaved changes to "<title>"?' with the reason, and Keep editing is focused (first button, AUTO_FOCUS). Every unsaved draft is named: note title, Folder file path, prompt/skill name. A veto with nothing nameable (a prompt mutation or path task in flight) asks "Quit before Library finishes saving?" with Stay / Quit anyway.
- The untouched-blank GC is deferred. `flush_pending_work(gc_untouched_blank=False)` skips it during confirm, and `prepare_for_quit` runs it once every quit prompt has said yes. A later Console/workflow "Stay" therefore never leaves the editor on a deleted row. The GC predicate moved verbatim, comments included, out of `_flush_library_note_save` into `gc_untouched_session_blank_note`, so navigation and quit share one copy. The default zero-argument call shape is kept for the many test doubles of that seam.
- Autosave max-wait: `LIBRARY_NOTES_AUTOSAVE_MAX_WAIT_SECONDS = 10.0` sits next to the 2 s debounce. `arm_library_note_autosave` caps each debounce by the time left in the burst. A burst starts at its first unsaved keystroke and is keyed on note/session/saved revision. The timer callback ends the burst, so a vetoed autosave is not retried per keystroke. The screen still passes its own module constants, which tests patch.
- Guard: `Tests/Architecture/test_flush_screens_have_quit_hooks.py` fails for any Screen that defines `flush_pending_work` without a zero-argument `confirm_quit`, and has a negative control. It freezes three pre-existing gaps in a shrink-only `_KNOWN_GAPS`: Research workspace, STTS, Workflows. Their flushes ask through `push_screen_wait`, so each needs its own quit-safe fix; filed as a concern. `test_quit_flow_prompt_choke_point.py` now scans the new delegate module and expects the Library roots.

The quit is recorded at `_run_approved_quit_cleanup`, reading the DB at that moment. **Final review fixes (whole-branch review, 2026-10-04).**
- *C1 (Critical): a zero-second autosave timer.* Once a burst's max wait had run out without its timer firing, the next keystroke armed a 0 s timer. Textual 8.2.8 kills a 0 s Timer with ZeroDivisionError before it calls back, and the callback was the only thing that ended a burst, so autosave stayed dead and stopping the app raised. `library_note_autosave_delay` now never returns less than `AUTOSAVE_MIN_DELAY_SECONDS` (0.05 s). The burst ends when a save of the note starts (`note_save_starts`, called from `LibraryScreen._save_library_note`) instead of in the timer callback, so a key landing between the timer and its save worker keeps what is left of the max wait. The unit test that asserted `0.0` against a fake `set_timer` now asserts a positive delay, and `Tests/Library/test_library_note_autosave_max_wait.py` arms an expired burst on a real Textual message pump. `Tests/UI/test_library_note_autosave_recovers.py` (PR-gated, two boots, about 20 s) reads the database row after Keep editing on a refused quit and after a rail switch away and back.
- *I1: typing in a synced note held its folder.* The max wait makes a second save during a sync pass routine, and the executor fences a folder when a note moves on mid-write. A save of a note whose previous save hinted a pass now waits for that pass first, bounded at 3 s (`RESAVE_SYNC_PASS_WAIT_SECONDS`, shorter than the 5 s flush bound so a flush that waits can still save) and shielded: `_LibraryDatabaseNoteSessionPort.settle_before_save`, awaited by `DatabaseNoteSessionCoordinator._drive_saves` before it reads the draft it saves. A note in no synced folder never waits. Past the bound the save proceeds and a hold is visible and healable as before; TASK-34000.51 owns the durable runtime fix.
- *I4: Ctrl+Q did not wait for the pass its own flush hinted.* After a clean flush `confirm_library_quit` awaits the runtime's `settle()`, bounded at 5 s and shielded (`await_sync_pass`), so a synced note's file holds the last edit when the app exits.
- *Tests.* `Tests/Notes/test_notes_sync_resave_window.py` (PR-gated, admission-sensitive step) drives the shipped session and port over the production runtime, executor and a real vault; `Tests/UI/test_library_synced_note_typing_extended.py` types steadily in the real app and quits from a synced note (outside the PR gate).
- *Live, 160x45, isolated harness (captures in `qa/notes-library-ux-review-2026-10-02/fixes/final-review/`).* After Keep editing on a refused quit held past the 10 s max wait, the fixed draft and the typed text saved on their own within 3 s. A note left dirty by a rail switch for 38 s saved within 2 s of returning. 404 keys in 62 s in a synced note: 10 saves, the folder healthy at every sample, no open operation, and the file equal to the note. No traceback and no ZeroDivisionError in the run log.
- *Task 1's old flake (a save stuck in `saving` plus a shutdown hang, 1 run in 6).* Not explained by C1: that test never reaches an expired burst, and its signature was a worker-thread call that did not return, not a dead timer. It did not recur in this wave's runs.
