## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-34100.16.1's review round v5r1. Custom tokenizers live in one folder shared by every profile, `~/.config/tldw_cli/tokenizers`. When a backup carries that folder (`tokenizers.custom` as an included root), restoring it as an isolated profile places it at the new machine's shared folder. The restore engine accepts that only if the folder already exists there as an empty, owner-only container (`restore_plan._tokenizer_container_owner`). On an ordinary new machine the folder does not exist, so the nearest existing parent, `~/.config/tldw_cli`, overlaps recovery-bootstrap, and every folder the user picks is refused at Review restore with `isolated_destination_parent_overlaps_control`. Dev's own round-trip harness (`Tests/Backup_Recovery/test_console_artifacts_roundtrip.py`) makes that container by hand before restoring.

TASK-34100.16.1 stopped the app from creating the folder empty when Console opens, so profiles that never add a tokenizer now back up without that root and restore isolated on a fresh machine (verified live, evidence `g161v5-a`/`g161v5-b`). Still affected:
- profiles that hold real custom tokenizers;
- profiles where an earlier build already created the empty folder at 0755. Their archives still carry it, and a 0755 folder also fails the owner-only check.

Live evidence of the refusal (rebased tree before the fix): `.worktrees/setup-wizard-ux-qa/evidence/g161v5-rt/05-07`, `g161v5-s/07`.
