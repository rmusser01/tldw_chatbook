## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: found by the TASK-32633 slice (TASK-34000 wave 1, Task 4) while proving
that restoring a deleted synced note brings its folder back to healthy. It
does -- and the next disk edit of that file then puts the folder into
"⚠ Needs attention" with nothing to review, for good.

The binding carries the note's `version` as a proxy for "the note is still
what we last synced". `NotesSyncExecutor._validate_initial` refuses an
`update_note` with `stale_observation` when `binding.note_version !=
request.note.version`, even though the same check also requires the note's
content to match the baseline (`_note_matches_baseline`). A soft-delete and
restore bumps the version twice while leaving the content alone; a
keywords-only edit does the same once. The reconciler, which is digest-based,
rightly sees no change, so no `update_file` ever runs -- and `update_file` is
the only path that rewrites the binding's `note_version`. From then on every
`update_note` the file side asks for is refused before an operation is
journaled: the root publishes `needs_attention` / `review_changes` with no
`action_id`, `list_incomplete_operations()` is empty, and a manual Check shows
a clean plan with one `update_note` that cannot be applied.

Pre-existing: the same sequence without any signal (restore, Check changes,
then a disk edit) wedges the same way. Pinned as a strict `xfail` in
`Tests/Notes/test_notes_sync_delete_restore_signal.py::
test_a_disk_edit_after_a_restore_still_flows_into_the_note` -- turning that
marker off is the acceptance test.

Two more facts from the TASK-32633 review (2026-10-04): the hold survives a
Check + Apply (`needs_attention / stale_observation`), another `note_changed`,
and a restart, where it becomes a durable hold. It is not strictly permanent:
editing the note in Chatbook turns it into an ordinary "Both file and note
changed" conflict, and Keep file completes and re-bases the binding (that is
the user-facing workaround until this lands). No data is lost and no side
wins silently.

The obvious shortcut is to drop the version clause. Decide deliberately: the
content clause already carries the invariant the version proxies, and the
fresh re-observe (`note != request.note`) already guards the observation
itself -- but the version proxy also appears at the resolution and reviewed
paths (`:1723`, `:2548`, `:3274`, `:5385`), and whichever way it goes, every
baseline-commit site has to agree.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Decision: the version proxy is dropped from every precondition against the
live note.** `binding.note_version` is the note's version at the last baseline
commit. It stays written at every commit site and is compared only against
journal-recorded binding facts; the content baseline (`_note_matches_baseline`)
and the exact fresh re-observe (`note != request.note` in `_validate_initial`,
`_classify`) carry "the note is still what we synced". The rule is recorded in
the `_note_matches_baseline` docstring and pinned by an AST scan. The rejected
alternative (re-basing the binding's version whenever a pass sees an unchanged
note with a moved version) needs a store write during a mutation-free Check and
a second mechanism for the same invariant.

**Every executor read of `binding.note_version`, reconciled** (line numbers at
base `76d5d157aa`):

- Dropped -- precondition against the LIVE note, each already guarded for
  content next to it: `_admit_undo` :1723 (`_note_matches_baseline` in the same
  conjunction), `_require_undo_binding` :2548 (reached only after
  `_require_undo_restored`, which compares the note's content digest to the
  journaled source payload and the restored-authority digest),
  `_require_move_restore_owner` :3274 and `_require_restore_owner` :5387
  (`_note_matches_baseline` in the same conjunction; `_classify_restore`
  follows), `_validate_initial` :4018 (`_note_matches_baseline` plus the fresh
  re-observe), `_binding_matches_current` :5557 (`digest_matches` is
  `_note_matches_baseline` for update_note; every caller first passes
  `_require_desired` / `_require_keep_both_desired` / `_require_restored`,
  whose `_classify` demands the exact observed note).
- Kept -- binding vs the journal-recorded copy of the binding itself:
  `_binding_matches_reviewed` :5523 (`reviewed.get("note_version")`).
- Dropped in fix round 1 -- `reconstruct_request` :1386-1387 required
  `operation.expected_note_version == reviewed_binding["note_version"]`: the
  LIVE note's version at admission against the binding's version, true by
  construction only while `_validate_initial` refused version-only moves.
  After the six-site change it made any version-only-moved update_note
  interrupted after admission unrecoverable (`recovery_authority_changed`,
  root published `failed`; reviewer probe). The remaining guards at that site
  carry the invariant: `_binding_matches_reviewed` (:1364, the live binding
  equals the journaled binding), the journaled payload digest against the
  journaled baseline digest (the admitted note was at baseline), and on
  resume `_require_reviewed_owner` + the exact re-observe (`_classify` at
  `RECOVERY_ADMITTED`, `_require_desired` at `FIRST_AUTHORITY_APPLIED`).
- `expected_note_version` readers, audited: :1419, :1563, :1575 compare the
  live note to its own admitted version (exact re-observe, keep); :2796
  (`note.version != expected + 1`, post-write, keep); :4250, :4270 compare the
  operation record to the request's note (keep); :1920 compares two journal
  facts of the same note (keep). None compares it to a binding version.
- Kept -- recorded into recovery metadata: :1823 (`_encoded_binding`), :3515,
  :4048, :4138. Every `note_version=note.version` commit site is unchanged.
- Unaffected -- operation-side checks of `expected_note_version` / `note.version`
  (:1407, :1551, :1563, :2786, :4240, :4260, `_classify` :5628).
