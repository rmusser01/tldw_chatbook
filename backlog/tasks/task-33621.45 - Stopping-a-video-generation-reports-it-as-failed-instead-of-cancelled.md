## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From TASK-33622.16 (PR #3006). Pressing Stop during /generate-video surfaces 'Video generation failed (VideoGenerationError)', although the user cancelled it. A cancel should read as a cancel, with no failure copy.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Stop during a generation produces cancelled copy, not a failure
- [x] #2 A real backend failure still reads as a failure
- [x] #3 Tests pin both
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Same code path as TASK-33621.50: adapters raise a plain VideoGenerationError on cancel and the Console's generic except reports 'Video generation failed (VideoGenerationError)'. Add a typed VideoGenerationCancelled (MiniMax + ComfyUI), catch it before the generic handler in generate and regenerate, and report cancelled copy; a real backend failure keeps the failure copy. Tests pin both.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The introduced typed VideoGenerationCancelled passes through the worker and
is caught before generic failures by Generate/Regenerate. Cooperative Stop
reports the local stop plus MiniMax's cancelled/refused/deleted/unconfirmed
answer. Real failures retain failure copy. Focused adapter, worker, helper,
Regenerate and mounted recorded-response evidence is recorded in
Docs/superpowers/qa/2026-11-01-pr3333-backlog-integration.md.

Reopened during PR3333 integration: AC#1 is broader than the qualified fix.
Stop during an in-flight GET or download can still finish as failure/success
at inherited poll boundaries. The current tests qualify cooperative Stop
paths and failure controls; historical 2026-10-30 live/source-branch checks
are not a universal Stop guarantee or current live-vendor qualification.
No new ADR: existing ADR-044 governs the unchanged ownership boundary.
<!-- SECTION:NOTES:END -->
