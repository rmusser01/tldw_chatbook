## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the same live profile as TASK-33620.15.3 (2026-10-10; 160x45, Anthropic haiku through the review proxy, 30 sampled sends; every UI-loop callback of 10 ms or more timed and the main thread sampled every 4 ms between acceptance and the provider call).

The Console's rail-and-controls projection runs on the UI loop from two places during a send window:
- poll ticks (`_sync_console_rail_and_controls` > `run_console_config_sync` > the config participants' operation): 92 ms per send in total, worst single callback 173 ms;
- explicit syncs, scheduled as workers on the loop: 39 ms per send, worst 155 ms.

About 131 ms per send in all. By main-thread samples inside it: the config operation's entry and exit (storage admission) 30-35%; the settings summary 20% (ChaChaNotes `has_active_memory_selection`); the control bar 17% (`get_trajectory_rows` through `library_activity_snapshot`); the Inspector state 14% (registry and AgentRuns reads); composer actions 8%.

Counterfactual on the same data: moving only the projection's storage admission and database reads off the loop takes the median longest callback after acceptance from 95 to 86 ms; together with the GC fix (TASK-33620.15.3) it is 48 ms, with sends that block for 100 ms or more down from 15/30 to 2/30.

Fix direction: worker-refreshed snapshots for those reads; coalesce the explicit syncs requested during run start; a warm-hit fast path for the config operation. Caveat: the profile path has about 10 components against about 5 for a real install, and storage-admission and posture costs scale per component.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The run's projection no longer runs the native checked-config operation on the UI loop or defers into whole-sync replays; it reads the Library activity rows and the Inspector's registry and appearance reads off the loop outside a send's start, and a run start's explicit syncs share one projection. A send's durable commit keeps the Console's whole syncs quiet, and a send's start reads its display rows on the loop as the base does. Sends reach the provider no later than on dev (AC#7); the projection's UI-loop time per send window fell 15% (AC#4, restated). Halving it is TASK-36571.

**Measured first (AC#1), dev 5b5920b8e2** (Anthropic haiku via the review proxy, 160x45, PYTHONPATH-only probe; evidence `uxrev/evidence/bd5/P4/`): 7 projections per send window, 57-65 ms. On-loop I/O inside them was ~9 ms (trajectory rows 2.6, registry 2.7, appearance 0.2, posture 0.1, native checked operation 3.8). The rest came from a cascade: an idle Console's checked display had always expired by the first poll tick, so that tick ran the native operation and deferred to a whole-sync replay (3.5 whole-sync requests and 0.8 replays per window). Harness: one projection per window, 6.7 ms.

**Changes**
- Library activity (`library_activity.py`, `view_workers.owned_display_read`): a 'console-library-activity' view worker reads the durable rows, keyed (database, conversation, activity revision). Only the newest read publishes; teardown and a local storage pause publish nothing. A send's start reads synchronously (`live_reads`).
- Workspace (`workspace.py`): in a run tick's shared context build, the registry display reads and the appearance map serve their last snapshot and re-read once off the loop, installing only for their own generation or map. This is off during a send's start.
- Config (`console_spend_projection.py`, `config_sync.warm_run_presentation`): the run poll's start re-reads the checked display, and while the poll ticks a projection re-reads it at half its life.
- Coalescing (AC#3, `config_sync`): a context-snapshot publication during a run is a cadence input. An explicit sync within one poll interval of the last projection leaves its projection to the poll's next tick, and a stopping poll hands a waiting request to the running sync's re-arm.
- Durable commit quiet gap (AC#8): `console_native_commit.durable_commit_window` marks an ordinary send's commit per store while its worker thread runs. `config_sync._held_for_durable_commit` lets the commit's first whole sync run and holds the rest until the poll's next tick, which skips; explicit syncs leave `_console_sync_requested` for the tick after. Each commit holds once, there are never two skipped ticks in a row, and with no poll nothing is held. It is wired through `run_periodic_console_sync` and `begin_console_sync`'s return value (chat_screen.py net zero).
- Send start (AC#2 carve-out): `config_sync.note_send_accepted` runs on both acceptance paths (the received intent a stock send takes, and the dispatched draft commit). `console_send_diagnostics.provider_entered_at` is noted at the provider request. Between them (3 s at most), the display rows above are read on the loop.
- chat_screen.py ratchet row 24344 -> 24345 with a dated owner-decision comment (the warm-up call).
- `test_console_tab_publication_maintenance.py`: waits for idle across three drained pauses (it took the session lock while the resume's whole sync was queued).

**Rework (owner decision 2026-10-23: sends must never be slower).** The first live round (30 sends per arm) had the projection at -14% but warm sends a median 31 ms later. In order:
1. The base's deferral had kept the UI loop quiet through the durable commit. On the branch, the first tick's re-armed whole sync and the next tick painted inside it. A first hold that let a held request force the next tick still painted twice in the commit (203 vs 182 ms). Holding until the next tick, which then skips, left one sync per commit.
2. With the hold in place, warm sends were 7 ms sooner but first sends 23 ms later (paired, 20 first sends per arm). An executor work-item probe found +264 ms of thread CPU per first send. Each off-loop display read opens its own SQLite connection (`run_owned_db_call`: 34 ms wall, 10 ms CPU alone; 20-60 ms CPU each in the app), and these reads started at acceptance and right after the commit. A probe that put them on the synchronous path made first sends 66 ms sooner (1418 -> 1352 ms, 8 per arm), hence the send-start window. A first version marked only the dispatched path; a live probe showed the stock send (received intent) never opened it, and a test now drives that path. The checked-display warm-up was cleared the same way: turning it off changed first sends by 3 ms.
