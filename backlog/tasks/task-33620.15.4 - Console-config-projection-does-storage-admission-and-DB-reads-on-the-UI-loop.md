## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the same live profile as TASK-33620.15.3 (2026-10-10; 160x45, Anthropic haiku through the review proxy, 30 sampled sends; every UI-loop callback of 10 ms or more timed and the main thread sampled every 4 ms between acceptance and the provider call).

The Console's rail-and-controls projection runs on the UI loop from two places during a send window:
- poll ticks (`_sync_console_rail_and_controls` > `run_console_config_sync` > the config participants' operation): 92 ms per send in total, worst single callback 173 ms;
- explicit syncs, scheduled as workers on the loop: 39 ms per send, worst 155 ms.

About 131 ms per send in all. By main-thread samples inside it: the config operation's entry and exit (storage admission) 30-35%; the settings summary 20% (ChaChaNotes `has_active_memory_selection`); the control bar 17% (`get_trajectory_rows` through `library_activity_snapshot`); the Inspector state 14% (registry and AgentRuns reads); composer actions 8%.

Counterfactual on the same data: moving only the projection's storage admission and database reads off the loop takes the median longest callback after acceptance from 95 to 86 ms; together with the GC fix (TASK-33620.15.3) it is 48 ms, with sends that block for 100 ms or more down from 15/30 to 2/30.

Fix direction: worker-refreshed snapshots for those reads; coalesce the explicit syncs requested during run start; a warm-hit fast path for the config operation. Caveat: the profile path has about 10 components against about 5 for a real install, and storage-admission and posture costs scale per component.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The run's projection no longer reads the trajectory sidecar, the workspace registry, the appearance map or the checked config through the native operation on the UI loop, and a run start's explicit syncs share the poll's projection. AC#4 is NOT met: on today's dev the projection is mostly render work, and it fell 14%, not half. Left In Progress for an owner decision (see "AC#4" below).

**Measured first (AC#1), dev 5b5920b8e2** (live: Anthropic haiku through the review proxy, 160x45, PYTHONPATH-only probe timing every outermost projection entry and its children on the UI thread; evidence `uxrev/evidence/bd5/P4/`, analysis scripts there).
- The 2026-10-10 profile (131 ms/send, ~85% admission and DB reads) no longer describes dev. Dev has since moved the settings summary's memory read onto a worker snapshot (ConsoleContextReadSnapshot) and added the checked config display (PR #3023) and the cadence (#3191).
- Per send window (acceptance to provider call), dev projected 7 times for 57-65 ms. On-loop I/O inside it was ~9 ms: trajectory rows 2.6, registry display reads 2.7 (once per send, after the commit's membership write moved the generation), appearance 0.2, config posture 0.1, and the native checked operation 3.8 (1.0 per window).
- The bigger cost was a cascade: an idle Console's checked display had always expired by the first poll tick, so that tick ran the native operation and the same tick's rail-visibility read deferred to a whole-sync replay 0.2 s later, whose follow-up re-armed again. 3.5 whole-sync requests and 0.8 replays per window; explicit projections 29 ms of it.
- A probe that wrapped `context_control_inputs` pushed the presentation read onto its synchronous fallback (it is identity-checked); dropped, recorded in lessons-live-verification.
- Harness (mounted send harness, in-memory DB, 12 sends per arm): one projection per window, 6.7 ms on dev; the harness has none of the live I/O or the cascade.

**Changes**
- Library activity (`library_activity.py`, `view_workers.owned_display_read`): a 'console-library-activity' view worker reads the durable rows, keyed (database, conversation, activity revision); the projection renders from what landed and holds the shown view across a revision move until the newer rows land. Newest read only publishes; teardown publishes nothing; a local storage pause neither renders nor caches; other failures degrade as before. In-memory/custom stores keep the synchronous read. `library_activity_snapshot(durable_rows=)` (store row unchanged, net zero lines).
- Workspace (`workspace.py`): inside a run tick's shared context build, with the run poll ticking and the stock services over file databases, the registry display reads serve the last generation's snapshot and the appearance map its cache, with one 'console-workspace-display-reads' re-read that installs only for its own generation (or map) and publishes to the next tick.
- Config (`console_spend_projection.py`, `config_sync.warm_run_presentation`, one call in `_start_console_transcript_sync_timer`): the run poll's start re-reads the checked display, and while the poll ticks a projection re-reads it at half its life while the current one renders. Idle Consoles keep re-reading on expiry.
- Coalescing (AC#3, `config_sync`): a context-snapshot publication during a run is a cadence input (`published`), owed to the stop; an explicit sync within one poll interval of the last projection leaves its projection to the poll's next tick; a request waiting a poll interval projects in whichever sync comes first; a stopping poll hands a waiting request to the running sync's re-arm. No poll: unchanged.
- chat_screen.py ratchet row 24344 -> 24345 with a dated owner-decision comment (the warm-up call).
- `test_console_tab_publication_maintenance.py`: the pin took the session lock while the resume's whole sync was queued (1 of 4 runs alone on dev); it now waits for idle across three drained pauses.
