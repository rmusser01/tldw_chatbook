## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ADR-012 (`backlog/decisions/012-provider-credential-settings-boundary.md`, Accepted) rules in its 2026-09-19 amendment (TASK-32806.2) that a stored credential outranks the provider's environment variable. The 2026-10-03 keychain amendment keeps that order. A stored credential is the `api_settings.<provider>.api_key` in config, or a keychain key recorded through `credential_source`. The environment variable is the fallback, then legacy `[API]`. The reason: a key the user types into Settings must take effect, where env-first let a stale shell `OPENAI_API_KEY` silently override what the UI showed. Two resolvers are out of line. The hosted provider engine (`LLM_Calls/hosted_provider_engine.py` `_resolve_api_key`, the 33 engine presets) resolves explicit, then environment, then stored. The custom-endpoint registry (`Chat/custom_endpoint_registry.py:495` `resolve_entry_credential`) resolves environment before stored; ADR-146 (`backlog/decisions/146-console-custom-endpoint-registry.md`) recorded that order as mirroring the provider semantics of its time. moonshot, zai, qwencloud, the bridged chat handlers, `config.get_api_key` and readiness already follow ADR-012.

**Owner decision (2026-10-25, re-confirmed with ADR-012 in view): keep ADR-012.** A stored credential wins over the environment variable for every provider, and the stragglers are aligned. The engine's existing fail-closed handling of an unusable stored key stays, because a placeholder the user typed must be surfaced, not silently shadowed.

Source: architecture review 2026-10-25, `Docs/QA/architecture-review-2026-10-25/report.md` §F11; claim-by-claim verification in `Docs/QA/architecture-review-2026-10-25/verification.md` (origin/dev 7a5e2513c5).
