## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
With `[chat_defaults] provider = "custom-ep:gpu-box"`, opening Settings (F4) kills the app: an unhandled ValueError from `Chat/provider_readiness._validate_provider_key` ('Provider key is invalid.'), raised under the Settings detail pane. Reproduced on TASK-33002.5's base and head exports on a scratch profile (app log rows `event=unhandled_exception ... raise_function=_validate_provider_key`, then App Unmounting). Pre-existing; not touched by Phase 2. Settings' `_provider_display_name` also shows such an id raw, because it calls `provider_display_name` without the config.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Opening Settings with a custom-endpoint default provider does not crash, and Providers & Models shows the endpoint's display name
- [x] #2 A mounted private-profile test opens Settings on that config and fails on the unhandled exception
- [x] #3 A default naming a registry slug with no entry (dangling) opens Settings with an honest not-ready "endpoint not found" state instead of crashing
- [x] #4 Readiness for a registry id resolves through the registry the way Console does (the family's readiness plus the entry's own API-key rule), for every caller of provider readiness, and ordinary providers read exactly as before
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Reproduce with a failing mounted private-profile Settings test (registry default and dangling slug) plus readiness-seam tests; reproduce live at 211x44 on a scratch profile.
2. Fix at the shared seam: `get_provider_readiness` resolves `custom-ep:<slug>` (either spelling) through the registry before canonicalizing it, so every caller (Settings, Home, Chat, wizard, evals, tools) is covered.
3. Settings `_provider_display_name` reads the registry entry's display name; Providers & Models names the dangling state.
4. Check Home and Overview readiness; run covering suites against a baseline; preflight.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- Root cause: `get_provider_readiness` canonicalized `custom-ep:gpu-box` to `custom_ep:gpu_box` and built a `ProviderReadiness` with that key, which `_validate_provider_key` rejects. It is the shared seam for all readiness callers (nine in Settings, plus Chat, Home through `build_console_settings_readiness`, the wizard, evals, the tools window and the permission summary), so the fix is there, not in Settings.
- New `_custom_endpoint_readiness` in `Chat/provider_readiness.py`, which runs before the normal path. It accepts both spellings (`canonical_custom_endpoint_id`). A resolvable entry reads as its family's readiness (`family_execution_key`) plus the entry's declared-credential rule. That rule reuses Console's `_custom_endpoint_missing_key_readiness`, which the gateway and agent routing already import. The record carries the entry's display name. The family record's credential is dropped: it comes from the family's slot table (for example `[api_settings.custom]`), never from the entry, and the send path resolves the entry's own credential. A dangling slug reads "Endpoint not found" (a new reason, mapped to `endpoint_missing`) with `provider_key="custom"`, the ADR-146 fallback family. Console does not reach that record for a dangling default: its `provider_unsupported` branch runs first and blocks with "Provider blocked: 'custom_ep:gone' is not available in Console yet".
- Settings: `_provider_display_name` returns the registry entry's `display_name`. `_provider_key_status` and `_provider_credential_status` say "Not ready · endpoint not found; choose another provider" for a dangling slug, beside the existing "Invalid provider settings" branch. Overview reads "Not ready: Endpoint not found". Docs/User_Guide/settings.md (Custom endpoints section) describes both states.
- Home and Overview: Settings Overview called `get_provider_readiness` directly and crashed. Home goes through `build_console_settings_readiness`, which already resolved a valid entry to its family key. For a dangling slug it canonicalized to `custom_ep:<slug>` and raised, but Home's `try/except` swallowed it and just reported not-ready, so it never crashed. It now gets the honest state. A seam test pins both cases.
