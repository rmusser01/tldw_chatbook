## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while measuring TASK-33628.5 (dev 7d155170dc, ConsoleHarness + file-backed ChaChaNotes DB, 160x48). Selecting message 1 of a 1,000-message chain mounts all 1,000 rows (8,085 widgets under #console-transcript-region) and the app takes 54 s to settle; at 3,000 messages it is 24,085 widgets and 183 s. With those rows mounted, one toggle of the console-transcript-region-focused class (frame.sync_console_focus_paint, run on every DescendantFocus/Blur) costs 9.6-12.2 s at 1k and 29-37 s at 3k, almost all in textual_css_fastpath.apply restyling every descendant. After the 1k selection had settled, a Delete of that subtree still held the loop for up to 2.6 s (10.2 s busy in total), and Undo -- which reselects the restored root, re-mounting the rows -- held it for up to 17.4 s (56.7 s busy). The equivalent 3k run hit the 300 s pytest timeout before its Delete finished (the selection settle and two class toggles took about 250 s of it). The durable write TASK-33628.5 moved off the loop was 0.15-1.8 s of this. The figures and the attribution above are the whole record: they came from a throwaway ConsoleHarness probe with stack sampling that was not committed, and TASK-33628.5's notes carry only the summary. Re-measure before optimising (lessons-testing-evidence, TASK-33628.5 entry).

## Implementation Plan

Measured first (ConsoleHarness 160x48, file-backed DB, branch = dev 8c4dfe59a2 + TASK-33628.5): selecting m0 of a 200-message chain mounts all 200 rows (1,689 widgets); a focus change into the transcript restyles 4,965 nodes, from two subtree restyles: Textual's watch_has_focus on ConsoleTranscript (every mounted row) and the console-transcript-region-focused class toggle on the region (every mounted row again).
Root causes: (a) reveal_message treats a reveal as 'near' (plain boundary extension) until it exceeds the prune LOW watermark, 12,000 estimated lines by default, i.e. ~4,000 short messages; the task-501/Undo pending-selection handoff in set_messages extends the boundary with no bound at all. (b) the focus cue class lives on an ancestor of every row; (c) Textual restyles a focused container's whole subtree.
1. Tests first (red on origin/dev): production-shaped 3k linear chain - mounted rows/widgets bounded after selecting m0 and after Delete+Undo from m0 (restored root selected, tail not mounted); focus change restyle count bounded and touching no transcript row; a fidelity test proving no stylesheet rule makes a transcript descendant's style depend on the transcript's own focus.
2. Far reveal bound: a reveal or a pending-selection handoff whose newly mounted stretch exceeds one load-shaped window (initial window budget, capped by the low watermark) re-centres a bounded window on the target instead of extending the boundary; window math in a small lazily-imported helper so console_transcript.py does not grow.
3. Focus cue: put the focus class on the stable title row (the only thing its CSS paints) instead of the region; ConsoleTranscript restyles only itself on focus/blur.
4. Re-measure select/focus/Delete/Undo at 1k/3k on both arms; keep the TASK-15455/15777 windowing suites, delete/undo suites, edge-rail focus tests green; live-verify via launch.sh with a seeded 3k conversation.
5. Session 2 (found while measuring): an Undo whose restored root the kept window already held (select m0, then m30, Delete, Undo) skipped every bound above -- the ingest keeps the window start and the root is inside it, so no reveal runs -- and mounted all 3,000 rows. The handoff now re-centres there too when more than one window lands below the root. Pinned by a test that fails with that one branch removed (Undo planned 3000 of 3000 rows).
6. Session 3 (review fixes): tighten the window bound the long-chat pins use from a fixed 300 rows (about 5x the 64-row window) to twice the rows one load-shaped window holds, derived from the transcript's own budget, so a partial regression cannot pass; record that the far-reveal bound needs two-sided windowing (windowing and pruning on); file the lesson beside the class-flip entry it extends. Re-run the new pins on the head (green) and on origin/dev (red).
7. Session 4 (AC#3, 2026-10-09). Measured first on dev 46c3959526 (ConsoleHarness 160x48, file-backed DB, gc frozen, per-asyncio-handle timing plus a 1 ms stack sampler; host load average 20-24): the worst Undo loop iteration is 196-316 ms at 3,000 messages and 211-229 ms at 60. It is one screen-update step: Textual lays out the freshly mounted window three times (the first layout, the virtual-size relayout every fresh widget triggers, and the relayout after the transcript's scrollbar reappears), each pass re-arranging ~400-466 widgets (68-175 ms), then paints the screen (20-88 ms). The Undo's own sync step (100-133 ms, a third of it building the 64 rows) can land in the same loop iteration. Shrinking the window to 2 or 1 viewport in the probe drops the worst block to 127/114 ms, so the cost follows the number of fresh rows mounted at once. A forced relayout with nothing new costs 6-7 ms at 1,074 widgets.
8. Fix: restore progressively. A re-centred window, and an Undo or swipe hand-off whose window would mount more than two viewports of rows below the selection, mounts the selection plus two viewports first and hands the rest of the same planned window to a fill that reveals two more viewports per step, each after the screen has laid out the previous step (logic in the lazily-imported reveal module; console_transcript.py net-zero).
9. Test first: a production-shaped 3,000- and 60-message Delete+Undo pin that counts the rows each transcript mount adds (dev: one batch of 64/60) and requires every batch to be at most the fill chunk, the planned window to complete, and the restored root selected and painted. Show it red on dev, green on the branch; re-run the windowing, two-sided, Delete/Undo/quit, Library reader refresh and long-chat suites against a detached dev worktree by test id. Re-measure n>=5 per arm at 60 and 3,000 messages, and live via launch.sh with a seeded 3,000-message profile (the app's own event_loop_stall records).
10. Deviations found while measuring (session 4): one-viewport batches instead of two (A/B n=5: worst Undo 122-158 ms vs 143-205 ms at 3,000 messages); each batch waits for the previous batch's relayouts to settle (pending _layout_required at two polls 30 ms apart), because a size-only gate let two batches share one 158 ms pass; live sampling showed the remaining worst blocks were whole Console syncs, so one asyncio.sleep(0) splits the sync into its rails and transcript halves; and a reader following the tail (the usual state after deleting the last turns) is paced too, detached quietly and re-attached once the window is whole.

Approach (commits 17d9878936, fc61e797e2, 50d74386b5; tests 18a32d8e29):
- Far-reveal bound (new Widgets/Console/console_transcript_reveal.py, lazily imported so boot pays nothing). A reveal or pending-selection handoff counts as far once it would mount more than one load-shaped window (the initial window budget, capped by the prune low watermark). A far one re-centres a bounded window on the target. Before, "far" meant more than the low watermark (12,000 estimated lines, ~4,000 short messages), and the handoff that Undo reuses had no bound at all. A handed-off selection the kept window already holds is bounded too when more than one window lands below it: select m0, then m30, Delete, Undo mounted all 3,000 rows that way. _check_anchor stays detached until the re-centred target is placed, so the ghost-follow heal cannot throw the jump away. The bound needs two-sided windowing (windowing and pruning on, sane watermarks). With the windowing kill switch on, the whole history mounts anyway. With pruning off, a far selection or Undo still mounts every row between the window and the target, as before (stated in the module docstring).
