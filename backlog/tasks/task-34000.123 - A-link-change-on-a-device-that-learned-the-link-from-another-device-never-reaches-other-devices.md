## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: PR #3423 re-review 4 (question 7), confirming the implementer's concern 2 from the re-review 3 fixes. Pre-existing: measured identically on dev `cf24ef7ba3` and on the PR head `6e4f2b0cbe`, with no Delete forever involved.

Sync v2 organization LINK intents -- `notes.keyword_link` (note and conversation subjects), `notes.folder_link`, and through the same code path `notes.keyword_collection_link` -- send their `source_version` as the envelope's `object_revision` (`tldw_chatbook/Sync_Interop/notes_outbox_producer.py:55`). A link's version is inferred (`notes_organization_sync_service.py:1892`): `_intent_lineage_with_cursor` sets it to one more than the highest version among this device's OWN intents for that link (`tldw_chatbook/Notes/notes_organization_repository.py:648-656`). The server head's `object_revision`, which the same function records as the base (`:634-646`), is ignored. So a device whose own history for a link is shorter than the server's sends a revision lower than, or equal to, its own base. A link's payload is its identity only, so its upsert and its tombstone have the same `payload_hash`. Other devices apply through `NotesOrganizationRepository.apply_envelope`: an equal revision with an equal hash is a `duplicate` (`:179-193`), a lower one is `stale` (`:170-178`), both are reported as a no-op (`Sync_Interop/domain_adapters/notes_organization.py:87-88`), and nothing changes.

Measured on the server-shaped transport of `Tests/Sync_Interop/test_notes_organization_two_device.py`:
- **Removal not applied.** Device A tags a note and files it in a folder; device B pulls both. B removes the keyword and takes the note out of the folder, and pushes them at revision 1 on base 1. A pulls two `duplicate`s and keeps both. A third device that pulls the history keeps both too. The server's heads are tombstones.
- **Removal after a longer history.** A adds, removes and re-adds the keyword (revision 3); B removes it at revision 1 on base 3. A reports `stale` and keeps it.
- **Re-add not applied.** A adds and removes the keyword (revision 2); B re-adds it at revision 1 on base 2. A reports `stale` and never gets the keyword back.
- **Later conflict.** After the first case, A's own next change to that link is based on A's own head, not the server's, and the server-shaped transport refuses it.

What the user sees: the device that made the change shows it; every other device keeps the old keyword or folder on the note, or never gets a re-added one, with no error and no conflict, and sync reports success. A later change to that link from another device may then fail as a sync conflict.

Note content is not affected by this mechanism: its envelopes carry no client `object_revision`. Organization resources (keywords, folders, collections) take their version from the row's own version, not from local intents, and were not probed for a similar lag.

Unknown: the client stores whatever `object_revision` the server returns when it accepts a push. If the real tldw server assigns its own revision and serves that on pull, the problem is masked there. The repo's fake echoes the client's revision.

This is not fixed in PR #3423: there, the purge pin for an unlink a device learned from the server asserts the server's heads, not the other device's links, for this reason.
