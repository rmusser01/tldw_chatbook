## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** The conversation rail's 'Filter visible titles' input does not keep what the user types. About 200 ms after each pause, the debounced search rebuilds the whole tray, and that includes a new search Input. The new input is seeded with the stripped, lowercased query, so 'OK' reads back as 'ok'. The next keystrokes then either:
(a) replace the whole query, because the re-focused Input selects all ('OK', wait 1 s, ' 9' gave '9' / '0 matches');
(b) are dropped, because focus lands on the Conversations section toggle ('A' then 'B' 300 ms apart gave 'a');
(c) hit a screen-level single-letter binding: typing 'Say' opened the full-screen Trace twice.

A filter that fights typing gets abandoned, pushing users to Ctrl+K or Library.

The verifier found that the result count mismatch has a different cause from the one reported. The persisted DB search counts matches in message content, but the rows are re-filtered by title, workspace and status only. A content-only match is therefore counted but never shown: filtering 'zebra' read '1 match. Showing 0 of 1' with no rows. A 'Show all' control would not fix this. Verdicts: live CONFIRMED, code and skeptic PARTIAL, on dev 64579cce2c.

**Severity / prior art.** P1, triage NEW. Related: TASK-1900 (Done), TASK-15454 (Done), TASK-354 (Done). The docstring in `console_workspace_context.py` records that the input is re-mounted on every changed sync while typing.

**Suggested direction.** Keep one Input instance across syncs and update only the result list and status. Never write the normalised query back into the Input; normalise only for matching. Any programmatic refocus keeps the cursor instead of selecting all. Make the total and the rows use the same matching rule: either count title matches only (as the placeholder promises) or show content-matched rows with a 'matched in messages' hint.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The rail's 'Filter visible titles' now keeps exactly what is typed, and its count and rows follow one title rule (owner decision 2026-10-27; AC#4 amended first).

Approach
- Raw query in state: build_console_conversation_browser_state stores the text as typed; only the matcher normalises (fix for 'OK' -> 'ok').
- One input across rebuilds: ConsoleWorkspaceContextTray gains _KeepsConversationFilterRow (between RecomposeCaptureGuard and Vertical). A rebuild removes every child except the mounted filter row, composes with that row offered back, and mounts the new children around it. The input keeps its instance, value, cursor and focus, so no select-all replace, no focus landing on 'New conversation' and no 'y' reaching Trace. A focused kept input is never written from state (a sync can lag the keystrokes); an unfocused one shows the state's raw query silently (keeps dev's stable-ids test contract). Clear empties the kept input itself. select_on_focus=False on the filter.
- Settle after a kept-row rebuild: the kept row keeps its geometry, so TASK-2154.3's 'every child reads 0' guard stopped catching mid-rebuild fits and the tray was pinned short (TASK-37160's mechanism, now routine); the bounded section then hid the counted row. The fit now waits for the screen's next layout after such a rebuild, then asks the owning ConsoleBoundedSection (matched by type -- its viewport shares the id prefix) to re-measure.
- Titles only: console_conversation_title_matches_query is the one matcher (state builder + flat-lane controller filter); the flat lane asks storage for title_only results, a new flag on ChatConversationService.list_conversations / CharactersRAGDB.search_conversations_page (count and page match the title as a literal substring, LIKE wildcards escaped; refused with query_terms). Library / Ctrl+K keep content search.

Evidence

No errors in the app log. Captures under the session's evidence/bd5/U12/.
