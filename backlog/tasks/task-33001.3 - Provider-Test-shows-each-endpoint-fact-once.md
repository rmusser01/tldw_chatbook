## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This happens on URL-based providers only (Chat/provider_endpoint_contract.py:24). How the duplicate gets in:
1. Settings Test builds its detail line in _provider_readiness_test_report, which appends any stored evidence for the current draft identity (UI/Screens/settings_screen.py:15143-15150).
2. action_settings_test_category passes that detail to the probe worker (:30801-30824).
3. _apply_provider_endpoint_probe_outcome appends the fresh evidence to the same detail (:15458-15469).

ProviderTestEvidenceStore.begin (Chat/provider_test_evidence.py:593) resets the store, but the stale copy is already inside the string. So a second Test on an unchanged draft after a failed probe shows 'model listing failed' next to 'model listing reached', and 'generation not tested' twice. While the probe runs, the in-flight line shows the old failure beside 'checking' (:30806-30808).

Both appends arrived in #2365 (939dee8dc2). Existing tests cover single runs only (Tests/UI/test_settings_configuration_hub.py:4533, :4576, :4622). Cloud providers are unaffected, because their Test never probes. That is by design (TASK-191, TASK-30011 AC#2).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
- Root cause: `action_settings_test_category` built its detail with `_provider_readiness_test_report()`, which appends the stored evidence for the current draft identity, and then used that same detail for the in-flight line and for the probe worker, whose `_apply_provider_endpoint_probe_outcome` appends the fresh evidence again. `ProviderTestEvidenceStore.begin` resets the store, but the stale copy was already in the string.
- Fix (UI/Screens/settings_screen.py only): `_provider_readiness_test_report` takes a keyword `probes_when_passing` (default False). When it is set and the report passes, the stored evidence is left out. The action computes the probe URL first and passes `probes_when_passing=bool(url)`, so the stored copy is dropped exactly when a probe will run. The in-flight line is then "... | model listing checking | generation not tested", and the settled line carries only the new probe's facts. Every other path is unchanged: a blocked Test, a cloud provider (never probes, may carry Console generation evidence), and the subscription refresh caller still show the stored evidence.
- The toast already carried "generation not tested" once (the readiness summary says "Live generation has not been tested"); AC#2 is now pinned by the new test.
- Test: `test_settings_provider_test_rerun_reports_each_endpoint_fact_once` in Tests/UI/test_settings_configuration_hub.py (under the file's `private_profile_test` wrapper, so it runs locally despite ADR-126). Negative control: with BASE's settings_screen.py it fails on the in-flight line, and with the in-flight assertions removed it still fails on the settled line.
- The three single-run pins (AC#5) pass unchanged; they are ADR-126-red locally, so they were run under a temporary, uncommitted private-profile wrapper and the file was restored.
- Docs/User_Guide/settings.md: one sentence on re-running Test, plus a Verified-against stamp from a live drive on a scratch profile (llama.cpp, endpoint down then a stub `/v1/models` up).
- Fix round 1 (review): a Hypothesis property test in Tests/Chat/test_provider_test_evidence.py pins the invariant the fix relies on: whenever `evidence_for(identity)` returns evidence, `begin(identity)` accepts it. So on the path where `begin` refuses an older draft generation, no stored copy could have been shown before the fix either, and dropping it loses nothing. It drives every store mutator, including save/rebase, and a scratch mutation (rebase keeping the older tested identity) makes it fail. The AC#5 pins and the vllm fence pins were re-run independently under a temporary private-profile wrapper, then restored (7 passed). Breaking the fence makes `[t]` fail with a TypeError, so that negative pin still bites. The live drive was repeated at this commit on a fresh scratch profile. The settled line after the reachable run was "configuration=complete | credential present, not verified | model listing reached | selected model confirmed | generation not tested", with no "failed" on screen. The toast was "Configuration check complete: llama.cpp is configured; model qwen. Live generation has not been tested; model-listing evidence updated; generation not tested."
