## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-33621.30's review (2026-11-24). Since TASK-33621.30, a chat whose active leaf is an empty checkpoint-free reply (`REMOTE_ACCEPTED` / `REMOTE_DISPATCH_STARTED`) tells the user to send a new message, and that send now works.

**What gets sent.** The provider request ends in two consecutive user turns, `[…, user, user]`:
- `assistant_state_allows_provider_history` (`DB/assistant_generation_state.py`) drops the empty `accepted` / `dispatch_started` reply from provider history.
- An earlier complete reply to the same message, such as the original answer a regenerate was replacing, is a sibling off the active path, so it is not sent either.

**Nothing merges plain consecutive user turns.** I checked the request builders:
- The Anthropic builder (`LLM_Calls/LLM_API_Calls.py`, the `role == "tool"` branch) coalesces only consecutive tool results into one user turn (task-263). Plain user messages are appended one by one.
- No `Chat/` or `LLM_Calls/` code merges adjacent same-role text turns.
- Anthropic's API accepted `[user, user]` live: claude-haiku-4-5 answered both questions in one reply ("alpha … beta").

**Where this can fail.** OpenAI-compatible local servers that apply the model's own chat template, such as llama.cpp or vLLM with Mistral- or Gemma-style templates, can refuse a request whose roles do not alternate ("Conversation roles must alternate user/assistant…"). The user then gets a failed send, on exactly the path the recovery copy recommends.
