## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Rider from TASK-33001.1 (preflight ruling R5). TASK-33001.1 fixed `resolve_effective_chat_configuration` so that `chat_defaults.model` applies only when the target provider canonically equals `chat_defaults.provider`. The same bug has a sibling in `resolve_effective_provider_model` (UI/Screens/provider_model_resolution.py, the model fallback after the console/settings model checks). When a console or settings provider is selected but no model is, the function returns `chat_defaults.model`, whichever provider owns it.

This path is reachable. `ConsoleSessionController._default_console_session_settings` (Ctrl+T, and the other new-session paths) feeds the pair from `ChatScreen._effective_console_provider_model` straight into the new session as an explicit model. So with the shipped config, it goes like this:
1. The palette's "LLM Provider Management: Switch to llama_cpp" (`[providers] Llama_cpp = ["None"]` gives an empty model list) sets the mirrors to (llama_cpp, None).
2. Ctrl+T then opens a llama_cpp tab on `gpt-5.6-terra`.

TASK-33001.6 deletes that palette producer. The mirrors can still be set to a provider with no model by the hidden compact bar's user-selection handler and by the first-chat control selection. Those paths need their own reachability check.

A related shape is in Settings. `_apply_navigation_provider_context` and `_provider_display_setting_values` pair a navigated-to provider with the resolved `chat_defaults.model` when the navigation carries no explicit model.
<!-- SECTION:DESCRIPTION:END -->
