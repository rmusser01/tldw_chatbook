## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Rider from TASK-33001.1 (preflight ruling R5). TASK-33001.1 fixed `resolve_effective_chat_configuration` so that `chat_defaults.model` applies only when the target provider canonically equals `chat_defaults.provider`. The same bug has a sibling in `resolve_effective_provider_model` (UI/Screens/provider_model_resolution.py, the model fallback after the console/settings model checks). When a console or settings provider is selected but no model is, the function returns `chat_defaults.model`, whichever provider owns it.

This path is reachable. `ConsoleSessionController._default_console_session_settings` (Ctrl+T, and the other new-session paths) feeds the pair from `ChatScreen._effective_console_provider_model` straight into the new session as an explicit model. So with the shipped config, it goes like this:
1. The palette's "LLM Provider Management: Switch to llama_cpp" (`[providers] Llama_cpp = ["None"]` gives an empty model list) sets the mirrors to (llama_cpp, None).
2. Ctrl+T then opens a llama_cpp tab on `gpt-5.6-terra`.

TASK-33001.6 deletes that palette producer. The mirrors can still be set to a provider with no model by the hidden compact bar's user-selection handler and by the first-chat control selection. Those paths need their own reachability check.

A related shape is in Settings. `_apply_navigation_provider_context` and `_provider_display_setting_values` pair a navigated-to provider with the resolved `chat_defaults.model` when the navigation carries no explicit model.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 `resolve_effective_provider_model` returns `chat_defaults.model` only when the selected provider canonically equals `chat_defaults.provider` (the same identity rule TASK-33001.1 applies), otherwise no model
- [x] #2 A new Console tab (Ctrl+T) opened while the control provider has no model gets that provider's own configured model, or none, never another provider's model; a regression test drives the real session-default path
- [x] #3 Settings' provider navigation without an explicit model shows the navigated provider's own model, or none, never `chat_defaults.model` of another provider
- [x] #4 The new-chat pair for the ordinary cases (no control selection; a control provider with its model) is unchanged
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Move TASK-33001.1's identity rule out of `resolve_effective_chat_configuration` into one shared predicate.
2. Use it in `resolve_effective_provider_model`'s `chat_defaults.model` fallback (red test first).
3. Drive the real Ctrl+T session-default path with a model-less control provider set by producers that still exist.
4. Check the Settings navigation path (AC#3) against Phase 8's fix before touching it.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
`chat_defaults.model` now reaches a provider only when that provider canonically is `chat_defaults.provider`, on every resolver.

- `Chat/console_session_settings.py`: new `owns_chat_defaults_model(provider, chat_defaults, app_config=None)`, the identity rule TASK-33001.1 wrote inline (canonical provider id, legacy aliases such as `OpenAI-Compatible`, registry-id spelling). `resolve_effective_chat_configuration` calls it instead of its inline copy.
- `UI/Screens/provider_model_resolution.py`: `resolve_effective_provider_model` falls back to `chat_defaults.model` only through that predicate; another provider gets `model=None`, `model_source="none"`. Settings drafts and Console models still win first, unchanged.
- AC#2: with no model on the Console control, `default_console_session_settings` receives no explicit model and resolves the provider's own `[api_settings.<provider>]` model, or none. The palette producer is gone (TASK-33001.6); the test sets the mirrors through the two that remain, the first-chat control selection (`wiring._apply_first_chat_control_selection`, which restores a model-less prior on rollback) and the compact bar's provider Select handler (`ChatScreen.on_console_compact_provider_changed`, which leaves the model unset).
- AC#3 was already fixed by Phase 8 (cbc9c75cd8, `Settings_Modules/provider_return.routed_model`): a route naming no model to another provider resolves that provider's model or none. Its pin, `Tests/UI/test_console_provider_return.py::test_a_route_that_names_no_model_never_borrows_another_providers_model[lists-no-models]`, is on the UI PR census and passes at this head (3 passed, serial). The resolver change also covers a Settings draft that stages a provider without a model.
- AC#4: `Tests/Chat/test_console_session_settings.py::test_new_chats_resolve_the_chat_defaults_pair` (no control selection; a control provider with its model) is unchanged and passes; the new test's `defaults-provider` case keeps the default pair.
