## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** `/emergency-stop` holds every new run and every scheduled dispatch, and the hold survives a restart. The only sign of it is a toast that lasts about 5 s. After the toast fades, the Console looks the same as before the stop:
- the header reads 'Ready' and the status strip is unchanged (its 'Agent blocked' chip is the Library-access permission from TASK-25732, not the stop);
- the Agent rail reads 'Agent: idle', and Send reads 'Send | $' and is enabled;
- after a relaunch, the empty transcript says 'Ready - type a message to begin.'

Each send is refused with 'Emergency stop is active: new runs and scheduled dispatches are held. Clear it to resume.' That message does not name the clear command. Scheduled dispatches are held with only a debug log line (`SchedulerLoop._dispatch_due`), and no UI reads the stop state. Held tasks are not lost: they fire once the stop is cleared. The clear syntax can be found only in the slash-menu row ('(clear to resume)') and in `/help emergency-stop`.

**Severity / prior art.** P1, verified live and in code (the skeptic rated it PARTIAL). This is a **REGRESSION of TASK-26004 (Done)**. Its AC#5 ('an attempted send ... reports plainly that the stop is active and how to clear it') is checked, but the shipped copy does not say how. The `visible_copy` docstring in `tldw_chatbook/emergency_stop.py` cites that AC.

**Suggested direction.** Have the header and status-strip presenters read `emergency_stop_state` and show a persistent hold state plus an 'Emergency stop - new runs held · Clear' chip whose action clears the stop. Feed the hold into the composer's Send disabled-reason. Put the exact clear action into `EmergencyStopState.visible_copy`. Show the hold on the Schedules screen and at boot. This task covers the state and indicator only. Ranking a per-tab '/stop' above '/emergency-stop' belongs with the per-tab Stop visibility work, not here.
