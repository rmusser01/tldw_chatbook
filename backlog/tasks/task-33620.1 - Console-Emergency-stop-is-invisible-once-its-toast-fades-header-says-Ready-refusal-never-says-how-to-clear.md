## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** `/emergency-stop` holds every new run and every scheduled dispatch, and the hold survives a restart. The only sign of it is a toast that lasts about 5 s. After the toast fades, the Console looks the same as before the stop:
- the header reads 'Ready' and the status strip is unchanged (its 'Agent blocked' chip is the Library-access permission from TASK-25732, not the stop);
- the Agent rail reads 'Agent: idle', and Send reads 'Send | $' and is enabled;
- after a relaunch, the empty transcript says 'Ready - type a message to begin.'

Each send is refused with 'Emergency stop is active: new runs and scheduled dispatches are held. Clear it to resume.' That message does not name the clear command. Scheduled dispatches are held with only a debug log line (`SchedulerLoop._dispatch_due`), and no UI reads the stop state. Held tasks are not lost: they fire once the stop is cleared. The clear syntax can be found only in the slash-menu row ('(clear to resume)') and in `/help emergency-stop`.

**Severity / prior art.** P1, verified live and in code (the skeptic rated it PARTIAL). This is a **REGRESSION of TASK-26004 (Done)**. Its AC#5 ('an attempted send ... reports plainly that the stop is active and how to clear it') is checked, but the shipped copy does not say how. The `visible_copy` docstring in `tldw_chatbook/emergency_stop.py` cites that AC.

**Suggested direction.** Have the header and status-strip presenters read `emergency_stop_state` and show a persistent hold state plus an 'Emergency stop - new runs held · Clear' chip whose action clears the stop. Feed the hold into the composer's Send disabled-reason. Put the exact clear action into `EmergencyStopState.visible_copy`. Show the hold on the Schedules screen and at boot. This task covers the state and indicator only. Ranking a per-tab '/stop' above '/emergency-stop' belongs with the per-tab Stop visibility work, not here.

Evidence: qa/console-ux-review-2026-09-29/findings.md → G3-05 (sources J8-07, L3-10). Files: evidence/evidence__J8__104-estop-after-toast.txt, evidence/evidence__J8__105-send-during-estop.txt, evidence/evidence__L3__34-estop-after-toast.txt, evidence/evidence__L3__36-estop-send-refused-later.txt.

Review finding ids: G3-05 — see qa/console-ux-review-2026-09-29/findings.md.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** The emergency stop now stays visible while it holds work, and it holds the Console's ordinary send again. Measured first on origin/dev 38c9d2edcf (live, 160x45, Anthropic haiku through the review proxy): after `/emergency-stop` the header read "Ready · not tested", the strip and Send were unchanged, and a send typed during the stop **reached the provider and got "Hi there!"** (proxy POST at 08:10:06 with emergency_stop.json active). The triage's "each send is refused" was true only of the dispatch path: the received-intent fast path (PR #3023) never reaches `send_refusal_copy`. That bypass became AC#7.

**Commits (one per fix).**
1. `emergency_stop.py`: `visible_copy` names `/emergency-stop clear`; the old test passed on "Clear it to resume." because "Clear" contains "clear".
2. `test_scheduler_holds_dispatch_when_stopped` was red on dev: its `__new__`-built loop lacked `_offload`'s task set after TASK-33620.15.24, so every read failed SAFE to stopped. Test-only repair; a mutation that skips the hold turns it red.
3. Transcript tick gate (`ChatScreen` sync): it keyed the send acknowledgement on the ack object existing, so a refused send's released "Sending…" row never invalidated it and an idle Console kept painting "Sending…" without the stored refusal row. Pre-existing on dev for any dispatch refusal (archive-in-progress reproduced headless); it hid this task's refusal, so it is fixed here: the gate compares the session's pending row id.
4. `UI/Console_Modules/emergency_stop_hold.py` (new, lazy): the screen's one cached view (`ChatScreen._console_emergency_stop_copy`), read off the UI loop on every Console arrival (`ScreenResume`, after `_ui_ready`), written by `/emergency-stop` (handler moved out of `ChatScreen`, write off-loop). The received path asks `received_send_held`, which reads the stop file itself (one small read per send, as every send did before #3023; no per-tick read) and leaves for the dispatch path, where `_console_send_blocked_reason` refuses with the copy (also before queue admission). A stop active at launch is announced once.
5. Display: `ConsoleControlState.emergency_stop_held` drives the header badge ("Held · emergency stop", "Held" at single-pane widths) and two strip segments, "Emergency stop: runs and schedules held · Clear" (left-most; Clear posts `ConsoleEmergencyStopChip.ClearRequested`, which clears off the UI loop). Send is held with "Send held — emergency stop is on" (rides the verbatim queue-reason slot, never the setup-wizard link). The empty transcript says the stop's copy instead of "Ready — type a message to begin.". The copy shown is fixed text (the typed reason is left out of markup-parsed surfaces).
6. Schedules: the scheduler tick records `held_by_emergency_stop` in its existing heartbeat; the liveness line adds "scheduled dispatches are held by the emergency stop (/emergency-stop clear in Console)". No new file read (Schedules already reads the heartbeat); the note follows the scheduler's tick, within one poll interval.

**Trade-offs.** The cached view can lag a stop written by another process until the next Console arrival or send, but sends cannot: the fast path reads the file, the dispatch path re-reads it before refusing from the cached hold (review round), and `send_refusal_copy` still does. AC#3 is met at the default widths (tested at 160x45); at 80 columns the Send reason line hides (TASK-24415's legible-budget rule), so the stop is named there by the header "Held", the strip chip and Send's tooltip (TASK-33620.1.3 tracks giving it priority). Size ratchets: `chat_screen.py` 24331/737 (row unchanged; the moved command handler paid for the new chip handler and lines).

**Follow-up.** TASK-33620.1.1: prompts queued before the stop still drain into new runs (`ConsolePromptQueueCoordinator._drain_waiting` and `submit_draft` have no stop gate; found by reading, not reproduced live).
