## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact (P0).** On dev @ 64579cce2c a Console send is refused before the provider is contacted, with no reason and no recovery, in these cases:
- the chat has any system prompt: a session prompt set before the first send or mid-chat, a character swapped in, or a 'Start new chat' character chat (the built-in Default Assistant included);
- the chat's only assistant history is a /generate-image result.

This reproduced 5 out of 5 times in two profiles. The log shows 'durable_commit status=succeeded', then about 4 ms later 'controller_submit status=blocked', with no error line in between. What the user sees:
- The user row stays in the transcript with no reply, no SYSTEM row and no toast.
- The header says 'Ready' and Inspect says 'Run: Ready' / 'Ready to send'. The only signs are a lowercase 'blocked' border label and '⛔ Blocked' in the Chats list; neither gives a cause or an action.
- Every later send is parked in 'Queue 0/10 · Unsent turn needs attention [Rest][Discard]', where 'Restore' is truncated.
- Nothing clears the state: not Restore then resend, not Discard, not clearing the prompt.

The controller catches everything around `_build_durable_trace_request` and pauses with TRACE_PROVENANCE. `trace_call_recovery_state()` filters that pause out, so the prepared 'Retry / Send without capture / Cancel' copy is never rendered, even though the controller supports all three actions. There is also a narrower image variant: an image generated after a normal exchange fails at trace_dispatch_commit with `surface_prefix_mismatch`. That path does render a 'Trace capture blocked' callout whose 'Send without capture' works, but the next send blocks again.

**Prior art:** REGRESSION of TASK-25814 (Done) AC#1-3, which says a trace-capture failure must still reach the provider as a non-blocking warning, and of TASK-31976 (Done) AC#3, 'A refused recovery remains visibly actionable and explains why it did not send'. Related: TASK-31976.1 (Done). G4-03 is KNOWN_PARTIAL: open PR #2882, which is not on dev, carries TASK-32951 AC#4 (unsaved effective system prompts) and TASK-32953 (dispatch-recovery dead end, GitHub #2708).

**Suggested direction:**
- Fix provenance admission by trigger. System-role rows from any source must be admitted as rendered system context. Image-generation assistant rows need provenance admission, and the dispatch-surface prefix check must accept them.
- Add TRACE_PROVENANCE to the recovery projection so the inline callout renders, with copy stating the provider was not contacted.
- Log a content-free error_category and exception_type at the catch, keyed by attempt_id.
- Make the header and the Inspect Run line show Blocked with its reason.
- Make the queue strip show the refusal's copy and size Restore/Discard to their labels.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Every Capture-On Console send in a chat with a system row, or after a saved /generate-image result, now reaches the provider. A send whose trace provenance genuinely fails stops with a visible, actionable callout, a Blocked header, run chip and Inspect Run line, a shelf that states the refusal, and a keyed, content-free log line.

**Root causes**
- `_build_durable_trace_request` labelled every unsaved provider row ACTIVE_REQUEST. The request aggregate's `system` category admits only RENDERED_SYSTEM, so every chat with a session prompt, a character template or a seeded greeting raised `TraceProvenanceAlignmentError` ("category mismatch: system"). The bare `except` swallowed it and paused the send with TRACE_PROVENANCE, and `trace_call_recovery_state()` filtered that pause out.
- An image-result assistant row was admitted as its saved revision. That revision projects the image, but provider history sends only its text, so every later send failed at `trace_dispatch_commit` with `surface_prefix_mismatch`.

**Fix**
- New module `Chat/console_trace_row_sources.py` follows the aggregate's partition. `unsaved_row_sources()` labels leading system rows RENDERED_SYSTEM, or CONVERSATION_MEMORY when they carry the memory marker. A system row inside the history becomes ACTIVE_REQUEST, and every other row gets dev's role mapping, `unsaved_trace_artifact_source()` (TOOL_CALL / TOOL_RESULT). `saved_message_id()` refuses the saved revision for a row that leaves out that message's saved media.
- At the provenance catch, `record_send_stage("trace_provenance", "failed", error=...)` writes `error_category`, `exception_type` and `attempt_id`, with no message text.
- `TRACE_PROVENANCE` is in the recovery projection, and the callout says "This send's trace record could not be saved" / "The provider was not contacted" with Retry capture, Send without capture and Cancel send.
- `blocked_turn_reason()` drives the header badge ("Blocked"), the run chip and the Inspect Run line ("Blocked — trace not saved"). It reads the paused trace-recovery preparation and answers "" only while a run is active (Retry or Send without capture running the turn). It first keyed on run status BLOCKED, and the checkpoint review found that a send refused behind the pause re-stamps that status ("Initializing hooks.", then "Preparation ended."), so after a second send all three read Ready again while the callout still showed.
- A send refused behind a paused turn keeps its controller copy (`ConsoleTurnRecoveryEntry.reason`). The shelf shows "Not sent: Last send is blocked; resolve it first", fitted so that Restore and Discard stay whole.
- The queue shelf's painted-label walk (`Tests/UI/test_console_prompt_queue.py`) paints the refused-send states: the "Last send is blocked" copy on an empty queue, and a longer controller copy behind a full queue.
- The module-size ratchet allows no growth. The controller stays at or below its line count: line-neutral on this branch's base, and 28 lines under dev 5e0341d1ec once rebased (32020 to 31992).
- User Guide: `console/semantic-trace-capture.md` and `console/chat-basics.md`.
