## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: TASK-34000.28 (polish-1 task 4) traced Move note's false "That folder changed elsewhere" to SQLite error 517 (SQLITE_BUSY_SNAPSHOT). It happens when a DEFERRED transaction has already read and another thread's connection retires with PRAGMA wal_checkpoint(TRUNCATE) before the first write. The busy handler never sees code 517, so the 15 s busy timeout cannot help. Measured on base: 7 false conflicts in 37 moves. Task 4 fixed it only for the eleven folder-repository mutations, by moving them to transaction(immediate=True) with a bounded retry on 517. Every other read-then-write transaction on the ChaChaNotes database still has the same exposure. Likely examples are note saves with an expected version, the remaining DEFERRED transactions in Sync_Interop/notes_organization_sync_service.py (the reconcile at about :295 and the owner/managed-placement transactions from about :430 on; polish-1 task 4 fixed only the create, attach and detach that Move note uses), keyword and conversation updates, and any other path that reads before it writes inside one DEFERRED transaction. Such a path can fail with a stale-data error even though nothing else changed the data.

Test support (polish-1a final review, 2026-10-26): the WAL-restart and stale-snapshot helpers (`_wal_restarted_after_the_first_read`, `_stale_snapshot_after_the_first_write`) live in `Tests/Notes/test_note_folder_repository.py`, and `Tests/Sync_Interop/test_notes_organization_intent_dispatch.py` already imports the first privately from that test module; move them to one shared test-support module (for example `Tests/Notes/wal_restart_support.py`) so every path AC#3 fixes reuses the same helper.
