## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`update_keywords_for_media` and `create_document_version` execute DML on the held connection and document that they assume an existing transaction, but the shipped reading-list import path opens none: `import_reading_items` -> `execute_reading_import_job` -> `_execute_reading_import_job` (a per-row loop) -> `_materialize_reading_import_row` -> `update_keywords_for_media`. Because the connection keeps the legacy isolation level, the first bare call opens an implicit transaction that nothing commits, and `transaction()` then borrows it without committing, so every later Media write on that thread is rolled back at close. Reproduced: two media rows expected, one found, with a keyword and a read-it-later row lost.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Both methods (update_keywords_for_media, create_document_version) now open self.transaction() themselves instead of taking the raw connection under a 'assumes called within an existing transaction' comment. transaction() joins an already-open outer transaction and leaves the commit to it, so the two callers that DO wrap these (Library/meeting_speaker_rename.py, local_media_reading_service.py:4875) keep all-or-nothing behaviour. The assumption is enforced rather than documented.

Measured on a file-backed DB (in-memory cannot observe a close-time rollback, which is why the existing Media suites never caught this):
  BEFORE: in_transaction True after the bare call; after close+reopen the second media row is GONE even though add_media_with_keywords returned 'Media Beta added.', and the merged keyword is gone.
  AFTER:  in_transaction False; both rows survive; keywords ['k1','k2']; 2 document versions persist; an aborting outer transaction still rolls the nested write back.
