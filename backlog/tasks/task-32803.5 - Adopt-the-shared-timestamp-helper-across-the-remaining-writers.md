## Implementation Notes

PR #2735. Drained the timestamp-writer census (from TASK-32803.1's guard): all 53
naive `datetime.now().isoformat()` writers (+ the 3 Audio
`.isoformat(timespec="seconds")` variants) across 28 files now go through
`Utils.timestamps.utc_now_iso()` — fixing the timezone (local→UTC) and
standardising the shape to canonical millisecond `Z`. Census is now empty
(0 rows), so the guard forbids ANY new naive timestamp writer (AC#3). Removed 9
orphaned `from datetime import datetime` imports.

AC#1 done: every censused writer migrated. All were machine/stored metadata
fields (created_at/updated_at/started_at/ended_at/exported_at/generated_at/
completed_at/timestamp, TTS profile metadata, chatbook stamps, etc.), not
user-facing local-time displays (those use strftime, never in scope). Checked
the one comparison-sensitive site (Subscriptions/site_config_manager): its
rate-limiter compares in-memory `datetime.now()` datetimes for elapsed-time math
(never serialised, never censused, untouched) — only its stored metadata
migrated. No test pins a migrated field's exact string (grep-verified).

AC#2 REFRAMED (owner-visible correctness finding from the ADR-173 review):
"remove julianday() where the write side is uniform" has a false premise for
existing data. ADR-173 does NOT rewrite stored rows, so any column that has
legacy rows or a CURRENT_TIMESTAMP default remains MIXED-shape indefinitely; a
bare SQL `col < ?` over it still mis-sorts (an earlier canonical `Z` value sorts
after a later space-separated value). The read-side `julianday()`/`datetime()`
normalizations (e.g. console_trace_settlement.recover_open_calls) are therefore
RETAINED — they are the correct handling for mixed columns and are harmless on
all-canonical data. Removing them is unsafe until a column is separately
migrated (backfill + default change), which is out of this task's scope.
