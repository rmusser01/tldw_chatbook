## Tier-2 scope correction (2026-09-21)

**This task is marked Done, but the writers it targeted are still there** -- the guard that
was supposed to confirm the adoption cannot see them.

`scripts/check_timestamp_writers.py` matches only `datetime.utcnow()` and naive `.now().isoformat()`.
Its docstring states `datetime.now(timezone.utc).isoformat()` "does not match and is fine" -- but
**ADR-173 names that exact expression as one of the drifting shapes it exists to eliminate** and mandates
a `Z` suffix. Measured on dev today, excluding `Third_Party/`:

| shape | live sites |
|---|---:|
| `now(timezone.utc).isoformat()` | 70 |
| `now(UTC).isoformat()` | 31 |
| `isoformat().replace("+00:00","Z")` (conforming) | 14 |
| `utc_now_iso()` (the helper) | 72 |

**101 writers still emit `+00:00`**, `scripts/timestamp_writer_census.tsv` is empty, and preflight prints
`timestamp writers: 0 site(s) ... OK`. Because `'+'` is 0x2B and `'Z'` is 0x5A, a row written at the same
instant by a `+00:00` writer sorts first and `WHERE ts >= '<...>Z'` **silently drops it** -- exactly the
failure TASK-32803.3 names. Re-open, or supersede via TASK-32897 (guard) + TASK-32914 (the writers).

Measured by the tier-2 review against `origin/dev d0face3ebe`; evidence in `qa/tier2-code-review-2026-09-21/` (`report.md`, `validation/`). Tracked as TASK-32903.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
PR #2735. Drained the timestamp-writer census (from TASK-32803.1's guard): all 53
naive `datetime.now().isoformat()` writers (+ the 3 Audio
`.isoformat(timespec="seconds")` variants) across 28 files now go through
`Utils.timestamps.utc_now_iso()` — fixing the timezone (local→UTC) and
standardising the shape to canonical millisecond `Z`. Census is now empty
(0 rows), so the guard forbids ANY new naive timestamp writer (AC#3). Removed 9
orphaned `from datetime import datetime` imports.

AC#1 done: every censused writer migrated. All were machine/stored metadata
fields (created_at/updated_at/started_at/ended_at/exported_at/generated_at/
completed_at/timestamp, TTS profile metadata, chatbook stamps, etc.), not
user-facing local-time displays (those use strftime, never in scope). Checked
the one comparison-sensitive site (Subscriptions/site_config_manager): its
rate-limiter compares in-memory `datetime.now()` datetimes for elapsed-time math
(never serialised, never censused, untouched) — only its stored metadata
migrated. No test pins a migrated field's exact string (grep-verified).

AC#2 REFRAMED (owner-visible correctness finding from the ADR-173 review):
"remove julianday() where the write side is uniform" has a false premise for
existing data. ADR-173 does NOT rewrite stored rows, so any column that has
legacy rows or a CURRENT_TIMESTAMP default remains MIXED-shape indefinitely; a
bare SQL `col < ?` over it still mis-sorts (an earlier canonical `Z` value sorts
after a later space-separated value). The read-side `julianday()`/`datetime()`
normalizations (e.g. console_trace_settlement.recover_open_calls) are therefore
RETAINED — they are the correct handling for mixed columns and are harmless on
all-canonical data. Removing them is unsafe until a column is separately
migrated (backfill + default change), which is out of this task's scope.

## Non-adopting writers still outstanding (TASK-32901, tier-2 review S08/S09)
<!-- Added 2026-09-22. This task is Done and its guard reports green; these
writers are invisible to the guard BY CONSTRUCTION, so "green" is not evidence
they are covered. Recorded here rather than swapped, for the reason below. -->

`scripts/check_timestamp_writers.py` matches exactly two shapes: `.utcnow` and
`.isoformat()` on a **zero-arg** `.now()` (its predicate is `not func.value.args
and not func.value.keywords`). Every writer below passes a `tz` argument, so the
guard excludes it and reports `0 site(s) ... OK`:

- `Scheduling/db/scheduled_tasks_db.py:713 _to_utc_iso` -- `.isoformat()`,
  microsecond + `+00:00`; ~30 write sites in that file use it. Plus `:3302
  _serialize_result_fields`, which stores server-supplied timestamp STRINGS
  (`Z`) verbatim, so the column is already mixed-shape.
- `Character_Chat/local_character_persona_service.py:160 _now()`
- `Character_Chat/local_chat_dictionary_service.py:205 _now()`
- `Character_Chat/buddy_conversion.py:440` (`converted_at` in an exported
  Actor Pack)

`grep -rln "Utils\.timestamps" tldw_chatbook/Scheduling tldw_chatbook/
Subscriptions` -> exactly ONE hit in that whole slice, against 28 repo-wide
importers.

**Why the tier-2 burn-down did not just swap them.** This task's own AC#2
records the governing constraint: existing rows are not rewritten, so a swap
makes the column mixed-shape and correctness then depends on read-side
normalization. In `Scheduling` that mitigation is present at only 3 sites
(`strftime`/`julianday` hits in `scheduled_tasks_db.py`) against 9 raw
comparisons/orderings of `created_at`/`updated_at` -- and the v6->v7 migration
comment states the stake: "picking the wrong 'newest' here is not a display
bug, it permanently discards the real newest row." Swapping the writer without
first auditing every read of those columns would CREATE the lexical hazard,
not close it. That audit is the work; it is a deliberate decision, not a P2
edit.

Also worth doing here: extend the guard to flag `.isoformat()` on an aware-UTC
datetime reaching a DB parameter, so the next census can see these at all.
