## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: `[chat_defaults] provider` is persisted as the canonical readiness key (`custom`, `custom_2`, `local_llm` — what First Run writes and what `get_provider_readiness` checks), and for those three providers it is not a `chat_api_call` handler key (`custom-openai-api`, `custom-openai-api-2`, `local-llm`). `briefing_service.resolve_persisted_briefing_defaults` returns the readiness key, and `generate_briefing` hands it straight to `chat_api_call`, so a scheduled or demo brief for one of those providers fails with "Unsupported API endpoint" after its sources were fetched — and the Reports demo consent (TASK-34000.23), which names the pair from the same resolver, promises a pair that cannot run.

The final review of PR #3184 fixed the identical defect for Library RAG Answer and scheduled automations (TASK-34000.21, `library_rag_answer_service._execution_endpoint`, reusing Console's `_READINESS_TO_EXECUTION_ALIASES`) and deliberately left briefings for this task: that path predates the batch and has its own tests and live-run evidence rules (ADR-079; no real recurring paid work left behind).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

<!-- AC:BEGIN -->
- [ ] A briefing run under `[chat_defaults] provider = "custom"` (and `custom_2`, `local_llm`) reaches the matching `chat_api_call` handler instead of failing with "Unsupported API endpoint"; the readiness key is still what the readiness check and the consent copy use.
- [ ] The Reports demo consent names a provider · model pair that the brief it starts can actually bill; the pair it names and the key the chat seam receives are pinned together for all three providers, asserting on the `api_endpoint` the chat seam receives.
- [ ] The mapping is shared with Library RAG Answer (one alias table, no second copy), and the boot census and app import-weight contracts are unchanged.
- [ ] A provider whose readiness key is already a handler key is passed through unchanged (pinned).
