## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A newcomer who runs a tldw server is never offered the connection where setup happens; the only way is a Settings control. The approved spec offers it at the end of setup, as a next step rather than a step, so the local-first majority pays nothing for it (decision D3, part 2).

The action opens the existing server dialog and commits through the one runtime-source coordinator (TASK-34100.19), never a wizard copy of the switch logic, and the Summary's tldw server row (TASK-34100.21) updates in place on success.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D3 part 2, D6 item 3, §10 F4.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Whenever no server is in use, the setup Summary offers 'Connect a tldw server… (if you run one)'; when a server is in use it is not offered
- [ ] #2 It opens ServerSwitchModal, and the result is committed only through the shared runtime-source coordinator. What Sync v2 preparation sends is said before the user confirms
- [ ] #3 On success the tldw server row shows the new state in place, without leaving the Summary. On failure the cause is shown with the shared probe's specific copy, and nothing is half-applied on disk or in memory
- [ ] #4 Cancelling the dialog writes nothing and leaves the Summary as it was
- [ ] #5 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: a fresh profile finished with a real OpenAI key, then 'Connect a tldw server…' against a real tldw_server: success, a wrong token, and the server stopped. Evidence is recorded in Implementation Notes

- [ ] #7 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
