## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Library is meant to be keyboard-first. These five findings are where it breaks for:
- a keyboard-only, low-vision user (Sam);
- a fast typist (Riley);
- a first-timer looking for help or for a way to bring in notes (Jordan).

**S-07 (P2) · Closing F1 or any dialog drops keyboard focus.** Every trip to help or to a dialog costs the user their place. At 120x36:
- On the landing, focus moves from the "From your Library" row to the nav bar's "⌃1 Home".
- In Notes, focus on a just-shown "✓ deleted · Untitled · Undo" receipt moves to Filter, and getting back to Undo takes 9 Tabs.
- In Conversations, focus lands on the Nav grip.
- In Skills, Tab walks the nav bar.
- The note editor, Media and the rail keep focus.

Verified cause: `on_screen_resume` runs `_refresh_library_visit_surfaces` on every `ScreenResume`, and `ScreenResume` also fires when a modal pops (`UI/Screens/library_screen.py:9262-9299`, refresh at `:9306`). `on_screen_suspend` (`:9205`) does not record whether the cover was an overlay, so a closed dialog is treated as a new visit. The Notes tree reloads, prompts and skills restore with `focus_identity=None`, and Conversations re-enters.

Suggested direction: in `on_screen_suspend`, record whether an overlay was pushed. On that resume, skip the visit refresh and the Notes canvas recompose. The landing restore should search the landing canvas. Add Pilot tests that F1 then Esc keeps focus on each surface. TASK-31421, a Skills loading/ready settlement race that can drop a focus restore, is adjacent but separate. TASK-34000.26 (S-10: focus landing on a widget being removed) belongs to the same focus lifecycle, so the two should agree on how a real arrival is told apart from a closed dialog. Lowered from P1 because the editor, Media and the rail keep focus.

**S-08 (P2) · Keys typed within ~0.15 s of submitting the Notes filter fire screen shortcuts.** A fast typist refining a search is thrown out of Notes:
- Typing "Recipe", Enter and then `i` opens the Import media canvas, whose footer reads "typing in field | esc back".
- Typing `n` the same way creates a stray note. The list says "Note created — select it from Notes to open.", a new "Untitled · now" row appears, and Notes (122) becomes Notes (123).

Cause (hypothesis, consistent with the captures): applying the filter recomposes the Notes canvas, so focus is briefly None. `on_key` (`UI/Screens/library_screen.py:8749`) then routes the bare letters to the screen accelerators (`i` at `:8929-8940`, `n` just below). Those accelerators stand down only while an Input or TextArea owns focus.

Suggested direction:
- Keep the filter Input mounted and sync only the results.
- Swallow single-letter accelerators while the Notes canvas is mid-recompose or a `then=` refocus is pending.
- Make the guard event-driven, not a timer (ADR-104).

Lowered from P1: the window is narrow, and the stray import needs a real path, so "one more Enter imports" was overstated.

**S-09 (P2) · F6 never enters the Export or Search/RAG canvas, and entry focus stays on the rail.** Both footers say "F6 next pane".
- Export (Media ▸ select one item ▸ Export, 160x45): F6 only moves to the rail's "Search Library…" box. Reaching the bundle name takes about 25 Tabs and "Choose destination…" about 29. Shift+Tab reaches it in 1-3 presses, so this is not a trap.
- Search/RAG: pressing F6 three times changes nothing.

Verified cause:
- The `library-canvas` `WorkbenchPaneTarget` lists only the landing hub ids and `library-ingest-path` (`UI/Screens/library_screen.py:1420-1435`).
- `_resolve_focus_target` (`Widgets/workbench_focus.py:71`) has no first-focusable fallback.

Suggested direction:
- Add Export targets (`library-export-name`, `library-export-destination`) and Search/RAG targets (`library-rag-query-input`, `library-rag-mode-toggle`).
- Let the resolver fall back to the pane's first visible focusable descendant.
- Land entry focus inside the canvas at every width.
- Add a contract test per rail row.

TASK-32301 owns list-entry focus for list destinations. This task covers the two canvases that have no list.

**S-15 (P2) · Footer and F1 disagree, F1 has a malformed row, and Search/RAG advertises a key that does nothing.** In the Notes editor at 120x36, F1 reads:
- "Library Shortcuts — Notes"
- "- : typing in field"
- "- esc: back to list"
- "- F6: next pane"
- "- shift+f6: Previous pane"
- "- ctrl+n: New note"

About 20 empty rows follow. Meanwhile the footer says "esc back to notes | ctrl+end end of note", and ctrl+end is missing from F1. Nothing explains autosave, Save, where Delete lives, links, or Use in Console.

On Search/RAG, the arrival footer offers "o open evidence", and pressing `o` before any result exists changes nothing on screen. Conversations' arrival footer shows only "F6 next pane", while F1 lists working `/` and `c`.

Verified cause:
- The F1 panel is assembled from footer chips plus active bindings (`UI/Screens/library_screen.py:25730-25768`). The key-less "typing in field" status chip (`:4827`) leaks in as "- :".
- "o open evidence" comes from a static footer set (`:1246`) that `check_action` does not gate.

Suggested direction:
- Have F1 read the footer tuple that was actually registered.
- Drop key-less rows, and expand "after esc:" into its own group.
- Gate `o` through `check_action`.
- Use one predicate for Conversations' `c`, and refresh the footer when Conversations arrives.
- Add a short "How Notes works" block through `WorkbenchHelpState.notes`. It must describe today's behaviour. For example, it must not promise Ctrl+S in Notes, which ADR-031 rule 2 forbids, and it must not imply that a typed [[Title]] is a working link.

**S-21 (P2) · The landing's only "Import…" goes to Media import, with no pointer to importing notes.** A first-timer with a Markdown or Obsidian folder presses the landing's "Import…". Its tooltip reads "Add files, links, and transcripts to your Library." (`Widgets/Library/library_entry_canvases.py:349-356`). They get "Import media", which lists "Supported: PDF documents, Word/Office documents, audio/video files, e-books, images, plain text files, web pages." Nothing mentions notes or Notes ▸ "Add from files…", so their notes become read-only Media items.

Suggested direction:
- Add an actionable line to the Import media canvas: "Markdown or Obsidian notes? Notes ▸ Add from files… keeps them editable".
- Offer "Import as notes / as media" when the selection is mostly .md.
- Make the landing tooltip honest.

Review finding(s): S-07, S-08, S-09, S-15, S-21. Source: qa/notes-library-ux-review-2026-10-02/report.md
