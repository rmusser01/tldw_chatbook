## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: while a lasting-sync check or activation runs, the user is meant to see its progress -- the add canvas composes "Checking folder…" / "Checking changes…" and a "Wait for the current step to finish." bar for the `checking` and `activating` phases, and the footer says `wait current step`. In the real app none of the canvas copy paints. The screen handlers for `CheckRequested`, `ActivateRequested` and the roots list's Check changes `await` the controller's check/activation inline, so the screen's message pump is held for the whole step: the canvas recompose that would paint the progress never runs until the step settles, the work pane stays blank (the previous page's widgets are gone, the new ones not yet composed), and every press made meanwhile -- a rail row, a toolbar button -- queues up and lands on the SETTLED page afterwards. The footer, which reads controller state directly, is the only honest surface.

Found during TASK-34000.17's review (reviewer probe `test_probe_rail_route.py`: mid-check painted text has neither "Checking folder" nor the wait line; a rail press stays queued until release). It predates .17: the inline `await` is the shape these handlers have always had, while the conflict-comparison path already runs its runtime call in a named worker (`library_notes_sync_comparison`) and publishes inline when it returns -- the pattern to follow.
<!-- SECTION:DESCRIPTION:END -->
