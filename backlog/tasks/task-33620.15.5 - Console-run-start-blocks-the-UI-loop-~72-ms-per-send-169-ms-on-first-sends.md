## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the live send-window profile of 2026-10-10 (the same round that filed TASK-33620.15.3, .4, .6 and .7). Method: isolated profiles, Anthropic haiku through the review proxy, 160x45, 56 sends over 10 launches; a probe on the app's PYTHONPATH timed every UI-loop callback and sampled the main thread every 4 ms while a callback ran, between a send's acceptance and its provider call.

After a send is accepted, run start (`ConsoleRuntime._run_custodied_turn` > `submit_draft`) holds the UI loop for 72 ms per send over 30 sampled sends, and for 169 ms on the first send after launch (5 sends). 81% of it is on-CPU. On first sends it was the longest single callback of the window in 3 of 5 sends (callbacks of 40 ms or more: median 76 ms, max 123 ms). On later sends its two longest callbacks were 16-28 ms each. By samples:
- `PromptHistory.append` builds a file job whose source selection calls `default_prompt_history_path()` twice. Each call is a guarded config operation (storage admission, companion guard, pause probe): about 12 ms per send.
- The MCP catalog fingerprint that decides catalog reuse (TASK-33620.15.1) reads the permission store and the local store, each through an admission scope, in one callback: about 19 ms per send.
- First sends only: lazy imports on the loop (the hooks v2 lifecycle package, `console_visual_transcript` with PIL, `web_tool_impls`) about 25 ms, and the full MCP composition in one callback of about 75 ms (fingerprint, kill switch, external catalog, built-in inventory, which parses `MCP/server.py` three times, tool states, local tool provider).

TASK-33620.15.1 made later run starts reuse the composed catalog. This task shortens what is left of run start's loop time without moving it to a worker thread: TASK-33620.15.1's worker hop made first sends reach the provider 97-249 ms later.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Run start does less work on the UI loop on first sends, and it never hops to a worker thread. On first sends, run start's loop CPU is halved, and it imports no modules there. Its longest callback fell about 40%, not half. Later sends' longest callback is unchanged. **AC#2 is not met.** The remaining longest callback is the post-commit step, filed as TASK-33620.15.8.

Changes:
- First-send imports warmed at idle. `Chat/console_first_send_modules.py` lists, in send order, the modules a first send imported on the UI loop on origin/dev (54-57 before the provider call, 9 at the run's end), taken from the live import record. `TldwCli._preimport_heavy_screens` imports them first on its daemon thread, then parses `MCP/server.py` once. It is paced like the screen routes: a pause as long as each import, and a park while navigation or Console custody owns the loop. The pass's heap freeze covers them. In a fresh interpreter the imports cost about 213 ms CPU (`Canvas.native_authority` is 190 ms wall of it), so the speculative screen routes start a few hundred ms later. Nothing runs before UI-ready.
- Prompt-history path kept on (config module, `current_config_identity()`, `HOME`), read before and after a resolution. A stale kept path is refused by the bound history's state check, as dev refuses it. Probed on both arms: deleting the data dir, or making it group-writable, between two appends gives identical outcomes.
- Manifest parse kept by `server.py`'s identity (path, dev, inode, size, mtime_ns, ctime_ns), checked before and after the read. The manifest is still built fresh on every call. Recorded in `Docs/Architecture/tool-catalog.md`.
- Yields: between the catalog fingerprint's two store reads (every send), and between the loop-side composition reads (non-stock sources only; dev's stock path reads in workers). Live, the run task waited a median 1 ms at the fingerprint yield (max 125 ms, 16 sends).

Evidence. Live, paired and interleaved, origin/dev vs the branch. Isolated profiles, Anthropic claude-haiku-4-5 via the review proxy, 160x45. Host load was 55-110 on 14 cores, so wall times are several times CPU times. Data, probe and scripts are in `scratchpad/uxrev/evidence/bd5/RRS/` and `scratchpad/rrs/`.
- Probe rounds (callback timings, 4 ms main-thread samples). probe3 compared origin/dev 4de437a5c5 with the pre-rebase head; probe4 compared origin/dev ce4aa4a231 with the rebased head. 10 first-send pairs and 24 later pairs.

Run start's total loop CPU fell 194 -> 97 ms (paired -98 ms, 10/10). Modules imported on the UI thread between Enter and the provider call fell 56 -> 1.
  - Later sends: longest callback 280 -> 262 ms (paired -4 ms, 12/24). The most CPU any one run-start callback used fell 37 -> 31 ms.
  - AC#1, by component of the longest callback (probe4 sample counts). Dev, first sends: catalog fingerprint 52 samples, lazy imports 38, local tool composition 19, prompt-history path 14. Dev, later sends: the composer's class sync 72, catalog fingerprint 63, memory preflight 22, history path 21, durable trace request 20. Fix, first sends: no imports, and no single dominant component. Fix, later sends: the composer's class sync 83 and single fingerprint reads 73. The history path appears only on memo misses after config writes. The harness's fresh profiles write catalog consent, `console.onboarding.first_send_completed` and rail state during the first two sends; an established profile writes them once.

  - First sends: median -911 ms (12/17 pairs fix earlier). Rebased rounds alone: -1,225 ms (9/11).
  - Later sends: median -139 ms (19/34).
- Launch to Console ready: paired median -0.4 s (14/25 fix faster).
