## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the live send-window profile of 2026-10-10 (the same round that filed TASK-33620.15.3, .4, .6 and .7). Method: isolated profiles, Anthropic haiku through the review proxy, 160x45, 56 sends over 10 launches; a probe on the app's PYTHONPATH timed every UI-loop callback and sampled the main thread every 4 ms while a callback ran, between a send's acceptance and its provider call.

After a send is accepted, run start (`ConsoleRuntime._run_custodied_turn` > `submit_draft`) holds the UI loop for 72 ms per send over 30 sampled sends, and for 169 ms on the first send after launch (5 sends). 81% of it is on-CPU. On first sends it was the longest single callback of the window in 3 of 5 sends (callbacks of 40 ms or more: median 76 ms, max 123 ms). On later sends its two longest callbacks were 16-28 ms each. By samples:
- `PromptHistory.append` builds a file job whose source selection calls `default_prompt_history_path()` twice. Each call is a guarded config operation (storage admission, companion guard, pause probe): about 12 ms per send.
- The MCP catalog fingerprint that decides catalog reuse (TASK-33620.15.1) reads the permission store and the local store, each through an admission scope, in one callback: about 19 ms per send.
- First sends only: lazy imports on the loop (the hooks v2 lifecycle package, `console_visual_transcript` with PIL, `web_tool_impls`) about 25 ms, and the full MCP composition in one callback of about 75 ms (fingerprint, kill switch, external catalog, built-in inventory, which parses `MCP/server.py` three times, tool states, local tool provider).

TASK-33620.15.1 made later run starts reuse the composed catalog. This task shortens what is left of run start's loop time without moving it to a worker thread: TASK-33620.15.1's worker hop made first sends reach the provider 97-249 ms later.

Run start does less work on the UI loop on first sends, and it never hops to a worker thread. On first sends, run start's loop CPU is halved, it imports no modules there, and the provider is reached earlier (round 5, without the probe: 8/8 pairs, median -333 ms). Its longest callback fell about 40%, not half. Changes:
- First-send imports warmed at idle. `Chat/console_first_send_modules.py` lists, in send order, the modules a first send imported on the UI loop on origin/dev (52 modules and three packages before the provider call, 9 at the run's end), taken from the live import record and the harness's send (75 entries; a few, such as the sync tick's and the dictation-state sync's, are already loaded in a live app before the first send, so dictionary hits there). `TldwCli._preimport_heavy_screens` imports them on its daemon thread after the screen routes (they ran first until TASK-33620.15.14 measured the cost to the first navigation; see the 2026-10-20 section below), then parses `MCP/server.py` once and freezes the heap again. It is paced like the screen routes: a park while navigation or Console custody owns the loop before each import, and a pause as long as the previous import. In a fresh interpreter the imports cost about 213 ms CPU (`Canvas.native_authority` is 190 ms wall of it). Nothing runs before UI-ready.
- Prompt-history path kept on (config module, the mapping it has installed, `current_config_identity()`, `HOME`, and whether each of ADR-127's two default data roots exists), read before and after a resolution. The root entries were added after the 2026-10-20 review: without them a default root re-selected on disk (conventional root removed, fallback root present) kept the old root's path, and the bound history's state check compared that stale path with itself instead of refusing it; pinned by a test that moves the root. The installed mapping is compared by identity because a forced reload (`load_cli_config_and_ensure_existence(force_reload=True)`) installs an edited file without a new generation; keyed on the identity alone, a history opened after such a reload bound the old profile's path and its first append was refused (found 2026-10-20, fixed, and pinned with a real file edit plus forced reload). A stale kept path is refused by the bound history's state check, as dev refuses it. Probed on both arms: deleting the data dir, or making it group-writable, between two appends gives the same outcome (recreated, or refused with nothing written). One difference is when, not whether: with a group-writable data dir, dev refuses at path resolution, so no history is constructed; with a warm memo the history is constructed and its first append is refused.
- Manifest parse kept by `server.py`'s identity (path, dev, inode, size, mtime_ns, ctime_ns), checked before and after the read. The manifest is still built fresh on every call. Recorded in `Docs/Architecture/tool-catalog.md`.
- Yields: between the catalog fingerprint's two store reads (every send), and between the loop-side composition reads (non-stock sources only; dev's stock path reads in workers). Live, the run task waited a median 1 ms at the fingerprint yield (max 125 ms, 16 sends).
