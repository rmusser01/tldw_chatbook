## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: In every Library list canvas with its own filter box -- Notes, Media, Prompts, Skills, Conversations and Collections -- Escape in the filter moves the caret into the rail's "Search Library…" box (the shared focus-rail hop). That box is also a text field, so the list's single-letter keys (`n` new note, `g` go to folder, `s` select, `/` find, `c` resume) still type as text after one Escape; only a second Escape (which leaves the rail search box for a canvas control) makes them live. task-32051 recorded the same hazard for the rail box itself ("the next printable key typed into the rail box").

TASK-34000.40 (polish-1a Task 5, ruling T5-b) made the footer honest about it: the typing footer in these filters no longer lists the list's keys behind "after esc:". The behaviour itself -- where Escape should land -- is a design question for the owner: keep the hop to the rail search (and the copy as it now is), or leave the field to a non-text control as `library_blur_text_field` does elsewhere.

Evidence (polish-1a Task 5 probe, LibraryHarness at 170x48): for each of the six filters, Escape landed focus on `library-search-input`, and before ruling T5-b the footer read, for example, `typing in field | esc focus rail | after esc: / focus search · s select` (Media) and `… after esc: n new note · / find note · g go to folder` (Notes).
