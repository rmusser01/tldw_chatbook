## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From PR #2943 thread PRRT_kwDOOcyyl86nulre. regenerate_message leaves the failed sibling off-path, restores the stopped original as the active leaf, and then recover_and_drain pauses FAILED. The shelf and the Manage modal offer only Resume, and on origin/dev Retry refused. The failed regeneration also moves the context epoch (0 to 3 in the review's probe), so any Retry or Resume from that state goes through resume()'s CONTEXT_CHANGED re-pause, and the fix must adopt or review the epoch explicitly. Decide between two options. Option 1: record the failed attempt on the pause (a registry snapshot change), then choose whether to re-run the off-path sibling or regenerate the anchor. Option 2: an inference rule that cannot mislabel FAILED pauses not caused by a turn (coordinator.py:296/564/825).

Corrected model from the PR #2943 round-3 review:
- **The retry never runs today.** After an unrelated context change, a Retry or Resume goes through resume()'s APPLIED CONTEXT_CHANGED re-pause, which creates no chain.
- **Why the controller refuses it.** recover_and_drain then runs the retry with a QueueGenerationAuthorization that authorizes() rejects, because no chain exists. Before #2943's guards, the refusal copy was thrown away and _pause_or_finish wrote FAILED/STOPPED back, so the press was a silent no-op.
- **So changing resume() to report the re-pause as not applied loses no working behaviour.**
- **What #2943 does instead.** It routes both Resume and Retry to 'Context changed | Review'. After 'Use current context' the queue drains the NEXT prompt and does not re-run the failed one. Whether to re-run it is part of this task's design decision.
