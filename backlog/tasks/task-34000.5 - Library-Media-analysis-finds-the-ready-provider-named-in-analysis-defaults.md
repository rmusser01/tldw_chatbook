## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: Library analysis never works, for any user. Generate on an item, bulk Analyze and Analyze-after-import are all dead. The message also sends the user to a Settings page that cannot fix the problem. The power user (Morgan) configured a ready provider and still could not analyse anything. A first-timer simply concludes the feature is broken. The app's own bootstrap writes an `[analysis_defaults]` section into the default config, so the shipped configuration is affected too.

What was observed (160 columns; verify capture 03):
- Library ▸ Media ▸ "Q3 planning memo" ▸ Analysis tab shows "No analysis yet.", "Add analysis   ○ Generate" and "No analysis provider is configured · Set one in Settings ▸ Providers & Models."
- This happens even though the run config has `[analysis_defaults] provider = 'OpenAI'`, `model = 'gpt-4.1-mini'`, with a ready key.
- Bulk "○ Analyze" shows the same reason (j4).
- The isolated probe (capture 08) prints `'analysis_defaults' in load_settings(): False`. `resolve(load_settings())` gives `ready=False reason='no analysis provider is configured'`. The same resolver with `analysis_defaults` added back gives `ready=True dispatch='openai' model='gpt-4.1-mini'`.

Verified cause (origin/dev 2d34cbf80d):
- `load_settings()` (config.py:1990) builds its return dict at config.py:2589-2620 and does not carry `analysis_defaults` over from the TOML. The shipped default config does write `[analysis_defaults]` (config.py:5514).
- The app stores `self.app_config = load_settings()` (app.py:1124).
- Library resolves the provider with `resolve_ingest_analysis_provider(self.app_instance.app_config)` (UI/Screens/library_screen.py:33087; Library/ingest_analysis.py:158-176). It therefore never sees the section.
- The remedy text is `NO_ANALYSIS_PROVIDER_NEXT_STEP` (Library/ingest_analysis.py:43).

Suggested direction (a direction, not a mandate):
- Carry the table through with `'analysis_defaults': copy.deepcopy(toml_config_data.get('analysis_defaults', {}))` in `load_settings()`, at about config.py:2605.
- Add a guard test that every top-level table the app reads through `app_config.get(...)` survives `load_settings()`. That closes this class of drop for good.

Ownership: TASK-28018 owns only the remedy wording. Its recon notes there is no in-app Settings control for the analysis provider, so "Settings ▸ Providers & Models" points at a page that cannot fix this. This task covers the config-load defect, the readiness it breaks, and the guard test. It does not change the remedy wording.

Review finding(s): L-02. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Cause (verified on wave base 3027850197).** `load_settings()` builds its return dict by hand (`config.py` `config_dict = {`, line 2666) and had no `analysis_defaults` entry, so `app.app_config` never carried the table although the raw TOML (and `COMPREHENSIVE_CONFIG_RAW`) had it. Every analysis path -- the Reader's Generate (`library_screen.py` `_library_media_analysis_provider_reason` / Generate handler), bulk Analyze, Analyze-after-import (`app_ingest_queue.py:2312`) and the Media viewer's panel seed (`media_viewer_panel.py:1523`) -- resolves through `resolve_ingest_analysis_provider(app_config)` (`Library/ingest_analysis.py:160`), so all of them reported "no analysis provider is configured".

**Fix.** One loader change: `config_dict["analysis_defaults"] = copy.deepcopy(toml_config_data.get("analysis_defaults", {}))` (same idiom as `appearance`/`persona_buddy`/`skills`). No reader, precedence, or remedy-copy (TASK-28018) changes. The same hunk also mirrors dev's conditional `buddy_interaction` carry-through verbatim (dev commit `3146bbd8da`, PR #3011) so the guard's register below stays exact across the merge and the merge is clean.

**Tests (TDD).** `Tests/Library/test_ingest_analysis_load_settings.py` (AC#5, AC#3): resolution over the REAL `load_settings()` via the fresh-module recipe (`install_config_source`; the shared config module is bound to the test bootstrap profile and refuses a redirected reload with `RecoveryRequired(raw_source_selection_changed)` -- see the lessons addendum). RED on 3027850197: `not ready: 'no analysis provider is configured'; 'analysis_defaults' in settings = False` (3 failed / 1 passed). GREEN: 6 passed in 8 s. AC#3 fences: empty provider -> `NO_ANALYSIS_PROVIDER_REASON`; absent user table + placeholder key -> not ready. Finding while writing them: the loader merges the shipped default config, whose `[analysis_defaults]` names OpenAI (`CONFIG_TOML_CONTENT`), so "absent from the user's file" + a ready OpenAI key resolves ready via that default -- by design, pinned by a test that documents it.

**AC#4 guard** `Tests/test_config_load_settings_table_guard.py`: DERIVES the top-level keys the package reads from the settings object (AST over `.get("k")`/`["k"]` whose receiver is `*.app_config`, bare `app_config`, a `load_settings()` call, or a local bound from one of those; sound text prefilter on those two names; 57 keys from 203 files), loads a TOML that defines every table pass 1 did not produce unconditionally, and fails naming each table dropped. Two pinned lists bound it, both checked in both directions: `DERIVATION_BOUNDARY` (2 non-table reads) and `PRE_EXISTING_DROPS` -- 21 tables the loader ALREADY dropped on the base (`API`, `AppRAGSearchConfig`, `HiggsSettings`, `OmniVoiceSettings`, `app_tts`, `chat`, `custom_endpoints`, `custom_openai_2_api`, `encryption`, `global_tts_settings`, `home`, `llm_management`, `media_creation`, `model_capabilities`, `network`, `provider_setup`, `rag`, `tldw_api`, `transcription`, `web_server`, `webhooks`), the same defect class, left out of this P0 because several change subsystem behaviour (TLS trust mode, TTS backends, RAG service constants) and need their own verification (TASK-34000.53). The register can only shrink: carrying a table through without deleting its row fails. Negative control: removing `analysis_defaults` from the loaded dict makes the guard name it with the `media_viewer_panel.py` read site (test), and with the entry removed from the loader the guard fails `analysis_defaults: read at tldw_chatbook/Library/ingest_analysis.py:160, tldw_chatbook/Widgets/Media/media_viewer_panel.py:1523, tldw_chatbook/Widgets/Media/media_viewer_panel.py:1595`. 7 passed in 13.6 s. Both files are in the fast PR lane (`derived-artifacts.yml` + `test_ci_queue_pressure_contract.py`).

**Fix round 1 (review 1, Important #1 + minors).** The derivation now also sees `(app_config or {})` / `a if c else b` receivers, `getattr(x, "app_config", ...)`, and ONE level of call-site propagation resolved through imports (a helper's parameter is a receiver only in the module the caller imports it from, or the caller's own file -- name-only matching had bound `Backup_Recovery/credentials.py`'s `record` and produced four false "dropped tables"). That surfaced `model_capabilities` (BoolOp), `webhooks` (`webhook_config_from_settings(load_settings())`, whose module contains neither name and is parsed only for the second pass) and `web_server` (`build_canvas_config_policy(app_config)` from the Settings screen) -- all three registered. Subscripts count only in load context, which moved `canvas` (setdefault + store only) out of the register. The boundary is stated in the module docstring and pinned by `test_derivation_sees_every_reader_shape` (13 seen shapes, 5 unseen) and `test_propagation_follows_imports_not_names`. RED count on the base, corrected: 5 failed / 1 passed.
