## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The model switcher lists a provider whose catalog is empty as "<name> · no models reported · type its name and an id". A user who follows that advice with the name they see in short form gets the wrong provider. On 2026-11-12, TASK-34100.2's live review (LV3-3, profile `g2cv5-v3-oai`) typed "MLX-LM custom-model-gamma" and "MLX custom-model-gamma" while the chat's provider was vLLM. Each became the row "MLX-LM custom-model-gamma · vLLM · typed id · in no catalog". Pressing Enter would have sent the model id "MLX-LM custom-model-gamma" to vLLM. Only the full display name, "MLX-LM (Apple silicon) custom-model-gamma", picked MLX-LM.

This is dev behaviour, outside TASK-34100.2's scope. The switcher's typed-id escape hatch (`ConsoleModelPopover._typed_rows`) pairs the typed text with the provider whose full display name the query starts with. Otherwise it pairs the text with the chat's provider. A display name that carries a qualifier in parentheses, such as "(Apple silicon)", therefore cannot be typed the short way. The captures for this fell in that run's capture gap (`.worktrees/setup-wizard-ux-qa/evidence/g2cv5-v3-hand/00-CAPTURE-GAP.txt`). The successful full-name pick and reply are in `27-recap-vllm-mlx-transcript.txt`.

The goal is that the text the row asks for selects the provider it names. A provider name must never end up inside a model id sent to another provider.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 In the model switcher, a query that starts with a provider's short name (its display name without the trailing parenthetical, for example "MLX-LM") or its provider key, followed by a model id, offers that id on that provider, not as a typed id on the chat's current provider
- [ ] #2 A query whose leading words name no provider still offers the typed id on the chat's current provider, as it does today
- [ ] #3 When a short name matches more than one provider, the switcher never silently picks one of them: the full display name still works, and the ambiguity is visible in the rows offered
- [ ] #4 A query that starts with a provider's full name, short name or key followed by a space is never offered, whole, as a model id on another provider (an id that merely contains a provider key, such as OpenRouter's `openai/gpt-4o`, is unaffected)
- [ ] #5 The "no models reported · type its name and an id" row (and the "catalog unavailable" variant) names text that works, or the rule it follows, and console.md's switcher section says the same
- [ ] #6 A switcher test types "MLX-LM custom-model-gamma" while the chat's provider is vLLM and asserts the offered row is MLX-LM with the id custom-model-gamma; it fails on the current code (the row is a vLLM typed id "MLX-LM custom-model-gamma") and passes after the fix
- [ ] #7 Verified live through the real app on a fresh isolated profile (a hand-edited MLX-LM with no catalog rows, the chat on another provider), recorded in the Implementation Notes
