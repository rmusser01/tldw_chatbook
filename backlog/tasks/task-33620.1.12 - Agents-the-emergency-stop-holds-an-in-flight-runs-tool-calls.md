## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`/emergency-stop` holds new runs, scheduled dispatches and composer sends, but an agent run that was already going when the stop landed keeps executing tools. A review found that the agent's own `shell_exec` tool never checks the stop: during a stop an in-flight run can still raise a shell approval card and, once approved, run the command. The same holds for every other tool source (built-in, local, MCP, sub-agent spawns).

Owner decision (2026-11-23, binding): "HOLD TOOL CALLS TOO — while the emergency stop is active, an in-flight agent run's tool calls (shell and others) are refused with the stop reason; nothing new executes until the stop is cleared."

The kill switch's and the existing stop gates' semantics stay as they are.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 While the emergency stop is active, no agent tool call executes: built-in, local, MCP, the shell tool, and sub-agent spawns are all refused
- [x] #2 Each refused call comes back to the model as a tool result naming the emergency stop (and its reason), which the user also sees on the call's row; the run winds down instead of crashing
- [x] #3 A call already executing when the stop lands is not left in an undefined state: it settles with its own result, and only later calls are refused
- [x] #4 An approval granted after the stop lands does not run the call, and no new approval card is raised while the stop is active
- [x] #5 An unreadable stop state refuses tool calls (fail safe), as the existing stop gates do
- [x] #6 Tools work again as soon as the stop is cleared, without a restart
- [x] #7 Covered by tests that fail on origin/dev for the reason they pin, and documented in the User Guide
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Find the one place every tool call of every run passes before it executes, whatever provider owns the tool, and hold there (not per provider).
2. Keep the agent loop pure: it asks an injected probe; `AgentService` (on the run's worker thread) reads the stop file, fail-safe like the send and scheduler gates.
3. Ask twice: once per batch before preparation/hooks/review (no approval card for a call that cannot run), and once per call at dispatch (an approval granted after the stop landed, or a later call in the same batch, is refused; a call already executing finishes).
4. Return the refusal as a blocked tool result naming the stop and its reason, the way the kill switch refuses, so the model winds down.
5. Tests first (each provider kind through `AgentService.run_turn`, approval-after-stop, mid-call landing, unreadable/corrupt/unresolvable state, Clear), red on origin/dev; mutation-check each layer.
6. Live round on a real app with claude-haiku-4-5; update the Console User Guide.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**What.** While `/emergency-stop` is active, an in-flight agent run's tool calls are refused with a blocked tool result naming the stop and its reason ("tool call blocked: the emergency stop is active (<reason>). No tool runs until the user clears it with /emergency-stop clear."). The model gets it as that call's result and winds down; the user sees it on the call's row (`· Blocked`). Clear lifts it at once.

**Choke point.** `agent_runtime._dispatch_call`: every tool call of every run passes there on its way to `_execute_call` -- the special-tool table (spawn_subagent, send_to_agent, merge/discard worktree, message tools, find/load_tools, skill_file, install_skill, run_skill_script, fork/new chat, run-log tools, recovery tools) and the ordinary path (`deps.invoke_tool` -> skill runner or `ToolCatalogRegistry.invoke_by_name` -> builtin, local, library, canvas, MCP, raw shell and any later provider). `invoke_by_name` was not enough: spawns, skills and the runtime's own tools never reach it. There is one `LoopDeps(...)` construction (`AgentService._run_one`) and one `run_agent_loop(...)` call, so primary, inline and fleet children, goal and workflow runs all get it.

**Two asks, one probe.** `_emergency_stop_refusal(state)` asks `LoopDeps.emergency_stop_refusal` (new, appended last; `None` = no stop wired). It runs (1) once per batch at the top of `_phase_prepare`, as a preparation refusal, so project-instruction preparation, hooks, the guard and the approval review never see a held call (no approval card is raised), and (2) per call in `_dispatch_call` when the verdict is still `proceed` -- an approval granted after the stop landed, or a later call in a batch whose earlier call was running when the stop landed, is refused there. A call already executing is untouched: it settles with its own result. The refusal is a verdict string, so it takes the existing refusal path (blocked `tool_result`, `status=refused`, continuation-safe via `_settle_continuation_refusal`), mirroring the Console review hook's kill-switch refusal. It is not an ADR-154 denial (no `approval_decision`), so the denial breaker does not count it.

**The read.** `AgentService._emergency_stop_refusal` runs on the run's worker thread (never the UI loop): it resolves `emergency_stop.default_emergency_stop_path()` once per service (the per-reply service) and reads the file per ask with `read_emergency_stop`. Fail-safe like the send and scheduler gates: unreadable/corrupt reads as active ("stop state unreadable"/"stop state corrupt"); a path that cannot be resolved, or a probe that raises in the loop, holds the call ("stop state unavailable"). The refusal copy lives in the import-free `Agents/tool_refusals.py` (`emergency_stop_tool_refusal`; reason collapsed to one line, capped at 200 chars). Kill switch and existing gates unchanged.

**Copy.** The activation toast now says "new runs, scheduled dispatches and agent tool calls are held"; the `/emergency-stop` suggestion row says "Hold ALL agent runs, tool calls + scheduled dispatches"; docstrings in `emergency_stop.py`, `emergency_stop_hold.py`, `console_command_grammar.py`. User Guide: `Docs/User_Guide/console.md` Emergency stop paragraph.
