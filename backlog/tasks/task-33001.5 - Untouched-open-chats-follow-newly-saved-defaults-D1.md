## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Owner decision D1, recorded in the ADR-095 amendment of 2026-09-26 (drafted in this worktree with the spec). The task-177 refresh (_maybe_refresh_stale_default_console_settings, UI/Console_Modules/session.py:3743) already converges a pristine chat: no messages, no user work, and settings still equal to their canonical baseline. Three readiness gates stop it:
- it returns early when the chat can already send (:3786);
- it skips labels outside _CONSOLE_REFRESHABLE_BLOCKED_LABELS (:3788);
- it swaps only when the new defaults can send (:3814).

Result: after a Settings Providers & Models save, an untouched chat on a keyless provider that reads Ready (llama.cpp reads Ready even when its server is down) keeps its old provider, model and sampling, and nothing on screen says so (C1(b)).

The same early return causes the first-run gap. Only 'Start chatting' stages the CONSOLE_FIRST_CHAT handoff (UI/Wizards/FirstRunSetupWizard.py:9936). The Home, Library and Notes exits (:7512-7531) and Skip (:9604-9610) do not. The Settings exit (:9585-9595) leaves setup incomplete and opens Providers & Models, so its outcome is an ordinary Settings save. Even the handoff is released without effect if config changes before Console consumes it (session.py:1353-1360). The wizard never bumps console_new_chat_default_generation, so the creation-time check does not block convergence here. Both gaps share one root cause, so this task owns both outcomes.

Cost: this refresh runs on every provider/model display rebuild through _ensure_active_console_session_settings (session.py:3695-3741; see the TASK-26839 note at :3715-3720), which task-24454 places on the composer keystroke path. Today the send-capable early return skips re-deriving defaults. Without it, re-derivation needs another bound.

The amendment says what stays:
- the eligibility test, unchanged, and the creation-time default-generation check;
- Persona identity;
- the task-16475 provider-swap notice;
- source-owned chats (Duplicate, Branch, Continue, handoffs), and chats with work never rebase silently (ADR-095:26-28).

The explicit 'Use saved defaults' action for chats that hold work is not part of this task. Guard tests that must keep passing: Tests/UI/test_console_session_settings.py:12697 and :12727, Tests/UI/test_console_provider_persistence_regressions.py:281, and Tests/Chat/test_workspace_default_session.py:276.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
An untouched open Console chat now takes the saved defaults whatever its readiness (ADR-095 amendment, D1). One root cause covered both gaps, so one change closes both: a Ready chat after a Settings Providers & Models save, and the first-run exits other than Start chatting.

**Mechanism** (`UI/Console_Modules/session.py`, no `chat_screen.py` lines, R8):
- `_maybe_refresh_stale_default_console_settings` loses its three readiness gates, the `_CONSOLE_REFRESHABLE_BLOCKED_LABELS` filter and its `build_console_settings_readiness` import. What stays unchanged: the eligibility test (no messages, no user work, settings equal to the canonical baseline), the creation-time default-generation check (AC#7), Persona identity (AC#8) and the task-16475 notice (AC#9).
- Bound (AC#10, R7): the session controller keeps `_pristine_defaults_checked = (session id, config mapping)`, and the refresh re-derives only when that pair changes. A published config write replaces `load_settings()`'s cache object, so identity is exact between two saves. No new root state. The discarded creation-time defaults in `_ensure_active_console_session_settings` are now derived only when a session is being created (the TASK-26839 pattern), so a display rebuild with a live session derives nothing. The same change in `_sync_console_session_draft` was tried and reverted: it shifted poll timing enough to expose two unrelated racy tests (`test_stale_unavailable_notice_token_cannot_acknowledge_receipts`, `test_mounted_partial_and_provider_failures_name_problem_and_allow_retry`), and no AC needs it.
- AC#11: the check reads only the already-resolved mapping; with readiness gone it makes no keyring or credential lookup at all (a slice of task-24454, which stays open for the other readiness legs).
- First-run (R6): removing the gates is the whole fix. Home, Library, Notes and Skip needed no handoff staging; Start chatting's handoff is untouched.
- Handoff interplay: `consume_pending_console_first_chat_intent` seeds the memo for its target. Its builder (`build_default_console_session_settings`) keeps llama.cpp's configured endpoint, which a blank chat drops. Without the seed, the syncs inside the consume re-derived the target under the handoff's own rollback fences, and a failed acknowledgement left the target instead of restoring the prior chat. A later save converges it like any untouched chat.

**Known limits**
- The memo is one slot on the controller, so switching away and back re-derives once.
- A Console "Make default for new chats" writes and reloads the config on a worker before the UI thread bumps `console_new_chat_default_generation`. The chat Make default was pressed on can never converge in that window: both surfaces live-commit first, which stamps `source="user"` and marks it worked (pinned by `test_make_default_write_before_its_publication_cannot_move_the_chat_it_came_from`). Only a switch to *another* pristine tab inside the window (two worker hops, milliseconds) would move that tab onto the default just made. Not closed: the durability state cannot tell an in-flight intent from a dismissed failure, so a guard on it would stop convergence for good after a dismissed save, and the intent lifecycle lock is held across the disk write.

The false "Review setup and try again" warning predates this task: rider TASK-33001.10.
