## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ADR-036 keeps `TldwCli` as the composition root and defers a typed immutable services bundle until there is more than one real composition root. MCP's standalone server, the mobile web service and config's lazy singletons now each compose their own databases. **Owner decision (2026-10-25): adopt the bundle.** It is a frozen, typed services bundle grouped per feature, built once in `app_service_wiring`. Consumers receive their slice through their constructors. Existing app attributes stay as aliases during migration. The standalone MCP server, the mobile web service and CLI tools such as `doctor` build their services through one shared factory instead of constructing databases ad hoc. There is still no DI container and no mutable registry. This task writes that decision up as an ADR (an ADR-036 amendment or a successor under the next free number) for the owner to accept. It does not implement the bundle.

Source: architecture review 2026-10-25, `Docs/QA/architecture-review-2026-10-25/report.md` §F1; claim-by-claim verification in `Docs/QA/architecture-review-2026-10-25/verification.md` (origin/dev 7a5e2513c5).

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
Wrote `backlog/decisions/244-application-services-bundle.md` with status **Proposed**, and added its row to `backlog/decisions/README.md`. It writes no code; TASK-36947.2 implements it once the owner accepts it.

- **Number and form:** 244 is the next free number at base 2b296e60b3 (the highest was 243). It is a successor that amends only ADR-036's deferral sentence: ADR-036's single-pass and Sync decisions are unchanged, so they keep their accepted record. ADR-036 itself is not edited until the owner accepts ADR-244.
- **AC#2:**
  - Shape: section 1 covers the frozen `ApplicationServices`, per-feature slices, `ScopedServices` for local/server/scope trios, and `Lazy` for members that are built lazily today.
  - Grouping: section 2 gives a table of the main slices and five rules for the rest, including what stays on the app.
  - Who builds it and in what order: section 3 covers the build in `TldwCli.__init__` and `app_service_wiring`.
  - Teardown: section 5. Whoever builds a bundle or a storage closes it; the TUI keeps its explicit unmount order.
  - Aliases: section 4. They are plain attributes or the existing properties, held in a shrink-only list. Each alias is deleted with its last reader, and there is no date.
- **AC#3:** section 6 gives the `open_profile_storage` signature, the per-database openers, and how each entry point uses them: the MCP server, the mobile engine and reading path, the RAG backfill, `doctor`, and the in-app config-getter consumers.
- **AC#4:** section 8. There is no DI container, no registry or locator, no lifecycle framework and no hot replacement.
- **Code facts behind the decisions:** every citation was checked at base 2b296e60b3. Several facts shaped the decisions:
  - The mobile engine builds a `HeadlessAppContext` stand-in for the app.
  - The mobile reading path opens the profile ChaChaNotes database without the migration seed.
  - The TUI's ChaChaNotes handle is config's singleton, and the note tools read it directly. So TASK-36947.2 must keep that handle until TASK-36947.6.
  - The app's unmount never closes the main databases, and its order is not reverse construction order.
  - Several services are composed after first paint or rebuilt, so they cannot live in a bundle that is built once.
- **AC#1 is not met:** it needs the owner to accept the ADR. The ADR lists five open questions with a recommendation for each. The task stays In Progress.
- **Verification:** `scripts/preflight.sh`, run through the scratch-profile wrapper, passed every derived-artifact check (exit 0). No tests were added, because the task changes only documentation.
