## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: lasting sync requires a note to stay unchanged from the moment an automatic file update is admitted until it completes. A second save of the same note inside that window fences the root (`stale_observation` or `postcondition_failed`). Sync then stops in both directions until the user opens Manage sync folders and presses Recovery.

TASK-34000.2 made that hold visible and healable: Recovery commits only a baseline it can prove, and never picks a winner. TASK-34000.1 added an autosave maximum wait, which makes a second save during a pass routine while the user keeps typing. The whole-branch review of wave 1a measured 3 Recovery-class holds in 93 seconds of steady typing in a synced note at the production timings, on a loaded machine.

Wave 1a mitigates on the UI side: a re-save of a synced note waits, bounded, for the pass its previous save hinted. That narrows the window but cannot close it. A slow pass can outlast the bound, and saves from tools or other writers do not wait.

The durable fix belongs in the runtime. An automatic update that was fenced only because its source note moved on is settled automatically on the next pass, with the same proven-baseline settle Recovery performs. The click adds no decision, so it should not be needed. Real conflicts, where the file also changed, must still wait for review.

The mitigation has a cost that this task should remove. Its wait joins every folder's in-flight sync work, not only the note's own folder. So a bound note's save can wait up to three seconds for another folder's pass, and note switch, Back and rail switch hold the Library screen for that long. Measured in the wave 1a re-review: a re-save waited the full bound while another folder's pass was in flight.
