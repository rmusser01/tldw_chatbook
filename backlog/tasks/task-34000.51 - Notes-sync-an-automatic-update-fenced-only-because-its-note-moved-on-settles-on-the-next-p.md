## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: lasting sync requires a note to stay unchanged from the moment an automatic file update is admitted until it completes. A second save of the same note inside that window fences the root (`stale_observation` or `postcondition_failed`). Sync then stops in both directions until the user opens Manage sync folders and presses Recovery.

TASK-34000.2 made that hold visible and healable: Recovery commits only a baseline it can prove, and never picks a winner. TASK-34000.1 added an autosave maximum wait, which makes a second save during a pass routine while the user keeps typing. The whole-branch review of wave 1a measured 3 Recovery-class holds in 93 seconds of steady typing in a synced note at the production timings, on a loaded machine.

Wave 1a mitigates on the UI side: a re-save of a synced note waits, bounded, for the pass its previous save hinted. That narrows the window but cannot close it. A slow pass can outlast the bound, and saves from tools or other writers do not wait.

The durable fix belongs in the runtime. An automatic update that was fenced only because its source note moved on is settled automatically on the next pass, with the same proven-baseline settle Recovery performs. The click adds no decision, so it should not be needed. Real conflicts, where the file also changed, must still wait for review.

The mitigation has a cost that this task should remove. Its wait joins every folder's in-flight sync work, not only the note's own folder. So a bound note's save can wait up to three seconds for another folder's pass, and note switch, Back and rail switch hold the Library screen for that long. Measured in the wave 1a re-review: a re-save waited the full bound while another folder's pass was in flight.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** The distinction is made where the facts are and acted on in the runtime. (1) Executor: a new internal reason `source_moved_on`, raised by `_validate_initial`, `_advance` (RECOVERY_ADMITTED) and `_require_desired` exactly when an AUTOMATIC `update_file` (no journal kind) finds its target intact (`file == request.file`; `_classify` target "original"/"desired"; target "desired" after the write) and only its source (the note) moved on -- `_source_moved_only`. A target that changed too keeps `stale_observation` / `postcondition_failed`; `update_note` and reviewed resolutions are untouched. (2) Runtime: `_execute_locked` returns a typed `_ExecuteOutcome`; on a `source_moved_on` result from an automatic pass it settles the entry under the root lock with the UNCHANGED `settle_attention` (`_settle_source_moved`: proven post-write baseline when the write is exactly on disk, the reviewed baseline otherwise, nothing written; a pre-admission fence has no row and needs no settle) and signals `replan`; `_reconcile_locked` then re-plans inside the same lock with the ordinary gates, at most `_SOURCE_MOVED_REPLANS = 2` times; at the bound the root is left UNBLOCKED with its dirty mark set, `changes_available / sync_now` is published and a hint is scheduled, so `_run_hint`'s loop or the next hint carries the rest. A refused settle (`recovery_authority_changed`, `operation_needs_attention`, `stale_observation`, unreadable authorities) falls through to today's Recovery hold with the reason persisted. `_resume_incomplete` settles a persisted `source_moved_on` entry at startup (`_settle_source_moved_at_startup`) before it would be classified as a hold, so the startup loop leases and reconciles the root. `apply_reviewed` and the activation path never auto-settle (they consume `.results` only). (3) AC#6: `settle_before_save`, `_sync_pass_hinted`, `_settle_port_before_save`, the `settled` plumbing in `_drive_saves` and `RESAVE_SYNC_PASS_WAIT_SECONDS` are removed; `await_sync_pass` / `SYNC_PASS_WAIT_SECONDS` (5 s) stay for the editor-line re-read and the quit flush.
