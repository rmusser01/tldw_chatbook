## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The judge's rule 3 and spec §5 call for one readiness vocabulary from one evidence owner:
- 'Ready · not tested'
- 'Ready · verified HH:MM'
- 'Ready · reachable HH:MM'
- 'Not ready · <reason>'

This keeps TASK-30011 AC#2 (Ready means no known blocker) while ending the overclaiming that AC#6 forbids. Spec §5 limits 'reachable' to local or URL endpoints, and says a public listing (OpenRouter's catalog needs no key, ADR-020) proves nothing about a key, so that provider stays 'Ready · not tested'.

Today each surface uses different words:
- Console: 'Ready to send' and 'Ready to send — credential not verified' (build_console_readiness_presentation, console_settings_summary.py:137-158).
- Settings: prose that leads with 'configuration is complete' (settings_screen.py:15246-15251).
- Setup verdicts: their own codes and copy (provider_readiness_verdict, provider_test_evidence.py:311-366).

There is also no way to record 'key accepted by a listing'. The credential facet becomes 'authenticated' only after a successful paid generation (_normalize_generation_credential, provider_test_evidence.py:1135-1155).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Spec §5's four words now come from one mapping in `Chat/console_session_settings.py`, and every model surface renders them.

**One mapping (AC#1/#7).**
- `readiness_words(ConsoleSettingsReadiness)` is used by the Console surfaces. `verdict_readiness_words(ProviderReadinessSnapshot, evidence)` is used by Settings' test result.
- Both read the same tables:
  - `_NOT_READY_REASONS`: every blocker code.
  - `_FAILURE_REASONS`: every endpoint failure category. 401/403 read "key rejected", and a refused connection reads "refused :PORT", with the port only, taken from the evidence connection.
  - `_VERDICT_READINESS`: every setup verdict code, mapped to a blocker, to "evidence", or to not tested.
  - `_SUBSCRIPTION_REASONS`: a Claude subscription names its login, not a key.
- `Tests/Chat/test_readiness_words.py` checks each table against its `Literal` codes, so a new code without a word fails.
- P4's `switcher_readiness_words` / `_NOT_READY_REASONS` (console_model_popover.py) is now a thin call (ruling 8).

**Evidence behind Ready (AC#2-#6, #9).**
- "verified" means a successful paid generation, or `credential == "listing_accepted"` on a cloud provider.
- "reachable" means a local, URL or custom endpoint (`URL_BASED_PROVIDER_KEYS | KEYLESS_PROVIDER_KEYS` or a custom entry) whose listing answered. This holds even with a key, per ruling 9.
- A cloud listing without key acceptance (OpenRouter) stays "not tested".
- Neither "verified" nor "reachable" is shown without an observed connection and time. HH:MM is the local settle time of the fact behind the word (`observed_at` for a listing, `generation_observed_at` for a paid test), never a provider time.
- New credential facet `listing_accepted`:
  - `ProviderProbeResult.key_accepted` records it at settle. It is only valid for an answered listing and only applies when a key was sent.
  - It moves with the endpoint fact in both the draft store and the shared owner. A later refused listing replaces it.
  - Normalization still promotes a successful paid test to `authenticated`, so the two never merge.
  - Task 4 produces it.

**Review round 1.**
- Precedence (AC#8): `verdict_readiness_words` ranks blockers as the Console does: configuration, then a missing model, then a failed, running or stale test. - Times (AC#9): `ProviderTestEvidence.generation_observed_at` (and `ConsoleSettingsReadiness.generation_observed_at`) hold the generation fact's time. A generation settle no longer restamps `observed_at`, so "reachable HH:MM" is the listing's time, and a paid "verified HH:MM" is the paid test's.
