## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** On 6 of 6 healthy sends at 235x52, while the header said 'Running' and the transcript said 'Thinking... 5s', the Inspect rail showed:
- pinned summary 'Run: Blocked';
- Run section 'Provider: blocked - Provider setup needed: current run is active', in red;
- Conversation settings 'Not ready - current run is active';
- collapsed edge badge 'setup'.

All of these reverted once the run finished.

On 3 of 5 slow-mode sends, 1.5-3 s after Enter, the composer also showed 'Send blocked - finish provider setup to continue >'. That strip links to `app.run_setup_wizard`, and clicking it mid-run opened the first-run wizard over the Console. The cause: the prompt queue's pre-acceptance 'Preparing...' tooltip (and, by the same code path, 'Queue full') is passed in the `setup_blocked_reason` slot.

The panel that answers 'What happens if I send now?' is therefore wrong on every turn. Users learn to ignore 'Blocked' and 'setup' before a real key problem ever occurs.

**Severity / prior art.** P1, confirmed by all three verifiers. This is a **REGRESSION of TASK-347 (Done)**: status surfaces should reflect active generation. It also regresses **TASK-32345 (Done)**, whose guard was applied to one consumer only, and **TASK-24602 (Done)**. TASK-21145 is related. The mechanisms:
- `active_run` is computed as a provider-readiness blocker and routed through the 'Provider setup needed: {blocker}' template (`console_settings_summary.py:167`, Inspector at chat_screen.py:14424-14433).
- The authority rollup evaluates 'Blocked' before run_active (`console_send_authority_summary.py:143-150`).
- The edge badge matches 'provider' plus 'blocked' in row text.

The umbrella task owns the shared ConsoleRunPresentation. This task makes these specific surfaces honest.

**Suggested direction.** Treat active_run as a run-state fact, not a provider blocker, for display consumers. Keep it only for gating settings mutations, where the settings modal already renders it correctly. Let run_active and a pending approval win over a provider 'blocked' caused by active_run. Derive the edge badge from the structured run status. Give the queue its own reason slot, so that Preparing and Queue full have their own copy and never get the setup link.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: a healthy active run is now treated as run state, not as a provider blocker. The Inspect surfaces and the composer read Running / ready / running during a run. The prompt queue's refusal states have their own composer copy, never provider setup and never the setup-wizard link.

Approach:
- `ChatScreen`'s readiness (chat_screen.py ~9900) no longer passes `active_run`. Its display consumers stop inheriting `blocker="active_run"`: the Inspector Provider row and pinned rollup, the settings summary, the Model rail recovery line, workbench chips, the setup card, and the send/setup blocked reasons.
- `active_run` stays as a mutation gate only, inside the settings modal. Its detail copy is now "Settings changes wait for the current run to finish." (console_settings_summary.py).
- Send admission during a run is still owned by the prompt-queue presentation, so no gate was lost. The only side effect is that `native_send_supported` is True mid-run, which only affects the "Capabilities unknown" label.
- The Inspect edge badge reads the structured run status (`FEEDBACK_ACTIVE_RUN_STATUSES`) and shows `running`. Precedence is failed > setup > blocked > approvals > running > tools, so a genuine blocker or pending approval still wins (console_rail_state.py).
- The composer gets a separate `queue_blocked_reason` slot (console_display_state.py, console_composer_bar.py):
  - it is shown verbatim;
  - it ranks below dispatch recovery, the sub-agent wake and genuine setup;
  - it never gets `console-composer-setup-blocked`;
  - it is cached together with the wake flag, so `_sync_current_action_state` (keystrokes, draft loads, resize) replays both.
- Queue copy (prompt_queue.py) is chosen by `activity.preparing_before_acceptance`:
  - "Queue opens once this turn is accepted" while a turn is preparing;
  - "Wait for the current run to finish" for chainless regenerate/continue runs;
  - "Queue full — manage it to make room".
  The wording is aligned with open PR #2934.

Decisions and trade-offs:
- Keep the verbatim-tooltip approach, with the prompt-queue presentation as the one source of copy. Only it can tell a regenerate from a turn awaiting acceptance.
- chat_screen.py is kept net -2 lines (ratchet already red on dev).
- Deferred to the TASK-33620 ConsoleRunPresentation umbrella:
  - "Ready to send" beside a composer that is refusing the send during Preparing;
  - the regenerate VALIDATING-phase copy.

IMPLEMENTATION NOTES for TASK-33620.4 (draft; I did not edit the task file)

A healthy active run no longer reads as a provider problem. Before the fix, every healthy run read "Run: Blocked" in the Inspect pinned summary, "blocked — Provider setup needed: current run is active" on the Provider row, "Not ready — current run is active" in Conversation settings, and "setup" on the edge badge. The cause was that ChatScreen's display and send readiness took `active_run` as a provider blocker. Separately, the prompt queue's Preparing / Queue-full tooltip rode the composer's setup slot, so mid-run it read "finish provider setup" as a link to the first-run wizard.

Changes:
- Readiness (`UI/Screens/chat_screen.py`): the display and send readiness no longer passes `active_run`. Only the settings modal still gates mutations on it. Its detail line (`Widgets/Console/console_settings_summary.py`) now reads "Settings changes wait for the current run to finish." instead of "Provider setup needed: …".
- Edge badge (`Chat/console_rail_state.py`): an active run is read from the structured run status (`FEEDBACK_ACTIVE_RUN_STATUSES`) and shows "running", ranked below failed, setup, blocked and approvals. It used to show "setup" because of a row-text match.
- Queue copy (`Chat/console_display_state.py`, `UI/Console_Modules/prompt_queue.py`, `Widgets/Console/console_composer_bar.py`):
  - The queue's refusal has its own composer slot (`queue_blocked_reason`). It never falls through to setup copy, never carries the setup-wizard link, and a real setup blocker still outranks it.
  - The copy is the shared constants QUEUE_REASON_PREPARING / FULL / RUN_HOLD, used by both the Send tooltip and the strip.
  - Only a prompt-chain turn is ever queue-accepted. A regenerate, continue or agent wake holds the slot with no chain, so it reads "Wait for the current run to finish" rather than "Queue opens once this turn is accepted".
- Docs: Docs/User_Guide/console/chat-basics.md, Docs/User_Guide/console/sessions-tabs-workspaces.md.
