## Implementation Notes (PR #2739) — cost cut applied; a correctness constraint on AC#1/#2

`_poll_console_credential_readiness` now runs its readiness rebuild + gate + sync
inside `self._console_derivation_scope()`, so each tick makes ONE `load_settings`
admission instead of six (the finding's ~49 ms → ~8 ms). Behaviour is unchanged.

AC#1 ("~1 ms/tick") and AC#2 ("rebuilt on a revision change, not every tick")
CANNOT both be met while staying correct: the review's revision-only
short-circuit would skip the rebuild when `subscription_readiness_revision()` is
unchanged, but `_SubscriptionReadinessCache.status()` reports a credential's
**time-based expiry** (`time.time()*1000 >= expires_at_ms`) with NO revision
bump — so a revision gate would leave the send controls showing a stale "ready"
past expiry. The current `(revision, status)` gate catches that, and
`readiness.subscription_status` is active-provider-gated, so it cannot be
replaced by the cheap cache status without changing which provider states the
poll reacts to. The safe win (one admission per tick) is applied; driving to
~1 ms would need an expiry-aware cheap signal (a cache accessor that versions
`expires_at_ms` crossings), which is `anthropic_subscription`'s to add.
Remaining: (3) stop the timer in `on_screen_suspend` (needs a matching
`on_screen_resume` re-arm; the timer is armed once for the screen's life today).
