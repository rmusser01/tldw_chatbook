## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-33621.30's review (2026-11-24); found by reading, not reproduced.

**The fix that exposed it.** TASK-33621.30 made `ConsoleChatStore.publish_durable_dispatch_checkpoint` replace an inert checkpoint-free owner (`REMOTE_ACCEPTED` / `REMOTE_DISPATCH_STARTED`) with a new send's durable owner.

**The gap.** In `ConsoleChatController`'s post-commit failure handling, the non-native path still publishes the committed turn's recovery owner only when `self.store.dispatch_recovery_for_session(session_id) is None` (around `console_chat_controller.py:13417`). An inert REMOTE owner is not None, so that path counts it as holding the session.

**The effect.** Suppose a send made from a REMOTE card fails after its commit but before `durable_owner_publication`. Then `publish_durable_recovery_owner` is skipped. The new committed turn has no in-memory recovery owner until the chat is reopened, while the stale inert card stays on screen.

**Suggested shape.** One shared "owner claims the session" predicate, used by both the store's publication and the controller's failure paths. It would be true for any owner except an inert checkpoint-free REMOTE_* owner, so the two sites cannot drift apart.
