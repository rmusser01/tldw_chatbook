## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Rider from the TASK-33001 final review (M4), pre-existing. ADR-012 treats `credential_source` as an explicit auth decision, and TASK-33001.7 relies on it: a keyless save records `credential_source = "none"`, because quitting writes the shipped template's `api_key_env_var` back into the section, and only "none" keeps that name inert (resolve_provider_credential honours it).

The legacy summarizer path does not. `_resolve_provider_credential` in LLM_Calls/Local_Summarization_Lib.py (used by the koboldcpp and tabbyapi summarizers) falls back to the environment variable named by `api_key_env_var` whenever no stored key resolves. It never reads `credential_source`. So for a section that says "none" and still carries the template's env-var name, exporting that variable later makes these summarizers send it as an API key to a local server, while resolve_provider_credential (and so Console readiness) resolves no key for the same section.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A provider section with credential_source = "none" makes the legacy summarizers send no API key, even when the environment variable named by api_key_env_var is set
- [x] #2 The summarizers resolve a credential the same way as resolve_provider_credential for every credential_source value, or the difference is recorded in ADR-012
- [x] #3 A test with the variable exported covers the "none" case for koboldcpp and tabbyapi and fails if the env fallback ignores credential_source
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Pin it first (TDD): with the named variable exported and `credential_source = "none"`, each summarizer must resolve no key and put none on the wire. Add a table that compares the summarizer's key with `resolve_provider_credential` for every source value, stored-key shape and variable state.
2. Make `_resolve_provider_credential` take its key from `resolve_provider_credential`, keep the legacy `[API]` rung and the blank-versus-absent result, and keep ciphertext out.
3. Record the two differences that remain in ADR-012, then run the files that cover the module.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The KoboldCpp and TabbyAPI summarizers now take their key from `resolve_provider_credential`, so `credential_source` decides for them as it does for Console readiness.

What changed:
- `LLM_Calls/Local_Summarization_Lib.py::_resolve_provider_credential`. "none" returns the blank result and reads nothing. Otherwise the key is whatever `resolve_provider_credential` returns for the modern table. Only when that is nothing and no source is recorded does the legacy `[API]` key (`kobold_api.api_key`, `tabby_api.api_key`) apply. The blank-versus-absent result is computed as before: blank when either table declares an `api_key`, absent otherwise.
- The first parameter is now the provider key. It was a caller key that both call sites passed as `None`, because they handle their own `api_key` argument first.
- Every candidate passes `resolve_provider_api_key`. Ciphertext was already kept out (TASK-34100.4); a placeholder such as `<API_KEY_HERE>` used to be sent as a bearer token and is now blank.
- ADR-012 has a 2026-10-10 amendment with the ruling and the three differences from readiness that remain (AC#2; the third was added in fix round 1).

The rider's premise holds for the resolver and not for the app's requests. The resolver returned the exported variable for a "none" section. A direct call of the TabbyAPI summarizer then sent it as `Authorization: Bearer`. The app never did: its only route to these summarizers is `analyze`, which bound the TabbyAPI summarizer by position, so the system message arrived as the caller's key and the resolver was never reached (fix round 1, below). KoboldCpp never puts a key on the wire: its summarizer builds no authentication header, and the key is used only to decide whether the run may go ahead. So the KoboldCpp rows of the test assert the resolved value, which was the exported key before the fix.

Rulings:
- Ruling: "none" returns blank ("", go ahead with no header), not absent (None, refuse the run) -- why: "none" is an explicit decision that the server takes no key, and AC#1 needs a request on the wire to show that no key is sent -- cost if wrong: a TabbyAPI section saved as "none" with no key anywhere now reaches the server unauthenticated. By a direct call it used to return an error string before contacting the server; through the app it used to reach the server with the system message as its bearer.
- Ruling: the legacy `[API]` key now ranks below the named environment variable; it ranked above it -- why: that is ADR-012's order (stored key, environment variable, legacy `[API]`), and it is the order Console readiness and the chat path use, so a summary and a chat now send the same key whenever readiness resolves one -- cost if wrong: a user with both `[API] tabby_api_key` and the template's `TABBYAPI_API_KEY` exported now sends the variable's value in summaries.
- Ruling: a placeholder key is screened, not sent -- why: CLAUDE.md requires a handler that reads its table directly to apply `resolve_provider_api_key`, and readiness already rejects it -- cost if wrong: none; a placeholder is not a credential.

Fix round 1 (2026-10-11), from the review of fc4326fc7b:

The fix above did not reach the app. `LLM_Calls/Summarization_General_Lib.py::_dispatch_to_api`, the only caller of the TabbyAPI summarizer in the app, passed `(text, prompt, temp, system_message, streaming)` by position against `(input_data, custom_prompt_input, system_message, api_key, temp, ...)`. `analyze` always fills a system message, so it arrived as the caller's key: the resolver was skipped and every request carried `Authorization: Bearer <system message>`. The streaming flag landed in the temperature slot and the temperature in the system-message slot. AC#1 and AC#2 held for a direct call only.

What changed:
- The dispatcher binds the TabbyAPI summarizer by keyword, so `system_message`, `api_key`, `temp` and `streaming` each reach their own parameter. On the app's route the request's first message is now the system message, a call that names no temperature sends 0.7 (it sent `false`), and `streaming=True` asks the server for a stream.
- `analyze(streaming=True)` returns the joined text for this provider, not an iterator: the recovery admission wraps the summarizer's generator, and `analyze` returns only a plain generator unconsumed. No caller in the app passes `streaming=True`.
- The caller's key is forwarded, as it is for KoboldCpp and every other provider. ADR-012 records it as the third difference from readiness: a non-blank caller key outranks the section, "none" included. Library ingest passes the key readiness resolved, which is none under "none".
- `config.py`: the loader's default for `tabby_api.api_key` is blank, as KoboldCpp's, where it was none (ruling below).
- ADR-012: the amendment no longer says the app sent the variable, it has the third difference, and its "Blank is not absent" bullet says what the shipped TabbyAPI section does.

Rulings:
- Ruling: the loader's default for `tabby_api.api_key` is blank -- why: with the call bound correctly the summarizer read its section for the first time on the app's route, and a TabbyAPI section in its shipped state (only the variable's name, no `[API] tabby_api_key`, the variable unset) resolved "no credential at all". Measured with the real loader: `analyze` returned `TabbyAPI: Unexpected error in summarization process: 'NoneType' object is not subscriptable` before any request, while readiness reports TabbyAPI ready (it is in `KEYLESS_PROVIDER_KEYS`) and the app had always sent the request. KoboldCpp's default was already blank -- cost if wrong: a TabbyAPI server that needs a key now answers 401 where the summarizer would have refused first. Only the summarizer reads that section. To undo, put `None` back and drop `test_a_shipped_tabby_section_goes_ahead_without_a_key_through_analyze`.
- The summarizer's refusal for settings that declare no key in either table is unchanged: `Tests/LLM_Calls/test_summarization_diagnostic_privacy.py::test_tabby_missing_credential_error_contract_is_unchanged` still passes.

Not fixed, outside this rider: the same dispatcher binds two more summarizers wrongly by position, with no effect on a credential. For KoboldCpp, `temp` and `system_message` are swapped (the summarizer uses neither) and `streaming` lands in `kobold_api_ip`, so `analyze` never asks KoboldCpp for a stream. For Ollama, `None` lands in `api_url` and `streaming` in `model`.
