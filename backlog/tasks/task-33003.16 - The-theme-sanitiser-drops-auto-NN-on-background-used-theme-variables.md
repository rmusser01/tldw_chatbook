## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
sanitize_theme_variables keeps 'auto NN%' for any variable name, but Textual's process_color accepts auto only for non-background properties. A saved theme with block-cursor-blurred-background = 'auto 30%' or surface-lighten-2 = 'auto 50%' passes the sanitiser and becomes a stylesheet error wherever Textual's CSS uses that name as a background. That is the crash class the sanitiser exists to stop (TASK-32940 review finding 1). Since TASK-33003.6 round 2 the contrast guard no longer raises on such values, but it does not make them paintable. Found in TASK-33003.6 review round 2.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A saved or imported theme that sets 'auto NN%' on a variable a stylesheet paints as a background no longer becomes a stylesheet error: the sanitiser drops the entry with a warning, and Textual's own colour for that name is used.

**The rule.** Textual's `process_color` takes `auto` for a text colour only. As a `background` (or any property whose name contains "background") it is "Invalid value ('auto') for the background property", and a border colour does not parse it either. `sanitize_theme_variables` now keeps 'auto NN%' unless the name is in `_NO_AUTO_NAMES` (css/Themes/themes.py):
- every name Textual generates whose own value is not auto (161 names: the surfaces, panels, primaries, borders, block-cursor and footer colours, text-primary, and so on), and
- the guard's three names (`GUARD_VARIABLES`).

So 'auto NN%' is kept on the seven names Textual itself sets to auto (`text`, `text-muted`, `text-disabled`, `link-color`, `link-color-hover`, `block-cursor-foreground`, `button-color-foreground`), which every stylesheet already paints with auto, and on a name no stylesheet knows, which paints nothing. The set is computed from Textual at import, one `generate()` call, so it follows a Textual upgrade. The dropped entry gets the sanitiser's existing warning, "dropping invalid variable '<name>'", which names the file and never the value.

- Ruling: drop auto on every generated name whose own value is a colour, not only on names found in a `background:` rule. Why: a name-by-use list needs a scan of Textual's widget CSS and this app's sheets, and a miss is a crash at startup. This app paints `text-primary` as a bar fill and as a border, and Textual's own Button tints with `$foreground`, so a name that reads like a text colour is not safe either. Cost if wrong: 'auto NN%' on a name that is only ever a text colour (`footer-foreground`, say) is dropped although it could paint; the theme then uses Textual's colour for it.
- Ruling: keep auto on names no stylesheet knows. Why: `Tests/Utils/test_user_theme_loader.py` already pins `scrollbar-color = "auto 50%"` as kept, and an unreferenced name cannot break a parse. Cost if wrong: none found; a tcss-defined `ds-*` name shadows a theme entry of the same name.

**Review round 1.**
- The rule is stricter than this rider's wording, and it stays. Of the 161 generated names that drop auto, 21 by a regexp scan of the declarations (the review counted about 20) are only ever a `color` or a `scrollbar-color` in Textual 8.2.8's and this app's CSS (`footer-foreground`, `footer-key-foreground`, `footer-description-foreground`, `button-foreground`, `input-cursor-foreground`, `markdown-h1-color` to `h6`, `scrollbar`, `scrollbar-hover`, `scrollbar-active` and others). Auto could paint there and is dropped. The rider's own set (names found in a `background:` rule) would still crash on `text-primary`, which this app paints as a fill and a border. An allowlist for the text-only names is the owner's call and needs a test that scans the CSS. The themes.py comment and the User Guide now say this.
- AC#4, added in this round as a scope decision rather than a silent fix. The sanitiser kept a text-style keyword on any name, so `text = "bold"` or `surface-lighten-2 = "bold"` passed and became `color: bold`: a `StylesheetParseError` when the theme applied, the crash class this rider is about. The mirror case crashed too: `link-style = "#ff0000"` is "Invalid value '#ff0000' in link-style property", in every app, because Textual's own widget CSS reads `$link-style`. Both were probed at head before the fix and are unchanged from the task base.
  - The rule, from the generated table already behind `_NO_AUTO_NAMES` (`_GENERATED`, still one `generate()` call at import): `_STYLE_NAMES` is the 12 names whose generated value is made of Textual's style flags (`link-style`, `link-style-hover`, and the block-cursor, button-focus, input-cursor and markdown `-text-style` names). `_COLOUR_NAMES` is the other 156 generated names and the guard's three. A text style is kept unless the name is a colour name; a colour or auto is dropped on a style name. A name no stylesheet knows keeps any valid form, as before.
  - Nothing shipped changes: no variable carried by the 70 shipped or 21 built-in themes is dropped, so cloning one and saving it loses nothing.
  - Tests, Tests/Utils/test_user_theme_loader.py: `test_load_user_themes_drops_a_value_of_the_wrong_kind` (five entries dropped with five warnings: `bold` on `surface-lighten-2` and `text`, `none` on `tldw-boundary`, a colour on `link-style` and on `block-cursor-text-style`; `link-style-hover = "italic"` and an unknown name's `underline` kept) and `test_a_value_of_the_wrong_kind_survives_css_refresh` (the loaded theme applies where a stylesheet paints those names as a fill, a text colour, a border and a text style, and the kept italic paints).
  - Pin rewritten on purpose, Tests/UI/test_theme_contrast.py: `test_user_theme_with_any_kept_variable_form_still_loads` expected `text = "bold"` kept; it now expects it dropped, and gains a kept `link-style = "italic"` row.

Green: `Tests/UI/test_app_instance_warning.py` (collected first, so the app import happens at collection, per lessons-testing-evidence.md) with the loader, contrast and theme-import files, 1487 passed.

**Review round 2.** AC#4 kept a text style on a text-style name, but not every kept value could paint. Textual takes `none` only on its own. The review probed five values at the round 1 head (`link-style = "bold none"`, `link-style-hover = "none bold"`, `markdown-h1-text-style = "none bold"`, `button-focus-text-style = "dim none"` and `link-style = "none none"`): each was kept and each ended the app with `StyleValueError: cannot mix 'none' with other style flags`. This round's red test reproduced that error on `markdown-h1-text-style = "none bold"`. The review found it unchanged from the task base; it is the crash class AC#4 was added to close.
- Fix, `_is_safe_variable_value` (css/Themes/themes.py): a run of text-style words is kept only when `none` is absent or is the whole value. It applies to every name, an unknown one included, since `none bold` is no text style anywhere. Probed against Textual 8.2.8: `bold bold`, `bold italic` and `dim strike reverse underline` are accepted, `none bold` and `none none` are refused. The loader, Settings import and the theme editor's load and save all go through this one function.
- Tests, Tests/Utils/test_user_theme_loader.py: `_WRONG_KIND_THEME` gains `markdown-h1-text-style = "none bold"` and `my-own-reset = "none none"` (both dropped, seven warnings in all) and `button-focus-text-style = "none"` (kept). `test_a_value_of_the_wrong_kind_survives_css_refresh` now mounts a widget that paints each of those names, and asserts the kept `none` replaces Textual's own `b reverse`. The first version of that row put the name under `:hover` and stayed green with the bad value kept: the error is raised when a widget paints the style, not when the sheet parses, so the row has to be on a mounted widget at rest.
