## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
In a fresh profile that declines the one-time online model-list check, a Console send with the shipped default OpenAI model `gpt-5.6-terra` is refused: "This request cannot fit the selected model. Response reservation and safety margin leave no model input capacity." The model picker shows that model at about 4k context. Its static capability row has no context window. A new user on default settings cannot send at all until they find a different model.

## Implementation Notes

Root cause (data): `Utils/token_counter.resolve_context_window` fell back to `PROVIDER_CONTEXT_WINDOWS["openai"] = 4096` (a 2025-06 GPT-3.5-era value) for any OpenAI model with no catalog/table entry, which includes the shipped default `gpt-5.6-terra` and the picker's `gpt-5.6-sol`/`gpt-5.6-luna`/`chatgpt-4o-latest`. 4096 - 4096 reservation - 512 margin <= 0, so `console_context_policy` refused every send. ADR-052's TASK-32709 amendment sets the final fallback to exactly 32,000 tokens; removing the row lets unlisted OpenAI models take it, still `verified=False` and labelled estimated. No context window was invented: none of the repo's sources document terra's.

Deliberately not changed: whether an *estimated* window should ever hard-refuse (`console_context_policy.py` raises the no-capacity error regardless of verification). ADR-052 says unknown windows stay "visibly unverified", which arguably means they should warn rather than refuse; changing that touches compaction semantics and belongs in its own task.

Evidence: `Tests/Chat/test_console_unknown_openai_window.py` (4 tests; RED on dev: refusal text / 4096, GREEN now). `Tests/Chat/test_console_session_settings.py::test_unknown_openai_model_uses_shared_unverified_api_fallback` moved from 4096/"provider fallback" to 32000/"application fallback". Live: a fresh UI-created workspace chat on the shipped default `gpt-5.6-terra` sent and completed (it was refused before).
