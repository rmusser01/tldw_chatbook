## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found live on 2026-10-20 while re-measuring TASK-33620.15.1 (isolated profiles, Anthropic claude-haiku-4-5, 235x52, Inspect rail opened during the reply, load 6-15). A probe timed ConsoleEnvironmentController.request_refresh on the UI thread. On origin/dev 2d071d6d71 and on the cadence branch alike, every round had 2-4 calls over 100 ms: 0.9-1.4 s right after the Inspect rail opened (notify_rail_opened), and 0.33-0.52 s at each run's completion, where the coalesced Agent fleet sync nudges it (_run_coalesced_console_agent_fleet_sync took 345-769 ms of which _sync_console_agent_section was 1-4 ms). Input waits for the whole call, and at completion it holds back the replay that renders the cost chip and the Agent rail. Its own docstring calls the local tier git status plus a cached backlog scan, never the network; whatever part runs synchronously in the dispatch is the cost to find. Not separately attributed inside request_refresh yet.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Closed by PR #3210 (merged 28d7ab2c9a, 2026-10-23) together with TASK-33620.15.1.6. #3210 shipped the fix but never updated this file; each AC was re-verified on 2026-10-27.

- AC#1 (measured and attributed, paired against the base build): #3210's live rounds (isolated profiles, Anthropic claude-haiku-4-5, 235x52, alternated with origin/dev) put 611 of 620 stack samples of the hold in the panel's root accessor, which built a whole turn configuration (RAG depth through storage admission, MCP maximum, skills, project authority) to keep `workspace_roots`. Paired: Inspect-rail open 553-1359 ms on the base against 1.8-26 ms; run completion 50-530 against 1.0-34 ms; full turn-configuration builds on the UI loop 212 against 0 (PR #3210 body; lessons-testing-evidence "A one-field accessor can cost the whole builder behind it"). Re-measured 2026-10-27 on origin/dev 3be493413a (after #3210): what was still synchronous was two or three Change Review consent SELECTs per refresh, attributed per call by a probe and fixed in TASK-33620.15.1.6.
- AC#2 (no more than 100 ms on account of the Environment refresh, live, real provider): not met by #3210 alone. On origin/dev 3be493413a at load 29-41, 5 of 20 rail opens held the loop 103-141 ms on that refresh, and at load 6-10 one run completion took 105 ms (two consent reads, 63.5 + 40.3 ms). Met with TASK-33620.15.1.6 (branch perf/task-33620.15.1.6-environment-consent-once, ABBA-paired against origin/dev, load 29-41): 16 rail opens at most 0.3 ms, 10 run completions at most 1.3 ms, and the continuations that land their results at most 2.9 ms. Evidence: tools/evidence/bd5/P16 (aggregate-base-loaded.txt, aggregate-fix-loaded.txt).
- AC#3 (a deterministic test fails on the base build and pins the slow part off the UI loop): `Tests/UI/test_console_environment_refresh_off_loop.py::test_rail_open_completion_and_poll_never_build_a_turn_configuration`, re-run 2026-10-27 on #3210's base build (5e9a4375a3, the merge's first parent): red with "an Environment refresh built a full turn configuration 8 time(s) (['ui-loop' x 8])"; green on origin/dev and on this branch. #3210 removed the slow part rather than moving it to a worker, and the test pins that it is never run on the UI loop on account of the refresh. TASK-33620.15.1.6's tests pin the consent reads that remained off the loop.
