## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: TASK-34000.5 found that `load_settings()` builds its returned settings from a fixed dict literal. Any top-level TOML table not listed there is dropped, so every reader of that table silently gets its defaults. That is how the Media Analysis tab could never see `[analysis_defaults]`, for every user.

The guard added in that task (`Tests/test_config_load_settings_table_guard.py`) derives the tables the app reads from the code. It found 19 more tables that are read from the loaded settings yet dropped by the loader. They are pinned in its `PRE_EXISTING_DROPS` register, which can only shrink:
- `API`
- `AppRAGSearchConfig`
- `HiggsSettings`
- `OmniVoiceSettings`
- `app_tts`
- `canvas`
- `chat`
- `custom_endpoints`
- `custom_openai_2_api`
- `encryption`
- `global_tts_settings`
- `home`
- `llm_management`
- `media_creation`
- `network`
- `provider_setup`
- `rag`
- `tldw_api`
- `transcription`

Several change behaviour that matters:
- `network`: TLS trust and `ssl_verify`;
- `encryption`;
- the TTS backends;
- the RAG service constants;
- custom endpoints.

A reader may also consult the raw TOML elsewhere, in which case the drop is harmless at that site. Each table needs that checked before it is carried through. For each table, decide whether the reader's user-set value was ever honoured, and fix the loader (or the reader) so it is. Carrying a table through can turn on behaviour users configured long ago but never got, so verify each one, and treat security-relevant tables (`network`, `encryption`) with care: a value that silently tightens or loosens TLS or encryption must be called out.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 For each of the 19 registered tables: a written finding (in the task notes) of whether the user's configured value reached its reader before the fix, and what changes once it does
- [ ] #2 Every table whose value should reach its reader is carried through by load_settings() and removed from PRE_EXISTING_DROPS; a table that is deliberately not carried is moved to the guard's documented exclusions with the reason
- [ ] #3 The network (TLS trust / ssl_verify) and encryption tables are verified end to end with a test that sets a non-default value in a temp TOML and asserts the effective behaviour, and any behaviour change is called out in the User Guide and the PR
- [ ] #4 PRE_EXISTING_DROPS is empty at the end, or each remaining row has an owning task
- [ ] #5 Regression tests over the real load_settings() fail on dev for each table that was dropped
