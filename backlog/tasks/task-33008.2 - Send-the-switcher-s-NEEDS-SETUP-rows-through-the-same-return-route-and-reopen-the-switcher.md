## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Phase 4's switcher lists providers that cannot send yet under NEEDS SETUP, with the reason and the fix. Its Enter on such a row opens Settings one way, with no return. The judge's mockup row reads 'Not ready · no key — Enter: add key in Settings ↩'.

A row whose fix is a credential or an endpoint has to leave Console. Without P8.1's return route, that recreates the dead end. Rows whose fix lies outside the app (a stopped local server) already keep in-place guidance since phase 5 and are not changed here.

A chat that already holds work keeps its own settings after a Settings save (ADR-095:26), so after returning the user still has to pick a model from the newly usable provider. Reopening the switcher filtered to that provider turns that into one Enter. Credentials stay in Settings (D4, ADR-012).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Enter on a NEEDS SETUP row whose fix is a missing key or endpoint opens Settings at that provider's exact control through P8.1's return route, replacing phase 4's one-way route.
- [x] #2 After the return, the switcher reopens filtered to that provider. Its models show the phase-5 readiness words, and one Enter applies the highlighted pair to this chat.
- [x] #3 Returning without saving reopens the switcher unchanged.
- [x] #4 An integration test on a scratch config drives a NEEDS SETUP row to Settings, saves a key, returns, and applies the pair. It asserts the chat's provider·model.
- [ ] #5 A live capture at 211x44 shows the reopened, filtered switcher.
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Carry the reopen request in the return handoff (R43): add an optional provider and model to the Console return intent and to the target Settings answers with, sent only when set, and keep both in the handoff store's own copy.
2. Have only the switcher's NEEDS SETUP opener ask for it, through a keyword on open_provider_setup (R42); the card's action, a blocked chat's action and a cloud Retry stay as Task 1 left them.
3. In the Console's landing, after the chat is active, synced and focused, reopen Switch model with the provider's name in Find and the row's pair as the highlight, in the card's mode while the card blocks (R44, R45, R46).
4. Keep a highlight pair that no server listed out of the list until readiness lands, so a fast Enter cannot apply a pair whose key was never saved.
5. Reword the Get started card's line so it promises no return for a custom endpoint, and update each reader of that line (the controller's R37 ruling of 2026-10-10).
6. Tests first; a real-app round trip on a scratch config (R47); guides; live check at 211x44 on a scratch profile.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A NEEDS SETUP row's return from Settings now reopens Switch model on that row's provider, saved or not. The route itself is Task 1's (R32); this task adds the reopen and its request.

- Route (AC#1): the switcher's setup opener calls open_provider_setup(..., reopen_switcher=True). The Settings context is unchanged: provider, model, the field the row's blocker names (api_key or endpoint), the return revision and the chat. The staged ConsoleProviderReturnIntent also carries switcher_provider and switcher_model. A custom-ep: row still goes one way (R35), because the intent refuses its provider key as the navigation target does.
- Handoff (R43): ConsoleProviderReturnIntent and ConsoleProviderReturnTarget gain the two optional fields, validated as a provider route's own provider and model are. to_context sends them only when set, so a recovery's context is byte-identical to Task 1's. PendingHandoffStore's detached copy keeps them. A provider key and a model id are not a key, an endpoint or prompt text.
- Reopen (AC#2, AC#3): Console_Modules/provider_return.py lands as before (switch to the chat, sync, focus the composer or the card), then calls reopen_model_switcher (model_switcher.py), which opens Switch model through _open_switcher with Find set to the provider's display name and a trailing space (R11), card mode while the Get started card blocks (R44), and the row's pair as highlight_pair (R45). Esc therefore leaves focus where the landing put it. It reopens after a save, after Return without saving, after the arrival Return to Console and after the conflict panel's return, because the Console does not read the outcome. It does not reopen for a stale or superseded handoff, a closed chat, Stay in Settings, or a Console reached by hand (none of those lands). It also does not reopen if the Console lost the screen during the landing's sync.
- Stale check: the Console now compares Settings' whole answer with the claimed intent (chat and pair), not the chat id alone.
- Popover: a highlight pair is listed before readiness only when a server listed its provider (the detected-server case, TASK-33008.3). A NEEDS SETUP row's pair waits for readiness, then shows as what it is: a pair to apply once the key is saved, the NEEDS SETUP row again if it was not.
- Card line (the controller's R37 ruling, R35): CONSOLE_SETUP_CARD_SUBTITLE's second line now reads "Cloud setup opens Settings and comes back here, except for custom endpoints. Rulings:
- The request rides in both the intent and the target (R43 as written), and the Console compares the two whole: a target that names another pair than the staged intent is stale. Cost if wrong: drop the target's two fields and the comparison goes back to the chat id.
- The reopen has no exception for a chat that already converged on the saved pair (R46 lists none). Such a chat sees its pair marked CURRENT and one Enter or Esc closes the list. Cost if wrong: one condition in the landing.
- The card line names its exception as "custom endpoints", the name of the Settings section that holds them. The built-in "Custom OpenAI-compatible" slots are ordinary provider keys and do have a return, so for them the line under-promises. Cost if wrong: one constant and the readers listed above.

Not fixed here, measured on the way (pre-existing in Settings, also on Chat settings' Configure credential and on Task 1's recovery whenever the routed provider is not the saved default): while a key is typed on a routed provider's page, the Provider row reads the saved default provider's name (for example "OpenAI" on Groq's page) and the edit is compared with that provider's saved key. The save itself writes the routed provider's table and the default provider's key is untouched (asserted in the round-trip test). A NEEDS SETUP row is by its nature another provider than the default, so this route shows it every time.
