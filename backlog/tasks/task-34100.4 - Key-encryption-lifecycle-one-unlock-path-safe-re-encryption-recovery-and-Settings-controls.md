## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Setting a key-encryption password in setup starts a lifecycle that nothing else in the app supports.
- Launching with python -m tldw_chatbook.app afterwards crashes in the unlock prompt (NoActiveWorker) and exits. The crash output prints frame locals that include part of the password verifier.
- The packaged tldw-cli prompt asks once, with no retry and no reset. A wrong password drops the user into Backup & Restore with no explanation.
- Protect ignores existing encryption, and Enter after success reopens the password dialog. A different second password rewrites the verifier over keys that are still encrypted under the first one. That locks out both launch paths, the step claims the keys are 'unchanged (plain text)', and every later save fails.
- No reachable screen can turn encryption off or change the password, although Protect points to Settings ▸ Privacy & Security.
- Encrypted values pass the API-key validity check, so any skipped decrypt would read as Ready and send ciphertext as a key.
- The password dialog opens without focus, so typed characters vanish.
- Protect misreads keyless, env-key and unsaved-key users, and its copy names a Skip button that doesn't exist.

This task implements SF6 (an encryption lifecycle with one owner) and roadmap items N8–N10 from Docs/superpowers/qa/first-run-wizard-ux-review-2026-10-02/README.md. It resolves protect-summary-01 to -07, new-protect-summary-02 and new-protect-summary-03. The risk is high, because a mistake here locks people out of their own app. Keep startup unlock pre-TUI and isolated, as the Backup_Recovery design intends. Never offer a way to start without decrypting until encrypted values read as absent.

Coordination:
- Open PR #2868 deletes UI/Tools_Settings_Window.py, the only code that calls disable_config_encryption and change_encryption_password. Once it merges, the wizard's Protect step is the only encryption UI, so this task adds the Settings ▸ Privacy & Security controls (enable, change password, turn off), porting them from git history.
- Update task-33621.25 to call out the module-path unlock as a user lock-out, and remove its census row along with the fix.
- Only the Protect-step parts depend on TASK-34100.1. The core can start immediately: module-path unlock through the shared startup preflight, ciphertext read as absent, refusing a second enable, validating before writing with rollback, and unlock retry and reset.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Scope of this PR: the encryption core, the one startup unlock, recovery/reset and the Settings card. The wizard Protect-step parts (AC #2, #7, #8, and the wizard halves of AC #1 and AC #5) wait for TASK-34100.1, which is moving the Protect step out of FirstRunSetupWizard.py; they ship as a second PR.

1. AC #1 (core) -- config.py: `enable_config_encryption` refuses when [encryption].enabled is already true (no write). It builds the encrypted document in memory and validates it before writing: a strict decrypt of the merged result with the new password, and no plaintext secret left. Any failure after the write restores the previous file bytes (or removes a file it created) and the previous in-process password. `disable_config_encryption` and `change_encryption_password` switch to strict decrypt (today a non-strict decrypt can write ciphertext back as plain values) and get the same rollback. Tests: enable(A) then enable(B) returns False with config.toml byte-identical; a forced publish failure restores bytes and password; change/disable refuse a stranded file without writing.
2. AC #10 -- `resolve_provider_api_key` treats an `enc:` value as absent, so readiness, `get_api_key`, the legacy-key bridge and the bridged providers all read a locked or undecryptable key as missing. `chat_api_call` drops an `enc:` api_key argument, and the provider handlers whose fallback reads `api_key` raw from config go through the resolver. Tests: a locked config's provider reads not-ready / key missing; an `enc:` value never reaches a handler as a credential.
3. AC #3 + #9 -- one startup unlock: a `startup_unlock()` in Backup_Recovery/launcher.py wraps `startup_preflight` (strict decrypt) plus admission and password install; `cli.main_cli_runner` and `app_entry._run_module_main` both call it. PasswordPromptApp is deleted along with its census row (scripts/textual_wait_push_census.tsv:91). Tests: drive `python -m tldw_chatbook.app` in a subprocess with the right and the wrong password; force an unlock failure and assert that neither the verifier nor the typed password appears in the output.
4. AC #4 -- the preflight retries in place ('That password didn't match. Try again.'). An empty entry gives up and offers '[R]eset saved keys' or '[Q]uit'. Reset runs after admission through a new config.py `reset_encrypted_config_values()`: it strips every `enc:` value in every section, drops [encryption], and writes through the normal locked writer. RecoveryApp stops auto-pushing Backup & Restore for unlock reasons and shows a plain sentence instead. Prompts say 'master password'. Tests cover retry, reset (chats/notes/docs untouched; no ciphertext left), quit, and the recovery host not pushing Backup & Restore.
5. AC #6 -- PasswordDialog: AUTO_FOCUS on the first password field, a non-focusable scroll wrapper, and a new shared glyph checkbox in Widgets/ for 'Show password'. Change mode gains a current-password field and returns both passwords. Pilot tests type without Tab in all three modes.
6. AC #5 (Settings half) -- a new Encryption card module under UI/Screens (`settings_encryption.py`) shows On/Off and has password-gated Encrypt / Change password / Turn off. Each action runs in a thread worker (exit_on_error=False) and reports its result inline. The logic is ported from Tools_Settings_Window, which is left untouched. settings_screen.py mounts the card in Privacy & Security and drops the 'Credential mutation: not available yet' row. Pilot tests cover each action against a real temp config.
7. AC #13 -- update Docs/User_Guide (settings Privacy & Security, first-run/startup unlock pages) where behaviour changed, with no 'Verified against' stamps. Reword task-33621.25's module-path row as a fixed user lock-out.
8. AC #12 -- RED proof per test on the pre-fix code; targeted pytest, collect-only sweep, preflight.sh; no size budget raised.
9. AC #11 -- live: a fresh isolated profile with a real OpenAI key, encrypted in the (pre-fix) wizard. Relaunch through python -m and tldw-cli with the right password, a wrong password and a reset. Run Settings enable / change / turn off with a relaunch after each. A hand-stranded `enc:` key reads 'not set up'. Finish with a first real reply. Evidence goes under setup-wizard-ux-qa/evidence/g4-*.
