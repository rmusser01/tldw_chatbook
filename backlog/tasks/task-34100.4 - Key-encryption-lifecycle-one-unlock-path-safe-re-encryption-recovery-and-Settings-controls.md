## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Setting a key-encryption password in setup starts a lifecycle that nothing else in the app supports.
- Launching with python -m tldw_chatbook.app afterwards crashes in the unlock prompt (NoActiveWorker) and exits. The crash output prints frame locals that include part of the password verifier.
- The packaged tldw-cli prompt asks once, with no retry and no reset. A wrong password drops the user into Backup & Restore with no explanation.
- Protect ignores existing encryption, and Enter after success reopens the password dialog. A different second password rewrites the verifier over keys that are still encrypted under the first one. That locks out both launch paths, the step claims the keys are 'unchanged (plain text)', and every later save fails.
- No reachable screen can turn encryption off or change the password, although Protect points to Settings ▸ Privacy & Security.
- Encrypted values pass the API-key validity check, so any skipped decrypt would read as Ready and send ciphertext as a key.
- The password dialog opens without focus, so typed characters vanish.
- Protect misreads keyless, env-key and unsaved-key users, and its copy names a Skip button that doesn't exist.

This task implements SF6 (an encryption lifecycle with one owner) and roadmap items N8–N10 from Docs/superpowers/qa/first-run-wizard-ux-review-2026-10-02/README.md. It resolves protect-summary-01 to -07, new-protect-summary-02 and new-protect-summary-03. The risk is high, because a mistake here locks people out of their own app. Keep startup unlock pre-TUI and isolated, as the Backup_Recovery design intends. Never offer a way to start without decrypting until encrypted values read as absent.

Coordination:
- Open PR #2868 deletes UI/Tools_Settings_Window.py, the only code that calls disable_config_encryption and change_encryption_password. Once it merges, the wizard's Protect step is the only encryption UI, so this task adds the Settings ▸ Privacy & Security controls (enable, change password, turn off), porting them from git history.
- Update task-33621.25 to call out the module-path unlock as a user lock-out, and remove its census row along with the fix.
- Only the Protect-step parts depend on TASK-34100.1. The core can start immediately: module-path unlock through the shared startup preflight, ciphertext read as absent, refusing a second enable, validating before writing with rollback, and unlock retry and reset.

The wizard Protect step is not in it, because TASK-34100.1 is moving that step out of FirstRunSetupWizard.py. **Approach**
- **Config core (config.py).**
  - `enable_config_encryption` refuses an already-enabled file without writing.
  - enable, disable and change all validate before they write. Validation means a strict decrypt of the merged replacement with the password the session will hold, and no plaintext secret left in an encrypted file.
  - On any failure after the write, they restore the exact previous bytes (or remove a file they created) and the previous in-process password. The restore goes through `_commit_serialized_cli_config_unlocked`, which is extracted from `_write_raw_cli_config_unlocked` so it also advances an owned recovery binding.
  - disable and change now decrypt strictly. The old non-strict path wrote ciphertext back as plain values, or kept it under a new verifier.
  - New: `verify_config_encryption_password`, `config_encryption_enabled_on_disk` (None when unreadable) and `reset_encrypted_config_values`. The reset strips every `enc:` value from every table and drops `[encryption]`.
- **Ciphertext is never a key.** `resolve_provider_api_key` treats `enc:` as absent; readiness, `get_api_key`, the legacy bridge and the bridged providers all use it. `chat_api_call` drops an `enc:` api_key. The raw fallbacks of openai, anthropic, cohere, huggingface, deepseek, groq, mistral and openrouter now go through the resolver. Ciphertext is deliberately NOT stripped from the loaded config: shutdown persistence re-writes that view and would delete the keys.
- **One unlock (Backup_Recovery/launcher.py).** `startup_unlock()` sits beside `startup_preflight`. It runs the pre-TUI preflight (strict decrypt), then admission, then either the password install or the reset; the reset runs after admission through the normal config writer, so the preflight stays config-free. `cli.main_cli_runner` and `app_entry._run_module_main` both call it. PasswordPromptApp is deleted, along with its W003 census row (27 roots / 69 pushes -> 26 / 68).
  - Behaviour: a getpass retry loop, 'That password didn't match. Try again.', and no attempt cap. An empty entry offers '[R]eset saved keys or [Q]uit'; any other answer re-asks. Ctrl+C or EOF quits with exit 0.
  - Every prompt says "master password". RecoveryApp no longer auto-pushes Backup & Restore for `configuration_unlock_*`; it shows a plain sentence instead.
  - `ConfigEncryption.verify_password` no longer logs an ERROR on a wrong password. Found live: the log line printed between the prompts.
- **Password dialog.** `AUTO_FOCUS` targets the first password field (the current-password field in change mode), and the VerticalScroll is `can_focus=False`. Change mode gains a current-password field and dismisses with `PasswordChange(current, new)`, whose repr hides both values; nothing else used the old change mode. 'Show password' is the new shared `Widgets/state_checkbox.StateCheckbox` (a check mark or a blank cell). The setup copy now says a forgotten password can be reset at startup.
- **Settings card (UI/Screens/settings_encryption.py).**
  - Shows On, Off or "On, but locked", with password-gated Encrypt keys…, Change password… and Turn off encryption…. The Encrypt dialog carries the comment-loss warning.
  - Each action runs in a non-exclusive thread worker (`exit_on_error=False`) behind a busy flag, and reports inline.
  - The state is re-read from the file off-thread after mount. Change and Turn off verify the password first, so a wrong one reports "That password didn't match. Nothing was changed."
  - The card is imported lazily from the Privacy & Security branch, so the screen pre-import payload ratchet is unaffected. The 'Config encryption' posture row and 'Credential mutation: not available yet' are gone; the header copy and the search index are updated.
  - The logic is ported from Tools_Settings_Window, not imported from it (PR #2868 deletes that file).
- **Docs.** First_Run_Setup.md gains "Starting chatbook when your keys are encrypted", and its Protect row now points at the card. settings.md documents the Encryption card. No 'Verified against' stamps. task-33621.25 now says the module-path row was a user lock-out and was fixed here. The diagnostic inventory is re-pinned after a `--statements` review: the new lines interpolate only fixed action names and exception type names; the removed ones interpolated `{e}`.
