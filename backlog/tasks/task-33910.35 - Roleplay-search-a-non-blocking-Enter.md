## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
On dev today, Enter in the Roleplay search box within the 0.2 s debounce puts the cursor on the previous result's first row, so the four-key find (Ctrl+F, a name, Enter, Enter) can open the wrong card on a local library; on a server source dev's reload blanks the list, so the find's second Enter opens nothing at any server latency. Roleplay frame B2a (TASK-33910.3) fixes both, the server case for servers that answer within 2 s, by having Enter wait for its search's render. The wait runs inside the screen's message handler, and that holds every non-priority key and message on Roleplay while it waits. Locally that is the render (about 30-40 ms); on a server source it is the server's round trip. The hold is new with B2a. B2a's final review bounded it at 2 s (`_SEARCH_SUBMIT_WAIT_SECONDS`): after that Enter does what dev did (it moves into the list, with the cursor on the first row shown if there is one) and the slow search still lands its rows. B2a does not remove the hold, and past 2 s the four-key find can miss (measured with a held read). On a server source B2a's reload also blanks the list first, so no row is shown when the wait ends and the second Enter opens nothing, as on dev. For a local read slower than 2 s the previous results are still shown: a second Enter before the new results land opens the previous results' first row, as on dev; one pressed after they land opens nothing, because the cursor was on a row the results replaced, and dev does the same.

The design to build: Enter records "land on the first match" and returns at once; the list applies it when the search's rows arrive; Enter on the list stays inert until they do.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 No key or message on Roleplay waits on a search render: a key pressed right after Enter in the search box is handled at once, whatever the server's latency
- [x] #2 The four-key find opens the first match on any server latency, including a search slower than 2 s, pinned by a test that holds the read
- [x] #3 Enter on the list while the search's rows are pending opens nothing, and the cursor lands on the first match when they arrive
- [x] #4 The 2 s bound and its fallback to dev's behaviour are gone
- [x] #5 When a pending search is superseded by a concurrent Lore-save refresh, list Enter opens nothing until matching rows publish; the cursor and next Enter then target the first match.
<!-- AC:END -->

Summary: Enter in the Roleplay search box records "land on the first match" and returns at once. The hold exists on dev today (new with B2a) and is removed here, together with _SEARCH_SUBMIT_WAIT_SECONDS, _wait_at_most and the fallback to dev's behaviour. The landing is one more WindowIntent reason ('first') on ListWindowState (owe_first, landing_owed, take_first), built on TASK-33910.34's owner, not beside it.

Behaviour (a server search slower than 2 s misses the four-key find on dev today; fixed here):
- Enter starts a still-pending search at once, owes the cursor on that search's list (same_list) and returns. PersonasScreen._list_window takes the landing after the searched list paints and puts the cursor on row 0 (the other kinds take it when their search render ends). If the list is already current (no search pending), Enter lands at once.
- Enter on the list is inert while the landing is owed: it opens nothing and does NOT call user_moved, so the landing stays owed (AC#3). A cursor key or a row click is a newer move and cancels it (.34's rule). A newer query, sort, tag or source change drops it when that list lands (landing()); a failed read (read_failed), an empty result and leave() drop it too; take_first clears it whether or not rows exist.
- The pane's own Enter handler now only focuses the list and posts the submit; it no longer moves the cursor onto the previous results' first row (that row-0 highlight on stale rows exists on dev today and is gone here).

Found on the way (exists on dev today; fixed here): a debounce timer stopped as it fires can still run its callback, and it cleared _search_debounce_timer while that named the newer keystroke's live timer.
