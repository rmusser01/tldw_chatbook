## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The copy-pasted store template has drifted: seven stores' `transaction()` catches `Exception`, so a `BaseException` skips the rollback and every later transaction on that thread raises 'cannot start a transaction within a transaction'; two readers use the raw connection as a context manager, which commits any caller-owned transaction on exit; and `MediaDatabase(check_integrity_on_startup=True)` always raises because the method it calls does not exist. One store already uses `except BaseException` and documents why.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Six stores' transaction() now roll back on BaseException instead of Exception: AgentRuns_DB, Client_Media_DB_v2, Library_Ingest_Jobs_DB, Prompts_DB, RAG_Indexing_DB, Workspace_DB. Library_Collections_DB and Workflows_DB already did, and are the precedent cited in the comment.

Mechanism, proven on Prompts_DB before the change: raise KeyboardInterrupt inside 'with db.transaction()' -> the except Exception arm does not catch it -> no rollback -> in_transaction stays True. Because transaction() treats an already-open transaction as nested (in_outer=True), the NEXT write borrows it and never commits. A prompt added after that point did not survive close+reopen: prompts after reopen ['A'], expected ['A','C']. That is the same data-loss shape as the Media P0, reached by a different route. After the change: in_transaction False, and ['A','C'] survive.

NOT changed (checked, not overlooked): ChaChaNotes_DB and Subscriptions_DB have no bare 'except Exception' in their transaction() within the scanned window -- they use different structures. Worth a separate look rather than a blind edit.

The other two items in this task's AC were already handled elsewhere in this branch: the two readers using the raw connection as a context manager, and MediaDatabase(check_integrity_on_startup=True) raising because the method does not exist, are still open -- see the follow-up note below.

FOLLOW-UP still open in this task's scope: (a) the two 'with self.get_connection() as conn:' readers in ChaChaNotes_DB (:12752, :12802) that commit a caller-owned transaction on exit; (b) check_integrity_on_startup=True always raising AttributeError. Both are real and neither is fixed here; they need their own change with their own evidence rather than being folded into this commit.
