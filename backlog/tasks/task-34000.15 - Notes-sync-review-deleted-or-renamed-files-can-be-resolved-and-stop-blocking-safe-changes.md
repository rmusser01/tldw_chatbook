## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: a Notes power user (j3) and a stress tester (j6) each ended up with a sync folder they could not repair from the UI. Deleting a file on disk, renaming one, or deleting a synced note in the app produces review rows. Each row lists every resolution the design promises, then disables all of them. The root-level Apply blocker also treats any deletion as blocking the whole plan, so the folder's unrelated safe changes, such as a new file waiting to be imported, are held back too. After one ordinary `rm` or `mv` the folder stops syncing for good, and the screen never says why. A keyboard-only user cannot even see the reason, because it exists only as a hover tooltip.

Observed (verify/nl-v-n-15 at 160x45): the repro is `rm ideas.md` and `mv quotes.md 'quotes renamed.md'` in a synced folder, then Check changes. The review reads "10 safe · 1 need attention · 0 skipped · 1 folder moves". The row "ideas.md · One side was deleted" and the row "quotes renamed.md · Preview explicit filesystem move" both say "Resolution unavailable for this item. No changes can be staged.". The first row's choices "○ Restore missing side / ○ Delete/archive counterpart / ○ Disconnect item" are dimmed, and so are the second row's "○ Apply once / ○ Leave unchanged". "Apply reviewed" is dimmed with no visible reason. The reason appears only on hover: "Deletion review is unavailable in this release." (16-hover-apply). The safe create ("fresh file.md · Create a Library note") never applies. j3 hit the same dead end after deleting a note in the app.

Verified cause (origin/dev 2d34cbf80d):
- Widgets/Library/library_notes_add_from_files_canvas.py:780-799 renders every attention-row choice with `disabled=True`, with no condition.
- Library/library_notes_lasting_sync_state.py:967-1000 `_apply_blocker` returns DELETION_REVIEW for the whole plan whenever a deletion exists, and MANAGED_PLACEMENT whenever a move exists. As a result `can_apply` is false even for the safe set. The runtime makes the same whole-root decision in Notes/notes_sync_runtime.py:2300-2310 `_blocked_plan_status`.
- The only explanation is the tooltip map at library_notes_add_from_files_canvas.py:1159-1182.

Constraint: ADR-059 (lines 146-147) already promises "delete/archive counterpart, restore missing side, or disconnect item" for deletions. ADR-059 and ADR-073 also require deletions, renames and moves to stay explicit, previewed user actions. The fix must keep them reviewed and never apply them automatically.

Suggested direction (the review's refined fix; a direction, not a mandate):
- First, let Apply reviewed apply the safe subset while attention rows stay pending.
- Show the blocker as visible text next to the button, not a hover-only tooltip.
- Enable Disconnect item.
- Then build Restore missing side (recreate the file or note from the surviving side) and Delete/archive counterpart (move the file to trash or soft-delete the note; never unlink).
- Let a detected rename be applied as the previewed move.
- Wherever an action stays unavailable, name the alternative, for example Recently deleted > Restore.

Owning-task note: TASK-32633 owns N-03 (deleting a note in the app leaves the root at '✓ Up to date'). Once it lands, in-app deletes will reach this review more often, so this dead end will become more common. This task owns resolving deletion and move rows, and applying the safe subset.

Review finding(s): N-15. Source: qa/notes-library-ux-review-2026-10-02/report.md
