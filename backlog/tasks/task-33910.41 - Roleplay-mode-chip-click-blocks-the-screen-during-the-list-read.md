## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A click on a Roleplay mode chip runs the new kind's read on the screen's own message pump, so nothing paints until the read ends: neither the blanked list nor B2b's 250 ms "Loading <kind>…" line (measured in B2b's dry run, probe P9-1; the `c`/`p`/`d`/`l` keys do paint it). It exists on dev today; B2b does not fix it. Found during Roleplay frame B2b (TASK-33910.4, plan Docs/superpowers/plans/2026-10-26-roleplay-b2b-toolbar-new-import.md).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fixed in burn-down PR 4 of the B2b follow-ups, with TASK-33910.39 and TASK-33910.43 (stacked on PR #3427).

- **On dev (base `7bf27353ef`):** present, and `Also in:` had it too (the B2b plan's note that `Also in:` painted was wrong; the triage was right). `_handle_mode_chip` and `_handle_also_in` are screen `@on` handlers that awaited `_run_guarded` → `_apply_mode` → the kind's read, so the screen's own message pump processed nothing until the read ended: a callback posted to the screen waited 3 s on the base, Ctrl+F was not handled, and the loading line never painted. The `c/p/d/l` keys run through the App's binding dispatch, so they painted, while holding the App's pump the same way (B2b's probe P9-1 measured `app_q=2`). This PR fixes all three.
- **Fix:** `_apply_mode` gains `await_read` (default True, the old behaviour for every direct caller: the import landing, the buddy conversion, the saved-mode restore, the New chooser, tests). The new `_switch_mode` (the chip, the keys and `Also in:`) runs the guarded switch with `await_read=False`: the kind's read starts at once in the existing `personas-library-search` worker (`_start_debounced_search_render`, the step the debounce timer reaches; Escape's rung 8 starts its clear's read the same way), and for Characters that worker runs the window read in the list-window worker behind the list fence, as the keys always did. No new worker group or fence. Personas already read in its own worker. A second switch during a held read runs at once: a Lore switch reuses the exclusive search worker, which stops the characters window worker; a Personas switch leaves it, and the late window is dropped at the fence.
- **Tests (`Tests/UI/test_roleplay_item_list_app.py`):**
  - `test_a_chip_or_also_in_switch_leaves_the_screen_pump_free_during_the_read` (chip into Characters with the characters read held, chip into Lore with the lore read held, `Also in:` into Characters): while held, a callback posted to the screen is answered within 3 s, Ctrl+F focuses the search box, and "Loading <kind>…" paints from the 250 ms timer; after release the rows land. RED on the base at the callback probe.
  - `test_a_second_switch_during_a_held_read_runs_at_once_and_the_older_read_lands_nowhere` (Lore and Personas as the second switch): the second click returns within 3 s, the new kind's rows show while the characters read is still held, and after release the rows, title and the screen's character rows are unchanged. RED on the base at the second click.
  - Mutations: M41-A (the switch awaits the read) turns all five cases red at the pump probe; M39-B (no blanking) turns the loading-line legs red; M41-F (Ctrl+F blurs) the focus leg; M41-C (no window fence) the Personas late-window case; M41-D (the search worker not exclusive) the Lore worker-stopped leg.
- **User Guide:** `Docs/User_Guide/roleplay-chat-dictionaries.md`, the loading paragraph.
- **ADR-011:** before/after capture with a `chips` phase added; see the PR body.
- **B6 (TASK-33910.11)** replaces the chips with rail rows: a rail-row click must go through `_switch_mode` too.
