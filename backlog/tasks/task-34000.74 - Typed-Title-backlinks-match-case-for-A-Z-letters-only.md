## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-34000.11 records a backlink for a typed `[[Title]]` when exactly one live note carries that title, matched
"case-insensitively" through SQLite's `COLLATE NOCASE`. That collation folds only the ASCII letters A–Z: a note titled
"Élan" is NOT found by a typed `[[élan]]`, while "Weekly" IS found by `[[WEEKLY]]`. The User Guide now says so
("case is ignored for A–Z letters"), and `Tests/Notes/test_note_links_typed_titles.py::
test_the_title_match_folds_case_for_ascii_letters_only` pins the current behaviour.

Fix round 1 of TASK-34000.11 ruled: document, do not widen — the DB connection layer (a custom collation or a
`casefold()`ed shadow column) is out of that task's scope. This task owns the Unicode case-fold match.

Options the implementer should weigh: a Python `casefold()` collation registered on every ChaChaNotes connection (then
the `IN (...)` statement stops being a plain `SCAN notes` on the title column; measure it with `sqlite_stat1` absent),
or resolving candidates in Python from a narrowed set (fetch `title, id` for the ASCII-folded matches AND the raw
titles, then group by `casefold()`), or a generated `title_folded` column with its own migration (schema bump; follow
`DB/migrations/README.md` and the `EXPECTED_CHACHANOTES_INDEXES` rule).
