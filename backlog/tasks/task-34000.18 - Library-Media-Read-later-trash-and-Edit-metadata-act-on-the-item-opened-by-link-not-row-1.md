## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: a first-time Library user (j2) imported a folder, chose "Open in Library" on the PDF and pressed Read later. The reader showed the PDF, but the list cursor ('▸') stayed on team-handbook in row 1. Read later saved team-handbook instead, 3 times out of 3, and the reader then swapped to team-handbook. "More ▸ Move to trash" asks an untitled "Delete this media? You can undo right away, or restore later from Trash.", so the user cannot tell which item is about to go. The verifier found that Edit metadata › Save targets the wrong row as well. Read later, Move to trash, Use in Console and Edit metadata all silently act on a document the user did not choose. Anyone who opens items by link is exposed: a first-timer after an import, or a researcher jumping in from Search/RAG.

Observed (verify/nl-v-l-03):
- r2-03-trash-confirm (160x45): the reader is titled 'paper-retrieval-practice', and the list shows '▸ team-handbook' plus 'paper-retrieval-practice … loaded'. The trash confirmation names no item.
- r2-log-edit-save-targets-media5: with the PDF open in the reader, the log reads "Failed to save Library media edit for 'local:media:5'" (team-handbook), caused by "UNIQUE constraint failed: Media.url".
- Control: clicking the PDF row first makes Read later save the right id.
- The Search 'Open' half of the original report did not re-reproduce in verify, but that route goes through the same branch.

Verified cause (origin/dev 2d34cbf80d):
- `_navigate_to_media` (UI/Library_Modules/library_media_controller.py:3166-3173) passes a bare id.
- The media branch of `_open_library_item_by_id` sets `self._media_state.selected_media_id = record_id` (UI/Screens/library_screen.py:34798) from that bare id, before it computes the canonical 'local:media:N' identity (:34801-34810).
- The reader session gets the canonical id but the selection keeps the raw one. When the browse refresh lands, the list highlight settles on row 0, and actions that read `_selected_media_id` act on that row. One example is `_start_library_media_read_later_toggle` (library_media_controller.py:4534-4552).

Suggested direction (the review's refined fix; a direction, not a mandate):
- Canonicalise record_id to 'local:media:N' in the media branch of `_open_library_item_by_id`, and move the list highlight onto that item.
- Make reader-scoped actions (Read later, Move to trash, Use in Console, Edit metadata) act on the reader session's loaded id rather than the list cursor.
- Name the item in the trash confirmation, for example "Move 'team-handbook' to Trash?".

Review finding(s): L-03. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** Every by-link route now lands the Media list highlight on the opened item, and every Reader-scoped
action acts on the item the Reader shows. The trash confirm names that item.

**Cause, as found on 32caa91c1a (two layers).** (1) The media branch of `_open_library_item_by_id` wrote the BARE
id the by-link callers pass (`_navigate_to_media`, the landing hub's recent Open, the deep-link entry) into
`selected_media_id`; page rows are canonical `local:media:N`, so the browse builder never found it and fell back to
row 0. (2) Even with a canonical id, the browse controller syncs once on `request` -- before any page exists -- and
that sync's tail (`_sync_library_media_browse_state`, `canvas_sync._sync_library_canvas`, `compose_content`) wrote
the builder's "" over the selection, so the landing page still fell back to row 0. A probe with a `__setattr__`
hook on `LibraryMediaState` showed the exact writer sequence (door -> "" at request -> row 0 at landing).

**Fix.**
- `_open_library_item_by_id` canonicalises at the door (`reader_identity[0]` when it resolves).
- `LibraryScreen._adopt_library_media_highlight(media_state)` is the one place the list's resolved highlight is
  written into the selection; it declines to clear a selection while the Reader holds (or is loading) an item the
  builder found no row for. All three former direct writes route through it.
- `library_media_reader_state.reader_action_target(session, selected_id, view)` + the controller's
  `_library_media_reader_target_id()` (one-line screen delegator) are read by Read later, the delete confirm, Edit
  Save, the analysis save and highlight add/delete. `_selected_media_handoff_payload` already read the loaded
  detail; it is pinned, not changed (AC#2's "Use in Console" half, see the AC note).
- Owner Q2 (b): `build_library_media_browse_state` highlights no row when `loaded_id` is not on the page; the
  list-view default (row 0 with nothing loaded) is unchanged.
- `LibraryMediaViewer(delete_target_title=...)` and the pure `library_media_delete_confirm_copy(title)`:
  `Move "<title>" to Trash? You can undo right away, or restore later from Trash.` (empty title -> `Move this
  item to Trash? ...`), threaded through the Reader builder and the unchanged-compare so an Edit > Save re-names it.
  Deviation from the brief: the title is the loaded detail's (`viewer_state.title`, what the Reader header paints),
  not `reader_session.loaded_title` -- an open-by-link seeds that slot with the bare record id and an edit never
  updates it, so the brief's order would have printed `Move "3" to Trash?` on exactly the by-link path.
- AC#4 is read as "any non-exiting action": after trash the viewer exits to the list by design; Read later and
  Edit Save refresh the loaded id, so the Reader stays (live: capture 04).

**Fix round 2 (re-review, 2026-10-20).** Round 1's scope-based hold (viewer AND unfiltered scope) failed under any
sticky type or query filter: an open-by-link of a filtered-out or off-page item highlighted row 0 and the Reader keys
went dead (the key gate needs ``loaded_id == selected_media_id``). Ruling: the hold is ORDER-based. New
``LibraryMediaState.highlight_held_by_reader`` (beside ``editing``; field count 83 -> 84) is set when an item is
opened or selected for the Reader (the open-by-link door, ``_select_library_media_reader_row``, the restored
selection; the receipt's Open goes through the door) and released only at the user's scope-change seams -- all of
them (type choice, typed query, filter Clear, sort, page) run ``_clear_library_media_selection_for_scope_change``,
which is the one release point -- plus the Reader reset and the viewer exit. ``_library_media_reader_holds_highlight``
reads the flag (and the viewer view); the scope is never read and an open never touches the user's filter. A filter
applied AFTER the open = the list moved on (TASK-15457, pin unchanged, green); an open AFTER the filter = the Reader
moved on (no cue, selection = Reader's item, keys live). Pins: the reviewer's cases A, B and E as
``Tests/UI/test_library_media_actions_target_opened_item_extended.py`` (appended to the lane census by the controller after fix round 2; 3 boots ~11 s), each
