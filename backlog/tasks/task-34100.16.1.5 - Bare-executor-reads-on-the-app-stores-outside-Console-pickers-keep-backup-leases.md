## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-34100.16.1's review round v5r2 (finding R2-1). An `asyncio.to_thread` (or `run_in_executor`) call that reads or writes the app's live ChaChaNotes or Media store leaves that pool thread's cached connection open. A backup's local pause cannot revoke such a foreign-thread lease (`participants.retire_current_thread_caches`), so after the user reaches one of these surfaces, an idle Create backup ends in `admission_timeout` until the app quits. `participants.run_finite_local_worker` is the fix: it retires only the caches the call itself opened.

TASK-34100.16.1 fixed the Library Notes paths, Console's retrieval-scope picker, the RAG FTS legs it scopes (`RAG_Search/pipeline_functions_simple.py`), and Console's dictionary and world-book pickers, each with a RED real-SQLite lease test and a structural guard. A heuristic census of the rest of `tldw_chatbook/` found 99 more executor offloads inside functions that touch `chachanotes_db`, `media_db`, `CharactersRAGDB` or `MediaDatabase`. Some already retire their own handle (for example `chat_conversation_scope_service`'s `list_and_close`, `console_conversation_hydration`'s `read`, the `app_lifecycle` quit paths), so each needs triage. By file:

- `Dreams/cycle_service.py` (6)
- `app_lifecycle.py` (6, mostly quit paths)

- `UI/Screens/watchlists_collections_screen.py`, `UI/Screens/chunking_lab_screen.py`, `UI/Console_Modules/workspace.py`, `UI/Console_Modules/message.py`, `RAG_Search/recovery.py` (3 each)

The census script and its output are in `.worktrees/setup-wizard-ux-qa/evidence/g161v5-r3/` (`census.py`, `census.tsv` before the fix, `census-after.tsv` after); rerun it rather than trusting these counts. A systemic alternative worth weighing first: give the app loop a default executor whose workers run every callable through `run_finite_local_worker`. That fixes every site at once, but it re-opens a connection per offloaded read, so it needs a latency measurement against the UI performance ratchets.

Measured in TASK-34100.16.1's pre-merge review (2026-11-13; `evidence/g161v5-pm/bench_reads.py`, real DBs under an isolated HOME, startup admission held, medians in ms). A wrapped read costs one connection open, about 40-50 ms, where a bare read on a warm cached connection took 0.3-4 ms: ChaChaNotes `list_notes` 0.5 → 46.9, Media `get_keyword_usage_stats` 1.1 → 39.5, the `[[` picker 0.6 → 48.0, backlinks 0.3 → 48.4. Two costs are already removed there. Retirement no longer waits on another connection's writer (it ran `wal_checkpoint(TRUNCATE)`: 3,019-3,077 ms behind a 3 s write, now about 50 ms). And each RAG leg and scope Save now opens once (media leg 125.9 → 42.3, conversations leg 93.0 → 52.4, scope Save 90.5 → 52.7). So a run-every-callable default executor would put about 45 ms on every offloaded read in the app. Weigh instead a small app-owned DB executor whose threads a backup's local pause can ask to retire their own caches (OPT-96 in `Docs/Development/console-optimization-review-list.md`). That keeps warm connections and still drains.
