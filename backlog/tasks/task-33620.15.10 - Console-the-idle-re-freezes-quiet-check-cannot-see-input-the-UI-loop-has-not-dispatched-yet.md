## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The idle heap re-freeze (TASK-33620.15.3, ADR-198 amendment) runs only after 2 s (5 s for a compaction) without user input. Input is stamped when App.on_event dispatches it, so a key the driver thread has already posted but the loop has not yet handled is invisible to the check. A refreezer timer that fires in that gap can start a re-freeze or a compaction (up to about 0.6 s, uninterruptible) right after the user pressed Enter. Never observed: 0 of 70 maintenances live in TASK-33620.15.3's round 9 fell inside a send window, with the window measured from Key construction in the driver thread. Closing the gap would make the guarantee hold by construction rather than by timing.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The idle heap re-freeze now counts a key the app has queued but not yet handled as recent input.

**Approach.** `UserInputTap` (`Utils/text_selection_crash_guard.py`, part of `TextualAppGuards`) also overrides `App.post_message`. An input event (`InputEvent` or `Paste`) is stamped when it is posted to the app, and again when `App.on_event` dispatches it. The driver's coroutine posts real input through `post_message` on the loop, and so does Pilot. A refreezer timer that fires while the key waits in the app's queue sees the fresh stamp and re-arms instead of running. One gap is left: the driver thread hands each key to the loop as a coroutine, and until that coroutine runs (one loop iteration) the key has not been posted. That is outside AC#1. The check is one `isinstance` per message posted to the app.

**Tests (red then green).** `Tests/Performance/test_gc_idle_refreeze.py::test_input_posted_but_not_yet_dispatched_holds_off_a_maintenance` posts a key to a running app, then fires the refreezer's timer without yielding to the loop.
