## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Provider keys live in config.toml or nowhere. The only protection offered is a master password typed at every launch, which is the most fragile area of the review (SF6), and nothing tells the user at the key field that the key will be readable plain text. The OS keyring already holds tldw server tokens and MCP bindings, but never a provider key.

The owner ruled on 2026-10-03 that keychain storage must be optional, not the default (spec Q3). So this slice keeps today's storage as the default and adds the keychain as a choice (decision D9 as amended). Under every provider key field, one line says where the key goes and whether it is plain text, and names encryption without asking for it: "Saved in config.toml (plain text; encrypt any time)  [ Use macOS Keychain… ]". The keychain button appears only where a secure keychain is detected, and nothing touches the keychain until the user chooses it. Once chosen, the keychain is honoured or the step stays put; a failure never falls back to config.toml silently. Keys the user puts in the keychain resolve after first paint through one provenance overlay that every reader uses, and no writer can copy them back into config.toml. An environment key is never stored. Encryption stays one profile-wide choice under TASK-34100.4; TASK-34100.6 AC#21 (amended) supplies the environment-key control. Server-token storage is unchanged. ADR-012 and ADR-029's 2026-10-03 amendments govern this.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D9, §3.2, §4.6, §4.7 item 7, §8.1 (Keychain, census tests), §8.4, §10 F12a; ADR-012 and 029-local-private-data-boundary amendments of 2026-10-03.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 With no choice made, a typed provider key is saved exactly as today: in config.toml, encrypted by the writer when password encryption is on. No keychain item is read or written, no keychain prompt appears, and keyring stays out of the boot-import and UI-ready censuses
- [ ] #2 Under each provider key field (Connect, Settings ▸ Providers & Models, and Spoken replies' inline key where the host allows key entry) one line says 'Saved in config.toml (plain text; encrypt any time)', or 'Saved in config.toml, encrypted with your password' when encryption is on. Encryption is named there but not chosen there
- [ ] #3 A [ Use <platform keychain>… ] button appears on that line only when a secure backend from the allowlist is detected (macOS, Windows, Secret Service, libsecret, KWallet), by a check that reads and writes no item. Where none is detected, the line gives the reason instead. Neither place is labelled 'recommended'
- [ ] #4 Pressing the button chooses the keychain and shows both places with their consequences, so the way back is one key away. A write/read/delete canary then runs in a worker with a timeout
- [ ] #5 Once the keychain is chosen, the key goes to the keychain or nowhere. A failed canary or a failed save keeps the step in place with the cause, [ Try again ] and [ Keep in config.toml instead ], and the key is never written to config.toml unless the user picks that
- [ ] #6 A keychain save writes the item, reads it back and compares, then makes one config write with credential_source = "keychain" and no api_key (and [credentials] scope_id the first time). If the config write fails, the item is deleted
- [ ] #7 When an environment variable exists, 'Use <VAR> from your environment (not stored)' is the default. Its value never reaches the keychain, config.toml, a draft or a log, whatever the user selects, and the storage line appears only for a different key the user types
- [ ] #8 Keychain-held keys resolve after first paint into one provenance overlay used by every reader: the spend path, get_api_key, resolve_provider_credential and the readiness checks. 'keychain' joins both persisted credential-source allowlists. Readiness shows resolving, resolved, absent ('Key not found in this computer's keychain' with Fix key) or waiting for you ('answer its prompt, then Check again'). A timeout is never cached, Check again works without a restart, and a send waits a bounded time and never sends another key
- [ ] #9 An entry older than the store's TTL is refreshed before a send, and a 401 drops it, so a key changed in another running instance is used at its next send
- [ ] #10 No writer can persist a keychain-held key to config.toml: a writer census over every whole-settings writer and a load → save property test both pass
- [ ] #11 Keychain items live under tldw_chatbook.provider_credentials.<scope_id>, where scope_id is a random id persisted once. Two TLDW_CONFIG_PATH profiles never share a key, and a profile that never chose the keychain has no scope id
- [ ] #12 A chainer backend with several secure children resolves to its highest-priority secure child, or the keychain is not offered, with the reason
- [ ] #13 Ready and the dashboard name where each key lives: 'key in config.toml (plain text)', 'key in config.toml (encrypted)', 'key in <platform keychain>' or 'key from <VAR> (not stored)'
- [ ] #14 Server-token storage is unchanged
- [ ] #15 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: macOS with no choice made (key in config.toml, no prompt); macOS Keychain chosen, with the access prompt answered Always Allow and Deny; macOS over SSH with a locked keychain; Windows Credential Manager; GNOME Keyring unlocked and locked; headless Linux with no keychain offered; two running instances with a rotated key; and relaunch through both tldw-cli and python -m. Evidence is recorded in Implementation Notes
- [ ] #16 New behaviour is covered by tests that fail on the pre-change code (RED verified), and no module-size or ADR-097 ratchet is raised
- [ ] #17 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
