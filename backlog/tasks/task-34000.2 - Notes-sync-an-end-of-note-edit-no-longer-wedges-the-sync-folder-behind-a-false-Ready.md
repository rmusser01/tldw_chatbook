## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: typing at the end of a note is the most ordinary edit there is. For a power user keeping a vault folder synced, that edit silently stops lasting sync in both directions for the whole folder. Every surface outside Manage sync folders keeps saying all is well, so the user goes on writing on both sides and the copies diverge. The only actions on offer loop back on each other, and the loop survives a restart. Disconnect reads "unavailable — not in this release", so there is no way out.

What was observed (160x45; the verifier reproduced it 2/2, with a control run):
- Trigger: a vault whose .md files end with a newline. Keep a folder synced, open a synced note, press Ctrl+End, type a word without Enter, wait ~5 s. A `notes_sync_operations` row is left at `update_file | needs_attention | postcondition_failed`. Control: the same edit ending in a newline completes.
- Capture 14 shows the editor saying "Saved 21:40 · Next: Keep editing; changes save automatically." and "In a synced folder · /…quotes.md · file written 2026-10-02 19:50". The list scope reads "Library notes · Ready" and the tree row reads "▾ VSync  ⇄ Sync managed".
- Capture 10 shows Manage sync folders with "Recovery failed — RuntimeError. Next: Check changes." and "⚠ Needs attention · Recovery failed — RuntimeError · Next: Check changes". The folder is titled "Sync folder (name unavailable before cutover)" and offers "○ Disconnect unavailable — not in this release".
- Review says "A recovery is still open for that folder. Resolve it, then Check again." with "0 safe · 0 need attention". Disk appends made later never arrive (j3).
- j6 reached the same state another way: an app edit plus a different disk edit to one note ('Budget 2026'). The editor showed "Saved", the DB ended "| riley-app | 1 | app2" and the file ended "| riley-disk | 2 |".

Verified cause (origin/dev 2d34cbf80d):
- `serialize()` appends a final newline when the captured profile has one (Notes/notes_sync_filesystem.py:259-260). The write postcondition in `_classify` compares the decoded file text with the raw note content, `file.text == request.note.content` (Notes/notes_sync_executor.py:5384; the same text comparison is at :3522 and :5167). A note without a trailing newline therefore never matches its own correctly written file, and `_require_desired` raises `RuntimeError("postcondition_failed")` (:5398-5400).
- The runtime then refuses every check while the root has an incomplete operation, raising `sync_recovery_unresolved` (Notes/notes_sync_runtime.py:2468-2484).
- `postcondition_failed` is missing from `_CHECK_FAILURE_ROW` (Library/library_notes_lasting_sync_state.py:1122), so `check_failure_row` falls back to the exception class name (:1201-1204). That is where "RuntimeError" comes from.

Suggested direction (a direction, not a mandate):
- In `_classify` (and at :3522 and :5167), compare the file bytes with `serialize(note.content, profile)` so like is compared with like. Recovery then self-heals roots that are already stuck.
- Add `postcondition_failed` to `_CHECK_FAILURE_ROW` with plain copy and a next action that actually moves forward.
- While a root has an incomplete operation, the tree folder row, the list scope line and the editor location line read 'Needs attention', not 'Ready' / 'Saved'.
- The consolidated entry also proposes treating a real both-sides change as an ordinary conflict row (Keep file / Keep note / Keep both), and offering Disconnect or 'Pause and keep both' as an escape hatch.

Ownership: no existing task owns this. Neighbouring findings are owned elsewhere:
- N-03 ("✓ Up to date" after a delete): TASK-32633.
- N-18 (folder titled "name unavailable before cutover"): TASK-32451.
- N-35 (the general exception-name fallback): partly TASK-32578.
- N-15 (unresolvable review rows): a separate finding.

This task covers the postcondition comparison, healing roots already stuck by it, plain copy and a working next action for this failure, and a truthful attention state across the tree, list and editor.

Review finding(s): N-02. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: the write postcondition compared the file's decoded text with the RAW note, so a note typed past its last newline never matched its own correctly written file under a final-newline profile; the entry stayed `update_file | needs_attention | postcondition_failed`, every Check refused the root (`sync_recovery_unresolved`), Recovery raised `recovery_authority_changed` (shown as "RuntimeError"), and the tree, list and editor kept saying Sync managed / Ready / Saved. Fixed at the cause, with a heal for roots already stuck, plain copy, and a truthful attention state on the three surfaces.

Approach (first implementer's draft reviewed, kept where right, adjusted where not):
- Like for like (`Notes/notes_sync_filesystem.py`, `Notes/notes_sync_executor.py`): `represented_text`/`represented_digest` name what a write leaves on disk; `_file_holds_note` compares the file's BYTES with `serialize(note, profile)` in `_classify`/`_classify_restore` and the create path. Every note-vs-baseline comparison accepts the note's represented digest as well as the raw one (`_note_matches_baseline`; the planner input in `notes_sync_runtime.observe_root`), because a binding keeps ONE baseline digest for both sides and older/migrated baselines kept the raw form. New baselines are committed in represented form (`_note_baseline_digest`). Nothing rewrites either side.
- Heal (`notes_device_state_store.settle_operation_attention`, `NotesSyncExecutor.settle_attention`, `NotesSyncRuntimeOwner.resolve_cleanup` + `_run_settled_pass`): Recovery on an `update_file`/`update_note` fenced at attention settles the entry at the most precise PROVEN baseline (post-write when the journal's desired digest proves the write is what is on disk, otherwise the reviewed baseline, unchanged) and runs one automatic pass. A one-sided remainder syncs; a two-sided change becomes the ordinary "Both file and note changed" review. The planner stays the only decider; no winner is picked.
- Plain copy (`Library/library_notes_lasting_sync_state.py`): `postcondition_failed`, `stale_observation`, `operation_needs_attention`, `binding_authority_changed` get refusal copy and a forward next action; the row's next action for a settleable attention entry is `resolve_cleanup` (Recovery first), not Review.
- Truthful attention (new `UI/Library_Modules/library_notes_sync_attention.py`, runtime `attention_folder_ids` / `note_sync_needs_attention`): the tree folder row says "⚠ Needs attention" (`library_notes_tree_state.py`), the list's idle status says "⚠ A sync folder needs attention · Next: Open Manage sync folders." and the editor says "Saved HH:MM in Notes · ⚠ Sync needs attention" with the location row "In a synced folder · ⚠ Sync needs attention · …" (`Widgets/Library/library_notes_canvas.py`). Unhealthy copy takes precedence; healthy wording is untouched (TASK-32633's slice can sit beside it). The post-save location re-read waits (bounded, 5 s, shielded) for the pass the save hinted, so the save that holds a folder is the save whose row says so; the runtime does not push status to the screen, so this and the lasting-sync snapshot publication are what keep the three surfaces in step.
- Second implementer's changes to the draft: the attention worker is scheduled as a `partial` (a superseded exclusive worker left a never-awaited coroutine, visible as a RuntimeWarning in the Pilot run); four fast-path unit tests added (location line, list status, editor status, tree row, refusal copy); the live run was redone end to end on the final code and the draft's captures replaced (the draft's "race B" set and a 120x36 "tree row" capture that did not show the row were dropped); User Guide copy written.

**Final review fixes (whole-branch review, 2026-10-04).** *I3 and deferred minor T2-a.* `library_notes_sync_attention._ask` turned any failure into its default, and the default for "which folders are held" is the empty set. Both runtime reads are producer calls, so a visit to Notes or a save during a backup wrote the empty set, repainted, and left a held folder reading healthy until something else published. A failed read now returns a distinct "could not say": the refresh keeps the last known folder set and the open note's line, and repaints nothing. In the same function both reads now finish before `tree_attention_folder_ids` is written, with no await between the write and the paint, so an exclusive successor that cancels the worker can no longer find the answer "unchanged" and skip the paint.
