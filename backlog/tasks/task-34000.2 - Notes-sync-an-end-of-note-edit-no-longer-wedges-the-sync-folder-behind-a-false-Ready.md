## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: typing at the end of a note is the most ordinary edit there is. For a power user keeping a vault folder synced, that edit silently stops lasting sync in both directions for the whole folder. Every surface outside Manage sync folders keeps saying all is well, so the user goes on writing on both sides and the copies diverge. The only actions on offer loop back on each other, and the loop survives a restart. Disconnect reads "unavailable — not in this release", so there is no way out.

What was observed (160x45; the verifier reproduced it 2/2, with a control run):
- Trigger: a vault whose .md files end with a newline. Keep a folder synced, open a synced note, press Ctrl+End, type a word without Enter, wait ~5 s. A `notes_sync_operations` row is left at `update_file | needs_attention | postcondition_failed`. Control: the same edit ending in a newline completes.
- Capture 14 shows the editor saying "Saved 21:40 · Next: Keep editing; changes save automatically." and "In a synced folder · /…quotes.md · file written 2026-10-02 19:50". The list scope reads "Library notes · Ready" and the tree row reads "▾ VSync  ⇄ Sync managed".
- Capture 10 shows Manage sync folders with "Recovery failed — RuntimeError. Next: Check changes." and "⚠ Needs attention · Recovery failed — RuntimeError · Next: Check changes". The folder is titled "Sync folder (name unavailable before cutover)" and offers "○ Disconnect unavailable — not in this release".
- Review says "A recovery is still open for that folder. Resolve it, then Check again." with "0 safe · 0 need attention". Disk appends made later never arrive (j3).
- j6 reached the same state another way: an app edit plus a different disk edit to one note ('Budget 2026'). The editor showed "Saved", the DB ended "| riley-app | 1 | app2" and the file ended "| riley-disk | 2 |".

Verified cause (origin/dev 2d34cbf80d):
- `serialize()` appends a final newline when the captured profile has one (Notes/notes_sync_filesystem.py:259-260). The write postcondition in `_classify` compares the decoded file text with the raw note content, `file.text == request.note.content` (Notes/notes_sync_executor.py:5384; the same text comparison is at :3522 and :5167). A note without a trailing newline therefore never matches its own correctly written file, and `_require_desired` raises `RuntimeError("postcondition_failed")` (:5398-5400).
- The runtime then refuses every check while the root has an incomplete operation, raising `sync_recovery_unresolved` (Notes/notes_sync_runtime.py:2468-2484).
- `postcondition_failed` is missing from `_CHECK_FAILURE_ROW` (Library/library_notes_lasting_sync_state.py:1122), so `check_failure_row` falls back to the exception class name (:1201-1204). That is where "RuntimeError" comes from.

Suggested direction (a direction, not a mandate):
- In `_classify` (and at :3522 and :5167), compare the file bytes with `serialize(note.content, profile)` so like is compared with like. Recovery then self-heals roots that are already stuck.
- Add `postcondition_failed` to `_CHECK_FAILURE_ROW` with plain copy and a next action that actually moves forward.
- While a root has an incomplete operation, the tree folder row, the list scope line and the editor location line read 'Needs attention', not 'Ready' / 'Saved'.
- The consolidated entry also proposes treating a real both-sides change as an ordinary conflict row (Keep file / Keep note / Keep both), and offering Disconnect or 'Pause and keep both' as an escape hatch.
