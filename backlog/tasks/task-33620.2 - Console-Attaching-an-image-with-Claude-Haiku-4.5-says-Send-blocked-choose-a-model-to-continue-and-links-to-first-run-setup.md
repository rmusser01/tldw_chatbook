## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** With Anthropic claude-haiku-4-5 selected, staging an image makes the composer strip read 'leaf.png - 116 B  Send blocked - choose a model to continue >', while the status bar says 'Model: claude-haiku-4-5'. Clicking the '>' link opens the full-screen first-run wizard ('Set up tldw chatbook', Step 1 of 6). The user can back out with Esc → Tab → Skip setup, and the draft survives, but the link sends an already set-up user to the wrong place.

Haiku 4.5 does accept images: a live probe returned the correct colour for a 32x32 PNG. The vision table (`model_capabilities.py` DEFAULT_MODEL_PATTERNS and the shipped config template) covers claude-3*, *opus-4*, *sonnet-4* and claude-sonnet-5. It misses claude-haiku-4-5, claude-opus-5 and claude-fable-5, all of which are in the shipped Anthropic model list.

The accurate vision copy ('claude-haiku-4-5 can't accept images. Remove the attachment, switch to a vision model, or ...') travels in the `setup_blocked_reason` slot. `build_console_disabled_reason` matches the substring 'model' and rewrites it to the generic line. The setup-blocked class then turns the strip into an `app.run_setup_wizard` link. The accurate text survives only in the Send tooltip and in a System row shown after Enter.

**Severity / prior art.** P1, NEW (verified live and by the skeptic as PARTIAL, confirmed in code). Related Done tasks: TASK-21145, TASK-2154.12 (its lesson: test the classifier with the verbatim reason string), TASK-2154.6, TASK-26023, TASK-335, TASK-869. This is one case of the Theme 0 'untyped blocker slot'. The umbrella task owns the typed-blocker model; this task fixes the capability data and the vision block's own presentation.

**Suggested direction.** Fix the capability data, preferably with a family rule: tier-first-named Claude families with major version 4 or higher accept images. Make it reach users whose config.toml carries the old patterns block, which replaces the defaults wholesale. Give attachment blocks their own slot, with 'Remove image' and 'Switch model' actions next to the chip. Keep the setup-wizard link for genuine readiness blockers only.

Evidence: qa/console-ux-review-2026-09-29/findings.md → G4-09 (source J4-03). Code refs: tldw_chatbook/model_capabilities.py:44-48, tldw_chatbook/Chat/attachment_core.py:413-442, tldw_chatbook/Chat/console_display_state.py:293-296.

Review finding ids: G4-09 — see qa/console-ux-review-2026-09-29/findings.md.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Two causes, two fixes.

**Capability data (closes TASK-37031 too).** `ModelCapabilities.get_model_capabilities` gained an Anthropic family rule (`_anthropic_family_reads_images`): an Anthropic-routed `claude-<tier>-<major>` id with major >= 4 reads images. It sits beneath the user's own direct and pattern rows (an explicit `vision = false` still wins) and above the models.dev gap-fill and the unknown-model default, so a config.toml carrying the old `[model_capabilities]` block (whose Anthropic list replaces the shipped one wholesale) no longer hides claude-haiku-4-5, claude-opus-5 or claude-fable-5. Scoped to provider `anthropic`: a local server's `claude-...` alias does not qualify; OpenRouter/Bedrock-style ids are out of scope. Measured first: `GET /v1/models/<id>` reports `capabilities.image_input.supported = true` for haiku-4-5, opus-5, fable-5 and sonnet-5; the dated claude-3/claude-4 ids are retired (not_found); claude-2.x never took images.

**Presentation.** The vision refusal rode `setup_blocked_reason`; `build_console_disabled_reason` matched "model" and the setup-blocked class made the strip an `app.run_setup_wizard` link. Now:
- `ConsoleAttachmentBlock(notice, reason)` (Chat/console_display_state.py) is its own `sync_action_state` / `build_console_disabled_reason` slot: the strip reads "Send blocked — <model> can't accept images", ranks below a setup blocker and above a queue state, and never sets `console-composer-setup-blocked`. The Send tooltip and a refused Enter keep the verbatim refusal.
- A row above the status line (`composer_run_controls.attachment_block_strip` / `sync_attachment_block`) names the model and the cause, with **Remove image** (shares `handle_console_clear_attachment` via its selector) and **Switch model** (`Button(action="screen.open_console_model_popover")`, the Alt+M picker; draft and image kept). The row joins the composer's `CONSOLE_TAB_REGIONS` entry and F6 map (Shift+Tab from the composer reaches it), a keyboard Remove hands focus back to the draft, and its copy wears the strip's warning-bold style (6.96:1 live; `$ds-status-blocked` measured 2.51:1).
- No new module at UI-ready (census 1032 = dev's 1032, dev already over its 1031 limit); boot CSS budget passes.

That round found a defect: after a mouse click on Switch model and a pick, typed keys went nowhere. The picker's dismissal restore (`Widgets/modal_dismissal.py`) found its opener still displayed and called `opener.focus()`, which Textual defers. The sync then hid the row and handed focus to the draft, and the deferred focus landed on the hidden button (2 of 3 instrumented harness runs). Fix: the row is disabled whenever it is hidden (and at compose), so the deferred focus is refused. The regression test replays the logged order through the real restore and failed on the pre-fix commit with focus on the hidden Remove image button. Re-verified live on the fixed build: with a neutrally named file (sample3.png, red square on white) staged on claude-2.1, a mouse Switch model followed by a haiku-4-5 pick put typed text into the draft. Enter then sent it, and the reply was "A red square on a white background." (50-52).
