## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.18. Since that task, each warm-up step that loads modules freezes the heap at once (freeze_long_lived_heap('first_send_step'), 53 step freezes and one closing freeze per launch). The warm-up parks on the app's navigation lock before each step, but not between a step's import and its freeze, so a navigation that started during the import can have its in-flight UI-thread objects (and any cyclic garbage not yet collected) moved into the permanent generation as boot objects. ADR-198 counts what a boot point froze into the refreezer's baseline, never as growth, so such objects are neither collected nor counted toward a compaction. Before that task the warm-up froze once, at its end, so the window for this was one freeze instead of 54. Nothing has measured how much a navigation that overlaps the warm-up leaves frozen this way.
<!-- SECTION:DESCRIPTION:END -->
