## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while pinning TASK-33621.46 (2026-11-21, origin/dev dc371f0842). In a real-controller harness (real store, SQLite, gateway, trace boundary factory, winning voice promotion and trace import; only the provider adapter recorded), a Capture-On typed send that follows a promoted Capture-On speculative voice turn is refused before the provider is contacted: "Trace capture could not start", blocker TRACE_CALL, `phase=trace_reservation error_category=validation exception_type=ValueError`. It happens with no image in the chat (a plain hello, then a voice turn, then a typed send).

Cause, from the traceback: `ConsoleTraceBoundaryFactory.__call__` builds a `CompletedToolTurnWitness` whose `__post_init__` validates `origin_call_id` and `terminal_call_id` as `SemanticRevisionRef` (canonical UUIDv4), but the voice turn's call ids come from `derive_post_dispatch_trace_ids` (UUIDv5 from the promotion id): "revision_id must be a canonical UUIDv4 string". Not yet reproduced live (needs a qualified speculative-voice setup with a microphone).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fixed on fix/task-33621.21-dictation-still-preparing (with .21, .113, .46). A Capture-On typed send after a promoted voice turn now reaches the provider and records its trace.

Cause: `console_trace_runtime` builds a `CompletedToolTurnWitness` from the latest call in the root segment, which after a voice turn is the voice call. Its id comes from `derive_post_dispatch_trace_ids` (UUIDv5 from the promotion id), and `__post_init__` checked both call ids through `SemanticRevisionRef`, which accepts only UUIDv4.

Why v4 is not needed: every consumer only looks the ids up (`repository.get_call` in console_trace_service and console_trace_continuation, and an equality check in the service). `TraceCallRecord` does not validate call ids at all, and the module already has `_validate_stable_opaque_id` for "random ledger IDs and repository-owned deterministic IDs" (used for segment, surface and artifact ids).

Change: `Chat/console_trace_final_values.py` validates `origin_call_id` and `terminal_call_id` with `_validate_stable_opaque_id`. The user, assistant and source revision ids keep `SemanticRevisionRef`: revisions, voice ones included, are always minted UUIDv4 (`new_opaque_id`), and `_initial_voice_message_revision_matches` requires that. Not changed, worth knowing: `discarded_assistant_message_id`, `discarded_followups` and `closed_followups` validate MESSAGE ids as `SemanticRevisionRef` (v4), and voice-promoted messages have UUIDv5 ids. Those fields are set only for discarded or failed-empty assistant chains. A promoted voice pair commits a complete assistant, so reaching them needs a voice reply that is discarded later; that path was not exercised here.

Test (`Tests/Chat/test_console_capture_send_triggers.py::test_a_typed_send_after_a_promoted_voice_turn_is_traced`; real controller, store, SQLite, gateway, trace boundary factory, winning promotion and trace import; only the provider adapter recorded): hello, a voice turn, then "thanks" must complete with one provider call, the five expected rows, and a recorded trace equal to what was sent. Red on the pre-fix code ("Trace capture could not start", blocker TRACE_CALL); green after. Mutation (origin call id back on `SemanticRevisionRef`, restored by edit): red again.
