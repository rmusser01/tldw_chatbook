## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during TASK-34100.5's review-round-1 live verification on 2026-10-04. The defect is already on the base (1d8fe87659), and the hosted transport is outside that task's diff, so it is filed here.

With a working OpenRouter key and `openai/gpt-4.1-nano`, every Console send to OpenRouter fails. A direct `curl` with the same key, model and messages returns HTTP 200 and "hi", both streaming and non-streaming.

The app's handler (`chat_with_openrouter` through the hosted transport) rejects the 200 reply:
- non-streaming: `ChatProviderError("OpenRouter returned a malformed successful response.", status_code=502)`;
- streaming: `HostedChatProtocolError("Hosted Chat stream event is malformed.")`.

The cause appears to be the transport's strict key allowlists (`_KNOWN_TOP_LEVEL_KEYS`, `_KNOWN_CHOICE_KEYS`, `_KNOWN_MESSAGE_KEYS` and `_KNOWN_STREAM_CHOICE_KEYS` in `LLM_Calls/hosted_chat.py`). OpenRouter's replies now carry fields those lists do not include:
- top level: `provider`, `service_tier`;
- choice: `native_finish_reason`, `logprobs`;
- message: `reasoning`, `refusal`;
- usage: `cost`, `cost_details`, `is_byok`.

The user sees one of two things:
- With capture on, the first try's 502 is retried in place as transient, and the retry's trace reservation is refused (`trace_tool_chain_unavailable`, TASK-33621.5). The card reads "Trace capture blocked / The provider was not contacted". 'Send without capture' then raises the false "delivery status is unknown" warning (TASK-33621.6).
- Without capture, after three attempts: "Agent run failed: provider returned HTTP 502 (Provider error from OpenRouter: provider unavailable. Status: 502.)". That blames OpenRouter for a reply chatbook could not read.

Evidence (setup-wizard-ux-qa):
- `evidence/g5-r1-or/03-first-send-t045.txt` (trace card);
- `04-send-without-capture-t045.txt` (duplicate-request warning);
- `05-retry-anyway-t030.txt` (502 copy);
- `homes/g5-r1-or/.local/share/tldw_cli/default_user/tldw_cli_app.log` lines 350-366;
- a probe of `chat_with_openrouter` with an isolated HOME, which fails the same way on the 1d8fe87659 snapshot.

Coordination (2026-10-04): TASK-34100.2's second pass (branch `fix/task-34100.2-first-chat-catalog`) is fixing this same defect, OpenRouter's extra reply fields, in `LLM_Calls/hosted_chat.py` (`_check_top_level_extras`) and `LLM_Calls/openrouter.py`. This task should be closed by that PR once it merges, after checking that its tests cover the ACs below; work it separately only if that PR leaves an AC open.
