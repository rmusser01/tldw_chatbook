## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact (P1, root-cause instance list).** Console recovery and readiness copy is picked from a coarse category, a status code, or a substring match on display text. The fact that would tell cases apart (provider body, phase, whether the provider was reached, which subsystem blocked) is dropped. Instances reproduced live on 64579cce2c:
- **(h) Doubled wrapper:** 'Agent run failed: provider returned HTTP 401 (Provider error from anthropic: authentication failed. Status: 401.)'.
- **(b) Wrong image hint:** the image hint is appended to that 401 auth failure ('This conversation includes an image attachment; if the model can't accept images, remove that message…'), although the same model had just read the image correctly.
- **(g) False 'setup' badge:** it shows on the closed Inspect handle during every ordinary running send, and the pinned line reads 'Run: Blocked'. While a run is active, readiness returns blocker active_run, the Provider row becomes 'blocked', and the 'provider' and 'blocked' substrings then produce 'setup'.
- **(f) Wrong blocked reason:** staging an image with claude-haiku-4-5 shows 'Send blocked — choose a model to continue', though a model is selected. The real reason ('can't accept images') rides the setup slot and matches the 'model' substring.
- **Unmatched reasons:** any unmatched non-empty reason falls back to 'finish provider setup to continue', so queue-full and pre-acceptance tooltips (prompt_queue.py:132/136) read as provider setup.
- **Confirmed in code only:** (a) every 400 gets 'Confirm the model is still available'; (e) active_run maps to 'Provider setup needed: current run is active'.

Fixing instances one at a time will not hold, because each new failure mode reuses the nearest template. The structured ConsoleFailureEvidence record and the RecoveryCallout belong to the Theme 1 umbrella. This task moves the surfaces above onto structured fields and removes substring matching. The trace-panel Impact line is handled with G4-04, and the 'source device' copy with G4-05.

**Prior art:** KNOWN_PARTIAL: TASK-2543 (To Do; non-HTTP failures reported as 502), TASK-32369 (To Do), TASK-19642.8.7 (To Do; expects failure rows to keep the image hint, so reconcile with it), TASK-32342 (Done), TASK-33005.2 (To Do; readiness evidence), TASK-2154.16 and TASK-2154.12 (Done).

**Suggested direction:**
- Render the system row, run state, disabled reason, readiness summary and rail badge from blocker and failure codes, never from display-copy substrings.
- Stop treating active_run as a provider-readiness blocker.
- Give attachment, queue and wake blockers their own codes.
- Show the image hint only for 400/413/415/422 whose body mentions image or vision, and the model hint only for 404/model_not_found.
- Emit a single wrapper.
- Separately, file the claude-haiku-4-5 vision capability gap (model_capabilities.py:44-48).

Evidence: qa/console-ux-review-2026-09-29/findings.md → G4-06 (source L3-03). **Review fixes (2026-10-30, on dev 7536ac3b87)**

The independent review found three blocking defects. Each was confirmed red before its fix.
1. **Crash.** `ConsoleBlockedReason` was a `str` subclass with a keyword-only `code`, so `copy`, `deepcopy` and `pickle` raised `TypeError`. prompt_queue's `.strip()` kept the subclass, so a refused Enter stored it as a System row's content, and the Inspect Context view (which deep-copies every row) failed.
   - It is now a frozen dataclass (`text`, `code`, `notice`) carried beside the sentence. Only `.text`, a plain str, reaches a tooltip, a row or a toast.
   - ChatScreen keeps `_console_setup_blocked_reason` and `_console_send_blocked_reason` returning sentences, and adds the coded `_console_composer_send_blocker` (the composer) and `_console_send_gate` (prompt_queue).
   - Red first: `test_a_refused_enter_writes_plain_sentences_the_context_view_can_copy` raised exactly that `TypeError` on 16a7ea7e2b.
   - Live A/B (real app, real Anthropic haiku through the review proxy): staging a PNG, pressing Enter, removing the image and opening View chat context. On 16a7ea7e2b it read "Preview unavailable · Refresh to retry" (U09/34); on the fix it read "Prepared now", messages (1) (U09/35).
2. **False fact.** The setup strip's code defaulted to the readiness blocker, so an HTTP-status or invalid-payload connection failure read "retry the connection".
   - Codes are now assigned per recovery action. The fallback is `provider_setup`, which reads "finish provider setup".
   - New STRIP_CASES cover http_status, invalid_payload, endpoint_invalid, provider_configuration_invalid and readiness_unknown. The first two were red on 16a7ea7e2b.
3. **AC#5.**
   - prompt_queue's refused-Enter row used a dead "Library Search/RAG" prefix match, and its toast used text equality. The row is now chosen by the gate's code. This is TASK-38331, folded in and closed. Its mounted test was red on dev: the row read "Add API key..." instead of the evidence blocker.
   - The controller's `_blocked_visible_copy` chose rows by `"Provider blocked" in copy` / `startswith("WIP:")`. The gateway's sentence is now the row verbatim, and only an empty one gets "Provider blocked.". Its test was red on dev (2 of 3 cases).
