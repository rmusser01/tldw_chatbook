## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-33620.15.21's live rounds (2026-10-30, origin/dev 7536ac3b87, Anthropic claude-haiku-4-5 via the review proxy, 160x45, a fresh isolated profile per launch, host load1 99-127 from a bounded busy-loop generator). At that load, run start's longest UI-loop callback had a median of 132 ms wall on first sends and 119 ms on later sends, with about 11 ms of its own CPU (48 sends). At load 3-9 it was 16.8 and 7.0 ms (24 sends). The post-commit step was that callback in only 6 of the 48 high-load sends.

Exact timers on 32 of the high-load sends show what held it in most first sends. In 14 of the 32, most of it was the catalog fingerprint's MCP source check: UnifiedMCPControlPlaneService.run_catalog_fingerprint > LocalMCPControlService.catalog_fingerprint > the mcp_source_participants guard > binding > MCP/recovery_activation.selected_path. That check does a storage admission plus generation witnesses, the stat and read syscalls in storage_admission's _Evidence.observe (_posture, _content).
- First sends: 6 of 8. The callback's median was 209 ms wall and 12 ms CPU, and the check alone took 199 ms.
- Later sends: 8 of 24. The callback's median was 113 ms, and the check took 107 ms.
- At low load the same check takes 5.4 ms (first sends) and 3.9 ms (later sends).

The check's CPU about doubles at load, to 8 ms. Most of its wall time is spent waiting to be scheduled again after its syscalls release the GIL (see lessons-live-verification, TASK-33620.15.1.6).

TASK-33620.15.5 kept the fingerprint's two store reads on the UI loop and split them across loop turns. The reason was that TASK-33620.15.1's worker hop made first sends reach the provider 97-249 ms later. A fix has to weigh that cost at both loads.

Other run-start holds at that load are smaller or rarer:
- Storage admission's evidence check (_Evidence.observe): on first sends, its longest call per send had a median of 16 ms (up to 113 ms), in a callback with a median of 38 ms.
- Provider entry's response-rule bindings read (ResponseRuleRuntime.begin_generation): median 5 ms, up to 123 ms.
- Local tool provider composition (Path.resolve in LocalToolProvider.__init__): 124-207 ms twice, on 1-2 ms of CPU.
- Callbacks with 2-4 ms of CPU and 60-300 ms of wall, where no code dominates.

The MCP check is one case of a wider cause: storage admission's filesystem syscalls on the UI loop. The same kind of wait, in admission's Path.resolve on ChaChaNotes transaction entry, held 3 of the 8 post-commit steps of 50 ms or more in the same rounds (see TASK-33620.15.21's notes). Moving only this check does not cover those tails; they need their own task.

Once this check moves, one of the holds above may become the longest callback, so AC#2's halving target may be out of reach by moving the check alone. Measure what would be the next-longest callback first (AC#1). If halving is out of reach, revise AC#2 with those numbers before implementing, rather than widening the fix.

Evidence: tools/evidence/bd5/M21/ (rounds r1-r3, the kit, analysis_all.txt).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A live Console send no longer takes the run catalog fingerprint. A run start with nothing to reuse takes a cheap anchor instead and keeps its composition pending. The next run start's own fingerprint then proves the pending composition or refuses it. This follows the owner's decision of 2026-11-05 on the first round: do not ship the worker-hop trade; take the first send's fingerprint after the composition and off the send's path, with a test-backed proof that a change in between cannot leave a send with a mismatched catalog. Where a run can reuse, the next run start's fingerprint still reads stock sources on one owned worker, as the first round built it; custom readers, a custom manifest provider and uninstalled stores keep the loop route and take the fingerprint before composing. On a stock profile no live send reaches that path (see the review follow-ups below).

**Measured first (continuation, origin/dev e8eeae7db9).** One live launch with zero-wrap `sys.monitoring` markers (k3smoke) on `run_catalog_fingerprint`, the cold composition `prepare_console_tools`, the reuse `install_composition` and `_keep`. On every send the fingerprint ran and then the cold composition; nothing was reused or kept. A live, non-temporary send freezes its MCP definition ceiling at composition (`composition_mcp = stock_mcp and not session.ephemeral`). Such a run never reuses, and it keeps nothing because its key changes when the ceiling freezes. So the check the first round moved decided nothing on a live send, and a first send has nothing kept to compare it with either.

**Approach** (`Chat/console_run_start_tools.py`)
- A run start with no kept composition, or one that freezes its ceiling, calls `_take_anchor` instead of the fingerprint. The anchor holds:
  - the governance checks the fingerprint makes first (a refused listing anchors nothing);
  - the stamps of both store files (two `stat` calls);
  - the admission epoch;
  - weak refs to the selected sources: permission store, local service, local store, manifest provider.
- Only stock sources are anchored. Custom readers or a custom manifest provider take the fingerprint before the composition, as before.
- `_keep` keeps an anchored composition pending (identity None) only when all of these hold: the anchored stamps were settled `SETTLE_NS` before the anchor (the eager keep's rule), the same sources are selected, the listing is allowed, the epoch did not move, and the connection states held.
- `_proven`: the next run start has an entry to compare, so it fingerprints. It proves the pending composition only if that fingerprint read through the same sources, every store file still has its anchored stamp, and the epoch has not moved. Only then does the fingerprint's identity become the kept identity, and the usual reuse comparison (identity, connection states, key) runs. Anything else drops the pending entry; the run composes from the stores and keeps eagerly, as before.
- Why a change in between cannot leave a send with a mismatched catalog:
  - a stamp carries `st_ctime_ns`, which every write changes (bytes put back included), and the file was settled before the anchor;
  - another store, generation file or manifest provider fails the source check;
  - a recovery or admission write moves the epoch;
  - a store whose recovery activation selects another generation fails the fingerprint's own binding check (`RecoveryRequired`), which drops the entry.
- Unchanged: the fingerprint, its worker read for stock sources (first round), the reuse comparison and every refusal.
