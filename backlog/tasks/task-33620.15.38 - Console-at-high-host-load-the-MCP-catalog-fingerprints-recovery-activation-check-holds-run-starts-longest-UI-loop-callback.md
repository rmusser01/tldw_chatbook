## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-33620.15.21's live rounds (2026-10-30, origin/dev 7536ac3b87, Anthropic claude-haiku-4-5 via the review proxy, 160x45, a fresh isolated profile per launch, host load1 99-127 from a bounded busy-loop generator). At that load, run start's longest UI-loop callback had a median of 132 ms wall on first sends and 119 ms on later sends, with about 11 ms of its own CPU (48 sends). At load 3-9 it was 16.8 and 7.0 ms (24 sends). The post-commit step was that callback in only 6 of the 48 high-load sends.

Exact timers on 32 of the high-load sends show what held it in most first sends. In 14 of the 32, most of it was the catalog fingerprint's MCP source check: UnifiedMCPControlPlaneService.run_catalog_fingerprint > LocalMCPControlService.catalog_fingerprint > the mcp_source_participants guard > binding > MCP/recovery_activation.selected_path. That check does a storage admission plus generation witnesses, the stat and read syscalls in storage_admission's _Evidence.observe (_posture, _content).
- First sends: 6 of 8. The callback's median was 209 ms wall and 12 ms CPU, and the check alone took 199 ms.
- Later sends: 8 of 24. The callback's median was 113 ms, and the check took 107 ms.
- At low load the same check takes 5.4 ms (first sends) and 3.9 ms (later sends).

The check's CPU about doubles at load, to 8 ms. Most of its wall time is spent waiting to be scheduled again after its syscalls release the GIL (see lessons-live-verification, TASK-33620.15.1.6).

TASK-33620.15.5 kept the fingerprint's two store reads on the UI loop and split them across loop turns. The reason was that TASK-33620.15.1's worker hop made first sends reach the provider 97-249 ms later. A fix has to weigh that cost at both loads.

Other run-start holds at that load are smaller or rarer:
- Storage admission's evidence check (_Evidence.observe): on first sends, its longest call per send had a median of 16 ms (up to 113 ms), in a callback with a median of 38 ms.
- Provider entry's response-rule bindings read (ResponseRuleRuntime.begin_generation): median 5 ms, up to 123 ms.
- Local tool provider composition (Path.resolve in LocalToolProvider.__init__): 124-207 ms twice, on 1-2 ms of CPU.
- Callbacks with 2-4 ms of CPU and 60-300 ms of wall, where no code dominates.

The MCP check is one case of a wider cause: storage admission's filesystem syscalls on the UI loop. The same kind of wait, in admission's Path.resolve on ChaChaNotes transaction entry, held 3 of the 8 post-commit steps of 50 ms or more in the same rounds (see TASK-33620.15.21's notes). Moving only this check does not cover those tails; they need their own task.

Once this check moves, one of the holds above may become the longest callback, so AC#2's halving target may be out of reach by moving the check alone. Measure what would be the next-longest callback first (AC#1). If halving is out of reach, revise AC#2 with those numbers before implementing, rather than widening the fix.

Evidence: tools/evidence/bd5/M21/ (rounds r1-r3, the kit, analysis_all.txt).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Run start's catalog fingerprint now reads its stock sources on one owned worker, so its recovery-activation checks no longer run on the UI loop. This was measured on current origin/dev first (AC#1). AC#2 was then restated from those numbers, before the paired round, because moving this check alone could not halve run start's longest callback.

**Approach**
- New `MCP/console_snapshot.read_run_catalog_fingerprint`, called by `UnifiedMCPControlPlaneService.run_catalog_fingerprint`. For stock, installed sources it reads in one `_owned_worker` hop, behind the same producer fence:
  - the permission store's `catalog_fingerprint`;
  - then `LocalMCPControlService._catalog_fingerprint_sources`: the manifest source hash, then the local store's `catalog_fingerprint`.
- "Stock" means: exact types, original class members and bound readers with pinned bodies, the default manifest provider, and both stores bound in `mcp_source_participants`.
- `_catalog_fingerprint_sources` is new and is the one body both routes run. `catalog_fingerprint` keeps its governance checks and connection states around it.
- These stay on the loop, around the hop:
  - governance before the hop, so a refused listing reads nothing, as before;
  - governance again after the hop;
  - a re-check that the service still selects the captured receivers with the same source identities; a change raises `RecoveryRequired("mcp_source_selection_changed")`, the error a changed selection raises inside a read;
  - the connection states.
- The reuse decision in `compose_run_mcp_provider` runs in that same loop turn, so it sees what it saw when the whole check ran on the loop.
- Custom readers, a custom manifest provider and uninstalled stores keep the loop route unchanged, with a yield between the two store reads (TASK-33620.15.5).
- The `_CONSOLE_STANDARD_METHODS` tables in local_control_service, local_store and permission_store now list the fingerprint readers, so those readers' identities and bodies are pinned.
- Unchanged: the reuse decision and `_keep`; every store read's own admission, recovery-activation and readability checks; the refusals (same exceptions). A governance refusal now comes before the permission store's read instead of after it. Either way the check raises and run start composes from the stores.

- Where that time goes (probe rounds v2plo and v2plo2, low load, 3 launches per arm each; v2plo2 without the sampler and heartbeat threads):
  - On the worker, the check took 7-13 ms in 8 of 18 sends, 27 ms in one, and 42-211 ms in the other 9, on 12-41 ms of CPU. It waits for the GIL while the freed loop renders the send.
  - Even with a 12 ms worker read, one first send reached the provider 94 ms later. While the run task is parked in the hop, the loop runs the first send's UI work, and the run task resumes behind it.
  - On origin/dev the check took 8-16 ms on the loop at this load. It held no longest callback there (0/3, 0/6 in AC#1).
  - This is the effect TASK-33620.15.1 and TASK-33620.15's hop rounds met (lessons-testing-evidence, "An input probe slows the arm whose UI loop it frees").
- From injection (tmux) to the POST, the same within 35 ms.
- Every Enter reached the provider: one POST answered 200 per Enter, in all 61 launches of the six rounds (183 sends). One send's injection stamp fell 189 ms after its key event (a wall-clock step), so the analysis now matches keys within 0.5 s.

**Owner decision needed (AC#3).** The branch trades about +55 ms on low-load first sends for:
- -1.1 s on high-load first sends;
- a shorter longest UI-loop callback at high load.
A way to avoid the trade, not tried here because it widens the fix: on the cold path (no kept catalog), the fingerprint decides nothing for the current run; it only lets the next run reuse. It could be taken after the composition and off the critical path, as a deferred keep that the next run start awaits. That needs its own proof that a store-selection change between the composition and the deferred read cannot keep a mismatched catalog. `_keep`'s stamp check alone does not cover a switch to an older generation file. The options are:
- accept the trade;
- restate AC#3;
- or file the deferred-keep design as its own task.

**Deviation from the plan.** The code was written while the AC#1 baseline ran. AC#2 was restated from that baseline before any paired measurement, and the fix's scope did not change.
