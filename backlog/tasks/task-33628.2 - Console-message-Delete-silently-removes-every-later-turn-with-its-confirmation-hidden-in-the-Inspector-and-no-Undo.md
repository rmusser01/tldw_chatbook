## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**User impact.** One mistaken Delete destroys the rest of a conversation, possibly hours of agent work, and nothing on screen says that will happen or offers a way back.

**What was verified on origin/dev @ 64579cce2c.** The reviewer selected the 2nd of 5 turns ('Name one colour.') and chose More… › Delete.
- **First click:** the transcript did not change at all (the capture is byte-identical to the selected state). The 'Press Delete again to remove this message.' copy appears only as a 'Delete confirmation' row in the Inspector's Selected Message section. The Inspector is collapsed by default, and even when opened at 160x45 the row sits about 20 wheel ticks below the fold. Reopening More… still shows a plain 'Delete' item.
- **Second click:** removed **8 messages**: the selected message, its reply and all three later turns.
- **Receipt:** the toast said 'Deleted message from transcript.' in the singular, with no Undo. A spurious second warning also appeared, 'Message deleted; recovered-media reference cleanup is pending.', although the chat contained no media.
- **Copy:** the tooltip, pending row and receipt all say 'this message'. The subtree scope is documented only in the User Guide (chat-basics.md:453, 480-484), which also implies the confirmation is visible.
- **Recovery:** all 8 rows are tombstoned in the DB (deleted=1, content kept), but no undelete path exists in the DB, store or UI.
- **Image hint:** the image-rejection recovery hint sends users to Delete, which would remove every turn after an earlier image message.

**Severity and prior art.** P1; the reviewer rated it P0.
- Triaged as a **REGRESSION of TASK-131 (Done)**. Its AC#8 was ticked for 'delete provide clear feedback and safe recovery or confirmation where destructive', and its notes say 'requiring a second activation after visible confirmation feedback'.
- The verifier's correction: commit 7829680c7a put the confirmation copy in the Inspector from the start, so the in-transcript gap is long-standing. That Done AC was never actually met on the transcript surface.

**Suggested direction.**
- Render the pending-delete state inline on the selected transcript row, e.g. 'Delete this and N later messages? [Delete N] [Cancel]', with N taken from the store's subtree ids. Reflect the pending state in the More… item as well.
- Make the receipt state the real count ('Deleted 8 messages') and offer Undo, matching the Archive receipt pattern. Undo clears exactly those tombstones and restores the prior active leaf. This needs a new subtree-undelete path in persistence. An alternative is for Delete to hide or branch the way /rewind does.
- Rewrite `_IMAGE_REJECTION_RECOVERY_HINT` to point to a non-destructive path: Edit & resend without the image, or switch to a vision model.
- Suppress the recovered-media cleanup warning when no recovered-media references exist.
- Update Docs/User_Guide/console/chat-basics.md.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented TASK-33628.2 on fix/task-33628.2-delete-scope-undo in two commits: 9827ac9cd4 (in-row scope, receipt and Undo) and eb9f14df03 (the review follow-up that makes Undo exact and retryable).

**Approach.** Console message Delete is now a three-step flow owned by UI/Console_Modules/message_delete.py.
1. **Arm.** The first Delete measures the real subtree through console_delete_scope. The action resolver swaps the selected row's actions for [Delete N messages] [Cancel] and puts the scoped question in the row legend. The transcript focuses Cancel and scrolls the row into view (Widgets/Console/console_transcript_delete_confirmation.py). Moving the selection drops the stale scope at plan time.
2. **Confirm.** If the subtree changed since arming, the prompt re-arms with the new count and a notice. Otherwise delete_subtree_for_undo captures the tree position, per-message marks and the durable cursor. It then deletes under a per-thread recovered-media release hold and records the tombstone versions of exactly the ids the DB delete committed.
3. **Receipt.** ConsoleMessageDeleteReceiptModal (the Archive receipt pattern) says "Deleted N messages" with Undo focused.
   - Undo calls restore_deleted_subtree: a version-checked CharactersRAGDB.restore_message_subtree plus the cursor, in one transaction. It then re-registers the same node objects in their original sibling order and rebinds the cached message versions, so Regenerate and variants don't hit ConflictError.
   - A ConflictError refuses Undo and makes the delete final. Other storage errors keep Undo on offer.
   - Done (or Esc) releases the held media references and warns only if that release really left cleanup pending.

**Other changes:**
- _release_recovered_messages no longer marks cleanup pending when references_absent proves that no current-profile reference names the messages.
- The image-rejection hint names a vision-capable model or /rewind.
- The chat-basics and attachments User Guide pages describe the flow.
