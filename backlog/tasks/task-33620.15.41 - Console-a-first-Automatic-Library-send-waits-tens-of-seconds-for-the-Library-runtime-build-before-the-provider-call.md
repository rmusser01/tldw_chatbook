## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while measuring TASK-33620.15.19 (2026-10-30). With a conversation's Library Auto set to Automatic and the BM25 Only RAG profile active, the first send after launch spent 17-39 s between Enter and the provider request, 26 s even at host load 19. Almost all of it was the Library search service's prewarm, the shared RAG runtime build, which runs on a worker thread. The UI stays responsive, but the user watches 'Searching Library…' for tens of seconds before the model is asked anything. A BM25 Only profile needs no vectors, so it is not clear why this path builds the embedding runtime at all; TASK-3601 asks the same question for the Library screen's rag mode. TASK-33621.20 made a cold-start timeout pause with Retry / Send once without Library / Cancel, but did not address the build cost. Every number so far was taken while another session loaded the host heavily, so a load-free measurement comes first.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** A BM25 Only (keyword-only) profile no longer builds the Library's embedding runtime. Its first Automatic send went from 6.0-10.1 s Enter-to-provider on dev (median 8.6 s) to 1.6-2.8 s (median 1.8 s), on an unloaded host, four paired rounds each. Embedding profiles still need the runtime; their wait is named again on the run chip ("Searching Library…"). Dev had been showing "Sending…" for it since 077e5bfa09.

**AC#1: measured live first, on current dev.** The WIP was cut on 804dc00231, about 1,550 commits back, so the branch was rebuilt from dev 29592ecc9b and the old commits were re-applied after the base was re-measured. Set-up:
- seeded isolated profile, built through the real app: one note, a chat with Library Auto: Automatic, all-MiniLM-L6-v2 cached;
- real app via launch.sh at 160x45, Anthropic claude-haiku-4-5 through the review proxy;
- probe on send stages, Library prewarm/search, the runtime-build sections and build-thread imports;
- the RAG profile set per launch (`[rag.service] profile`), recorded with each round.

Dev, BM25 Only, unloaded (rounds R1/R4/R5/R6, 1-minute load at Enter 6.9-11):
- Enter-to-POST 10.1 / 8.6 / 6.0 / 8.5 s, of which the prewarm (the shared runtime build) took 7.7 / 6.7 / 4.2 / 6.5 s, or 70-78 %.
- About 80 % of the build was imports on the build thread: 6.5 / 5.6 / 3.2 / 5.2 s, mostly sentence-transformers, then torch, transformers and chromadb.
- The rest was the embedding model load (0.8-1.5 s) and the dimension probe.
- The app log said "Created shared RAG service (profile=bm25_only)".

Dev, BM25 Only, loaded (load 98-110, another session's 88 busy loops): 33.6-36.4 s, of which 26.5-29.2 s was the build. That is the task's 17-39 s.

**Cause.** `LibraryLocalRagSearchService._search_rag` and `prewarm()` resolved the shared RAG runtime before reading the profile's mode. A plain profile then ran the four-seam keyword search, which reads no vectors. The runtime was built only to learn which route to take (TASK-3601's finding).

**Fix (AC#2).** The service now reads the active profile's mode and name without a runtime:
- `active_config.resolve_active_rag_search_mode` and the new `resolve_active_rag_profile_name` resolve the same profile the runtime would: pointer, builtin fallback, `RAG_SEARCH_MODE`.
- The read runs off the event loop (30 ms live), once per shared-service generation, and is joined, not repeated.
- For a plain profile, `prewarm()` and the rag route build nothing and skip the `embeddings_rag` gate, so BM25 Only also works without the extras (TASK-3601, now Done).
- A cached runtime, any non-plain mode, or an unreadable profile resolves the runtime exactly as before. The first-run settings import still runs inside that build. It snapshots the active profile's own config, merging only top-k, threshold, citations and reranking, so it can never change a plain profile's mode.

**The embedding-profile wait (honest, and as short as the design allows).** Semantic and Hybrid profiles must embed the query, so they keep the build: 4.4-7.7 s of 6.2-10.7 s Enter-to-POST unloaded.
- Dev's run chip read "Run: Sending…" for all of it. 077e5bfa09 (TASK-34601.1) mapped every VALIDATING state to "Sending…", which hid TASK-33621.20's "Searching Library…". TASK-33621.20's own UI test has been red on dev since then.
- `console_send_activity_copy` now keeps that one copy. Live on the branch the chip reads "Run: Searching Library…" from about 1 s after Enter until the search ends; on dev it reads "Sending…" throughout.
- Inside the build, the imports and the model load are the cost. Starting the build before Enter would hide it, but that changes TASK-33621.20's "nothing runs unless an Automatic send is preparing", so it is filed for an owner decision as TASK-33620.15.41.1.
