## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Chat settings keeps each listing with the connection it listed, and pick mode offers it only while the provider still uses that connection.

- `Widgets/Console/console_settings_field_row.py`: `_served_models` maps a provider to `(connection identity, model ids)`. `_served_endpoint(provider)` is the identity the modal already computes (`_discovery_connection_identity`) for the URL a pick onto that provider uses: the Endpoint field for the draft's own provider (`_discovery_endpoint_value`), and the stored draft URL for another one (`_base_url_for_provider`; a registry entry's own URL either way). `_keep_served_models` records a listing with that identity; `_open_model_picker` passes pick mode only the listings whose identity still matches, so `model_switcher.py` and the switcher keep their provider-keyed `served` mapping (its docstring says so now).
- `console_settings_modal.py`: the listing-result handler records through `_keep_served_models` (one line fewer), and `__init__` starts the map empty, typed by the mixin's annotation. `_list_then_pick` (a created entry) records the same way.
- Going back to the endpoint that listed the models offers them again: they are still what that endpoint served.

Test (red at fc9f3ec375, green after): `Tests/UI/test_console_endpoint_discovery.py::test_a_listing_is_offered_in_pick_mode_only_for_the_endpoint_that_listed_it`. Test connection lists `served-y` at 127.0.0.1:9099, then the Endpoint changes to :9100 and back. At the base, `("llama_cpp", "served-y")` was still offered after the change. The created-entry and listing tests in `Tests/UI/test_console_settings_model_change.py` stay green (whole file, xdist).
