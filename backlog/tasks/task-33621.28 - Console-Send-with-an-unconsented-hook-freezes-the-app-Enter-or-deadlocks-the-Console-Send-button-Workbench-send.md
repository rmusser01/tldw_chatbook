## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Live on dev since PR #2922 (hook review on next Send; commits 2bce8ffa0f and aed1b13501). A Send that needs a hook review awaits request_hook_review on a message pump (Widgets/Console/console_hooks_review_modal.py ~413). Textual 8.2.8 runs a pushed screen's result callback via requester.call_next, and the requester is the pump that is awaiting the answer, so the callback can never run.

- **Enter:** the send runs on the APP pump via app.call_later. The app stops reading keys: Escape never reaches the review modal and Ctrl+Q is ignored. This is a total freeze in the same class as the Choose-folder freeze (TASK-33621.13).
- **Send button and Workbench send:** the requester is the ChatScreen. Escape dismisses the modal, but the send never settles and the Console pump is dead from then on.

The W003 investigation on the TASK-33621.13 branch (PR pending) found it and pinned all three routes with strict xfails in Tests/UI/test_console_hook_review_send_freeze.py. A mutation that resolves the answer from the modal's own result future fixes the two ChatScreen routes but not Enter.

Suggested direction:
- Resolve the review answer from the modal's result future, not from a callback on the requester pump.
- Run the Enter continuation's review-then-dispatch off the app pump, in a worker.

The second part touches the app.call_later contract pinned by Tests/UI/test_console_send_draft_snapshot.py, #2922's 'Allow resumes once' continuation, and the spoken-send acknowledgement.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fixed the hook-review Send freeze in both places it lived (commits e6269d7cea and 6f0d2d6c16 on fix/task-33621.28-hook-review-send-freeze, stacked on #2944).

Approach:
- The review modal settles its own answer future in `dismiss()`, and as a cancel on unmount. So `request_hook_review` no longer depends on a `push_screen` callback that Textual queues on the awaiting requester pump.
- `ConsoleHooksController.dispatch` hands the review-then-dispatch continuation to a ChatScreen worker whenever the caller is not a worker's own task, and returns `ConsolePromptDispatchStatus.AWAITING_REVIEW` immediately. That covers Send button and Workbench handlers on the Console pump and Enter's `app.call_later` callback on the app pump. Worker callers (spoken send) still await the whole continuation and get the real outcome.
- `hooks.in_worker_task()` decides this by task identity: `asyncio.current_task()` against Textual 8's private `Worker._task`, where None counts as current while the worker is running (the eager-task-factory first step). It does not use the inherited `active_worker` contextvar, which a navigated screen's pump inherits from the `screen-navigation` worker.

Technical decisions:
- Task identity over threading an explicit `await_review` flag. Every pump caller is safe by construction, about 19 test fakes keep their fixed signatures, and chat_screen.py stays within its line budget (25494 vs 25496).
- `_task` is private. If a Textual upgrade drops it, the check answers False (hand off), which is the safe side; the spoken-send tests would flag the regression.
- `ConsolePromptDispatchResult.accepted` is narrowed to SENT/QUEUED.
- The UI diagnostic scopes record `awaiting_review`; the worker records `hook_review_continuation` with the real status.
- `request_hook_review` logs an ERROR when awaited outside a worker task (inventory row added), because W003 can no longer see this await shape.

AC#1's Ctrl+Q clause is NOT met in the real app. It is a pre-existing, app-wide gap (non-priority `ctrl+q` at app.py:924 plus Textual's `_modal_binding_chain`), reported for an owner decision rather than changed here.
