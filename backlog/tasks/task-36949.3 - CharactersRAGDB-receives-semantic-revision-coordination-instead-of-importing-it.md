## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Twelve write sites lazily import `Chat.console_semantic_revision`, which imports `CharactersRAGDB` at top level, a dependency cycle between persistence and Console domain code. The coordination must still run inside the write transaction.

Source: architecture review 2026-10-25, `Docs/QA/architecture-review-2026-10-25/report.md` §F8; claim-by-claim verification in `Docs/QA/architecture-review-2026-10-25/verification.md` (origin/dev 7a5e2513c5).

- [x] #2 Semantic-revision coordination still runs inside the same write transaction, under the existing mutation-guard tests

## Implementation Plan

Coordinator ruling (2026-11-06): option A, a process-wide port that fails closed.
1. Add a stdlib-only DB-layer port (slot, install, fail-closed read, named error).
2. Route the two coordinator call sites in ChaChaNotes_DB through it; same placement inside the write transaction.
3. `Chat.console_semantic_revision.install_semantic_coordination()` (idempotent; the module also self-registers on import) and explicit installs at every composition root (pyproject scripts, `-m` entries, tldw-serve, mobile service, MCP server, RAG backfill).
4. Test suite: conftest installs the real coordinator (lazily) before any fixture; fresh-interpreter test children that write messages install explicitly.
5. Tests: in-transaction placement, rollback, fail closed with nothing persisted, idempotent install, one behavioural check per root.
6. Ratchets (layer allowlist row, ChaChaNotes_DB size row), Tests/Architecture, preflight.

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
Coordinator ruling 2026-11-06: option A, a process-wide port that fails closed.

**Behaviour change:** an uncomposed process (a Helper_Script or bare library use that never runs a composition root and never imports `Chat.console_semantic_revision`) now raises `SemanticCoordinationNotInstalledError` on its first coordinated message write, and the write rolls back. Before, the DB imported the coordinator itself, so every process coordinated.

Approach:
- Port: `DB/transaction_observer.py` (stdlib only, already in the DB boot closure, so no import-closure or ui-ready snapshot changes): slot, `install_semantic_coordinator_factory`, `semantic_coordinator_for`, `SemanticCoordinationNotInstalledError` (message names the install function and says to call it at the composition root). `ChaChaNotes_DB` calls `semantic_coordinator_for(self)` from the same two places as before (`_ensure_initial_semantic_revision` x4 callers, `_coordinate_semantic_mutation` x8), inside the write transaction. Unset: create raises inside the transaction after the INSERT (rolled back); update raises before the mutation runs. No call site swallows the error (`create_message_variant` re-wraps it as `CharactersRAGDBError` after rollback, as it does any coordinator error).
- `Chat.console_semantic_revision.install_semantic_coordination()` installs the real coordinator (idempotent); the module also calls it on import, as a convenience only.
- Composition roots, each installing explicitly with a function-level import (no layer allowlist row added; the `ChaChaNotes_DB -> Chat.console_semantic_revision` lazy row is deleted):
  - `tldw-cli` (pyproject) and `python -m tldw_chatbook`: `cli.main_cli_runner` -> `app_entry.main_cli_runner` (install right after `set_launch_cwd`). Its `recovery` branch and `Backup_Recovery/__main__` construct no CharactersRAGDB and write no messages.
  - `python -m tldw_chatbook.app` (also every textual-serve session): `app_entry._run_module_main`.
  - `app_entry.get_app()`, the textual-serve app factory (not a console script).
  - `tldw-serve` (pyproject) and `python -m tldw_chatbook.Web_Server.serve`: `serve.main` -> `run_web_server`; `mobile_service.MobileChatService._build_engine` (runs in the serve process, also installs).
  - MCP: `python -m tldw_chatbook.MCP` and `python -m tldw_chatbook.MCP.server` -> `server.main`.
  - RAG backfill CLI: `RAG_Search/backfill.main`.
  - No `[project.gui-scripts]`. The other `__main__` modules under tldw_chatbook (Tools/Audio/TTS/STT workers, css builders, Metrics, Terminal launcher, Chunking lab runner, Backup_Recovery workers, private SQLite helper, artifact share server, Prompts_Interop, Third_Party examples) construct no CharactersRAGDB and write no messages.
- `tldw-cli` now imports the coordinator (5 modules, ~20 ms measured) before logging setup instead of later; all 5 were already ui-ready residents.
- Tests: `Tests/conftest.py` installs a lazily-imported real coordinator in a session-scoped autouse fixture (session scope so module/class-scoped fixtures that write see it; lazy because in-process tests pin `sys.modules`). Fresh-interpreter children that wrote messages before anything imported the coordinator failed closed (37 failures found by running them); each now installs explicitly: `Tests/Backup_Recovery/test_canvas_recovery_validation.py`, `test_complete_roundtrip.py`, `test_isolated_restore.py`, `test_projection_recovery.py`, `test_recovered_media_direct_messages.py`, `Tests/Packaging/test_mcp_unified_distribution.py`. Children found by an AST scan of `Tests/` string programs and helper scripts, then run: the rest either load the coordinator themselves before writing (for example through `chat_persistence_service`, or by reaching the app's UI-ready point) and pass, or fail identically at base.
- Helper_Scripts/scripts with CharactersRAGDB writers, **now fail closed unless installed**: `Helper_Scripts/verify_console_context_memory_live.py` (imports `chat_persistence_service`, which loads the coordinator, so it coordinates today); `scripts/validate_live_tts.py` (drives TldwCli; fails only if it writes a message before the app has loaded the coordinator). `Helper_Scripts/Benchmarks/rag_citation_provenance_benchmark.py` failed closed under its CI-run test (`Tests/Performance/test_rag_citation_provenance_benchmark.py::test_cli_never_reads_or_writes_host_config_data_or_secrets`), so its `main()` now installs (inside its isolated host state). `scripts/check_schema_table_allowlist.py` builds a schema only. Dev-only CLIs in the same position (no test runs them in a subprocess): `Tests/Benchmarks/character_qualification_fixture.py` `build`/`native` (imports nothing that loads the coordinator before `add_message`) and `Tests/Benchmarks/generate_console_trace_legacy_fixture.py`.

Evidence (`Tests/DB/test_semantic_coordination_port.py`, 17 tests): coordination inside the write transaction (create and update), coordinator failure rolls back a create and an already-run guarded update, fail closed on create/update with nothing persisted, idempotent install, a fresh uncomposed interpreter fails closed then works once the coordinator is imported, one behavioural startup test per root (7; console-script roots start from the pyproject target itself), and a test that fails for any `[project.scripts]`/`[project.gui-scripts]` entry that is neither a tested root nor in a commented exemption list. Red: a silent skip when unset turned 3 tests red (create, update, uncomposed process); replacing every root install with `pass` turned all 6 root cases red on the `_factory` assertion; a `commit()` before each coordinator call turned the 3 in-transaction/rollback tests red (create rollback `assert 1 == 0`, the other two refused by the coordinator's own `caller_transaction_required`). Review fix round 1: `get_app` without its install made `[get_app]` red (`assert None is SemanticRevisionCoordinator`); a temporary extra pyproject script made the completeness test red. All temporary edits reverted. `semantic_coordinator_for` reads the slot once: a clear before that read raises `SemanticCoordinationNotInstalledError`, a clear after it still runs the factory it already read, and neither gives a TypeError. `test_slot_cleared_after_the_read_never_becomes_a_type_error` forces the late clear with a `sys.settrace` hook on the `return` line; on the old double-read code it failed with `TypeError: 'NoneType' object is not callable`.
