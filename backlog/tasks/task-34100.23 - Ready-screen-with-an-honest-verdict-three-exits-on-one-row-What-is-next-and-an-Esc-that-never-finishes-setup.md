## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The setup Summary is the peak of first run, and today it predicts an outcome it never checks: it says done when config is saved, not when a chat can be sent [cross-cutting-01]. It docks five exits in two rows, which take the read-back's space at 80x24, and shows arrival toasts that cover the nav bar.

The approved spec turns the Summary into Ready (decision D4, and What's next from D6 item 1): a verdict computed by Console's own shared readiness verdict (TASK-34100.2), never a wizard copy, with one mark per region; read-back rows only for steps the user saw; Data and Config paths; a "What's next" list of relevant next steps; and at most three exits plus Back on one row. Esc never finishes setup. It builds on TASK-34100.9's outcome record and "Ready to chat?" row and on TASK-34100.12's 80x24 frame.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D4, D6 item 1, §3.0, §3.6, §5, §8.1, §10 F8.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The last step is titled Ready. Its verdict region shows exactly one of these, computed through the shared readiness verdict: '✓ Ready to chat — <provider> · <model> (<context>)' when the key is proven; '✓ Set up — <provider> · <model> (<context>)' with 'The key isn't checked yet' when the key cannot be proven offline; '✗ Can't chat yet — <plain cause>'; or '– Chat not set up — no AI provider connected'. The region never shows two marks
- [ ] #2 A ✗ or ! verdict carries one fix action (or the two TASK-34100.9 AC#10 names) that lands on the step that fixes it with the staged key intact. 'Chat not set up' carries [ Connect a provider ]
- [ ] #3 Read-back rows appear only for steps the user saw: on Quick, Provider (where messages go and where the key lives), Model, tldw server and, when more than one provider has a credential, Keys; on Full, rows in step order with ✗ and ! rows first. Rows are read back from disk, and the legend '✓ saved · – skipped · ! needs attention · ✗ failed' shows whenever –, ! or ✗ is on screen
- [ ] #4 'Data:' and 'Config:' lines show the effective paths, middle-truncated, each with [ Copy ]
- [ ] #5 'What's next' is one focusable list computed from config each time Ready renders: only items whose area is not set up, at most three, then 'More (N)', marked → (ASCII ->). More expands in place, and Esc or ← collapses it. On Full at the short tier the list starts as one row. Every destination comes from the exit-route table, and an item whose home does not exist is hidden
- [ ] #6 Exits sit on one nav row with [ ← Back ]: on first run at most three ('Start chatting' or, when the verdict is ✗ or not set up, 'Go to Console', plus 'Add a document' and 'Write a note'); on a re-run walkthrough, TASK-34100.10 AC#14's exits. Below 100 columns the Library exits use their short labels. 'Explore Home' and 'Open Settings' move into What's next ▸ More
- [ ] #7 Esc on Ready never finishes setup: it collapses an expanded list and is otherwise inert, and the hint does not advertise it
- [ ] #8 Focus starts on the primary exit when the verdict is ✓ Ready to chat, and on the fix action when it is ✗ or !
- [ ] #9 Ready fits 80x24, 100x30, 120x40 and 200x60 on both tracks, in glyph and ASCII modes, with both Library exits and (on Full) at least 8 read-back rows visible. The five-actions live-contract test is rewritten as three exits plus Back, not deleted
- [ ] #10 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: a real OpenAI key (✓ Ready to chat); a real OpenRouter key (✓ Set up, key not checked); the real llama.cpp server; a model whose context size is unknown (✗ with Choose another model); and no provider at all (Chat not set up). Evidence is recorded in Implementation Notes

- [ ] #12 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
