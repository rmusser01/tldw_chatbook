## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Live 2026-11-23 on TASK-33620.1's branch at 9130078ee3 (evidence bd5/U04/r5-2026-11-23/40-55, real app, isolated profile, raw CLI unlocked and armed). During an emergency stop a '! echo hi' draft read Held and Enter was refused with a System row naming /emergency-stop clear, as the owner decision wants. After Clear the button read Run, but Enter was refused with 'Raw CLI could not persist this command locally. The exact draft was restored.' The same happened in a chat that had already run a raw command, and with a freshly typed command. A chat with no refusal row ran its command. In that chat a second raw command in a row was refused the same way, and on origin/dev 9418f179e3 (same profile setup, no stop involved) a second raw command in one chat was refused the same way too. Reading the code: `ConsoleRawCliController._execute` resolves the command's transcript anchor with `persisted_message_id_for_session_node(session, active_leaf)` and refuses when the leaf has no persisted id. A refusal's System row is never persisted, and in this scratch profile the raw marker was not either: the profile also logged 'run log: base directory escapes root; logging disabled' and 'Raw CLI persistence was incomplete'. So the stop's refusal row always blocks the next raw command in that chat, and the 'two in a row' case may or may not reproduce outside this profile layout. A likely fix is to anchor to the nearest persisted ancestor (`ConsoleChatStore._nearest_persisted_ancestor_id`), as ordinary persistence already does, but the raw path's anchor custody needs its own review.

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
Fixed on TASK-33621.4's branch (fix/task-33621.4-ready-may-pause-and-estop-held), 2026-11-23, because this branch's emergency-stop refusal (owner decision C) created the refused-then-Clear dead end.

**Root cause.**
- `ConsoleRawCliController.start_user_command` captures `native_anchor = active_leaf_anchor(session)`, which was the store's `active_leaf`.
- `_execute` then resolves `persisted_leaf_anchor(session, native_anchor)` (`persisted_message_id_for_session_node`) and refuses ("could not persist this command locally") when that row has no saved id.
- The saved id becomes the run row's `assistant_message_id`. On reopen, `ConsoleAgentBridge.resume_marker_messages` places the command's output after that saved message, or at the transcript start for `None`.
- A raw command's own marker is a TOOL row and never becomes the leaf (`_append_message`'s TOOL-marker invariant). But a refusal or notice appended through `_append_native_console_system_message` is a SYSTEM tree node: it becomes the leaf, and it is never saved.
- So after the stop's refusal row, the next raw command was refused.
- **The dev "two in a row" case is the same mechanism with a profile-specific trigger.** The scratch profiles disable the run log ("run log: base directory escapes root"; also with the default data location under the isolated HOME, evidence r5 70-72). The first command then appends "Raw CLI persistence was incomplete.", a System row, and that row blocks the second. With a working run log, two in a row already ran on the pre-fix head (`test_two_raw_commands_in_a_row_both_run_and_persist[available]` passes there).

**Fix.**
- The store's `local_command_anchor_leaf` walks up from the active leaf past unsaved SYSTEM rows only, as saved replies already thread past such rows (`_nearest_persisted_ancestor_id`). The wiring passes it through `raw_cli_anchor_callables`.
- An unsaved USER or ASSISTANT row (a reply still in flight) stays the anchor, so the command is refused rather than filed under the turn before it.

**Tests** (`Tests/Chat/test_console_raw_cli_persistence.py`, real store, real AgentRunsDB, the wired anchor pair):
- `[unavailable]` two in a row.
- Stop refusal, then Clear, then the command runs and persists.
- A lineage control: the second command is filed under the later answer, and on reopen the order is q1, a1, raw, q2, a2, raw.
- An in-flight reply still refuses.
- All three were red on 15d356dd41 with the live message. 51 pass on the fix.
- Mutations:
  - no walk: 3 red.
  - walking past any unsaved row: the in-flight control goes red (the command ran under q3).
  - wiring reverted to `active_leaf`: 3 red.
