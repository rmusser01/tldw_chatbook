## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The system-prompt note for a named workspace (`workspace_context_note`) lists bound folders relative to the app's launch directory and adds a `Launched from:` line. A folder outside the launch tree is shown by its last name only. No file tool resolves paths that way: the fs_*/git_* tools resolve paths relative to the bound folder itself, chosen by a per-binding `root_alias` the note never mentions, and the opt-in read_file/list_directory/write_file tools resolve relative paths inside the chat's private scratch space.

Live evidence (gpt-4.1-mini, new chat in a UI-created workspace): the model's first calls were `fs_list {"path":"myproj"}` -> `not a directory: myproj` and `fs_read {"path":"myproj/README.md"}` -> `file not found`, exactly the paths the note gave it. It recovered only by guessing `"."`, which works only when one folder is bound.

Regression: the note shipped in 08067c54ac (2026-08-17) when fs_* tools were rooted at the launch directory, so it was correct then. 180fefc29d (2026-08-23, private scratch) and e62ae7c6dc (2026-08-30, per-binding admitted roots) changed what tool paths mean and never updated the note. Existing tests pin the note's text only for folders inside the launch directory and never check that a named path works in a tool call.
<!-- SECTION:DESCRIPTION:END -->
