## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The system-prompt note for a named workspace (`workspace_context_note`) lists bound folders relative to the app's launch directory and adds a `Launched from:` line. A folder outside the launch tree is shown by its last name only. No file tool resolves paths that way: the fs_*/git_* tools resolve paths relative to the bound folder itself, chosen by a per-binding `root_alias` the note never mentions, and the opt-in read_file/list_directory/write_file tools resolve relative paths inside the chat's private scratch space.

Live evidence (gpt-4.1-mini, new chat in a UI-created workspace): the model's first calls were `fs_list {"path":"myproj"}` -> `not a directory: myproj` and `fs_read {"path":"myproj/README.md"}` -> `file not found`, exactly the paths the note gave it. It recovered only by guessing `"."`, which works only when one folder is bound.

Regression: the note shipped in 08067c54ac (2026-08-17) when fs_* tools were rooted at the launch directory, so it was correct then. 180fefc29d (2026-08-23, private scratch) and e62ae7c6dc (2026-08-30, per-binding admitted roots) changed what tool paths mean and never updated the note. Existing tests pin the note's text only for folders inside the launch directory and never check that a named path works in a tool call.

## Implementation Plan

RED: an end-to-end contract test through the real first-request plan, a real registry/session/admitted roots and a real LocalToolProvider with its real worker: every alias the fs_* schema advertises must be named in the note next to its folder, and `fs_list` with that alias and "." must list the folder.
2. Rewrite `workspace_context_note` in the tools' own terms (alias -> folder name [access], paths relative to the folder) and drop the launch-directory framing.
3. Feed it the aliases the run's offered path tools actually accept (new `path_root_aliases()` on LocalToolProvider and VirtualCliProvider) and the offered built-ins whose relative paths land in scratch; build the note after the final allow-list.
4. Move the tests that pinned the launch-relative format to the new contract.

## Implementation Notes

The note now reads `  - <root_alias> → <folder name> [read-only|read-write]` under a header that states the addressing rule ("pass root_alias ... and a path relative to that folder; "." is the folder itself"). It never carries an absolute path and no longer mentions the launch directory (`_relativize_root` deleted; `set/get_launch_cwd` stay for Console @-references).

`build_console_first_request_plan` now builds the note after `plugin_tool_ceiling`, passing `path_tool_aliases` (union of the aliases advertised by the local fs_*/git_* provider and `virtual_cli`, only for providers whose tools survived the allow-list) and `scratch_relative_tools` (offered `read_file`/`list_directory`/`write_file`, from the new public `SCRATCH_RELATIVE_PATH_TOOLS`). A working-folder selection that narrows the run's admitted roots therefore narrows the note too; with bound folders but no path tools the note says exactly that.

Evidence: 8 new contract tests in `Tests/Chat/test_console_workspace_folder_note_contract.py` (one/two folders x inside/outside the launch dir, narrowing, no path tools, scratch sentence) were RED on dev for the bug itself (alias absent; "launch directory" present) and are GREEN. 24 tests in `Tests/Tools/test_workspace_file_roots.py`, `Tests/Chat/test_console_ssh_composition.py` and `Tests/Chat/test_console_turn_execution_context.py` were moved from the old format to the new one, keeping their protections (no absolute path, no `..` chain, whitespace collapse); the launch-label double-slash test was deleted with the label. Three failures in those files (`test_all_consumers_share_validation_and_write_prefilters`, `test_change_review_gates_precede_binding_validation`, `test_workspace_note_reaches_system_prompt_on_fence_protocol_endpoint`) fail identically on a clean origin/dev 2d34cbf80d worktree (sandboxed-config environment failure), not on this change.
