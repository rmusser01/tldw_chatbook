## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** Measured at 160x45 with 100-150 ms polling:
- After Enter, nothing changes for 0.44-0.66 s.
- The composer then clears to its placeholder, showing 'Send disabled: type a message', while the Send button still reads 'Send'.
- For the next ~1.1-1.9 s every status surface stays idle: header 'Ready', no tab '●', no Run chip, rail row unchanged. The transcript still says 'No messages yet.' on a first send or a new Ctrl+T tab.
- The user row first appears 1.8-3.2 s after Enter.

The store has the echo much earlier: durable_commit succeeded at about 760 ms, so the gap is in rendering, not admission. The J5 profile log shows a 2.9 s synchronous admission on a cold send, so longer gaps are plausible.

Consequence, verified: retyping the prompt and pressing Enter 0.9 s into the gap created a queued duplicate that auto-dispatched. The result was two identical user rows, two replies and two paid provider calls.

**Severity / prior art.** P1, confirmed by all three verifiers. This is a **REGRESSION of TASK-351 (Done, AC#1**: 'echoes the user's message ... the instant the submit is accepted ... closing the composer cleared but transcript still says No messages yet gap') and of **TASK-457 (Done, AC#1**: cold-send optimistic echo). The acceptance-time echo was removed in b7dd8e53f2. TASK-485 (Done) already provides a transient-echo rollback. Raw admission latency stays with the PERF series; this task is about acknowledgement.

**Suggested direction.** Paint the pending user row, marked 'Sending…', and flip the header, tab marker, Run chip and Send control directly from the key handler or the runtime accept return. Do this before the synchronous admission work, not on the whole-screen sync tick. While a turn is pending, suppress the empty-draft reason, and key the empty state off 'no messages and no pending send'. Roll the row back with an inline error if admission or commit fails.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Enter now puts a "Sending…" acknowledgement on screen before the send's admission work runs: the user row marked "Sending…", a Running header, the tab dot, "Run: Sending…" and a disabled "Sending..." Send button. The send itself is unchanged and starts once that frame is drawn. A per-tick control-bar restyle was also removed. This makes a send feel faster; it does not make it run faster. The 0.25-1.0 s synchronous admission on the UI thread is still there and stays with the PERF series.

**Measured on dev 7d155170dc first** (live, Anthropic claude-haiku-4-5 via the review proxy, tmux frame polling; mounted harness with the app's eager task factory and a main-thread stack sampler):
- Enter → composer blanked: 946 ms (first send), 458 ms (warm), 800 ms (new tab) at 160x45; 592 ms at 80x24; 378 ms at 235x52. In those frames the header still read Ready, the transcript said "No messages yet." and the composer said "Send disabled: type a message".
- Enter → user row and status surfaces: 2155 / 1831 / 1669 (row 3131) ms at 160x45; 1089 ms at 80x24; 1010 ms at 235x52.
- Causes: (1) Enter's send ran its synchronous admission (`_build_console_turn_execution_context`) on the UI pump before anything was painted; (2) nothing acknowledged the send before that work; (3) the row and status surfaces only reached the screen through the 0.2 s whole-screen sync tick; (4) every tick `ConsoleControlBar._set_recovery_height` removed and re-added its height class, re-applying CSS to the whole bar (20-108 ms per settled tick).

**After (final build, live, same recipe):** 9 of 9 sends (80x24 first and two warm; 160x45 first and two new tabs; 235x52 first and warm) showed the row, "Sending…", the Running header, the tab dot and the Run chip in the first changed frame, 31-78 ms after Enter. No frame had an empty composer under an idle header with no row, and "Send disabled: type a message" never appeared while the send was pending. Settled-tick cost in the harness: control-bar sync 32-115 → 12-15 ms.

**Cost.** In the mounted harness the send starts 34-53 ms after Enter (dev: 1-5 ms) and admission starts 78-132 ms after Enter (dev: 66-172 ms). That is the paint (~20-30 ms) plus a wait of one to a few frames for the frame to be drawn.

**Approach.**
- `UI/Console_Modules/send_acknowledgement.py` (new; imported on the first Enter only, so the UI-ready census stays at 1033/1033): a per-session, view-only acknowledgement. Nothing writes the store, the runtime or the durable turn, so durable acceptance and the trace pipeline are untouched. Only an idle session's chat draft is acknowledged. A typed `! ` local command, a slash command, an empty draft, a live run or queue, and a send behind a Blocked turn (TASK-33621.2) keep their own surfaces. A pasted `! …` or `!important` is chat; an escaped `\! ` row shows the text actually sent.
- The synthetic row is projected into the transcript until the store's own echo appears. It is released when the dispatch admits no turn, or when the runtime's custody of the admitted turn ends without an echo (terminal callback on `accept_turn`). Admission binds to the Enter whose send is running (a ContextVar copied into a hook review's worker), so an earlier turn can never mark a newer Enter's row admitted.
- Hand-off: the paint relabels the tabs, then mounts the row; the send is handed to the app pump after one refresh plus frame-length timer hops until the row and Run chip have a region (at most 6 frames).
- Every later sync derives the same facts: `_console_active_run_copy` (Blocked copy first, then "Sending…"), `_console_run_active` (its own check: image edit, an active run status, or an acknowledged send; a Blocked turn is never run-active), the hidden mode-bar copy (now read from the Run chip copy), the prompt-queue presentation (`sending` → "Sending..."), the tab-marker overlay and the transcript projection.
- `ConsoleControlBar._set_recovery_height` touches classes only when they change.
