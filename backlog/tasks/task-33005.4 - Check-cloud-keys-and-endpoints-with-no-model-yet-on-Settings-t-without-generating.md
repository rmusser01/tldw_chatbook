## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This implements owner decision D2, which settles C3's labelling question. The ADR-012 amendment of 2026-09-26 (drafted in this worktree with the spec) already states the rules and the outcome table; this task makes the code match it.

Today 'Test Provider' ('t') never contacts a cloud provider. _provider_live_probe_base_url returns "" outside URL_BASED_PROVIDER_KEYS (settings_screen.py:15343-15363; the action is at :30793-30830). So a fake OpenAI key reads 'OpenAI configuration is complete. Credential is present; provider acceptance has not been tested.' (:15246-15251).

That behaviour was deliberate and is pinned:
- TASK-191, and TASK-386's visible guidance (settings_screen.py:16926-16941).
- Tests/UI/test_settings_configuration_hub.py:4622 test_settings_provider_test_skips_probe_for_cloud_providers.
- The toast copy pins at :3778 and :4653.

The local half: `passed = bool(readiness.ready and model)` (settings_screen.py:15238) gates the live probe (:30802), so a URL-based provider cannot be probed until a model is typed. Listing the server's models is exactly how a first-timer would find one (report persona Jordan: 'Test is blocked until a model ID is typed').

The seam already exists:
- LocalLLMProviderCatalogService.discover_models resolves saved or staged draft credentials and endpoints (local_llm_provider_catalog_service.py:481-613).
- The discovery client sends the provider's auth header, including Anthropic's x-api-key (openai_compatible_model_discovery.py:165-186), and maps 401/403 to rejected credentials (:726-737).

Eligibility is decided by supports_openai_compatible_model_discovery (:392-422). Anthropic is not in the base-URL-inferable set (:52-69), so whether its shipped endpoint qualifies must be proven, not assumed.

The amendment requires the check to use the endpoint and credential the spend path would use. Two open tasks bear on that and are not absorbed: TASK-2117 (the send path drops api_base_url for most providers) and TASK-2523/TASK-2524 (readiness and spend credential lookups diverge).

Other constraints:
- ADR-002: discovery persistence stays manual.
- ADR-020: consent must not be recorded through a Settings action.
- TASK-30014 AC#1: providers with no non-billable check must say so.
- TASK-32806.1 owns the placeholder-key validity rule; it is not absorbed here.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Settings 't' now checks a cloud provider's key with one explicit, non-generating model listing, and lists a URL-based provider's models before a model is chosen (ADR-012 amendment of 2026-09-26, owner decision D2).

Approach:
- Cloud key check (AC#1-#10): `_provider_key_check` calls the app's `llm_provider_catalog_scope_service.discover_models(mode="local", use_shared_cache=False)`, i.e. the real `LocalLLMProviderCatalogService` and discovery client, with staged settings holding the endpoint `effective_provider_endpoint` resolves for the draft and the key `_provider_current_draft_credential` resolves (the same key the evidence identity digests, Task 2 review I-1). Nothing is cached, saved or consented. It runs in the existing `settings-endpoint-probe` worker (exclusive), begun and settled through the draft store, so a reply for a changed draft or an earlier run is dropped (AC#13) and settled evidence reaches the shared owner (AC#12).
- `key_check_probe_result` (settings_endpoint_probe.py) maps the result: listed + key sent -> `key_accepted` ("Ready · verified HH:MM"); 401/403 with a key -> unreachable unauthorized/forbidden ("Not ready · key rejected"); timeout/refused/connection error/other status keep their category ("timed out", "refused", ...); a 404 or unreadable list -> model_listing_unavailable (key not checked, no send blocker); a refusal before any request (unsupported endpoint, no `[providers]` list, settings problem) -> no evidence and a "Key check" row saying why. Evidence keeps at most 100 model ids (the existing bound), with the chosen model kept first so the Model row never calls it unlisted; the count reads "100+" past the bound.
- Discovery client: `ModelDiscoveryError.category` (new optional field, default None) carries the bounded category; kinds are unchanged, so the wizard and auto-refresh are unaffected.
- AC#7: the TASK-32806.1 rule via the resolved draft credential: a missing, placeholder or blank key sends nothing, even when an env var would fill in for readiness.
- AC#6: OpenRouter/NVIDIA (`PUBLIC_MODEL_LISTING_PROVIDER_KEYS`) read "models listed; key not checked" and stay "Ready · not tested".
- AC#11: the probe gate is now readiness (configured), not readiness-and-model; the toast reports "Model listing reached (N models listed); choose a default model." and the Readiness row stays "Not ready · no model".
- AC#12 gap fixed: with no endpoint typed or saved, Save's setup mutation had no semantic identity, so a typed key's evidence never carried to the saved connection (Task 1 keyed the built-in endpoint, Save did not). Save now rebases onto the tested identity with draft -> stored in that case.
- AC#17: `PROVIDER_TEST_GUIDANCE` is the tooltip, the visible guidance and the F1 note; the footer verb stays "test provider" (its pins unchanged).

Rulings (recorded in the report):
- A 404 or unreadable cloud listing records model_listing_unavailable, not unreachable: it proves nothing and must not block sends.
- No egress pre-check on the cloud listing: it is the manual Discover path already used, and the key goes only where a send takes it.
- Subscription (Claude Code login) auth gets no key check: the token is not an API key the discovery client should send.
