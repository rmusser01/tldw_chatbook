## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Library's pane frames paint $ds-column-line ($surface-lighten-2), which TASK-33003.6 did not cover (its ACs name the grid-line and control-edge boundaries). They measure 1.28:1 at origin/dev and on the Phase 3 branch, below the WCAG 1.4.11 3:1 floor for component boundaries. Found in TASK-33003.6 review round 1 (F7).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Library pane frames measure at least 3:1 against surface and panel on every shipped theme whose colours resolve, gated by a test in the style of Tests/UI/test_theme_contrast.py.
- [x] #2 A live 211x44 capture of the Library screen records the measured ratios in the task notes.
- [x] #3 The Workflows library and navigator pane edges, which share the Library frames' line token, measure at least 3:1 against the fill they sit on, and text painted straight on that fill reads at least 4.5:1, on every shipped theme whose colours resolve. A rule test and a rendered test gate it. (Added in review round 2: the token change took those edges to 1.32:1 on litestep.)
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Add the gate first, in the style of Tests/UI/test_theme_contrast.py: `$ds-column-line` and each Library pane-frame rule against surface and panel, on every measurable theme.
2. Point `$ds-column-line` at the guard-pinned `$tldw-boundary` and rebuild the generated sheets.
3. Measure the live Library screen at 211x44 on a scratch profile.
4. Review round 2, AC#3: failing tests first (a rule gate and a rendered one) for the Workflows pane edges, then give both panes a pinned fill, measure the text that fill now sits under on every theme, and rebuild the split sheet.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Library's pane frames now read at 3:1 on every measurable theme.

**Fix.** `$ds-column-line` resolves to `$tldw-boundary` (css/core/_variables.tcss), the colour the theme guard already pins to 3:1 on surface and panel for `$ds-grid-line` and `$ds-control-edge`. It was `$surface-lighten-2`. No Library rule changed: `#library-shell-grid`, `#library-rail`, `#library-file-notes-rail` and `#library-canvas` still say `border: solid $ds-column-line` on `$ds-surface-panel`.

**The token is shared, so every other user moves with it.** The pane frames and section rules paint on a `$surface` or `$panel` fill, which is what the gate measures:
- Home: `#home-triage-grid`, `#home-rail`, `#home-canvas` (panel).
- Console: the rail section rules `.console-rail-section-header` (surface) and `.console-workspace-conversations-header` (the rail's panel); the context tray, session, workspace and run-inspector frames (panel).
- Settings: `.settings-instant-apply-group` and `.settings-secondary-card` (panel).
- Lab: the `#lab-rail` right edge (panel).

One user is not a frame on a pinned fill, and no gate covers it (review round 1 corrected this; the notes first said every user sat on `$surface` or `$panel`):
- The Console transcript separator `.console-transcript-rule` (features/_console.tcss) is a text and hatch ink, not a frame. It sits on the transcript region's panel fill, so by the same token it becomes a 3:1 line between messages; it is never weaker than before on any of the 89 themes. It was resolved from the token, not captured live for this rider.

**Workflows pane edges (AC#3, review round 2).** The Workflows library and navigator right edges (features/_workflows.tcss) set no fill, and nothing above them did, so they sat on `$background`, where no line colour is pinned (the TASK-33641.1 nav-bar ruling). The token change therefore made one theme worse: litestep fell from 3.64:1 to 1.32:1, and five more shipped themes stayed under 3:1 (apricot 2.63, frutiger_aero 2.71, cloudy_day 2.72, palm_mall 2.83, parchment 2.99). Round 1 recorded that as a proposal for a later rider; round 2 fixed it here under a new AC.
- Fix: `WorkflowLibrary#workflows-library` and `WorkflowNavigator#workflows-navigator` each set `background: $ds-surface-panel` and `color: $ds-text-primary`. The panes are now panel rails, as the Library, Home and Lab rails are. Only the Workflows split sheet (`screen_feature_workflows.tcss`) was rebuilt; the boot bundle is unchanged.
- Why the `color`: the fill that fixes the edge also sits under the two pane headings ("Workflow library", "Step navigator"), which inherited the theme's `$foreground`. With the fill alone, that text fell under 4.5:1 on five themes where it had passed on `$background`: atom-one-dark 6.57 to 3.45, tokyo-night 8.10 to 4.23, solarized-dark and solarized_dark 4.75 to 4.11, solarized-light 4.99 to 4.39. `$ds-text-primary` is Textual's auto ink, worked out against the fill under it.
- Measured after the fix, rendered under the production stylesheet at 211x44 on all 89 measurable themes: edges are 3.02:1 or better (sweet_sorbet lowest; litestep 3.13:1, textual-dark 3.05:1), and text straight on the pane fill is 5.90:1 or better (catppuccin-frappe lowest). Before this task four themes read that heading under 4.5:1 (pastel_dreams 2.53, bunny_fluff 3.39, solarized_light 4.13, sweet_sorbet 4.29).
- Against the task base, litestep's edge is 3.13:1 where it was 3.64:1: above the floor, and the only theme lower than at base. textual-dark is 3.05:1, from 1.75:1 at base (round 1 alone gave 4.18:1 on `$background`).
- What it looks like: on every theme the two rails' gutter columns, heading row, pager row and edge column paint `$panel` where they painted `$background`. The lists, the search field and the buttons keep their own fills. This is a visible change nobody had seen before it was made; the Capture phase should show Workflows on litestep and on the default theme.
- Tests, Tests/UI/test_theme_contrast.py: `test_workflow_pane_edges_clear_non_text_contrast` (89 themes: each pane rule's `border-right` token against the fill the same rule sets) and `test_workflow_panes_paint_readable_edges_and_text` (rendered, 9 themes: the edge cells and the text cells read from the frame). Red first: 91 failed with no fill (89 "sets no background", plus litestep 1.32:1 and apricot 2.63:1 rendered); with the fill alone, 5 failed on text. Green: 98 passed. Negative controls on the built sheet, each restored by a rebuild: without `color`, 5 failed; without `background`, 2 failed; the navigator rule alone without either gives the same failures, named `#workflows-navigator`.
- Live, the real Workflows screen at 211x44 (tmux on its own socket, `env -i`, HOME, XDG and TLDW_CONFIG_PATH in scratch, null keyring, `capture-pane -p -e` parsed): on litestep both pane edges (34 cells each) paint (114,114,112) on (212,208,200), 3.13:1, and both headings (27,27,26) on the same fill, 11.21:1; on textual-dark the edges are (119,119,119) on (36,47,56), 3.05:1, and the headings (226,227,229), 10.63:1. Those are the figures the rendered test gives. No capture is committed; the real profile was unchanged before and after.
- The Workflows screen's own tests cannot be measured plainly on this machine (they raise `RecoveryRequired` without an isolation marker). With a scratch plugin that stamps `bootstrap_profile`, for comparison only: test_workflows_editor.py, test_workflows_paging.py and the Workflows nodes of the two destination files gave 3 failed, 86 passed at this head and at the round's base, the same three names (a "Run unavailable" copy assertion from other work).
- `_rule_token` in that file now reads a declaration that follows a `;` on the same line (`_workflows.tcss` writes one rule per line).
- Docs: Docs/User_Guide/workflows.md (the rails), backlog/docs/design-language.md (a pane that carries a line sets its own fill, and text on it takes the readable ink).

**Gate (AC#1)**, Tests/UI/test_theme_contrast.py, 89 measurable themes (70 shipped, 19 built-in):
- `test_library_pane_frames_clear_non_text_contrast` (new): reads each Library frame rule's border token from features/_library.tcss and resolves it through `_variables.tcss`, then asserts 3:1 on surface and on panel.
- `test_boundary_tokens_clear_non_text_contrast_on_every_theme`, `test_user_saved_themes_get_visible_boundaries` and `test_user_theme_with_any_kept_variable_form_still_loads` now also measure `ds-column-line` (through `_assert_boundaries_visible`), so saved user themes are covered.
- Red before the fix: 182 failed (89 + 89 + 4 user-theme nodes), for example "zero_day_stealth: ds-column-line #393940 is 1.51:1 against surface #1A1A20". Green after: 781 passed.

**Live (AC#2).** tmux, 211x44, scratch profile (HOME, XDG and TLDW_CONFIG_PATH in scratch, null keyring), default theme textual-dark, Library opened from the top tab, `capture-pane -p -e` parsed as one stream. - Ruling: change the token, not the three Library rules. Why: all but one user of `$ds-column-line` is a pane frame or section rule under the same WCAG 1.4.11 floor (the transcript separator is an ink, above), and TASK-33641.1 names the Console rail rules among them. Cost if wrong: a surface that wanted a quieter line (the transcript separator is the likeliest) needs its own token. A user of the token that sets no pinned fill is the other cost: the Workflows panes, fixed above.
- Ruling (review round 2): fix the Workflows edges here, under AC#3, instead of filing a rider. Why: the regression is this rider's own, the owner's rule is that no finding is deferred, and the change follows the rails that already exist. Cost if wrong: the owner has not seen the panel rails; removing `background` and `color` from the two rules puts the old paint back and the two new tests then fail by design.
