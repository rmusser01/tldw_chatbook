## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.5. The post-UI-ready pre-import pass now imports the Console's first-send modules (about 213 ms CPU, paced 1:1 and 3:1 on low-core hosts) before the speculative screen routes, and the warm-up parks while a navigation or accepted Console work owns the loop. So the screen routes start a few hundred ms later, and a send in the first second after UI-ready defers every speculative screen import until that run settles. The latency of the first navigation after boot was not measured on either arm, so a regression there would go unseen.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The branch's first order (warm-up, then the screen routes) made the first navigation about a second after launch slower; the warm-up now runs after the last route, and at the sampled times no first navigation, keystroke or first send is worse than on origin/dev. Input during the warm-up's own window is unmeasured (TASK-33620.15.18).

Method. Live, paired and interleaved: origin/dev 2d071d6d71 against the branch, both arms launched side by side per cell (launch order alternating) through uxrev/launch.sh, 160x45, Anthropic haiku via the review proxy, established isolated profiles (catalog consent recorded), 8 launches per arm per cell. A PYTHONPATH-only probe (sitecustomize in scratch worktrees) recorded the key or click as the app's driver thread received it, the first frame written for each new screen class, every ScreenRoute.load_screen_class with its thread, ConsoleComposerBar.insert_text, and UI-loop callbacks of 8 ms or more. Each action is timed from that arm's own first Console frame. Latency = the destination's first frame minus the input's arrival.

Round 1, origin/dev vs the branch head eef1cffc34 (warm-up first). Medians dev / branch, paired median, branch better:
- Library click at 1 s: 356 / 451 ms, paired +39 ms, 3/8. Library was cold at the click in 8/8 branch launches and 0/8 dev launches; the click imported about 198 modules on the UI loop (load 121-247 ms) against 36.
- Library at 3 s 176 / 171; at 6 s 183 / 174. F4 Settings at 1 s 357 / 338 (cold on both arms, 7/8 and 8/8), at 3 s 177 / 177, at 6 s 183 / 185.
- One key at 1.5, 2, 3, 4 and 6 s: key to next frame 3-5 ms on both. At 0.5 and 1 s it is boot work (300-380 and 35-111 ms), the branch not worse.
- The send cell (prompt typed at 0.5 s, Enter at 1 s, Library at 3 s) is void for the branch arm: the typed prompt landed in 1 of 8 branch launches (6 of 8 dev), so most branch launches never sent. See the key-loss finding below.

Change (2386c75dc6; measured live as 5735974f63, its pre-rebase commit with an identical code patch): TldwCli._preimport_heavy_screens runs the routes first, then the warm-up. The warm-up parks before every import (so a send that starts as the routes finish imports what it needs itself) and pauses for the previous import's cost x ratio, then parses the manifest and freezes the heap again (ADR-198), since the routes' freeze ran before it. Option chosen: the one the owner named (after the screen routes). Interleaving was not needed.

Round 2, origin/dev vs 5735974f63 (warm-up after the routes; the same code as 2386c75dc6), new established profiles for both arms:
- Library at 1 s: 366 / 393 ms, paired -18 ms, 4/8; cold 0/8 on both. At 3 s 175 / 172 (paired -6), at 6 s 186 / 186.
- F4 Settings at 1 s 375 / 370 (+6, cold on both), at 3 s 179 / 181, at 6 s 180 / 179.
- Send at 1.5 s (prompt typed at 1 s, landed 8/8 on both arms), Library at 3 s: 424 / 360 ms, paired -35 ms, 7/8; Library warm on both.
- One key at 0.5 s 374 / 317 (-34), 1 s 134 / 106 (+16), 1.5-6 s 3-5 ms on both.
- First-send gains kept, on moderate evidence (probe-free round, a timing hook only; fresh profiles, 12 s idle after ready, so after the pass had finished; 2 sends per launch, 8 launches per arm): Enter to provider POST, first sends 2,272 / 2,326 ms medians (the unpaired medians favour dev by 54 ms), paired -200 ms, 6/8 earlier, Wilcoxon signed-rank p about 0.08 (TASK-33620.15.5's timing7, warm-up first, measured -333 ms, 8/8); later sends 1,777 / 1,700, paired -37 ms, 4/8.
- The warm-up's own window was not sampled: on established profiles it starts a median 1.9-2.4 s after the Console's first frame and lasts about 0.3 s, and none of the 656 inputs on the fix arm landed inside it. Filed as TASK-33620.15.18.

Key-loss finding (not a regression; filed as TASK-33620.15.17). A 29-character prompt typed 0.5 s after the Console's first frame is sometimes lost whole: the nav bar's Home button holds the initial focus until ChatScreen._restore_console_workbench_focus runs from the screen's idle callback (0.1-2.5 s after the first frame), and keys dispatched before then fail _should_capture_console_input. On reused profiles the arms differed (dev 18/22 landed, branch 7/22 in the first three batches), but those profiles had diverged: an arm whose bursts landed carried a restored draft into later launches. On fresh seeded profiles per launch the arms matched: 7/10 landed on each, composer focus median 1.18 s dev, 0.64 s branch. A single key at 0.5 s landed in all 32 launches.
