## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-33620.15.17's arrival window (keys typed before the composer's first focus land in the draft) ends at the first focus change. On a path where the activation restore never moves focus, a later printable key typed on the untouched arrival widget, such as a nav button left focused after an explicit Resume, is still claimed for the draft, possibly long after arrival. Low risk and in line with the restore's intent, but the window should be exactly 'before the restore lands'. Clearing it at the end of the restore itself is not enough: keys already queued ahead of the restore's deferred focus() would then be dropped again (found in the TASK-33620.15.17 review).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The window ends once the activation restore has run and its deferred focus has landed, whether or not focus moved
- [ ] #2 Keys queued ahead of the restore's deferred focus still land in the draft, in order
- [ ] #3 A printable key typed on an untouched arrival widget after that point is not claimed
