## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This is a rider from the TASK-33001.13 hotfix review (PR #2847), traced in code but not reproduced live.

**How it happens:**
- At load time, the runtime copies a legacy `[API] <provider>_api_key` value into `api_settings.<provider>`, and only when that provider's env var is unset (config.py:1735-1752).
- Settings sees that key as stored. Since #2847, a model-only save records `credential_source = "stored"` and keeps `api_key` untouched instead of rewriting it.
- The key only ever lived under `[API]`, so the `[api_settings.<provider>]` table on disk then says "stored" but holds no `api_key`.
- If the env var is exported later, readiness reports no key (the stored source has nothing to read), while actual requests use the env key.

Before #2847, dev saved "environment" and deleted the key, so this is strictly better. The two views can still disagree, though, which is what ADR-012's single credential lookup is meant to prevent.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A Settings save that records "stored" for a key the loader copied from legacy `[API]` now writes that key into `[api_settings.<provider>]`. Readiness and the send path then resolve the same stored key whether or not the provider's env var is exported.

The premise holds at 10fead87cb. The new Settings test, run before the fix, failed at the comparison made after the env var was exported: readiness resolved no key while the send path still held one (`At index 0 diff: None != 'sk-settings-legacy-api-canary-33001'`; pytest shortened the send-path value to `'sk-se...canary-33001'`, which by the loader's order is the env key).

What changed:
- `config.py`: `_normalize_legacy_provider_api_key` reports each table it fills from `[API]` through a new optional `bridged_from_legacy` set, and the loaded settings carry the names as `legacy_api_key_providers` (a tuple, always present, never a key).
- `Chat/provider_setup_persistence.py::build_provider_setup_mutation`: in the kept-key branch (`keep_stored_credential`, no typed value), a table named in `legacy_api_key_providers` gets its key written. Every other table is handled as before.
- `settings_screen.py` is not edited; its call is unchanged.
- ADR-012 has a 2026-10-10 amendment with the rule, and `Docs/User_Guide/settings.md` says in the API key row that the first save copies a legacy `[API]` key into the provider's table.

Rulings:
- Ruling: the loader reports where the key came from, and the builder reads that from the settings it is handed -- why: the loaded settings do not carry `[API]`, the builder does no I/O, and the TASK-33001.13 test pins that a key the table already holds stays out of the write, so the builder must tell the two apart exactly -- cost if wrong: one more top-level key in the loaded settings; a caller that builds settings by hand without it gets the old behaviour.
- Ruling: a copied key the setup validator would refuse (over 8192 characters, or with control characters) is not written, and the save still succeeds -- why: writing it would fail the whole save, which is the failure TASK-33001.13 removed -- cost if wrong: for such a key the table still says "stored" without holding it.
- Ruling: the `[API]` entry is left in place -- why: the rider asks for the key to reach the provider's table, not for a migration, and removing a user's line is a separate decision -- cost if wrong: the key stays in two places in config.toml.

Known property: the list is made at load. After a save in the same session it still names the table, so a later save in that session writes the table's current key again, unchanged. The in-memory settings follow each save, so the value written is the one on disk.
