## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while measuring TASK-33628.5 (ConsoleHarness + file-backed DB, branch fix/task-33628.5-delete-off-ui-thread). With a conversation holding 3,000 messages on a branch that is not on the active path, so the transcript shows four rows, merely arming a Delete (a status-only Console sync, no database write) blocked the event loop for 0.20-0.84 s at its worst and 0.64-1.55 s in total across three runs. After TASK-33628.5 the Delete and Undo themselves cost about 25 ms on the loop at that size; the 0.1-0.46 s loop blocks that remain around them are this same sync (_sync_native_console_chat_ui at 0.19-0.62 s per call; stack samples put most of it in _sync_console_rail_and_controls / _run_console_config_sync and compositor renders). The figures above came from a throwaway probe that was not committed; TASK-33628.5's notes record the loop-block ranges around Delete and Undo measured on both arms after that task (n=6).

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Measured first (ConsoleHarness 160x48, file-backed DB, branch = dev + TASK-33628.5; earlier probe logs reused): with the 3,000 messages off the active path the sync's Python call count and profiled wall time match the 0-message session (290k call events either way; 1.35 s vs 1.29 s over 5 profiled syncs), so nothing grows with them. The floor is constant waste: the control bar removes and re-adds its unchanged height class every sync (two restyles of the bar, 110 nodes), the Send reason strip, voice chip and attachment indicator do the same, and the settings summary runs four screen-wide queries for four rail labels, each walking every mounted transcript row.
1. Tests first (red on the pre-fix branch): an idle post-action sync restyles nothing and walks no transcript node; with a Delete armed, one sync's restyles, transcript walks and store snapshots are identical with and without 3,000 off-path messages, and the first two are zero.
2. Make the height/size class swaps idempotent (change classes only when they change).
3. Move the Model-section label writes into the Context rail and look them up there by id.
4. While measuring, also cut what the sync pays per active-path message (5.1's Undo lands on a 3,000-message active path): store snapshots copy fields directly instead of re-running the dataclass __init__, and the continuation-recovery lookups scan live rows and snapshot only the match.
5. Session 2 (re-measured on the branch, GC off, 3,000-message active path): the largest per-message cost left in a sync is context_control_inputs, run twice per sync, each reading every active-path message's durable version from SQLite on the loop and building 3,000 validated lineage snapshots (~19 ms of ~29 ms per call). For a conversation with no rewind summary and no active memory selection the answer is always raw history, so check that first (one indexed query) and skip the lineage capture; conversations holding memory keep the full path. Pinned by counting lineage captures in an idle sync (red on the pre-fix branch: 2).
6. Re-measure arming a Delete at 0 and 3,000 off-path messages on both arms (n=3 each).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: an idle post-action Console sync now restyles nothing, walks no transcript row, and reads no lineage for a chat without memory. With a Delete armed, the sync does the same work with and without 3,000 off-path messages. The per-message store costs a 3,000-message active path paid on every sync are cut.

Approach (commits 6dae46e407, e586478e36, ef4c1515cf; tests 18a32d8e29 plus the unit files below):
- Idempotent size classes: the control bar's height class, and the size classes of the Send-reason strip, voice chip and attachment indicator, change only when they actually change. Before, each sync restyled the bar twice (110 nodes).
- Scoped lookups: ConsoleLeftRail.sync_model_section_values writes the Model section's sampling values and readiness word (ChatScreen hands it the summary), and the source-readiness card is looked up inside the right rail. The four screen-wide queries they replace walked every mounted transcript row on every sync. The timer-path inventory rows follow the moved writer; the head reports strictly fewer timer-path findings than the base.
- Store:
  - Snapshots copy the message fields directly (copy_console_message) instead of going through dataclasses.replace (~16 us per message). This is exact while ConsoleChatMessage has no __post_init__ and no init=False field, pinned by Tests/Chat/test_console_message_copy.py.
  - The continuation-recovery lookups scan the live rows and snapshot only the match.
  - The Library activity footer counts come from one pass that groups rows by turn (count_library_activity_by_turn), instead of a projection per active turn: 1,500 projections for a 3,000-message chat, quadratic. Pinned by Tests/Chat/test_library_activity_projection.py.
- Memory presence: context_control_inputs runs twice per sync. Each call captured the whole active lineage to prove which memory applies: one SQLite version read and one validated snapshot per message, ~19 ms of each ~29 ms call at 3,000 messages. may_hold_branch_memory now skips that capture when there is no usable /rewind summary and no active selection row (ConsoleContextRepository.has_active_memory_selection, one indexed LIMIT 1 query). A repository double without the real API keeps the full path. Pinned by Tests/Chat/test_console_memory_presence.py, and by a UI positive control where an active selection event brings the capture back.

AC#2: with 3,000 messages off the active path, the pre-fix sync's call count and profiled wall time matched the 0-message session (290k call events either way). Nothing grew with those messages; the floor was the constant waste removed above. Pinned: one armed-Delete sync's restyles, transcript-node walks and store snapshots are equal with 0 and with 3,000 off-path messages, and the first two are 0. Red on the base, as is the idle-sync pin (0 restyles, 0 transcript nodes walked, 0 lineage captures).

AC#1, measured with the scratch heartbeat probe (ConsoleHarness 160x48, file-backed DB, gc frozen, host load average 20-50):
- Arming Delete with 3,000 off-path messages: max loop gap 28-33 ms on the head (n=3; loop-thread CPU 24-29 ms), 103-205 ms on the base at 0 and at 3,000 off-path messages (n=3 each).
- With the 3,000 messages on the active path, arming Delete takes 0.08-0.11 s on the head and 11.1 s on the base. Interleaved at 60 messages: head 0.06-0.09 s, base 0.14-0.18 s.
- Live arming (370 and 488 on-path messages) logged no stall >= 250 ms. The app's own detector cannot see below 250 ms, so the 100 ms evidence is the probe.

Residual, not in these ACs: with 3,000 messages on the active path, an idle sync still pays ~50 ms that scales with them (store copy ~14 ms, transcript row build and diff ~16 ms, avatar scope check ~8 ms; 4 messages: ~6 ms). It is linear with a small constant and no longer quadratic. Making it proportional to what changed would need a dirty-tracking store API, which is a separate change.
