## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This rider comes from the TASK-33002.12 review round 2 live check. With a hand-edited `[chat_defaults] provider = "custom-ep:gone[/]"` (a dangling registry id whose text is Textual markup), Console's workbench mode strip raises `MarkupError` at startup. The app log names `site_function=_sync_mode_label` (`UI/Workbench/workbench_widgets.py:398`, `label.update(mode.label)`) with `widget_type=ChatScreen`. The app survives only through task-32533's keep-alive, so the strip is left half-painted.

The mode label carries user text (the provider id) into a markup sink unescaped. TASK-33002.12 fixed the same class in Settings; this is the Console sink, which that task left out of scope.

A hand-edited config should degrade to an honest not-ready state, never raise.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The workbench `ModeStrip` (UI/Workbench/workbench_widgets.py) builds its chips with `markup=False`, so a mode label renders as typed. `_sync_mode_label`'s `label.update(mode.label)` follows the widget's own markup flag (`Static.update` visualizes with `self._render_markup`), so the one keyword fixes both sinks the rider named. No mode label relied on markup: all seven come from `ConsoleControlState` as plain strings ("Provider: …", "Model: …", the assistant label, the Library chip, Sources, Tools, Approvals), and `ModeStrip` has no user other than the Console.

The fix is at the sink rather than in `provider_display_name`: the id and an endpoint's `display_name` are user text that other sinks render with their own markup rule, and a dangling id stays identifiable as typed.

Test (new, mounted, private profile, the shipping Console under the production stylesheet at 211x44, config written by the real writer): `Tests/UI/test_console_mode_strip_literal_text.py::test_the_mode_strip_shows_a_markup_like_provider_literally`, two cases:
- `[chat_defaults] provider = "custom-ep:gone[/]"`: the provider chip reads `Provider: custom-ep:gone[/]` (AC#1). Before the fix the harness app died with `MarkupError: auto closing tag ('[/]') has nothing to close` from `workbench_widgets.py` `sync_modes` → `_sync_mode_label`. No other Console sink raised on that config: the harness has no keep-alive, so any MarkupError fails the test.
- a `custom-ep:gpu-box` entry named `GPU [b]box[/b]`: the chip reads `Provider: GPU [b]box[/b]` (AC#2). Before the fix it read `Provider: GPU box` (bold, brackets lost), with no error (AC#3: both red before, green after).
