## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This rider comes from the TASK-33002.12 review round 2 live check. With a hand-edited `[chat_defaults] provider = "custom-ep:gone[/]"` (a dangling registry id whose text is Textual markup), Console's workbench mode strip raises `MarkupError` at startup. The app log names `site_function=_sync_mode_label` (`UI/Workbench/workbench_widgets.py:398`, `label.update(mode.label)`) with `widget_type=ChatScreen`. The app survives only through task-32533's keep-alive, so the strip is left half-painted.

The mode label carries user text (the provider id) into a markup sink unescaped. TASK-33002.12 fixed the same class in Settings; this is the Console sink, which that task left out of scope.

A hand-edited config should degrade to an honest not-ready state, never raise.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The workbench `ModeStrip` (UI/Workbench/workbench_widgets.py) builds its chips with `markup=False`, so a mode label renders as typed. `_sync_mode_label`'s `label.update(mode.label)` follows the widget's own markup flag (`Static.update` visualizes with `self._render_markup`), so the one keyword fixes both sinks the rider named. No mode label relied on markup: all seven come from `ConsoleControlState` as plain strings ("Provider: …", "Model: …", the assistant label, the Library chip, Sources, Tools, Approvals), and `ModeStrip` has no user other than the Console.

Round-1 review found a second sink for the same strings. `ConsoleControlBar`'s eight hidden compatibility Statics (Widgets/Console/console_control_bar.py: the summary line and the provider, model, assistant, RAG, sources, tools and approvals labels) still parsed markup. `_push_console_control_state_if_changed` syncs the control bar before the status chips and the mode strip, and records the pushed state only after them. So on the rider's own config the first push after open raised `MarkupError` at `sync_state`'s `widget.update(label)`, for example when a loaded MCP catalog sets `app.console_mcp_tool_count` (console_chat_controller.py). A switch to an endpoint named `GPU [/]box` raised there too. In the shipping app the keep-alive swallowed the error, so the visible chips and the mode strip never got that state: the rider's "half-painted" strip. Those Statics are now built with `markup=False`, the same rule as the strip, and none of their labels uses markup. The visible status chips already used `markup=False`. AC#1 and AC#2 now hold on every push, not only at open.

The fix is at the sinks rather than in `provider_display_name`: the id and an endpoint's `display_name` are user text that other sinks render with their own markup rule, and a dangling id stays identifiable as typed.

Tests (mounted, private profile, the shipping Console under the production stylesheet at 211x44, config written by the real writer), `Tests/UI/test_console_mode_strip_literal_text.py`, 3 cases. In each, the strip's provider chip and the status strip's provider segment (`ConsoleStatusChips.segment_text("provider")`; the boxed `#console-provider-chip` until dev's one-line strip, TASK-35160) must both read the expected text literally:
- `test_the_mode_strip_shows_a_markup_like_provider_literally[custom-ep:gone[/]]`: `[chat_defaults] provider = "custom-ep:gone[/]"` reads `Provider: custom-ep:gone[/]` at open (AC#1). After open, `app.console_mcp_tool_count = 3` plus a control-bar sync must reach the strip's Tools chip and leave the provider literal.
- `...[custom-ep:gpu-box]`: an endpoint named `GPU [b]box[/b]` reads `Provider: GPU [b]box[/b]`, at open and after the same push (AC#2).
- `test_switching_to_a_markup_named_endpoint_shows_its_name_literally`: opened on llama.cpp, the chat switches (`replace_session_settings`, then `_sync_console_control_bar`) to `custom-ep:gpu-box` named `GPU [/]box`, then gets the same push (AC#2 on a runtime switch).
