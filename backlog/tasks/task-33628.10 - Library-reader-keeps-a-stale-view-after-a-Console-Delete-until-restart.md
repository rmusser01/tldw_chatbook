## Description

<!-- SECTION:DESCRIPTION:BEGIN -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The Library reader now re-checks its loaded transcript every time the Conversations list reads again, and reloads it when the transcript changed. It uses the path the list already uses: a return visit to the reused Library screen runs ScreenResume, then a page request, then apply, then _ensure_library_conversation_reader_selection.

Root cause: _ensure returned early whenever the list record's conversation version matched the loaded one. A message delete, Undo, edit or send never changes conversations.version, so the list re-counted the messages while the reader kept its load.

Fix:
- New module UI/Library_Modules/library_conversation_reader_freshness.py (not a *_controller glob member). ensure_reader_current holds the existing version decision, moved over unchanged. Once per list read, keyed by (conversation id, list request generation) in the new LibraryConversationsState.reader_checked_read field, it starts a re-check of an eligible loaded transcript. The re-check is one bounded read (one message, one character) of the saved message_epoch and message_total. message_epoch hashes the conversation's message row count and version sum, so every reader-visible write moves it.
- If either value moved, the reader reloads through the existing fenced pipeline (_start_library_conversation_reader_selection). Read/Info mode and the Find query are kept.
- A load that _ensure started in the same list read is marked, so it is never re-checked again.
- The re-check is fenced:
  - mounted authority;
  - Conversations row still selected;
  - not in select mode;
  - same loaded id and loaded generation.
- A failed or None read keeps the transcript as it is. The list's own absence check settles a deleted conversation.
- library_conversation_reader_controller.py: _ensure delegates through a local import, so nothing is added at boot. The file went from 976 to 964 lines, and its ratchet row was lowered to 964. library_screen.py is untouched. No schema change. No new diagnostics (the diagnostic inventory is unchanged).

Tests:
- Tests/UI/test_library_reader_console_delete_refresh.py (production TldwCli, real Library + Console screens, real router suspend/resume, real Console store and delete flow, one file-backed ChaChaNotes DB):
  - Delete through More > Delete > confirm > Done, then return to Library: the reader reads 2 of 2 with the surviving rows painted.
  - Delete then Undo, then return: the reader re-read the restored rows (current revisions, new loaded_generation, 4 of 4).
- Tests/UI/test_library_conversation_reader_freshness.py (LibraryHarness with a scripted detail service):
  - no re-check for a load the same list read started;
  - a moved epoch with a moved count reloads;
  - an edit (epoch moves, count same) reloads;
  - an unchanged transcript costs one re-check read and no reload;
  - a re-check overtaken by selecting another conversation never reloads the old one;
  - a failing re-check keeps the load and leaves no failed worker.
- Both files carry bootstrap_profile, pass under the plain command, and were added to scripts/ui_pr_gate_census.txt. The census slice ran serially in CI shape: 73 passed.
- Red on dev: the two new files ran in a detached checkout of the merge base (f0ffcf9e81), with the new module copied in only so the files collect (dev's controller never calls it). 6 of 8 failed for the reported reason. After Delete: reader total=4 while list message_count=[2]. After Undo: the reader still held the pre-delete revisions. After a moved epoch: no reload. The two that passed are restraint guards that hold on dev too. The same 8 pass at head.
- Mutation-checked: dropping the load mark, the supersession fence, the epoch comparison, or the exception guard each fails a test. The first three were re-run before commit, each killed by its named test.
- Two pre-existing tests in Tests/UI/test_library_conversation_reader.py injected a loaded reader state whose message_epoch disagreed with their seeded service. They now carry the service's epoch (epoch-chat-a). Otherwise the first list read correctly reloaded them.

Residuals:
- A list re-read from paging or filtering also costs one bounded re-check read while a transcript is open.
- The reader mounts newly inserted rows at the end (pre-existing _sync_messages behaviour). That is correct for sends and for anything appended. A restore that inserts rows in the middle while the reader already shows the gap is not reachable from Console today, because Undo is only offered before you can leave.
