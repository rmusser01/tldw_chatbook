## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-36511's measurements (2026-11-03), outside the compact gates' window. On first mount, `compose_content` costs 150-190 ms of CPU (mostly deriving inspector state), and the screen-resume CSS pass costs 250-420 ms. `compose_content` is paid once per launch. The resume CSS pass recurs: Textual's `Screen._on_screen_resume` re-applies styles on every resume with `refresh_styles=True`, the default when the user returns to the Console. Both delay a usable frame.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**No code change; both costs need a design change (AC#2).** The sampler ran on dev bb80905eb3 sources. The harness probe and the warm-visit profiler ran on this branch's head, whose sibling changes do not touch compose or resume.

**`compose_content`, once per launch.** Sampler: 51 steps, CPU median 187 ms. Shares are of the step's samples.
- 72%: the Inspector-state derivation (`_build_console_inspector_state` -> `_selected_console_conversation_inspector_rows` -> workspace context -> `_with_console_conversation_browser_state`). Almost all of it (71%) is `_ensure_console_agent_bridge` -> `ConsoleRuntime.ensure_agent_bridge`, which builds the agent bridge synchronously on first use for the browser's sub-agent and progress counts. That breaks down as:
  - `ensure_activity_receipt_service`: 34%, opening `AgentRunsDB` (schema init 33%, private-SQLite helper start 15%);
  - `ensure_provider_gateway`: 28%, the gateway's owned httpx `AsyncClient` (TLS trust plus transport);
  - lazy imports under both: 29%.
- 15%: active session settings. 10.5%: control state.
- In the send harness, which has no durable DB and so builds no agent runtime, `compose_content` costs 54-59 ms of CPU (3 runs, load 9) and restyles 37 nodes.
- **Why not here.** Moving the bridge off the loop means building it asynchronously and painting the conversation browser without sub-agent and progress counts until it lands. That is a lifecycle change to `ConsoleRuntime` (bridge, gateway and receipt-DB ownership and disposal), not a local fix. Preloading the imports belongs to the pre-import payload, whose ratchet never rises (ADR-097).

**Screen-resume CSS pass, every return to the Console.** Sampler: 35 steps, CPU median 285 ms.
- 60%: Textual's `Screen._on_screen_resume` -> `update_node_styles(animate=False)`, a whole-screen restyle. Textual's own `switch_screen` and `push_screen` post `ScreenResume()` with `refresh_styles=True`.
- 27%: `Screen._on_resize` -> `update_classes(breakpoints)`, a second whole-screen restyle when a `BaseAppScreen.VERTICAL_BREAKPOINTS` class flips. That happens once per mount or terminal resize, not on every resume.
- About 27%, overlapping: the following `_refresh_layout` and compositor render.
- 6.6% is the test profile guard's hook, a test artefact.
- In the send harness the resume handler restyled 538-554 of the screen's 555 nodes, 55-58 ms of CPU at load 9. The warm-visit profiler (8 Library -> Console visits, 170x48, load 9-12) measured first interactive 57 ms median (p95 106) and full ready 205 ms median (p95 232) over 559 widgets.
- **Why not here.** Both restyles are private Textual handlers.
  - A ChatScreen resume handler could call `event.prevent_default()`. `MessagePump._get_dispatch_methods` stops its MRO walk on `_no_default_action`, so `Screen._on_screen_resume` would not run (lessons-textual, `Widget.on_mount` entry). But that also drops the handler's other work: removing the suspended-screen class, bumping `stack_updates`, refreshing notifications, auto-focus, and the `_refresh_layout` on a size change. Skipping it would mean re-implementing that private Textual code in ChatScreen.
  - Either way, skipping safely needs a signal that no style input changed while the screen was off the stack (theme, CSS reload, or classes written while suspended). Textual does not expose one. The same signal would let app navigation post `ScreenResume(refresh_styles=False)` instead.
  - The breakpoint restyle needs Textual's breakpoint mechanism replaced with a scoped one.
  - So the verdict stands: both are design changes.

**No regression.** No code changed. On the branch head (this task's siblings included), the first-mount and boot-budget tests (`test_console_first_chat_first_mount`, `test_console_first_send_preimport`, `test_boot_budget_ratchet_messages`, `test_boot_css_byte_budget`, `test_console_mount_profile`, `test_boot_worker_census`, `test_screen_preimport_payload_budget`, `test_app_import_weight`, `test_ui_ready_module_census`) gave 70 passed, 3 failed. The 3 failures (`test_preimport_pass_payload_stays_within_budget`, `test_app_import_own_module_count_stays_at_the_post_diet_size`, `test_ui_ready_module_census_stays_at_the_pinned_size`) fail identically with the five touched source files reset to bb80905eb3, so they are pre-existing locally.

**Files:** this task file only. The probes were temporary and are not committed.
