## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: The PR #3423 review (finding I-2) found that the Library's bulk Add/Remove keyword wrote plain database links, so on a Sync v2 local-first device the change never reached the user's other device; the fix routes the bulk worker through `NotesScopeService.change_local_note_keyword`, the editor's keyword path, which records the `notes.keyword` resource and `notes.keyword_link` intents. The notes importer has the same shape and was left alone there by ruling: `note_import_executor._link_keyword` (`tldw_chatbook/Notes/note_import_executor.py:649`) and `_unlink_keyword` insert and delete `note_keywords` rows directly on the import's cursor and record only the legacy `sync_log` change, never an organization intent. So on a Sync v2 device the keywords an import puts on its notes (frontmatter `tags`/`keywords`, a re-import's keyword changes) stay on this device, and a keyword the import creates is never published, while the import's receipt reports them as applied. No reconciliation scan later picks up unrecorded local links (I-2's trace).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 On a ready Sync v2 local-first profile, an import that links keywords to its notes records one notes.keyword_link intent per link it creates and per link it removes, and one notes.keyword resource for each keyword it creates, in the import's own transaction
- [ ] #2 On a profile whose Notes organization group is not ready, the import's keyword change is refused or reported, never applied silently as if it would sync
- [ ] #3 Without Sync v2, an import's notes, keywords and receipt are as they are today, pinned by the existing import tests
- [ ] #4 A real-database test over the real import executor and the real organization sync service pins #1 and #2, failing before the fix
