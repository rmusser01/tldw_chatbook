## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Every persona fails to find a note again with the filter:
- A first-timer types "meet" and gets nothing, although three notes say "meeting".
- A power user types the start of a title ("Lisb") and gets nothing.
- A researcher filters on the keyword the app itself attached to a captured answer and gets nothing.

Keywords look like tags, but the filter ignores them. Yet the User Guide (`Docs/User_Guide/library/notes.md:1266-1268`) says filtering the list on `conversation:` finds every answer kept from one chat.

Observed at 160x45 on the golden profile:
- A note with the keyword 'zebra' is not found: "filter: zebra · 0 results" and "No notes match “zebra”. Clear the filter." (`verify/nl-v-n-09/17-filter-zebra-160x45.txt`).
- "filter: size chunk · 0 results", while "chunk size" returns 4 (`07-filter-size-chunk-160x45.txt`).
- The journeys also saw "meet" return 0 against 3 for "meeting", "Lisb" return 0, "homelab" and "keyword:homelab" return 0, and a conversation-id keyword "71d30fb1" return 0.

Verified cause (origin/dev 2d34cbf80d):
- The Notes list filter binds the whole input as one quoted FTS5 phrase: `build_phrase_match_query(query)` at `Notes/note_folder_repository.py:808`, defined at `Utils/fts5_match_forms.py:368-391`. Words must therefore be whole, next to each other and in the typed order.
- notes_fts indexes only title and content (`DB/ChaChaNotes_DB.py:1096-1101`), so keywords are never consulted.
- TASK-19558 kept this seam as a phrase on purpose ("widening them to AND would be an unmeasured behaviour change"). This task is that deliberate, measured change, for the Notes list filter only.

Suggested direction (a direction, not a mandate):
- Use the `and_then_prefix` form that the RAG engine and the Library four-seam path already share (`Utils/fts5_match_forms.py`; TASK-15700/17755): AND the tokens, prefix-match the last one, and treat the input as a phrase only when it is quoted.
- Include notes whose keywords match, through note_keywords or a '#tag' / 'tag:' form.
- Make the zero-result message name what was searched and suggest fewer words.
- Any new index needs a query plan captured with sqlite_stat1 absent and a row in `scripts/index_plan_pin_census.tsv` (CLAUDE.md gotcha 1).
- The other phrase seams named in `build_phrase_match_query`'s docstring (keywords, keyword collections, datasets) are out of scope.

No existing task owns this. TASK-32201 (Done) made the filter reach the search service in the first place.

Review finding(s): N-09. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** The Notes LIST filter now matches words in any order, treats the last word as a prefix, consults the
note's keywords, and matches a phrase only when the input is wrapped in double quotes. The zero-result line names
titles, bodies and keywords and offers a next step. Base `47650eeae6` (P1-B, stacked on P1-A).

**Approach.**
- One pure rule in the primitive module (`Utils/fts5_match_forms.build_notes_filter_match` →
  `NotesFilterMatch(expressions, phrase, fts_expression)`, `NOTES_FILTER_MAX_TOKENS = 32`,
  `NOTES_FILTER_MIN_PREFIX_CHARS = 2`). Word mode: `fts5_query_tokens` + `quote_fts5_token` per word, the last kept
  word starred when its final alphanumeric run is ≥ 2 chars (so `a` stays whole). Phrase mode only for a matching
  straight or curly quote pair around searchable text. Every string that reaches SQL is built by the primitive's one
  escape (TASK-19558); FTS operators typed by the user are literal text.
- One SQL shape in `Notes/note_folder_repository.search_note_tree_placements`: the `matching_notes` CTE body is the
  module-level `_NOTES_FILTER_MATCH_SQL` with one FIXED `_NOTES_FILTER_MATCH_LEG_SQL` per word, AND-ed; each leg is
  "in the title/body (`notes_fts`) OR in a live keyword (`keywords_fts` → `note_keywords`)". Parameters only
  (`2 × len(expressions)` + the normalized path query); the folder-path leg, the Unfiled leg, ordering, paging and
  the total are unchanged. `search_notes` (the RAG/Search seam) and the keyword seams stay phrases
  (`build_phrase_match_query`'s docstring records the move).
- **No index** (AC#5 second clause, satisfied vacuously): the FTS legs are MATCH-driven and the keyword leg walks the
  existing `idx_notekw_kw`, so no `CREATE INDEX` and no `scripts/index_plan_pin_census.tsv` row. The plan is pinned
  with `sqlite_stat1` absent in `test_the_filter_cte_never_scans_the_fts_tables` (every FTS step carries SQLite's
  `VIRTUAL TABLE INDEX 0:M<n>` MATCH flag; `SEARCH nk USING INDEX idx_notekw_kw`). Note: SQLite prints a MATCH-driven
  FTS5 step as `SCAN <fts> VIRTUAL TABLE INDEX 0:M…`, so "no step starts with SCAN notes_fts" is not the right
  budget -- the `M` flag is.
- Copy: `build_library_notes_list_state` empty copy → `No notes match “<text>” in titles, bodies or keywords. Try
  fewer words, or clear the filter.`; `empty_kind` and the Clear filter button unchanged; status line unchanged.
