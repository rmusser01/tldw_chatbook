## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`tldw_chatbook/css/widget_css.py:243-249` sends top-level trivia — including `$var: value;` definitions — to both output streams, so a screen block's local variable fallbacks are in scope for every block emitted after it in the same generated sheet (e.g. `EmojiPickerScreen`'s `$ds-*` fallbacks in `screen_css_scoped.tcss` cover all later blocks). Verified INERT today: the only `$ds-*` uses sit inside EmojiPickerScreen's own block, and the blocks after it use no custom variables. But the next screen consolidated below it silently inherits those fallbacks — the same collision class the separate-sheet design exists to avoid, narrowed from app-wide to sheet-wide rather than eliminated. Fix direction: per-block variable isolation in the builder (emit block-local definitions only into that block's slice, or fail the build on cross-block shadowing). Found during the TASK-15450 CSS-consolidation review (PR #1616, merged `c3ed2854a`); evidence in the session review record and `Docs/Design/2026-08-11-input-latency-audit.md`.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Confirm the Textual variable-resolution mechanism directly against the installed `textual` package: does `$name: value;` scope to the whole *file*, or something narrower? Read `textual/css/parse.py` (`substitute_references`) and `textual/css/stylesheet.py` (`_parse_rules`/`parse`) to see whether the variable dict is built fresh per `Stylesheet.parse()` call (per *source*) or accumulates across sources.
2. Confirm empirically: which of the two currently-affected files (`screen_css_scoped.tcss`/`screen_css_self.tcss`) actually carry a top-level `$var:` declaration today, and whether any block other than `EmojiPickerScreen` references `$ds-*` without a local definition (grep already suggests not, per the task description -- verify against HEAD).
3. Decide the mechanism: given (1), Textual resolves `$var` refs via one left-to-right token scan per source/parse-call, so a generated sheet -- one source built from many blocks' concatenated text -- gives every block in it the same scope. True per-block isolation is therefore only achievable by *not* emitting the local declaration into the shared text at all: substitute each block's own local `$var` references with their resolved value at *build time*, then drop the declaration. This eliminates the collision class rather than just detecting it, and is feasible because the values in practice are simple (a literal or a reference to another already-defined name), matching Textual's own define-before-use, left-to-right accumulation.
4. Implement `isolate_local_variables()` in `tldw_chatbook/css/widget_css.py`: a per-block pre-pass (before `split_scoped_css`) that finds top-level `$name: value;` statements, resolves each value against the block's own already-seen local variables (chained references), substitutes every local-variable use in the block's own rules with the resolved text, and drops the declaration statements entirely so the name never appears in the emitted sheet.
5. Wire it into `render_stylesheets` (shared by both the widget-defaults and screen tiers) immediately before `split_scoped_css`.
6. Add regression tests in `Tests/UI/test_widget_css_consolidation.py`: direct unit tests of `isolate_local_variables` (inlining, chaining, malformed-CSS error), and a synthetic two-block fixture (`Alpha` defines a local `$var` and uses it; `Bravo` references the same name without defining it) parsed with Textual's *real* `Stylesheet` -- the fix must turn Bravo's reference into a genuine `UnresolvedVariableError` rather than a silent resolve. Prove born-red by disabling the fix and re-running.
7. Regenerate all five generated sheets via `build_css.py`, diff against HEAD, confirm the only delta is `EmojiPickerScreen`'s block (declarations dropped, `$ds-focus-bg`/`$ds-focus-fg` replaced with their resolved values `$surface`/`$text` -- the same resolved value as before, so no user-visible change) and the bundle's timestamp line; run `check_bundle_sync.py` (5/5).
8. Run the full `Tests/UI/test_widget_css_consolidation.py` file, the focus-contract test that reads `EmojiPickerScreen`'s source (`test_non_obscuring_focus_contract.py`), ruff check/format on touched files, and a live app-boot smoke check.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Mechanism: true per-block isolation (build-time substitution), not a build-failure guard.** Read against the installed Textual 8.x source: `Stylesheet._parse_rules` calls `parse(..., variable_tokens=self._variable_tokens)` once per **source** (`Stylesheet.read`/`add_source`), and `substitute_references` (`textual/css/parse.py`) builds its working `variables` dict as `css_variables.copy()` -- a *copy* seeded from the stylesheet-shared theme variables, then mutated only by `$name:` statements encountered while scanning *that one string*. A generated sheet (`screen_css_scoped.tcss` etc.) is exactly one such string, built by concatenating every block's CSS in declaration order, so every block in it shares one variable scope -- confirmed both by reading the algorithm and by a direct probe (`Stylesheet(variables=...).parse()` on a two-block fixture: a block-local `$leak-var` defined in block A's trivia resolved block B's reference too, silently, with no error). Genuine app/theme variables (`$surface`, `$primary`, `$text`, ...) are unaffected by this — they come from `Stylesheet.set_variables`/`App.get_css_variables()`, a source shared across every parse call, not from file text. `$ds-*` design-system tokens (e.g. `$ds-focus-bg: #51677e;` in `tldw_cli_modular.tcss`) are themselves just plain top-level `$var:` text local to *that* file/source -- they were never reachable from `screen_css_scoped.tcss`'s own parse call in the first place (a separate source), which is exactly why `EmojiPickerScreen` needed its own local fallback to parse at all ("so this CSS parses without the app bundle"); this task does not change that resolved value for `EmojiPickerScreen`, only removes the risk that its fallback attaches to some *other*, later-consolidated block.

Given per-source scope is inherent to how Textual resolves variables (not a policy choice this build script can override without abandoning "one generated file per tier"), true elimination requires performing the equivalent substitution ourselves at build time, scoped per block, before concatenation -- rather than only detecting a collision after the fact. Implemented `isolate_local_variables()` in `tldw_chatbook/css/widget_css.py`: a pre-pass (mirroring `split_scoped_css`'s existing depth/quote/comment-aware tokenizer) that, per block, resolves each top-level `$name: value;` statement's value against that block's own already-seen local names (chained, left-to-right, matching Textual's own define-before-use accumulation), substitutes every local-variable *use* in the block's own rules with the resolved text, and drops the declaration statements so the name never reaches the emitted file at all. A reference to a name the block never defines locally (a real app/theme variable) is left untouched. Wired into `render_stylesheets` (shared by both the widget-defaults and screen tiers) immediately before `split_scoped_css`, so the fix applies uniformly rather than screen-specifically.

**Born-red evidence** (`test_local_variable_definitions_do_not_leak_across_blocks`): a synthetic two-block fixture (`Alpha` defines `$leak-var` locally and uses it; `Bravo` references the same name with no local definition) run through `render_stylesheets` and parsed with Textual's real `Stylesheet` (real theme variables, so a coincidental app-var name could not mask the leak). With the `isolate_local_variables` call temporarily removed, the fixture parses *without error* -- Bravo's reference silently resolves to Alpha's fallback, reproducing the bug exactly. With the fix restored, the same fixture raises `UnresolvedVariableError` for `$leak-var`, because Alpha's declaration is now inlined into Alpha's own rule and dropped, so it never reaches Bravo's text. Also added: direct unit tests for `isolate_local_variables` (inlining + dropping a declaration, chained local references, and a malformed-CSS `ValueError`).

**Sheet-stability accounting**: regenerated all five files via `build_css.py`. `widget_defaults_self.tcss` / `widget_defaults_scoped.tcss` are byte-identical (no `BUNDLED_CSS` block declares a local top-level `$var` today). `tldw_cli_modular.tcss` differs only in its `Generated:` timestamp line (the pre-existing, `check_bundle_sync.py`-ignored non-determinism of re-running the builder; untouched by this change otherwise). `screen_css_self.tcss` / `screen_css_scoped.tcss` differ only in `EmojiPickerScreen`'s block: the two `$ds-focus-bg`/`$ds-focus-fg` declaration lines are gone, and its `:focus` rule now reads `background: $surface;` / `color: $text;` directly -- the exact same *resolved* values the rule already had (its local fallback's own RHS), so this is not a user-visible styling change, only the removal of the leak vector. `check_bundle_sync.py` reports 5/5 in sync.

**Follow-up hardening round** (independent review, verdict FIX-FIRST -- report at commit `c52239c88`): the review confirmed the core mechanism, evidence, and sheet-stability accounting above, but attacking the new resolver directly found three real correctness gaps relative to Textual's own variable semantics -- all inert against today's tree (no shipped block exercises them) but the same silent-misresolution bug class this task exists to eliminate, relocated into the new resolver rather than closed:

1. **Forward references silently accepted, not rejected.** `$a: $b;\n$b: blue;\nFoo { color: $a; }` -- Textual, parsing this standalone, raises `UnresolvedVariableError` immediately (single left-to-right scan, `$b` unresolved at the point `$a`'s value references it). The old resolver had no way to distinguish "a name declared later in this same block" (a real bug Textual rejects) from "a name never declared here" (a legitimate global) -- both looked identical (absent from `local_vars` *so far*). Demonstrated silent-wrong-value repro: if an unrelated global happens to share the forward-referenced name, the old resolver produced a resolved-but-WRONG value with no error anywhere.
2. **Quote-unsafe substitution (both helper scanners).** (i) `content: "price is $a dollars"` had its quoted contents rewritten (`$a` substituted inside the string), though Textual's tokenizer treats a quoted string as one opaque token, never re-scanned for a `variable_ref`. (ii) `$sep: "a;b";` corrupted the output -- the value-terminator scan tracked paren/bracket depth and comments but not quote state, so the `;` inside the string ended the declaration early and leaked the string's tail (`b";`) into the emitted CSS as raw text.

**Fix**: rewrote the resolver around an explicit two-pass, opaque-span-aware design. `_split_opaque_spans` first splits a block's CSS into `(kind, text)` segments (`"code"`, `"string"`, `"comment"`, `"open"`/`"close"` for bare `{`/`}`) so quoted strings and comments become atomic, never-rescanned units everywhere downstream. `_collect_declared_names` walks those segments once to build the *complete* set of names this block declares anywhere (regardless of position) before any value is resolved. `_substitute_variable_refs` then does the actual left-to-right resolution: a reference already in `local_vars` substitutes; a reference in `declared_names` but not yet resolved is a **forward reference** and raises `ValueError` naming the block, the declaring variable, and the referenced name; a reference in neither is an external app/theme variable and passes through untouched -- an opaque atom is always copied through verbatim and never scanned. `_consume_variable_defs` (declaration stripping) and `_substitute_local_variables` (rule-body substitution) both now operate over these opaque-aware atom sequences instead of raw characters, closing gap 2 for both scanners it previously only half-covered. `isolate_local_variables` gained a `scope` parameter (`render_stylesheets` now passes `block.class_name`) purely so a forward-reference error names the offending block.

Two bugs surfaced *during* this rewrite (not from the review, found while testing the new code against nested rules): the segment-based main loop initially appended a rule's closing `}` to the output *before* its substituted body text (`.thing {} background: $surface;` instead of `.thing { background: $surface; }`), and a nested rule's own braces were spliced into the output ahead of the outer rule's still-unflushed body text. Both were caught immediately by a basic sanity probe before any test was written, and fixed by reordering the flush-then-brace sequencing and by deferring nested `{`/`}` into the body accumulator instead of emitting them directly.

**Born-red evidence** for all three review gaps: extracted the previous commit's `isolate_local_variables` via `git show HEAD:...` into a throwaway module and ran the reviewer's exact repros against it -- forward reference: `'\n\nFoo { color: $b; }\n'` (no exception, dangling `$b`); shared-name variant: `'\n\nAlpha { color: $fwd-shared; }\n'` (no exception, silently wrong once a same-named global resolves it); quoted content: `'...note: "price is red dollars"...'` (the string's `$a` was rewritten); quoted semicolon: `'b";\nFoo { color: red; }\n'` (output corrupted, matching the review's exact observed strings). All four now raise or resolve correctly against the hardened resolver. New regression tests: `test_isolate_local_variables_rejects_a_forward_reference` (both the plain and shared-name variants), `test_isolate_local_variables_leaves_quoted_content_untouched`, `test_isolate_local_variables_handles_semicolon_inside_a_quoted_value` -- 3 more tests, 28 -> 31.

**Re-verification**: full `Tests/UI/test_widget_css_consolidation.py` re-run, 31/31 passed (including the pre-existing 28, confirming no regression from the rewrite -- the `EmojiPickerScreen` isolation and the original leak-across-blocks pin both still hold).
