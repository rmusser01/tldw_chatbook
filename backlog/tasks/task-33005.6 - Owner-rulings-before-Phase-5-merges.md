## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The owner ruled on all three questions on 2026-10-02; the code, docs and tests now match.

**AC#1, live cloud-key evidence.** Owner ruling: the documented local stand-in is accepted for parent AC#11's valid-cloud-key case (qa/model-config-p5-2026-10-01/task-4/README.md, and qa/model-config-33005-captures captures 10-12, both of which say a local server stood in for OpenAI). No real key was used.

**AC#2, keyless "verified".** Owner ruling: a successful paid test reads "Ready · verified HH:MM" even for a keyless provider. Already matched, so nothing changed: console.md's readiness table says "or a paid generation test succeeded", and `Tests/Chat/test_readiness_words.py::test_a_successful_paid_test_reads_verified` and `::test_verified_by_a_paid_test_reads_the_time_of_that_test` pin it on keyless llama.cpp.

**AC#3, shipped-default probing.** Owner ruling: keep probing the shipped localhost defaults when Switch model opens, so a server already running at its default port is found. A shipped default the user never configured that refuses is listed quietly as not running, never as a "refused :PORT" NEEDS SETUP row. A provider the user configured or edited that refuses still reads "Not ready · refused :PORT".

Ruling, what "configured" means (recorded here; TASK-33005.5 AC#1 left it open). A listed local provider is configured when the user owns it by use or by edit:
- by use: it is this chat's, the chat default's, the previous pair's or a recent pair's provider. That is the switcher's `_used_provider_keys`, the same set that keeps legacy aliases listed (ADR-066);
- by edit: its saved `[api_settings]` table differs from the shipped template's (`DEFAULT_CONFIG_FROM_TOML`). Every loaded profile carries the template tables, so a table alone proves nothing; `first_run_setup_state.any_provider_configured` refuses template endpoints for the same reason, and `speech_settings_model` defines "configured" as differing from the shipped default;
- a `custom-ep:` registry entry is always the user's own.

Everything else is an untouched shipped default. Only a refusal (`connection_refused`) is quiet: a timeout can be a hung server that is running, so it keeps its NEEDS SETUP row.

Implementation: `console_session_settings.provider_left_at_shipped_default(app_config, provider_key)` (pure config comparison, no network) and, in the popover's `_build_rows`, a refused, retry-in-place row for an unused provider left at its shipped settings goes into one "NOT RUNNING · local servers never set up · rechecked on open" line instead of NEEDS SETUP (typing still filters it by name). Probing is unchanged. console.md documents the NOT RUNNING line.

Tests (Tests/UI/test_console_switcher_local_probe.py): `test_an_untouched_shipped_default_that_refuses_is_quietly_not_running` (RED before the fix: aphrodite and tabbyapi were in NEEDS SETUP), `test_a_configured_default_that_refuses_still_reads_refused[chat default|edit]`, and `test_an_untouched_shipped_default_that_runs_reads_reachable`. Mutation checks: dropping the use test fails `[chat default]`, and dropping the template comparison fails `[edit]`. Live: qa/model-config-33005-captures/fix/.

Not part of the rulings: the header badge's Ready/Blocked fallback below 84 columns stays as designed (TASK-33005.3).
