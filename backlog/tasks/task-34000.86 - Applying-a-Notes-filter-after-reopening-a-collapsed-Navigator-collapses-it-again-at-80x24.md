## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: At 80x24, Escape from the Notes filter moves focus toward the rail and collapses the Notes Navigator pane, giving the Library pane the layout priority. If the user then reopens the Navigator from its collapsed handle, clicks into the filter and applies a filter (Enter, and so also Down, which applies the box the same way), the Navigator collapses again and focus lands on the rail's "Notes" row. The filter is applied, but the user is thrown out of the pane they just reopened, and the next key goes to the rail.

Minimal repro (seeded power profile, isolated harness, 80x24): Library ▸ Notes ▸ `/` ▸ type `thes` ▸ Enter ▸ Escape (the Navigator collapses) ▸ click the collapsed Navigator handle (it reopens) ▸ click the filter box ▸ End, Backspace ▸ Enter. The pane collapses to the rail and the rail's `▸ Notes (122)` row holds focus.

Evidence: reproduced on a `git archive 5e746fe393` export (before polish-1a Task 5) with Enter, so it is not caused by the filter's Down fast path; found during TASK-34000.28 / .40's live walk (polish-1a Task 5). Hypothesis, not traced: the canvas sync that applies the filter re-resolves the reader layout with the Library-priority request Escape set, which a reopen from the handle does not clear.
