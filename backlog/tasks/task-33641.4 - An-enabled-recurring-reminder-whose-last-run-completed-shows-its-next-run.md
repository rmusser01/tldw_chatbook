## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`_format_next_run` (UI/Screens/scheduling/task_detail.py) returns "—" for any task whose display status is Completed, and it checks this before it reads `next_run_at`. That branch was meant for a fired one-time reminder (UAT finding 3e). An enabled recurring reminder whose last dispatch completed also reads Completed, so its scheduled next run is hidden: the task detail shows "Next Run: —" from the first successful run onward. Checked on the Phase 3 branch: a recurring weekly reminder (enabled, last status Completed, next_run_at 2026-10-05 09:00 UTC) formats as "—". The cubic review of PR #2937 found it in schedules-task-detail-211x44.after.txt. task_detail.py is unchanged from origin/dev, so this is unrelated to the model-configuration work. It is filed here only so that it has an owner.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
An enabled recurring reminder now keeps showing its stored next run after a dispatch. The badge still reads Completed, Missed or Timed out for the last run. The same line fixes a fired one-time reminder that was given a new time and enabled: it is one-time, enabled and Completed with a stored next run, and it read a bare dash too.

What changed:
- `_format_next_run` (`UI/Screens/scheduling/task_detail.py`): the bare "—" branch now tests `isinstance(task, ReminderTask) and reminder_has_fired(task)`. It used to test `_task_status(task) == TaskStatus.COMPLETED`, which is also what an enabled reminder reads after any successful dispatch, because `_task_status` falls through to `last_status`. One condition changed; `_task_status`, the badge and the buckets are untouched.
- The queue column needed no change: `_row_subtitle` calls the same formatter with `compact=True`.
- `Docs/User_Guide/schedules.md`, Next Run readability: a recurring task keeps its next run after it has run, and a fired one-time task shows its new time once its schedule is edited and it is enabled. Disabled tasks (review rounds 2 and 3): the closing sentence now states the rule as the complement of the fired case, "every other disabled reminder reads Disabled / — (disabled), whether or not a next run is still stored underneath", and gives three examples: one the user disabled, a fired one-time reminder given a new time and not yet enabled, and an overdue one-time reminder the server parked disabled on a move (the guide's own "Moving a task between this device and the server" section). It used to call the user-disabled row "the only shape". The rule is `_task_status`: a reminder that is not enabled and has not fired reads Disabled. Its formatter half is pinned by the older `test_disabled_reminder_next_run_shows_no_concrete_time` (next run stored) and `test_completed_one_time_reminder_still_reads_disabled` (one-time, disabled, no next run, never ran). That the server parks an already-passed one-time run disabled, with no catch-up run, is the guide's 2026-09-02 live measurement; no server was driven here. What this device then does with that answer was read and run (review round 4; the run is under Verification). A move goes `SchedulingService.begin_transfer_to_server`, which queues a `transfer_to_server` mutation, -> `SyncEngine._push_reminder_transfer` -> `ScheduledTasksDB.convert_row_to_server_mirror`, whose UPDATE writes only `server_id`, `owner_id`, `transfer_state` and `updated_at`. The cycle that pushes the move pulled before it pushed (`SyncEngine._network_phase`), so the server's `enabled` and `last_run_at` reach the row on the next pull: `ScheduledTasksDB._apply_pulled_reminders` copies every reminder column present in the server item, and the item always carries both keys, `last_run_at` as a null for a task the server has not run (`ReminderTaskResponse` declares both fields, and `ServerNotificationsService._dump` is `model_dump(mode="json")`, which keeps nulls). So the row reads Disabled from the first sync after the one that moved it.

Rulings:
- Ruling: a projection (`ScheduledTask`) whose status is Completed no longer gets the bare dash; it shows its `next_run_at`, or "-" when it has none -- why: the rider keeps that branch for a fired one-time reminder only, and no projection emits Completed (briefing and dreams emit Waiting; watchlist emits Waiting, Disabled, Paused or Needs Attention) -- cost if wrong: one more `or` on that branch.
- Ruling: an enabled reminder that has a Completed last status and no stored next run (a recurring one whose cron is exhausted) now reads "-" where it read "—" -- why: it is the existing "enabled, nothing scheduled" case that `test_enabled_reminder_without_next_run_still_reads_dash` pins for a one-time reminder -- cost if wrong: one character. Pinned by `test_enabled_recurring_reminder_with_no_next_run_reads_the_plain_dash`.
- Ruling: the "paused" case is a reminder whose last status is Paused -- why: that is the only way a reminder's display status becomes Paused -- cost if wrong: none; a paused projection was already pinned.
- Ruling: only the new test nodes carry `pytest.mark.bootstrap_profile` (phase ruling R7) -- why: both files have no isolation marker, so every node in them errors at setup with `RecoveryRequired: raw_source_selection_changed` -- cost if wrong: the older nodes in these two files still do not reach their assertions in a plain local run.
