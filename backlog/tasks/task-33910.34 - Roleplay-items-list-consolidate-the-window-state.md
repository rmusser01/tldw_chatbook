## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Roleplay frame B2a (TASK-33910.3) made the Roleplay items list read the database in windows of 200 rows. The list's window state is five variables split between the widget (rows past the loaded end, the asked-for window, the row waiting to load) and the screen (the rows fence, the deferred End or load-through), and each is reset on some paths only. B2a's final review found the first user-visible symptom (End did nothing in Lore books and Chat dictionaries after a partial Characters window) and B2a fixed that one by resetting the widget's three fields on a kind switch. These edge cases remain. Each is new with B2a (dev's paged list had no windows), each is narrow (locally a window takes a few milliseconds), and B2a does not fix them:

- End or a load-through asked for during a reload is replayed when the reload lands without checking that the user still wants it (End then Home, or a load-through to one row then a selection of another, during the reload).
- End pressed during the 0.2 s search debounce is dropped: its fence is taken before the reload's generation bump.
- An End or load-through append that a concurrent write reload cancels is lost.
- A row waiting to load from a load-through a newer list cancelled can move the cursor when a later window brings that row in (the kind-switch case is fixed by B2a).
- On a server source, a reload's blank sets the rows fence before any server row arrives, so a window request queued before the blank can start an offset-0 append that cancels the server reload's tail.
- The leave hook's suspend path (Task 7's rows-fence re-stamp, the reload on return, a leave inside the replace's paint) runs only in tests: Roleplay's route is not reusable today, so every leave is an unmount. It needs re-checking when PERF-22 (TASK-33281) makes the route reusable.

## Implementation Notes

Summary: the Roleplay items list's window state has one owner, ListWindowState (with WindowIntent and same_list) in UI/Persona_Modules/roleplay_frame_state.py. PersonasScreen creates it and passes it through PersonasLibraryPane to RoleplayItemList (the fast-lane host's list makes its own). The five B2a fields, _reload_on_return and the page generation are gone from the list and the screen (a static test pins it). Every reset is a named transition: reload_started / landing / painting / forget_rows (a reload's rows), set_more / ask / answered (windows), kind_switched, want / asked_for / user_moved / arrived / take_end / take_replay (the owed End or load-through), leave / returned (the visit). TASK-33910.35's 'land on the first match' is meant to be one more WindowIntent reason.

Fixes (each edge case exists on dev today, new with B2a; each fixed here):
- AC#2/AC#8: a newer cursor move or selection forgets the owed move, whether a reload deferred it or its read is still running. The moves are Home/Up/Down/PgUp/PgDn, a row click, Enter in the search box and opening a row. AC#8 was added before implementing: it covers the in-flight case, a behaviour change from dev, where End moved the cursor to the last row regardless.
- AC#3: an owed move belongs to a list by query/sort/tag/source (same_list ignores the generation), so End during the search debounce replays on the searched list.
- AC#4: a write reload of the same list replays the move whose append it cancelled.
- AC#5: landing drops a move owed on another list before its rows paint.
- AC#6: the server reload's blank and the source-change blank are no list's rows, so no append starts against them.
- AC#7: _end_visit stops the search debounce timer; a leave inside a replace's paint (the painting bracket) reloads on the return.
