## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** On macOS without a cached parakeet-mlx model, Dictate and Hands-free show '◐ Preparing speech model…' indefinitely: still up after 90 s, and after 52 minutes in an earlier session. The model is not downloading; the load is deadlocked.

Mechanism:
- Inside the Textual app, the first Hugging Face fetch raises 'ValueError: bad value(s) in fds_to_keep', because tqdm's multiprocessing lock meets Textual's stderr capture, whose `fileno()` is -1.
- parakeet-mlx swallows the error and falls back to a local path, which produces a misleading '[Errno 2] No such file or directory: …/config.json'.
- tqdm's class-level lock stays held by the dead warm-up thread.
- The warm-up failure is treated as degraded, so the streaming model load goes ahead and blocks forever.

What the user sees:
- Two toasts that vanish within 5-8 s. One of them says the capture 'may be slow', which is false, and includes an errno and a path.
- After that, a chip with no progress.
- A second press shows no failure toast at all.
- While preparing, the button still reads 'Dictate'; only the tooltip says 'press to cancel'.
- Esc turns Hands-free off, but its 'starting' capture is not cancelled, so the chip stays.

**Severity / prior art.** P1, REGRESSION:
- Commit f8bae35d15 claims 'A warm-up failure is reported as a model/provider problem'.
- Commit 2c0d8db8c5 made the Preparing chip a held message.
- TASK-32495 (Done) covers Hands-free failure honesty.

**Suggested direction.**
1. Make in-app model fetches work under Textual: disable Hugging Face progress bars, or set tqdm's lock before stderr is captured.
2. Classify a load failure as fatal, with one plain message and a next step.
3. Bound the preparing phase with a watchdog or a progress check.
4. Cancel a 'starting' capture when Hands-free exits.
5. Label the preparing button as Cancel.
6. Keep errno values and paths in Logs, not toasts.

Evidence: qa/console-ux-review-2026-09-29/findings.md → G3-09; qa/console-ux-review-2026-09-29/evidence/evidence__J8__124-dictate-fresh-28s.txt, evidence__J8__125-dictate-cancel.txt, evidence__J8__63-hf-after-exit-14s.txt.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Dictate/Hands-free can no longer sit on 'Preparing speech model…': an in-app model download now works under Textual, every failed load ends preparing with one plain, named error and a retry, and a load with no visible progress is bounded.

Root cause (reproduced in-process and live on origin/dev 1eaa6a9429, parakeet-mlx, isolated profile): the first Hugging Face download built tqdm's write lock even though progress bars are disabled; its multiprocessing.RLock started the resource tracker with Textual's fileno() == -1 stderr, raised 'bad value(s) in fds_to_keep', and left TqdmDefaultWriteLock.th_lock held. parakeet-mlx reported it as a missing local config.json, the controller called it 'may be slow' and went on to the streaming load, which blocked on the orphaned lock (0-byte .incomplete).

Changes
- tldw_chatbook/Utils/model_download_guard.py (new): allow_tqdm_without_stderr_descriptor() sets tqdm's own thread-only fallback (mp_lock = None) before any dictation download, and replaces a class lock a dead construction left held (also one 'owned' by a reused thread id, seen in the repro). HubDownloadProgress counts bytes landing in the hub cache (in-flight .incomplete + blobs written since the load began).
- Chat/console_voice_input.py: the guard runs at the top of _run_begin (before the warm-up and start_dictation's streaming load). Every warm-up failure is fatal: _fail with 'The '<provider>' speech model could not be downloaded or loaded.' + 'Nothing was recorded. Check your network connection and press Dictate to try again. The log has the details.'; the raw error is logged only. VoiceModelWarmupFailed / WARMUP_DEGRADED_REASON_TEMPLATE removed (UI/Console_Modules/dictation.py handler too). The warm-up wait polls progress each second: growth repaints the chip ('Downloading speech model… 412 MB') and resets the clock; no progress for dictation.model_prepare_stall_seconds (default 120, validated like handsfree_send_delay_seconds) ends the attempt with SpeechModelStalled ('…stopped loading: no progress for 120 seconds.').
- tldw_chatbook/__init__.py: os.environ.setdefault('HF_HUB_DISABLE_XET', '1'). Measured live: with hf_xet the 2.4 GB parakeet file stayed at 0 bytes while the app's RSS grew 1.1 -> 1.7 GB in 70 s (host swap to 9.4 GB), so no progress could be shown or a stall told apart; plain HTTP streamed 52 -> 178 MB in 4 s into .incomplete and resumes. A user-set HF_HUB_DISABLE_XET wins.
- AC#4/#5 were delivered by TASK-33626.1 (#3302: 'Cancel' label; Hands-free exit cancels a starting capture). Pinned here by a rendered-screen test at 80x24 and 235x52 and verified live.
- Docs/User_Guide/console/attachments-images-voice.md and voice-and-hands-free.md: download progress, the failure message/retry, the stall bound and its config key.

Decisions: every warm-up failure is fatal, not only typed load errors -- the warm-up uses the very transcriber/provider/model the capture would, each press builds a fresh service and re-warms (so a transient error costs one press; pressing again is the retry), and dictation.warm_model_before_capture=false remains the escape hatch. The progress probe watches the whole hub cache rather than mapping provider -> repo id.
