## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
For the nine cloud providers, config.py::_normalize_legacy_provider_api_key never reads credential_source. With credential_source 'none' saved after a Clear in Settings, or 'environment' with the variable unset, and a key still present under the legacy [API] section, the loader copies that key into api_settings.<provider>.api_key and into the legacy <provider>_api dict. Readiness then resolves no key (so the Console says the provider is not ready) while readers of that dict, such as summarize_with_openai, send the cleared key. This is the opposite direction of TASK-33001.15 and older than it. Found by Phase 9's Task 9; read from the code, not run. ADR-012 says a credential the user removed is not used.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 With credential_source none or environment recorded for a provider, the loader does not copy a legacy [API] key into the provider's table or its legacy dict, proved by a real-loader test on a scratch config for at least two of the nine providers
- [x] #2 A provider with no credential_source recorded keeps today's legacy fallback, pinned by the existing normalisation tests
- [x] #3 Readiness and the legacy readers agree for every combination of credential_source and key location the tests cover, and the combinations are listed in this task's notes

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
Phase 9 Task 17 (2026-10-17). The premise holds at the base (0af11c2871). Measured with the real loader: with `[API] openai_api_key` set and `[api_settings.openai] credential_source = "none"` (or `"environment"` with the variable unset), `load_settings()` held the `[API]` key in `api_settings.openai.api_key` and in `openai_api.api_key`, while `get_provider_readiness` resolved none. `summarize_with_openai` no longer exists. The readers now are the chat handlers that read the legacy dict or the table when the caller hands them no key. A summary no longer reads the dict (TASK-33001.14).

What changed: `config.py::_normalize_legacy_provider_api_key` reads the table's `credential_source`, normalised as `provider_readiness.configured_provider_credential_source` does it. It cannot import that function, because the import would be a cycle.
- "none": no key.
- "stored": the table's key, else the `[API]` key copied into the table (TASK-33001.15's case). Never the variable.
- "environment": only the variable the table names.
- Nothing is copied under "none" or "environment".
- No source recorded: unchanged (the table's key, the conventional variable, then `[API]`, copied).

The rider asked only for "none" and "environment" not to copy. "none" leaving a variable's or table's key in the dict, "environment" leaving the table's, and "stored" leaving the variable's were the same disagreement with readiness, and AC#3 covers them, so they are fixed too.

ADR-012 has an amendment of 2026-10-17 with the ruling and the one older difference: with no source recorded, the bridge reads the conventional `<PROVIDER>_API_KEY` while readiness reads the variable the table names. `Docs/User_Guide/settings.md` says that once a save records "no credential" or an Env var, the `[API]` key is no longer shown or copied and chats and summaries no longer send it. It names the readers this task does not reach, which read the raw `[API]` section themselves: `config.get_api_key` (Console realtime, OpenAI and ElevenLabs TTS, the MCP server's chat tools, and the Models screen's vLLM connection probe and credential flag; the vLLM callers added after the round-2 review), `RAG_Search/simplified/active_config.py`, TTS's projection `TTS/legacy_bridge.py` (which `TTS/TTS_Backends.py` reads; the projection added after the round-2 review), and `Model_Artifacts/acquisition.py`'s Hugging Face resolver (Parakeet, OmniVoice and remote GGUF downloads; added after the round-2 review).
