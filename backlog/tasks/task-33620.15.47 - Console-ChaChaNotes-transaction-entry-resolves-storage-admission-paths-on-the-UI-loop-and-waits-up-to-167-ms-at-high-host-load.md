## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-33620.15.21's live rounds (2026-10-30, origin/dev 7536ac3b87, Anthropic claude-haiku-4-5 via the review proxy, 160x45, a fresh isolated profile per launch). 48 sends ran at host load1 99-127 from a bounded busy-loop generator, and 24 at load1 3-9.

Every ChaChaNotes transaction entry (TransactionContextManager.__enter__) first enters storage admission: _core_operation > storage_admission._repository_operation > acquire_storage > _execution_selection_for. That path calls Path.resolve on the participant path, the effective config selector and the source path, and each resolve is a chain of stat calls in realpath. Only after that does _enter_transaction issue BEGIN IMMEDIATE. Run start's post-commit step makes two such entries on the UI loop: the durable trace request's and the owners' trajectory write. Any other transaction the UI loop enters outside an already-open admission operation pays the same resolution (_repository_operation reuses an open operation on the same participant and skips it).

At high load:
- The step's two entries together had a median of 2.75 ms wall (1.75 ms CPU) on first sends and 2.16 ms (1.68) on later sends. In 6 of 48 sends they took 10 ms or more, up to 167 ms.
- In 3 of the 8 post-commit steps of 50 ms or more, this wait held the step: 43.8, 142.8 and 167.2 ms, on 1.4-2.1 ms of CPU. Of those steps' 4 ms samples, 6 of 7, 23 of 25 and 29 of 40 sit in admission's Path.resolve under the trace request's entry. None is on the BEGIN statement, so this is not SQLite lock contention.
- Across all 48 steps, 89 of the 184 samples were in storage admission's Path.resolve, 70 of them under a transaction entry.

At low load the two entries take a median of 1.0-1.1 ms, at most 1.5 ms.

The thread releases the GIL for each stat call and then waits to be scheduled again; under oversubscription that wait is the cost (lessons-live-verification, TASK-33620.15.1.6 and TASK-33620.15.21). TASK-33620.15.38 covers the same kind of wait in the MCP catalog fingerprint's recovery-activation check. TASK-33620.15.5 recorded that TASK-33620.15.1's worker hop made first sends reach the provider 97-249 ms later, so a fix has to weigh any hop's cost at both loads. Storage admission's guarantees are set by backlog/decisions/126-complete-local-backup-and-recovery.md; a fix keeps them.

Evidence is outside the repo, in the measuring session's directory: ~/.claude/projects/-Users-macbook-dev-Documents-GitHub-tldw-chatbook/c28a6a75-4221-4434-989d-fbf24a73c96b/tools/evidence/bd5/M21/ (rounds r1-r3, all_sends.json).

**What changed.** `storage_admission._resolved(path)` returns exactly `path.resolve()`. On macOS 11+ (Darwin 20+) it proves that an absolute, normalized, link-free path resolves to itself in three filesystem calls: one `O_NOFOLLOW_ANY` open of the parent (the kernel refuses a link in any component), an lstat of the leaf through that descriptor, and a close. `Path.resolve` makes one lstat per component plus a stat. A link, any error, another path shape, an older kernel or another platform runs `Path.resolve()` unchanged, so Linux and Windows keep today's cost. All five resolutions per transaction entry go through it: one in `_repository_operation`, two in `_Operation.check`, and the selector and source in `_execution_selection_for`. Values, comparisons, ordering and refusals are unchanged, and nothing is cached. The leaf is never opened, because closing a descriptor of a SQLite file would drop this process's POSIX locks on it. ADR-126 has a dated subsection, and `backlog/docs/backup-recovery-owner-inventory.md` carries the reviewed `_resolved | open` row.

**Review follow-ups (2026-11-06).** An independent review of 59b040e90c found nothing blocking. What was done with each point:
- The rule that `_resolved` never opens the leaf (closing any descriptor of a SQLite file drops this process's POSIX locks on it) had no direct test. Only the macOS storage-unit census caught a leaf open, by count. The new lock test above pins it: with the reviewer's mutation (open and close the leaf before the parent open), it is the only one of the 26 that fails, and it passes again once the mutation is removed.
- The descriptor test no longer counts the whole process's `/dev/fd` entries; it pairs `_resolved`'s own opens and closes on the test's thread.
- The earlier rebase note miscounted the helper failures on dev as 10; it was 9. The evidence paths now name the directory they are relative to.
- Declined: a note in ADR-126 about macOS privacy protection. `_resolved` opens the leaf's parent directory where `Path.resolve` only lstat-ed it, but every path it resolves (the participant database, the config selector, the acquired source) is a file the app itself opens or creates in that same directory. So the parent open needs no access that the app's own use of the leaf does not already need, and any open error falls back to `Path.resolve`, which gives the same value. Nothing was observed either way.
