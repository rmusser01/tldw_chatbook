## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From the PR #2941 checkpoint review. In a legacy flat conversation (every parent_message_id NULL), the store chains the roots in memory only (_chain_legacy_flat_roots), but ChaChaNotes_DB.soft_delete_message_subtree follows parent_message_id. A scratch probe with 4 flat rows ran Delete on f1. The prompt read 'Delete this message and 2 later messages?', the receipt counted 3, and the in-memory transcript showed [f0]. But the DB tombstoned only f1 (deleted flags [0,1,0,0]). f2 and f3 stay live: they still appear in search and exports, and they come back on reopen. origin/dev had the same split between memory and DB, but #2941's scoped copy now states the wrong count outright. Undo is unaffected (it restores the committed ids).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Delete in a legacy flat conversation now tombstones exactly the subtree its prompt counts, on branch fix/task-33628.6-flat-delete (merge-base origin/dev f80d3e0090).

**Approach.** The store already knew the right scope: `_chain_legacy_flat_roots` chains the NULL-parent roots in memory, and `console_delete_scope` counts that chained subtree. The DB delete only followed `parent_message_id`, so it tombstoned just the selected row. The store now passes its resolved subtree down:
- `CharactersRAGDB.soft_delete_message_subtree` takes a keyword-only `subtree_message_ids`. These ids join the selected id as anchors of the same recursive CTE, bound as one JSON array through `json_each(?)` (the module's existing pattern), so there is no SQL interpolation.
  - It is still one IMMEDIATE transaction, with the same existence and version fence on the selected row.
  - An anchor counts only if it is in the selected row's conversation and still live.
  - Parent-link descent still runs from every anchor, so hidden rows (tool or empty) under any of them go too.
  - The default `()` leaves every other caller's behavior unchanged.
- `ChatPersistenceService.delete_message_subtree` forwards the ids.
- `ConsoleChatStore._delete_message` passes the persisted ids of `_subtree_ids`, exactly what the prompt counts. console_chat_store.py has a net change of zero lines. Its size ratchet is already over budget on dev (22,550/22,344); this change does not touch that.
- Undo needed no change. It restores the ids the DB delete committed, and the recovered-media hold collects every returned row.

**Deviation from plan.** Step 2 said "declare-to-receive". The store passes the argument unconditionally instead: `ChatPersistenceService` is the only implementation, and the only test fake (`FaultInjectingSemanticPersistence`) takes `**kwargs`.

**Tests.** Six new tests in Tests/Chat/test_console_message_delete_persistence.py. They run the real store over a real `ChatPersistenceService` and an in-memory `CharactersRAGDB`, under the module's `bootstrap_profile` marker, and pass under plain `pytest`:
- Flat and flat-prefix delete: the prompt count, the receipt count and the DB tombstones are equal, and reopen, FTS search and text export agree.
- A tool row parent-linked under a later flat root is tombstoned, and Undo restores it.
  - Mutation check: making the anchors replace descent fails only this test ([0,1,1,1,0,1]). The other 17 tests pass under that mutant.
- Undo restores all four flat rows, in the DB and on reopen.
- A genuine root-level fork stays un-chained and keeps its other branch.
- Anchor scoping: another conversation's id and an already-deleted id are untouched, and the existing tombstone's version does not change.

RED on f80d3e0090, with 4 failures for the right reasons: flags [0,1,0,0], [1,0,0,0] and [0,1,0,0,0,0], plus a TypeError on the new keyword. GREEN on the branch, 18 passed. The touched files are identical on origin/dev ef8fd5d38a.

**Related suites.** 29 related files (store, store tree, controller, fork, rewind, delete/Undo UI, native chat flow, semantic inventory and writer routing, Sync interop, DB migrations, recovered media) plus the Architecture size ratchet, run on both the branch and the merge-base. 596 failures are present on both (405 are the sandbox's `RecoveryRequired: raw_source_selection_changed`). None are new; the only difference is the 4 new tests. Preflight passes.

**Live** (isolated profile, real app, 160x45, 2026-10-02):
- Merge-base: Delete on a1 of a seeded 4-row flat conversation asked "Delete this message and 2 later messages?" and the receipt said 3. The DB flags were [0,1,0,0]. After a restart, Library read 3 messages (a0, a2, a3), and searching a2's token still matched.
- Branch: the same prompt and receipt, and DB flags [0,1,1,1]. After a restart, Library and Console both show only a0, and searching a2's token finds nothing.
- Branch, Undo: Delete then Undo on a second flat conversation restored all three rows ("Restored 3 messages.", DB [0,0,0,0]). After a restart it reads 4 of 4, and its token still matches.

**Follow-ups (out of scope; recorded, not fixed).**
- A hidden tool or empty row with a NULL parent in a flat conversation is never a store node, so the chain skips it. It is neither an anchor nor a parent-link descendant, so it stays live after the delete and still shows in search and export.
- A store root with no saved id: if the selected message has no persisted id, the store skips the DB delete entirely, even when persisted rows hang under it in memory. Those rows come back on reopen.
- Seen live, not investigated: after a Console delete, the Library list's count updated, but the reader pane kept its earlier 4-of-4 load until a restart.
