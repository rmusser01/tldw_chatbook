## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From the PR #2941 checkpoint review. In a legacy flat conversation (every parent_message_id NULL), the store chains the roots in memory only (_chain_legacy_flat_roots), but ChaChaNotes_DB.soft_delete_message_subtree follows parent_message_id. A scratch probe with 4 flat rows ran Delete on f1. The prompt read 'Delete this message and 2 later messages?', the receipt counted 3, and the in-memory transcript showed [f0]. But the DB tombstoned only f1 (deleted flags [0,1,0,0]). f2 and f3 stay live: they still appear in search and exports, and they come back on reopen. origin/dev had the same split between memory and DB, but #2941's scoped copy now states the wrong count outright. Undo is unaffected (it restores the committed ids).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
TASK-33628.6 has two commits on fix/task-33628.6-flat-delete, based on origin/dev f80d3e0090. The touched files are byte-identical on today's origin/dev, ecc0a531c8.

Commit c6e09d7e02: the fix, reviewed earlier and kept.
- `ConsoleChatStore._delete_message` passes the persisted ids of `_subtree_ids`.
- `ChatPersistenceService.delete_message_subtree` forwards them as `subtree_message_ids`.
- `CharactersRAGDB.soft_delete_message_subtree` seeds the existing recursive CTE with them through `json_each(?)`. It is still the same IMMEDIATE transaction, behind the same version check, with seeds limited to the selected row's conversation and to live rows, and parent-link descent still runs from every seed.

Commit 568e950602: the follow-ups from the checkpoint review, which had no blocking findings.
1. **Planner steer.** In tldw_chatbook/DB/ChaChaNotes_DB.py, the recursive step in both the SELECT and the UPDATE now reads `+child.conversation_id = ?`.
   - Without `sqlite_stat1`, each child is now looked up with a `parent_message_id` index. Before, the planner used `idx_messages_conversation_id_id (conversation_id=?)` and scanned the whole conversation once per subtree row.
   - Measured on a 2,998-row delete: 0.09 s, against 3.4 s (flat) and 3.87 s (threaded) before.
   - New test `test_subtree_delete_descends_by_parent_link_without_statistics` captures the executed statements with `set_trace_callback`. It dedupes them, because trigger sub-programs re-report the outer statement, and asserts that every child step is `SEARCH child USING INDEX ... (parent_message_id=?)`.
   - The test asserts the column rather than an index name, because both `idx_msgs_parent` and `idx_messages_variants_by_parent` lead with `parent_message_id`. For the same reason the index plan-pin census rows are unchanged.
2. **Off-path test.** New test `test_flat_delete_reaches_chained_roots_off_the_active_path` has two items. A regenerated reply under f0 is the active leaf, so the chained spine f1..f3 is off the active path. A mutant that passes only the active-path ids fails only these two items.
3. **Docstrings and typing.** The parameter is typed `Sequence[str | None]` in the DB and the service. Both docstrings now say the caller may send its whole in-memory subtree, with `None` for unsaved nodes, which is ignored.
4. **Store lookup.** The store builds `saved = [... for n in subtree_ids if n in nodes]`, the same leniency as its purge loop, so programmatic callers cannot hit a new KeyError. This is a net-zero line change; console_chat_store.py stays at 22,550 lines, the same as dev.
