## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact (P1, triage NEW).** Tested with capture on (the default) using Anthropic claude-haiku-4-5 at 160x45. When the provider returns a transient error (429, 504, and 500 in the prior L3 log), the send ends at 'Trace capture blocked / Problem: Trace capture could not be saved. / Impact: The provider was not contacted.' The provider was contacted: the proxy logged exactly one POST, which it answered with 429 or 504.

The real cause never reaches the main surfaces. The transcript shows a blank Assistant row and the strip says 'Agent blocked'. No toast appears. The Inspector says 'Run: Ready', 'Provider: ready' and 'Ready to send'. The HTTP status and the words rate-limit or timeout appear nowhere in the UI; only the trace view (Y, then j/i) shows 'Model request failed; retry 1 of 2…' and mislabels the trace failure as 'unexpected provider error'. A non-retried 401, by contrast, shows 'Agent run failed: provider returned HTTP 401'. Users who hit a rate limit are told local trace storage is broken, and they then try capture actions that cannot help (see G4-05).

**Verified cause.** The agent's in-place transient retry (TASK-25901) reserves its second call as a TOOL_LOOP continuation. `console_trace_runtime.py:497` refuses it with `trace_tool_chain_unavailable`, because the previous call never reached RESPONSE_STARTED or COMPLETE. The resulting TraceCallPersistenceError pauses the preparation as TRACE_CALL. With capture on, the TASK-25901 retry therefore never reaches the provider, so even a one-off blip that a retry would fix ends in this callout.

**Prior art:** TASK-25814 (Done), TASK-31976 (Done), TASK-25901 (Done), TASK-26838 (To Do), PR #2882, ADR-097:309.

**Suggested direction:**
- When an attempt already has a recorded provider error, make it the terminal failure: a failed row plus a callout naming the provider, the status and its meaning. Show any trace problem as a secondary note.
- Reserve an in-place retry as a retry of the same logical call, or exempt it from the tool-chain invariant.
- Carry provider_contacted (yes/no/unknown) and derive the Impact line from it; the evidence record itself is owned by the Theme 1 umbrella.
- Make the Inspector reflect the failed run.
- Stop labelling the trace-persistence failure as a provider error.

Evidence: qa/console-ux-review-2026-09-29/findings.md → G4-04 (sources LEAD-02, L3-01). The row's evidence files, uxrev/evidence/trace-blocked-misreport/after-provider-504-160x45.png, uxrev/evidence/L3/05-provider-429.txt and 55-provider-500.txt, were not copied into qa/evidence. Code: provider_continuation_recovery.py:180-205, console_trace_errors.py:25-36, console_trace_runtime.py:452,497.

Dev-tip note (reviewed 64579cce2c; checked against 857b3dd7d0): No commit in 64579cce2c..857b3dd7d0 touches the trace runtime or the recovery copy. Open PR #2882 (not on dev) edits console_trace_runtime.py and the gateway, but it only maps unsupported_surface_change (TraceSurfaceChangeRefused) to reservation_status 'not_established'. The trace_tool_chain_unavailable refusal on the retry still yields 'unknown', so this is not fixed there either.
