## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-33620.15.18. ADR-198 sizes the permanent generation by walking it (`gc.get_freeze_count`) and puts the cost at about 5 ms of CPU per 1.3M objects. In the running app one walk takes far longer, because the frozen set is scattered across the heap. TASK-33620.15.18 removed the walks from the boot points; the idle refreezer still walks on the UI loop at its maintenance (its first look, and the budget check after every re-freeze).

Live on origin/dev 7536ac3b87 (160x45, established profiles, load 4-7, 40 launches without the first-send warm-up): the first maintenance walked on the UI loop a median 4.2 s after the Console's first frame (2.35-4.35 s), taking 24-41 ms (median 26.5 ms); origin/dev's `_ui_ready` freeze walked there too (median 21.6 ms; the TASK-33620.15.18 fix removes that one). In one launch the maintenance callback held the loop 32 ms CPU just as a key was sent, and the key's frame came 34 ms after the send against 12-13 ms otherwise (tools/evidence/bd5/M18/r2, p6-key-fz-n). The maintenance waits for 2 s without input, so only the first key after a pause can meet it.
