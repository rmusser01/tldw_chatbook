## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-34100.16.1's review round v5r2 (finding V2). Each Create backup registers the roots it copies as `backup.source.*` entries in the admission registry (`recovery-bootstrap/admission/registry.json`). If one of those roots is later removed, every later Create backup fails and Chatbook refuses to start until the root is back. Live, this was an empty `~/.config/tldw_cli/tokenizers` folder, removed on the User Guide's own (since withdrawn) advice. The code path is generic: a profile's data folders and database files are registered the same way.

The refusal is ADR-126 policy, not an accident. Its 2026-09-15 owner-approved refinement tolerates an absent root only when an enrolled directory already owns it, and says "missing roots without such already owned coverage still refuse". The registry is also shared with Replace restore, which moves registered roots aside and resolves them through its journal while they are missing. So treating a vanished root as absent needs an owner decision on when absence is safe outside a replacement journal; it is not a contained fix.

TASK-34100.16.1 made both refusals name the location and give the remedy verified for folders (create it again, empty): Create backup shows `registered_storage_missing` with the path, and the refused start lists the missing paths. This task owns the behaviour itself. Evidence: `.worktrees/setup-wizard-ux-qa/evidence/g161v5-v2a/24-28`, `g161v5-v2d` (hidden traceback and registry), `g161v5-r3`.
