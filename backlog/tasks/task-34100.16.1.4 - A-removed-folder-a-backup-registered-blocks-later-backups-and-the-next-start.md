## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in TASK-34100.16.1's review round v5r2 (finding V2). Each Create backup registers the roots it copies as `backup.source.*` entries in the admission registry (`recovery-bootstrap/admission/registry.json`). If one of those roots is later removed, every later Create backup fails and Chatbook refuses to start until the root is back. Live, this was an empty `~/.config/tldw_cli/tokenizers` folder, removed on the User Guide's own (since withdrawn) advice. The code path is generic: a profile's data folders and database files are registered the same way, and so are restore-registered roots. Isolated restore registers its destination's existing private parent (`isolated.<operation>`, for example `~/chatbook-restores`, the folder the User Guide tells users to create), so removing that folder later blocks backups, Replace restore, later rollback and the next start the same way.

The refusal is ADR-126 policy, not an accident. Its 2026-09-15 owner-approved refinement tolerates an absent root only when an enrolled directory already owns it, and says "missing roots without such already owned coverage still refuse". The registry is also shared with Replace restore, which moves registered roots aside and resolves them through its journal while they are missing. So treating a vanished root as absent needs an owner decision on when absence is safe outside a replacement journal; it is not a contained fix.

TASK-34100.16.1 made both refusals name the location and give the remedy verified for folders (create it again, empty): Create backup, Replace restore and later rollback show `registered_storage_missing` with the path, and the refused start lists the missing paths. This task owns the behaviour itself. Evidence: `.worktrees/setup-wizard-ux-qa/evidence/g161v5-v2a/24-28`, `g161v5-v2d` (hidden traceback and registry), `g161v5-r3`.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 ADR-126 is amended, per the owner's ruling of 2026-11-28 (the text ships with group g23), so that a registered folder root that no longer exists is treated as absent and skipped at capture and at start admission only when all four conditions hold: (1) no pending operation, replacement journal or later-rollback record names the root; (2) its parent still exists and resolves to the registered location, not a replaced path, a mount point or a symlink; (3) a capture that skips it records the omission in the archive manifest; (4) the strict refusal stays whenever a journal names the root. This extends TASK-42115's file-root rule (`effective_roots.deleted_file_roots`) to folders
- [ ] #2 After a backup registered a folder and the folder is removed, with its parent intact and no journal or record naming it, Create backup succeeds without the user recreating the folder; the folder is not in the archive, and the archive manifest records the omission
- [ ] #3 After such a removal, Chatbook starts normally
- [ ] #4 A Replace restore interrupted while a registered root is moved aside still refuses Create backup and a normal start, and so does any missing root that a pending operation, replacement journal or later-rollback record names
- [ ] #5 A missing folder root whose parent is gone, or whose parent no longer resolves to the registered location (a replaced path, a mount point or a symlink), still refuses with `registered_storage_missing` and its path
- [ ] #6 Regression tests on a real temp HOME cover a later capture (including the manifest's omission record), the next start's admission, a journal-named root and a replaced or symlinked parent
- [ ] #7 The User Guide's "Restore a backup" note and the two refusal messages match the ruled behaviour

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Narrowed by dev's TASK-42115 (noted 2026-11-23 at TASK-34100.16.1's round-24 port onto dev b31e3e9241).** A registered *file* root deleted from a folder that is still there now holds nothing at every root consumer (`effective_roots.deleted_file_roots`), so it no longer blocks Create backup or the next start. What remains for this task is a removed *folder* root (and a file whose folder is gone, replaced or a mount point), which ADR-126 still keeps strict. The port makes the refused start's list skip such deleted file roots, so it names only what refuses.

**Owner ruling 2026-11-28 (ADR-126, a vanished registered folder): YES, with four conditions.** A registered folder root that no longer exists may be treated as absent, and skipped at capture and at start admission, only when:
1. no pending operation, replacement journal or later-rollback record names the root;
2. its parent still exists and resolves to the registered location, not a replaced path, a mount point or a symlink;
3. a capture that skips it records the omission in the archive manifest;
4. the strict refusal stays whenever a journal names the root.

This extends TASK-42115's file-root rule to folders. The ACs above are amended to it:
- AC#1 is now the ADR-126 amendment itself. Its text ships with group g23 (backup absent roots) of the 2026-11-28 burn-down plan, not in this hygiene change.
- AC#2-#4 carry conditions 1-4.
- AC#5 (new) covers the parent conditions.
- The old AC#5 (tests) is now AC#6, widened to each condition.
- The old AC#6 (User Guide) is now AC#7.

Status stays To Do.
