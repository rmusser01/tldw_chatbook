## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Strict-JSON parsing exists in three drifted families: the wire family caps depth and node count but accepts duplicate keys, the storage family rejects duplicate keys but has no depth cap, and neither does both. A tool-call argument accepted on the wire can therefore raise an uncaught validation error on the way to storage. Fifteen copies exist across provider, chat, MCP and persona modules; a private validator in the shared input-validation module is the natural home.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
PR #2738, all ACs done (AC#3 reframed to the owner's scoping decision).

CORE (AC#1/#2/#4): public `strict_json_loads` in Utils/input_validation.py
provides depth/node-count/duplicate-key options; the 4 drifted
`_strict_json_loads` (hosted_chat, qwencloud_streaming, provider_continuation,
thinking_blocks) delegate to it and all reject dup keys, so wire and storage
agree (fixes the D1 crash — a tool-call argument accepted on the wire could
raise on the way to storage); 2 `_reject_json_constant` clones deleted;
round-trip dup-key test added.

BOUNDARY FOLLOW-UP (AC#3, owner decision 2026-09-20 "only config/security
boundaries"): swept all ~40 `parse_constant=` sites. Most already pair an
`object_pairs_hook` (reject dups). The remaining gaps were hardened where they
are trust boundaries — a duplicate key is ambiguity/tamper there, not a
convenience:
  * MCP/permission_store.py — the two PERMISSIVE reads (`load()` enforcement,
    `_load_for_raw_getter()` inspection) used plain `json.loads`; a tampered
    policy file with a duplicate `global_default` took last-wins. Both now
    reject dups; the error is a `ValueError` (already caught) so the file
    fail-closes to safe defaults.
  * Chat/console_generation_settings_metadata.py — external metadata STRING
    decode (the mapping path re-serializes our own dumps, no dup possible).
  * DB/ChaChaNotes_DB.py (conversation-metadata write-validation),
    DB/VisualIdentity_DB.py + Character_Chat/visual_identity.py (4 stored-pack
    reads) — storage integrity.
  * LLM_Calls/qwencloud.py — the NON-streaming tool-call-argument parse, to
    match its streaming sibling and the continuation checkpoint (which already
    reject dups); tool-call arguments drive tool execution, so the two paths
    for the same provider must agree.
Left last-wins by the decision: generic external API-response bodies. Left
unchanged (already safe): `TTS/profile_validation.decode_options`, whose
canonical-equality check already rejects any duplicate-keyed input.

DEFERRED (not a checkbox): the purely mechanical replacement of the remaining
per-module `_reject_json_constant` one-liners with the single shared helper —
routing them all through `strict_json_loads` would impose its depth/node caps
at ~40 sites (some parse legitimately large payloads), i.e. the "consolidate
all" shape the owner did not choose.

Tests: permission_store dup-key load + raw-getter (discriminating — a dup in an
otherwise-valid file must back up / return defaults), gen-settings metadata
dup-key, qwencloud tool-arg dup-key, ChaChaNotes conversation-metadata dup-key.

Modified: input_validation.py (core), permission_store.py,
console_generation_settings_metadata.py, ChaChaNotes_DB.py, VisualIdentity_DB.py,
visual_identity.py, qwencloud.py + their tests.
