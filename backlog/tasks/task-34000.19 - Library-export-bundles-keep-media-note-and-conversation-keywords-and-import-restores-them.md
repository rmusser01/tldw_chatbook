## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: a Library power user (j4) and a researcher (j7) exported Library items, one to hand to an advisor and one as a backup. Every keyword was gone. Media, notes and conversations all export with `"tags": []`, and media metadata carries `media_keywords: null`. The Export canvas mentions nothing ("Bundle: 2 media items · text only · about 4 KB"). Keywords are these users' triage and provenance. A round-trip import cannot restore what was never written, and nothing warns them before they rely on the bundle.

Observed (verify/nl-v-l-04):
- db-keywords.txt lists the source keywords, for example media 8 'reference,markdown', note 'Meeting Notes 2026-09-30' 'meeting', note 'Index — start here' 'moc', and conversation 'Release notes draft v1.0' 'launch'.
- In the unzipped notes manifest, all three notes have `"tags": []` and `"metadata": {}`.
- j4 saw `media_6.json` with `metadata.media_keywords` null, and a conversation with tags `[]` while its DB keyword was 'homelab'.
- j7 saw tags `[]` for a note with 3 note_keywords rows.

Verified cause (origin/dev 2d34cbf80d):
- The creator reads keyword keys that the source rows do not have: `note.get('keywords')` (Chatbooks/chatbook_creator.py:1454) and `media_item.get('media_keywords')` (:1620). Both come from `SELECT *` rows with no keyword column (DB/ChaChaNotes_DB.py:17825-17826; DB/Client_Media_DB_v2.py:7200).
- The conversation ContentItem (chatbook_creator.py:841-849) carries no tags at all.
- On import, notes are created without keywords (Chatbooks/chatbook_importer.py:2406-2407), and media read the same missing key (:2772).
- Batch keyword readers already exist: `fetch_keywords_for_media_batch` (DB/Client_Media_DB_v2.py:8567), `get_keywords_for_notes_batch` (DB/ChaChaNotes_DB.py:20030) and `get_keywords_for_conversations` (:19788).

Suggested direction (the review's refined fix; a direction, not a mandate):
- Fetch keywords in batch, and write them into each item's metadata and ContentItem.tags for all three types.
- On import, re-link note and conversation keywords. ADR-057's Prompt records already carry "the canonical active keyword membership", which is the precedent.
- List 'Keywords' in the export consequence line.
- Add a creator→importer round-trip test per type.

Owning-task notes: TASK-155 (Done) fixed the wrong media column keys but not keywords. L-18 (the export canvas copy, file names and same-day overwrite) is owned by TASK-32381 and TASK-32382 and is out of scope here.

Review finding(s): L-04. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Keywords now ride in an export bundle for media, notes and conversations and come back on import, in ADR-057's shape: the item's own record carries them (`metadata.media_keywords` as a list, the note's frontmatter `tags:` line, the conversation JSON's new `keywords` list) and so does the manifest `ContentItem.tags`; import restores membership through the ordinary write paths. No schema change (`_CURRENT_SCHEMA_VERSION` stays 82); the bundle format is additive (old bundles import unchanged).

- **Creator** (`Chatbooks/chatbook_creator.py`): one batch read per type before the loop -- `get_keywords_for_notes_batch`, the module function `fetch_keywords_for_media_batch` (ordered, filters deleted media), `get_keywords_for_conversations` (row dicts; the text is `row["keyword"]`). The old `note.get("keywords")` / `media_item.get("media_keywords")` reads never matched a column. Items with no keywords carry `[]` in both places.
- **Importer** (`Chatbooks/chatbook_importer.py`): `_ensure_chachanotes_keyword` is get-or-create (case-insensitive active lookup; `add_keyword` undeletes a soft-deleted row; `ConflictError` answered by one more lookup -- the two-importers race). `_restore_chachanotes_keywords` links after the item is created (notes after `add_note`; conversations after the per-conversation transaction commits, so a refused keyword never rolls a conversation back), skips blanks, links casefold duplicates once, and logs a failure with the item id and the exception class only -- never the keyword (ADR-057's diagnostics boundary) -- without failing the item. Notes take the manifest tags first and the frontmatter `tags:` line only when the manifest gives none (a hand-edited legacy bundle); conversations take the JSON `keywords` first and the manifest tags as fallback. Media import was already correct and now receives the list.
- **Model**: `ContentItem.from_dict` coerces `"tags": null` to `[]` (Review Focus 5).
- **Consequence line** (`Library/library_export_state.py`): `text + keywords only` for the media-only scope (the "only" still means "never the original media file"), `text + keywords` for the notes, conversations and prompts scopes (superseded by fix round 1 below: Everything is media-bearing and also keeps "only").
