## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: if the caret is in the Notes filter and the user opens the command palette (Ctrl+P) and closes it, focus sometimes does not come back to the filter. It lands on the Notes rail row, `#library-row-browse-notes`, so typing no longer reaches the box.

Evidence:
- **Measured rate.** `Tests/UI/test_library_notes_filter_fast_path_and_draft.py::test_escape_in_the_filter_keeps_the_draft_and_the_footer_says_typing` asserted focus was back in the filter after the palette closed. It was red 4/8 on `38cf61faae`, 2/6 on `5487e54639` and 2/6 on that round's working tree, with `assert 'library-row-browse-notes' == 'library-notes-filter'`. Polish-1a Task 5 fix round 2 weakened that arm to a footer-agrees-with-focus check, so the PR gate stays deterministic. This task restores the focus assertion.
- **Not every flow reproduces it.** A simpler one-boot probe (open Notes, click the filter, Ctrl+P, Escape, wait 1 s, twice) kept focus in the filter 3/3 on dev `38623632e9` and 3/3 on the branch. The race needs the resume's tree work to land in the window described below.

Mechanism, traced with logged `set_focus` and `_sync_library_canvas` calls in a failing run:
1. The resume's Notes visit refresh (`_refresh_library_visit_surfaces` → `_supersede_library_notes_navigation` → the tree's initial load) runs several Notes canvas syncs.
2. One sync recomposes the canvas and prunes the focused filter box. Textual's `_reset_focus` then parks focus on `#library-browse-library-grip`.
3. A later sync (a tree slice page, the trash load, `_reconcile_library_entry_state`) captures that grip as the focus identity, with stage `rail` and an empty role.
4. That sync's replay (`_restore_library_notes_after_targeted_sync`) resolves the identity to the Notes rail row.
5. The earlier sync's restore of the filter is vetoed, because the prune reset reads as a user focus move.

This is the same family as TASK-34000.85 and TASK-34000.89: a transient fallback focus is trusted as the user's.
