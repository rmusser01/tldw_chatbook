## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: a stress tester (j6) added one legacy file and one Windows-edited file to a synced folder, which is ordinary for a researcher or power user whose notes come from many tools. One latin-1 file (byte 0xE9) stopped the whole folder. Replacing it with a file that mixes CRLF and LF line endings stopped it again. While either file was there, nothing in the folder synced: the deletes and renames elsewhere in the folder were not processed until both files were gone. The message named neither the file nor the cause, and the suggested next action ("Check changes") just repeats the failure.

Observed (verify/nl-v-n-16 at 160x45):
- 03-check-latin1: Manage sync folders shows "Check failed — NotesSyncRootRefused. Next: Check changes.". The root row reads "⚠ Needs attention · Check failed — NotesSyncRootRefused · Next: Check changes".
- 05-app-edit-while-blocked: in the same blocked state, an in-app edit to a note in that folder shows "Saved 21:43 · Next: Keep editing; changes save automatically.", and the tree still shows "▾ Verify Sync ⇄ Sync managed". The user gets no sign that the edit is not reaching disk.
- The app log reads `reason=unsupported_encoding`, then `reason=mixed_newlines`.

Verified cause (origin/dev 2d34cbf80d):
- Notes/notes_sync_filesystem.py:132-150 `_parse_supported_text` raises a per-file gate error: `unsupported_encoding`, `mixed_newlines` or `unsupported_newline`.
- Notes/notes_sync_runtime.py:930-946 counts those per-file refusals, then raises one `NotesSyncRootRefused("root_discovery_incomplete", reason_code=<dominant>)` for the whole root. The plan already has a per-file skip channel: `plan.item_skips`, which Library/library_notes_lasting_sync_state.py:895-908 renders as 'skipped' rows with the file's relative path.
- The root row comes from `check_failure_row` (library_notes_lasting_sync_state.py:1189-1204), which looks the code up in `_CHECK_FAILURE_ROW` (:1122-1135). That table has none of the per-file gate codes, although `_CHECK_REFUSAL_COPY` (:1008 onward) has copy for them. So the row falls back to the exception class name 'NotesSyncRootRefused' and the next action 'sync_now'.

Suggested direction (the review's refined fix; a direction, not a mandate): record per-file gate refusals as skip rows that name the file, for example "Skipped — not UTF-8: latin1.md" or "Skipped — mixed line endings: notes.md", and let the rest of the folder sync. Keep a root-level refusal only for failures that really affect the whole root, such as a listing failure or an offline folder. Keep the `_CHECK_FAILURE_ROW` and `_CHECK_REFUSAL_COPY` key sets equal, pinned by a test, so that a code with copy can never fall back to a class name.

Owning-task notes:
- TASK-32578 owns writing copy for the three reason codes that still have none in the refusal copy table.
- This task owns the behaviour (one bad file must not block the folder, and the skipped file is named) and the drift between the two existing tables for codes that already have copy.
- The false '⇄ Sync managed' / 'Ready' health shown while a folder is blocked belongs to this review's N-02 finding (TASK-34000.2). This task does not change those badges.

Review finding(s): N-16. Source: qa/notes-library-ux-review-2026-10-02/report.md
Owner question 4 ruling (P1-C batch, 2026-10-23, controller: YES): every reason
`PosixNotesSyncFilesystem.observe` can raise for ONE file becomes a per-file skip --
the three this task names (`unsupported_encoding`, `mixed_newlines`,
`unsupported_newline`) plus `unsupported_metadata`, `max_file_bytes_exceeded`,
`non_regular`, `multiple_links`, `link_or_reparse`, `target_changed_during_read`
and `operation_failed`. `missing_target` (the file vanished mid-walk) stays silently
ignored, as today. A root-level refusal (`NotesSyncRootRefused`) is kept only for a
listing failure or a non-gate filesystem error of the root itself.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**What changed.** A per-file gate refusal from `PosixNotesSyncFilesystem.observe` is now that
file's own skipped row, never the folder's refusal. The gate set is named once
(`notes_sync_filesystem.FILE_GATE_REASON_CODES`, ten codes, owner Q4 = yes; `missing_target`
stays silently ignored). `observe_root` records a refused file by path, logs reason codes and
counts only (TASK-32243 -- the root id was dropped from the line too, because the diagnostic
inventory reads `root.root_id` as a path-shaped expression), skips the refused path's binding in
the bound loop, and passes `refused_files=` into `ReconciliationInput`. The pure model owns the
contract: `ReconciliationInput.refused_files` (tuple of `ReconciliationItemSkip`) is type-checked,
refuses a path that is also a binding (`ValueError`), is hashed into the observation token, and
is appended to `plan.item_skips`. A listing failure and a non-gate filesystem error still raise
`NotesSyncRootRefused`. Copy: `_FILE_GATE_SKIP_EFFECTS` (one plain sentence per gate code, merged
into `_ITEM_SKIP_EFFECTS`) and the nineteen `_CHECK_FAILURE_ROW` rows that make the row-phrase
and refusal-copy key sets equal (pinned).

**Data integrity (the batch's review question).** A refused BOUND file is excluded from the
observed bindings, so a Check can never read it as a deleted file; the pure model refuses the
input if a refused path is also a binding (negative control: disabling the runtime exclusion
makes `test_a_bound_file_that_turns_non_utf8_is_skipped_not_planned_as_a_deletion` fail with
that `ValueError`, not with a deletion). A skip produces no action, so apply never writes over or
deletes a refused file; the Pilot asserts the fixtures' bytes after activation.

**TASK-32244 pins flipped by name (intended).** `test_root_discovery_refusal_names_its_count_
and_dominant_reason` -> `test_two_read_only_files_are_two_skip_rows_and_the_rest_is_planned`;
`test_root_discovery_refusal_carries_a_non_permission_dominant_reason` ->
`test_a_mixed_newline_file_is_one_named_skip`. TASK-32244's intent (the dominant reason reaches
the UI) is kept per file, by name. New root-level pin: `test_a_listing_failure_still_refuses_the_
whole_root`.
