## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** In a chat that holds a pending agent-handoff draft, a send whose handoff-draft save fails while the send is preparing (the user keeps typing and that write fails) is refused with 'Draft custody is unconfirmed.' after its preparation has already moved to COMMITTING. Nothing pauses or abandons that preparation, so it stays COMMITTING with no pause kind: the same state TASK-33621.53 fixed for a failed durable commit, which neither the card nor the shelf can end. Once the handoff write succeeds again, every later send in that chat is refused with 'A run is already running in this tab.' and no save is ever attempted.

**Where it was seen.** Found by the TASK-33621.53 review (2026-10-29) by reading; reproduced the same day on fix/task-33620.3-durable-commit-failure (origin/dev 38c9d2edcf plus the TASK-33621.53 fix, which does not touch this path) with a throwaway probe on the real ConsoleChatController and ConsoleChatStore. Set-up: a session with a pending v2 handoff (durable revision 1); the session draft changed during preparation (set_session_draft from inside stage_durable_turn_identity); the persistence's update_agent_handoff_draft returned False. Observed: the send returned accepted=False 'Draft custody is unconfirmed.'; the preparation stayed COMMITTING (pause_kind None); no commit was attempted. After the handoff write succeeded (drain_agent_handoff True), the next send returned accepted=False 'A run is already running in this tab.' and the preparation was still COMMITTING. Not yet reproduced on the real screen or live.

**Cause, as read.** _controller_accept_durable_turn (Chat/console_native_commit.py) returns 'Draft custody is unconfirmed.' when store.drain_agent_handoff is False, after the caller in console_chat_controller.py moved the preparation READY to COMMITTING. Unlike the commit-failure branch, it neither pauses nor abandons the preparation. A MANUAL send checks custody once earlier (top of submit_draft), so only a handoff write that fails between the two checks reaches this. Non-manual origins (queued prompt, hook continuation, machine follow-up) skip the early check, so a session already in 'review_required' or with a failed writer may reach it directly; that variant was not probed. A sibling to check in the same fix (read, not probed): right after READY to COMMITTING, the controller returns _block('Hook continuation is no longer current.') for a stale hook continuation, and _block also neither pauses nor abandons the preparation.

**Suggested direction.** Confirm custody before READY to COMMITTING, or on this refusal pause the preparation as a shelf-releasable kind (or abandon it with its echo) so the card and the shelf can end it. Reproduce on the real screen before fixing.
