## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fixed in burn-down PR 5 of the B2b follow-ups (stacked on PR #3441). Restore, not a toast (the triage's recommendation; no new copy).

- **On dev:** present. The same-kind branch of `_land_import`'s `select` cleared the search, wrote the box (with no `prevent`) and reset a relevance sort to name, then returned when its second decision failed, leaving all of it applied. On the base the new test read `('', '', 'name_asc')` after a draft was started during the landing's refresh.
- **Fix (`personas_screen.py`):** `_clear_search_for_import_landing` snapshots the search, sort and box value and the count of the user's list changes, clears them, and writes the box under `prevent(Input.Changed)` (the TASK-33910.39 idiom; on dev the write posted it, which armed a second debounced read). When the second decision fails, `_restore_search_after_import_landing` puts the state back first, writes the box under `prevent(Input.Changed)` (a restore is no newer intent) and starts one read through the search worker, whose currency check lets a later typed search supersede it. The import intent cannot tell a draft started meanwhile (restore) from a search typed meanwhile (keep), so a counter, `_list_state_changes`, decides: every user change to the list bumps it (the search handler, `_apply_mode`, `_cycle_sort`, `_apply_tag_filter`, Escape's clear), and the restore runs only when it has not moved since the clear.
- **Fix round 1 (review of `c3656b399c`):** the first cut compared the list's values with what the clear left, so a change that ended on those values (a key typed and erased, a switch to Lore and back) got the old search restored over it. That was new with this PR; on dev the search simply stayed cleared. The counter replaces the comparison.
- **Test:** `test_a_landing_that_then_toasts_restores_the_search_and_sort_it_cleared` (`Tests/UI/test_roleplay_import_app.py`, with `_hold_the_landing_refresh`): a relevance search for "Abel", an import whose landing refresh is held, then one of six things. A draft gets the search, box and sort back, the list is read once with "Abel" and shows one row, and the draft is kept. A newer search "Zed" stays. A key typed and erased, a switch to Lore and back, the sort cycled back to Name, or a tag picked and cleared leaves `('', '', 'name_asc')`, and no read of "Abel" happens. The four round-trip cases were red on `349a9b09d7` at `('Abel', 'Abel', 'relevance')`.
- **Mutations:** M51-A (no restore) and M51-C (the restore's box write posts `Input.Changed`: reads `['', 'Abel', 'Abel']`) turn the draft case red. M51-B (no newer-change check) turns the five other cases red. M51-D (the value comparison back) turns the four round-trip cases red. M51-E1 to E4 (one site not counted: the search handler, `_apply_mode`, the sort cycle, the tag pick) each turn their own case red. Escape's clear is counted too; it cannot be the only change in this flow, because it acts only on a search or tag that is itself counted.
- **Live (mounted harness, 120x36):** after the failed landing, the box reads "Abel", the sort chip "Relevance", the list title "Characters 1 of 3" with only Abel Host, and the "Draft Hero" draft is kept with "Unsaved changes" (`.b2b-evidence/followups/fu-landing-evidence/live/head-search-restored.*`).
