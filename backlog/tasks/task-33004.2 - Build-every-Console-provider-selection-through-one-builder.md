## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This subtask absorbs task-32859.

Commit 097411fca0 already extracted a single selection core (ConsoleSelectionCore and resolve_console_selection_core, Chat/console_chat_controller.py:593-682). Two builders still construct the full ConsoleProviderSelection separately:
- build_console_provider_selection_from_settings (:685-720)
- the screen chain at UI/Screens/chat_screen.py:9614, :9631, :9666 and :9687, which constructs its own at :9731

ConsoleProviderSelection is constructed at eight sites. The _provider_settings helpers also disagree: Chat/console_session_settings.py:1996 is registry-aware per ADR-146, while Chat/console_provider_gateway.py:7171 raises.

The switcher resolves a selection and readiness for many provider·model pairs. A third path would recreate exactly the drift task-32859 documents: the PR-2668 fix had to be applied twice. Removing the screen's copy also frees lines in chat_screen.py, which has only 32 lines of headroom. No ADR is needed, because ADR-006 ('Console owns effective session resolution') already covers the consolidation.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**One builder.** `build_console_provider_selection_from_settings` (`Chat/console_chat_controller.py`) is the only code that builds a `ConsoleProviderSelection` from Console session settings. It now takes the screen's extra inputs: `endpoint_policy` (a policy that owns the provider/model makes the endpoint ephemeral and turns the configured-endpoint fallback off), `identity_session` and `global_user_name` (a named persona/character with a trusted template sends a fresh expansion), next to `workspace_context` and `legacy_model`. `ChatScreen._build_console_provider_selection_from_settings` only gathers the screen's inputs (workspace, the session's endpoint policy, the session, its own display name, read lazily as before) and calls it; `ConsoleChatController._provider_selection_for_session` does the same with the controller's inputs. The identity pick (kind-appropriate name and template) lives once in `console_roleplay_identity.session_send_system_prompt`, used by the builder and by `_resolved_system_prompt`. One controller-path change: a character session with no usable template now keeps its settings prompt (the screen's rule) instead of the controller's own `system_prompt`.

**Blank Max tokens.** The controller copy refilled a blank session Max tokens from the provider default (`build_default_console_session_settings(app_config, provider, None)`); the screen copy, which is the production send path, never did. The one builder keeps the session value: ADR-095 D3 resolves a blank at Apply time, so the stored value is the effective one. Voice preflight, compaction, the thinking-history policy and the project-instruction preview now build the same selection the send builds.

**Other construction sites (AC#2), none built from Console session settings.** Pinned by `test_only_the_builder_constructs_a_selection_from_session_settings`:
- `ConsoleChatController._provider_selection`: a bare controller's own attributes, used only when the session has no settings.
- `console_turn_context._detached_selection`: a deep copy of an already-built selection.
- `console_visual_evaluation.resolve_visual_evaluation_model`: an explicit provider/model for an evaluation run.
- `console_agent_bridge._StreamingModelAdapter._resolve_routed_resolution`: a sub-agent routed to an explicit provider/model/endpoint.
- `console_side_chat._build_selection`: the side chat's typed "provider/model" string.
- `PersonasPreviewController._selection_from_defaults`: the Personas screen's preview of a `[character_defaults]`/`[chat_defaults]` section; not a Console session (no workspace, endpoint policy or identity; the section's model is explicit by design).

**Model chain (AC#3).** `console_session_settings.configured_provider_model` is the only spelling of model -> api_model -> default_model. The core, the gateway's send fallback, `resolve_effective_chat_configuration`, the settings modal's `_default_model_for_provider` and agent routing's `_configured_model_for` call it. Blank values and the `None`/`null` placeholders are skipped, as the modal and the core already did; the gateway and the effective-configuration resolver used to accept a placeholder as a model.

**Provider-settings lookup (AC#4).** `console_provider_settings` (was the private `_provider_settings`) is registry-aware (ADR-146) and returns an empty mapping for a malformed or ambiguous table. The gateway's two call sites pass `strict=True` and so keep its raising policy (the QwenCloud "must be a configuration table" block and the context-window target); the gateway's own copy is deleted. The core now reads through it too, so a registry entry's first model is its configured model and an aliased table (`[api_settings.OpenAI]`) is found; the gateway already fell back to both, so the resolved send model is unchanged. Left alone on purpose: `provider_setup_persistence._provider_settings` (ownership-scoped writer for `api_settings`; registry entries are not setup-owned), the settings modal's and the endpoint-template modal's `api_settings` scans (both handle registry entries through their own entry lookup).

**AC#5/#6/#8.** Effective-settings precedence (`build_default_console_session_settings`) is untouched; the Console settings suites fail the same names at base and head. The PR-2668 identity rule exists only in `resolve_console_selection_core` (the modal's `_snapshot_provider` reference is the draft-snapshot validator, not a selection). chat_screen.py: 25,496 -> 25,414 lines, 766 -> 766 methods. console_chat_controller.py: 30,701 -> 30,659 (R2 cap 30,698). console_settings_modal.py: 7,764 -> 7,761.

**AC#7 is open.** Switch model does not exist until TASK-33004.4. Per controller ruling R4, AC#7 means "the switcher has no selection logic of its own" and is checked at that task's review; switcher rows take readiness from the screen-injected config-only resolver and build no selection. This task moves to Done when that review ticks it.

**Tests.** New in `Tests/Chat/test_console_selection_core.py`: endpoint policy, identity (six cases), blank Max tokens, registry and alias lookup in the core, the chain helper, the strict lookup, the controller path's endpoint policy, and the construction-site inventory. New in `Tests/UI/test_console_session_settings.py`: `test_screen_send_selection_keeps_endpoint_workspace_and_identity` (passes at base too; it pins that the screen's fields survive). Mutants (builder ignores the policy; builder drops identity; screen or controller drops the policy) each fail at least one of them.
