## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while fixing TASK-33621.70 (2026-11-21). Now that Retry anyway is enabled for composer sends, pressing it reaches the provider and the reply arrives, but the trace records no call for that request although Capture is on. The interrupted call stays `dispatch_started`, and the Inspector's trace for the answered turn ends at it.

Evidence:
- Live, fix branch fix/task-33621.6-retry-capture-regression (origin/dev dc371f0842 plus the .6/.70 fixes, which do not touch this path); claude-haiku-4-5 through the review proxy. After a SIGKILL mid-request and a relaunch, Retry anyway made 1 POST and the reply "Green." arrived. `console_trace_calls` then held the killed call (`dispatch_started`) and no call for the retry. Captures: tools/evidence/bd5/U06/retrycap-2026-11-21/02-04.
- Mounted test: in `Tests/UI/test_console_trace_recovery_after_provider_error.py::test_retry_anyway_redispatches_a_genuine_unknown_delivery`, the retry goes through `retry_dispatch_recovery`'s `_resolve_dispatch_retry_context` branch (route RETRY). The gateway's `_reserve_trace_call` is never entered, and the trace keeps only the 429 call (`error`).

Decide whether this is intended. A restart retry may be unable to rebuild trace provenance, but then the trace (or the panel) should say the retry was sent uncaptured. Otherwise capture it like any other Capture-On call.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
Owner decision, 2026-11-21: record the retry. While Capture is on, **Retry anyway** reserves and records its own trace call like any other send. The killed call it replaces is closed as abandoned or unknown. This decision was recorded on the TASK-33621.6/.70 branch (fix/task-33621.6-retry-capture-regression), which does not implement it; that needs its own change.
