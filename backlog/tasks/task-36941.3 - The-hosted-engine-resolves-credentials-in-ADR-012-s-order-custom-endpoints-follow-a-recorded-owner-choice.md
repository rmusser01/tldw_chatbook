## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ADR-012 (`backlog/decisions/012-provider-credential-settings-boundary.md`, Accepted) governs provider credential precedence:
- Its 2026-09-19 amendment (TASK-32806.2) rules that the stored `api_settings.<provider>.api_key` outranks the provider's environment variable, which is the fallback. The reason: a key the user types into Settings must take effect, where env-first let a stale shell `OPENAI_API_KEY` silently override what the UI showed.
- Its 2026-10-17 amendment from TASK-33641.11 ("a recorded credential source decides") makes a recorded `credential_source` decisive.
- Its keychain amendment is not built yet (TASK-34100.31).

The hosted provider engine (`LLM_Calls/hosted_provider_engine.py` `_resolve_api_key`, the 33 engine presets) resolves explicit, then environment, then stored. The custom-endpoint registry (`Chat/custom_endpoint_registry.py:495` `resolve_entry_credential`) resolves environment before stored, has no `credential_source`, and follows `backlog/decisions/146-console-custom-endpoint-registry.md`, which recorded env-first as mirroring the provider semantics of its time. moonshot, zai, qwencloud, the bridged handlers, `config.get_api_key` and readiness already put the stored key before the environment variable when no source is recorded. Remaining gaps have owners: TASK-35227 (key readers that ignore a recorded source, including `config.get_api_key`), TASK-35369 (Moonshot/Z.ai readiness leftover key) and the `chat_with_google` env-only case named in CLAUDE.md.

**Owner decision (2026-10-25, re-confirmed with ADR-012 in view): keep ADR-012, and align the hosted engine to it.** That decision did not cover custom endpoints, which have their own ADR. **Owner decision for custom endpoints (2026-10-26): keep the existing order that ADR-146 records** — the entry's own `api_key_env` reference, then its stored `api_key`. The env var there is one the user named on the entry, not a provider-default variable, so ADR-146 needs no amendment. The engine's existing fail-closed handling of an unusable stored key stays.

Source: architecture review 2026-10-25, `Docs/QA/architecture-review-2026-10-25/report.md` §F11; claim-by-claim verification in `Docs/QA/architecture-review-2026-10-25/verification.md` (origin/dev 7a5e2513c5).

## Implementation Plan

1. Engine (`LLM_Calls/hosted_provider_engine.py::_resolve_api_key`): keep the caller-key branches as they are. With no caller key, let readiness's own resolver (`Chat/provider_readiness.py::resolve_provider_credential`) pick the key, so the engine and readiness use one resolver. Keep the fail-closed error for an unusable stored key wherever the recorded source reads that key (no source, or "stored").
2. Readiness already resolves engine presets through `resolve_provider_credential`, and Console passes readiness's key to the engine as the caller key. With step 1 the non-Console spend path (`chat_api_call` with no key, the model catalog) uses the same function.
3. Custom endpoints: no code change. Pin `resolve_entry_credential`'s ADR-146 order (the entry's `api_key_env`, then its stored `api_key`).
4. Tests: one parametrized engine test for a preset with both a stored key and an exported variable (no source, "stored", "environment", "none") that also checks readiness reports the source the engine spends; one test pinning the custom-endpoint order. Rewrite the existing assertion that pinned env-first. Show each new test red before the fix.
5. Docs: update the credential-precedence table in `Docs/Architecture/llm-providers.md` (with an ADR-012 link), the engine module docstring, and add one CHANGELOG entry under Unreleased.
6. Run the covering tests with xdist through run.sh, run Tests/Architecture serially, then preflight.
