## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From TASK-33621.153's review. TASK-33621.153 stops a chain's automatic-work wall clock while a wake waits at the Ask compaction trigger (compaction_ask). The ledger ends that hold at any admission in the allowance (_check_admission resolves the allowance root), including other automatic work under the same root, such as a wake claimed in a chat the agent started. claim_wake has no paused-status gate, and the coordinator's in-memory pause is keyed per (conversation, chain), so that other wake runs. Ending the hold then is the safe choice, because that work's running time must count. But the held chat's wait is not re-held afterwards: the root is set active, the rest of its wait counts, and a late /compact can again be refused (wall_budget, 'Paused: time limit'). The review's probe showed this (root wall_seconds=10 with a member from prepare_chat_start/accept_chat_start; root paused compaction_ask at 1004; member admitted at 1005; root retry at 1100 refused wall_budget). Tests/DB/test_automatic_work_deadlines.py::test_other_automatic_work_in_the_allowance_ends_the_hold pins today's conservative behaviour, and ADR-134 and the User Guide say so. The full fix probably needs the ledger to know which conversations are still held at compaction_ask under a root, so the hold can start again once the other work settles.
<!-- SECTION:DESCRIPTION:END -->
