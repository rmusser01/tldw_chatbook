## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-33620.15.3 moved main-thread generation-2 collection out of Console send windows by re-freezing the long-lived heap at idle points, with a compaction (unfreeze, full collection, refreeze) bounding frozen garbage. In its live round 9 (2026-10-20, against origin/dev 2d071d6d71) the branch's five worst UI-loop pauses were all compactions: 492/611 ms CPU/wall at worst and 296 ms CPU median, against dev's worst automatic generation-2 pass of 202/212 ms. There were 27 compactions over 24 conversation switches and 20 runs, because a switch away from a transcript frozen while shown owes one. A compaction starts only after 5 s without input and with nothing in flight, but once started it cannot be interrupted, so a key pressed during it waits up to about 0.6 s. No acceptance criterion of TASK-33620.15.3 measured that delay. Owner sign-off is needed on whether this trade-off stands or the compaction cadence changes.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Not done: the goal cannot be met while TASK-33620.15.3's re-freeze stays. It waits for the owner's ruling (AC#5).

**The ruling asked for (2026-10-20).** "Bound the pause first": no idle maintenance may pause the UI loop for longer than origin/dev's worst automatic generation-2 pass. The frozen garbage must still be reclaimed, nothing may run in a send window or while the user types, and 15.3's send-window gain must stay (AC#4). The ACs were rewritten to say this.

**Why no design meets it.** On CPython, garbage in the frozen set can be reclaimed only by one uninterruptible collection over the whole heap, boot heap included. 3.13 and 3.14.5+ run the same collector as 3.12 (ADR-198, Python versions).
- Probe on 3.12.11, a scratch pytest file deleted afterwards. Cyclic garbage was frozen while live, then `gc.unfreeze()` was called. The garbage survived `gc.collect(0)` and `gc.collect(1)`: both took 0 ms and reached none of it. It died only in `gc.collect(2)`. That pass took 36, 39, 46 and 56 ms as the heap grew from 231K to 431K, 631K and 1.03M objects, and a pass over the same heap with no garbage took 31, 38, 47 and 54 ms. Its cost follows the whole heap, not the garbage.
  - So splitting the reclaim across idle slices is not possible: generations 0 and 1 never reach frozen objects, and the generation-2 pass is a single step.
  - Aborting a compaction when input arrives before it starts, or waiting longer before it, changes how often a key collides with it. It does not shorten it.
- Live, 15.3's round 9 (same day, same protocol as AC#1). All 27 compactions took 235-492 ms of UI-loop CPU. Fitting each compaction's collection CPU to the objects it freed gives 235 ms plus 1.27 ms per 1K objects; the 26 compactions after a switch alone give 261 ms plus 0.72 ms per 1K. The boot heap ADR-198 freezes is about 625K of those objects. Origin/dev's worst automatic generation-2 pass in that round took 202 ms of CPU. Even a compaction with no garbage is over the bound.
- Live smoke under a lighter load, 2026-10-20 (TASK-33620.15.10's round). The same profile and protocol ran on both arms back to back: chats of 4 and 3 turns, 6 switches, 4 run cycles, host load 7-9.
  - The branch's 7 compactions took 176-220 ms of CPU (median 186).
  - Origin/dev's worst automatic generation-2 pass took 85 ms of CPU (median 63).
  - Small chats shrink dev's passes, but not the boot heap a compaction has to scan.
  - Compacting only past a size bound makes compactions rarer but longer, because each one frees more. The 2026-10-19 round showed this: 212-373K objects freed at once took 2.1-2.8 s of CPU.
- The only way to meet AC#1 is not to freeze after boot: collect the unfrozen heap at idle without freezing it. Such a pass scans what dev's automatic pass scans, and nothing is stranded. But it keeps almost none of 15.3's gain, so AC#4 fails.
  - Dev's generation-2 passes follow allocation: in round 9's four dev latency launches, 97 of 139 came exactly 11 generation-1 collections after the one before, the minimum CPython allows. A send window allocates enough for two to five of them.
  - Best case: a collection run exactly at Enter, earlier than any idle point could. It would have removed 8 of the 45 generation-2 passes in round 9's 16 dev send windows. Median main-thread generation-2 CPU per window: 189 -> about 162 ms. The re-freeze measured 189 -> 77 ms.
  - The passes left in each window would stay full size, so the longest callback in a window would not improve.

**Options for the owner.**
1. Keep the current cadence. Send windows keep the measured gain. A switch away from a frozen transcript costs one compaction of 235-374 ms of CPU (round 9) after 5 s of quiet, and a budget compaction comes about every 20 runs (round 9: 492 ms). A key pressed while one runs waits until it ends.
2. Replace the re-freeze with an idle collection that freezes nothing. AC#1-#3 hold by construction, but most of 15.3's gain is lost (estimate above, not measured live).
3. Drop TASK-33620.15.3 and keep origin/dev.
