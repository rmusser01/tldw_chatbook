## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Binding a tldw server lives inside a Settings method that saves the address and token to config.toml before it binds. When the bind fails, the new values stay on disk, although ADR-033 promises that a failed commit leaves every observer on the old binding. The connection test in ServerSwitchModal reports "Reachable (HTTP n)" for any server that answers, so it cannot say "this is not a tldw server", and its TLS settings are not guaranteed to match the client that will be bound. Setup is about to gain two more places that bind a server, so the commit needs one owner first.

The approved spec moves the commit into one app-level coordinator used by every surface that binds, with rollback on disk, and adds one shared, app-free probe with specific outcomes (decision D3, part 4; ADR-033's 2026-10-03 amendment). Binding still prepares Sync v2 exactly as Settings does today (owner ruling Q5), and server-token storage is unchanged. This slice is independent of the wizard work.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D3 part 4, §4.7 item 6, §8.1 (tldw server fixtures), §10 F3.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Before any production change, Implementation Notes record exactly what Sync v2 preparation sends to and stores on a real tldw_server when a server is bound (at least the computer's display name), and the spec's disclosure sentence (D3 part 4, §3.4) is corrected if it differs
- [ ] #2 Every bind goes through one app-level coordinator in its own module. Settings and ServerSwitchModal use it, and an architecture guard fails if any other module writes [tldw_api] or the runtime binding
- [ ] #3 When a bind fails after the config write, the prior [tldw_api] values are restored on disk and any keyring token stored in that attempt is removed, so config.toml, the keyring and every in-memory observer stay on the old binding
- [ ] #4 Test connection reports exactly one of: can't reach the address; a tldw server that rejected the token (401/403); answered but not a tldw server; certificate not trusted; blocked by chatbook's network policy; connected and token accepted; or a tldw server with no token checked. Each uses the spec's D3 copy
- [ ] #5 'Not a tldw server' is decided from the identity the server's own health and docs-info endpoints report, so a reverse proxy in front of a real tldw_server is recognised as one
- [ ] #6 The probe uses the same TLS verification, CA bundle, proxy and egress policy as the client that would be bound, so a certificate result always agrees with what the bound client does
- [ ] #7 The token check does not change server state. If tldw_server offers an authenticated read endpoint, it replaces today's POST to the sync endpoint, and the choice is recorded in Implementation Notes
- [ ] #8 Server-token storage and Sync v2 preparation behave exactly as Settings does today; only the probe copy and the rollback change what a Settings user sees
- [ ] #9 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: a real tldw_server: success; a wrong token (401); a wrong port (not a tldw server); the server stopped (unreachable); the server behind a reverse proxy; and a forced bind failure that leaves config.toml exactly as before. Evidence is recorded in Implementation Notes
- [ ] #10 New behaviour is covered by tests that fail on the pre-change code (RED verified), and no module-size or ADR-097 ratchet is raised
- [ ] #11 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
