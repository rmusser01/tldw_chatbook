## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the PR #2938 thread triage and its checkpoint review. PR #2938 (TASK-33621.14) merged as c3e2ecd3fb, so its code is now on dev:
- tldw_chatbook/UI/Wizards/first_run_step_guard.py defines provider_switch and clear_contained_error;
- FirstRunSetupWizard.py's _select_provider_option wraps the pick in `with step_guard.provider_switch(...)`.

The bug reproduces on dev now. The pick is dispatched from three handlers: _on_provider_highlighted, _on_provider_list_interacted and _on_provider_chosen.

After the first interaction with the provider list, one arrow press or one click reaches _select_provider_option twice. Textual's OptionList posts OptionHighlighted, then ProviderChoiceList.Interacted on a key, or OptionSelected on a click. If the first pass fails after selected_provider_key moved (e.g. capture_provider_config_precondition raising OSError), the second pass is a no-op re-pick. provider_switch's success path then calls clear_contained_error, which removes the line. The error is logged and commit re-runs discovery, but the user is never told. Only the very first interaction, and Enter/Space on the already-highlighted row, dispatch once. PR #2938's User Guide sentence ('A failure after the new provider is already selected leaves it selected, and the line then names no other provider') and the provider_switch docstring ('its line names none') therefore describe a line that most paths never show.

Evidence: PR #2938's test_a_switch_that_fails_after_selecting_does_not_name_the_old_provider (Tests/Wizards/test_first_run_provider_catalog.py) passes only because it resumes a session with OpenAI already chosen, so its failing Down press is the list's first interaction. Its docstring records that later presses re-run the pick as a no-op that clears the line. Re-run on dev with the list arrowed onto OpenAI first, instead of resumed there, the failing Down press runs _select_provider_option twice for Anthropic. The OSError is reported as a contained error, and the pinned line is empty afterwards, so the test's `assert "went wrong" in message` fails.
<!-- SECTION:DESCRIPTION:END -->
