## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: once during the accessibility journey (Sam, keyboard-only, low vision, j5), the keyboard stopped working entirely. Tab, F6, F1 and Ctrl+P all did nothing, and only a mouse click brought it back. For a keyboard-only user that is a hang with no way out.

Observed (j5, 80x24):
- Setup: resize 120 → 80 on Search/RAG with focus on a Sources checkbox, then Shift+Tab ×27 to the rail row 'Notes (122)' and Enter.
- Then 45 Tabs changed 0 cells, F1 opened no panel and Ctrl+P opened no palette. The process was alive and idle (0.1% CPU).
- One mouse click on '▸ Journal' restored input, and F1 worked straight after.

What the verifier proved and did not prove:
- NOT proved: the full hang. It did not reproduce naturally in 20 attempts, and j5's two exact replays also failed. tmux key loss cannot be fully ruled out for the original episode.
- Proved by instrumentation: one instrumented run (h-focus-instrumented-nl-v-s-10-5.log) recorded 7 focus writes to widgets that were already being removed (`pruning=True`, `display=False`) during ordinary rail switches. The targets were:
  - `#library-media-type-filter` ×3;
  - `#library-conversations-filter`;
  - `#library-prompts-filter`;
  - `#library-notes-filter` ×2.
- Proved by a minimal repro on Textual 8.2.8 (textual-dead-focus-mechanism.out): focusing a widget while it is being pruned leaves `screen.focused` on the detached widget after removal. Keys then reach no binding (F1 is not delivered) until a click.

Cause:
- Verified (origin/dev 2d34cbf80d): all 7 dead writes in the log have the same stack. Each goes through the list-entry focus path:
  - `_focus_library_list_entry_if_current` (UI/Screens/library_screen.py:10803, call at :10829);
  - then `_focus_library_list_entry` (:10878), which calls `self.set_focus(control)` at :10930 and :10943.
- It is reached from two places: screen after-refresh/idle callbacks (5 writes) and the retry timer's `_tick` (:10595; 2 writes) from `_retry_library_list_entry_focus_while_armed` (:10552).
- The entry-focus picker chooses a list filter that the canvas recompose is already removing. Nothing in `BaseAppScreen` (UI/Navigation/base_app_screen.py:22) refuses a focus target that is detached or being removed.
- Not proved: that the j5 episode came from this exact write and not from the resize recompose path.

Suggested direction (the review's refined fix):
- Make `BaseAppScreen.set_focus` refuse detached or pruning widgets.
- Make the list-entry retry skip pruning candidates and count only attached focus as "landed".
- Add an app-level guard that refocuses a sensible target when `screen.focused` is detached.
- Add a race Pilot test.
