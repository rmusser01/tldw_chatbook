## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A user usually files a note right after a quick capture, and that is exactly when the folders appear to be gone.

A power user capturing from Console through the palette ("New Note" → Blank note → Esc) comes back to a tree with two blank rows and then "▾ Unfiled":
- Agent_Lessons, Journal, Meetings, Projects, Recipes, Research and Study are missing.
- "g go to folder" lands on Unfiled.
- "Add note to folder" opens with nothing to choose.

The folders come back only after the user presses the rail's Notes row or creates another note.

Observed at 160x45 from a fresh golden launch, reproduced in two runs:
- After Create > Blank > Esc, the tree starts "▾ Unfiled / Capture from console · now / Ideas inbox · 2h …" with no folder rows above it (`verify/nl-v-n-13/r1-05-after-esc-160x45.txt`).
- Opening Add to folder shows the "Add note to folder" dialog with an empty folder Select (`r4-03-select-open-160x45.txt`).
- Both the palette's "New Note" and the rail's Create ▸ New note lead here.

Cause (traced by the review's verifier; file:lines confirmed at origin/dev 2d34cbf80d):
- The tree projection emits folder rows only after the root folder branch `NotesBranchKey(None, "folders")` has been loaded (`Library/library_notes_tree_state.py:1062-1071`).
- The rail-row entry requests that branch. The create path does not.
- `_create_library_note` (`UI/Screens/library_screen.py:30657`) reconciles the tree for "note_create" at :30804. That reconciliation then locates the new note through `_locate_library_notes_tree_target` (:18560).
- Nothing on that path requests the root branch when it is missing, so the tree is painted without folders and the folder pickers have nothing to list.

Suggested direction (a direction, not a mandate):
- In the create path, request the root (None, "folders") branch when it is missing, before locating the new note.
- Never paint rows with no label while the folders load; show "Loading folders…" instead.

No existing task owns this.

Review finding(s): N-13. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**What changed.** The database-notes tree now owes its root slices wherever the list is shown, and the `g` gate tells the automatic Unfiled group from a real folder row.

- `LibraryScreen._ensure_library_notes_tree_root_loaded(*, await_load=False) -> list[NotesBranchKey]` (`UI/Screens/library_screen.py`) replaces the dead `_ensure_library_notes_tree_folder_loaded(folder_id)` (no production caller). For `NotesBranchKey(None, "folders")` and `NotesBranchKey(None, "placements")` it requests a slice that is absent, or that a mutation fence left `uninitialized` and not loading; `fresh`/`stale`/`loading` slices are left alone (idempotent, two dict lookups). Guarded on `_notes_state.source == "database"`. `await_load=True` awaits each load inline (the orchestration tests' form); the default schedules the slice worker so the existing "Loading folders…" pager row paints while it runs.
- `_reconcile_library_notes_tree_mutation`: the `note_create` arm calls the helper AFTER `_locate_library_notes_tree_target` (fix round 1, M-1: the locator has just loaded root placements for the new note, so only the root FOLDERS slice is fetched -- one root-placements page per Create arrival, pinned in the lane), behind the existing `visit_is_current()` fence.
- `_exit_library_note_editor_guarded`'s `finish_list_projection` schedules the helper with `call_later` after `_refresh_local_source_snapshot()` -- the belt for every editor-to-list return (deep link, media "Note", a fence that dropped the create's own request); skipped while the screen is suspended (TASK-31521, fix round 1 M-4). A root slice whose first load failed stays `uninitialized` with its error, so the helper retries it on a create or an editor return (fix round 1 ruling, M-3; documented in the docstring).
- `_library_notes_folder_rows` (the `g` gate and chip, ADR-031) excludes rows with the new `library-notes-unfiled-row` class unless the root folders slice is `fresh` (then Unfiled is the only group and counts). `Widgets/Library/library_notes_canvas.py` gives the Unfiled row that second class.

**Deviation from the brief (deliberate).** The brief wrote the reconcile call as `await_load=True`, and its test 4 expects "Loading folders…" to paint in the list after create+Esc while the root folders page is held. Those two are incompatible: an awaited load inside the create reconcile blocks before the editor opens (the tree is not on screen), so the loading state could never be observed there. The task's own direction ("request the root branch ... show Loading folders… while the folders load") and AC#3 describe the non-blocking shape, so the reconcile uses the worker form: the editor opens at once, the list shows the existing loading row until the slice lands, exactly as a rail entry does. `await_load=True` stays for callers that must have the root before continuing (pinned by the navigator test).

**AC#3 sharpened before implementing** (dated note in the AC): the review's "two blank rows" are the `#library-notes-status` and `#library-notes-empty` Statics, present on every entry route; the tree never paints a label-less row. The pure negative control in `Tests/Library/test_library_notes_tree_state.py` documents that the projection was never the defect.
