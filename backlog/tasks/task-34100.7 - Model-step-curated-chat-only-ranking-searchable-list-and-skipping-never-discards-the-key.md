## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The Model step holds two of the review's five blocking issues. First, Provider only stages the connection in memory, and it is saved only when a model is committed. So Next or Enter on Model without a pick silently throws away the key the user just typed. The tracker keeps Provider ✓, and the Summary then blames the user ('✗ Provider — no credentials or saved endpoint'). Second, '(recommended)' is just the first id the provider's API returned, cut to 20 rows before anything else happens. For OpenAI that is a different model on most runs and often a text-to-speech or realtime model, and the Summary ticks it anyway. Around those: 466 OpenRouter ids are shown 20 at a time in a five-row box, with no count or search. Typed ids are never checked, so typos save silently. A fresh install pre-types the template model, which competes with the recommendation and is wiped by browsing. Errors render as greyed, cut-off radio rows, and cloud users are told to start a server. The Provider step's success line also always claims 'your chosen model was not in its list', because that verdict is hard-coded.

This task implements structural fix SF2, a curated, searchable model picker that knows what each model can do, together with stage 1 of SF3, 'skipping Model keeps the key'. Both are described in Docs/superpowers/qa/first-run-wizard-ux-review-2026-10-02/README.md, §5.1. It also delivers enhancement E4 (curated starting choices). Resolves: model-01, model-02, model-04, model-05, model-06, model-07, model-09, new-cross-cutting-02, new-model-01.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 [model-01] Skipping Model never discards what Provider staged. Next or Enter with no model chosen opens a two-button confirm ('Choose a model' focused; 'Skip — keep the key, no default model'). Skipping saves the staged credential and endpoint to that provider's settings without touching the default chat provider or model. The tracker and Summary name the missing model instead of '✗ Provider — no credentials or saved endpoint', and 'Review provider setup' lands on Model when only the model is missing
- [ ] #2 [model-02] '(recommended)' marks a curated, chat-capable model that discovery returned and that resolves a context window. It is the same model on every run, never a TTS, embedding, realtime, image or moderation model. Ranking and filtering happen before the row limit, and the order is deterministic: curated first, then newest by created date, else alphabetical. Hidden non-chat ids stay reachable, servers with no curated match show no tag, and the subtitle gives the reason for the pick
- [ ] #3 [model-04] A fresh install pre-types no template model; prefill happens only after setup has completed or when chat_defaults differ from the shipped template. On a genuine re-run, the current model is a pressed '(current)' row, or '(current — not listed by <provider>)'. Browsing never erases a value the user can't see
- [ ] #4 [model-05] Typing in the model field filters every discovered id, not just the first 20, and a non-focusable count line reads, for example, 'Showing 20 of 466 — type to filter'. Enter on an unmatched value accepts it as a typed id. The list is taller on this step while the input stays on screen at 80x24
- [ ] #5 [model-06] The model field offers inline completion from the discovered ids. When a listing succeeded and the typed id isn't in it, a soft 'Not in <provider>'s list — did you mean …?' warning appears, plus a Summary '!' row. Variant suffixes such as :nitro and :latest are normalised before comparing. Nothing blocks the typed-model rescue when listing is unavailable or the server is down
- [ ] #6 [model-07] Model-step statuses render as a wrapping, non-focusable text line above the list, never as disabled radio rows, with a real Retry button on that line and the server origin rather than the chat URL. Copy depends on the provider class. Local: start the named server. Hosted: check the connection or the status page. Auth: '<provider> rejected this API key. Go Back to fix it.', with no 'enter a model ID' clause. Net line change is ≤ 0 (absorbs and widens task-33008.5)
- [ ] #7 [new-cross-cutting-02] The Provider probe's model verdict comes from the listed ids: 'confirmed' when the staged or prefilled model is listed, and model-neutral when none is chosen. It never claims a model is missing because of a hard-coded value
- [ ] #8 [model-09] Model copy says 'model ID' everywhere, with a per-provider example placeholder and proper plurals ('Found 1 model', 'Found 3 models'). No message names the nonexistent 'Refresh models' control. With no provider, the input is disabled and the step says to go Back and pick one. The unreachable-server dialog has its own title and a model-specific body ('Save without checking?')
- [ ] #9 [new-model-01] The Provider step's success line reads '✓ Connected — <provider> returned N models. Pick one on the next step.'. The readiness 'model confirmed' check compares against the full discovered set (or a sorted sample), so its answer is the same on every run
- [ ] #10 [E4] Major providers get 2–3 curated starting rows with plain trade-offs (e.g. 'Fast & inexpensive — gpt-4.1-mini · 1M context'). The rows come from one table that Settings and the Console switcher also read, and CI tests that table against model_capabilities. A caption reads 'This is the model new Console chats start with. Switch any time with Alt+M — nothing here is permanent.'
- [ ] #11 Verified live on a fresh isolated profile through the real app (no mock servers): real OpenAI (137 ids, served in varying order), OpenRouter (466 ids) and Anthropic keys, and a real llama-server on a non-:8080 port for the local and server-down typed-model paths. A Model skip followed by a relaunch shows the key still saved. Ollama's embedding filtering is covered by tests only, because Ollama is not installed on the dev machine. Evidence recorded in Implementation Notes

- [ ] #13 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
