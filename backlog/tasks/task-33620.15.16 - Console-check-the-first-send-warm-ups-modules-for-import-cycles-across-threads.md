## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.5. The pre-import daemon thread now imports the Console's first-send modules while a send on the UI thread may be importing the same ones. If two of them import each other at module level, Python's per-module import locks break the cross-thread cycle by handing one thread a partially initialised module, which would surface as an AttributeError or ImportError in the first send. The warm-up inherits this risk from the screen pre-import design; it is low probability and has not been checked for this list.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A test builds the module-level import graph of the first-send warm-up's modules and fails on any cycle among them, naming the modules in it
- [x] #2 Any cycle found is broken, or shown safe by a test that races the two imports on two threads
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Take the modules the warm-up really imports (fresh interpreter, app + chat first, then the list).
2. Read each one's module-level imports from source (skip function bodies and TYPE_CHECKING), build the graph among them, fail on any strongly connected component, naming its modules; check the static reading's blind spot (module-level import_module calls) is empty.
3. Mutation: inject a module-level back-import and confirm it is named. Break any real cycle found, or race it on two threads.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
No cycle exists, so nothing needed breaking; the check now guards the list.

Tests/UI/test_console_first_send_import_cycles.py imports the app and the initial Console route in a fresh interpreter (the state at UI-ready), then the warm-up list, and takes the tldw modules that import added (94 on 2026-10-20). For each it reads the imports that run when its body runs: function bodies and TYPE_CHECKING branches are skipped; class, if/else, try, with and loop bodies are walked; 'from pkg import name' counts pkg and pkg.name when that is a module. It fails on any strongly connected component among those modules, naming them. Only cycles inside the warm-up's closure matter: a module already loaded at UI-ready takes no import lock, and every member of a cycle reachable from the closure is in it.

Evidence: green on the branch (no component). A temporary 'from . import engine' at the top of Agents/hooks_v2/budgets.py (restored with Edit) turned it red with 'tldw_chatbook.Agents.hooks_v2.budgets <-> tldw_chatbook.Agents.hooks_v2.command_executor <-> tldw_chatbook.Agents.hooks_v2.engine'. A unit case pins the finder on a three-node cycle with a tail. AC#2: no cycle was found, so there was none to break or race.

Blind spots, stated in the test: an import done by a function called at module level, and a module-level importlib.import_module call. The second is checked to be absent from all 94 modules.

Runs under the plain command (bootstrap_profile, like its sibling pre-import tests). Not yet on a PR-required lane: that is TASK-33620.15.15.
