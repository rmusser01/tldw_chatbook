## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
This is the C2 root cause.
- The Console's active readiness, _active_console_settings_readiness_uncached (chat_screen.py:9853-9869), calls build_console_settings_readiness with no evidence and no current identity.
- The future-chat path, _console_default_readiness (chat_screen.py:2846-2859), does the same.
- So the endpoint facet is always 'not_tested' (provider_readiness.py:316-319), and the unreachable blocker at console_session_settings.py:1644 can never fire in the Console.
- llama.cpp is keyless (provider_readiness.py:89-111) and defaults to 127.0.0.1:9099 (console_provider_gateway.py:195). A known refused server therefore still reads Ready in the Console, while the modal that ran the test says Not ready. That violates TASK-30011 AC#6.

This readiness feeds the status row, rail Model section, setup card, Inspector and send gate (the consumer list is in _console_provider_blocker_copy, chat_screen.py:15067-15107). A known failure therefore becomes a real send blocker, so recovering from it must take one action.

The readiness derivation runs inside the per-pass memo (_console_derivation_scope) and on hot paths:
- task-24454: readiness is recomputed on every composer keystroke.
- task-32804.3: the 0.25 s idle credential poll rebuilds readiness each tick.

Evidence reads must not add cost there.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
The Console's readiness now reads the shared connection evidence (TASK-33005.1), so a refused or timed-out test of the active chat's connection on any surface blocks the Console with a one-action retry.

Approach
- `Chat/console_session_settings.py`:
  - `build_console_settings_readiness(..., connection_evidence=owner)`: when no explicit `evidence` is passed and the owner has ever changed (`version`), `_console_connection_identity` builds the connection key from values the build already resolved: the endpoint a send uses (`effective_provider_endpoint`, llama.cpp's default origin when nothing is saved), the digest of `ProviderReadiness.api_key` (or the entry credential), and the credential source as Chat settings derives it. No second config or keyring read (ruling 5). The owner's exact record then feeds the existing evidence path, so `endpoint_unreachable` / `retry_connection` (and `credential_rejected`) fire unchanged.
  - `ConsoleSettingsReadiness` gains `connection` (the identity the evidence was read for; the retry probes it) and `observed_at` (for TASK-33005.3's HH:MM). Both `None` without current evidence.
  - A failure blocker's `detail` names the failure ("llama.cpp failed its last connection test (connection refused).") instead of "llama.cpp is ready" -- it is the "Unavailable: ..." copy of Make default for new chats.
- `Chat/provider_test_evidence.py`: `shared_connection_evidence(app)` returns the running app's owner or `None` (bare screens/units); the draft store's `_shared` uses it.
- `UI/Console_Modules/connection_probe.py` (new, lazily imported, not in the boot census): `probe_console_connection` (the bounded catalog probe, moved verbatim out of `ChatScreen._test_console_connection`, which now delegates, so the modal's seam and its tests are unchanged), `settle_connection_probe` (probe + settle into the owner through a throwaway draft store, so TASK-33005.1's begin ordering decides late results; TASK-33005.5 reuses it), and `retry_console_connection` (ruling 7).
- `UI/Screens/chat_screen.py`: both readiness paths pass `shared_connection_evidence(lambda: self.app)` (the same app object the modal and Settings link); the idle poll's snapshot tuple gains the owner's `version` (ruling 6); recovery target `retry` routes to the retry from the setup card / empty-transcript action / prompts, and from the Conversation settings button; the composer reason says "Provider unreachable. Retry connection before sending."
- `Widgets/Console/console_settings_summary.py`: `retry_connection`'s action target is `retry` (was `console`, i.e. open Chat settings). `Chat/console_display_state.py`: the composer hint reads "Send blocked — retry the connection to continue".
- `Docs/User_Guide/console.md`: a known failure, the one-action retry, and the switcher's readiness source.

Rulings
- Ruling: the retry runs in a worker and re-probes only connections with a models route; anything else keeps opening Chat settings -- a one-action re-test is only honest where the same test that produced the evidence can run again -- cost if wrong: TASK-33005.4's cloud key-check evidence needs its own retry route (see concerns).
- Ruling: "status row" is read as every Console readiness surface that exists today (header status, Model section, Get started card / empty-transcript action, Inspector, composer, Conversation settings rows) -- the status chips gain readiness words only in TASK-33005.3 (its AC#8) -- cost if wrong: TASK-33005.3 also owns the chip word.
- Ruling: the integration test drives the retry through the setup card, and the Conversation settings button through its handler -- at 211x44 the right rail (with that button) is closed by default, so `Button.press()` there is a no-op -- cost if wrong: none; both entry points are covered.
