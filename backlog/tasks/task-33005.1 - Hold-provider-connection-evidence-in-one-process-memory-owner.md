## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Foundation for the phase. Today connection-test evidence cannot cross surfaces, for three reasons:
- Each surface owns a private store: the Chat settings modal (console_settings_modal.py:1304) and Settings (settings_screen.py:2949 and :13313-13318). Settings also copies its store into a cross-visit snapshot (:12854-12855, restored at :12950-12952), so every visit forks it.
- ProviderTestEvidenceStore is single-slot. It keeps one identity's evidence, clears it when another identity begins, and rejects older draft generations (provider_test_evidence.py:564-620, :996-1019).
- Each surface stamps its own counters into ProviderDraftIdentity: the modal uses _model_discovery_generation and its entry credential revision (console_settings_modal.py:5807-5814), and Settings uses _provider_draft_generation and _provider_credential_revision (settings_screen.py:13401-13436). So identical saved configuration never compares equal across surfaces.

The evidence record has no observation time (ProviderTestEvidence, provider_test_evidence.py:461), yet the readiness words need one.

ADR-033 permits a narrow process-memory owner but no new root application-state object. The TTS provider-test evidence store is the in-repo precedent: it is process-scoped and keyed by a fingerprint that includes the saved revision (ProcessProviderTestEvidenceStore and process_provider_test_evidence_store, settings_speech_tts.py:604 and :731-742).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Shared connection evidence now lives in one process-memory owner per app; each surface keeps its own draft-scoped store in front of it.

Approach
- `Chat/provider_test_evidence.py`:
  - `ProviderConnectionEvidence` holds settled evidence per connection. The key is a `ProviderDraftIdentity` without its surface-local `draft_generation`: provider, custom endpoint id, canonical endpoint, credential source and credential revision.
  - Only terminal facts merge, one facet at a time (endpoint or generation). Each facet keeps the observation whose probe BEGAN last, by a process-wide begin order carried on the store's tokens, whichever surface settles first. Observation time is display-only, so a late timeout never replaces a fresher result and a clock step cannot reorder results (AC#9 across surfaces).
  - A reader gets only its own connection's record. An unsaved draft's result stays with that draft (AC#3), and a changed endpoint or credential is another connection, so the owner never reuses older evidence for it (AC#4). The surface that still holds the older result marks it changed since test (its draft store's `latest_evidence()` projection, Settings' stale Test rows). Spec §5's readiness words have no "changed since test" word, so a reader of the owner reads that connection as not tested.
  - A connection with credential revision 0 sends no key, so it is keyed as `none` whatever source names it. Chat settings reads an explicit `credential_source`, while Settings reads what resolves. They disagree only when nothing resolves, for example `"stored"` with no key.
  - `provider_connection_evidence(app)` attaches the owner as one private attribute on the running app, mirroring the TTS `process_provider_test_evidence_store`. No root state object (ADR-033), and nothing is persisted.
  - `version` counts record changes, for TASK-33005.2's idle-poll tuple. Republishing the same facts at the same time is not a change.
- `ProviderTestEvidenceStore(app=...)` stays single-slot and draft-scoped (controller ruling 1).
  - Every successful `settle` / `settle_generation` of a new observation publishes the settled facet with its token's begin order. A rebound earlier result (a `ProviderTestEvidence` outcome) was published when it was observed, so it is not published again. A preserving `rebase_after_save` copies the tested connection's facts, with their begin orders, to the saved connection (`carry`).
  - `evidence_for` falls back to the owner for an exact connection only, re-stamped with the asker's identity. It never does so for an identity `begin` would refuse, so TASK-33001.3's invariant holds.
  - Settings' no-argument `invalidate()` now clears only the Settings draft, never another surface's result.
- `ProviderTestEvidence.observed_at`: an aware local datetime, excluded from equality and appended last, so positional constructors keep their meaning. It is stamped at settlement. A rebound earlier observation passed as a `ProviderTestEvidence` keeps its own time; `settle_generation` now accepts that form too.
- `connection_credential_revision(key)`: a process-salted HMAC of the key a send would use (0 when none). Every surface now stamps it (ruling 2):
  - Chat settings: `ProviderReadiness.api_key`, or the entry's own credential. It was always 0.
  - Settings: `_provider_draft_credential_revision` gives the readiness key for an untouched credential, the typed key for a draft, and the named env var's value. This replaces the edit counter `_provider_credential_revision`, which was removed.
- Chat settings modal (7,761 to 7,751 lines):
  - Constructor link and canonical revision. Readiness is resolved only on the non-entry path, where it is used.
  - The three rebinding sites, including the sole-model rebind after a probe, pass the settled evidence. Its observation time and begin order survive.
  - With no base URL typed, the connection is keyed on `effective_provider_endpoint`, the endpoint a send uses. The `https://provider-default.invalid` sentinel remains only for a typed URL that does not parse.
- Settings:
  - Linked store.
  - `_VllmDefaultPresentationSnapshot` no longer carries the store or the credential counter (ruling 3).
  - On a visit whose Test result is still "has not run", the Test rows and the Overview headline adopt the saved connection's shared result (AC#6).
  - With no endpoint saved or typed, the draft identity is keyed on the provider's built-in endpoint, so a cloud provider is one connection in Settings and Chat settings (AC#1). Before this, Settings had no identity there at all.
- Docs: `Docs/User_Guide/settings.md` Test Provider paragraph says the last result is kept for the session, across surfaces, and is not saved.

Deviations and rulings
- Ruling: every surface publishes all settled evidence keyed by its exact values, rather than only identities that equal the saved connection. The owner answers exact connections only, with no per-provider fallback. Why: identity equality confines a draft's result to identical values (AC#1/AC#3). Checking "saved" in the modal would have meant re-resolving the session endpoint there. A fallback is what let a discarded draft's result reach the saved connection (review round 1, I-2). Cost if wrong: a reader of the owner shows a changed connection as "not tested" rather than "changed since test".
- Ruling: Settings' edit counter `_provider_credential_revision` was retired, not kept in the snapshot. Why: the canonical revision is computed, not counted, so nothing remains to restore. Cost if wrong: none observed; the late-handoff restore keeps `provider_draft_generation`.
- Ruling (review round 1, I-3): a connection with no explicit endpoint is keyed on the endpoint a send would use. Chat settings uses `effective_provider_endpoint`. Settings uses the built-in endpoint when nothing is saved or typed; when something is saved, its field shows it. This is the rule Task 4's ruling names, so TASK-33005.2 (Console) and .4 (Settings key check) must key cloud connections the same way. Cost if wrong: a cloud result never crosses surfaces.
- Ruling (review round 1, I-1): the shared owner orders observations by when their probe began. Why: wall-clock settle time let a late timeout replace a fresher reachable result, the cost the plan's pair 1-5 ruling names, and TASK-33005.5 reuses this rejection. Cost if wrong: none at one surface, because the draft stores still keep their own token order.
