## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-34100.5.3.2 (review round v5r1, R1-4) and re-checked on its branch, built on origin/dev 4b90eb860b.

When config.toml is loaded, the loader rewrites a few old settings into their current form before it fills in defaults. One example: an old profile with `[console] replay_thinking = false` and no `reasoning_history` is read as `reasoning_history = "off"`.

The structured settings writer does not do this when it republishes the runtime config after a save. It rebuilds the in-memory config from the text it just wrote and fills in the shipped defaults, but skips the old-setting rewrites. So after any ordinary settings save, the rest of that session runs as if the old setting were absent: in the example, `reasoning_history` falls back to "auto". Restarting the app reads the file again and restores "off", so the user sees a setting that silently changes until the next launch.

Probe on an isolated profile containing only `[console] replay_thinking = false`:
- `load_cli_config_and_ensure_existence(force_reload=True)` gives `reasoning_history` = "off";
- after `save_setting_to_cli_config("general", "default_tab", "chat")` it gives "auto";
- a forced reload gives "off" again.

TASK-34100.5.3.2 fixed this only for its own one-line upgrade write, by republishing through the full reload. Every other writer that republishes from the text it wrote still has the gap.
