## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Follow-up to TASK-33621.30 (owner decision 2026-11-23: "Neutral copy now, durable fix next").

**The problem.** This device writes reply rows that have no recovery record, so after a crash it cannot tell its own stale reply from a synced one. Today such a reply reopens with device-neutral copy and no actions. Two existing paths save an empty `accepted` reply row with no dispatch checkpoint, just before the provider is called:
- `ChatPersistenceService._create_pending_assistant`, reached through `save_conversation_mixin_attempt(pending_assistant=...)` from `ConsolePromptMixinService.accept_attempt` (regenerate, edit and continue turns);
- `save_pending_assistant`, reached through `save_pending_reply` (wake and goal turns).

Both are called from `_stream_assistant_response`. Only the durable composer-send path, which owns a checkpoint, moves its row from `accepted` to `dispatch_started` before sending (`transition_checkpoint` → `cas_state`). These pending rows stay `accepted` while the provider streams. A crash, or another window still streaming, leaves a row that reopens as the checkpoint-free owner (`REMOTE_ACCEPTED`).

**Why "Send again" was not shipped in TASK-33621.30.** No existing mechanism guarantees a single dispatch for a checkpoint-free row:
- `ConsoleDispatchRepository.cas_state` is the only database-level single-dispatch guarantee. It looks the owner up through the checkpoint table, so for these rows it returns NOT_FOUND.
- `claim_dispatch_recovery_action` only claims in memory, for one process.
- There is no dispatch lease.
- The profile instance lock is detection-only (`Utils/instance_lock.py`; the owner runs concurrent instances deliberately).
- Synced and imported rows carry `assistant_generation_state` but never the device-local checkpoint. By the 2026-08-22 Library-controls spec they stay inert: no Retry or Discard, and no exactly-once claim across devices.

**Live evidence** (TASK-33621.30 round, `evidence/bd5/U30/`):
- A regenerate under a 12 s proxy delay, then SIGKILL, left the regenerated reply `accepted` with 0 checkpoints. The proxy then forwarded the request upstream: it got a BrokenPipe writing back to the dead app. So an `accepted` row can already have been sent.
- On dev it reopened as "Response accepted on another device; waiting for dispatch.".

**The goal.** When this device saves a reply row before provider entry, it also writes its own device-local recovery checkpoint, using the existing table and the existing accepted → dispatch_started compare-and-swap. A stale reply of its own then reopens with the existing Retry response / Retry anyway, guarded by `cas_state`. Rows from other devices stay inert.

**Related observation.** The transcript row of a checkpoint-free reply reads "Response accepted; waiting for dispatch." (`DB/assistant_generation_state.py`), while its card reads "Response was accepted but its delivery wasn't confirmed." The row copy is shared with the checkpoint-owning ACCEPTED owner, where it is true, and with exports. About 10 test files pin it.
