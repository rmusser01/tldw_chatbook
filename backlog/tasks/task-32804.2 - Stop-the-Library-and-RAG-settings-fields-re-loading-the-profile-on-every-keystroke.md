## Implementation Notes

Landed on PR #2739 (`fix/core-review-loop`).

`_library_rag_loaded_defaults` ran `load_rag_defaults_from_active_profile()`
(~53 ms; 4x `get_cli_setting` through the storage-admission scope) fresh for
every staging-cascade consumer and compose part -- 7 loads per keystroke, 1.3 s
on the first. Now cached on the screen for the lifetime of a category visit
(`_library_rag_loaded_defaults_cache`) and invalidated
(`_invalidate_library_rag_loaded_cache`) at exactly the points the on-disk
profile can change -- entering the category (`_select_category`), save
(`_apply_library_rag_save_result`), revert (`_revert_category`), set-active
(`_rag_after_set_active`), and clone/rename/delete (`_rag_after_profile_action`)
-- the same contract as the file's `_image_gen_raw_section_cache`. Subsequent
keystrokes read the cache (0 loads); a mutation drops it so the next read
reflects disk (AC#1/#2).

AC#3: gate-free `Tests/Chat/test_settings_rag_loaded_cache.py` pins the
memoise + invalidate contract (load runs once across reads, again only after
invalidation); the invalidation hook-ups are exercised by the CI-run settings
save/revert/profile suites. The report's second, smaller lever (compute
`_library_rag_validation_result` once in `_mark_library_rag_settings_staged`
and thread it) was NOT taken -- the loaded-defaults cache removes the dominant
7x cost; the 4x validation is a follow-up.
