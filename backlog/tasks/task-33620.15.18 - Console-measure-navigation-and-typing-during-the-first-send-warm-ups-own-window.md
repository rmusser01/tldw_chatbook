## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.5 and TASK-33620.15.14. The post-UI-ready pre-import pass imports the Console's first-send modules after the last screen route, on its daemon thread. On established profiles that window starts a median 2.15 s after the Console's first frame (1.74-6.15 s over 72 fix-arm launches; 8.1-9.0 s on a fresh-profile smoke) and lasts about 0.3 s. TASK-33620.15.14 sampled navigation at 1, 3 and 6 s and single keys at 0.5-6 s, and none of its 656 fix-arm inputs landed inside that window, so a click or key that overlaps one of the warm-up's imports (they share the GIL with the UI loop; Canvas.native_authority is the longest) is unmeasured. Route imports, the same kind of daemon work, cost keys 3-7 ms, so the risk is low but unproven. A first send made before the pass finishes also gets none of the warm-up's gain (it pays the imports on the UI loop, as on origin/dev); that is not a regression, but nothing measured how often a first send arrives that early.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
On origin/dev the warm-up's window did slow navigation and, at its end, every input. The fix removes those; one moment is left, a click landing at the start of the aiohttp import, which no yield can split (TASK-33620.15.42). AC #2 is open for that moment, and for the first send's time to the provider, which re-measured about 20 ms later than origin/dev (TASK-33620.15.51), so this task stays In Progress, blocked on both.

Method. Live, paired, ABBA-interleaved, 160x45, established isolated profiles (one per arm, seeded by two real launches with the catalog consent recorded, then reused; a typed key is cleared with Backspace before quitting). Copying a seeded profile does not work: the app refuses it at startup (`recovery_scope_uncertain`). Arms: origin/dev 7536ac3b87 (W) and the same code with the warm-up call removed from `_preimport_heavy_screens` (N, "origin/dev without the warm-up"). A PYTHONPATH-only probe (scratch `sitecustomize`) records Textual driver-thread input, every `App._display` frame and its screen class, `ConsoleComposerBar.insert_text`, the pass's route start and end, each warm-up step with CPU, the freezes and their walks, UI-loop callbacks of 1 ms or more with thread CPU, and GC passes with CPU. It writes a trigger file at the pass's own events. The driver sends the input when the file appears; N gets it at route end plus the latest W offset for that event. Latency runs from the tmux send to Library's first frame (click) or to the first frame after the composer's insert (key). The driver thread's own stamp waits for the GIL and hid the freeze completely (see the lesson). Unless stated, load averages were 2-8 (14 cores). Each cell has 8 pairs; the random cells have 10. All numbers below are paired medians (warm-up minus no warm-up).

origin/dev (W vs N, evidence/bd5/M18/r2, r4rand):
- Library click at the start of `Canvas.native_authority` (one step, 85-222 ms wall, 63-70 ms CPU; it loaded aiohttp, html5lib, tinycss2 and their dependencies): +48.6 ms, 8 of 8 slower (idle pairs +40 to +72; Library 181-216 ms against 141-165 ms).
- Key at the same moment: +2.0 ms (idle +0.7).
- Key sent during the closing freeze: it reached the app 22-23 ms later than without the warm-up in the idle pairs where the control was not delayed itself. Its frame came a paired median +11.1 ms later over the 4 idle pairs (+23, +22, 0, -4; in the last two the launch without the warm-up arrived 25-27 ms late as well, in one of them during the idle refreezer's own walk, TASK-33620.15.43), and about +282 ms at load ~110. Click: Library's first frame +16 to +41 ms later idle (paired median +24.4 ms, 4 of 4 slower), up to +384 ms loaded. The freeze walked the frozen set with the GIL held: one `gc.get_freeze_count()` took 15-34 ms idle and 160-290 ms loaded, and every boot point walked once (before the refreezer's first look) or twice.
- Random moment of the window: click +9.1 ms (9 of 10), key +0.6 ms.

Mechanisms and fix (five commits, each test-first):
1. 50d65daa18. A boot freeze no longer walks the frozen set. Before the refreezer's first look it only freezes. After the look it counts the unfrozen generations it moves (`gc.get_objects`) and adds that count to the baseline. The next budget check still walks once. ADR-198 records this in a dated note. `_ui_ready`'s freeze, which walked on the UI loop (median 21.6 ms), no longer walks either.
2. d9320f721e. Each third-party package the send path loads is its own step, after its dependencies (webencodings, html5lib, tinycss2, multidict, propcache, yarl, frozenlist, aiosignal, aiohappyeyeballs, aiohttp, and textual_serve), followed by the canvas modules, leaves first. The largest step is now aiohttp, at about 37 ms CPU.
3. 354ee93872. Docs: ADR-198, app-shell.md and the module docstring.
4. 8e9e9c3409. No step starts until 0.15 s has passed with no input, and then the warm-up parks again. A navigation takes its lock only when the click reaches its handler: the park found the lock free 1-7 ms after a click and started gateway (46 ms) inside the navigation. The lock was held 27-53 ms after the click. The pass's route pacing is unchanged.
5. f1b164cc2f. Each step that loads modules freezes them at once: 54 freezes per launch with the closing one, a median 4.0 ms in all per launch (2.6-10.5 ms over the 60 r6/r6rand launches; 53 of them had at least one freeze over 0.4 ms, and the longest single freeze was 5.6 ms). With the step's modules left unfrozen until the last step, a click during the window ran a generation-2 collection on the UI loop in 9 of 10 launches (median 5.6 ms) against 0 of 10 without the warm-up. That cost +10.5 ms even when no import was running at the click.

Final head f1b164cc2f vs N (evidence/bd5/M18/r6, r6rand, r7fz):
- Key at the aiohttp step's start: +0.2 ms. Click at the window's start: +2.0 ms (4 of 8).
- Closing freeze (r7fz: re-run on fresh per-arm profiles with the trigger keyed to the closing freeze's label; every warm-up input was sent 0.1-1.7 ms after that freeze began, and the freeze took 0.33-0.93 ms): key -0.2 ms (3 of 8 slower), click +3.5 ms (5 of 8; -27 to +100 ms). In the two largest click gaps (+33, +100 ms) the click reached the app after the window had closed, and in the +100 ms pair Library's build callback ran 115 ms of CPU, against 75-85 ms in 12 of the other 15 launches (both of pair 1's took about 230 ms). The intermediate heads, whose closing freeze was already walk-free, agree: clicks +2.7 ms (r3) and -5.3 ms (r5), keys -0.1 and -0.8 ms. Over the 60 r6/r6rand launches the closing freeze took a median 0.37 ms (max 0.85 ms), against 30.6 ms on origin/dev (r2, 32 launches).
- r6's own closing-freeze cell is discarded. Its trigger file was written at every warm-up freeze, so the input was sent at the first step's freeze, 2-8 ms after the route pass ended, while the launch without the warm-up got its input at the closing freeze's offset (it arrived 536-891 ms after the route pass). Neither arm was at the closing freeze, and the two were not at the same moment. An earlier version of these notes reported it as the closing freeze (key -3.4 ms, click +4.4 ms).
- Random moment: click -9.5 ms (2 of 10 slower; one +65 ms pair in which the warm-up was asleep for the input yield and then parked on the navigation lock, so it was not warm-up work). Key -0.2 ms (0 of 10).
- Click at the aiohttp step's start: +13.8 ms, 6 of 8 slower (-3 to +23 ms), against +48.6 ms for origin/dev at its heaviest step (both from the click's send to Library's first frame). aiohttp's package `__init__` imports its client stack as one unit, so the step cannot be split further, and a started import cannot be interrupted. Filed as TASK-33620.15.42 with the numbers: the run end's `Canvas.gateway` imports `aiohttp.web` at module scope and builds a `web.Application` in `__init__`.
- Intermediate heads, for the record: d9320f721e (steps only) +26.2 ms at aiohttp's start, with the freeze cells fixed (r3). 8e9e9c3409 (with the input yield) +20.0 ms there, and +10.5 ms at random moments (r5, r5rand).

First send after the pass (AC #2's gain; real Anthropic claude-haiku-4-5 through the review proxy; each launch types its prompt 3 s after the pass ends and presses Enter 1.5 s later, 4.52-4.56 s after the pass; every send got HTTP 200 and the reply shown):

When the pass finishes (AC #3), measured from the launch command:
- Established profile, origin/dev, idle host (37 launches): the Console's first frame comes at 9.5 s (median). The warm-up starts 1.92 s after that frame (1.76-12.3 s) and the pass ends 2.31 s after it (2.05-15.4 s), 11.9 s after launch (11.35-31.45 s). The window lasts 369 ms (290-3,099 ms). At load ~110 (15 launches) the pass ends 14.4 s after the first frame and 44.7 s after launch, with a window of 2.7 s. The fix head (60 launches, each with one input in the window): the pass ends 2.37 s after the first frame and 11.7 s after launch, about 60 ms later than origin/dev; its window lasts a median 598 ms (287-1,223 ms), against 369 ms, and each input in it adds at least the 0.15 s input-quiet wait.
- Fresh profile (a ready config with an empty data dir, 5 launches per arm): first frame 10.8-11.0 s after launch; the pass ends 2.2-2.3 s later, 13.1-13.3 s after launch, the same on both arms.
- True first run (no provider key, setup wizard over Home, 3 launches per arm): the pass ends 13.1-13.4 s after launch, while the wizard is still open, so it is done before any first send can be made.
- So the gain needs the first Enter to come about 2.3 s after the Console's first frame on an idle established profile, and up to about 15 s after it at load ~110. An Enter before that pays the remaining imports on the UI loop, as on origin/dev before TASK-33620.15.5.
