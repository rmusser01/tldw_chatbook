## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A view tab is laid out again when its label changes, so it paints its whole label however the view was reached.

Cause. `Button.label` repaints but asks for no layout, and a tab's width is `auto`, so a tab kept the width of its old label until something else laid it out. A click or Enter on a tab moves focus onto the tab and off it again, and those paths painted whole labels already. The path that did not: Context and memory with focus in a field (where a click or Enter on its tab leaves it), then Alt+M and Esc or a pick, which shows Model and generation with no tab touched. The Model tab kept its 22 cells and the Context tab its 31, the widths in qa/model-config-p3-2026-09-28/task-2/tabs-after.txt, and the row painted "Model and generation" with no mark.

Fix. `_show_settings_view` sets both tabs in one loop and calls `refresh(layout=True)` on each after its label. No CSS changed. The loop replaces two copies of the label, class and tooltip code and two `variant = "default"` writes that did nothing (nothing else sets a tab's variant): 13 fewer lines. The modal's size row drops from 6,193 to 6,189; this plan task's two other code riders use the other nine lines.

Test. `Tests/UI/test_console_settings_geometry.py::test_view_tabs_paint_their_whole_labels_after_each_view_switch` at 211x44 and 235x52: click Context, click Model, click Context, Alt+M, Esc, reading the tab row from the compositor's painted strips after each. Against the modal at 10fead87cb both sizes fail at the last step with `'  Model and generation       Context and memory '`; with the fix both pass.

Live, scratch profile, tmux, 211x44. At 10fead87cb: Context reached by a click and by Enter on its tab, then Alt+M, Esc, painted ` Model and generation       Context and memory` both times. At this head the same two runs painted ` Model and generation · Selected  Context and memory`. Opening, Shift+Tab to the tabs, Tab and Enter, and Alt+M then Esc from a focused tab painted whole labels at 211x44 and 235x52.

Review fix (2026-10-11). Compose still wrote each tab's selected label, class and tooltip from `_active_view`, and none of that text reached the screen: `on_mount` runs `_show_settings_view` before the first paint, and the loop sets all three again. Compose now yields the two tabs with their plain names, ids and the `console-settings-view-tab` class, and the loop is the only code that marks a tab: 26 fewer lines, and the modal's size row drops from 6,188 to 6,162. A tab's plain name is still written twice, once in compose and once in the loop. The paint test now opens on Context and memory first (`focus_context=True`) and reads `Model and generation  Context and memory · Selected` before any switch, at both sizes. With the loop changed to leave the Context tab unmarked while the modal mounts, that assert fails at both sizes and the two Model-open focus nodes pass, so it is this assert that pins the Context-selected open.

Restack onto Phase 8's final head (2026-10-16): the mark is now a leading '●' (TASK-33007, d96370e009), not ' · Selected'. The paint test's tab-row constants pin ` ● Model and generation  Context and memory ` and ` Model and generation  ● Context and memory `, and it passes at 211x44 and 235x52; the painted rows quoted above (the live runs and the review fix's Context-first row) predate the dot. AC#1 says '●' since the whole-PR review, round 1 (2026-10-18).

User guide: Docs/User_Guide/console.md says the tab of the view shown starts with "●" ("● Model and generation"), whichever way the view was reached, Alt+M's return included.
