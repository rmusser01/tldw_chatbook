## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: found pre-existing on dev by the TASK-34000.16 review (2026-10-23) while probing that task's rename cases. Repro on the real adapter: activate a folder holding `ok.md` and `old.md`; `mv old.md new.md`; write a new, VALID `.md` to `old.md`; Check changes. The bound binding for `old.md` finds no file at its path, so the identity fallback matches its inode at `new.md` (a move), and the fresh `old.md` is an unbound candidate (a create). Across six runs of that probe the reviewer saw more than one plan shape -- three runs produced one shape and two another; the sixth run's shape was not recorded in the review -- so which rows the review shows depends on the order the pass happens to visit bindings and candidates in, not on what is on disk.

A Check is mutation-free, so nothing is lost, but a review that differs between two identical Checks cannot be trusted, and the token that pins it changes with it. TASK-34000.16's fix round 1 made the identity lookup run first for a REFUSED file at the old name (I-1) and pinned that case; this task owns the valid-file case.

Direction (not a mandate): make the pass's claim order deterministic (bindings resolved by path first, then by identity, then candidates — in a fixed sort), and pin the plan shape for this repro so that two Checks over the same disk state produce the same rows and the same token.
