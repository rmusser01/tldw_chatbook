## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A re-run replays first-run setup [cross-cutting-05]. Even with TASK-34100.10's prefill it remains a corridor: changing the default model costs a power user about 75 keystrokes through eleven steps, and the user never sees the whole setup at once.

The approved spec opens a re-run of a working setup on "Review your setup" (decision D7): the same verdict region as Ready, one row per area with its current value read from config, and Enter on a row opens just that step in a single-step host and comes back. Untouched areas are never written, and Done returns where the user started. One predicate (has_usable_chat_provider, TASK-34100.20) decides between this dashboard, the first-run corridor and Quick-at-Connect. Console's readiness links keep TASK-34100.10 AC#8's routing (owner ruling Q9). It builds on the entry contract and origin-return rule (TASK-34100.10), the outcome record (TASK-34100.9), the setup registry's names (TASK-34100.15) and Ready (TASK-34100.23).

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D7, §3.0, §3.7, §3.8, §4.2, §10 F11.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Every setup entry chooses its first screen by one predicate: a valid draft opens the resume dialog; a deferred AI setup with no usable provider opens Quick at Connect; a usable chat provider opens 'Review your setup'; a completed setup with no usable provider opens a prefilled Welcome run as a first run; a fresh profile opens Welcome
- [ ] #2 The dashboard shows the verdict region, one row per area in Full order (Provider, + Add another provider…, Model, tldw server, Search, Tools, Spoken replies, Dictation, Appearance, Keys) with values read from config on every render through the same row builder and labels as Ready, a detail line for the highlighted row, the legend, Data and Config, and the exits [ Done ] and [ Run the full walkthrough ]. It fits 80x24
- [ ] #3 Enter on a row opens that single step in a single-step host with the step's own state and commit and a [ Cancel ] / [ Save ] pair. Save returns with the row refreshed and highlighted, the verdict recomputed and the receipt 'Saved: <area> → <new value>'. Cancel writes nothing and reads 'Nothing changed.' Changing Provider continues into Model only when the provider changed
- [ ] #4 Opening the dashboard and pressing Done leaves config.toml byte-identical. Done, and Esc, return to the origin given to the entry contract
- [ ] #5 '+ Add another provider…' and its palette command open Connect in add mode with 'Also use it for new chats' off by default, so adding a provider never changes the default silently
- [ ] #6 Each area has a palette command named from the spec's area table ('Setup: Review your setup', 'Setup: Change model…', 'Setup: Connect a tldw server…' or 'Setup: Change tldw server…', and so on). Each opens its single step directly and returns to where the palette was used
- [ ] #7 An entry that names an area opens the dashboard with that row highlighted and its reason expanded. Console's readiness links keep TASK-34100.10 AC#8's routing to the control that fixes each reason
- [ ] #8 Settings' setup buttons read 'Review setup', 'Resume setup' or 'Run setup' by the same predicate and drafts, and 'Review setup' joins the setup glossary
- [ ] #9 'Run the full walkthrough' opens the prefilled corridor with the last-used track preselected
- [ ] #10 The single-step host gives each step its host capabilities, so a step never promises a resume the host cannot do
- [ ] #11 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: a profile set up with a real OpenAI key: change the model from the palette in six actions or fewer with a config diff only in the model keys; change the provider to the real llama.cpp server; Cancel in every area writes nothing; re-runs from Settings and from the palette return to their origin. Evidence is recorded in Implementation Notes
- [ ] #12 New behaviour is covered by tests that fail on the pre-change code (RED verified), and no module-size or ADR-097 ratchet is raised
- [ ] #13 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
