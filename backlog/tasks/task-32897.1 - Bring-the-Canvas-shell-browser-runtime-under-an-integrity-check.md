## Description

Found while repairing `check_canvas_mermaid_assets.py` (TASK-32897). Closing that guard's laundering hole
put `canvas_runtime_worker_v2.js` and `canvas_renderer_v2.js` under a digest pin. **Three larger, equally
exposed files were left with no integrity check of any kind:**

| file | bytes | covered by |
|---|---:|---|
| `tldw_chatbook/Canvas/static/canvas_shell.js` | 51,455 | nothing |
| `tldw_chatbook/Canvas/static/canvas_shell.css` | 10,408 | nothing |
| `tldw_chatbook/Canvas/static/canvas_shell.html` | 7,720 | nothing |

All three are served to the browser by `Canvas/gateway.py:126-130`. Grep across `tldw_chatbook/`, `scripts/`
and `Tests/` finds them in no manifest, no census and no digest pin -- only a packaging **presence**
assertion (`Tests/Packaging/test_canvas_gateway_distribution.py:34-36`, which checks the files exist) and a
fetch test (`Tests/Canvas/test_gateway.py:189`). Neither asserts content.

## Why this is worth more than the hole it was found next to

`canvas_shell.js` is not passive markup. It references `Authorization` 3 times and `token` 6 times, and the
gateway hands the browser its grant in the **URL fragment** -- `gateway.py:1492`:
`browser_url = f"{clean_url}#boot={quote(grant.token, safe='')}"`.

So the shell script is the code that reads the bootstrap token out of the fragment and attaches it to
requests. Tampered, it is positioned to exfiltrate that token. It is 51 KB, it ships in the wheel, and
nothing in the tree would notice a byte changing.

**Correction to how this was first written up:** the review and the implementing agent both described this
file as "holding the session cookie". It does not -- `grep -i cookie` on it returns nothing, and the gateway
authenticates with a fragment-delivered bearer token, not a cookie. The distinction matters for the threat
model (fragment tokens are not sent to the server by the browser automatically, and are readable by any
script on the page), so state it as a token.

## Recommended shape

Reuse the pattern TASK-32897 just established rather than inventing one: a digest pin in
`scripts/check_canvas_mermaid_assets.py` (or a sibling check), deliberately located **outside** the
directory the vendor script writes to, so that re-running the documented reproducible command cannot
regenerate the pin from tampered bytes. That placement is the whole point of the fix and is easy to lose.

Source: tier-2 code review 2026-09-21 -- discovered during TASK-32897. Evidence and the end-to-end tamper
reproduction are in `qa/tier2-code-review-2026-09-21/validation/LEAD-guards.md`.
