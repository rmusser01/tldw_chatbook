## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during TASK-34100.13's live re-verification (2026-10-27, profile g13v5-b80): after first-run setup's Appearance step saved "Startup animation: Off" (`[splash_screen] enabled = false` in config.toml, and the next launch correctly played no splash), Settings ▸ Splash Screen showed **Enabled: On** and **Duration 7.0** — the built-in defaults, not the saved values. Setup's Appearance step points users to that page for the splash card and startup animation, so they are shown settings that are not the ones in effect.

Cause (read, not yet fixed): TASK-32804.8 replaced per-key reads with one section read, `get_cli_setting("splash_screen", default={})`, in both `Widgets/settings_splash_screen_viewer.py` (`_load_config`) and `Widgets/splash_screen.py` (`SplashScreen._load_config`). `get_cli_setting` treats a call with no key and an undotted section as invalid and returns the default, so both loaders always see `{}` and fall back to every default. A probe on an isolated HOME holding that profile's config: `get_cli_setting('splash_screen', default={})` → `{}`, while `get_cli_setting('splash_screen', 'enabled', True)` → `False`. The startup splash itself still honours enabled/duration/card/reduced motion because `splash_options()` passes those in, but the widget's own reads (for example `active_cards`, the effects table) are defaults too.
