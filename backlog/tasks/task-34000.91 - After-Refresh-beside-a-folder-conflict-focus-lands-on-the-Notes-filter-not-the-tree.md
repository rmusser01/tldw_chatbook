## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: TASK-34000.28 (polish-1a task 4) put a Refresh control beside a genuine folder-conflict notice in Library Notes. Refresh reloads the tree as a fresh visit and re-arms the list-entry focus, which is meant to land on the first tree row (`handle_library_notes_notice_refresh` in `library_notes_controller.py` syncs the canvas with `then=_arm_library_list_entry_focus`). The tree is still empty when that arm resolves, so it takes the designed empty-list fallback (task-31946, `LibraryScreen._focus_library_list_entry`) and focus lands on `#library-notes-filter`; the rows that load a moment later do not move it. Repro: provoke a genuine conflict (another connection changes the folder under a pending Move note), then press Enter on Refresh: focus is in the filter, and the next printable key types into it instead of walking the reloaded tree. Evidence: `Tests/UI/test_library_notes_move_never_false_conflicts.py::test_a_genuine_conflict_offers_a_working_refresh` pins the landing as observed (`screen.focused.id == "library-notes-filter"`); the task 4 re-review traced it to the arm resolving against the empty tree. Nothing is lost on disk; a keyboard user needs an extra Down or Tab to reach the rows they just refreshed.
