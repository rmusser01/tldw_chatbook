## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Three thread and connection defects in the Console persistence layer: a capture-detail write leaks one registered database connection per call on a file-backed database; two store locks are held across the persistence adapter's own `BEGIN IMMEDIATE` while the UI thread takes them in the opposite order; and the permission-summary worker reads (and can persist) the owner-thread-only store from a raw worker thread, a path the tests never exercise because they stub the thread.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 The capture-detail write releases its connection, with a test asserting the registered-handle count does not grow
- [x] #2 The store locks are narrowed or removed so no lock is held across the adapter's transaction
- [x] #3 The permission-summary worker does not touch the owner-thread-only store off its owner thread
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Leak: route `run_repository_call`'s `repository.replace` through the existing `_run_owned_chat_db_operation` so the bare thread's handle is retired; keep the Event/call_soon_threadsafe cancel handoff.
2. Inversion, trajectory: drop `_trajectory_lock` entirely. `upsert_trajectory_rows` assigns seq inside its own BEGIN IMMEDIATE and the adapter already retries the losing writer, so the store lock adds no correctness and only supplies the lock-then-DB order.
3. Inversion, quiescence: keep the purge fence but stop holding `_capture_quiescence_lock` across the adapter write. Admit a writer under the lock, count it in flight, write outside the lock, and have `begin_capture_quiescence` wait on a Condition for in-flight writers to drain (bounded; on timeout it un-arms and reports blocked).
4. Cross-thread store: build the summary tail on the UI thread in `_maybe_fire_permission_summary` and pass it to the worker; the worker keeps only the network call.
5. Tests: handle-count assertion for 1, a two-thread ABBA test for 2, a thread-identity assertion for 3.
6. preflight, targeted suites, name-set comparison against baseline.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
All three defects fixed in one commit (55811694d4); preflight green; failing test NAME sets identical to baseline (21 vs 21 on the five shared files, 11 vs 11 on test_console_chat_store_exchanges.py), zero regressions.

**#1 connection leak.** `run_repository_call` in `replace_conversation_capture_detail` now calls through `_run_owned_chat_db_operation` instead of `repository.replace` directly. That helper already existed for exactly this and is what every sibling off-loop write in the controller uses; it retires only a handle the call itself opened, so the non-offloadable inline branch borrows the loop thread's handle and is untouched. The hand-rolled Event/`call_soon_threadsafe` handoff is kept — the cancel-survival semantics are load-bearing.

**#2 lock-order inversion.** Two different resolutions, because the two locks are not the same kind of thing.

`_trajectory_lock` is deleted. Its docstring claimed it serialized `seq` assignment, but `CharactersRAGDB.upsert_trajectory_rows` assigns `seq` inside its own `BEGIN IMMEDIATE` and `ChatPersistenceService.write_trajectory_rows` already retries the loser so it re-derives seqs. The lock added no correctness and supplied the lock-then-sqlite half of the ABBA.

`_capture_quiescence_lock` could NOT simply be narrowed: it is the purge fence. `begin_capture_quiescence` returning True has always meant no exchange write is in flight, and `commit_full_capture_purge` deletes rows on that promise — it was inherited from mutual exclusion, so narrowing alone would have let an admitted writer re-add rows the purge had just deleted, trading a stall for silent capture resurrection. Instead the fence is made explicit: a writer is admitted under the lock and counted in `_capture_exchange_writers`, does its adapter write outside the lock, then decrements and notifies. `begin_capture_quiescence` arms the fence first (new writers are rejected immediately) and waits on a Condition for the admitted ones, bounded by one adapter busy timeout; on timeout it un-arms and returns False, which the caller already reports as `purge_in_progress`. `_attach_message_exchanges_locked` now returns the message needing a flush instead of persisting under the lock, and `_persist_exchanges_only_locked` is renamed `_persist_exchanges_only_admitted` since it is no longer called with the lock held (two rows in the semantic-mutation inventory and its doc renamed to match).

The pre-existing `test_capture_quiescence_waits_for_inflight_exchange_write` is the regression pin for this: it asserts the lease blocks while a writer is mid-write and still returns True afterwards. It stays green.

**#3 cross-thread store access.** The tail is built in `_maybe_fire_permission_summary`, which runs on the store's owner thread, and passed to `_permission_summary_worker` as an argument. The worker's import list drops `build_messages_tail` and its docstring now states it may not touch `self.store`.

**Evidence.** Every new test was run against the unfixed shape (restored in a `try/finally` driver, no stash) and fails there:
- `test_a_worker_trajectory_write_does_not_deadlock_the_branch_mutation` — 16 s timeout before, 0.5 s after, both rows stored.
- the three structural probes — report the held lock by name before, empty after. The probe uses `_is_owned`/`locked`, not `acquire(blocking=False)`: an RLock re-acquires from its own owner, so an acquire-based probe reports a re-entrant hold as free, which is exactly the case under test.
- `test_capture_detail_writes_do_not_grow_the_connection_registry` — registry grows by one per write before, flat after.
- `test_the_store_read_happens_on_the_spawning_thread_not_the_worker` — reports the worker's thread id before, the owner's after.

**Environmental note.** Six tests in `test_permission_summary_wiring.py` fail on origin/dev itself, and the cause is now traced: `get_runtime_config_snapshot()` raises `RecoveryRequired('raw_source_selection_changed')` under `Tests/`'s conftest, the trigger swallows it into "no resolution", and no summary ever fires. Same ADR-126 admission gate already flagged on this branch. The new test stubs the snapshot so thread ownership is what decides its result; the six existing reds are untouched and are not this task's to fix.

**Diagnostic inventory.** One added statement (`capture_quiescence_drain_timeout`, binding only a generated session id — no user content, secret, path or URL). Read via `--statements --since` before `--write`, per CLAUDE.md.
