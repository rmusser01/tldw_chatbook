## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** With Library set to Automatic, nothing on a turn says what retrieval did for it. A grounded turn looks the same as one that was:
- sent with 0 matches;
- sent once without Library after a timeout, a failure or a Stop.

A user who relies on grounded answers cannot tell them apart.

**What exists.**
- The controller persists a bounded `library_preparation` record on the USER message (message_trajectory_metadata), but only for `zero_matches` and `bypassed`.
- `project_library_preparation` (Chat/library_preparation.py) can project those records onto active USER turns, but no UI calls it.
- A successful retrieval (N sources sent) is not persisted at all.

Moved out of TASK-33621.20 (its AC#1 and the first test of its AC#5) so that task could close. TASK-33621.20 fixed the pause, the jam and the cold start. Review finding: G2-09 (qa/console-ux-review-2026-09-29/findings.md); prior art TASK-19900.3 AC#6/#7.

**Design notes (from TASK-33621.20, not yet a plan).**

1. **Persist success with a count.** Extend the closed `library_preparation` v1 vocabulary (`_DISCLOSURE_OUTCOMES`, `LibraryPreparationEvent.outcome`) with an evidence-sent outcome whose `result_count` is the number of evidence rows sent. Attach it in `prepare_library_for_turn` when a bundle exists; `_preparation_contribution` hard-codes `result_count=0` today.
   - Pre-merge reviewer's note: the bypass outcome should keep its reason (timed out / stopped / failed), which also means extending the vocabulary, e.g. a bounded reason field. The preparation's `error_code` is known when the card's Send once without Library runs `bypass_library_preparation`.
   - Older app versions read an unknown outcome as a corrupt row and leave that turn inert. Check `trajectory_export.py` and the round-trip tests in `Tests/Chat/test_library_preparation.py`.
2. **Projection.** Call `project_library_preparation` over the active-path USER turns from `db.get_trajectory_rows(conversation_id)` and map the result to native USER message ids.
   - It must not add a DB read to every UI sync: cache by (conversation id, active path, transcript revision).
   - `ConsoleChatStore.library_activity_snapshot` is the precedent for reading these rows; put the new code in a helper module, because `console_chat_store.py` is over its size-ratchet row on dev.
3. **Rendering.** Add a screen-owned mapping (native USER message id -> line) pushed into the transcript like `set_citation_counts` / `set_library_activity_counts`, and a new `_TranscriptRow` kind rendered under the USER message.
   - `console_transcript.py` is about 87 lines over its ratchet row on dev. Either raise the row with a dated owner-decision comment or move the row widget out.
4. **Live line.** The record is written in the acceptance transaction, so a re-projection after acceptance shows the line without a restart. Branch switch and restart come for free from reading the persisted rows.
<!-- SECTION:DESCRIPTION:END -->
