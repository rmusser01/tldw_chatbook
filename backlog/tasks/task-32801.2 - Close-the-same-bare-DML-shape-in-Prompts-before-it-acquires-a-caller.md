## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`PromptsDatabase.update_keywords_for_prompt` has the identical shape to the Media data-loss defect: DML on the legacy-isolation held connection with no transaction or commit, and a public wrapper in `Prompts_Interop` that opens none. It is a trap rather than a live loss only because that wrapper currently has no caller, which is not a property anyone maintains deliberately.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
update_keywords_for_prompt now opens self.transaction() itself, exactly as the Media P0 fix (TASK-32801.1) did for its two methods. Prompts_DB.transaction() nests the same way (in_outer = conn.in_transaction, commit only at the outermost), so add_prompt and the other wrapping callers are unaffected.

Reproduced on a file-backed DB, both trees:
  UNFIXED: in_transaction True after the bare update; after close+reopen the prompts are ['Alpha'] -- the entire 'Beta' prompt added afterwards is GONE.
  FIXED:   in_transaction False; prompts ['Alpha', 'Beta'].

So this was a live data-loss mechanism, not merely a latent one: it is P2 rather than P0 only because its public wrapper (Prompt_Management/Prompts_Interop.py:230) currently has no caller. That is not a property anyone maintains deliberately, which is the whole reason to close it now.

No regressions: Tests/Prompts_DB/ is 1 failed / 298 passed before and after, same failing test. ruff E9,F63,F7,F82 clean.
