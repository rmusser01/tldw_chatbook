## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while measuring TASK-33620.15 (2026-10-05/06). With that fix a send's admission no longer holds the UI loop (longest hover wait before acceptance 85-193 ms over 12 sends, idle baseline 24-39 ms), but between acceptance and the provider call input is still blocked: live (Anthropic haiku via the review proxy, 160x45) the longest hover wait before the provider call was 341-723 ms on the fix, about the same as before it. Main-thread samples put the largest block (341-587 ms) in the durable post-commit effect composing the run's MCP provider on the UI loop: _compose_mcp_provider, MCPToolProvider.compose_catalog, get_kill_switch and local_external_catalog, each paying the MCP store's storage-admission checks (recovery_activation.observed, generation witnesses, bootstrap pinned_directory opens). The other 100-250 ms blocks are Console syncs (_run_console_config_sync under config_participants.operation, the settings summary, _global_context_policy_overrides), again mostly storage-admission syscalls. In the mounted harness the UI also waited on the config writer locks while workers held them: hook-permission snapshots (locked_hooks_config_snapshot parses the whole config under the write lock, 4-5 times per send, 40-157 ms each) and a 155 ms save_settings_to_cli_config. Tried and rejected during TASK-33620.15: moving the five MCP permission-store reads to five worker hops (provider call 0.45-1.27 s later; lessons-testing-evidence) and a 1 ms GIL switch interval (worse: provider call 4.0-4.6 s after Enter instead of 3.2-4.1 s, waits up to 263 ms before acceptance). Evidence: scratchpad uxrev/evidence/bd3/A/bd5 (C1-*, X-fix-sw5-*, X-fix-sw1-*).

Re-measured 2026-10-06 on the final TASK-33620.15 branch, and left out of that PR. Live, sampled every 4 ms, three sends, from acceptance to the provider call, the main thread's busy time split three ways: run-start composition (`_compose_mcp_provider` plus `_compose_local_provider`) 30-38%, Console syncs 20-38%, other 17-26%. The composition is the longest single busy stretch (621-725 ms). Inside it, `get_kill_switch` runs three times per send at about 60 ms each, plus `local_external_catalog` and `effective_tool_states`. Each MCP store call runs a full writing raw-participant scope: storage admission, generation witnesses and bootstrap pinned-directory opens. The syncs alone still produce 150-400 ms waits throughout a run, so moving only the composition cannot meet AC#2. The same per-call scope cost makes the syncs slow, and its GIL contention keeps some hover waits during admission above 100 ms. Cutting that cost (once per loop batch, as `_config_file_posture` now is, or batched) is the shared fix, a Backup_Recovery design decision. A caution on the rejected five-hop variant: it was measured with the hover poller running, and the poller loads only the arm whose loop is free. With no poller, TASK-33620.15's single precapture hop cost about 100 ms at acceptance and no provider-call delay (8 paired sends). A single-hop composition should be re-measured with no poller before it is ruled out (lessons-testing-evidence, "An input probe slows the arm whose UI loop it frees"). Evidence: scratchpad uxrev/evidence/bd3/A/bd5r3 (fixS-a-* sampled, *-sendonly*).

Residual left by TASK-33620.15 (final branch, 2026-10-08, six paired live sends): before acceptance the longest hover wait was 50-142 ms against an idle 20-35 ms (parent build 224-387 ms), so one send in six still waited 107 ms over idle; on 2026-10-06 four sends in twelve did (up to about 145 ms). Main-thread samples put those waits in the acknowledgement's own layout pass and in a Console sync that ran during the precapture hop (`_provider_readiness_app_config` under `load_settings`, `resolve_provider_endpoint`, storage admission), slowed by GIL contention with the precapture worker's storage-admission syscalls. That is the same per-call cost as above, so this task also owns the before-acceptance residual (AC#6).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Run start no longer composes MCP tools on the UI loop, and the Console sync tick stops paying three kinds of per-tick storage work it did not need. Input waits after acceptance are shorter (paired live median 188 → 142 ms), but most sends still have one wait over 100 ms, so AC#2 and AC#6 stay open, and first sends reach the provider later, so AC#3 stays open (numbers below).

**Measured first (AC#1), base 46c3959526.**
- Harness (mounted send harness; loop heartbeat, code-object sampler, per-call costs): one checked config operation 2.4 ms, `get_kill_switch` 2.1 ms, `local_external_catalog` 3.5 ms, `get_inventory` 18 ms, all of `_compose_mcp_provider` 20 ms; a warm sync tick 25-46 ms. The harness's in-memory DB runs no agent runtime, so run start and the DB-side sync costs were attributed live.
- Live (Anthropic haiku via the review proxy plus a timing proxy, 160x45, all threads sampled about every 4 ms, 10 sends): from acceptance to the provider call the main thread was 21% busy. Per send: run-start MCP/local composition about 26 samples (63-130 ms stretches: the kill switch read three times, `local_external_catalog`, `effective_tool_states`, `get_inventory`). In the 0.2 s sync tick: the global context-policy read (a full config operation, about 9), rendered-receipt acknowledgements (one DELETE transaction per earlier turn per refresh, about 5), the config-sync admission (about 6) and other render work. The busiest worker was the Character browser's scope check: about 28 DB calls per send, 17 a second, each worker opening a fresh connection (a private SQLite helper subprocess). Hover waits after acceptance were 143-403 ms. They line up with the composition, the sync ticks, and GIL contention from those workers.

**Changes**
- `Chat/console_run_start_tools.compose_run_mcp_provider`: the kill switch, catalog (`local_external_catalog`, built-in inventory, permission states) and definition-maximum gating are read in ONE `asyncio.to_thread` hop, at the same point as before (run start, after the durable commit) and still fresh. The hop drives `compose_catalog` on its own short-lived loop, and the provider stays bound to the UI loop for tool calls.
  - The kill switch is now read once there, for MCP and the local tools. It was read three times within the step. `compose_catalog(kill_switch_engaged=...)` takes the value; its default still reads.
  - A failed read fails both closed with the same log lines. The diagnostic inventory moved three constant-text warnings (reviewed with `--statements`).
- `Chat/console_context_policy.read_global_context_policy_overrides`: the nine `[console]` policy keys go through the checked config operation only on a new installed config, a warm-hit miss (external edit, selector change) or an active local storage pause. Otherwise the parsed result is reused.
  - The operation predated warm reads: TASK-32628 added it, then TASK-32804.1 made warm reads free.
  - It lives in an already-resident module to keep the ADR-097 UI-ready census at 1033.
- `ConsoleRuntime.acknowledge_rendered_terminal_receipts`: a receipt whose acknowledgement completed is skipped while the last mark read does not list it. A mark learned of later is still acknowledged. With no mark read yet, or after a failed acknowledgement, it retries, as before.
- `ConsoleCharacterContextController`, during a run (`run_active` wired from `_console_run_active`): the database scope is checked at most once a second while the ambient scope (database handle, current character, open chat) is unchanged, whatever the last check found.
  - Every message write bumps the revision, so each tick of a send had reloaded the browser or failed to settle.
  - Outside a run, after any ambient change, a forced refresh or an invalidated scope, it checks at once.
  - The skip keeps the tick's former await point.
- `test_console_workspace_switch_refresh_is_not_dropped_during_inflight_sync` (dev test) now holds only its own sync, and starts it again if the screen's own sync got there first. With this branch the UI loop no longer waits on config locks for the policy read, which shifted that timing.
  - It failed 4 of 9 runs on the precondition. With the memo disabled it failed 0 of 4; the base build failed 0 of 7.
  - Hardened, it passes 8/8 here and 3/3 on the base. The negative control (the in-flight request dropped) still fails it.
