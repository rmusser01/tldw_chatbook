## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in the independent review of TASK-33621.21 (2026-11-22). On a first run the controller emits "Preparing speech model…" (WARMUP_MESSAGE_FIRST_RUN), but the warm-up wait's first progress check, about 50 ms later, finds no attributed download (every current adapter, ADR-284) and repaints the chip with "Loading speech model…" (WARMUP_MESSAGE): `Chat/console_voice_input.py`, the quiet-loading branch of `_run_warmup_off_the_executor` (around lines 2112-2116). So the first-run copy is effectively never seen; live captures show "Loading speech model…" at 6 s. Two tests assert the first-run copy and pass only when they read the chip inside that 50 ms: `Tests/UI/test_console_dictation_firstrun.py::test_a_slow_first_run_shows_the_preparing_message_not_a_frozen_button` and `::test_an_unrelated_ui_refresh_cannot_wipe_the_preparing_message` fail about 1 run in 3 on dev (the first failed on dev ddd3c02052 and passed on the TASK-33621.21 branch in the same comparison run).

2026-11-24: the first of the two failed in both merge-queue runs of PR #3708 (run 45362116936, Linux), on dev 9fa2bf1b1d alone, and on the rebased branch (`assert '◐ Loading speech model…' == '◐ Preparing speech model…'`). The light CI tier (TASK-42521) runs this file whole for any PR that edits it, so the race now evicts such PRs. Evidence for AC #1: the "Loading" repaint is the newer copy (da28a28595, 2026-11-01; the first-run copy dates from 2026-07-28). That same commit wrote `Docs/User_Guide/console/attachments-images-voice.md`: "Current adapters show **Loading speech model…**: they do not expose an exact download artifact or a native-load heartbeat", with the first-run explanation carried by the toast detail.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A first-run quiet load shows "Loading speech model…" in the chip. The two tests now assert that copy and no longer race the warm-up's first poll. Test-only change, landed on the TASK-33621.21 branch (PR #3708) after the queue evicted it twice on the first of these tests.

AC #1, the copy. This was dev's decision already, so no new product decision was needed. da28a28595 (2026-11-01) added the quiet-loading repaint to `WARMUP_MESSAGE`. In the same commit it wrote the User Guide's "First run" entry (`Docs/User_Guide/console/attachments-images-voice.md`): "Current adapters show **Loading speech model…**: they do not expose an exact download artifact or a native-load heartbeat". The first-run explanation (`WARMUP_DETAIL_FIRST_RUN`) rides in the toast. The first-run chip copy dates from 2026-07-28, so the "Preparing" assertion was the stale side. Once shown, the chip keeps "Loading" until something else replaces it. The same file covers each replacement: real progress (the "MB" download test), the still-preparing note (TASK-33621.21's note test), and the end of preparation (both tests reach "Dictating", and the refresh test asserts "speech model" is gone). It also survives an unrelated control-bar refresh (the second test).

AC #2. Both tests now wait for the painted `◐ Loading speech model…` instead of any "speech model" text, and assert it exactly. The refresh test takes its "before" snapshot from that settled copy. Before, a snapshot of the first-run copy was overwritten by the warm-up's own repaint about 50 ms later, so the failure was a test race, not a refresh wiping the chip. The composer still re-applies the held preparing message on every resync. 10 of 10 runs alone for each test (2026-11-24, macOS).

Left as is: the first-run copy still paints for up to one poll (`WARMUP_POLL_SECONDS`, 0.05 s) before the repaint. Dropping that first paint would be a product change; `test_the_first_run_message_differs_from_later_presses` pins the first event's first-run copy. A mutation check of the refresh test (dropping the held message in `sync_dictation_state`) was not run: the edit to the product file was refused in this session.
