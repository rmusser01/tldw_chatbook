## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in the round-1 review of Phase 9 Task 17 (2026-10-17). TASK-33641.11 made the loader's legacy `[API]` bridge honour `credential_source`, and TASK-33001.14 made summaries take the key readiness resolves. Readers that go to the raw `[API]` section themselves were outside that task and still ignore the source. `config.get_api_key` never reads `credential_source`: it reads the table's `api_key_env_var` even under "none", then falls back to `get_cli_setting("API", "<provider>_api_key")` and the conventional variable. Its callers are Console realtime (`UI/Console_Modules/realtime.py`), the OpenAI and ElevenLabs TTS backends, the MCP server's chat tools (`MCP/server.py`, `MCP/tools.py`), and the Models screen's vLLM connection probe (`UI/LLM_Management/vllm_connection.py::_default_credential_resolver`, which sends the key as `Bearer`) and credential flag (`UI/Screens/llm_screen.py`): under "none" `get_api_key("vllm")` returns the variable the shipped `api_key_env_var = "VLLM_API_KEY"` names whenever it is exported, though readiness ignores it. `RAG_Search/simplified/active_config.py` reads `OPENAI_API_KEY` and then `[API] openai_api_key` directly. Text to speech takes its OpenAI key in `TTS/legacy_bridge.py::legacy_provider_config`, which reads the raw TOML's `[API] openai_api_key` (then `OPENAI_API_KEY`) into the projection's `openai_api` dict that `TTS/TTS_Backends.py::_prepare_backend_config` hands to the backend, so fixing `TTS_Backends.py` alone leaves TTS sending the removed key. Two TTS surfaces read the same raw `[API] openai_api_key` themselves, from `COMPREHENSIVE_CONFIG_RAW`, and never check the source: `UI/Screens/settings_speech_tts.py::_credential_states` (its `_CREDENTIAL_LOCAL_LOCATIONS["openai"]` ends in `("API", "openai_api_key")`) sets the Settings ▸ Speech & TTS credential source, which `Widgets/Settings_Widgets/speech_tts_settings_panel.py` shows as "Saved local config" with "Replace credential"; and `UI/Wizards/first_run_voice_credentials.py::find_openai_credential` (its `_SAVED_KEY_LOCATIONS` end the same way) picks the key the first-run Voice step reports as found, sends in its test and lets its save go ahead with. With no `OPENAI_API_KEY` exported, both agree with what synthesis sends, because the projection sends the `[API]` key too, and fixing the projection alone would leave the panel showing a saved key that synthesis no longer sends, and the Voice step testing with it: the readiness/spend split ADR-012 forbids. With the variable exported the readers split whatever the source, and which one is out of line depends on the source and on where the saved key is. The projection (and `_prepare_backend_config` behind it, which puts its key in the backend's explicit-override slot) and `find_openai_credential` read `api_settings.openai.api_key`, then `[API] openai_api_key`, then the environment; `_credential_states` ranks the environment first. With no `credential_source` recorded, for a table key the projection's order is ADR-012's 2026-09-19 order, which chat, readiness and `get_api_key` follow, so the panel is the reader out of line: it says "Credential is available outside Chatbook." and "A saved local fallback is shadowed." while synthesis sends the table key. `Tests/UI/test_settings_speech_tts_model.py::test_load_state_keeps_credentials_out_of_editable_provider_values` pins that environment-first label with table keys. For an `[API]` key the projection's order inverts the 2026-09-19 order, under which the variable the table names outranks `[API]`: chat, readiness and `get_api_key("openai")` send the variable and the panel's "Environment" agrees with them, while synthesis and the Voice step use the `[API]` key. So a user with a stale `[API]` key and a valid exported one sees "Environment" and still gets an auth failure; the defect there is in the projection, not the panel. A recorded source moves chat and readiness, so the reader out of line can flip. Under "stored" they send the table's key (or the `[API]` key the bridge copied there), as `get_api_key`, the projection and the Voice step do, so the panel is out of line for an `[API]` key as well as a table key. Under "environment" they send only the variable, as the panel says, so the projection and the Voice step (and, for a table key, `get_api_key`) are out of line for a table key as well as an `[API]` key. Under "none" they send nothing while every other reader still finds a key. ElevenLabs is labelled the same way, but no `[api_settings]` table names its variable, and its readers disagree on `[API]` against `ELEVENLABS_API_KEY`: the loader's `elevenlabs_api` dict (`os.getenv("ELEVENLABS_API_KEY", …)`) and the panel take the variable first, and the projection and `get_api_key("elevenlabs")` take `[API]` first. Two surfaces write the OpenAI TTS key and record no `credential_source`: Settings ▸ Speech & TTS Set/Replace (`Event_Handlers/STTS_Events/stts_events.py`, whose `_TTS_SETTING_BINDINGS["openai_api_key"]` writes only `api_settings.openai.api_key`) and the first-run Voice step's Next (`UI/Wizards/first_run_voice_step.py`, same field). Readiness ignores a table key under "none" (`Chat/provider_readiness.py::resolve_provider_credential`). So once the TTS readers honour the source, a key saved there after a Clear in Settings ▸ Providers goes unused, while the panel's post-save state, rebuilt in `Widgets/Settings_Widgets/speech_tts_settings_panel.py` from the mutation alone, says a local credential is available, and after a reload it shows Missing. `Model_Artifacts/acquisition.py::EnvConfigCredentialResolver` reads `HUGGINGFACE_API_KEY`, `HF_TOKEN`, then `[API] huggingface_api_key`; Parakeet, OmniVoice and the Models screen's remote GGUF installs use it by default. Probed at the Task 17 head (74b5af9d16) with the real loader on a scratch config with `[API] openai_api_key` set and `[api_settings.openai] credential_source = "none"`: readiness resolved no key and `openai_api.api_key` was None, but `get_api_key("openai")` returned the `[API]` key. Probed again at 366741be8f the same way: with `[API] huggingface_api_key` set and Hugging Face's source "none", readiness and `huggingface_api.api_key` were None but the artifact resolver returned the `[API]` key; with OpenAI's source "none", `legacy_provider_config("openai", …)` put the `[API]` OpenAI key in `openai_api`; with vLLM's source "none" and `VLLM_API_KEY` exported, readiness resolved no key but the vLLM probe's resolver returned the variable. Probed at a3990cd6f3 with `[API] openai_api_key` set and OpenAI's source "none" in `COMPREHENSIVE_CONFIG_RAW` and no `OPENAI_API_KEY`: `_credential_states` gave "Saved local config" with `local_saved` True, and `find_openai_credential` returned the `[API]` key. Probed at fd7e5df142 the same way with `OPENAI_API_KEY` and `ELEVENLABS_API_KEY` exported and `[API] elevenlabs_api_key` set: `_credential_states` gave "Environment" with `local_shadowed` True for both, `legacy_provider_config` put the `[API]` keys in `openai_api` and `elevenlabs_api`, and `find_openai_credential` returned the `[API]` OpenAI key. Probed at c9570133ea with a scratch HOME and a clean environment, the shipped `api_key_env_var = "OPENAI_API_KEY"`, no source, and `OPENAI_API_KEY` and `ELEVENLABS_API_KEY` exported. With `[API]` keys: the chat bridge's `openai_api.api_key`, readiness and `get_api_key("openai")` gave the variable, `legacy_provider_config` and `find_openai_credential` the `[API]` key, and the panel "Environment" (shadowed); for ElevenLabs the loader's dict and the panel gave the variable, and the projection and `get_api_key("elevenlabs")` the `[API]` key. With table keys instead, every OpenAI reader but the panel gave the table key and the panel said "Environment"; for ElevenLabs the projection and `get_api_key` gave the table key, and the loader's dict and the panel the variable. Probed at cbca546ede the same way with each source recorded. Under "stored", with an `[API]` key or a table key, the chat bridge, readiness, `get_api_key`, the projection and the Voice step gave the saved key, and the panel said "Environment". Under "environment", the chat bridge and readiness gave the variable and the panel said "Environment", while the projection and the Voice step gave the saved key, and `get_api_key` gave the table key when there was one. Under "none", the chat bridge and readiness gave no key, while `get_api_key` gave the table key or, for an `[API]` key, the variable, the projection and the Voice step the saved key, and the panel said "Environment". So after a Clear in Settings, these features still spend the key the user removed, against ADR-012. The User Guide's settings page names them as still reading the `[API]` line, and says the vLLM connection check still sends `VLLM_API_KEY`.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 With credential_source none recorded for a provider, `config.get_api_key` returns no key even when the provider's `[API]` key, its table's named variable or its conventional variable is set, proved by a real-loader test on a scratch config
- [ ] #2 With credential_source environment, `config.get_api_key` returns only the variable the table names, and with stored only the table's key (or the `[API]` key the bridge copied there), matching readiness for every combination the test covers
- [ ] #3 A provider with no credential_source recorded keeps today's order, pinned by the existing `get_api_key` tests
- [ ] #4 The TTS projection (`TTS/legacy_bridge.py`, and `TTS/TTS_Backends.py` behind it), the RAG embedding reader and the Hugging Face artifact resolver take their key from the same rule as `config.get_api_key`, and the Settings ▸ Speech & TTS credential state (`settings_speech_tts.py::_credential_states`) and the first-run Voice step's key lookup (`first_run_voice_credentials.py::find_openai_credential`) follow the same rule as the TTS projection, or each remaining difference is recorded in ADR-012
- [ ] #5 With no credential_source recorded, a table key (`api_settings.openai.api_key` or `api_settings.elevenlabs.api_key`) and the provider's variable both present, the Settings ▸ Speech & TTS credential state reports the table key as the one in use, as synthesis and the Voice step use it (and, for OpenAI, chat, readiness and `get_api_key`), proved by a test (`test_load_state_keeps_credentials_out_of_editable_provider_values`, whose fixture is a table key, changes with it). A recorded source is AC#1, AC#2 and AC#4's: under "environment" the panel keeps reporting the variable chat and readiness spend
- [ ] #6 With no credential_source recorded, a legacy `[API] openai_api_key`, no table key, and the variable the table names (the shipped `OPENAI_API_KEY`) exported, the TTS projection and `find_openai_credential` use the variable, as the chat bridge, readiness and `get_api_key("openai")` already do, and the panel keeps reporting the environment above `[API]`, proved by a test with `[API]` plus an exported variable. A recorded source is AC#1, AC#2 and AC#4's: under "stored" the panel moves to the `[API]` key the bridge copied, which chat, readiness and the projection spend. For ElevenLabs, whose variable no table names, the projection, `get_api_key("elevenlabs")`, the loader's `elevenlabs_api` dict and the panel rank `[API] elevenlabs_api_key` and `ELEVENLABS_API_KEY` in one order, recorded in ADR-012
- [ ] #7 A Settings ▸ Speech & TTS Set/Replace or a first-run Voice-step save of the OpenAI key, made while "none" or "environment" is recorded, records "stored" (as a Settings ▸ Providers save does), or the surface tells the user the key will not be used; either way the panel's post-save state matches what a reload shows, proved by a test
- [ ] #8 The User Guide's settings page no longer names these features (the `[API]` readers and the vLLM connection check) as ones a Clear does not reach once they honour the source
