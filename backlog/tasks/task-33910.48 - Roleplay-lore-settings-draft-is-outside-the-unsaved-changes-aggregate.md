## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A lore settings draft, or a lore settings save in flight, is not in the dirty aggregate, so an import landing or a guarded action can proceed over it. It exists on dev today; B2b widens its reach to cross-kind import landings and does not fix it. ## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Interim only; the task stays To Do for B9a (TASK-33910.14).** Owner ruling 2026-11-05, "Interim landing check (Rec.)": a narrow lore-settings baseline used only by the import landing; B9a replaces it. Shipped in burn-down PR 5 of the B2b follow-ups (stacked on PR #3441).

- **On dev:** present. Nothing counted a lore Settings draft or a lore Settings save in flight. On the base a lore book with an edited scan depth was replaced by a same-kind landing ("Harbour Lore imported.") and left by a cross-kind one ("Character imported.", the mode switched to Characters).
- **What the interim covers (AC#2, ticked):** `PersonasLoreDetailWidget` keeps a loaded-settings baseline (`settings_snapshot()` after `load_book`; cleared by `clear`; `mark_settings_saved` moves it to the saved controls after a save whose view is still current) and `has_unsaved_settings` compares the controls with it, leaving out Enabled, which saves on each toggle. `PersonasScreen._lore_settings_unsaved_for_landing` is true while a Settings save holds admission (`_lore_settings_save_in_flight`, the save handler's existing predicate, now shared) or while the selected lore book's Settings differ from the baseline. Only `_land_import`'s clean test reads it, so a landing toasts where the import went and selects nothing.
- **What it does not cover (AC#1, not ticked):** guarded actions. The term is deliberately not in `_aggregate_roleplay_draft_snapshot`, `_run_guarded` or the leave-Roleplay veto: those would offer a Save that cannot save lore Options. A kind switch, a row pick or leaving Roleplay still drops a lore Settings draft without asking, as on dev. A draft left behind by a kind switch does not hold a later landing (the selection is gone, so the form cannot be reached). B9a's `lore_settings_dirty` domain with its save and discard executors replaces all of this.
- **Tests (`Tests/UI/test_roleplay_import_app.py`):** `test_an_import_never_replaces_a_lore_settings_draft[same-kind|cross-kind]`, `test_a_saved_lore_draft_lets_an_import_land_and_a_save_in_flight_holds_it`, `test_a_lore_settings_draft_left_by_a_kind_switch_holds_no_later_import`. Mutations M48-A (the landing ignores lore Settings), M48-B (no loaded baseline), M48-C (no in-flight term), M48-D (no `mark_settings_saved`) and M48-E (the interim ignores which kind is selected) each turn at least one case red.
- **Live (mounted harness, 120x36):** a lore book with scan depth typed as 7 and a card imported: the toast is "Imported Wren Halloway · in Characters", Lore › Kepler Atlas stays open and the value stays (`.b2b-evidence/followups/fu-landing-evidence/live/head-lore-draft-import.*`).
