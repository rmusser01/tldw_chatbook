## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
`on_mount` builds default readiness once, in its closing sync. The open as a whole builds it six times (eight when a suspended draft is restored): see "After `on_mount`" below.

Measured before. Four builds while mounting, not the three the rider lists: `_show_settings_view`, the recovery-region sync (it calls `_show_settings_view` again when no recovery shows), the direct call, and `_sync_completion_actions`. Restoring a suspended draft added a fifth through `_sync_readiness_display`.

Fix. `_sync_default_readiness` returns at once while `_defer_default_readiness` is set. `__init__` sets it; `on_mount` clears it just before its closing `_sync_completion_actions()`, after a suspended draft is restored and the generation controls are synced. The direct call in `on_mount` is gone. The sync sets every footer control from the draft each time it runs, and no step of `on_mount` between the skipped calls and the last one reads what it sets, so the mounted state is the same.

Test. `Tests/UI/test_console_session_settings.py::test_console_settings_mount_builds_default_readiness_once[model]`, `[context]` and `[suspended]` count the default-readiness resolver's calls made before the modal is mounted: 4, 4 and 5 against the modal at 10fead87cb, 1 each now. In the suspended case the restore's own sync is one of the calls the flag skips, so the count of one pins that `on_mount`'s build came after the restore. Each node also asserts that Apply is enabled, and the suspended one that Temperature is restored and Save as model default shows. Those asserts run after the number fields' echoes have rebuilt the footer (below), so they pin the settled open, not `on_mount`'s build.

AC#2. The files that cover the modal show no failing name that the base does not have (two load flakes aside, both green alone); the plan task's report lists the runs.

After `on_mount` (review fix, 2026-10-11). The count above stops when the modal is mounted. A print-only probe that logs every `_sync_default_readiness` call with its callers, run on the three nodes above and on `Tests/UI/test_console_settings_geometry.py::test_view_tabs_paint_their_whole_labels_after_each_view_switch` (both sizes), showed at c83a9c1150, before any key or click:
- 1 build in `on_mount`.
- 4 builds from `_generation_number_changed` (6 with a suspended draft): two for each number field whose compose-time `Input.Changed` arrives, one through `_cancel_generation_test` and one through the handler's own `_sync_readiness_display`. All arrive while `_updating_controls` is still set.
- 2 builds on the first `_poll_subscription_readiness` tick (the timer is 0.25 s, and `on_mount` sets the snapshot to None, so the first tick always differs): one through `_sync_readiness_display`, whose last statement is `_sync_completion_actions()`, and one from the poll's own `_sync_default_readiness()` call straight after it.

So an open built seven times (nine with a restored draft). The poll's own call is deleted: the display sync before it already ends in the same sync, and `_sync_saved_defaults_action` re-fits the footer itself when it changes a label. The same probe after the deletion: 1, 4 (6) and 1, so six builds (eight), and a later subscription change builds once where it built twice. `Tests/UI/test_console_session_settings.py::test_console_settings_subscription_change_builds_default_readiness_once` resets the snapshot, calls the poll and counts one more resolver call: `assert 7 == (5 + 1)` before the deletion, green after.

Not changed: the four (six) echo builds and the first tick. Guarding the echo changes more than a count.
