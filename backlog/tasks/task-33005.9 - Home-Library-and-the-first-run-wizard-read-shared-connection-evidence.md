## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Home, the Library "Use in Console" lock pre-check and the first-run wizard now share the Console's connection evidence.

- Home (`HomeScreen._home_console_model_state`) and the Library pre-check (`LibraryScreen._console_setup_would_block`, the readiness call only, with a function-local import) pass `connection_evidence=shared_connection_evidence(lambda: self.app)`, as the Console's own builders do. The owner is process memory, so a read makes no request (the test fails on any `httpx` send). After a refused test of the default connection the Library toast fires (before Console's first send only: `console_setup_is_blocking` is False once `first_send_completed` is set, and Console then shows the failure as Not ready instead of the Get started card) and Home's Model reads "Not ready", as the Console does.
- Home's word (review round 1): Home's "Not set up" covered every not-ready state, so reading shared evidence turned a configured local server that is down into "Model: Not set up". Spec §5 gives a known failure "Not ready" on every surface, while TASK-34100.5 AC#9 keeps "Not set up" for a skipped setup, so Home now tells the two apart instead of changing one word for both. `HomeScreen._home_console_model_state` returns (ready, failed check), where a failed check is a blocker a connection test produces (`endpoint_unreachable` or `credential_rejected`, the set `console_model_popover._TEST_FAILURES` names). `HomeDashboardInput` and `HomeContentSnapshot` carry it as `model_check_failed`, and `dashboard_state._model_word` gives the header, the Details summary and the agent-readiness line "Ready", "Not ready" or "Not set up". What blocks is only an `unreachable` listing result (refused, timed out, a connection error, a 401, and from a local server any non-2xx status but a 403 or 404, a redirect included, or an unreadable or oversized body). A failed generation test and a 403 or 404 listing ("model listing unavailable") leave Home at Ready and the Library unlocked, and the User Guide copy now says so. Review round 2: the next action under the header said "Set up Console model" after a failed check too, so `choose_next_best_action` now gives a failed check "Reconnect Console model" / "Console's model failed its last connection check." (the Console calls this state a reconnect). The action id stays `fix_model_setup`, so it still opens Settings ▸ Providers & Models; a missing setup keeps "Set up Console model". AC#4 records the Home behaviour.
- The wizard: the plan's premise holds (UI/Wizards/first_run_provider_step.py built a private `ProviderTestEvidenceStore()`). Linking it was not enough: the step's `ProviderDraftIdentity.credential_revision` is an edit counter (pinned monotonic by its tests and used by its discovery keys and write guard), not `connection_credential_revision`, so its facts would key no connection the Console reads, and a counter of 0 would key the keyless connection. `ProviderTestEvidenceStore` gains `credential_of`: the key a probe begun now sends. `begin` records the connection (the identity with that key's digest) and `settle` publishes under it; `rebase_after_save` carries a saved typed key from the draft to the stored connection; and such a store reads no facts back (`evidence_for` has no shared fallback), because its identities are not connections and an invalidated result would be read back for the identity it tested (the wizard's tests assert None there). If `credential_of` raises, the probe runs and its result stays private. Other stores are unchanged (`_shared_identity` is the identity itself). The step's store is `ProviderTestEvidenceStore(lambda: self.app, credential_of=lambda: self._credential_at_request_boundary()[1])`; the file stays at 2,454 lines (one comment reflowed).
