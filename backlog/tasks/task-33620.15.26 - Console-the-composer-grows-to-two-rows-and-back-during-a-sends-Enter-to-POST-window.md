## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while attributing TASK-33620.15.20 (2026-10-27). After that task's fix, the Enter-to-POST window's longest UI-loop callback on later sends is a whole-screen reflow and paint. A live probe that recorded which widgets each reflow resized or moved (160x45, Anthropic claude-haiku-4-5 through the review proxy, a chat of 32-46 messages, origin/dev 3be493413a and the TASK-33620.15.20 branch) showed two kinds of big reflow per send window:

- the user message and the assistant placeholder join the bottom-anchored transcript, so all 225-255 transcript widgets move and the whole transcript repaints;
- in 12 of 16 sends the composer grows from one row to two about 0.45-0.72 s after Enter and back to one row 0.9-1.35 s after Enter. The visible draft first narrows from 95 to 54 cells (the Send reason strip appears), then goes 54x1 -> 54x2, then 54x2 -> 54x1. Each change resizes both rails and the transcript (about 77 widgets re-clipped) and is followed by a reflow that moves every transcript turn. Each of those reflow callbacks took a median of 50 ms of UI-thread CPU (108 ms wall) at host load 15-24.

Pane captures of the TASK-33620.15.20 branch at 160x45 (a 65-character prompt, the chat's second send) show why. Until the turn is accepted the composer keeps the sent text and Send reads "Preparing...". About 0.6 s after Enter the Send reason strip appears with "Queue opens once this turn is accepted"; it takes about 40 cells, the draft narrows, and the sent text wraps to a second row ("about lanterns." on its own line). About 1.3 s after Enter the draft clears and the strip reads "Type to queue", so the composer is one row again.

The second kind changes no content the user asked for: it is the composer's own height reacting to the Send reason strip while the send is in flight. The same 1 -> 2 -> 1 row change also happens about 1.4 s before Enter while the prompt is typed in one burst (63x1 -> 95x2 -> 95x1 within about 100 ms).
