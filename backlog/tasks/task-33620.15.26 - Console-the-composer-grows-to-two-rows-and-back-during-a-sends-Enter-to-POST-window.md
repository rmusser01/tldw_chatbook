## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found while attributing TASK-33620.15.20 (2026-10-27). After that task's fix, the Enter-to-POST window's longest UI-loop callback on later sends is a whole-screen reflow and paint. A live probe that recorded which widgets each reflow resized or moved (160x45, Anthropic claude-haiku-4-5 through the review proxy, a chat of 32-46 messages, origin/dev 3be493413a and the TASK-33620.15.20 branch) showed two kinds of big reflow per send window:

- the user message and the assistant placeholder join the bottom-anchored transcript, so all 225-255 transcript widgets move and the whole transcript repaints;
- in 12 of 16 sends the composer grows from one row to two about 0.45-0.72 s after Enter and back to one row 0.9-1.35 s after Enter. The visible draft first narrows from 95 to 54 cells (the Send reason strip appears), then goes 54x1 -> 54x2, then 54x2 -> 54x1. Each change resizes both rails and the transcript (about 77 widgets re-clipped) and is followed by a reflow that moves every transcript turn. Each of those reflow callbacks took a median of 50 ms of UI-thread CPU (108 ms wall) at host load 15-24.

Pane captures of the TASK-33620.15.20 branch at 160x45 (a 65-character prompt, the chat's second send) show why. Until the turn is accepted the composer keeps the sent text and Send reads "Preparing...". About 0.6 s after Enter the Send reason strip appears with "Queue opens once this turn is accepted"; it takes about 40 cells, the draft narrows, and the sent text wraps to a second row ("about lanterns." on its own line). About 1.3 s after Enter the draft clears and the strip reads "Type to queue", so the composer is one row again.

The second kind changes no content the user asked for: it is the composer's own height reacting to the Send reason strip while the send is in flight. The same 1 -> 2 -> 1 row change also happens about 1.4 s before Enter while the prompt is typed in one burst (63x1 -> 95x2 -> 95x1 within about 100 ms).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A later send no longer changes the composer's height between Enter and the provider call, and moves the transcript at most twice (up to four times on origin/dev). Under the owner decision of 2026-10-29 recorded on TASK-33620.15.20 (do not bound the transcript; cut the whole-transcript reflows per send).

**Measured first (AC#1).** Headless (160x45, a later send of a 65-character prompt in a chat longer than the screen, every reflow from Enter to the provider call recorded with the regions it changed), origin/dev 38c9d2edcf:
- Both send paths: the Send reason strip's "Queue opens once this turn is accepted" appeared beside the text still in the composer and took about 40 cells from it (draft 95 -> 54 cells), so the one-row prompt wrapped to two rows, and back once the send took the text. Each height change cost two whole-screen reflows: the resize, then the bottom-anchored transcript moving every row.
- Stock path (the received-intent path a real Enter takes): then the store's echo and, 0.1-0.6 s later, the reply placeholder, usually in separate reflows. Whole-transcript reflows per window: median 4 (max 4), composer height change in 7 of 9 sends (3 runs x 3 later sends, archive check held 0.5 s as live preparation takes).
- Acknowledged path (the mounted send harness; custom, command and queue dispatch): the "Sending…" row, the echo replacing it (a row shorter, so every row above moved), the placeholder: five whole-transcript reflows.
- Live on origin/dev (r2 base arm, below): a send whose composer changed height spent 4 whole-screen reflows on it, 71-205 ms of UI-thread CPU per window (median 173 ms over the 4 such sends of 10).

**Fix.**
- `ConsoleComposerBar.note_draft_sending(stash)` records the capture a visible send took. `send_acknowledgement._schedule`, which both send paths share, calls it before admission (admission can sync the composer to "Preparing..." at once) and forgets it when the send is refused. While the composer shows that capture unedited, `_refresh_visible_draft` keeps the rows the composer already has: the strip still shows beside the text (as on dev), and the narrowed text is cut to its row instead of wrapping. An edit or a refusal makes the draft the user's again; the empty draft after the send is one row with the strip.
- `ConsoleSendAcknowledgement.project`: once the echo lands the send is released as before (Send, Run chip and tab read the turn's own state), but its "Sending…" row stands in for the echo until the echo's turn writes its next row, the echo stops being a plain row, or custody ends (`release` drops a stand-in too). On the acknowledged path the echo and placeholder land in one layout pass.
- Two earlier versions were replaced, both on live evidence. The first marked the draft in `show_send_acknowledged`, which the stock path never calls (r1: the fix arm still went 1, 2, 1 rows). The second hid the strip while the sent text showed; a within-launch ABBA toggle on a quiet host found it 50-75 ms slower to the POST (per launch +80, +75, -14, +73, +46, +106 ms, r6), likely because the strip's first layout moved from Enter into the durable commit's window. Two lessons added.
- Files: `Widgets/Console/console_composer_bar.py` (module size ratchet 7043 -> 7068 with a dated owner-decision comment), `UI/Console_Modules/send_acknowledgement.py`; User Guide `console/chat-basics.md` (the composer keeps its height while the sent text shows; a Sending… row keeps its mark until the reply row).

**Tests** (`Tests/UI/test_console_send_window_reflows.py`, three cases, about 32 s; on the UI PR gate census as three node ids at the tail, floor 1148):

Asserts no composer height change from Enter until the reply placeholder is laid out, the strip shown whenever the draft is empty, and at most two whole-transcript reflows; positive controls: the strip sat beside the sent text, and the prompt fits one row at the idle width but wraps at the width the strip leaves.
