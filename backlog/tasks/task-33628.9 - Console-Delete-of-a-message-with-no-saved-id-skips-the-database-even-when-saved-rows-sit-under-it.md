## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Carried over from the TASK-33628.6 (PR #2965) reviews. If the selected message has no persisted id (it is still in memory), the store skips the database delete entirely, even when persisted rows sit beneath it in the in-memory subtree. Those rows disappear from the transcript but come back on reopen.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Deleting an unsaved message also tombstones the persisted rows beneath it (or the delete is refused with a clear reason)
- [x] #2 Reopen agrees with what the Delete showed; a real-store test pins it
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Red test first (real store, real persistence service, in-memory DB): in a saved conversation, a message with no saved id has a saved reply under it; Delete it, then reopen. Show the reply coming back on origin/dev.
2. Fix: when the selected message has no saved id but its in-memory subtree holds saved rows, anchor the durable subtree delete on the first saved row and seed it with every saved id, in the same dispatch-branch mutation that moves the cursor. console_chat_store.py stays net-zero.
3. Undo restores the tombstoned rows (held ids -> committed tombstones); reopen agrees with the transcript.
4. Related suites and ratchets.
5. Checkpoint review follow-up: pin the case on the real UI path -- an unsaved interstitial SYSTEM note (a skipped-skill note) between a saved prompt and its saved reply -- red on origin/dev, green here.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Approach: tombstone, not refuse.** `ConsoleChatStore._delete_message` now runs one dispatch-branch mutation for every delete. Inside it, it builds the seeds (`console_legacy_flat_roots.delete_seeds`: the subtree's saved ids, plus .7's hidden flat rows) and anchors the durable delete on `message.persisted_message_id or` the first saved id among them. So when the selected message has no saved id but saved rows sit under it in memory (a saved child of an unsaved node is written under its nearest saved ancestor), the store still calls `delete_message_subtree`, fenced on that first saved row and seeded with every saved id of the subtree. A subtree with no saved row, or no persistence, takes the cursor-only path as before. A saved row with no `delete_message_subtree` seam now raises the existing "could not be persisted" error instead of being skipped. Undo needs no change: the held ids are the committed tombstones, so it restores them and reinserts the unsaved node in memory.

**Evidence.** `test_deleting_an_unsaved_message_tombstones_the_saved_rows_under_it` (real store over the real `ChatPersistenceService` and an in-memory `CharactersRAGDB`): a saved conversation, an unsaved prompt, then a saved reply under it (written under `c3`). Delete counts 2. The saved reply is tombstoned and held, search no longer finds it, and reopen shows exactly what the transcript shows. Undo restores the row and the in-memory pair, and reopen matches the pre-delete reopen. RED on the merge-base code (`f0ffcf9e81`): the saved reply stayed live (`[0] != [1]`), so it came back on reopen. GREEN here. The red run is the mutant that drops the fallback anchor.

`console_chat_store.py`: 22,491 -> 22,487 (the two deleter branches merged into one). Files: `tldw_chatbook/Chat/console_chat_store.py`, `Tests/Chat/test_console_message_delete_persistence.py`.

**Review follow-ups (checkpoint review).** The unsaved-node-with-saved-children state is reachable from the UI: the controller appends a skipped-skill note as an unsaved SYSTEM row mid-turn, and the reply after it is saved under the prompt (its nearest saved ancestor, `_nearest_persisted_ancestor_id`). `test_deleting_an_interstitial_note_tombstones_the_saved_reply_under_it` drives that shape: the note offers Delete (`ConsoleMessageActionService.available_actions`), Delete counts 2, the saved reply is tombstoned and the prompt stays, reopen matches the transcript, and Undo restores the reply, the note in memory, and the pre-delete reopen. RED on origin/dev (`[0, 0] != [0, 1]`: the reply stays live), GREEN here; the mutant that drops the fallback anchor fails it and the original test.

Not changed: when the fallback anchor (the first saved id in the subtree) was already tombstoned elsewhere, the delete is refused, not partial. A probe (deleted before commit) tombstoned that row directly and then deleted the unsaved prompt: `ValueError: Message ... not found` from `delete_message_subtree`, the transaction rolled back, the store kept every node, and the other saved row stayed live. That is the same refusal a selected message whose own saved row was tombstoned elsewhere gets today, so it is left as a follow-up rather than changing the persistence seam's anchor rule here.
