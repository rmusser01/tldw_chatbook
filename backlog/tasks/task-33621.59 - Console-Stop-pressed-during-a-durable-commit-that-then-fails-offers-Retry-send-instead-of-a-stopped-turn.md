## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during the TASK-33620.3 / TASK-33621.53 review (2026-10-29). Stop sets the ordinary commit owner's explicit_stop while its durable commit runs. If that commit then fails, the send is paused as PERSISTENCE and its card reads 'Send could not be saved' with Retry send, although the user asked to stop. By reading (not probed), this holds both for a failure inside the commit's transaction (the store's existing pause) and, since TASK-33621.53, for one before its reservation (which used to jam the chat instead, so the new behaviour is still an improvement). Decide whether an explicitly stopped send whose commit fails should settle as stopped, with its text given back, rather than offer a retry.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->

- [ ] #2 The stopped outcome is the same for a failure before the commit's reservation and for one inside its transaction
- [ ] #3 A test on the real controller and store presses Stop during a failing commit, in both windows, and asserts the stopped outcome, no provider request, and that the next send in that chat is answered
- [ ] #4 A commit that fails with no Stop still pauses as 'Send could not be saved' with Retry send (unchanged)

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Owner decision 2026-10-29: TREAT AS STOPPED (Stop wins).
1. Measure on dev with a probe on the real ChatScreen/runtime/controller/store and a file-backed DB: hold the commit, press Stop, let it fail before and inside the reservation; record pause, card, shelf, draft, attachments.

4. Runtime: a stopped refusal returns the unsent turn to the draft with its attachments (the card Cancel path) instead of shelving it.
5. User Guide copy, gates (size ratchet, diagnostic inventory, preflight), live verification with a real commit failure and the palette Stop.
