## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented as 6 SDD tasks (spec `Docs/superpowers/specs/2026-08-07-deep-search-tool-design.md`, plan `Docs/superpowers/plans/2026-08-07-deep-search-1356.md`), each independently reviewed and fix-rounded before the next began. Port source: tldw_server2's live `WebSearch_APIs.py` (read-only reference).

**Port inventory + deviations (Tasks 1-2).** Task 1 (1093331f8) hardened phase 1 in-place: sanitized/deduped sub-questions with an empty (not `[original_query]`) LLM-failure fallback, provider warnings surfaced into `web_search_results_dict["warnings"]` instead of silently swallowed, and `timeout=30` added to the serper/exa/yandex backends (the seven older engines' missing timeouts filed separately, task-3060). Task 2 (aea606ffe) ported the server's phase-2 hardening: typed `FinalAnswerDict` on every `aggregate_results` branch (replacing three different final-answer key names), chunked map-reduce aggregation (`_build_chunk_infos`, per-chunk failure degradation), computed confidence, `cancel_event`-cancellable relevance, and a non-interactive `review_and_select_results` (the blocking `input()` deleted). Deliberately NOT ported (spec, recorded): the per-provider circuit breaker (no chatbook analogue), `_enforce_provider_outbound_policy` (chatbook's search-provider calls are fixed HTTPS endpoints per task-1355), the server's extra engines, Bing's deprecation.

Two real deviations surfaced by review, not by design: the plan's confidence formula was transcribed as "verbatim" but was actually WRONG in two places — a flat `+0.05` LLM bonus where the server conditions `+0.1` on `failed_chunks==0`, and an inverted `chunk_count==0` case (should be `chunk_success=1.0`, zero chunks is not a penalty). Fix round 1 (a4f5d3cd9) corrected both, hand-computed against the server source line-for-line. The same round carried a MAP-phase rework ruling: the initial port summarized every chunk (MAP) but REDUCE always synthesized from the raw numbered entries, so N chunk-summarization calls were pure waste — paid, computed, never read. Ruling: a single chunk skips the MAP call entirely (context is already bounded); multiple chunks restore the server's design (synthesis consumes the chunk summaries), with an added "preserve `[n]` markers" instruction so the citation-integrity fix survives the reduce step.

**Review shape.** Every task's initial implementation went through an independent model review before the next task started; findings were triaged Critical/Important/minor, Criticals and Importants were fixed in a same-task follow-up commit (re-verified RED-then-GREEN before merging into the branch), and minors were explicitly deferred with the reason recorded in the SDD ledger — several were carried forward as handoff notes to the task that would actually own the fix (e.g. Task 2's malformed-timeout note became Task 4's config-guard requirement).

**SSRF guard (Task 3, f551ac34b + aaec9efe2).** `is_public_http_url()` added to `Utils/egress.py`, wired into `search_result_relevance`'s scrape step ahead of every Playwright navigation to an arbitrary result URL; a refusal falls through to the existing snippet/title/url fallback exactly like a scrape failure, never raised. Review found two Criticals, both fixed same-round: (1) multicast addresses (e.g. `239.255.255.250`, a real SSDP/UPnP discovery address) were classified "public" because `ipaddress.is_global` does not exclude multicast — an explicit `is_multicast` check now tightens every `_classify_ip` consumer; (2) `is_public_http_url` did synchronous DNS resolution called directly inside async `search_result_relevance`, blocking the event loop for the resolver's full duration (egress.py's own docstring warns against exactly this) — offloaded via `asyncio.to_thread`, bounded by `scrape_timeout_s`; a guard timeout raises `asyncio.TimeoutError`, which falls into the existing scrape-failure `except Exception` handler — no new code path.

**Config revival (Task 4, 5158dcb4c + c6b455174).** `[SearchSettings]` revived with all nine keys documented in the template (six existing consumers wired for the first time, three new: `relevance_llm_timeout_s=30`, `relevance_scrape_timeout_s=30`, `deep_search_timeout_s=240`). New `_get_int_timeout_value()` loader rejects booleans (`int(True)` silently succeeding was the trap) and malformed strings, degrading to the default with a logged warning; extended in review to also reject non-positive values (0, negative). Review also caught a missing `[tools] web_deep_search_enabled = false` template key — added with a restart-requirement + cost-shape comment.

**Tool honesty design (Task 5, cf5670aaa + b09fe5d92 + 09a3a38e3).** `web_deep_search` runs phase 2 under a wall-clock deadline (`deep_search_timeout_s`); on expiry, `cancel_event` is set cooperatively and the pipeline synthesizes from whatever was actually analyzed rather than discarding paid work. Two review rounds hardened what the tool is allowed to CLAIM: round 1 fixed a Critical where a deadline hit before any result was scored reported "Analyzed N results" and advised rephrasing — both false, and the advice steered toward a doomed second full-price run; round 2 (N2) found the fix itself still overclaimed ("none were scored in time" is unknowable whenever the watchdog fires mid-loop, since the pipeline exposes no scored-count signal) and reworded it to state only what's knowable, softening the footer's deadline language from "partial synthesis" (a claim) to "results may be incomplete" (what `deadline_hit` actually means). The footer is always present (confidence/engine/sub-queries/analyzed-count/fallback/warning/deadline facts); the Sources block carries two DISTINCT honest omission markers — a size-budget cutoff marker (so a zero-emitted-sources case from an oversized single line is never silently indistinguishable from "no sources") and a separate count-cap marker for evidence beyond `DEEP_SEARCH_SOURCES_MAX`.

**Caps/ceiling rationale (final shape).** `DEEP_SEARCH_ANSWER_MAX_BYTES = 10 * 1024`, `DEEP_SEARCH_TOTAL_MAX_BYTES = 15 * 1024` (combined answer + Sources + footer), `deep_search_timeout_s` default `240` — all sized against two independently-discovered runtime ceilings, not chosen in isolation: (a) the agent runtime truncates a tool RESULT to `RunBudget.max_tool_result_chars = 16,000` chars HEAD-FIRST (`content[:max_chars]` plus a trailer, never the tail), so the total output must leave headroom under that boundary or the Sources list and the honesty footer are silently cut off the end — 15 KiB keeps the whole output under 16,000 chars with margin; (b) the agent runtime's default per-call time ceiling is `RunBudget.max_tool_call_seconds = 300s`, and the tool's own internal deadline (240s + a 30s `wait_for` grace + a 5s thread-join slack = 275s worst case) must undercut it so a deadline-hit run can still return its honest partial synthesis before the runtime kills the call outright.

**Correction (2026-08-07, final whole-branch review fix wave, Minor 5):** the Task 6 bullet above (`Added LocalToolProvider.timeout_for()...overrides ONLY web_deep_search's per-call timeout to 290s...while staying under the runtime's own 300s outer ceiling`) describes a design fix round 1 had ALREADY replaced before Task 6 even started -- it was stale at the time it was written, not a later regression. `timeout_for()` calls `Tools/web_tool_impls.deep_search_outer_timeout_s()`, which DERIVES the outer per-call ceiling as `deep_search_timeout_s` + `_DEEP_SEARCH_DEADLINE_GRACE_S` (30s) + `_DEEP_SEARCH_THREAD_JOIN_SLACK_S` (5s) + `_DEEP_SEARCH_SCHEDULING_JITTER_S` (15s) -- i.e. configured value + 50s, unclamped against any 300s ceiling. At the shipped 240s default this still evaluates to 290s (matching the bullet's number by coincidence, not because 290 is a fixed constant), but for any OTHER configured `deep_search_timeout_s` the "staying under the 300s outer ceiling" framing is simply false -- there is no such clamp, and the "undercut 300s" obligation the plan/spec originally imposed on the operator no longer exists for any value.
