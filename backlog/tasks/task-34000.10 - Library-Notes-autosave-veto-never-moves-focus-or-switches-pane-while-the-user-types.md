## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
A character the user cannot see can send their typing into a different field. A first-timer types a title that ends with a space, Tabs to the body and keeps typing. Autosave fires, is vetoed, and pulls the cursor back to Title, so the next words land there. A stress tester with a duplicate keyword ("ok, x, X") saw the whole pane flip to Info, and the body text ended up in Keywords. The note is changed without the user noticing, and the status line contradicts itself.

Observed at 160x45:
- **Title case:** New note > Blank, title "Groceries " (trailing space) > Tab Tab > "milk" > wait 3 s > " eggs". The title becomes "Groceries  eggs" and the body holds only "milk" (`verify/nl-v-n-07/06-after-eggs-160x45.txt`).
- **Keyword case:** with Keywords "ok, x, X", text typed into the body ended up in Keywords as "ok, x, X body2", shown on the Info pane (`12-kw-after-body2-160x45.txt`).
- **Status line:** it reads "Title begins or ends with whitespace — remove it to save. · Next: Keep editing; changes save automatically."

Verified cause (origin/dev 2d34cbf80d):
- The coordinator returns a VALIDATION_VETO for leading or trailing whitespace in the title and for duplicate keywords (`Library/library_notes_session.py:582-597`). ADR-027 (`backlog/decisions/027-portable-database-note-session-coordinator.md`) requires this: saving must never strip or rewrite content.
- The screen then handles an autosave veto exactly like a veto on an explicit Save. `_apply_library_note_save_outcome` (`UI/Library_Modules/library_notes_controller.py:3945-3978`) routes to the vetoed field and focuses it without checking whether the save was explicit.
- For a keywords veto, `_route_library_note_validation_field` (:3865-3874) also switches the pane to Info.

Suggested direction (a direction, not a mandate):
- Pass whether the save was explicit through to the outcome handling.
- On an autosave veto, mark the field inline. Never move focus and never change Edit/Preview/Info.
- Move focus to the vetoed field only on an explicit Save or when the user tries to leave the note.
- When the user leaves a field, tidy title edge whitespace and duplicate keywords as a visible draft edit. This fits ADR-027, because it is a change the user sees in the draft, not a silent rewrite at save.
- While a veto is showing, drop the "save automatically" suffix.

No existing task owns this. TASK-32253 (Done; Shift+Tab selected the whole title) was a different focus defect. A vetoed nav-bar switch being silent is a separate review finding (S-17).

Review finding(s): N-07. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** A refused autosave now never moves focus or switches the pane, wherever focus is; the vetoed field is outlined with the coordinator's own reason under it and the status line reads "Fix the marked field, or press Save to go to it."; leaving Title or Keywords tidies exactly what the save would refuse, as a visible draft edit. Explicit Save, conflict Overwrite and leaving the note still route to the field.

**Approach.**
- `UI/Library_Modules/library_note_autosave.keep_autosave_veto_in_place` (TASK-34000.1's N-07 guard, extended): the focused-field condition is gone, `_EDITOR_FIELD_IDS` with it; the guard records `LibraryNotesState.validation_field` (new, 110 -> 111 in the wiring census). The three explicit veto presenters (`_apply_library_note_save_outcome`, the conflict-Overwrite veto, `_flush_library_note_save`) record it too and keep routing; `_schedule_library_note_autosave` clears it, and the presentation exposes it only while `autosave_state == "validation"`, so the mark can never outlive the veto.
- `LibraryNotePresentationState.validation_field` / `validation_message`; `LibraryNotesCanvas` composes one display-gated hint Static under each field (`#library-note-{title,keywords,context-keywords,body}-hint`, class `library-note-field-hint`), marks the vetoed field with `library-note-field-invalid` at compose time (the mount-time apply never runs, TASK-34000.25) and on every sync (`_apply_field_validation_marks`); `_authority_copy` gains the `state.validation` arm above the empty-body arm (a vetoed title on an empty note needs the fix named, not "Start typing").
- `Library/library_note_field_tidy.py` (pure): `tidy_note_title` (edge strip), `tidy_note_keywords` (first spelling of each case-folded identity, in order, joined ", "); Hypothesis pins each as the inverse of exactly its veto. `tidy_library_note_field_on_blur` (duck-typed, no Textual import) guards editor view, Notes/Create row, armed, not syncing, attached, note identity, then sets the Input's value under `prevent(Changed)` and calls the field's own screen `Changed` handler synchronously -- the same route a keystroke takes, with no window for a stale sync to overwrite the Input. ADR-027 holds: the edit is visible, the session takes it as a draft mutation, the save payload is untouched. Three `@on(Input.Blurred)` delegators on `LibraryScreen` (lazy import).
- CSS: new `css/features/_library_notes_panels.tcss` (the clarify batch, #3184's later commit 76850b108c, carves a sheet of this name out of the over-ceiling `_library_panels.tcss`; it is not in this branch's ancestry, so this task opens the file with only its rules and the same registration -- an add/add on the rebase, resolved by appending this block). Every selector token is Library-prefixed (0 bytes in the boot bundle; the rules land in `screen_agentic_library.tcss`). Compact layouts cap the hint at one row (nowrap + ellipsis; the status row carries the full reason): measured at 60x20 the wrapped hint took two rows and the body fell from five to two.
