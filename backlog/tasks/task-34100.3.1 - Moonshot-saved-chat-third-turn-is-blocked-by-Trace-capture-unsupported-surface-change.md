## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-34100.3's live verification. That task made Moonshot (Kimi) replies persist in a saved chat, which made a later turn reachable for the first time. The trace planner is not in that task's diff, so the defect is filed here rather than fixed there.

Every model Moonshot lists returns reasoning on each reply, and Console saves it with the reply so the next turn can replay it. With trace capture on (the default), turns 1 and 2 of a saved kimi-k3 chat reply normally. The third send stops before the provider: "Trace capture blocked · Problem: Trace capture could not be saved · Impact: The provider was not contacted", with Retry capture / Send without capture / Cancel send. The log records `phase=trace_reservation status=failed error_category=unsupported_surface_change exception_type=ValueError`. Send without capture then gets the right reply, so only the trace stage fails. A real OpenAI chat on the same build completes three turns, so the failure is specific to replayed continuations.

Likely mechanism (from `ConsoleTraceService` surface planning, `Chat/console_trace_service.py`, the `matches`/suffix loop that raises `unsupported_surface_change`): turn 2's request is [history…, continuation 1]; turn 3's is [history…, assistant 2, user 3, continuation 1, continuation 2]. The planner admits "new messages before an unchanged continuation suffix", but here the continuation list also grows, so the request has two change points and is refused. This is the same family as TASK-33621.29 (Compact now) and TASK-31742 (completed tool turn), whose notes record that a new admission shape changes the trace-admission contract governed by ADR-097 and needs design approval first.

Two more things seen in the same run, possibly related:
- On that blocked turn, **Cancel send** refused with "Trace reservation status is unavailable." Send without capture worked.
- After a relaunch, the earlier turn-2 assistant message showed an extra "▸ Error · failed" row. It comes from the blocked turn's agent run (`42a3245d…`, "unexpected provider error (Provider call trace persistence f…"), which is now drawn on the wrong message.

Found by TASK-34100.3's review (round 1), on the same blocked turn:
- **Retry capture** is the first action the card offers. It meets the same refusal, and then the turn shows the false delivery-unknown card ("Response delivery status is unknown on the source device. Retry anyway may send a duplicate request") with "Send blocked — resolve response recovery first", although the card itself said the provider was not contacted. A `dispatch_started` dispatch checkpoint is left behind. The likely path, read from the code and not yet confirmed by a test: `ConsoleChatController.resume_durable_postcommit` finds `checkpoint_transition` done and `provider_entry` not done, `_verify_trace_preparation_recovery` refuses again, and the `TraceCallPersistenceError` branch marks dispatch recovery needed as unknown delivery. If so, any trace-call pause whose retry is refused again is affected, not only Kimi (not checked on base).
- On that card, **Retry anyway** does nothing when clicked (no UI change, no log line), so **Discard** is the only way out, and no reason is shown.
- After a relaunch, the blocked attempt's error row has been drawn on turn 1's reply in one run and on turn 2's in another, so the target varies.

Reviewer evidence: `evidence/g3-verify-k3/26-31` (k3 turn four: Retry capture, the recovery card, Retry anyway, Discard), `evidence/g3-verify-k26/09-19` (k2.6), `evidence/g3-verify-k3/20-25` (the error row on turn 1 after relaunch).

Evidence (setup-wizard-ux-qa): `evidence/g3-live/07-k3-saved-turn-two.txt`, `08-k3-saved-turn-three.txt`, `09-k3-turn-three-send-without-capture.txt`, `12-turn-four-cancelled.txt`, `18-relaunch-history-chat.txt`; `homes/g3-live1/.local/share/tldw_cli/default_user/tldw_cli_app.log` (`unsupported_surface_change` at 19:09:07); OpenAI control `evidence/g3-live-regress/06-08-openai-*.txt`.

Updates from TASK-34100.3 review round 2 (2026-10-06):
- **Retry capture (AC#6)** no longer shows the delivery-unknown card for this pause. The pause records the failure itself because no call boundary was ever built, and a retry of that shape now returns to the same TRACE_CALL pause with "Trace capture was refused again; the provider was not contacted" (`Chat/console_trace_retry_refusal.py`). Verified live on kimi-k3 and kimi-k2.6 (`evidence/g3-r2-k3/11-12`, `g3-r2-k26/19`). Still open under AC#6: the pause itself already holds a `dispatch_started` checkpoint (rev 2) before any retry (`g3-r2-k3/10`), and what a relaunch shows during the pause has not been checked. A refused retry whose pause recorded a real boundary still goes to response recovery.
- **Retry anyway (AC#7)** is no longer reached from this pause. The card's own defect remains for other paths.
- **Error row after relaunch (AC#4)**: re-observed on turn 1's reply (`g3-r2-k3/25-relaunch-history-top.txt`).
- **What the planner admits (AC#1/AC#2)**: a probe through the real Console stack (`evidence/g3-r2-probe/01-turn3-replay-shapes.txt`) filtered the turn-3 replay four ways. Replaying both checkpoints, dropping all of them, and keeping only the newest were all refused (`unsupported_surface_change`). Only keeping the oldest one was admitted. So dropping the optional replay is not a workaround: removing an active continuation is itself a surface change. A fix needs the planner to admit an append in each domain (new messages, plus new continuations after the unchanged ones), which is an ADR-097 admission change.
