## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-34100.31 lets a user keep a new key in the system keychain, but keys already stored stay where they are, and the owner ruled that keys move to or from the keychain only on the user's request (spec Q3). A user who wants an existing plain-text or encrypted key out of the file, or a keychain key back in config.toml, needs a way to do that safely: a half-finished move must never leave a key in two stores or in none. Items an older build left behind need an owner, and long credentials on Windows need handling, because its credential store caps a value at 2,560 bytes. Backups are not this slice's work: TASK-34100.31 registers the backup adapter with the first keychain save (ADR-126's 2026-10-03 amendment), so a key moved to the keychain here is captured in local rollback archives like any other keychain-held key.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): D9 (moving keys, older builds, long credentials), §3.5, §4.6, §8.1, §8.4, §10 F12b.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The Keys step (in the walkthrough and as a single step) and Settings ▸ Privacy & Security offer only the moves that apply, and nothing moves by itself: 'Move to <platform keychain>' for a key in config.toml (plain, or encrypted within an unlocked session) where a keychain is detected, and 'Move to config.toml' for a key in the keychain. The default action on each key writes nothing
- [ ] #2 A move to the keychain writes the item, reads it back and compares, then removes the key from config.toml and sets credential_source in one config write. If any step fails, nothing is removed. Success says older backups or synced copies of config.toml may still contain the key
- [ ] #3 A move to config.toml makes one config write with the key (encrypted when encryption is on) and credential_source = "stored", reads it back, then deletes the keychain item. If the config write fails, nothing changes. If the delete fails, the key is used from config.toml and the leftover item is listed as orphaned
- [ ] #4 When the last encrypted key has moved to the keychain, Keys offers to turn password encryption off, through TASK-34100.4's lifecycle owner
- [ ] #5 Keychain items in chatbook's namespace that no provider uses (for example after an older build replaced the marker) are listed with Leave it, Use it and Remove it, and nothing is deleted automatically
- [ ] #6 On Windows a long credential is split with the server-credential store's part scheme, or the keychain is not offered for it, with the reason
- [ ] #7 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: moves in both directions on macOS Keychain, Windows Credential Manager and GNOME Keyring, each leaving exactly one live copy; a move of an encrypted key followed by turning encryption off; a round trip through the pre-change build that orphans an item; and a long JSON credential on Windows. Evidence is recorded in Implementation Notes
- [ ] #8 New behaviour is covered by tests that fail on the pre-change code (RED verified), and no module-size or ADR-097 ratchet is raised
- [ ] #9 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
