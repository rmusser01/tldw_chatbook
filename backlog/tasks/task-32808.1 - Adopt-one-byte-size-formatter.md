## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Sixteen byte-size formatters exist with no shared public helper, and their output drifts in ways users see: kilobytes against kibibytes, one decimal place against none, ladders that stop at gigabytes, terabytes or petabytes, and one that mixes decimal thresholds with binary divisors so 1,000,000 bytes renders as '1.0 MB'. A private helper in the shared utility module already does this correctly.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.
<!-- SECTION:DESCRIPTION:END -->

BYTE-SIZE ADOPTION 2026-09-20 (continuing .1): the public `format_size_bytes`
capped at GB, a regression for the ~15 file/repo copies that show TB+ (a 2 TB
repo would render "2048.0 GB"). Extended it to scale through PB (binary loop);
≤GB output is byte-identical to before, so existing pins hold (added TB/PB cases).
Adopted at the 2 gate-free-verifiable copies, both byte-identical for reachable
inputs: Tools/web_tool_impls._format_size (fetches < 1 TB; "5 B" pin holds) and
Library/library_ingest_state._human_size (incl. PB; its 512.0 TB/1.0 PB/1024.0 PB
test holds). DEFERRED: the remaining ~13 copies are ADR-126-gated user-facing
widgets whose adoption changes visible strings (spacing 5KB→5 KB, precision
.0f→.1f, unit ceiling) — a display-standardization UX call needing per-site
test-pin verification, not a mechanical swap. attachment_core._format_size is
DELIBERATE (MB cap, .0f KB for small attachments; pinned by test_attachment_core).
