## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: TASK-34000.16 made a file the walk can list but cannot read as note text (not UTF-8, mixed or CR-only line endings, not writable, more than one name on disk, changed during read) a named skipped row instead of the whole folder's refusal. Its review (2026-10-23) found that three kinds of file never reach that gate, because `discover_import_sources` refuses them BEFORE `PosixNotesSyncFilesystem.observe` runs, so they still refuse the whole folder exactly as before:

- a file over 10 MB (`ImportSelectionError("max_file_bytes_exceeded")`, `note_import_discovery.py` `_admit_file`);
- a symlinked `.md` (discovery does not follow links);
- a FIFO or other non-regular entry.

For a researcher's folder this is the same stop-the-folder failure the parent task removed, just for a rarer file. Separately (pre-existing, found in the same review): `sync_paths.py` `read_bytes` turns any `os.open` failure into `link_or_reparse`, so a chmod-000 `.md` is skipped as "A link, not a file — move it out of the folder" when the true cause is that it cannot be opened (the `operation_failed` copy, "Couldn't be read — check that you can open it", is the right row).

Direction (not a mandate): let discovery report these entries as per-file failures the runtime can turn into `ReconciliationItemSkip` rows with their own plain copy (the `_FILE_GATE_SKIP_EFFECTS` table already has `max_file_bytes_exceeded`, `link_or_reparse` and `non_regular` sentences), keeping a root-level refusal only for a listing failure; and distinguish an open refused by permissions from a link in `read_bytes`.
<!-- SECTION:DESCRIPTION:END -->
