## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Rider from TASK-33001.7. Settings ▸ Providers & Models picks the credential source for a save in `SettingsScreen._provider_current_credential_source`. When no credential field is dirty, it returns "environment" as soon as the Env var field holds a name, before it checks for a stored `api_key`. The shipped config template gives every `[api_settings.<provider>]` table an `api_key_env_var`, and Settings prefills that field from it.

So a legacy section (no `credential_source`) that holds both a stored `api_key` and the template's env-var name loses the key on any connection save, including a model-only change. The shared builder turns "environment" into a write of `api_key_env_var` and `credential_source = "environment"` plus a delete of `api_key`. If the variable is unset, the provider stops working and the key is gone from config.

Reproduced at BASE 68240aba01 and at TASK-33001.7's head, with a mounted Settings screen on a private profile and a captured mutation. The section was `[api_settings.openai]` with `api_key = <stored>`, `api_key_env_var = "OPENAI_API_KEY"` and a model, and `OPENAI_API_KEY` was unset. Changing Model to `gpt-4.1-mini` and saving produced this mutation:
- sections: `{'api_settings.openai': {'model': 'gpt-4.1-mini', 'api_base_url': …, 'api_key_env_var': 'OPENAI_API_KEY', 'credential_source': 'environment'}, …}`
- deletes: `{'api_settings.openai': ('api_key',)}`

That legacy precedence also contradicts ADR-012's 2026-09-19 amendment: resolve_provider_credential prefers the stored key, so readiness before the save read "config:" and after it reads the environment.

TASK-33001.7 changed this function only for keyless providers. For those, an untyped template name on a legacy section no longer counts, and the readiness fallback decides. Keyed providers were left as they were.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: a Providers & Models save that touches no credential field now keeps the credential that currently resolves. A stored key is no longer saved as "environment" and deleted.

Root cause: `SettingsScreen._provider_current_credential_source` returned "environment" whenever the Env var field held a name. It did that before it looked for a stored `api_key`, and the shipped template prefills that name for every provider. The shared `build_provider_setup_mutation` then wrote `credential_source = "environment"` and deleted `api_key`. That was the reverse of `resolve_provider_credential`, which ranks the stored key first (ADR-012, 2026-09-19 amendment).

Fix (one guard in the shared source function, so both callers get it):
- When neither `api_key` nor `credential_env_var` is dirty, the function asks `resolve_provider_credential` itself which credential resolves now. If it is the stored key (`config:`), the answer is "stored". The builder then keeps `api_key` and records `credential_source = "stored"`. Every other case falls through to the unchanged dev logic.
- Both callers route through this function: `action_settings_save_category` (the save mutation) and `_provider_current_draft_identity` (the Test evidence identity and the post-save rebase). The tested identity and the saved identity therefore still agree.
- Quit path: `persist_cli_config_for_shutdown` merges the template back into the file, so the env-var name returns next to `credential_source = "stored"`. On dev, the next model-only save of that section would have deleted the key, even with an explicit "stored" source. The fix covers that state too (test row explicit-stored-template-name). The key still resolves after the quit rewrite, even with the variable exported.
- Explicit actions keep dev behaviour: typing a key ("draft"), Clear saved key (falls back to the env var), and typing an env-var name (deletes the stored key). A keyless provider with no stored key saves exactly as on dev ("environment"). TASK-33001.7 changes that row separately. A keyless provider that does hold a stored key now keeps it, like any other stored key. On dev it was deleted, and TASK-33001.7's code also returns "stored" there.
- Edge case: a stored key that the resolver accepts but the builder's stricter `_validate_credential_value` rejects (control characters, over-long) now fails the save with the existing "Provider settings are invalid" message. It is not deleted.

Tests: `Tests/UI/test_settings_configuration_hub.py::test_settings_model_save_keeps_the_stored_key_that_resolves` runs 7 rows on a private profile (`private_profile_test`, scratch TLDW_CONFIG_PATH). The real atomic writer runs, and a delegating spy records the mutation. It asserts that `api_key` is not in the deletes, the value in the written file, `resolve_provider_credential` on the file before and after the save, and `get_provider_readiness` on the reloaded runtime config before and after. For the model rows it also runs the real shutdown persist and a forced reload. RED on dev: 3 bug rows fail with `assert 'api_key' not in ('api_base_url', 'api_key')`. GREEN after the fix: 7/7.

Docs: `Docs/User_Guide/settings.md` does not describe credential precedence on save, so it is unchanged.
