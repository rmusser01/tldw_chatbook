## Description

Apply the per-conversation automatic policy before provider dispatch with
fixed source categories and explicit recovery instead of silently sending
after retrieval failure.

## Acceptance Criteria

- [ ] Eligible sends use the executed draft and fixed Notes, Media, and
      Conversations categories, never a manual search's source filters.
- [ ] Current item scope narrows Notes/Media and excludes Conversations under
      the established active-scope semantics.
- [ ] Explicitly staged evidence and all existing ineligible send kinds skip
      automatic retrieval without duplicate spend or context.
- [ ] Preparation is visible and cancellable before provider dispatch; Cancel
      preserves the exact draft/attachments/evidence/prefill, removes the
      transient echo, and sends nothing.
- [ ] Timeout/failure pauses with Retry, Send once without Library, and Cancel;
      every choice preserves standing policy and has a distinct tested result.
- [ ] Success stages evidence into the exact dispatched request, while zero
      matches and one-shot bypass persist bounded device-local sent-turn
      disclosures containing no query or source identity.
- [ ] A pure preparation-sidecar projection owns those disclosures without
      changing generic trajectory timing/message ownership; default/full export
      remain bounded and import is inert.
- [ ] A store-owned compare-and-set preparation state survives navigation and
      makes repeated/racing Retry, Bypass, Cancel, close, and shutdown
      exactly-once in process; a changed resolved destination cannot be silently
      substituted on retry.
- [ ] Ordinary-session durable identity and auto-title remain staged until the
      conversation/policy/USER/assistant/checkpoint/preparation transaction
      commits; injected failures at every write boundary roll back SQLite,
      preserve the prior in-memory identity/title and exact staged state, enter
      a recoverable paused state, and retry without orphaning or duplicating a
      conversation.
      Automatic and Never sends share this commit boundary; Never performs no
      retrieval and shows no Library-preparation status.
- [ ] Persistence failure shows generic Retry/Cancel for both Automatic and
      Never; Send once without Library appears only for Automatic retrieval
      timeout/failure and never as a database-recovery action.
- [ ] The atomic transaction creates one empty assistant recovery owner plus a
      revisioned row in the foundation's dedicated device-local
      `console_dispatch_checkpoints` table. Post-commit failures hydrate that
      owner: accepted offers Retry response/Discard, dispatch-started offers
      warned Retry anyway/Discard, and no state automatically replays or
      creates another USER/assistant row.
- [ ] The checkpoint contains no request/content/credential payload, is absent
      from sync/import, both trajectory export modes, provider context, and
      generic trajectory projection, and is removed only after a durable
      assistant terminal state; unreconstructable transient inputs disable
      retry with a literal reason.
- [ ] Terminal completion and Discard atomically update the expected assistant
      and delete its expected-revision checkpoint. Loader reconciliation treats
      terminal assistant + stale checkpoint as terminal, hydrates valid
      nonterminal pairs, quarantines invalid ownership/role, and infers no
      recovery from an ordinary checkpoint-free assistant.
- [ ] Complete/empty, stopped, failed, and discarded outcomes persist the closed
      assistant generation state under frozen USER/assistant message versions
      and both `deleted = 0`; provider-history and literal empty/status
      rendering follow the specified outcome matrix.
- [ ] Ordinary provider history excludes accepted/dispatch-started owners;
      continuation-active content enters only through ADR-063's validated
      projection, so no empty recovery owner becomes a normal assistant item.
- [ ] A durable tool-call batch atomically writes ADR-063 continuation,
      transitions message state/version/hash/sync intent, and deletes the
      dispatch checkpoint before any tool executes. ADR-063 then exclusively
      owns recovery; if both owners are loaded, continuation wins and dispatch
      retry is never exposed; continuation completion/Discard writes the closed
      assistant terminal state in its message transaction.
- [ ] Valid active ADR-063 continuation is authoritative even when a pre-v45,
      older-sync, or imported assistant has NULL/missing generation state; the
      loader exposes its recovery surface with actions disabled and lazily
      normalizes under message-version/deletion CAS. Success publishes the
      committed version/hash to the recovery handle before Resume/Discard;
      known rollback re-reads the unchanged owner, while CAS conflict re-reads
      and hides/quarantines changed or deleted ownership instead of retaining
      stale actions. Resume/Discard after normalization and racing
      version/deletion/replacement paths are covered.
- [ ] Runtime state transitions use the foundation's migrated Sync-v1 triggers
      and backward-compatible Sync-v2 record/source/envelope contract. This task
      carries the closed state through active-path JSON, `.chatbook`, and
      text/Markdown projections but never exports the local checkpoint. A
      remote/imported unresolved owner renders inert literal source-device copy,
      and Retry as a new response creates a sibling rather than claiming it.
- [ ] Queued preparation retains the exact entry/authority, pauses later queue
      advancement, commits/acknowledges once, and releases the same entry back
      to pending on precommit Cancel.
- [ ] After durable acceptance, queued recovery never returns the entry to
      pending: later entries stay paused, post-commit effects are idempotent by
      preparation ID, and Retry/Discard settles that same entry before queue
      advancement.
- [ ] Ephemeral promotion contributes `library_preparation` rows through the
      foundation's transaction seam and restores preparation/session state on
      failure without depending on the later activity task. Ephemeral dispatch
      recovery remains in memory only, and any unresolved preparation or
      checkpoint analogue visibly blocks promotion without a write.
- [ ] Targeted send-path tests prove no failure path silently falls through to
      provider dispatch and replace TASK-3504's narrower zero-result proposal;
      fault injection covers every precommit write and every post-commit effect,
      dispatch-start, provider-call, atomic terminal/Discard settlement,
      ADR-063 handoff, sync/export/import projection, reconciliation, restart,
      ephemeral-promotion, and manual/queued recovery boundary.
