## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: PR #3423 review I-2 sent the select-mode bulk Add/Remove keyword through `NotesScopeService.change_local_note_keyword`, so each note takes the editor's keyword path, which applies the policy gate and records the Sync v2 organization intents. Before that, the change never reached another device.

The cost, as it was (measured 2026-11-06 on a real database, after the PR #3423 re-review's per-note transactions, `fcdebff32c`): with a ready Sync v2 local-first profile, each note resolved the profile inside its own write transaction. That was four `SyncStateRepository` reads: one `list_sync_v2_profile_states` from `resolve_profile_scope`, and three `get_sync_v2_profile_state`, two of them from `_profile`. One editor save pays them once.
- Speed: 50 notes took 6.9-7.5 s and 120 notes 17.2-18.6 s, with a median per-note lock hold of 136-152 ms, at load ~4. Under load ~100, 120 notes took 32.5 s. Without Sync v2, 50 notes take 90 ms.
- The lock: the ChaChaNotes database (conversations and messages too) was write-locked for 99.5% of the run. An `add_conversation` started halfway through waited out the rest of the run: 1.1-3.8 s for 50 notes and 2.7-9.1 s for 120. Started at the first of 120 notes under load, it failed after 15.6 s. `add_note` failed at once.
- The re-review N-1 measured about the same for the single transaction it replaced.

The fix (`e4888d67db`) resolves the profile once per bulk, outside every write transaction, through an optional, additive `resolved_profile` seam:
- `NotesOrganizationSyncService.resolve_profile` / `require_ready`, and `sync_subject_keywords(resolved_profile=...)`;
- `NotesScopeService.resolve_local_note_keyword_profile`, and `change_local_note_keyword` -> `_sync_local_note_keywords` -> `_organization_profile_scope`.
The group's readiness is checked once up front (a group that is not ready refuses every note before any is written), and each note re-checks it from the Notes checkpoint row inside its own transaction, with no profile read. Without a resolution, every other caller resolves as before.

Measured after the fix with a scratch probe that drives the real dialog and worker over real stores (the "as it was" figures above came from the same probe on `fcdebff32c`), at load ~4, 3 runs per case.

| | 50 notes | 120 notes |
|---|---|---|
| per-note loop | 0.057-0.061 s | 0.13-0.15 s |
| Apply to receipt (dialog, resolution, refresh) | 0.70-0.96 s | 0.76-1.18 s |
| median per-note lock hold | 0.6-0.7 ms | 0.6-0.7 ms |
| lock held, share of the loop | 63-70% | 63-70% |
| `add_conversation` started after the middle note commits, nobody waiting for it: it gets in within the remaining run (0.04-0.30 s measured, including PR #3423 re-review 2's runs) | 0.11 s here | 0.04-0.06 s here |
| `add_note` started the same way | "database is locked" at once, 3 of 3 | "database is locked" at once, 2 of 3; 1 ok |

Pinned in `Tests/UI/test_library_notes_bulk_keyword_per_note.py`: zero profile reads inside the note transactions, and the same 3 outside, for 5 and for 25 notes; and the un-gated `add_conversation` within 1 s at 50 and at 120 notes -- a bound, not a fairness guard: at 50 notes it often waits out the rest of the run, and the profile-read pin is what guards the seam. The scope-service pins are in `Tests/Notes/test_notes_scope_service_change_note_keyword.py`.

What remains (AC #5): the notes are still committed back to back, so the lock is held for about two thirds of the per-note loop. A deferred writer such as `add_note` fails at once if it lands inside that window, whoever holds the lock. The window is now 0.06-0.15 s instead of 7-18 s. Two ways to close it are not in this task's change: yield between notes (that trades the run's length for the share of it), or make `add_note`'s transaction `BEGIN IMMEDIATE` so it waits out the busy timeout like `add_conversation` does.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-11-06, `e4888d67db` (PR #3423, polish-1b): the bulk keyword worker resolves the Sync v2 profile once, before its per-note `BEGIN IMMEDIATE` transactions, through an optional `resolved_profile` parameter. The parameter runs through `NotesScopeService.change_local_note_keyword`, `_sync_local_note_keywords`, `_organization_profile_scope` and `NotesOrganizationSyncService.sync_subject_keywords`, so no note reads `SyncStateRepository` while it holds the ChaChaNotes write lock. Readiness:
- It is checked once up front; a group that is not ready refuses every note, naming the not-ready reason.
- Each note re-checks it inside its own transaction from the Notes checkpoint row.
- A profile whose mode or dataset changes during the 0.1 s run is not seen until the next bulk.

ACs #1-#4 are met; the numbers are in the description. AC #5 is not: the lock is held for 63-70% of the now 0.06-0.15 s per-note loop, and a mid-run `add_note` still failed at once in 5 of 6 probe runs (see "What remains"). The task stays open on AC #5 alone.
