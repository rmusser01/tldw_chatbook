## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: PR #3423 review I-2 sent the select-mode bulk Add/Remove keyword through `NotesScopeService.change_local_note_keyword`, so each note takes the editor's keyword path, which applies the policy gate and records the Sync v2 organization intents. Before that, the change never reached another device.

The cost, measured on a real database (2026-11-06, corrected after the PR #3423 re-review): with a ready Sync v2 local-first profile, 50 notes take 6.0-6.4 s to add a keyword and 5.9-6.4 s to remove it, and 120 notes take 15.6 s, at load average ~4; under load ~100, 120 notes took 32.5 s. Without Sync v2, 50 notes take 90 ms and 30 ms. (The first figure here, 10.8 s for 50, was taken under heavy machine load.) Each note pays four `SyncStateRepository` reads (one `list_sync_v2_profile_states` from `resolve_profile_scope`, three `get_sync_v2_profile_state` from `_profile`), about 120 ms at low load and 260 ms under load, the cost one editor save pays once.

What it does to everyone else is the real problem (re-review N-1). The re-review fix commits each note in its own `BEGIN IMMEDIATE` transaction, so a note that fails rolls back alone and the database is free between notes; a writer that arrives between two notes gets straight in (`Tests/UI/test_library_notes_bulk_keyword_per_note.py`). But each note's profile reads still run inside its write transaction, so the ChaChaNotes database (conversations and messages too, not only notes) is write-locked for nearly all of the run (50 holds with a 118 ms median in a 6.07 s run), in back-to-back slices, and the bulk retakes the lock microseconds after each commit while a waiting writer sleeps in SQLite's busy handler. Measured with a second thread writing mid-run:
- `add_conversation`, which waits on the 15 s busy timeout, gets in only when the bulk ends: 3.0-3.2 s when started halfway through 50 notes, 7.8 s halfway through 120; started at the first of 120 notes under load, it failed with "database is locked" after 15.6 s.
- `add_note`, whose deferred transaction cannot wait out a held write lock, fails at once ("database is locked" after 0.05 s) at any selection size.
That is about the same exposure as the single transaction the re-review measured (`add_conversation` waited 7.7 s for 50 notes and failed after 16.2 s for 120). Nothing caps the selection, and the Library's own Notes interlock is held for the whole run as well.

The fix is to resolve the Sync v2 profile once per bulk, outside the write transaction, which brings each note's hold back to milliseconds. There is no seam for that today: `_sync_local_note_keywords` accepts an explicit profile but still validates it with a private read, and `NotesOrganizationSyncService.sync_subject_keywords` reads `_profile` on every call.
