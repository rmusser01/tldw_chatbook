## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Review issue provider-13 asked for local detection to find LM Studio and for LM Studio to be
a provider the user can pick. TASK-34100.6 shipped the detection half: discovery probes
127.0.0.1:1234 in the same parallel short timeout, names the server 'LM Studio', and sets it
up through the generic Custom (OpenAI-compatible) row. What is still missing is an 'LM Studio'
row of its own in the shared provider catalog. Settings ▸ Providers & Models and the setup
wizard both read that catalog. Today a user who runs LM Studio and searches for it finds
nothing by that name, and a hand-picked setup lands on 'Custom' with no :1234 default.

A preset is more than a catalog row. Earlier presets (TASK-33510/33511, recorded in
`backlog/docs/lessons-testing-evidence.md`, "A provider preset's own tests never touched the
surfaces users set it up with") passed their own registry and dispatch tests. They still
failed on the surfaces users touch: Settings couldn't save them, the endpoint contract
rewrote their URLs, and readiness looked for the wrong variable. This task adds LM Studio
across every surface a preset needs:
- the provider registry and catalog record (local, default base URL
  http://127.0.0.1:1234, no key required, route suffix, check kind);
- the shipped config template's provider table;
- chat dispatch to an OpenAI-compatible handler;
- `provider_setup_persistence`'s canonical provider set and the endpoint contract;
- readiness.

Detection then maps :1234 to the LM Studio row instead of Custom. Split from TASK-34100.6
AC#17 because it is a new provider across all of those surfaces, not a Provider-step change.
<!-- SECTION:DESCRIPTION:END -->
