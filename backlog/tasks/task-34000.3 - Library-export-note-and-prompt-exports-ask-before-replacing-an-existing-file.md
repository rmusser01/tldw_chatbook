## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: exporting a note or a prompt can destroy a file outside Chatbook, such as the user's own ~/TODO.md. There is no confirmation and no undo, and the app reports success. A first-timer accepts the defaults. A researcher exports a recurring title. Both are exposed, because the default name is derived from the title and the picker starts in `~`. Two notes titled "Reading list" both default to `~/Reading list.md`, so a recurring title collides by default (B-static). Triage escalated this from P1 to P0: it is an unrecoverable loss of a user file behind a "success" toast.

What was observed (160x45; the stress journey j6 and the verifier):
- The user exports a note to an existing `exp/precious.md` that held "PRECIOUS USER FILE". The toast reads "Note exported successfully to precious.md" and the header "Saved · Export complete." The file now starts with the note's front matter (verify capture 09).
- Prompt export does the same: "Prompt exported successfully to Weekly review coach.md", with no replace prompt (capture 15).
- The toast gives only the file name, never the folder.

Verified cause (origin/dev 2d34cbf80d):
- Note export opens `FileSave(location=str(Path.home()), default_file=f"{safe_title}.md")` (UI/Library_Modules/library_notes_controller.py:4300-4323). The picker's `can_overwrite` defaults to True (Third_Party/textual_fspicker/file_save.py:37).
- The note is written with a plain `Path.write_text` (UI/Screens/library_screen.py:21160).
- Prompt export uses the same pattern (UI/Library_Modules/library_prompts_controller.py:3709-3712), also written with `write_text` (library_screen.py:27359).
- Code-traced, not reproduced live: the Report artifact export (UI/Library_Modules/library_artifacts_controller.py:758, write at :775-777) opens the same picker the same way. The Collections legacy-recovery export (UI/Library_Modules/library_collections_controller.py:1164) records the existing target's identity at :1193 only as a race guard, and still replaces the file without asking.
- Library is inconsistent with itself here: the Export-bundle canvas already checks `destination_exists` (UI/Library_Modules/library_export_controller.py:1408).

Suggested direction (a direction, not a mandate):
- Add an overwrite confirmation at the shared FileSave seam: 'Replace "x.md" in ~/exp? Cancel · Replace', with Cancel focused. Apply it to the note, prompt, artifact and collections exports.
- Write through a temp file plus `os.replace`.
- Remember the last export directory.
- Put the full destination path in the success toast.

Ownership: no existing task owns this. Related but out of scope:
- L-18 (the Export-bundle canvas's same-day zip overwrite): TASK-32381 and TASK-32382.
- N-12 (cancelling an export is reported as "Export failed"): a separate finding.
- N-20 (invalid YAML front matter): a separate finding.

Review finding(s): N-11. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. One seam for every single-file Library export: a new `UI/Library_Modules/library_file_export.py` owns the
   replace confirmation (`ConfirmationDialog`, Cancel focused, Escape = Cancel, prompt names the file and its
   folder), the atomic write (`Utils/atomic_file_ops.atomic_write_text`: temp file in the same directory +
   `os.replace`, temp cleaned up on failure), the remembered export folder for the session, and the full-path
   success receipt. The note, prompt, Report-artifact and Collections legacy-recovery exports all go through it.
2. Callers keep validating through `path_validation.validate_path_simple` where they do today; the screen's two
   write methods and the two controller write methods become thin delegators (the controllers and the screen are
   at or over their size ratchets, so the bodies move into the new module rather than growing in place). The four
   `FileSave` pushes open in the last folder exported to this session (home until then).
3. The confirmation is pushed with a result callback, never awaited (`push_screen_wait`) from a handler or a
   `call_after_refresh` callable -- the W003 freeze shape.
4. TDD: a real-app Pilot test (note and prompt export onto a pre-existing file) asserts the file's bytes are
   unchanged until Replace is chosen and after Cancel/Escape; RED on 633b6504e4, then GREEN. Unit tests pin the
   atomic write (a failing write leaves the original intact, no temp left behind), the remembered folder, the
   prompt copy, and the artifact/collections paths with fake owners.
5. Live verification in the isolated harness at 160x45 and 120x36 (Cancel, Escape, Replace; `md5` before/after),
   captures under `qa/notes-library-ux-review-2026-10-02/fixes/task-34000.3/`.
6. User Guide (`library/notes.md`, `library/prompts.md`, `library/collections.md`) updated; targeted tests,
   collect-only sweep and `./scripts/preflight.sh` run before the commit.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fixed at the shared save seam, so every single-file Library export is covered by one confirm and one atomic write.

**New module `tldw_chatbook/UI/Library_Modules/library_file_export.py`.** It owns:
- `request_export_write(app, destination, on_replace, on_cancel)` — writes at once when nothing is there; otherwise pushes the house `ConfirmationDialog` ("Replace existing file?", Cancel focused, Escape/backdrop = Cancel, prompt names the file and `~`-shortened folder, per ADR-031) **with a result callback, never an awaited `push_screen_wait`** (the W003 freeze shape). `on_replace` runs only for an explicit Replace.
- `write_export_text` — `atomic_write_text` (temp file in the destination's own directory + `os.replace`, `preserve_existing_mode`), so a failure leaves the original intact and no temp behind; it refuses to invent a missing parent folder.
- `remember_export_directory` / `library_export_picker_location` — the next picker of the session opens in the folder last exported to (home until then), with a fall-back when that folder no longer exists.
- `describe_export_destination` — the receipt string (folder + file, home shown as `~`).
- The four export write bodies, moved off their owners (all at/over their size ratchets): `export_library_note_file`, `export_library_prompt_file`, `export_library_report_file` (off the UI loop via `asyncio.to_thread`), `export_library_collections_recovery` (confirm runs on the `.json`-normalized path; the recovery service's own atomic, identity-guarded writer still publishes).

**Owners became thin delegators.** `LibraryScreen._write_library_note_export_file` / `_write_library_prompt_export_file` keep their `validate_path_simple` step and hand the write to the seam; the artifacts and collections controllers' write methods delegate too. All four `FileSave` launches now open at `library_export_picker_location(...)` instead of `str(Path.home())`. Imports are lazy so the seam stays off the Library preimport closure (pinned by `test_library_preimport_closure.py`). The note Cancel path reports its own status sentence (`failure_line`) rather than the generic "Export failed".

**Deviation (AC#4):** the receipt shows the folder + file with the home directory shortened to `~` (`~/exp/precious.md`), not the literal absolute string — a one-line status region clips a ~100-char path, and `~` is the form the picker itself uses. Outside home the path is absolute. The finding's intent (the toast named only the file, never the folder) is met.
