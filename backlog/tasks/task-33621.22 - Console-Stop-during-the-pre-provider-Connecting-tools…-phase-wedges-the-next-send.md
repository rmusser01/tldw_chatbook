## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the TASK-33625.1 final verifier (PR #2934) and reproduced identically on clean dev 857b3dd7d0 through the collapsed-strip Stop. Stopping a run after 'agent reply start' but before trace reservation ends the turn with status=failed exception_type=CancelledError phase=durable_commit, and 'runtime turn ended with exception_type=ValueError'. The next send is refused with a RuntimeError and parked as 'Queue 0/10 · Unsent turn needs attention'. PR #2934 makes Stop reachable from the composer, Ctrl+G, /stop and the palette, so users will reach this wedge much more often. Evidence: the U6-final captures 30-35 and app-base-235x52.log from the batch-1 run.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Stop pressed while the row reads "Connecting tools…" now ends the turn as Stopped, and the next send goes out.

**Reproduced first (live, dev ed7481a30c, Anthropic haiku through the review proxy, 235x52, fresh profile).** Ctrl+G 0.92 s after Enter, while the row read "Connecting tools… · <1s". The row said "Stopped", but the log had `phase=durable_commit status=failed exception_type=CancelledError`, `controller_submit status=failed` and "Console runtime turn ended with exception_type=ValueError". Enter twice and the Send button then sent nothing; each showed "Draft or chat changed; Send again." On this dev the wedge shows as that refusal, not the "Unsent turn" shelf the task describes. Evidence: tools/evidence/bd5/U03/01-05 and log-u03a.txt.

**Cause.** Between "console agent reply start" and the provider call, the agent reply composes its tools, waits for trace maintenance, moves the durable checkpoint from ACCEPTED to DISPATCH_STARTED and builds the profile tools. Only the bridge call after that window and the checkpoint move itself handled a Stop. A Stop anywhere else raised a bare CancelledError out of the reply. The stream wrapper then retired the run's cancel event, so the accepted-turn handler took the Stop for a failure. That was a ValueError if Stop had already marked the row stopped, or "Response recovery failed" for an ACCEPTED checkpoint. The turn's preparation never settled and kept the tab's send slot.

**Fix.**
- `Chat/console_pre_provider_stop.py` (new): `PreProviderSetupStop` wraps the setup window inside `_pre_provider_setup_phase`. It suppresses a CancelledError only for an explicit Stop, that is, when the run's own cancel event is set. `settle()` then settles an ACCEPTED checkpoint through `settle_accepted_durable_turn_owned(terminal_state="stopped")`, so no dispatch is invented. Any other row goes through `_mark_stream_stopped`. If the settlement cannot complete, it raises `ConsoleDispatchSettlementError`, and the accepted-turn handler keeps the turn for recovery. Its one log line is content-free and names only the checkpoint kind.
- `stop_active_run`: while the window is open, Stop leaves settlement to the window's owner. It records the deferred user-stop marker and cancels the reply, as it already did while the dispatch checkpoint move drains. A repaint's preparation read in flight at that moment no longer sends Stop down the "cancel the reads" branch.
- `ConsoleRuntime.cancel_received_intents` skips durably accepted custody. Without this, a repeated Stop after the reply had settled cancelled the finishing turn in its last await. That showed up live with Ctrl+G pressed every 30 ms.

**Test (AC3).** `Tests/UI/test_console_stop_connecting_tools.py` drives the real received-intent ChatScreen path (runtime, controller, store and a file-backed DB; only the provider call is a double). It has two cases: "composing tools" (checkpoint ACCEPTED) and "after the dispatch checkpoint" (DISPATCH_STARTED). In each, one setup step is held and the row reads "Connecting tools" with Stop shown. A repaint's read is held in flight when Ctrl+G is pressed. Ctrl+G is pressed three more times while the turn's last await is held. Then a follow-up is sent in the same tab. The test asserts:
- the turn task returned (it was not cancelled and did not raise);
- the assistant row is `stopped`, "Response stopped by user." is in the transcript, and the run state is STOPPED;
- no dispatch recovery, preparation or turn recovery is left, and the provider was never called;
- the next send reaches the provider and paints its reply;
- there is no "Unsent turn" shelf and no "Send again" toast;
- no failure line is logged and no send stage reports `failed`.

Both cases fail on dev ed7481a30c and on ff815f8559, the base after the rebase, because the turn task ended `cancelled`. Both pass on the head.

**Mutation (head, each part reverted alone, all red):**
- runtime durable-accepted skip: both cases, turn `cancelled`.
- `stop_active_run` defer: composing tools, row stays `pending`.
- read-diversion guard: both cases; Stop never reaches the reply, so the turn never gets to its tail.
- `__aexit__` suppression: `ConsoleDispatchSettlementError` in one case, row `failed` in the other.
- ACCEPTED settlement branch: composing tools, row `pending`.
- user-stop record: composing tools, no "Response stopped by user." row.

**Review fix: Retry (2026-10-29).** The independent review found that a Stop on a **Retry** of a failed reply, pressed during tool composition, still locked the tab, and the new owner reported it as a success. A Retry enters the setup window with its row still `failed`; the reply prepares it (`prepare_message_retry`) only after composition. `settle()` called `_mark_stream_stopped` as if a fresh reply were streaming, so `mark_message_stopped` refused the `failed` row and `_mark_stream_stopped` returned early: no STOPPED run state, the deferred user-stop marker never consumed, run state left at "Agent running.", and every later send refused with "A run is already running in this tab."
- `PreProviderSetupStop` now takes `prepares_row` (Retry or variant) and the reply sets `row_prepared` once `prepare_message_retry`/`begin_variant_stream` ran. `settle()` passes both to `_mark_stream_stopped` (`prepare_retry`/`retry_prepared`), exactly as the direct path does. A Retry stopped before its row was prepared leaves the row `failed`, so Retry is offered again, and still stops the run, records "Response stopped by user." and frees the tab.
- Test-first: `test_stop_while_a_retry_connects_tools_frees_the_tab` (UI, real ChatScreen/runtime/controller/store/file DB; the first send fails at the provider double, Retry is pressed on the failed row, composition or the profile-tools step is held, Ctrl+G, then a follow-up send). The `composing-tools` case was red on 199a1b3983 (run state STREAMING "Agent running.") and both cases are red on origin/dev ff815f8559 (the Retry never returns after Stop). Both pass on the fix. Mutations: `prepares_row=False` turns `composing-tools` red (STREAMING); dropping the `row_prepared` assignment turns `after-retry-prepared` red (row stays `pending`).
- Cheap review follow-ups applied: Stop publication (STOPPED run state, then the user-stop record) is one helper, `publish_stopped_run`, used by both `_mark_stream_stopped` and the ACCEPTED-checkpoint settlement, so they cannot drift; `_stops_settled_in_setup` is renamed `_replies_in_pre_provider_setup` (it holds every reply in the window); the setup-stop context is now the outer one, so a raising phase exit cannot strand its registration; `cancel_received_intents`' docstring no longer claims a Stop owner exists right after acceptance.
