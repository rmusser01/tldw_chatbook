## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the TASK-33628.6 (PR #2965) review. In a legacy flat conversation, a role='tool' (or empty) row with a NULL parent between flat rows is skipped by the store's _ingest_full_tree. It is never a node in the in-memory chain, so it is neither one of the ids the delete passes to the DB nor a parent-link descendant of one. After deleting a flat row above it, that hidden row stays live: invisible in the transcript, but it still appears in search and exports.
<!-- SECTION:DESCRIPTION:END -->

- [x] #2 Undo restores them

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Approach.** The store already sends the durable delete the saved ids of its whole in-memory subtree (TASK-33628.6); a hidden flat row is not in that subtree, so nothing named it. `console_legacy_flat_roots.delete_seeds` now builds that seed list. When the subtree holds a chained flat root (a saved node whose native parent is not its saved parent -- the flat repair hung it there), it reads the conversation's live parentless rows in the database's root order (`get_message_tree_rows_for_conversation`, the read resume uses) and appends every root after the first deleted root that resume never shows: a tool-role row (never a store node) or an empty row (no content, image, generation state or continuation; dropped at hydration), unmarked by `root_fork`. The DB delete then tombstones them and descends from them as from any seed, in the same transaction behind the same fence. Undo needs no change: it restores the committed tombstones (the held ids), so the hidden rows come back with the rest. The prompt and receipt count only what the transcript shows, as before.

Not taken: a DB-side rule ("every parentless row after X") would also take a marked fork or a row that arrived after load; the store-side rule touches only rows resume itself hides. Ordinary (threaded) deletes do no extra read: the trigger needs a chained root in the subtree.

**Evidence.** `test_flat_delete_tombstones_hidden_rows_later_in_the_chain` (real store, real `ChatPersistenceService`, in-memory `CharactersRAGDB`), five cases: tool row between flat rows, empty row between (seeded through `update_message`, since `add_message` now refuses one), hidden row after the last flat row, an earlier hidden row that must stay, and a marked first-message fork that must stay. Each checks the prompt/receipt count, the DB tombstones, the held ids, search and text export, reopen, then Undo and reopen. RED on origin/dev code: 4 failed (the hidden row stayed live: `[0, 1, 0, 1, 1] != [0, 1, 1, 1, 1]`), the stay-control passed; GREEN here. `test_console_message_delete_persistence.py`: 44 passed.

`console_chat_store.py` stays at 22,491 lines (the lazy import replaces the comment line); its ruff E402 count matches dev. User Guide: `Docs/User_Guide/console/chat-basics.md` (Delete section) says how Delete reads a conversation saved before branching, including hidden rows.

Files: `tldw_chatbook/Chat/console_legacy_flat_roots.py`, `tldw_chatbook/Chat/console_chat_store.py`, `Tests/Chat/test_console_message_delete_persistence.py`, `Docs/User_Guide/console/chat-basics.md`.

**Live verification (2026-10-03, branch fix/task-33628.7-delete-edge-cases @ 6bd551727c, isolated profile).** Two legacy flat conversations were seeded into the profile's ChaChaNotes DB: f0 user, f1 assistant, a tool row, f2 user, an empty assistant row, and f3 assistant, all parentless. In the real app, Library showed all 6 rows and Console showed the 4 chained flat rows. More > Delete on f1 asked "Delete this message and 2 later messages?" and the receipt said "Deleted 3 messages". The DB then had f1, the tool row, f2, the empty row and f3 tombstoned and f0 live, and a content search for the tool row's text returned nothing (before the delete it returned the row). After a relaunch, Library listed the conversation with 1 message. In the second conversation, Undo on the receipt restored all five rows, hidden ones included, and the transcript. Screen captures were kept locally (not committed), 01-12.

**Review follow-ups (checkpoint review).** The review found the gate claim above (threaded deletes do no extra read) untested: with the `_was_chained` gate removed, all 48 tests stayed green. `test_threaded_delete_reads_no_root_rows_and_leaves_a_hidden_root` now pins it: a parent-linked conversation with a parentless tool row, deleting the root and a tail message; `get_message_tree_rows_for_conversation` is never called and the tool row stays live. A sixth case of the hidden-rows test, `marked-hidden-root-stays`, pins `_never_shown`'s `root_fork` exclusion: a marked empty USER root between flat rows is not taken. Both pass on origin/dev by design (dev never reads or takes hidden rows); their teeth are Edit-based mutants, both restored: dropping the gate fails both threaded cases (`reads == []`), and dropping the exclusion fails the marked case (`[0, 1, 1, 1, 1] != [0, 1, 0, 1, 1]`).

**Final gate: gate narrowed.** `_was_chained` also fired for a saved row whose native parent is an unsaved interstitial note (an @-reference or skipped-skill note): that row is saved under its nearest saved ancestor, so its saved parent differs from the note's (missing) saved id. Deleting the first message of a parent-linked conversation over such a turn then read the conversation's root rows and took a parentless hidden tool row after the root, which a parent-linked conversation leaves alone. The gate now also requires the native parent to be saved, which every chained flat root's is (the previous flat root). `test_threaded_delete_over_an_unsaved_note_reads_no_root_rows` pins it: red before the change (`get_message_tree_rows_for_conversation` was called), green after; it passes on origin/dev by design (dev never reads root rows). `test_console_message_delete_persistence.py`: 54 passed.

**PR #3004 review: the root read is paged and parentless-only.** The hidden-row lookup read every live row of the conversation (`get_message_tree_rows_for_conversation`) and kept the parentless ones; a flat conversation continued after branching shipped holds parent-linked rows under its last flat row, none of which can be a hidden root. Reproduced before the fix: deleting f1 of five flat roots with six threaded rows under f3 read all 11 rows in one unpaged call. New `CharactersRAGDB.get_root_message_rows_page(conversation_id, after_message_id=, limit=)` returns one bounded page of live parentless rows of a live conversation, keyset-paged on `(timestamp, rowid)` after the previous page's last id (compared in SQL, so the stored timestamp never round-trips through the DATETIME converter), in the order resume reads roots (timestamp, ties in insertion order), with presence flags instead of the message text. `delete_seeds` iterates it in pages of `ROOT_ROWS_PAGE_SIZE` (500); `_never_shown` reads the flags. Plan, with `sqlite_stat1` absent: both statements `SEARCH m USING INDEX idx_msgs_conv_ts`, the later pages with `timestamp>?`, no TEMP B-TREE (census row flipped to plan-pinned). Measured (file DB, 4×5,000 other flat rows; median of 7 `delete_seeds` calls): 3,006 flat roots 18-26 ms → 11-12 ms; the same plus 6,000 threaded rows 56-68 ms → 14-15 ms. Tests: `Tests/DB/test_message_root_rows_page.py` (order parity with the tree read across page sizes 1-100 with tied timestamps, flags, deleted conversation/unknown cursor, limit validation, plan pin); the hidden-rows test now also runs with a page of one; `test_flat_delete_reads_root_rows_in_pages_not_every_row` pins no full read and the exact pages; the two threaded tests count both readers. Mutants (Edit-restored): ordering/keyset by `id` fails the order and plan tests; keyset on timestamp alone fails the tied-timestamp pages. Dropping the unary `+` does not change today's plan; it stays as a guard.
