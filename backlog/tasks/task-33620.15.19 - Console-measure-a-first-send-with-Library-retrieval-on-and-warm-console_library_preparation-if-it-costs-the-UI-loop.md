## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.5 (2026-10-22). Dev's extraction of Library preparation (146565efb7/a136e93257) left a function-local import in ConsoleChatController.prepare_library_for_turn (`from .console_library_preparation import prepare_library_for_turn`), reached on the automatic Library-retrieval send path. The module (181 lines) is not resident at UI-ready and is not in Chat/console_first_send_modules.FIRST_SEND_MODULES, so the first send with Library retrieval on imports it on the UI loop. Its own module-scope imports (Library.library_rag_service, UI.Views.RAGSearch.search_handoff, Chat.console_turn_preparation) are resident at UI-ready on dev e2cffbed60, so the cost is probably one small module, but neither the harness send nor the TASK-33620.15.5 live smoke exercised that path (no retrieval was configured), so it is unmeasured. Adding it to the warm-up raises the ADR-097 first-send warm-up row (MAX_FIRST_SEND_WARMUP_ADDED_MODULES, 94) by one, which needs a measured reason. (console_project_index_preparation is fine: it runs through asyncio.to_thread.)

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
**Result (historical report; see integration evidence qualification below).** A first send with Automatic Library retrieval loads two modules on the UI loop that the first-send warm-up does not cover: `Chat.console_library_preparation` and `Chat.console_library_search`. Together they cost 0.5-3.6 ms wall (0.5-0.9 ms CPU) per first Automatic send. They stay lazy. Warming them would raise ADR-097's `MAX_FIRST_SEND_WARMUP_ADDED_MODULES` from 94 to 95, and the owner declined that on 2026-10-31, verbatim: "Don't raise it" -- "Drop the warm-up and close the task with the measurement, since 0.5-3.6 ms isn't worth breaking the rule." The task ships the measurement, a test that pins it, three lessons entries and a follow-up. It changes no production code.

**Live record (AC#1; historical report, unverified; see integration evidence qualification below).** Real app, Anthropic claude-haiku-4-5 through the review proxy, 160x45, isolated profile with a null keyring. The profile was seeded once through the app: a Library note ("Lighthouse keeping notes"), a conversation whose Library Auto was saved as Automatic, the BM25 Only RAG profile, and the embedding model already downloaded. Each launch started from a fresh copy of that profile, reopened the conversation, and sent "Fresnel lens lighthouse keepers" 60 s after launch, once the warm-up had finished. A probe wrapped `_frozen_importlib._find_and_load` and recorded every first-time module load with its thread, wall time, CPU time and the loop callback it ran in. It also recorded the Enter key and the provider POST. The probe kit and per-launch import logs were kept in the working session's evidence folder, outside the repository; the original session reported the numbers below from them; the folder is not retrievable from this snapshot.
- origin/dev `7536ac3b87`, 5 launches (D1, R1-R4). Between Enter and the POST, the UI loop loaded exactly these two modules from the send's path, every time. They loaded inside the send's own run-start callback (5-30 ms wall, 5-9 ms CPU), where `ConsoleChatController.prepare_library_for_turn` and then `console_library_preparation.prepare_library_for_turn` import them:
  - `console_library_preparation`: 0.32-3.27 ms wall, 0.30-0.54 ms CPU.
  - `console_library_search`: 0.17-0.33 ms wall.
  - Nothing else on the retrieval path was lazy. The service's runtime build ran on a worker thread through `asyncio.to_thread`: 17-39 s at load 94-131, and 26 s at load 19.
- A warmed arm, 4 launches (R1-R4), interleaved with dev's R1-R4 and alternating which arm went first, had both modules in `FIRST_SEND_MODULES`. In all 4, the `tldw-screen-preimport` thread imported both 11.9-18.1 s before Enter, and the UI loop loaded no Library-path module in the window. That warm-up was not merged (see AC#2).
- Every launch reached the provider with Library evidence, shown as "Library: 2 sources sent" (the note plus the seeded conversation). Every HTTP status received was 200. On the warmed arm's R4 the quit came before the headers.
- Other modules loaded on the UI loop in the window, in both arms, were not from the send: `Workspaces.change_retention` (the app's retention callback), and `settings_quit_guard` with `console_voice_controls` (the driver's Ctrl+Q, which landed inside the window when the POST was late).
- A send paused for Library (Retry, Send once without Library, Stop) imports only from the same two modules (the `console_chat_controller.py` retry, bypass and CancelledError paths). It was not run live.

**Cost and decision (AC#2; historical report, unverified; see integration evidence qualification below).** On dev the two imports cost 0.5-3.6 ms wall (0.5-0.9 ms CPU), once per launch, on the first Automatic send. The branch first warmed both and re-pinned `MAX_FIRST_SEND_WARMUP_ADDED_MODULES` 94 → 95, with an ADR-097 ledger row and a refreshed `first_send_warmup.json`. The AC that asked for the re-pin had been filed by an agent reviewing TASK-33620.15.5, not by the owner, and the row's own 2026-10-20 owner decision said never to raise an existing limit. So the row was marked PENDING and the owner was asked. The answer, 2026-10-31: "Don't raise it" -- "Drop the warm-up and close the task with the measurement, since 0.5-3.6 ms isn't worth breaking the rule." The warm-up list, the payload-budget row and its comment, the snapshot, the ledger row and the `console_library_search` docstring are back to origin/dev exactly. The row stays at 94. (At `7536ac3b87` the same census measured 93 on dev, because `UI.Console_Modules.config_sync` had become resident at UI-ready; this task does not change the row.)
