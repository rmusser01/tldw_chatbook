## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in review of TASK-33620.15.5 (2026-10-22). Dev's extraction of Library preparation (146565efb7/a136e93257) left a function-local import in ConsoleChatController.prepare_library_for_turn (`from .console_library_preparation import prepare_library_for_turn`), reached on the automatic Library-retrieval send path. The module (181 lines) is not resident at UI-ready and is not in Chat/console_first_send_modules.FIRST_SEND_MODULES, so the first send with Library retrieval on imports it on the UI loop. Its own module-scope imports (Library.library_rag_service, UI.Views.RAGSearch.search_handoff, Chat.console_turn_preparation) are resident at UI-ready on dev e2cffbed60, so the cost is probably one small module, but neither the harness send nor the TASK-33620.15.5 live smoke exercised that path (no retrieval was configured), so it is unmeasured. Adding it to the warm-up raises the ADR-097 first-send warm-up row (MAX_FIRST_SEND_WARMUP_ADDED_MODULES, 94) by one, which needs a measured reason. (console_project_index_preparation is fine: it runs through asyncio.to_thread.)

## Implementation Notes

**Result.** A first send with Automatic Library retrieval loaded two modules on the UI loop that the first-send warm-up did not cover: `Chat.console_library_preparation` and `Chat.console_library_search`. Both are now in `FIRST_SEND_MODULES`, in send order (after `console_context_window`, before the compaction preflight). The warm-up imports them on its daemon thread after UI-ready. On the branch, the same send loads nothing on the UI loop for Library retrieval.

**Live record (AC#1).** Real app, Anthropic claude-haiku-4-5 through the review proxy, 160x45, isolated profile with a null keyring. The profile was seeded once through the app: a Library note ("Lighthouse keeping notes"), a conversation whose Library Auto was saved as Automatic, the BM25 Only RAG profile, and the embedding model already downloaded. Each launch started from a fresh copy of that profile, reopened the conversation, and sent "Fresnel lens lighthouse keepers" 60 s after launch, once the warm-up had finished. A probe wrapped `_frozen_importlib._find_and_load` and recorded every first-time module load with its thread, wall time, CPU time and the loop callback it ran in. It also recorded the Enter key and the provider POST. The probe kit and per-launch import logs were kept in the working session's evidence folder, outside the repository; the numbers below are read from them.
- origin/dev `7536ac3b87`, 5 launches (D1, R1-R4). Between Enter and the POST, the UI loop loaded exactly these two modules from the send's path, every time. They loaded inside the send's own run-start callback (5-30 ms wall, 5-9 ms CPU), where `ConsoleChatController.prepare_library_for_turn` and then `console_library_preparation.prepare_library_for_turn` import them:
  - `console_library_preparation`: 0.32-3.27 ms wall, 0.30-0.54 ms CPU.
  - `console_library_search`: 0.17-0.33 ms wall.
  - Nothing else on the retrieval path was lazy. The service's runtime build ran on a worker thread through `asyncio.to_thread`: 17-39 s at load 94-131, and 26 s at load 19.
- Branch, 4 launches (R1-R4), interleaved with dev's R1-R4 and alternating which arm went first. In all 4, the `tldw-screen-preimport` thread imported both modules 11.9-18.1 s before Enter, and the UI loop loaded no Library-path module in the window.
- Every launch reached the provider with Library evidence, shown as "Library: 2 sources sent" (the note plus the seeded conversation). Every HTTP status received was 200. On branch R4 the quit came before the headers.
- Other modules loaded on the UI loop in the window, in both arms, were not from the send: `Workspaces.change_retention` (the app's retention callback), and `settings_quit_guard` with `console_voice_controls` (the driver's Ctrl+Q, which landed inside the window when the POST was late).
