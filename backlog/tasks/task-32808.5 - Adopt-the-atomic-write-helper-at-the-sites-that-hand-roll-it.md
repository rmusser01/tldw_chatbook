## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Nine sites hand-roll a temporary-file-and-rename write beside a shared helper that has nine importers, and three of those skip the fsync entirely -- including one module that describes itself as durable. Two more write configuration and profile JSON with a bare truncate-then-write.

Source: core-runtime code review 2026-09-17 — `qa/core-code-review-2026-09-17/report.md`; per-slice evidence in `qa/core-code-review-2026-09-17/slices/`, reproductions in `qa/core-code-review-2026-09-17/phase4-verification.md`.


## Tier-2 scope correction (2026-09-21)

**This task is marked Done, and its premise is inverted.** Measured independently by four
review slices, `Utils/atomic_file_ops.py` is the **weakest** of three durability implementations in this
repo, not the canonical one:

- `Utils/atomic_file_ops.py:103,178` -- `f.flush(); os.fsync(f.fileno()); os.replace(...)`, with **no
  parent-directory fsync anywhere** and no Darwin `F_FULLFSYNC`.
- `Backup_Recovery/native_platform.py:12-22 flush_file` -- `os.fsync` **plus** `fcntl(F_FULLFSYNC)` on Darwin.
- `Notes/sync_paths.PinnedSyncRoot.replace_bytes` -- fsyncs the temp file **and** the parent directory.

`os.replace` + a file fsync is atomic but **not durable**: the rename itself can be lost on power failure
until the parent directory is fsynced, and on Darwin plain `os.fsync` does not force the drive cache.
So every remaining "adopt the shared helper" conversion is a **silent durability downgrade** at the sites
that are currently stronger.

Re-open as **"harden the helper, then adopt it"**, in that order -- see TASK-32896.

Measured by the tier-2 review against `origin/dev d0face3ebe`; evidence in `qa/tier2-code-review-2026-09-21/` (`report.md`, `validation/`). Tracked as TASK-32903.

## Implementation Notes (partial)

Landed on PR #2745 (`fix/core-review-helpers`):

- **RAG profile JSON** (report line 2187, the clearest data-loss risk) —
  `ConfigProfileManager._save_one` wrote each user profile with a bare
  `open(path, "w")` + `json.dump` (truncate-then-write, no atomicity). Routed
  through `Utils/atomic_file_ops.atomic_write_text` with byte-identical JSON
  (`json.dumps(..., indent=2, default=str)`), so a crash mid-write leaves the
  prior profile intact. Gate-free test
  (`test_save_one_writes_atomically_and_content_is_unchanged`) pins
  content-preservation + no temp-file leftover; the storage-admission scope
  stays covered by the (gate-blocked-locally, CI-run) save_profile suite.

**AC#2 (durability fsync) — DONE.** Audited every named site's fsync vs
os.replace: the one write that *claims* durability and skipped fsync was
`emergency_stop._write` (docstring "durably (atomic write)", temp-write +
os.replace, no fsync) -- fixed by routing through `atomic_write_text` (fsyncs
the temp inode before rename). `MCP/permission_store.py` and
`Tools/local_tool_impls.py` already fsync (2 each). The remaining 0-fsync sites
-- `Utils/tls_trust.py` (a trust cache its own docstring says is "regenerated
whenever a source changes"), `Agents/local_tool_provider.py` `_write_spill` (a
transient agent-overflow spill), and `Chat/trajectory_export.py` (a one-shot
user export) -- do NOT claim durability, so skipping fsync is acceptable per
AC#2. `RAG_Search/config_profiles._save_one` (a bare truncate-then-write, the
worst offender) was fixed in the prior commit.

Still open (AC#1 cosmetic adoption + AC#3): the 9 hand-rolled temp-file+rename
sites in the atomic-write census (`emergency_stop.py`, `Agents/local_tool_
provider.py`, `Chat/trajectory_export.py`, `Tools/local_tool_impls.py`,
`UI/Console_Modules/video.py`, `Utils/tls_trust.py`, Agents `_write_spill`,
`MCP/permission_store.py`), of which three skip fsync (AC#2) -- each needs a
per-site read of whether it claims durability and whether its `dir_fd` reason
is justified (AC#3), so they are a focused follow-up pass, not a blind swap.
