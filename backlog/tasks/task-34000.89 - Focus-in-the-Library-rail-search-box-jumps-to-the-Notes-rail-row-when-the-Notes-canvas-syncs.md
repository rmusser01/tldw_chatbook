## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: while the caret is in the Library rail's "Search Library…" box on the Notes route, any Notes canvas sync moves focus out of the box onto the Notes rail row. Background syncs (a filter landing, a tree page arriving, a notice refresh) can fire while the user types, and the next printable keys then stop reaching the box.

Evidence (TASK-34000.28 fix round 1 re-review, probe P3, a one-boot Pilot probe on `38cf61faae`): Escape from the Notes filter put the caret in `#library-search-input`. A plain `_sync_library_canvas(screen, "notes")` then gave `BEFORE-SYNC: library-search-input` → `AFTER-PLAIN-SYNC: library-row-browse-notes rail`. There was no Down and no hand-off in play. Base masked this in the Down-then-Escape flow by refocusing the filter box. Since polish-1a Task 5 the flow ends on the rail row.

Mechanism: `_capture_library_notes_focus_identity` (`library_screen.py`, about lines 5369–5414) captures the box as stage `rail` with an empty semantic role. The canvas sync's replay then resolves that identity to the stage's fallback target, the Notes rail row.

A one-line role does not fix it. Polish-1a Task 5 measured a portable `rail-search` role on the box (fix round 1), and it broke Escape from the box: the Pilot pin of Escape leaving the rail search box for a non-text canvas control went red. So it was reverted. The fix needs a design decision on how a rail text field survives a canvas sync without trapping Escape.

Same family (polish-1a final review, 2026-10-26): the Notes **Clear filter** button (`#library-notes-filter-clear`) has no portable semantic role in `LibraryScreen._library_notes_semantic_role`'s `direct_roles` either, so a canvas sync while it is focused replays the navigator fallback (the filter box) instead of keeping focus on it.
