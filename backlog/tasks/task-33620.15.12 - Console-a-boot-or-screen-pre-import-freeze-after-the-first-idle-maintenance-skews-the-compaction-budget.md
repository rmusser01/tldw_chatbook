## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The idle heap refreezer (TASK-33620.15.3) sizes the permanent generation after each of its own re-freezes and compares the growth with a budget set from its size after the last compaction (or its first look). The boot points (_ui_ready and the screen pre-import, ADR-198) also freeze the heap, but a freeze there after the refreezer's first maintenance neither marks its measured size stale nor moves the baseline, so for one cycle the budget reads an old size, and the pre-import's objects can count as growth and bring a compaction forward. The error is bounded and self-correcting, but the budget should count only what idle re-freezes add.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Summary: boot-point freezes (_ui_ready, the screen pre-import and the first-send pre-import) now go through the refreezer, so their objects move the compaction baseline instead of counting as growth. The next budget check also re-measures the frozen set.

Approach: `freeze_long_lived_heap` keeps its young collection and then calls `IdleHeapRefreezer.freeze_at_boot_point(_freeze)` on the process refreezer. After the refreezer's first look, that method walks the permanent generation before and after the freeze, adds the difference to `_baseline`, and sets `_stale`, so the next `compaction_due()` re-walks. Before the first look nothing extra runs, because the first look measures the boot objects itself. A per-instance `threading.RLock` is held by the boot freeze, `compaction_due`, `maintain` and `_look`, because the pre-imports freeze from their own threads. Without it, a maintenance running between the boot point's walks would read its objects as growth. The lock is reentrant because `maintain` calls `_look` and `compaction_due` while holding it. The compaction now freezes on its own path (`try/finally: _freeze()`) instead of through the boot helper. `_freeze()` centralises gc.freeze plus the freeze-epoch bump.

Cost: one extra permanent-generation walk per boot freeze after the first look, about 2 ms per 700K objects measured on 3.12.11. That applies to the whole-registry and first-send pre-imports, which run on their own threads and hold the GIL for the walk. A UI maintenance that meets the lock waits only for that walk.

Tests (Tests/Performance/test_gc_idle_refreeze.py, fake collector routed through the real freeze_long_lived_heap):
