## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-36946's criterion is that adding an engine preset touches only its registry record and its config template section. After TASK-36946.1 and .2, checked on dev `d85e90bc9e` on 2026-11-20, the newest preset (`commandcode`) still appears by hand in two more product files, and tests fail unless a new preset is added there too:

- `ContinuationProvider`, a `Literal` in `Provider_Contract/provider_continuation.py`. `Tests/test_provider_registry.py` pins it equal to the registry-derived `CONTINUATION_PROVIDER_KEYS`.
- `KEY_URLS` / `KEY_URL_UNCONFIRMED` in `Provider_Contract/provider_setup_facts.py`. `Tests/Chat/test_provider_setup_facts.py` requires every keyed provider in one of the two.

The default config template also names the preset twice: its model list under `[providers]`, and its `[api_settings.<key>]` section. AC #1 is read strictly: "its config template section" is the `[api_settings.<key>]` section, so the `[providers]` model list counts as a second place too, unless the owner rules otherwise. TASK-36946.2's notes do not include the demonstration the parent's criterion asks for.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

1. Probe: add a scratch preset (record + `[api_settings]` section only) on the base and run the registry, setup-facts, dispatch and provider-sweep tests, to list every hand-kept place a new preset still needs (beyond the three in the description).
2. `ContinuationProvider`: drop the hand `Literal`; the closed set is the registry-derived `CONTINUATION_PROVIDER_KEYS` that `_PAIRINGS` enforces.
3. Setup facts: `KEY_URL_UNCONFIRMED` = keyed providers without a sourced `KEY_URLS` row (registry-derived); per-account base-URL label/example move onto the record so `BASE_URL_FIELDS` derives too.
4. `[providers]` model lists of the engine presets: a `seed_models` record field, rendered into the template in place of one placeholder comment (values and key order unchanged; show the written-file diff).
5. Any other hand list or frozen test pin the probe finds (auto-refresh list, readiness/display-name pins): derive it, or retarget the pin to "base values unchanged, new presets come from the record".
6. Re-run the probe after the change (AC #2), then remove the scratch preset; update ADR-179, CLAUDE.md and the provider architecture doc.

**Changes**
- `ContinuationProvider = str`. The closed set is `CONTINUATION_PROVIDER_KEYS`, which `_PAIRINGS` enforces on parse and restore; a Literal can only repeat it by hand.
- `KEY_URL_UNCONFIRMED = PROVIDERS_REQUIRING_API_KEY_KEYS - KEY_URLS`. A new keyed preset gets the dashboard copy with no edit.
- New record field `seed_models`. The 8 seeded presets' lists moved onto their records, with their provenance comments. The template's engine block is one placeholder comment; `config.py` replaces it with `ENGINE_PRESET_MODEL_LISTS_TOML` (registry, record order, `custom-hosted` excluded).
- `AUTO_REFRESH_PROVIDER_LIST_KEYS`: the 7 bespoke providers stay hand-ordered (the Settings order is unchanged); the engine tail comes from `ENGINE_RECORDS` with `auto_refresh`.
- Test pins retargeted, none deleted: base values must stay; anything beyond the base must be an engine preset carrying its record's value. The `get_args(ContinuationProvider)` checks read `CONTINUATION_PROVIDER_KEYS`, with the old Literal frozen as a base subset.
- Docs: ADR-179 Consequences, CLAUDE.md "New LLM Provider" (it still named the `_LazyHostedChatHandler` / `PROVIDER_PARAM_MAP` lines TASK-36946.2 removed, and "13 sites in 9 files"), `Docs/Architecture/llm-providers.md`.
- Deviation from plan step 3: the per-account base-URL copy was not moved onto the record (see the rulings).

**Unchanged behaviour (probe, base vs branch, through the scratch-profile wrapper).** Parsed default config identical (whole tree and `[providers]` item order); `AUTO_REFRESH_PROVIDER_LIST_KEYS` tuple identical, order included; `KEY_URL_UNCONFIRMED`, `KEY_URLS`, `_PAIRINGS` and `CONTINUATION_PROVIDER_KEYS` identical; the old Literal equals the derived set (36 keys). A user's existing file loads the same: the shipped defaults it merges over parse identically.

**Written default config, diff for a new profile.** Comments only; every value is byte-identical in content:

**Rulings needed before AC #1 can be ticked**
1. Adding a preset's `[api_settings]` section changes the template bytes, so `_TEMPLATE_SHA256` (`Tests/test_config_load_settings_table_guard.py`, TASK-36945.1) must be re-pinned. That pin guards every template byte on purpose; it is not a provider list. The options are to accept the re-pin as part of the cost (ADR-179 and CLAUDE.md say so now) or to scope the hash so engine-preset sections are excluded, since `test_identity_fields_match_config_tables` already checks those sections against the records.
2. A per-account-host preset (`base_url_required`: Azure, Cloudflare and Databricks today) still needs its setup and readiness copy (`BASE_URL_FIELDS`, `Chat/provider_readiness.py::_BASE_URL_RECOVERY`) and a row in the `PROVIDERS_REQUIRING_BASE_URL_KEYS == {...}` pin. That is data the record does not carry: the field label, the example URL and the recovery copy. Moving it onto the record would close this case. ADR-179 lists it as an exception.

A sourced key page stays an optional `KEY_URLS` row: without one the setup form shows the dashboard copy and every test passes.
