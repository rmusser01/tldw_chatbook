## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`raw_participants._local` is a `threading.local` (tldw_chatbook/Backup_Recovery/raw_participants.py:47). A registered config or runtime-state raw operation that is held across an `await` on the Textual UI loop is therefore visible to every other asyncio task on that thread. `_runtime_operation` and `_scope` find it and `_check` compares it with `storage._task_identity()`; the other task has a different identity, so its guarded config IO raises `RecoveryRequired("raw_operation_provenance_invalid")`. TASK-33008.3 met this live: on a plain launch, the Get started card's local-server discovery ran on the UI loop and was refused on its only attempt, so "Use detected <server>" never appeared (lessons-live-verification.md, "A card with no detected server may mean discovery never ran"). TASK-33008.3 moved that one caller into its own thread and loop (`ChatScreen._discover_local_servers_for_setup_card`, `asyncio.to_thread(asyncio.run, ...)`). That avoids the refusal for discovery only; any other UI-loop coroutine doing guarded config IO in the same window is still refused, and a caller that catches the refusal, as discovery did, reads it as an empty result. Found in the TASK-33008.3 review (fix round 2).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**The premise was half right (AC#1).** A raw scope did leak to another task, but no scope is held across an `await`. A scratch launcher (scratch profile, 211x44, discovery put back on the UI loop) logged every raw scope still open when the loop next ran, and every `_check` made by a task other than the operation's owner. At base `a8812db42e` it logged no held scope, and one foreign check, 10.5 s into the first launch:

- **Scope:** route `config`, opened by `run_console_config_sync` (`tldw_chatbook/UI/Console_Modules/config_sync.py`) for `ChatScreen._sync_console_rail_and_controls`, in the `message pump ChatScreen()` task.
- **How another task got inside it:** the render under that scope reaches `_sync_console_setup_modal`, `_maybe_start_console_local_discovery` and `run_worker`. Textual's `App.run_async` installs `asyncio.eager_task_factory`, so the worker's first step runs inside `create_task`, inside the open scope, as a different `asyncio.current_task()`.
- **What was refused:** the worker's `recovery_review._Operation`, through `generation_witnesses._witnesses`, `bootstrap._control_records`, `private_paths._native_open` and `raw._runtime_operation`. The result was `ProviderReconnectRequired`, with `RecoveryRequired('raw_operation_provenance_invalid')` as its context.
- **Why mounted tests never saw it:** `App.run_test` installs no eager factory.

The detector was checked against a scope that really is held across an `await`, and it fires.

**The fix (AC#2).** `raw_participants._local` is now a `_TaskLocal`: its `operation` is kept per thread and per asyncio task, so every existing `raw._local.operation` reader and writer works unchanged. `_check` is untouched, and a task that presents another task's operation is still refused. A `ContextVar` was not used: `create_task` copies the creator's context, so the eager worker would still have read the owner's operation (measured).

**One refusal kept on purpose.** With the lookup per task, a second task could enter a source that another task of its thread is in the middle of, because the source locks are reentrant on a thread. `_scope` still refuses that with `raw_operation_provenance_invalid`, for every route except config. The existing pin `test_mcp_source_lifetimes.py::test_history_private_helpers_reject_other_paths_and_foreign_task` failed without that guard and passes with it, unedited.

- Ruling: config is the one source a second task may enter while another task holds it — AC#3 asks for exactly that, and at base a setting saved from such a task was dropped (`save_setting_to_cli_config` returned False) — if wrong, the guard loses its `route not in config_files.ROUTES` clause and AC#3 is unmet.
- Ruling: no guard for a config write made while another task of the same thread holds the config write lock; it waits on the file lock and never gets it — the same wait already happens at base when one task writes config inside its own write lock (measured), and all 18 `_config_write_lock` holders are in `config.py`, which has no `await` and starts no task (the builders and callbacks that callers pass in to run under the lock were not all audited) — if wrong, such a write freezes the UI where base refused it.

**The discovery thread hop can go.** With discovery on the UI loop the card offered "Use detected llama.cpp (127.0.0.1:9099)" on the first launch, and moving through Settings, Lab, Meetings, Research and Logs logged no refusal. Removing the hop is a `chat_screen.py` edit plus a rewrite of the thread assertion in `test_blocked_card_runs_discovery_once_and_offers_detected_server`; this task leaves both alone.

**Not changed.** `storage_admission._operation_local`, `chat_source_participants._LOCAL` and `dictionary_file_participants._local` are thread-locals of the same shape. The launcher saw no foreign check on the SQLite operation during boot or navigation.

**Tests added** (`Tests/Backup_Recovery/test_raw_operation_task_discovery.py`, both red before the fix with `RecoveryRequired: raw_operation_provenance_invalid`):
