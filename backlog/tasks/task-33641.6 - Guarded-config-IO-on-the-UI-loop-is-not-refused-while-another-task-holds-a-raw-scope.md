## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`raw_participants._local` is a `threading.local` (tldw_chatbook/Backup_Recovery/raw_participants.py:47). A registered config or runtime-state raw operation that is held across an `await` on the Textual UI loop is therefore visible to every other asyncio task on that thread. `_runtime_operation` and `_scope` find it and `_check` compares it with `storage._task_identity()`; the other task has a different identity, so its guarded config IO raises `RecoveryRequired("raw_operation_provenance_invalid")`. TASK-33008.3 met this live: on a plain launch, the Get started card's local-server discovery ran on the UI loop and was refused on its only attempt, so "Use detected <server>" never appeared (lessons-live-verification.md, "A card with no detected server may mean discovery never ran"). TASK-33008.3 moved that one caller into its own thread and loop (`ChatScreen._discover_local_servers_for_setup_card`, `asyncio.to_thread(asyncio.run, ...)`). That avoids the refusal for discovery only; any other UI-loop coroutine doing guarded config IO in the same window is still refused, and a caller that catches the refusal, as discovery did, reads it as an empty result. Found in the TASK-33008.3 review (fix round 2).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**The premise was half right (AC#1).** A raw scope did leak to another task, but no scope is held across an `await`. A scratch launcher (scratch profile, 211x44, discovery put back on the UI loop) logged every raw scope still open when the loop next ran, and every `_check` made by a task other than the operation's owner. At base `a8812db42e` it logged no held scope, and one foreign check, 10.5 s into the first launch:

- **Scope:** route `config`, opened by `run_console_config_sync` (`tldw_chatbook/UI/Console_Modules/config_sync.py`) for `ChatScreen._sync_console_rail_and_controls`, in the `message pump ChatScreen()` task.
- **How another task got inside it:** the render under that scope reaches `_sync_console_setup_modal`, `_maybe_start_console_local_discovery` and `run_worker`. Textual's `App.run_async` installs `asyncio.eager_task_factory`, so the worker's first step runs inside `create_task`, inside the open scope, as a different `asyncio.current_task()`.
- **What was refused:** the worker's `recovery_review._Operation`, through `generation_witnesses._witnesses`, `bootstrap._control_records`, `private_paths._native_open` and `raw._runtime_operation`. The result was `ProviderReconnectRequired`, with `RecoveryRequired('raw_operation_provenance_invalid')` as its context.
- **Why mounted tests never saw it:** `App.run_test` installs no eager factory.

The detector was checked against a scope that really is held across an `await`, and it fires.

**The fix (AC#2).** `raw_participants._local` is now a `_TaskLocal`: its `operation` is kept per thread and per asyncio task, so every existing `raw._local.operation` reader and writer works unchanged. `_check` is untouched, and a task that presents another task's operation is still refused. A `ContextVar` was not used: `create_task` copies the creator's context, so the eager worker would still have read the owner's operation (measured).

**Two refusals kept on purpose.** With the lookup per task, a second task could enter a source that another task of its thread is in the middle of, because the source locks are reentrant on a thread. `_scope` still refuses that with `raw_operation_provenance_invalid`, for every route except config:

- by source object, before any selector runs. The existing pin `test_mcp_source_lifetimes.py::test_history_private_helpers_reject_other_paths_and_foreign_task` failed without this guard and passes with it, unedited.
- by the path lock's own key, once that lock is taken (review, fix rounds 1 and 2). The lock is keyed by the resolved file, or for a settings source by its bound root, so every object under one key shares it; production has such a pair, `PromptHistory(default_prompt_history_path())` in `Chat/console_runtime.py` and `UI/Console_Modules/prompts.py`. Round 1 compared the selected path. That let in a second object that spelled the file another way (`/var/...` against `/private/var/...`, measured on macOS), and a second settings object on another file under the same root (two `EvalConfigLoader` objects, one saving and one exporting). `_State` now carries the lock's `source_key` and the guard compares it. The selected-path comparison stays, for the routes that take no path lock. No production pair that spells one file two ways was found, so this closed a hole in the guard, not a known live fault.

**A config write inside the write lock is refused, not waited for (review, fix round 1).** A second task may enter config, so a write from a task started under `_config_write_lock` reentered both thread RLocks and then slept on the OS file lock its own thread held, on the loop thread, for good. The lock is handed to code outside `config.py`: `locked_hooks_config_snapshot` yields it to `Agents/hook_permissions.py` and `Chat/console_runtime.py`, and the literal-settings transaction calls its callers' `mutation_builder`, `before_replace` and `after_replace`. `_config_write_lock` now records the thread inside each file's write transaction and raises `RecoveryRequired('raw_operation_provenance_invalid')` to that thread if it comes back, so `save_setting_to_cli_config` returns False at once, as it did at base. The same applies to one task that writes config inside its own write lock, which waited for good at base too.

The review suggested raising where the file lock reports `AlreadyLocked`. That was built first and measured: the refusal then comes from inside the writer's own config operation, whose failure path sets `_CONFIG_PERSISTENCE_ERROR = "config_operation_failed"`, and the config participant cannot drain until the next successful write. At base the write was refused before it opened an operation and nothing was recorded. The check therefore has to run before any operation opens. Round 1 put it on the first line of `_config_write_lock` and said here that nothing was recorded. That was wrong for two of the lock's 18 callers (review, fix round 2): `read_cli_config_snapshot` and `replace_cli_config_serialized` open an operation of their own and then take the lock. For those two the refusal was raised inside an entered operation and did set the flag; under a holder that does not write, `locked_hooks_config_snapshot`, nothing cleared it. The check is now a helper, `_refuse_config_write_lock_reentry`, which `_config_write_lock` calls first and those two call ahead of their own operation. `replace_cli_config_serialized` was `@guarded`, and the decorator opens the operation before the body runs, so it is now a plain entry over a guarded body, `_replace_cli_config_serialized_guarded` (the shape `get_runtime_config_snapshot` already has), and the decorator's name list carries the new name. An AST walk of `config.py` found no third caller that opens an operation and can reach the lock, and no module outside it opens a config operation around a config write. The test runs all three calls and pins, for each, that the refused task opened no operation and no failure was recorded.

**Neither of those two refusals can fire from the UI today (review, fix round 3).** Round 2 called the pair the Settings raw editor's read and save, here and in the lesson. Only the read is the editor's, and it cannot be refused. The callers at `afcb585a22`, by `git grep`:

- `read_cli_config_snapshot` has one production caller, `SettingsConfigAdapter.read_snapshot`. The raw editor calls that twice (`AdvancedConfigSettings.inspect_current` and `replace_draft`, in `UI/Screens/settings_advanced_config.py`), both through `asyncio.to_thread`. It runs on a worker thread, which is not inside the write transaction.
- `replace_cli_config_serialized` has one production caller, `SettingsConfigAdapter.replace_serialized`, and nothing calls that method, tests included.
- The raw editor saves through `SettingsConfigAdapter.replace_snapshot` and `replace_cli_config_snapshot`, also on a worker thread. That function opens no operation ahead of the lock, so the check on the lock's first line was already early enough for it. Round 2 did not change it.

The round 2 change to the two entry points is therefore correct and defensive: tests can reach the refusal, and no production caller can.

- Ruling: config is the one source a second task may enter while another task holds it — AC#3 asks for exactly that, and at base a setting saved from such a task was dropped (`save_setting_to_cli_config` returned False; a test now pins that it lands) — if wrong, the guard loses its `route not in config_files.ROUTES` clause and AC#3 is unmet.

**The discovery thread hop can go.** With discovery on the UI loop the card offered "Use detected llama.cpp (127.0.0.1:9099)" on the first launch, and moving through Settings, Lab, Meetings, Research and Logs logged no refusal. Removing the hop is a `chat_screen.py` edit plus a rewrite of the thread assertion in `test_blocked_card_runs_discovery_once_and_offers_detected_server`; this task leaves both alone.

**Not changed.** `storage_admission._operation_local`, `chat_source_participants._LOCAL` and `dictionary_file_participants._local` are thread-locals of the same shape. The launcher saw no foreign check on the SQLite operation during boot or navigation.
