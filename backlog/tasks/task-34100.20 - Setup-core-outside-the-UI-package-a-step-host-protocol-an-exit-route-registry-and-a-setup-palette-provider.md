## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The approved setup shape hosts the same steps in four places: the first-run corridor, the "Review your setup" dashboard, single-step sheets (including over Console), and plain-text setup in a terminal. Today none of that is possible. Steps call the wizard container and app_instance directly, Provider and Model keep their logic inside Textual classes, and importing the setup state module loads Textual (about 0.29 s), which plain-text setup cannot afford. Exit routes are admitted inside app.py, which has 28 lines of headroom and silently drops routes it does not know. app_command_providers.py is at its size budget, so setup palette commands have nowhere to go.

This slice builds those seams without changing anything the user sees (spec §4.7 items 1–4). TASK-34100.1 moves the step classes into their own modules but defines no host, so this follows it directly.

Spec: Docs/superpowers/specs/2026-10-03-first-run-setup-shape-design.md (revision 3, approved by the owner on 2026-10-03; ADR-217): §4.1 (INV-1), §4.2 (entry predicate), §4.7 items 1–4, §8.1 (import purity, exit routes), §10 F0.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A tldw_chatbook/Setup/ package holds the track definitions, a pure SetupSession reducer (events in, state out, including cross-step state such as the provider outcomes Model reads), pure Provider and Model step states (key-check results, detection results, mutation building), the commit builders and has_usable_chat_provider. UI/Wizards/first_run_setup_state.py remains importable as a re-export shim
- [ ] #2 Importing the setup core in a fresh subprocess does not load textual, checked through sys.modules
- [ ] #3 Steps reach the outside world only through a SetupStepHost protocol: commit, the session, a narrow services object with no app_instance, capabilities (allows_secret_entry, resume_copy, nav_kind) and finish. The corridor implements it, and an architecture test fails on any step that calls the wizard container or app_instance directly
- [ ] #4 has_usable_chat_provider is true only for a provider with a credential that resolves through the runtime's own resolver and is not a placeholder, or a keyless provider with an endpoint that is not a template value. Over generated configs, template values (for example the shipped OpenAI section with no key) never count
- [ ] #5 A Hypothesis state machine over SetupSession asserts the stable-total invariant: after the run leaves Welcome, the step list never changes until the user returns to Welcome, across typed and cleared keys, an environment key, provider switches, Back and resume from a draft
- [ ] #6 Exit-route admission lives in its own module with a typed route table shared with the setup registry. Every route in the table is admitted by a test, and an unknown route is refused with a diagnostic instead of being dropped
- [ ] #7 Setup palette commands have their own command-provider module, and app_command_providers.py gains no lines
- [ ] #8 Quick and Full setup behave exactly as before: the existing wizard tests pass with only import-path changes, and app.py and FirstRunSetupWizard.py do not grow
- [ ] #9 Verified live on a fresh isolated profile (TLDW_CONFIG_PATH and HOME set) through the real app, with real providers and the real llama.cpp server, never mock servers: Quick with a real OpenAI key and with the real llama.cpp server, and Full with a real Anthropic key, each behaving exactly as on the pre-change build. Evidence is recorded in Implementation Notes
- [ ] #10 New behaviour is covered by tests that fail on the pre-change code (RED verified), and no module-size or ADR-097 ratchet is raised
- [ ] #11 The matching Docs/User_Guide page content is updated where behaviour changed (no 'Verified against' stamps)
