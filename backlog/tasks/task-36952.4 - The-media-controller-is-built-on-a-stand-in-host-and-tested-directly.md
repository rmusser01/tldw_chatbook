## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-36952's first criterion is that the media subsystem's controller is constructed without the screen and tested directly. After TASK-41757, `LibraryMediaController` reaches its host only through the typed `LibraryMediaHost` protocol: four shell-service protocols plus the Textual services it reads off the host. Production still passes `LibraryScreen`, which the owner accepted on 2026-11-22. But no test builds the controller on anything else, so nothing shows that the protocol is the whole contract. Every media test goes through a mounted `LibraryScreen`.

Owner ruling, 2026-11-23, on how TASK-36952 closes: "Add a direct test, then close". A test builds the media controller on a stand-in host (not `LibraryScreen`) and exercises it directly. Production still passes the screen. TASK-36952 closes when this task lands.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A test builds `LibraryMediaController` on a stand-in host that is not `LibraryScreen` or a subclass of it, and the test module does not import `LibraryScreen`
- [ ] #2 The stand-in host provides every member `LibraryMediaHost` declares, checked by a test, so that a member added to the protocol later fails that check until the stand-in gains it
- [ ] #3 Through the controller, the test exercises at least one member of each of the four shell-service protocols (shell, review set, reader-layout sync, workspace depth), and asserts both what the stand-in received and the controller's resulting state or return value
- [ ] #4 Each new assertion is shown red by a temporary change to the controller or the stand-in, and the change is reverted
- [ ] #5 The notes quote the owner's ruling and state that production still constructs the controller with `LibraryScreen`
