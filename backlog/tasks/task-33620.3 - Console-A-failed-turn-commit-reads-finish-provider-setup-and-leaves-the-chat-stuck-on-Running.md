## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Impact.** A send in a conversation with no `console_conversation_library_policy` sidecar row failed inside durable commit. The log shows 'Durable turn commit failed; turn refused (exception_type=RuntimeError)', phase=durable_commit status=failed, raised from `chat_persistence_service.py:1507-1525` when the policy row is None. The UI then stayed like this for more than 3 minutes:
- the user message with no assistant row;
- header 'Running';
- composer 'Send blocked — finish provider setup to continue ›' next to 'Preparing...';
- queue shelf 'Unsent turn needs attention';
- the quit dialog counting the chat as 'Live agent runs: 1'.

The provider was configured correctly throughout. So users are sent to fix a provider setup that isn't broken, and the chat looks stuck running forever. Any legacy or imported conversation without the sidecar row would take the same path.

**Severity / prior art.** P1; the reviewer rated it P2. NEW, with no prior art. It was found by a single reviewer and was **not** run through the live, code and skeptic verifiers; re-confirm the repro before implementing. It is another case of a failure travelling in the setup-blocked slot (Theme 0; the umbrella task owns typed blocker codes). The turn-lifetime owner is ADR-094.

**Suggested direction.** Map durable_commit failures to their own display state ('Turn not saved — nothing was sent', with Retry and Copy draft). End the Running and Preparing state for the owning session. Backfill or lazily repair a missing sidecar policy row on open, instead of refusing the turn.

Evidence: qa/console-ux-review-2026-09-29/findings.md → GAP2-16. Files: evidence/evidence__GAP2__56-nearfull-commitfail-2min.txt, evidence/evidence__GAP2__55-nearfull-send-later.txt, evidence/evidence__GAP2__seed_output.txt.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Two fixes, one per commit. (1) TASK-33621.53's pause delivers AC#1-#3 for a commit failure. (2) The durable commit repairs a missing Library-policy row (AC#4).

Re-confirmed first (the finding was never verifier-confirmed). Live on dev f9baac8706 (evidence U01/r2): a saved chat whose console_conversation_library_policy row is missing (the legacy/imported shape) refused every send at the durable commit ('Durable Console Library policy no longer matches acceptance.'). Send, Retry send, Discard and send again all read 'Send could not be saved; your message was not sent'. The 'finish provider setup' and 'Running' parts were already gone on dev for this post-reservation failure (TASK-33620.4 / TASK-33621.2 / TASK-33621.20 work): the header read 'Blocked', the chip 'Run: Blocked — send not saved', and the shelf offered Restore/Discard. A failure before the store's reservation still jammed the chat in COMMITTING (TASK-33621.53).

Repair (chat_persistence_service.commit_durable_turn, existing-conversation branch): when the row is missing and both the frozen authority (source 'missing') and the session's candidate are the safe Never/Blocked default, insert that row in the same BEGIN IMMEDIATE transaction (console_library_policy.repairs_missing_policy). Any other mismatch still refuses, so nothing broader than what the turn ran under is saved. The session's policy then reads back as durable revision 1 and later sends validate against it. A lazy repair on open was not needed: the commit is the first write. The module-size row for chat_persistence_service.py rose 4263 -> 4272 (owner rule: a fix over a size ratchet raises the row; folding the existing mismatch check elsewhere would only have moved unrelated lines).

AC#2 as verified: after a commit failure the header reads 'Blocked' (never 'Running'), 'Preparing...' clears, the composer is never setup-blocked and offers no setup-wizard link, controller.lifecycle_impact().live_run_count is 0, and Ctrl+Q quits at once with no live-run dialog (live). Send is usable as soon as the failed send is ended by any of Retry send, Cancel send, Restore or Discard. While the card is still up, a new send is refused by the established one-paused-send rule, and its toast reads 'Draft or chat changed; Send again.' That toast is misleading and pre-existing for every pause kind, so it is filed as TASK-33621.56 rather than fixed here.

Tests: Tests/UI/test_console_durable_commit_failure_recovery.py adds an imported chat that sends twice and gets its (0, 0, 1) row (red on dev), and a negative control where a staged Automatic candidate still refuses and writes no row (red with the candidate check removed). The commit-failure copy/state/actions cases are listed under TASK-33621.53. Census +1 node (1143 -> 1144).

Live on the fix branch (real Anthropic haiku via the review proxy, isolated profile, null keyring; evidence U01/r3-fix, 2026-10-29): the policy row was deleted from a saved chat, the app restarted and the chat reopened. beta and gamma were sent and answered, the row was repaired to (0, 0, 1), and durable_commit succeeded both times. Real commit failures (profile DB write lock held past the 15 s busy timeout) showed the not-saved card, Blocked header/chip and shelf. Retry send, Discard + new send, and Restore + Enter each led to exactly one saved, answered turn.

Not covered here: Temporary-chat Save & Send also failed live on dev with 'Send could not be saved' (U01/r2/12; post-reservation, store-paused). TASK-33621.17's owner decision (2026-10-27: Temporary tabs default to capture off) reworks that flow, so it is left to that task.
