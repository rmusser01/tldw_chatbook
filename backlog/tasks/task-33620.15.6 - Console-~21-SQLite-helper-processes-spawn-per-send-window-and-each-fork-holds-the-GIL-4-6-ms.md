## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Live profiling of Console sends (2026-10-10, Anthropic haiku via the review proxy, 160x45, 5 sends with call chains) found about 21 private-SQLite helper processes started between send acceptance and the provider call (median window 1.5 s). Every fresh private connection starts one (ADR-125: file and sidecar validation runs in a python -I -S helper so the app never opens and closes descriptors on a live database). Each fork_exec holds the GIL 4-6 ms (max 24): about 116 ms per send window, from asyncio executor threads and the agent loop thread, which stalls the UI loop (a stdlib micro-test on this Python 3.12/macOS: main-thread wake overshoot median 8.5 ms during a fork against 0.27 ms otherwise), and each spawn starts a Python interpreter. The biggest source is the Console Character browser's scope check: 7.8 spawns per send from get_local_authority_id under _read_database_scope_metadata, plus 0.8 from its projection load. Each sync pass's check makes two finite owned reads (two fresh handles, two helpers), and when a message insert bumps the search revision the follow-up refresh makes five more (capture, load, fence capture): up to seven helper starts for one check, about 70-100 ms of helper round trip each. The helper and the no-idle-worker-handle backup rule (TASK-32628) are not in question; the fix is to open fewer handles per operation. The general close-per-call lifecycle stays with TASK-33268 (PERF-09).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Summary.** A sync-driven Console Character display check (the active-run check about once a second, and the idle display check) now decides and reloads in one finite callback. It opens one worker handle, so it starts one ADR-125 helper process, whether its scope changed or not. On dev a changed check started two: the scope probe, then the reload batch, which reads the same scope again. An unchanged check makes no more UI-loop handoffs than the original probe; qualifying the stock readers on the loop adds about 0.5 ms of loop CPU per check (see the cost probe below).

**Why the helper stays.** ADR-125 validates every fresh file-backed private connection in a `python -I -S` helper, so that closing a validation descriptor never cancels a live connection's POSIX locks. It also rules out any listener, daemon or long-lived RPC. ADR-126 and TASK-32628 require finite Console work to leave no idle worker handle. So "reuse a long-lived helper or connection" is not available here. ADR-126 also rules out a metadata cache for this check. Caching the local authority id would not help anyway: it would save one query on a handle the check opens regardless, not a spawn. The fix opens fewer handles per check. General per-thread handle reuse belongs to TASK-33268 (PERF-09).

**Re-baseline.** The task was filed on 2026-10-10 at 21 helpers per send window, 8.6 of them Character. The interrupted WIP (`OwnedDBSession`, an operation-scoped thread held across awaits) was dropped: it conflicts with ADR-126's Character custody rulings, and dev had rewritten the code it patched. A re-measure of dev on 2026-10-19 gave about 15.5 helpers per window with a Character share of 2.7, after TASK-33620.15.1 and the finite Character batch. The ACs were restated against that measurement.

**Approach (`UI/Console_Modules/character_context.py`).**
- `_check_recent_batch(presentation, settled)` builds the stock readers with the displayed fingerprint (`unchanged_from`). It then runs the existing inner batch once inside `_await_database_work`, which supplies preparation-read custody: per-use storage admission, the quiescence fence, `operation_owned_connection` plus `_core_operation`, and retirement on the worker thread. `_read_recent_scope_sync` ends after the first fresh pair when that pair still matches `settled`. Otherwise it loads the groups and fence-reads the final pair, as before. Nothing publishes until the callback has retired. A reload then advances the generation, as `_begin` would, and publishes once, with no intermediate "Refreshing…" state.
- Outcomes mirror the two-callback route:
  - An owner that moved on, or a qualified body that changed during the read, gets no publication.
  - A scope that moved during the load goes to the original `refresh`.
  - Every outcome that neither finds the scope unchanged nor publishes a reload drops the last-successful-refresh marker, as the original route's `refresh()` did on entry. Without this (found in review), an active-run check whose owner or reader changed during its read and then changed back left the idle two-second memo armed, and the next idle display kept the old list until the next sync event. A published reload sets the marker under the same reader/generation guard `refresh()` uses.
  - For a current owner, the original probe-then-refresh route takes over in three cases: a first read that did not settle or failed; an unchanged read whose ambient scope or displayed fingerprint changed by its retirement; a refresh dispatch customized during the read.
- Unchanged cost (second commit). A settled pair returns before the batch's post-pair owner handoff, and the pre-read owner check is dropped. The readers are built synchronously from the same accessors just before, so that check could only fail for an owner key computed in the same synchronous stretch. The ambient scope is then confirmed on the loop after retirement, as `_capture_scope` does.
- The new route is wired into the run-active check (`refresh_if_scope_changed` with the display-owner closure) and the idle display (`refresh_presentation_if_scope_changed`). Forced, direct and custom routes are unchanged. Docs: Architecture `console.md`; an ADR-126 amendment note; User Guide `console/sessions-tabs-workspaces.md`. Visible change: a background check that finds changed chats usually updates the list in place, without first showing "Refreshing local character chats…". **Retry** reloads directly and shows "Refreshing local character chats…" while it works, or "Searching local character chats…" when a Context search query is active (it then runs `search()`). The User Guide makes no claim about switching open chats: during a run that still takes the original refresh (the known-changed route), while an idle check now updates in place, and a remounted rail widget takes the original route. Tests cover this through state assertions, and the review-fix live check below observed it.
