## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
On a Windows host without the legacy Windows Media Player, audio playback hands the clip's path to cmd.exe. Python quotes an argument for cmd.exe only when it contains a space, so a space-free file name containing `&` reaches cmd.exe as a command separator. The Artifacts screen plays a `briefings` audio path taken from the database, checked only for existence and a few patterns, so a tampered or corrupted row is a command injection. This exists on dev today (found by the TASK-38227 audit, which this blocks); this PR fixes it. Owner decision 2026-11-05, "Fix sink, startfile (Rec.)": play through `os.startfile` with no cmd.exe, and confine the Artifacts row to the briefing audio folder like the Library and Watchlists players. Accepted cost: pause and stop cannot reach a clip handed to the default app.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 On Windows without the legacy player, a clip opens through `os.startfile` with its path unchanged; no audio playback code builds a cmd.exe command, a path containing `&`, `|` or `^` never reaches a shell, and a file that is not a local audio file (by its name or its link target) is refused
- [x] #2 Artifacts-screen playback plays only the resolved path inside the briefing audio folder and refuses one that resolves outside it, symlinks included, with a literal toast that never shows the path
- [x] #3 When the `os.startfile` fallback is used, the app says playback moved to the default audio app and never reports a pause or stop it did not perform
- [x] #4 After a hand-off, Stop on the Console and in the Speech playground neither reports the clip stopped nor deletes its file before a bounded retention; the Speech playground stops polling for an end it cannot see and says where the clip plays; and the hand-off toast is raised on the app's thread from any caller thread

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Both defects existed on dev `29592ecc9b`; this PR fixes them.

**Sink.** `SimpleAudioPlayer.play()`'s Windows branch now calls the new `TTS/windows_audio_launch.py`, imported inside that branch only (never resident on macOS or Linux; it also keeps the pre-import census at 426,508 of 426,512 LOC, down from dev's 426,512). With wmplayer.exe present the list argv is unchanged. Without it, `hand_off()` calls `os.startfile(path)` (ShellExecute, no command line is parsed) after `hand_off_refusal` passes both the given and the resolved (`resolve(strict=True)`) path. ShellExecute runs whatever an extension is registered to run, so both names must carry an audio suffix of the player's set, case-insensitively, and a `:` after the drive (an alternate data stream) or a UNC/device root is refused. On dev, `payload.bat` would have run through `cmd /c start` too.

**Artifacts.** On dev the Play handler trusted the cached row and played `validate_path_simple`'s unresolved path, which the player opens against the working directory. It now plays only the resolved result of `validate_path(raw, briefing_audio_dir(), redact_paths=True)`, as the Library player does: a relative row means the audio folder, links are followed, the absolute result can never be read as a player option, and nothing logs the row's path. A path outside the folder, or an in-folder link that resolves outside it, is refused with a literal `markup=False` warning toast that names no path. Note: on dev the Artifacts screen is not routed in the live app (ADR-172 aliases `artifacts` to Library), so this sink was reachable there only through code that mounts the screen directly; the cmd.exe sink itself was reachable from every live playback path.

**Ruling (stop/pause truthfulness on the fallback).** Smallest truthful option: say so, once per hand-off, and never claim control the app lacks.
- The player records a handed-off clip as current and PLAYING with `handed_off=True` and no process. It cannot see the clip end, and keeping it current means no surface frees the file while the default app is opening it (the Console deletes its cached clip, and the Speech playground deletes its PCM copy, as soon as playback ends).
- `pause()` and `resume()` return False (Windows has no pause branch; `_supports_pause=True` keeps pause off the stop-and-restart path, which would report a pause). `stop()` releases the slot but returns False, so the Speech playground no longer says "Playback stopped" (on dev it did: stopping the cmd.exe wrapper left the default app playing).
- `hand_off()` shows the literal toast "Playing in your default audio app. Pause or stop it there." (`markup=False`) in the running app, found through Textual's `active_app` context variable (private API, as `console_session_surface.py` already uses; with no active app it logs instead). `AsyncAudioPlayer.play` now runs the call in a copy of the caller's context so the toast also crosses its executor thread.
- Chosen over reporting FINISHED or IDLE at once: those would let the Console delete the clip before the default app opened it, the Speech playground would say "Playback complete", and IDLE would make the Console report "Failed".
- Residual, accepted with the cost: the in-app transport cannot tell when the default app finishes, so the Console header keeps "Playing" until the next clip, a stop, or its 300 s bound, and hands-free waits its text-length bound. Not verified on a Windows host.

**Other changes.** `stop()` resets state with `AudioPlayerInfo()` instead of eight field assignments (same defaults, and the new flag cannot outlive a stop). The Windows `_find_player` comment no longer claims COM pause support. User Guide: one Troubleshooting entry in `console/voice-and-hands-free.md`. Diagnostic inventory re-pinned after reading `--statements`: three new log lines in `windows_audio_launch.py` name no path or user text; `audio_player.py` has no changed statement (its two legacy debug rows gained a `self._current.state` path expression because `play()` now builds `_current` from `file_path`).

**Tests.** `Tests/TTS/test_audio_player.py` (+18 cases: startfile path unchanged and no cmd.exe argv; `&`, `|`, `^`, `%VAR%` names untouched; non-audio refused; wmplayer argv unchanged; the Ruling at the player; the toast from the loop thread, `asyncio.to_thread` and `AsyncAudioPlayer` in a real Textual app; the Speech playground's copy; a static guard that no TTS, Audio or Media_Playback list literal names cmd.exe) and `Tests/UI/test_artifacts_screen_reports.py` (+2: outside row refused, escaping symlink refused; the in-folder case was already pinned). Seventeen of the new cases and both Artifacts cases fail on dev; all pass here. Twelve named mutations each turn at least one new case red; restores were assert-once swaps from a backup, verified with `cmp`.

**Fix round 1 (security review, 2026-11-05).** The first commit checked the Artifacts row with `audio_file_path_is_safe` (relative rows resolved against the folder) but still played the unresolved path, so a relative row could play a file from the working directory or pass a `-`-leading name to the player as an option; it now plays the resolved path (above). `hand_off` checked only the given name's suffix, so a link `clip.mp3 -> payload.exe`, a stream `x.bat:evil.mp3` and a UNC path passed; it now resolves first and checks both names (above), and its refusal log is a fixed sentence. Tests added: 11 `PureWindowsPath` predicate cases (each refusal pins its rule; `X.MP3` and `x.Mp3` accepted), a real link escape through `play()`, an upper-case suffix, a failed `os.startfile` that neither toasts nor records PLAYING, and four Artifacts cases (a relative row plays from the folder; a working-directory-only row is not played; a `-clip.wav` row reaches the real afplay argv as an absolute path; the refusal logs no path). Twenty-two mutations, including the two that survived the first round, each turn at least one case red. Same-pattern gap left for a follow-up: the Watchlists player (`watchlists_collections_screen.py` `handle_play_audio_requested`) also plays the unresolved row path on dev. A clip whose resolved path is a network share (a mapped network drive resolves to one) is no longer handed off.

**Fix round 2 (Qodo, 2026-11-06).** Three findings, all new with this PR's hand-off path (none exists on dev, which has no hand-off); this round fixes them. (1) **Toast off the UI thread.** `_tell_running_app` called `App.notify` from whatever thread reached `play()` (`asyncio.to_thread` in the Console, the `AsyncAudioPlayer` executor in the Speech playground). `notify` only posts a message and is documented thread-safe, but the crossing is now explicit: on the app's own thread it is a direct `notify`; from any other thread it goes through `App.call_from_thread(app.notify, ..., markup=False)`. The thread test is the one `call_from_thread` uses to refuse its own thread in Textual 8.2.8 (`textual/app.py`: `App._thread_id`, set by `_thread_init`/`run_async` from `threading.get_ident()`), private API like `active_app`. An app that is not running (`call_from_thread` raises `RuntimeError`) gets a log line instead. (2) **Stop deleted a playing clip.** `stop_audio_playback_if_current` returned True whenever the file matched, discarding `stop()`'s False, so the Console accepted the Stop, reported "stopped" and deleted the clip; the Speech playground released (securely deleted) its WAV copy regardless. Now the player records a hand-off as its own state, `PlaybackState.HANDED_OFF` (replacing the `handed_off` flag on a PLAYING clip, so callers can tell it apart); the Console helper refuses a handed-off clip before touching the player and otherwise returns `stop()`'s own result; and both surfaces separate releasing the in-app slot from deleting the file. **Ruling:** a handed-off file is kept for `HAND_OFF_RETENTION_SECONDS` = 300 s from the hand-off (one constant in `audio_player.py`, equal to the Console's poll bound), then deleted; the handler's shutdown and the pane's unmount, the existing cleanup points, delete or release it at once. In the Console the owned runner records the hand-off time on the worker thread and passes the remaining bound to `_cleanup_audio_file`, which reschedules itself once instead of deleting (so a displacing next clip or a cancel cannot delete early either); the legacy stop branch and 5 s cache timer consult the live player. In the Speech playground the release moves into a timer held in `_hand_off_releases`, and `_retire_hand_off_retention` (called from `on_unmount`) cancels the timers and runs the releases itself, because a timer cancelled before its first step never runs its body. (3) **Speech polled forever.** `_update_progress_timer` now ends on HANDED_OFF: it hides the bar and the transport the app cannot drive, shows the hand-off notice as the status, and retains the copy as above. Pause on a handed-off clip answers with the same notice (it performed none). The poll bound treats HANDED_OFF like PLAYING (assumed played through), not as a failure. Tests: `Tests/TTS/test_audio_player.py` (thread routing on the fake and a real app, a stopped app, the Ruling with the new state, Speech Stop/polling/exit retention), `Tests/TTS_Events/test_file_playback_failures.py` (poll bound, owned Stop refused + retained + deleted after the bound, shutdown deletes, legacy Stop, displacement), `Tests/UI/test_speech_playground_pane_lifecycle.py` (real pane: polling ends, status, unmount releases the lease). Seventeen named mutations, each killed. The stop helper's player shape is now `get_current_file`, `get_state`, `stop` (and the owned runner reads `get_state` right after `play()`), so five existing consumer fakes that modelled only the old two methods gained `get_state` (`test_spoken_feedback_streaming.py`, `test_utterance_speech_entry.py`, `test_console_speech_presentation.py`, `test_watchlists_artifacts_pane.py`); the paired gate found them. Ratchets re-pinned per the owner's rules: `tts_events.py` 4968 -> 5061 and the pre-import LOC pin 426,512 -> 426,620 (ADR-097 row). Also new on this branch: the Console cannot pause a handed-off clip either, and a Stop pressed in the window before `os.startfile` returns still reports "stopped" (the file is retained regardless).
