## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
If the user opens help or files a note right after typing, autosave silently stops. A first-timer presses F1 to look up a key, closes it, and keeps working while the status line still says "changes save automatically". Nothing is saved until they leave the note. A stress tester got the same result from Move note. Add the Ctrl+Q loss (N-01, owned by TASK-34000.1) or a crash, and the edit is gone. Even without that, the status line keeps making a false promise about saved state.

Observed at 160x45:
1. Open "Gardening log" and type.
2. Within the 2-second autosave delay, press F1 (or open Move note, or the command palette).
3. Close it and wait 20 s.

The status still reads "Unsaved changes · Next: Keep editing; changes save automatically.", and the stored note is unchanged (`verify/nl-v-n-06/07-after-20s-160x45.txt`; a second run is in `12-run2-before-quit-160x45.txt`). Control: a resize with no dialog saves normally. In j1, the DB row was still 'Untitled||1' 25 s after F1 → Esc.

Verified cause (origin/dev 2d34cbf80d):
- Library is a reusable route (TASK-31521), so pushing any modal posts ScreenSuspend.
- `LibraryScreen.on_screen_suspend` (`UI/Screens/library_screen.py:9205`) stops and clears `_notes_state.autosave_timer` (:9256-9260). This is deliberate: no debounce should fire against a hidden screen.
- `on_screen_resume` (:9262-9298) never re-arms that timer, even when the note session is still dirty.
- The "save automatically" wording depends only on the note being dirty, not on whether a save is actually scheduled.

Suggested direction (a direction, not a mandate):
- On resume, schedule the autosave again when the note session is dirty (`_schedule_library_note_autosave`, `library_screen.py:20738`). Alternatively, flush at suspend instead of only stopping the timer.
- Show "changes save automatically" only while a save is actually scheduled or running.

Severity: j1 rated this P0. It is P1 because the data loss itself belongs to N-01.

No existing task owns this. TASK-34000.1 (N-01) covers quit, the debounce's maximum wait and the blank-note orphan. This task covers only the modal suspend/resume gap and the status line's promise.

Review finding(s): N-06. Source: qa/notes-library-ux-review-2026-10-02/report.md

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Cause, confirmed on this tree.** Every pushed modal (F1 `WorkbenchHelpPanel`, `LibraryNoteFolderTargetDialog`
for Move note / Add to folder, the command palette) posts `ScreenSuspend` to the reusable Library screen;
`on_screen_suspend` stops and clears `_notes_state.autosave_timer` (TASK-31521, kept) and `on_screen_resume`
never re-armed it. The "changes save automatically" wording read only `dirty`.

**Fix.** Two seams, both in the autosave policy module `UI/Library_Modules/library_note_autosave.py` (kept out
of the two ratcheted files by its own docstring):
- `resume_library_note_autosave(screen) -> bool`: called once from `on_screen_resume`, right after the suspended
  flag clears. Schedules through the existing `_schedule_library_note_autosave` (which invalidates first, so the
  re-armed timer is the only one) for a dirty, unsaving, unconflicted editor note with no timer and no validation
  veto, then repaints the status so the promise is true again. The burst clock keeps running through the dialog,
  so a save that was due fires at `AUTOSAVE_MIN_DELAY_SECONDS` and a fresh burst waits its 2 s. A vetoed draft is
  not re-armed (it cannot succeed without an edit; Task TASK-34000.10 shows the veto on the field).
- `autosave_is_scheduled(state, snapshot)`: armed timer, or `autosave_state == "saving"`, or `snapshot.saving`.
  `_library_note_presentation_state` carries it as the new `LibraryNotePresentationState.autosave_scheduled`;
  `_authority_copy`'s editor branch paints "Keep editing; changes save automatically." only when scheduled or
  clean, and "Keep editing; press Save to save now." for a dirty note with nothing armed.
- `_fire_library_note_autosave`, `_save_library_note` and the nav-bar leave path (`flush_pending_work`) are
  untouched. Suspend's stop-and-clear became `_invalidate_library_note_autosave()` (fix round 1), so a save a
  just-fired timer had queued is fenced off too.
- Resume vetoes (fix round 1, review I-1/I-2 + the chained-dialog minor): the screen must be `app.screen`
  (a chained dialog still covers it); the visible rail row must be Notes or Create ▸ New note with the editor
  showing (a note parked by a switch to Media or another reader row is saved only on the return to Notes, the
  rail-switch precedent); and `autosave_state` must not be `validation` OR `error` -- a failed write keeps
  "Save failed …" on both status channels until Save or the next keystroke, and a retry at resume could write a
  draft "Discard and quit" had just discarded.

**Promise wording.** "Keep editing; changes save automatically." is painted while an autosave is armed, running,
or paused by a covering dialog (the covered line keeps what it last showed; the countdown resumes on close).
