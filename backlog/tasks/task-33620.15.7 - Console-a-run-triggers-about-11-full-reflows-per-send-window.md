## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the same live profile as TASK-33620.15.3 (2026-10-10; 160x45, Anthropic haiku through the review proxy). The probe timed Textual's `Screen._refresh_layout`, `Compositor.reflow` and `render_update`, and recorded which widgets posted the `Layout` messages before each reflow.

Textual screen updates (`Screen._on_timer_update` > `_refresh_layout` > reflow and render) are the longest UI-loop blocks after a send is accepted: 242 ms per send in total, worst 487 ms, with about 590 visible widgets at about 50 turns. Between acceptance and the provider call a send runs a median of 11 reflows of 5 ms or more, 498 ms per send in the launch that recorded requesters (median reflow 37 ms, max 405).

The widgets whose `Layout` message preceded those reflows, most often first: `Static`, `Button`, `Horizontal`/`Vertical`, `ConsoleCharacterContext`, `ConsoleRunChip`, `ConsoleMarkdownMessage`/`ConsoleAssistantTurnWidget`, `ConsoleInspectorRail`, `ConsoleCostChip`, `ConsoleControlBar` and `ComposerControlButton`. Run-state and cost chips change text during a run and request a full layout each time.

Even with the GC and projection fixes (TASK-33620.15.3, TASK-33620.15.4) and run start moved off the loop, the counterfactual floor stays at a median of 43 ms and a p90 of 85-98 ms; this is that floor.

Fix direction: fixed-width chips and controls, so a content change needs no layout; `batch_update` around multi-widget syncs; a bounded transcript.
