## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From PR #2941 thread PRRT_kwDOOcyyl86ntGYn; this predates the PR, since origin/dev's handler already called store.delete_message inline on the UI thread. ChaChaNotes_DB.soft_delete_message_subtree issues one UPDATE per row. Measured: 0.67 s for 1,000 messages and 7.4 s for 3,000. A scratch probe on a file-backed DB took ~600-630 ms for 999 messages through delete_subtree_for_undo, and Undo took ~75 ms. CLAUDE.md's rule is: workers for anything over 100 ms. The Console store is UI-thread state, and the recovered-media hold is per-thread, so a worker must carry the store's fork-source and voice-promotion fences.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Measured first on dev 7d155170dc (file-backed DB): DB delete 0.45-1.1 s / restore 1.0-1.8 s for 3k rows, run inline on the UI loop; profile shows the per-row sync_log proof attach (2,999 UPDATEs) and the per-row undelete loop dominate the DB time.
1. DB: batch restore_message_subtree's undelete (chunked UPDATE ... WHERE deleted = 1 AND id IN (...), rowcount-checked, inside the existing IMMEDIATE transaction) and the delete's per-row sync_log proof attach (one CASE-keyed UPDATE per chunk, uniqueness checked first); chunks bounded by the live SQLITE_LIMIT_VARIABLE_NUMBER via _bounded_id_batches (extended for fixed/per-id variable counts).
2. Split the store's monolithic _delete_message into plan (UI thread, in-memory reads + validation) / durable write (thread-agnostic: dispatch-branch transaction, subtree tombstone, active-leaf cursor, hidden flat-root scan) / apply (UI thread, in-memory purge) in a new small Chat module; the store delegates (net shrink, ratchet row already over on dev).
3. Async delete/undo variants that hold the fork-source + voice-promotion fences on the UI thread across the whole operation, run the durable half off the event loop (inline only for thread-local :memory: DBs, the _run_fork_io precedent), open the recovered-media hold in the worker thread that tombstones, and publish the in-memory result from a done-callback so a cancelled awaiter cannot strand the store.
4. Receipt modal gains a working state (Deleting/Restoring N messages...) that refuses Escape/Done and answers Ctrl+Q with refuse_quit_while_working; guarded-modal census row added. Done's held-reference release also runs off the loop.
5. Tests first, red on dev: statement-count pins for the batched writes (AC3), a production-shaped Console test proving the event loop keeps ticking and the in-progress state paints while a 3k-message delete/undo is in its durable phase, quit-while-working, and existing delete/undo/tombstone/sync suites kept green.
6. Measure before/after (1k/3k), live-verify via launch.sh with a seeded 3k conversation; file the non-DB UI costs found while measuring as follow-ups.
7. Review follow-ups (checkpoint review): keep a delete/Undo that committed from being reported as failed or retryable when the post-commit UI refresh raises (test-first); pin Undo's pending-dispatch refusal on the off-loop path and the Escape-while-Undo-mounts crash fix with tests; make the receipt count what was actually deleted; correct the User Guide's responsiveness claim; fix the follow-up tasks' pointer to probe data; re-measure both arms (n>=3, ranges) and correct the timing claims in these notes.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Batched the subtree writes and moved the durable half of Console Delete and Undo off the event loop. What this does and does not buy is measured below; most of what a user of a long chat waits for is elsewhere (TASK-33628.5.1, .5.2).

Profiled first on dev 7d155170dc (file-backed DB, 3,000-message subtree): the largest DB shares were the per-row sync_log proof attach (2,999 UPDATEs) and the per-row undelete loop; the tombstone UPDATE itself was already one recursive statement.

DB (ChaChaNotes_DB.py): restore_message_subtree undeletes with one rowcount-checked UPDATE ... WHERE deleted = 1 AND id IN (...) per id batch, inside the existing IMMEDIATE transaction (the version check before it still refuses the whole Undo). _attach_chat_delete_base_hashes does one SELECT and one CASE-keyed UPDATE per batch and still requires exactly one delete intent per tombstone. _bounded_id_batches takes reserved/per_id so batches that also bind a timestamp or several values per id stay inside the live SQLITE_LIMIT_VARIABLE_NUMBER. The FTS and sync triggers still fire per row. No schema or index change; the new statements' plans are index searches (idx_sync_log_entity, rowid, sqlite_autoindex_messages_1).

Store: _delete_message is now plan/write/apply phases in the new Chat/console_subtree_delete.py. The write phase reads no store state. It goes through two new stateless static helpers, ConsoleChatStore._dispatch_branch_transaction and _write_active_leaf (the existing methods delegate to them), and console_legacy_flat_roots.delete_seed_plan/hidden_seeds (delete_seeds composes them). console_chat_store.py shrank 27 lines.

Off-loop flow (console_message_delete.py): delete_subtree_off_loop/restore_subtree_off_loop take the store's fork-source and voice-promotion fences on the loop before reading anything and release them after the result is applied. The recovered-media hold opens in the worker thread that tombstones. run_durable_off_loop settles the outcome on the loop from a done-callback, so a cancelled awaiter cannot strand the store or its fences. A :memory: DB runs inline because it is thread-local (the _run_fork_io precedent). Done's held-reference release also runs off the loop.

UI: the receipt modal opens at confirm in a working state, 'Deleting N messages…'. Undo shows 'Restoring N messages…'. While a save runs, Escape, Done and backdrop clicks are refused ('It can't be cancelled'), and confirm_quit answers Ctrl+Q with refuse_quit_while_working; a second Ctrl+Q asks before quitting. A quit cannot half-apply: each durable half is one SQLite transaction. The receipt's outcome is the save's: a Console refresh that fails after a saved delete or Undo is logged (exception type only) and no longer turns the receipt into 'failed' (no Undo) or 'retry' (Undo offered for rows already back). The receipt counts what the delete saved. The guarded-modal census has a row for it. The User Guide's Delete section is updated, including that a very long transcript can still pause while it redraws after the save.

Measured (both arms, n=6 each: two rounds of three on one machine at load average ~24, ConsoleHarness 160x48, file-backed DB, 3,000-message branch off the active path under the deleted prompt so the transcript stays four rows; origin/dev 49206beea9 vs this branch):
- Durable work alone, inline, no UI (store.delete_message / restore through the sync wrappers): delete 0.160-0.201 s on dev vs 0.128-0.171 s here; Undo 0.214-0.355 s on dev vs 0.059-0.094 s here. The batching makes Undo about 3.5x cheaper and the delete only marginally cheaper: the tombstone UPDATE was already one recursive statement and its per-row triggers dominate.
- Confirm to receipt-with-Undo: 0.47-0.90 s on dev vs 0.43-0.93 s here, i.e. no wall-clock change. Longest event-loop block in that window: 0.16-0.48 s on dev vs 0.065-0.28 s here (5 of 6 runs at or under 0.078 s).
- Undo press to rows restored and receipt closed: 0.33-0.47 s on dev vs 0.39-0.55 s here (slightly slower: a thread hop, and the receipt now stays open through the refresh). Longest loop block: 0.32-0.46 s on dev vs 0.08-0.33 s here.
- The loop blocks that remain (up to about 0.33 s) are the post-action Console sync, filed as TASK-33628.5.2; arming a Delete, which writes nothing, blocks the loop 0.2-0.8 s in the same shape.
An earlier single probe here reported '3k DB delete 1.1 s -> 0.26 s, restore 1.76 s -> 0.2 s'; that does not reproduce (above) and is withdrawn. The first measurements on dev 7d155170dc (durable delete 0.45-1.1 s, Undo 1.0-1.8 s) were taken under different machine load and are not comparable with the table.
Caveat on AC#2: it holds for the shape above. Deleting from the first message of a long linear chat is dominated by transcript costs outside this task: selecting that message mounts every later row (183 s to settle at 3k), each focus-paint class toggle then restyles all of them (29-37 s), and Undo of a 1k chain held the loop up to 17.4 s. Filed as TASK-33628.5.1 (p1), the lever for long-chat Delete/Undo latency.

Live (launch.sh, isolated profile, seeded 3,002-message off-branch subtree): on the committed build (9e829cea01), with the write held behind an external sqlite3 BEGIN IMMEDIATE (7 s, then 6 s), the receipt painted 'Deleting 3002 messages…', answered Escape ('The delete is still being saved. It can't be cancelled.') and Ctrl+Q ('Still working… Quit again once it finishes'), and showed 'Deleted 3002 messages' with Undo after COMMIT (DB: 3,002 tombstoned). Undo did the same with 'Restoring 3002 messages…' and 'Undo is still restoring the messages', then closed with all 3,004 rows live and the rows back in the transcript. Unheld, single samples with a 100 ms tmux poll: confirm to receipt 1.46 s, Undo to closed 1.50 s. Earlier single live samples were 1.24 s / 1.44 s on this branch and 0.98 s / 0.54 s on dev; the dev Undo figure is not comparable, because dev closes the receipt before it restores. On dev the same held write froze the screen with no progress state until COMMIT. A 23 s hold past the 15 s busy timeout made the delete fail cleanly: rolled back, error toast, nothing deleted.
