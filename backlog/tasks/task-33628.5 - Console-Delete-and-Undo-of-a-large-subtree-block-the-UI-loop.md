## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From PR #2941 thread PRRT_kwDOOcyyl86ntGYn; this predates the PR, since origin/dev's handler already called store.delete_message inline on the UI thread. ChaChaNotes_DB.soft_delete_message_subtree issues one UPDATE per row. Measured: 0.67 s for 1,000 messages and 7.4 s for 3,000. A scratch probe on a file-backed DB took ~600-630 ms for 999 messages through delete_subtree_for_undo, and Undo took ~75 ms. CLAUDE.md's rule is: workers for anything over 100 ms. The Console store is UI-thread state, and the recovered-media hold is per-thread, so a worker must carry the store's fork-source and voice-promotion fences.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Measured first on dev 7d155170dc (file-backed DB): DB delete 0.45-1.1 s / restore 1.0-1.8 s for 3k rows, run inline on the UI loop; profile shows the per-row sync_log proof attach (2,999 UPDATEs) and the per-row undelete loop dominate the DB time.
1. DB: batch restore_message_subtree's undelete (chunked UPDATE ... WHERE deleted = 1 AND id IN (...), rowcount-checked, inside the existing IMMEDIATE transaction) and the delete's per-row sync_log proof attach (one CASE-keyed UPDATE per chunk, uniqueness checked first); chunks bounded by the live SQLITE_LIMIT_VARIABLE_NUMBER via _bounded_id_batches (extended for fixed/per-id variable counts).
2. Split the store's monolithic _delete_message into plan (UI thread, in-memory reads + validation) / durable write (thread-agnostic: dispatch-branch transaction, subtree tombstone, active-leaf cursor, hidden flat-root scan) / apply (UI thread, in-memory purge) in a new small Chat module; the store delegates (net shrink, ratchet row already over on dev).
3. Async delete/undo variants that hold the fork-source + voice-promotion fences on the UI thread across the whole operation, run the durable half off the event loop (inline only for thread-local :memory: DBs, the _run_fork_io precedent), open the recovered-media hold in the worker thread that tombstones, and publish the in-memory result from a done-callback so a cancelled awaiter cannot strand the store.
4. Receipt modal gains a working state (Deleting/Restoring N messages...) that refuses Escape/Done and answers Ctrl+Q with refuse_quit_while_working; guarded-modal census row added. Done's held-reference release also runs off the loop.
5. Tests first, red on dev: statement-count pins for the batched writes (AC3), a production-shaped Console test proving the event loop keeps ticking and the in-progress state paints while a 3k-message delete/undo is in its durable phase, quit-while-working, and existing delete/undo/tombstone/sync suites kept green.
6. Measure before/after (1k/3k), live-verify via launch.sh with a seeded 3k conversation; file the non-DB UI costs found while measuring as follow-ups.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Batched the subtree writes and moved the durable half of Console Delete and Undo off the event loop.

Measured first (dev 7d155170dc, file-backed DB, 3,000-message subtree): the durable delete was 0.45-1.1 s and the durable Undo 1.0-1.8 s, both inline on the UI loop. Profiles showed the per-row sync_log proof attach (2,999 UPDATEs) and the per-row undelete loop as the largest shares; the tombstone UPDATE itself was already one recursive statement.

DB (ChaChaNotes_DB.py): restore_message_subtree undeletes with one rowcount-checked UPDATE ... WHERE deleted = 1 AND id IN (...) per id batch, inside the existing IMMEDIATE transaction (the version check before it still refuses the whole Undo). _attach_chat_delete_base_hashes does one SELECT and one CASE-keyed UPDATE per batch and still requires exactly one delete intent per tombstone. _bounded_id_batches takes reserved/per_id so batches that also bind a timestamp or several values per id stay inside the live SQLITE_LIMIT_VARIABLE_NUMBER. The FTS and sync triggers still fire per row. No schema or index change; the new statements' plans are index searches (idx_sync_log_entity, rowid, sqlite_autoindex_messages_1). After: 3k DB delete 0.26 s, restore 0.2 s (was 1.1 s / 1.76 s in the same probe).

Store: _delete_message is now plan/write/apply phases in the new Chat/console_subtree_delete.py. The write phase reads no store state. It goes through two new stateless static helpers, ConsoleChatStore._dispatch_branch_transaction and _write_active_leaf (the existing methods delegate to them), and console_legacy_flat_roots.delete_seed_plan/hidden_seeds (delete_seeds composes them). console_chat_store.py shrank 27 lines.

Off-loop flow (console_message_delete.py): delete_subtree_off_loop/restore_subtree_off_loop take the store's fork-source and voice-promotion fences on the loop before reading anything and release them after the result is applied. The recovered-media hold opens in the worker thread that tombstones. run_durable_off_loop settles the outcome on the loop from a done-callback, so a cancelled awaiter cannot strand the store or its fences. A :memory: DB runs inline because it is thread-local (the _run_fork_io precedent). Done's held-reference release also runs off the loop.

UI: the receipt modal opens at confirm in a working state, 'Deleting N messages…'. Undo shows 'Restoring N messages…'. While a save runs, Escape, Done and backdrop clicks are refused ('It can't be cancelled'), and confirm_quit answers Ctrl+Q with refuse_quit_while_working; a second Ctrl+Q asks before quitting. A quit cannot half-apply: each durable half is one SQLite transaction. The guarded-modal census has a row for it. The User Guide's Delete section is updated.

Result at 3k (harness, off-branch subtree so the transcript stays four rows): the delete and Undo themselves cost about 25 ms on the loop (plan 2-4 ms, capture 2-4 ms, apply 12-19 ms; Undo about 10 ms), and the write runs on a worker thread. Loop blocks around them are now 0.1-0.46 s, down from 0.24-0.63 s; arming the Delete alone (no write) blocks 0.2-0.84 s, so the rest is the generic Console sync, filed as TASK-33628.5.2. Caveat on AC#2: deleting from the first message of a long linear chat is dominated by transcript costs outside this task. Selecting that message mounts every later row (183 s to settle at 3k), and then each focus-paint class toggle restyles all of them (29-37 s). Filed as TASK-33628.5.1.

Live (launch.sh, isolated profile, seeded 3,002-message off-branch subtree): with the write held behind an external sqlite3 BEGIN IMMEDIATE, the fix build painted 'Deleting 3002 messages…', answered Escape ('can't be cancelled') and Ctrl+Q ('Still working… Quit again once it finishes'), and showed the receipt about 1.3 s after COMMIT. Undo did the same with 'Restoring 3002 messages…' and 'Undo is still restoring the messages'. Unheld: confirm to receipt 1.24 s, Undo to closed 1.44 s; DB 3,002 tombstoned, then all 3,004 live. On the dev baseline the same held write froze the screen: an identical capture before and after Escape, with no progress state, until COMMIT. A 23 s hold past the 15 s busy timeout made the delete fail cleanly: rolled back, error toast, nothing deleted.

Tests: Tests/DB/test_message_subtree_batched_writes.py (statement-count pins red on dev: 1,199 per-row statements each), Tests/UI/test_console_message_delete_off_loop.py (production-shaped 3k delete+undo with the write gated: red on dev 'the durable subtree delete ran on the event-loop thread'; also pins the fences, the hold's thread and the in-progress paint), Tests/Chat/test_console_delete_off_loop.py (runner and cancelled-awaiter cases), and the receipt's quit hooks in test_app_quit_in_flight_modals.py and test_modal_quit_in_flight_hooks.py. Mutation-checked: undo inline, no fence, no hold, and settle after await each fail the pins. Updated: the semantic mutation census row for the moved delete_message_subtree call, the registry-purge accounting test, the recovered-media ui_warning fake, ABSENT_AT_READY_MODULES, and the diagnostic inventory (one content-free warning added, one moved).
