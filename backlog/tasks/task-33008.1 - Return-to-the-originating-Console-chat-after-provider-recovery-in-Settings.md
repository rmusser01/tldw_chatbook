## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
_open_console_provider_recovery (chat_screen.py:20533-20565) sends credential blockers to Settings. It passes category, provider, model and field context but carries no return, so the user is stranded after adding a key (the remaining part of C1).

Every recovery entry routes through this one function, so a fix there covers all of them:
- the setup card (Widgets/Console/console_setup_modal.py:550)
- the transcript's blocked-state action (Widgets/Console/console_transcript.py:2554)
- the prompts configure-provider hook (UI/Console_Modules/prompts.py:1265)

The Chat settings modal's credential detour already has a return. It stages a secret-free ConversationSettingsReturnIntent on HandoffChannel.CONVERSATION_SETTINGS_RETURN (chat_screen.py:3556-3600), and Settings shows a return continuation (settings_screen.py:16980-17004, handler :28656). ADR-033 (application-session-state:13-23) makes PendingHandoffStore the owner of such handoffs.

Settings' return copy and button are written only for that modal case (settings_screen.py:12228-12242, :16976-16990).

ADR-012:31 requires recovery to open the exact credential control. ADR-095 and its 2026-09-26 amendment decide what happens to the returning chat: an untouched chat converges to the saved defaults (D1, phase 1), and a chat that holds work keeps its own settings.

chat_screen.py has 32 lines of headroom (test_screen_size_ratchet.py:85).

Two tests pin today's context dict, which has no return:
- Tests/UI/test_console_native_chat_flow.py:6526, test_console_add_api_key_recovery_targets_provider_settings_category
- :6562, test_console_add_api_key_recovery_tolerates_missing_session_settings
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Navigation types (R33, R34, R36): a Console return intent that names only the chat, staged on the Chat settings return channel; an optional session_id and a wider field on the Settings target; a strict Console return target.
2. One route out (R32, R35): open_provider_setup stages the return, validates first and falls back to the one-way route; _open_console_provider_recovery delegates its Settings branch to it.
3. Settings (R37, R38): labels and status copy follow the target's kind and name the chat; the claim checks the exact kind and chat.
4. Console (R39): a Console_Modules consumer claims the exact revision, switches to the chat, syncs and focuses the composer or the card; stale and missing-chat returns show a notice.
5. Tests first (R40, R41): rewrite the four pinned tests, unit tests for both sides over the real stores, two private-profile tests on the real app.
6. Covering run, architecture run, boot census, preflight, live check at 211x44, docs.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A Console provider recovery that leaves for Settings now carries a way back to the chat it left.

- One route (AC#1, R32): open_provider_setup (UI/Console_Modules/model_switcher.py) is the single exit from Console to Settings. The recovery action (card, transcript, prompts hook), a cloud key check's Retry and the switcher's NEEDS SETUP rows all reach it. _open_console_provider_recovery keeps its own provider, model and field and delegates. Settings opens on the provider with focus in the named field, as before.
- Handoff (AC#5, R33): ConsoleProviderReturnIntent has one field, session_id. It is staged on HandoffChannel.CONVERSATION_SETTINGS_RETURN, so the store's single slot makes a newer request of either kind supersede the older one. No key, endpoint, prompt or title enters it.
- Validate before staging (R35): a provider or model the target rejects (a custom-ep: id, no provider) or a Console with no chat stages nothing and posts the old one-way context. A navigation that fails discards its exact pending revision.
- Settings (AC#2, R34, R37, R38): ProviderSettingsNavigationTarget gains an optional session_id (None is the Chat settings modal, whose context is byte-identical) and accepts field api_key, endpoint or none. The two return buttons read "Return to Console" for a Console target and are relabelled in _update_provider_return_widgets. The status names the chat by title, read from the live Console store when drawn: "Credential saved. Return to Console to continue in “Chat 1”; provider acceptance is not yet verified." After a save focus lands on the return, so Esc, s, Enter is save and go back. Since fix round 1 the Console kind also shows the return on arrival (below). The claim accepts only the target's own kind and chat (target.matches).
- Console (AC#3, AC#6, R36, R39): Settings answers with ConsoleProviderReturnTarget {session_id, return_revision, outcome}. ChatScreen.apply_navigation_context hands it to UI/Console_Modules/provider_return.py, and the mount and resume consumers call it through _consume_pending_conversation_settings_return. It claims the exact revision and type, switches to the chat if it is not active, syncs, then focuses the composer, or the card's primary action while the card still blocks. A superseded, settled or mismatched handoff, or a closed chat, shows a notice and changes nothing. It adds no convergence code: the save writes the new-chat default and D1's refresh moves an untouched chat onto it.
- Return without saving (AC#4): unchanged widgets and confirmation; it lands on the same chat with nothing written.
