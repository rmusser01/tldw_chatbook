## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
_open_console_provider_recovery (chat_screen.py:20533-20565) sends credential blockers to Settings. It passes category, provider, model and field context but carries no return, so the user is stranded after adding a key (the remaining part of C1).

Every recovery entry routes through this one function, so a fix there covers all of them:
- the setup card (Widgets/Console/console_setup_modal.py:550)
- the transcript's blocked-state action (Widgets/Console/console_transcript.py:2554)
- the prompts configure-provider hook (UI/Console_Modules/prompts.py:1265)

The Chat settings modal's credential detour already has a return. It stages a secret-free ConversationSettingsReturnIntent on HandoffChannel.CONVERSATION_SETTINGS_RETURN (chat_screen.py:3556-3600), and Settings shows a return continuation (settings_screen.py:16980-17004, handler :28656). ADR-033 (application-session-state:13-23) makes PendingHandoffStore the owner of such handoffs.

Settings' return copy and button are written only for that modal case (settings_screen.py:12228-12242, :16976-16990).

ADR-012:31 requires recovery to open the exact credential control. ADR-095 and its 2026-09-26 amendment decide what happens to the returning chat: an untouched chat converges to the saved defaults (D1, phase 1), and a chat that holds work keeps its own settings.

chat_screen.py has 32 lines of headroom (test_screen_size_ratchet.py:85).

Two tests pin today's context dict, which has no return:
- Tests/UI/test_console_native_chat_flow.py:6526, test_console_add_api_key_recovery_targets_provider_settings_category
- :6562, test_console_add_api_key_recovery_tolerates_missing_session_settings
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
A Console provider recovery that leaves for Settings now carries a way back to the chat it left.

- One route (AC#1, R32): open_provider_setup (UI/Console_Modules/model_switcher.py) is the single exit from Console to Settings. The recovery action (card, transcript, prompts hook), a cloud key check's Retry and the switcher's NEEDS SETUP rows all reach it. _open_console_provider_recovery keeps its own provider, model and field and delegates. Settings opens on the provider with focus in the named field, as before.
- Handoff (AC#5, R33): ConsoleProviderReturnIntent has one field, session_id. It is staged on HandoffChannel.CONVERSATION_SETTINGS_RETURN, so the store's single slot makes a newer request of either kind supersede the older one. No key, endpoint, prompt or title enters it.
- Validate before staging (R35): a provider or model the target rejects (a custom-ep: id, no provider) or a Console with no chat stages nothing and posts the old one-way context. A navigation that fails discards its exact pending revision.
- Settings (AC#2, R34, R37, R38): ProviderSettingsNavigationTarget gains an optional session_id (None is the Chat settings modal, whose context is byte-identical) and accepts field api_key, endpoint or none. The two return buttons read "Return to Console" for a Console target and are relabelled in _update_provider_return_widgets. The status names the chat by title, read from the live Console store when drawn: "Credential saved. Return to Console to continue in “Chat 1”; provider acceptance is not yet verified." Nothing shows before a save; after a save focus lands on the return, so Esc, s, Enter is save and go back. The claim accepts only the target's own kind and chat (target.matches).
- Console (AC#3, AC#6, R36, R39): Settings answers with ConsoleProviderReturnTarget {session_id, return_revision, outcome}. ChatScreen.apply_navigation_context hands it to UI/Console_Modules/provider_return.py, and the mount and resume consumers call it through _consume_pending_conversation_settings_return. It claims the exact revision and type, switches to the chat if it is not active, syncs, then focuses the composer, or the card's primary action while the card still blocks. A superseded, settled or mismatched handoff, or a closed chat, shows a notice and changes nothing. It adds no convergence code: the save writes the new-chat default and D1's refresh moves an untouched chat onto it.
- Return without saving (AC#4): unchanged widgets and confirmation; it lands on the same chat with nothing written.
- Modal round trip (AC#7): its intent, target, checks and copy are unchanged; test_conversation_settings_return_real_navigation_restores_fresh_console_modal passes.
- Pinned tests rewritten on purpose (AC#8, R40): test_console_add_api_key_recovery_targets_provider_settings_category and test_console_add_api_key_recovery_tolerates_missing_session_settings (now private-profile tests that pass here), test_needs_setup_route_names_the_provider_its_model_and_the_field and test_a_cloud_key_check_failure_retries_in_settings_not_chat_settings. Each asserts the return-bearing context and the staged intent.
- Integration (AC#9, R41): Tests/UI/test_console_provider_return.py::test_recovery_round_trip_returns_to_the_chat_on_one_enter runs the real app on a scratch config at 211x44 with nothing patched: Enter on the card, type the key, Esc, s, Enter. It asserts the chat id, composer focus, ready_to_send and the key in the scratch config file. A second private-profile test covers Return without saving, both Console labels and the kind surviving a fresh Settings screen.
- Sizes (AC#10): chat_screen.py 25,076 -> 25,074 lines, methods unchanged; settings_screen.py 33,732 -> 33,725; providers_models_card.py 2,300 -> 2,296. No row edited. No CSS.
- AC#11 (captures) is discharged by the phase's Capture step (R4); the task stays In Progress. A live check at 211x44 on a scratch profile (HOME, XDG and TLDW_CONFIG_PATH all scratch) showed the status line, Return to Console, and the Console ready on Chat 1 after one Enter; nothing was committed.
- Docs: Docs/User_Guide/settings.md (the return, both kinds) and Docs/User_Guide/console.md (Set up provider, Retry connection, Common tasks).

Rulings:
- The Settings claim calls target.matches instead of keeping the literal modal type check: that check has to become kind-aware, and matches is the exact-type check for each kind. Cost if wrong: one line to restore.
- The Console always syncs before it focuses, not only after a switch: the focus decision needs the readiness the save just changed. Cost if wrong: one redundant sync per return.
- The claim is acknowledged whether or not the landing succeeds: nothing retries a failed landing, so a requeued revision would only linger. Cost if wrong: a failed landing cannot be replayed.
- The chat-title rule moved to one function (fitted_chat_title) that Applies to and the return copy share. Cost if wrong: a four-line hunk in applies_to_copy to rebase.
- New tests were added to Tests/State/test_conversation_settings_navigation.py and test_pending_handoff_store.py; every test that was there is unchanged and passes.
- With Retry connection, a key test alone saves nothing, so no return shows (R37). The guide says so.
