## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The Phase 5 capture checkpoint (qa/model-config-33005-captures, captures 10 and 12) found "verified" claimed for models the key check never saw:
- Settings reads "Readiness Ready · verified 07:33" directly above "Model gpt-5.6-terra (draft) · not listed by the server". The key was accepted, but the chosen model was not in the listing, and a send with it may fail.
- In Switch model, every OpenAI row reads "Ready · verified 07:33" although the listing returned only two models (gpt-4o, gpt-4o-mini); the rows for models it did not list claim the same proof.

"Verified" is the strongest readiness word (spec §5). It must not be stretched from "this key lists models" to "this model will answer".
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 When an accepted key check did not list the chosen model, Settings' Readiness row and Model row do not contradict each other: the word for that model is not 'Ready · verified', or the Model row explains why it still is
- [x] #2 Switch model rows read 'verified' only for models the accepted listing returned; the provider's other rows keep a weaker word
- [x] #3 The Console header badge, rail Model line and switcher agree with Settings for the same provider and model at the same moment
- [x] #4 Tests cover a listed and an unlisted model under one accepted key check, with a negative control
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Fix the shared word builder: an accepted key check's "verified" needs the model facet "confirmed".
2. Let one provider readiness word each of its models (Switch model resolves one readiness per provider).
3. Pin listed and unlisted models under one key check, with a negative control, on every surface that reads the word.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
"Verified" from a key check now covers only the models its listing returned.

- `Chat/console_session_settings.py::_ready_words` takes the Model facet. An accepted cloud key (`listing_accepted`, or `authenticated` over a reachable listing) reads "Ready · verified HH:MM" only when the facet is "confirmed" (the listing returned the model). Another model under that key reads "Ready · reachable HH:MM": the server answered and the key was accepted, but nothing says this model will answer. A paid test still verifies the model it sent, and a public listing still proves nothing. `readiness_words` passes `readiness.model`; `verdict_readiness_words` (Settings' Readiness row) passes `snapshot.model`, so both read the one rule (AC#1, AC#3).
- AC#2: Switch model resolves one readiness per provider, for a representative model, and painted that word on every row of the provider (capture 12). `ConsoleSettingsReadiness` now carries the evidence it read (`evidence`, excluded from equality and repr), and `model_readiness_words(readiness, model)` words one row's model from it: the listing's models for "verified", and `for_model` for a paid test. `console_model_popover.switcher_readiness_words` takes the row's model.
