## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
In Settings, Esc releases a text field so the single-key shortcuts work (task-1560). Nothing is focused after that. Pressing r then opens the Discard changes dialog. When the dialog closes, keyboard focus lands on the app navigation bar's first button (Home), so a following Enter leaves Settings.

Measured on 2026-10-04 on the TASK-33007.9 branch, in a mounted Settings with the real stylesheet at 211x44. Focus landed on Home in all four cases: from the Provider control and from the Endpoint field on Providers & Models, closing the dialog with Discard changes and with Keep editing.

Cause: the screen resumes with nothing focused, and the framework then focuses the screen's first focusable widget. Settings names no widget of its own for that. The path is not specific to Providers & Models; any Settings field left with Esc takes it. Other Settings categories and other dialogs opened from Settings were not measured.

Found by the TASK-33007.9 review (finding M6). That task's change does not cause it, so it is filed on its own.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
After the Revert dialog closes (either button), keyboard focus stays released instead of landing on the navigation bar's Home.

- Cause, confirmed: `Screen._on_screen_resume` calls `_update_auto_focus`, which focuses the first focusable widget (`#nav-home`) when the resumed screen has nothing focused, which is the state Esc leaves (task-1560). It is dispatched after `SettingsScreen.on_screen_resume`, because Textual walks the MRO subclass-first, so a `set_focus(None)` there would be undone.
- `SettingsScreen.on_screen_resume`: `self.AUTO_FOCUS = ""` when the screen resumes with nothing focused, else `None` (the app's default). The nav bar's first-paint focus is unaffected because it is placed before the first resume: `Screen._compose` runs `_update_auto_focus` and focuses `#nav-home`, so the mount's own resume already finds focus set. Review round 1 dropped a `not mount_already_refreshed` clause that claimed to protect that first resume; measured with a spy on `on_screen_resume` in a mounted Settings, the first resume sees the token False (`on_mount` runs before `is_mounted` is set, so `_queue_sync_rows_refresh()` returns False) and focus already on `#nav-home`, so the clause never applied. The fix is not specific to Revert or to one category: any dialog that closes over a Settings screen whose focus was released leaves it released. Settings' own Tab with nothing focused still goes to the rail's Overview.
- Phase 8 Task 1's return-action focus (`_focus_provider_return_continuation`) focuses a widget explicitly and is unaffected.
- Rewritten on purpose: `test_settings_focus_help_line_never_describes_the_nav_bar` (Tests/UI/test_settings_configuration_hub.py) pinned `screen.focused is home` after a modal closed. It now asserts focus stays None and focuses Home by hand to keep its help-line pin.

Test (Tests/UI/test_settings_connect_rows.py, gated whole in the UI census; real stylesheet, 211x44, private profile): `test_the_revert_dialog_leaves_focus_off_the_navigation_bar`, 4 cases: the Endpoint field (Providers & Models) and Threshold (Console Behavior), each with Discard changes and Keep editing. Each asserts focus is not in the nav bar, Enter posts no navigation (`host.seen_routes == []`), the draft is gone or kept with the typed value, and s and r act without another Esc (Keep editing: r reopens the dialog and s saves; Discard: r and s toast "No Settings changes to revert/save."). Red before the fix in all 4 (`focus went to the navigation bar: NavigationButton(id='nav-home', ...)`); with the fix removed and the focus check skipped, the Enter check fails too (`['home']`).
