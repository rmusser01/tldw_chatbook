## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the TASK-33621.13 verifier. After a restart, a saved chat whose first send had been blocked shows 'Response accepted on another device; waiting for dispatch.' The send happened in the same profile on the same machine, so the copy states a fact the record does not hold (umbrella TASK-33621).

**2026-11-24: AC #2 reworded to match the owner's re-decision.**
- Owner decision, 2026-11-23: "Response accepted but never sent. Send again to retry.", with a Send-again action.
- The safety check below showed that a checkpoint-free `accepted` row can come from three places:
  - a synced or imported conversation (sync and `.chatbook` carry `assistant_generation_state`, never the device-local checkpoint);
  - another app instance on the same profile that is still streaming (concurrent instances are deliberate; `Utils/instance_lock.py` is detection-only);
  - this device's own reply row, saved before provider entry by `_create_pending_assistant` (through `accept_attempt`) or `save_pending_assistant` (through `save_pending_reply`). That row stays `accepted` while the provider streams.
- No existing mechanism guarantees a single dispatch for such a row:
  - `ConsoleDispatchRepository.cas_state` looks the owner up through the checkpoint table and returns NOT_FOUND;
  - the recovery claim (`claim_dispatch_recovery_action`) is in-memory for one process;
  - there is no dispatch lease.
- "Never sent" is also not a fact the row holds: live, a stale `accepted` row's request reached the proxy, which then forwarded it upstream.
- Owner re-decision, 2026-11-23: "Neutral copy now, durable fix next." The durable fix is TASK-33621.195.

**Live** (real app, claude-haiku-4-5 through the review proxy, isolated profiles; evidence in `evidence/bd5/U30/`):

**Lessons** (kept here, not in `lessons-live-verification.md`):
1. A unit test of a gate is not evidence that the action works. `dispatch_recovery_blocks_submission` was False (green), yet the real send failed after its commit. Only the live send (0 POSTs) and a real-controller test showed it.
2. To make a checkpoint-free `accepted` row live, use Regenerate with the proxy in `slow` mode, then SIGKILL within 12 s. With `stall`, a one-word reply completed before the stall point.
3. After SIGKILL, the proxy still forwarded the request upstream. An `accepted` row is not evidence that the request was never sent.
