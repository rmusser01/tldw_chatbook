# How the app's CSS is built and loaded

Developer notes for `tldw_chatbook/css/`, last revised 2026-11-03 (TASK-36523).

Textual CSS has no `@import`, so there is no entry-point stylesheet. Every sheet
the app loads is generated by `build_css.py` and committed.

## Sources

- **TCSS modules** in `core/`, `layout/`, `components/`, `features/` and
  `utilities/`. The `CSS_MODULES` list in `build_css.py` names the modules that
  are built, in cascade order: core, layout, components, features, utilities. A
  file missing from that list is never loaded. A listed file that does not exist
  fails the build.
- **CSS declared in Python.** A widget declares its rules as a class-level
  `BUNDLED_CSS` string literal, and a screen or modal as `BUNDLED_SCREEN_CSS`.
  Do not use `DEFAULT_CSS` for new rules: Textual adds a stylesheet source for
  each class that declares it (TASK-15450). `widget_css.py` reads these
  literals with `ast`, without importing the modules.

Put comments that explain a rule in the source. The build strips comments from
the generated sheets.

## Generated sheets

`python tldw_chatbook/css/build_css.py` writes every sheet below. It builds them
in a staging directory and moves them into place only after every builder has
succeeded.

| Sheet | Built from | Loaded by |
|---|---|---|
| `tldw_cli_modular.tcss` (the bundle) | `CSS_MODULES` in order, each under a `/* ===== MODULE: … ===== */` banner | `TldwCli.CSS_PATH` in `app.py`, at boot |
| `screen_css_scoped.tcss`, `screen_css_self.tcss` | `BUNDLED_SCREEN_CSS` | `TldwCli.CSS_PATH`: the scoped sheet before the bundle, the self sheet after it |
| `widget_defaults_self.tcss`, `widget_defaults_scoped.tcss` | `BUNDLED_CSS` | `TldwCli._get_default_css`, through `build_css.widget_defaults_sources()`, ahead of Textual's own default CSS |
| `screen_agentic_library.tcss`, `screen_agentic_settings.tcss` | rules split out of the Library and Settings modules | the `CSS_PATH` of `LibraryScreen` and `SettingsScreen` (and `ConsoleHooksReviewModal`), on first visit |
| `screen_feature_*.tcss` (plugins, evals, scheduling, watchlists, workflows, roleplay) | rules split out of the owning feature module | `_SCREEN_OWNED_ROUTE_CSS` in `UI/Navigation/screen_registry.py`, on first navigation to the route |
| `screen_modal_*.tcss` | rules split out of `features/_console.tcss` and `features/_notes.tcss` | the owning modal's `CSS_PATH`, on first open (`MODAL_OWNED_SPLIT_SHEETS`) |

`SCREEN_OWNED_SPLITS` in `build_css.py` defines the split sheets. A rule moves
out of the bundle only when every `#id` and `.class` in its selector belongs to
one owner. The owning screen then parses it on first visit instead of before the
first paint. The rest of that module stays in the bundle.

Never edit a generated sheet. Edit its source and rebuild. Each build also
writes `.css-build-manifest.json`, which git ignores. It records the content
hash of every input, and the startup check below reads it.

## Changing CSS

1. Edit a module, or a `BUNDLED_CSS` or `BUNDLED_SCREEN_CSS` literal. For a new
   module, create the file and add it to `CSS_MODULES` at its cascade position.
2. Run `python tldw_chatbook/css/build_css.py` with the repo's Python (3.12 or
   newer). `./build_css.sh` at the repo root runs the same command. It uses
   `$PYTHON` when that is set. Otherwise it uses the first of `.venv/bin/python`,
   `python3`, `python3.14`, `python3.13` and `python3.12` that is 3.12 or newer,
   and it stops with an error when none is.
3. Commit the source change with every regenerated sheet.
4. Run `./scripts/preflight.sh`.

## Checking

`python tldw_chatbook/css/check_bundle_sync.py` rebuilds every generated sheet
in a temporary directory and compares it with the committed copy. It exits 1 and
names each drifted module when they differ. It also fails when a `CSS_MODULES`
entry is missing. It needs only the standard library. It is the first check
`./scripts/preflight.sh` runs ("generated stylesheets"). CI runs it in the
Derived Artifacts workflow (`.github/workflows/derived-artifacts.yml`, in the
step "Generated stylesheets reproduce from their sources").

Tests that cover the build:

- `Tests/UI/test_css_build_integrity.py`: the build is complete and deterministic.
- `Tests/UI/test_css_staleness_manifest.py`: the startup staleness check.
- `Tests/UI/test_widget_css_consolidation.py`: how `BUNDLED_CSS` is lifted.
- `Tests/Performance/test_boot_css_byte_budget.py`: CSS bytes parsed at boot.

## Rebuild at startup (source checkouts only)

The startup check runs only when the package sits beside a `pyproject.toml`,
which means a source checkout rather than a wheel install. Before the app
starts, the entry points in `app_entry.py` call `_generated_css_is_stale()`.
Those entry points are `main_cli_runner` (the `tldw-cli` script and
`python -m tldw_chatbook`), `python -m tldw_chatbook.app`, and `get_app()` for
`textual serve`. When the sheets are stale, they run `build_css.py` in a
subprocess. The sheets are stale when:

- a generated sheet is missing;
- with a manifest: a recorded input's content has changed, a recorded input
  has been deleted, or a `.py` file newer than the build declares `BUNDLED_CSS`
  or `BUNDLED_SCREEN_CSS`;
- without a manifest: a module in the five source directories, or a `.py`
  file with such a declaration, is newer than the oldest generated sheet.

If the rebuild fails, the console script and `python -m` log the error and start
with the sheets already on disk. `get_app()` raises instead. There is no fallback
CSS. A rebuild rewrites the committed sheets in your working tree, so commit
them with your change. The startup check is a development convenience;
`check_bundle_sync.py` is what decides whether the committed sheets are correct.

## History

This file began on 2025-06-29 as the plan and log for splitting the 3,939-line
`tldw_cli.tcss` into these modules. The plan made `main.tcss`, a list of
`@import` lines, the entry point. Textual cannot load `@import`, so
`build_css.py` concatenated the modules instead. `main.tcss` stayed in the tree,
unloaded, until TASK-36523 removed it, by which time it imported two deleted
sheets. The plan, the log and the fallback to CSS in `Constants.py` it describes
(since removed) are in this file's git history.
