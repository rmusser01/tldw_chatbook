## Verdict (hand-written; everything above is generated by `run_bakeoff.py`)

**No embedder passes all five spec §7 gates. The bake-off FAILS.** Per the
spec's fail branch as written, `AUTO_ORDER` would stay SpeechBrain-first; the
failed gate is named below. **Decision (2026-09-08):** the separation gate was
overridden as not the right cross-embedding-space test (see the qualification
at the end), so `AUTO_ORDER` is ONNX-first — spec §10 records it. The
measurements above are unchanged.

**The blocking gate is self-match separation, for every candidate.** ECAPA's
separation is 0.734; the best ONNX embedder (titanet_small at cluster 0.95)
reaches 0.640, which is 0.094 below it against a 0.05 allowance. Live purity
additionally fails for `wespeaker_resnet34` (0.888) and `campplus_en` (0.847)
against a 0.911 floor.

Every other gate passes, and three of them by a wide margin:

| gate | ECAPA | best ONNX | verdict |
| --- | --- | --- | --- |
| Stop-pass DER | 0.371 | 0.125 (eres2net_en) | PASS -- ONNX is 3x better, not merely within 0.02 |
| Live purity | 0.941 | 1.000 (titanet_small, eres2net_en) | PASS |
| RTF | 0.015 | 0.038 (titanet_small) | PASS (ceiling 0.15; ECAPA is the faster one) |
| Embed latency (median) | 27.6 ms | 11.8 ms (titanet_small) | PASS (ceiling 150 ms) |
| Self-match separation | 0.734 | 0.640 (titanet_small) | **FAIL** (0.094 short, allowance 0.05) |

One honest qualification, which does **not** change the verdict: the
separation gate compares an absolute cosine margin across two different
embedding spaces. titanet_small's own *self* similarity is higher than
ECAPA's (0.933 vs 0.847); its margin is narrower because its
*other-speaker* similarities also sit higher (0.303 vs 0.107). That is why
the harness reports a recommended `voice_match_threshold` per embedder
(0.377 for titanet_small, 0.526 for ECAPA) rather than assuming one constant.
Whether an absolute cosine margin is the right cross-space test is a question
for the task that acts on this report; as the gate is written today, it fails.

a **three-file narrowing sweep** whose cells are not in this `results.json` --
it holds only the final full-corpus cells at the chosen thresholds. The
narrowing procedure is written out in [`README.md`](README.md#reproducing);

### Not measured

- **The x86 proxy run.** The x86 runner job is landed but **not dispatched
  for this PR** — the RTF and latency *runner* halves are unmeasured, and
  **the verdict does not depend on them**. Every number above is from the
  Apple M-series machine, so "RTF <= 0.15 on both machines" and "latency
  <= 300 ms on the runner" are unverified; both pass on the M-series with
  2-4x of headroom, and the two gates that actually fail (separation,
  purity) are machine-independent. The report generator now derives the
  latency ceiling from the recorded machine, so a runner report will grade
  itself at 300 ms rather than the M-series' 150 ms.
- **Peak RSS of the ONNX worker looks high** (0.8-2.3 GB, vs 1.1 GB for the
  ECAPA worker). This is ONNX Runtime arena behaviour over a whole file, not
  steady-state live cost; the spec sets no numeric gate on it, and it was not
  investigated further.

### Incidental finding (not part of the bake-off)

`diarizer_engine_speechbrain._batch` calls `torchaudio.load`. torchaudio
>= 2.9 routes that through torchcodec, which is a separate package: without
it the call raises `ImportError` and the SpeechBrain **Stop pass returns no
segments at all** (the live path is unaffected). Measured here on
**torchaudio 2.11.0 / torch 2.14.0** -- the exact versions are now recorded in
`results.json` as `baseline_python`, so the header above proves this report is
the post-torchcodec run and not the broken one. The baseline only ran after
torchcodec 0.16.0 was installed and the Homebrew ffmpeg dylibs were put on the
loader path. Worth filing against the SpeechBrain engine -- the `diarization`
extra pins neither `torchaudio < 2.9` nor `torchcodec`.
