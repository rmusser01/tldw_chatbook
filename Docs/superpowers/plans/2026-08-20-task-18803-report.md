## 2. The fix

### OpenAI (`tldw_chatbook/LLM_Calls/LLM_API_Calls.py`)

* The sampling-omission decision consults the **existing TASK-18802
  predicate** `openai_model_rejects_sampling_params`; the hand tuple
  `_OPENAI_REASONING_MODEL_FAMILIES` / `_is_openai_reasoning_model` is
  deleted. Value-level nuance mirrored from 18802: the rejection is of
  *non-default* values (P8: `temperature: 1` → 200), so omission is correct
  either way and the existing explicit-param warning is kept.
* The token-cap key consults `openai_model_requires_max_completion_tokens`:
  Responses branch keeps `max_output_tokens`; any modern-family
  chat-completions request now gets `max_completion_tokens`; everything else
  keeps `max_tokens`. This closes the headline hole — previously only the
  gpt-5.6 special case escaped the `max_tokens` fall-through.
* `_is_openai_gpt_5_6_model` **stays**, deliberately: its two remaining
  consumers answer a different question — *which API branch to use*
  (`_openai_use_responses_api`'s `effort == "none"` carve-out exists because
  gpt-5.6's chat-completions surface accepts a `reasoning_effort` parameter,
  including "none", that other models' surfaces do not) and *whether to emit
  that chat-completions `reasoning_effort` knob*. Neither is the token-cap
  question nor the sampling question; conflating them into the family
  predicate would change routing behavior this task has no evidence for.

### Moonshot (`tldw_chatbook/LLM_Calls/moonshot.py` + `model_capabilities.py`)

* `moonshot_model_supports_reasoning_effort` — true for the whole kimi
  series (`kimi` at a token boundary), replacing the exact-id `kimi-k3` pin.
  Wire-verified: 200s on kimi-k2.6, kimi-k2.7-code, kimi-latest. The value
  set gains `"medium"` (wire-verified on k3 and k2.6) and is renamed
  `_KIMI_REASONING_EFFORTS`; value validation itself is kept.
* `moonshot_model_rejects_sampling_params` — true for the **versioned** kimi
  family only (`kimi-k<major>`): those ids reject non-default sampling
  value-level, so the builder keeps omitting for them; `kimi-latest`, the
  legacy `moonshot-v1` family and unrecognised future ids now pass the
  caller's sampling values through for the server to adjudicate — replacing
  the frozen `startswith('moonshot-v1-')` allowlist that silently discarded
  user settings for everything else.
* `moonshot_model_requires_min_temperature_for_multiple_choices` — the
  documented v1-family n>1/temperature≥0.3 interplay rule, extracted as a
  predicate so the builder carries no model-name checks at all.

### Z.ai (`tldw_chatbook/LLM_Calls/zai.py` + `model_capabilities.py`)

* `zai_model_supports_reasoning_effort` — GLM family at or above the
  **(5, 2) version floor**, replacing the exact-id `glm-5.2` pin, so a
  `glm-5.3` / `glm-6` / `glm-5.2-air` release is not client-side-rejected on
  release day. No key exists, so this is a conservative liberalisation of a
  client-only gate, documented as not wire-verified; below-floor and
  unparsed ids keep the historical rejection.
* The unconditional `thinking={"type": "enabled", ...}` payload is **left
  unchanged** — the local reproduction shows no concrete breakage and no
  wire evidence exists (recorded in the task, per the no-evidence-no-change
  rule).

Design rules as established in the arc: immutable module-level predicates
*outside* the config-driven capability tables (pinned by the
survive-user-config test), boundary-safe family parsing (`kimiko-7b`,
`glm-5x`, `moonshot-v10-*` never parse), no legacy-family over-match.

### UI/docs alignment

`KIMI_K3_REASONING_EFFORT_SELECT_OPTIONS` in Settings gains `"medium"` so
the selector, the builder and the wire agree, and
`Docs/User_Guide/settings.md`'s Moonshot/Z.ai rows now describe the
family-wide effort acceptance and the versioned-Kimi sampler drop. The
remaining exact-id literals in Settings' selector scoping and the
response-side kimi-k3 pins are **TASK-19170** (§7).
