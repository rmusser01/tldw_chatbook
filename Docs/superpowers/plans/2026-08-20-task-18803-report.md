### Finding 3 — REPRODUCED client-side; wire boundary mapped

Local: the `startswith('moonshot-v1-')` allowlist at :527 silently drops all
five sampling params for kimi ids and keeps them for the legacy family:

```
FINDING3 kimi-k3        payload={"messages": [...], "model": "kimi-k3", "stream": false}
FINDING3 moonshot-v1-8k payload={..., "frequency_penalty": 0.1, "n": 1, "presence_penalty": 0.1, "temperature": 0.4, "top_p": 0.9}
```

Wire (real key, `api.moonshot.ai`): `GET /v1/models` → the API currently
serves **kimi-k2.5, kimi-k2.6, kimi-k2.7-code, kimi-k2.7-code-highspeed,
kimi-k3, kimi-latest, moonshot-v1-{8k,32k,128k}, moonshot-v1-auto and the
three `-vision-preview` variants**. Param acceptance:

* `kimi-k3` + temperature 0.4 (+top_p/n/penalties) → HTTP 400
  `{"message": "invalid temperature: only 1 is allowed for this model", "type": "invalid_request_error"}`
* `kimi-k2.6` + the same → HTTP 400, identical body; `kimi-k2.5` + temperature → identical 400
* `kimi-k3` + top_p 0.9 alone → HTTP 400 `"invalid top_p: only 0.95 is allowed for this model"`
* `kimi-k3` + presence/frequency penalties alone → HTTP 400 `"invalid presence_penalty: only 0 is allowed for this model"`
* `kimi-k3` + temperature **1** → HTTP 200 (`chatcmpl-6a872afa62f375d4129446c7`) — value-level, same shape as OpenAI's gpt-5 rule
* `kimi-latest` + the full five-param sampling set → **HTTP 200**
  (`chatcmpl-6a872b9816ceb0c0ae780b1e`, served as `kimi-latest-8k`)
* `moonshot-v1-8k` + temperature/top_p → HTTP 200 (`chatcmpl-6a872ac1fe949ba3ecc8b094`)

So the silent drop is wire-*correct in effect* for the versioned kimi family
(sending would 400) but wrong for `kimi-latest`, whose accepted params are
silently discarded today, and the allowlist mechanism remains the staleness
trap the task names.
