### Q2 — does a multi-turn continuation REQUIRE replaying `reasoning_content`?

**NO — the API accepts both and rejects neither.** Follow-up turn built from leg
A's actual response (`assistant` message with vs without the prior
`reasoning_content`), question "multiply that result by 2":

```
== C1_kimi-k2.6_with_replay HTTP 200
{"id":"chatcmpl-6a8768cbb5c429b466fbc43a","model":"kimi-k2.6","finish":"stop","content":"510",...}
== C2_kimi-k2.6_without_replay HTTP 200
{"id":"chatcmpl-6a8768ccb5c429b466fbc43c","model":"kimi-k2.6","finish":"stop","content":"510",...}
== C1_kimi-k3_with_replay HTTP 200
{"id":"chatcmpl-6a8768ce65640bfb1b0e4930","model":"kimi-k3","finish":"stop","content":"510",...}
== C2_kimi-k3_without_replay HTTP 200
{"id":"chatcmpl-6a8768d1a190ada43ce58fb8","model":"kimi-k3","finish":"stop","content":"510",...}
```

Correct answers both ways on both models; no protocol-level degradation
observed. Token-accounting nuance from `usage`: on the plain-turn replay,
`kimi-k3` **counts** the replayed reasoning (`prompt_tokens` 158 with vs 151
without, delta ≈ the 12-char replay) while `kimi-k2.6` **ignores** it
(`prompt_tokens` 48 both ways despite a 380-char replay) — so k2.6 plain-turn
replay is currently discarded server-side rather than consumed. In the
tool-call loop (below) k2.6 **does** consume it (156 vs 106).

### What the verdicts decide (fix directions, per site)

1. `provider_continuation.py` `_KIMI_K3_MODEL` no-calls-round gate: **real gap
   for the versioned kimi family** — k2.6/k2.5/k2.7-code turns DO return
   reasoning_content, so the k3-only preserved-thinking checkpoint shape must
   widen to the versioned family (new response-side predicate; `kimi-latest`
   excluded per probe A).
2. `_moonshot_continuation_candidate` / `_apply_continuations` k3 pins: widen
   per the same predicate. Replay is wire-safe (accepted everywhere, required
   nowhere), so extending k3-style preserved-thinking replay to the family
   cannot 400; not extending it silently drops recorded reasoning.
3. `console_chat_controller.py` `keep_all`: same predicate — resume history
   must retain the family's complete checkpoints, or the newly preserved
   reasoning is discarded on resume.
4. `settings_screen.py` `_model_profile_reasoning_effort_options`: derive from
   the 18803 REQUEST predicates (`moonshot_model_supports_reasoning_effort`,
   `zai_model_supports_reasoning_effort`) — the curated lists are the values
   the builders accept, so the UI list must follow the same family gates. The
   whole-series moonshot predicate (incl. `kimi-latest`) is correct HERE
   because the builder accepts `reasoning_effort` for the whole series
   (18803 wire probes: 200 on kimi-latest), even though `kimi-latest` returns
   no reasoning_content.

One durable-data constraint found during code-read (recorded before fixing):
pre-19170 versioned-kimi (non-k3) tool-loop checkpoints were persisted
**complete with all-calls rounds** (no final reasoning round). The parse rule
"a complete checkpoint must END with a no-calls reasoning round" therefore
cannot be widened from k3 to the family without invalidating stored data —
the fix keeps that must-end rule k3-pinned (its pipeline always appended),
accepts BOTH complete shapes for the rest of the family, and branches replay
on checkpoint SHAPE (final round has no calls) rather than on model id.
