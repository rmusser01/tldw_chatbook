# Console learned response rules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Console users learn a tested, Chat-scoped response rule with `/omfg <problem>` and receive bounded corrections that retain existing work.

**Architecture:** Keep immutable structured definitions and local bindings under the existing private SQLite owner. Application-owned services build and evaluate rules through the sensitive auxiliary gateway; the existing queue owner combines native corrections and genuine hook proposals in one admission transaction. Thin Console and Settings adapters expose one rules manager and project retained runtime state.

**Tech Stack:** Python >=3.12, Textual >=8.0.0,<9, existing Pydantic, SQLite, asyncio and provider adapters; no new dependency.

**Spec:** [Approved Console learned response rules](../specs/2026-10-03-console-response-rules-design.md)

**Status:** User accepted the plan subject to this requested audit and selected Native execution on 2026-10-03. Audit refinements are incorporated; Native implementation is underway in the managed Console response-rules worktree.

ADR required: yes

ADR path: [backlog/decisions/219-console-learned-response-rules.md](../../../backlog/decisions/219-console-learned-response-rules.md)

Reason: Local storage/recovery, scope ownership, completed-response assessment and native correction admission extend architectural boundaries. ADR-219 records the approved decision; no additional ADR is needed for direct implementation of it.

## Global Constraints

- Current Chat is the default; Workspace/profile-global promotion is explicit. Saved Chat rules are device-local; temporary Chat rules are memory-owned.
- Native structured rules only. No executable code, arbitrary regex, generated expression trees, hidden judge-provider substitution or authority supplied by model output.
- Completed user-facing Console text answers only. Preserve failed answers and completed tool actions; additional work uses normal permissions and the original task's scope.
- At most three candidate attempts, each one draft call and at most one model-validation batch. Whole learning operation: 120 seconds; each helper call: at most 30 seconds, shortened by remaining allowance.
- Completed-response assessment: 30 seconds total, shortened by remaining inherited limits. At most one model batch per response and 16 effective rules after scope resolution.
- Rule definition: at most 8 KiB serialized. Title: 120 characters. Semantic applicability: 1,024 UTF-8 bytes. Criteria and feedback: each 2,048 UTF-8 bytes. Synthetic fixture: 8 KiB.
- Deterministic predicate: one supported operation, at most 16 nonempty literal strings or eight headings, explicit boolean case flag, each literal/heading at most 256 UTF-8 bytes; reject unknown fields and nested trees.
- Helper output: at most 4,096 tokens, further limited by gateway/model/current automatic-work caps. Unsettled helper requests: four application-wide, one per Chat, through actual provider cleanup; zero adapter retries for native-rule helpers.
- Native feedback: at most 4 KiB UTF-8; combined native/hook body: at most 8 KiB including attribution. Refuse overflow without truncating, splitting or dropping rules.
- Two native correction turns per operation/chain, including initial `/omfg` repair, within shared three admitted continuation turns and 120 elapsed seconds. Current tighter limits and user priority remain effective.
- Rule state, response verdict and execution outcome remain independent. Unknown/missing evidence cannot establish success or absence. Synthetic examples cannot invent tool success.
- SQLite transactions never span provider calls. Acceptance and late callbacks revalidate exact source, branch, rule revisions and current authority. Cancelled caller tasks are not proof of provider cleanup.
- Local tables stay outside conversation metadata, sync, export and handoff. Ordinary diagnostics contain IDs/counts/reason codes, not complaints, fixtures, feedback or automatic instruction bodies. Restored records are inactive; startup never replays checks/corrections.
- Reuse canonical F9 Settings, declared Console view-hook slots, `$ds-*` tokens and component patterns. Keep actual Stop reachable during checking, including 80x24. No new permanent composer button or terminal-convention shortcut.
- Targeted tests only unless the user explicitly requests a full suite. Separate scripted transport tests, actual model behavior and visible native terminal evidence.

## Review Focus

1. A synchronous provider finishes after Stop or a profile switch: retain its capacity until physical completion, reject content and charge usage once to the original owner (Task 3).
2. A corrected answer refers to earlier tests after another file edit: historical results remain usable only for accurately qualified claims, not current-state success (Task 4).
3. Duplicate settlement callbacks arrive alongside Stop-hook feedback and a new user prompt: accept at most one follow-up, preserve vetoes and let the user prompt win (Tasks 6–7).
4. A temporary Chat is saved, forked, permanently deleted or imported from backup: rules/evidence follow the approved ownership policy without copying activation or replay authority (Task 2).
5. All rules are inapplicable, a semantic batch is unavailable, or rules conflict: avoid a false pass, retain valid deterministic results and stop repairs at the shared limits (Tasks 1, 4, 6 and 8).
