## Concrete ADR024 amendment draft: first-use key publication without SQLite custody

This amendment supersedes the unresolved-owner wording above. It is a narrow implementation of the authorized default-on/first-use/no-replacement contract, submitted for the parent's pre-code review. It does not ask the user for another feature or permission decision.

### Decision

1. Keep the existing secure OS-keyring adapter and exact 32-byte key validation. Key material stays only in secure keyring and process memory. First-use composition stays lazy. Existing records always refer to their original persisted key ID; no call provisions that ID after a failed load.
2. Split first-use into finite DB snapshot, key-only operation, finite DB publication. The snapshot captures the persisted identity and whether any fingerprint-bearing family exists. No operation-owned SQLite callback or connection stays live across the key-only wait. Use existing `run_owned_db_call` and its physical-retirement pattern only for the finite DB phases.
3. The repository retains at most one in-flight acquisition record: exact captured identity plus `concurrent.futures.Future` and `threading.Thread`. The key worker is a named daemon thread whose target receives only the provider, captured existing ID, optional fresh unpublished ID, and result future. It receives no repository, DB, app, screen, callback into those owners, or native lease. Its only completion effect is settling that future with a codec/key-ID/state result. A codec's existing redacted repr is preserved; no raw key bytes enter logs, files or argv.
4. The synchronous provider is physically uninterruptible. A caller cancelling its await does NOT cancel/retire that thread. Use a shielded async wrapper around the retained concurrent future so a departing waiter cannot cancel shared work. Cancellation propagates immediately from the key-wait phase; no DB publication is scheduled by a completion callback. A later live caller may await the same operation. Repository lifetime retains the exact thread/future until completion; completed work is not called retired until thread completion is observed. At application exit a still-blocked daemon key-only thread has no DB/UI/native resource to close and makes no late DB write. Report this limitation explicitly.
5. For a missing existing key, the worker may provision only a freshly generated, unpublished opaque ID, and only if its finite preflight found no fingerprint-bearing rows. This provision is outside SQLite. Existing-ID load and fresh-candidate provision both use the secure adapter. The worker returns the successfully loaded codec and its exact ID; it never publishes repository state.
6. A live uncancelled caller enters a short owned `transaction(immediate=True)`. Re-read the persisted identity and the fingerprint-bearing predicate under this lock. Adopt the candidate only if the full old identity is unchanged and no protected row now exists. Publish the new fingerprint_key_id by conditional UPDATE; change no profile/authority IDs. After commit publish identity and codec together under the repository's existing short `_key_lock`. No keyring operation or future wait occurs under `_key_lock` or a DB write transaction.
7. If rows appeared, do not adopt the new ID and do not overwrite/delete the old account. If another process already published an identity, retain the winner. Outside the transaction load the resulting original/winner key once, then perform a finite identity recheck before publishing the codec. If identity changes again, fail closed for this use and retry via the existing unexpected/unavailable readiness path on a later explicit use; do not spin/reprovision indefinitely.
8. An unused provisioned ID is an inert orphan, never referenced by DB records. Do not opportunistically delete it: completion/cancellation could be concurrent with successful publication. A crash before CAS can leave one orphan; a crash after CAS leaves a recoverable published key. Existing backup discovery follows only the DB's current citation key ID. This amendment deliberately accepts bounded-per-attempt inert keyring residue instead of adding a key garbage collector or risking deletion of a published key.
9. Existing transactional identity checks remain mandatory for all fingerprint-bearing writers. If B commits a protected row before A's CAS, A sees it and refuses. If A commits CAS first, B's stale identity check inside its write transaction rejects its prepared write. Two provisioners have distinct candidate IDs; only one CAS wins. No process-local lock is credited with cross-process safety.

### Concrete internal interfaces

Keep public `ensure_local_fingerprint_key() -> bool` for eager synchronous batch callers and `ensure_fingerprint_key_off_loop(repository: Any) -> None` for live async callers. Internally share the same three-phase algorithm; do not create another service or generic scheduler.

- A finite snapshot helper returns `(LocalCitationIdentityContext, bool)` for current identity and protected rows. It performs no key access.
- `_acquire_key_candidate(provider, identity, candidate_key_id: str | None)` is a key-only target returning `(CitationFingerprintCodec | None, CitationKeyState, str)`; result ID is exactly existing or fresh candidate. Pass only primitive identity values needed by the target; never a closure retaining repository state.
- A finite repository publication helper accepts the captured identity and completed candidate result, returning whether publication won or which currently persisted identity must be loaded. It performs no provider call, future wait, or async suspension.
- Retained operation tuple is repository-local; creation/publication uses `_key_lock` only for brief state updates. Double-checked readiness prevents two live async callers starting duplicate threads. No lock is held while awaiting the concurrent future or running SQLite.
- `ensure_local_fingerprint_key` cannot be called from a live finite-DB owner to wait on the key. It must reject pending acquisition if already inside a DB write transaction rather than provision there. Eager composition keeps blocking batch semantics; live callers move to the async readiness helper before finite DB work. Test eager compatibility and no-write-transaction enforcement.

### Live caller integration

- Shared staged/Automatic capture already awaits the async helper; retain it before builder creation and pre-acceptance, plus its owning request fences.
- `read_citation_counts` awaits readiness before creating the finite reader operation. A held key plus cancelled count view exits without opening reader DB work. A ready key plus held reader retains the original physical DB drain exactly. A late key completion only settles the retained future, so it cannot revive a closed footer.
- `_load_sources` awaits readiness before launching its finite hydration reader and checks its generation before entry/publication. `_hydrate_rows` no longer calls ensure. Apply existing finite DB ownership to the actual hydration callback instead of leaving an unowned `to_thread` connection.
- UI edit application and fork staging await readiness first, then revalidate original identities/fences. A shared pending guard makes bypassing sync callers refuse/rollback safely.
- Remove direct ensure calls added inside `CitationArtifactOwnershipCoordinator.reconcile_pending` and guarded `CitationLegacyMigrationService.migrate_idle_unit`. Existing async app startup units (`app.py::_reconcile_citation_artifact_ownership` and `_migrate_legacy_citations_idle_unit`) run their finite need check, retire it, await readiness, then issue the original bounded reconciliation/migration call. A fresh profile still skips key access if neither saved rows nor legacy sidecar need it. No general startup owner changes.

### Why this is the smallest safe owner

Existing `Audio/meeting_owner.py::_load_voiceprint` demonstrates the repository's key-only daemon-thread pattern; it cannot be copied wholesale because its timeout reports failure while a reader remains live and captures an owner. Here one explicit retained future/thread and a target with no database/UI reference provide the required lifetime split, without another process, new IPC, a worker pool, a timeout knob, or a general lifecycle registry. Existing finite DB owners continue doing the stronger physical-retirement work they already promise.

A contained child process is the rejected heavier alternative for this task: it would offer physical keyring termination, but requires secret IPC, launch/packaging and process-tree custody changes not needed to keep the UI/DB close finite. If the parent requires physical OS-keyring operation termination itself, this thread design does not satisfy that stronger requirement and must be replaced before code; the current repair brief requires bounded UI/DB closure and honest physical-lifetime accounting.

### Required proof additions

- Observe that held key load/provision has no `run_owned_db_call` ancestor, operation-owned DB connection, active transaction or view reference; an unrelated writer commits.
- Cancel the count host repeatedly while the key is held. Host drain completes without increasing existing bounds; thread/future remains explicitly in flight, no hydration/read callback starts. Release it and join actual thread completion in test cleanup; no DB publication or closed-view update occurs.
- With a ready key, keep the original count-host native-held test unchanged in semantics: repeated cancellation retains the actual connection/future/lease until physical reader return, then retires it before drain completes.
- Cancel the caller between key completion and CAS; no CAS. Cancel during issued finite CAS; drain the physical callback, observe actual committed result, suppress cancelled UI publication. Identity remains valid after reopen.
- Use independent processes and real SQLite for publication races, not only two futures under `_key_lock`. Retain an already-loaded stale repository writer and show transactional identity refusal after a winning CAS.
- Ensure at most one key-only thread per repository under concurrent readers/edits/capture. Genuine unavailable key outcomes keep current sticky-state semantics; do not implement .8's mid-session recovery product change inadvertently.
