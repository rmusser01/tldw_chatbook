# Project SQLite quota foundation — amendment proposal

Status: **CONDITIONAL, not a completed 1 GiB certificate.** Source basis: merged semantic worktree at dev merge 2070d9453bcf4f2cacb0b007cff5a41861aee188, with the reviewed project store/runtime/service/lifetime paths unchanged. This is a proposal for the controller's plan/task amendment. No product code, tests, runtime imports or database were changed or run.

## Decision and source evidence

Keep optional per-binding float32 vectors plus immutable membership/generation records in additive WorkspaceProjectIndexDB v4 tables, with bounded exact cosine streaming. Keep keyword available without embeddings and saved Library settings untouched. A generation owns its path/identity/hash/line metadata; it cannot point at mutable keyword chunk IDs. Staging, old Ready, obsolete generations, FTS, control and freelist all share the same SQLite main-file cap. This eliminates Chroma's independent allocator, but does not itself prove the binding-wide limit.

The source observes all regular-file lengths through binding_bytes (service.py:71) and serializes a keyword scan through an authority-scoped BindingLifetime (models.py:94; service.py:953,1011). Its keyword cap uses two main copies plus fixed 1 MiB (service.py:1089-1099); initial open and migration use analogous reserves (Workspace_Project_Index_DB.py:309-321; runtime.py:170-189). Cleanup uses size + size/64 + 65536 (service.py:627-650). These are policies, **not a proven general journal envelope**, and no keyword overrun was demonstrated. max_page_count caps main pages only. Status can insert control (Workspace_Project_Index_DB.py:324-361), authority reconciliation can update it (:421-435), and revoke writes before its later full-lifetime cleanup (service.py:544-562). Semantic inserts alone cannot receive a quota rule while these paths may allocate unreserved bytes.

The budget is owned **regular-file lengths**, not cluster allocation or directory metadata, matching progress.md's ruling. Let B = 1,073,741,824 bytes. binding_bytes must still reject aliases, unknown objects and inventory overflow. All other namespaces count even if obsolete. Never subtract freelist pages, deleted rows or expected checkpoint/prune savings.

## Required project-only allocation owner

Make one project_index admission helper, not a generic store-kernel quota layer. Every project-index mutation uses a stable binding-group allocation capability before sampling lengths and keeps it through native SQLite settlement. The current lifetime filename derives from data_authority_id, not binding_namespace (models.py:84-99), so two authority generations need not share that lock. A per-service mutex, current-generation lock alone, or sample-then-write cannot serialize all namespaces.

The existing cleanup-owner-v1.lock is binding-stable and already a native exclusive object (service.py:697-748, 765-825). Reuse it as the allocation gate if receipt handling and lock order can be safely changed. Acquire it before any authority-scoped lifetime, correcting the present inverse enrollment/start order; detached cleanup already takes receipt before generation lifetimes. Keep the authority-scoped lifetime as the inherited scanner/native-retirement capability. Full all-lifetime acquisition for Clear and receipt/CAS history remain. If reuse causes unavoidable lock inversion, use one new, known, counted binding-stable lock file in the closed cleanup inventory; that is still a project control file, not a persistence owner. All processes must use the same order, without waits/joins under registry fences.

The helper owns a finite operation and exact held SQLite connection. It freezes competing allocations, inventories the whole group, computes admission, sets and verifies the native cap, performs one approved write transaction, settles commit/rollback, and only then releases the gate. A keyword build completes first; its writer retires its native connection and allocation operation before semantic construction starts. Search/cosine reads retain existing read owners but cannot perform hidden control writes. Fresh-key status should return a model-only Off state; first durable control creation belongs to an admitted mutation. A stale authority read should fail closed or queue admitted reconciliation, never quietly write during search.

This gate certifies cooperating new-version processes. An older process writing the same group without this stable gate is a concrete cross-version gap. Before semantic write, prove prior authority-scoped lifetimes retired and inventory stable under the gate; otherwise refuse. That cannot stop an older binary creating a fresh authority-scoped writer later. A universal mixed-version hard guarantee needs an external OS/filesystem quota or an old-writer-compatible protocol, neither established here. The implementation plan must state this deployment boundary.

## Conservative per-transaction equation

Permit one attached main database only; no ATTACH, WAL, PERSIST/TRUNCATE/OFF/MEMORY journal, EXCLUSIVE locking, VACUUM, backup copy, disk temp output, raw connection or separate vector file. Require and verify DELETE journal, NORMAL locking, FULL or EXTRA synchronous, INCREMENTAL auto_vacuum, secure_delete=ON, foreign_keys=ON, temp_store=MEMORY and cache_spill=OFF on **each actual held connection before writes**. Do not silently change an existing WAL database to DELETE: transition/checkpoint is itself a write needing separate proved admission, otherwise refuse. Verify linked SQLite compile options do not force temp files despite temp_store=MEMORY. Statement/subjournals must be proved memory-only for the linked build or the operation is unsupported. SQL plans must avoid unbounded on-disk sorter/materialization. Require verified SQLite power-of-two page size P in [512,65536], and existing main length equal to page_count × P. Pin the linked SQLite implementation/version and pager sector upper bound S. Current upstream pager.c clamps S to 65536, but this report did not inspect the installed binary/source. Unsupported geometry/build/refused PRAGMA means no semantic write.

At each transaction start under the stable gate, let N be verified main page_count, M its regular-file length, O the sum of **all other** binding regular-file lengths except this main and its DELETE journal (including obsolete namespaces, lifetime files, receipt, sidecars and control), J0 the observed journal length, and E maximum additional separately permitted control-file growth (for example 4096 minus the current receipt length, or zero when none may grow). Refuse a preexisting nonempty/hot journal or WAL/SHM until separately admitted recovery/transition positively settles. With cache spills disabled and no explicit intermediate journal sync/header insertion, reserve:

    J_bound(N,P,S) = 2S + N(P+8)

SQLite's file format says an old page occurs at most once in one rollback journal and each record is page data plus two 4-byte fields. The first header is sector padded; 2S allows conservative end alignment. The format allows later aligned headers after spill, hence cache_spill=OFF and verification of the no-extra-header path are preconditions. If the linked pager can add headers in a permitted path, derive and add their finite count or refuse it. journal_size_limit truncates after a transaction and is not an admission control.

Choose integer C for max_page_count satisfying:

    C >= N
    O + E + C·P + max(J0, J_bound(N,P,S)) <= B

For example, C = floor((B - O - E - max(J0,J_bound))/P), with **no minimum-one-page clamp**. Refuse negative residual, C < N, or M > C·P. Set PRAGMA main.max_page_count=C on the same held connection before BEGIN; verify returned/read-back value is at most C and at least N. SQLite will not lower it below the current database size. Keep the cap through transaction settlement. Recompute N, O and J_bound for every subsequent transaction. This reserves a journal for rewriting **every old page**, covering FTS, secure deletion, schema/index/control changes, Ready CAS and incremental-vacuum page movement without estimating touched rows. New pages are limited by C; old and new generations consume the same allowance. Source input bytes and fixed 1 MiB are not substitutes for a page/journal bound.

This is a **conditional envelope**. Exact unresolved proof obligations: (1) linked pager sector maximum and absence/count of extra headers with spills off; (2) linked temp/statement-journal behavior and compile options; (3) every project write entrance using the gate and held cap, including mixed-version writers; (4) safe admission of existing hot-journal recovery; (5) indeterminate COMMIT and hot-journal settlement. The controller should not mark a hard cap certified until these are resolved. Near-capacity observed peaks are qualification evidence, not the analytical proof.

## Bounded mutations and settlement

Semantic insert/checkpoint accepts at most 32 members and at most 1 MiB encoded BLOB plus metadata **per transaction**, after dimension, float32 length, finite-value, path and manifest validation. A pathological 400-word chunk can exceed a byte limit; refuse oversized members before fetching/inserting. Use stable indexed keysets, with <=32 rows and <=1 MiB payload per source/query page enforced before materialization. No generation-wide fetchall or bulk SQL sort. Checkpoint and members land atomically. Ready pointer swaps in one CAS against scope, authority, separate semantic revision/settings/model/manifest and claim. Failure, pause, quota refusal and interrupted rebuild preserve older **compatible** Ready. Changed authority/settings/model may make it ineligible, but never delete it merely to finance staging. Current live candidate validation handles a later keyword-manifest advance.

Settings, claim, failure status, checkpoint, Ready CAS and receipt writes each require admission, even when small. A post-full failure-status write is not free: if its own admitted transaction cannot fit, report the refusal in memory and preserve previous durable state. For pruning and Clear, revoke eligibility durably under admission, drain readers/borrowers, then delete bounded keyset pages under repeated admission. Retain cleanup receipt and old Ready until compatible swap or full revoke. Reclaim_free_pages uses bounded incremental_vacuum steps, each admitted; deleted rows do not release physical bytes until shrink succeeds. v4/v3/v2 cleanup-only catalogs must be recognized without migration and delete semantic tables in FK-safe bounded order. Keep v1 quarantined, as current cleanup-only code does (Workspace_Project_Index_DB.py:249-264). Fresh v4 creation and v3→v4 DDL are separately admitted before first SQL write; migration failure must leave the prior exact catalog valid.

A project wrapper must own transaction settlement because SQLiteStoreKernel.transaction rolls back only exceptions **inside** its body and calls commit in the else arm (store_kernel.py:198-214). On body, COMMIT or SQLITE_FULL exception, inspect actual held connection.in_transaction, attempt rollback if needed, then verify native close and main/journal inventory while still holding the gate. Failed rollback/close, indeterminate COMMIT or hot journal retains the store/capability as unretired and blocks reuse; do not immediately write Partial/Error/receipt assuming rollback completed. A later admitted retry recovers and rereads durable CAS/claim. A successful COMMIT retains the gate until DELETE-journal finalization and native close settle. No generic kernel change is needed; project mutations must use this owner rather than bare transaction().

## Primary SQLite references

- [Temporary files and statement journals](https://www.sqlite.org/tempfiles.html): possible SQL temp/statement files; ATTACH adds a super-journal; VACUUM adds a temporary database.
- [PRAGMA max_page_count, cache_spill, temp_store and journal_mode](https://www.sqlite.org/pragma.html): page cap cannot go below current size, cache-spill control, MEMORY temp and compile override, post-commit journal_size_limit.

## SQLite 3.49.1 source-pinned refinement (2026-10-22)

Root's read-only `sqlite-runtime-probe.json` identifies the *tested Python runtime*, not every future deployment: SQLite 3.49.1, source ID `2025-02-18 13:38:58 873d4e274b4988d260ba8354a9718324a1c26187a4ab4c1cc0227c03d0f10e70`, `TEMP_STORE=1`, `MAX_PAGE_SIZE=65536`, `THREADSAFE=1`, and in-memory `temp_store=2`, `cache_spill=0`. [The official 3.49.1 release record](https://www.sqlite.org/releaselog/3_49_1.html) carries that exact source ID. Admit an on-disk writer only after checking its own linked `sqlite_version` and `sqlite_source_id` against this pin and its actual connection PRAGMAs; re-derive the proof for any different build. The probe does not qualify existing project files, the Windows VFS or a production connection by itself.

For *this source tag*, [pager.c](https://raw.githubusercontent.com/sqlite/sqlite/version-3.49.1/src/pager.c) defines `MAX_SECTOR_SIZE=0x10000` (lines 402-408), clamps `sqlite3SectorSize` to it (2544-2556), and uses `sectorSize` for `JOURNAL_HDR_SZ` and `pageSize+8` for `JOURNAL_PG_SZ` (739-749). `pager_open_journal` writes the first header at transaction start (5504-5559); `writeJournalHdr` writes a full sector (1372-1482). `syncJournal(pPager,1)`, which can append another header, is called by `pagerStress` (4387-4392); with the OFF spill flag, `pagerStress` returns before that call (4359-4368). The ordinary commit calls `syncJournal(pPager,0)` (6239), which cannot append a header (4122-4126). The main journal uses a bit-vector to avoid rewriting an already journaled old page (5737-5747); `dbOrigSize` is captured at BEGIN (5636-5640). Thus in the admitted single-main, no-spill, no-explicit-SAVEPOINT, no-ATTACH path, the one-header normal journal is at most `S + N*(P+8)` bytes, where `S<=65536`, and the proposal's `2S + N*(P+8)` has one sector of slack. It also covers `syncJournal`'s possible one-byte write at the *next aligned header offset* (4082-4087) when the prior journal is absent/zero: at worst this reaches less than `2S + N*(P+8)`. `writeSuperJournal` is a no-op for the single-main `zSuper=NULL` path (1624-1632); ATTACH remains forbidden. DELETE journal finalization removes the journal after settlement (1947-1992), subject to successful native operations.

This is a source-conditioned bound, not an unconditional SQLite format promise. In a rare `sqlite3PagerMovepage` read-error branch, pager.c clears an old page's in-journal bit and explicitly says a later write could journal that page twice (6842-6863). The project owner must stop issuing SQL on *any* SQLite/pager error, attempt rollback/close and quarantine ambiguity. It may not catch an error and keep mutating inside the same transaction. This is particularly relevant to `SQLITE_FULL` and I/O failures. `temp_store=MEMORY` is effective with the probed `TEMP_STORE=1` per [SQLite's temp-file rules](https://www.sqlite.org/tempfiles.html); this source tag's [global.c](https://raw.githubusercontent.com/sqlite/sqlite/version-3.49.1/src/global.c) says statement journals stay entirely in memory when `temp_store=MEMORY` (183-192), and [pager.c](https://raw.githubusercontent.com/sqlite/sqlite/version-3.49.1/src/pager.c) passes in-memory subjournaling through `sqlite3PagerBegin` (5582-5594). The actual writer must set/verify `temp_store=2` **before** statements that may allocate temporary structures, and disable cache spill/verify readback on that same connection. No SQLite guarantee is claimed for later versions or changed compile flags; FTS/SQL plans and any extension-created file must stay inside this permitted envelope or be rejected.

**Pre-open hot-journal rule.** Under the binding-stable allocation gate and before *any* SQLite connection touches a target namespace, inventory its main/journal/WAL/SHM and all regular files. A nonempty `-journal` (hot or merely ambiguous), any WAL/SHM, unexpected sidecar or unretired native handle makes that namespace unavailable for both read and write through this service. Do not call `PRAGMA` or a read query first: [SQLite documents automatic hot-journal recovery on next open](https://www.sqlite.org/tempfiles.html), which can write the main file before the cap is installed. Do not delete or rename the journal to make admission pass. Recovery, if supported later, needs a separately bounded admitted protocol; otherwise preserve it for operator action. A zero-byte journal can be counted as an existing regular file only after file identity/type and mode checks; avoid an implicit mode transition that writes. This rule applies to fresh v4 create, v3-to-v4 migration, and ordinary reopen. Existing cached native handles must retire positively before this preflight; the current migration constructor's open-before-admission order must be inverted in the project layer.

**Physical and logical settlement.** The project operation owns the exact native connection through `COMMIT` or rollback, native close, and post-settlement inventory, while retaining its allocation gate. On a body or commit exception, issue no further mutation; check `in_transaction` on the held connection, attempt rollback when active, and seek positive native close. If commit raised after SQLite already ended the transaction, the *logical* CAS outcome is unknown; after a positive close and no journal, release the physical gate only after inventory confirms the bound, then reread durable state in a fresh admitted operation before reporting success/failure or retrying. If rollback, finalization, native close, or inventory is ambiguous, retain the exact handle and gate as unretired/quarantined and block further project writes. A later process that lost the native lock at crash will see the journal and fail closed before open. Do not use the generic kernel's bare transaction context to settle this edge: its `commit()` occurs outside its body-exception rollback arm (`store_kernel.py:198-214`). No generic kernel change is needed.

**Cross-version limit.** Present `_AdmittedStoreFactory.retain` pins a verified data identity and refuses a different identity; `__call__` refuses a key whose authority differs from its current pin (`runtime.py:126-159,211-216`). Old v3 `WorkspaceProjectIndexDB` validates an exact v3 catalog after opening (`Workspace_Project_Index_DB.py:239-267`), so once an exact namespace is v4, an old constructor should reject it rather than migrate it backward. Before v4 DDL, the new owner should drain actual old native handles/lifetimes for that binding, not merely check names. Those facts narrow same-namespace stale-writer risk, but **do not prove a mixed-binary 1 GiB certificate**: an already-running old binary may retain a prior authority, or create/write a distinct v3 namespace in the same binding without taking the new binding-stable gate. The explicit supported analytical envelope is cooperating new-version processes after old-native retirement and no concurrent old-version writer. If deployment must tolerate concurrent old binaries, require an external quota or a compatible cross-version exclusion mechanism before promising the cap. These are deployment/plan decisions, not facts established by this source review.

## Per-SQL-unit allocation gate and lock order (final consistency check)

**Feasible with a required lifecycle refactor; no hard architecture blocker found in these seams.** Holding the binding allocation gate for the whole scan or semantic provider call would exclude keyword search while the provider waits. The gate should instead cover one finite SQLite unit: acquire it nonblocking, preflight target/all-group files **before first SQLite touch**, open or reuse a store object with no live native connection, set/verify cap and PRAGMAs, perform bounded read/write, settle transaction, positively `close_native()` on that same owning thread, inventory, then release the gate. Keep the job's authority pin, read slot, claim and authority-scoped native lifetime across the scan; these are job-retirement owners, not allocation reservations. Prepare/chunk/embed outside the gate; keyword commit finishes and its connection retires before embedding starts. A gate-busy unit can pause/retry/return busy without consuming a claim or opening SQLite. Never keep the gate across scanner IPC, provider wait, worker join, registry wait or an arbitrary filesystem capture.

The source supports this split. `scanner._scan_units` calls `frontier()`, then `admit_unit()`, waits for `_unit(...)` worker IPC, and only then calls synchronous `emit(unit)` (`scanner.py:412-461`); `service._write_bound` supplies all three callbacks, with SQL in frontier/admit/emit and the scan wait between admit and emit (`service.py:1072-1127`). `SQLiteStoreKernel.connection()` yields a thread-local held connection and does **not** close it at context exit (`store_kernel.py:145-164`), while `WorkspaceProjectIndexDB.close_native()` positively checks exact native retirement (`Workspace_Project_Index_DB.py:289-303`). The current writer already closes its management-thread connection before dispatch, then opens its own thread-local connection and closes it at completion (`service.py:1014-1032,1138-1154`). Thus the store *object* and native job owner can survive while each SQLite **handle** is retired between units. The current `emit` uses a separate cap-setting `connection()` followed by `commit_scan_unit`; those must become one admitted held-handle unit. `frontier`, `admit`, final status/pending checks and supervisor `retire_job`/`suspend_job` each need the same wrapping, with no handle escaping. A source-discovered semantic provider callback likewise cannot hold an open project connection while it waits.

**Lock discipline.** The job may already hold the authority-scoped lifetime when it tries the stable group gate; `BindingLifetime.acquire` is nonblocking on both Windows and POSIX (`lifetime.py:33-63,100-120`). This reverses the initial report's proposed universal gate-before-lifetime order, but avoids a cycle if *every* gate holder treats acquisition of any lifetime/receipt/native owner as try-only, unwinds and releases the gate on busy, and retries later without holding either lock. In particular, cleanup under the gate must return Pending on a live job lifetime, not wait for the scanner; `_stop_local` and supervisor `writer.join()` already exist (`service.py:536-543,1187-1194`) and must occur only after all allocation gates and SQLite handles have retired. `_enroll_cleanup_owner` currently takes receipt after current lifetime and may probe older lifetimes (`service.py:707-752`); keep those acquisitions nonblocking and move any receipt write/inventory into an admitted finite gate unit. The detached cleanup path already takes receipt then enumerates lifetimes (`service.py:799-825`); any busy acquisition must release receipt/gate and leave cleanup pending. Retained ambiguous native close remains a hard fail-closed quarantine, not a spin/retry that drops its owner.

**Seams that prevent a wrapper-only patch.** `WorkspaceProjectIndexDB.__init__` opens SQLite for page count/catalog validation and may create/migrate in a transaction (`Workspace_Project_Index_DB.py:212-276`); `_AdmittedStoreFactory.__call__` currently constructs before the caller can wrap a SQL method (`runtime.py:211-244`). Factory/constructor pre-open, migration and cleanup-only validation must therefore enter the group gate before construction, not merely wrap `commit_scan_unit`. `service.status` may suspend a stale Building claim (`service.py:246-341`), and `search` currently keeps one store connection across up to 100 candidate `live_reader` filesystem captures and repeated status queries (`service.py:380-490`). Search should retain its authority/read-slot ownership but close the native connection and release the gate between bounded SQL candidate/revalidation units and live file capture; use the existing manifest/authority checks on each reacquisition. `_revoke` currently joins local runs while a store object and possible thread-local connection are in scope (`service.py:536-562`); close/release before join, then reenter admitted units for clear/status. Supervisor retirement likewise cannot hold the gate while joining. These are concrete work items, but the present service already separates job lifetime from SQLite thread-local handle, so no generic kernel change is required.

The **only supported guarantee** is that all cooperating project SQLite opens, including reads and control/cleanup/migration, use this finite unit. A pre-open hot journal discovered by any unit fails closed before SQLite can replay it. Keyword search remains available during scanner/provider waits because no allocation gate or project SQLite handle is retained across those waits. A concurrent old binary that ignores the gate remains the previously stated deployment-boundary gap.

One lock-wait detail for the implementation plan: the project store currently calls `connect_private_sqlite(..., db_path)` without a `timeout` override (`store_kernel.py:91-115`), while that connector explicitly says its operation deadline does not bound SQLite's lock timeout (`private_sqlite.py:1917-1938`). For a strict try-only gate order, the project-specific connection opener must use SQLite `timeout=0` (or equivalently verify `busy_timeout=0` before lock-taking SQL); treat `SQLITE_BUSY` as an unwind/retry after native close and gate release. Do not rely on the connector's admission deadline as a SQLite lock-wait bound. This is a project-store override, not a generic kernel edit.
