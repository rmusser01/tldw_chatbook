# K4 unchanged-source permission and composition probe

Scope: source mapping only. Read `task-4-brief.md`, `AGENTS.md`, `Docs/Architecture/README.md`, `tool-catalog.md`, `console-file-authority.md`, the bounded production modules and immediate review/root-capture helpers, and directly relevant existing tests. No product or test edits and no test/runtime execution. The K1 search interfaces below are expectations from the K4 brief, not a claim that changing K3 source was inspected.

## 1. Local review and the effective `fs_read` floor

- `LocalToolProvider` takes `resolve_state`, `kill_switch`, `approval_callback`, `is_session_approved`, `persist_approval`, and `record_decision` callbacks (`Agents/local_tool_provider.py:771-802`). `_compose_local_provider` supplies them from `unified_mcp_service` under the synthetic `local:__local__` hub, with the selected profile captured per run (`Chat/console_chat_controller.py:15658-15688,15739-15784,15902-15917`). Its `_resolve_state` calls `gate_tool_test` or `gate_tool_test_for_profile` and then `persona_floor_state` (`:15859-15885`). This is the exact existing effective profile/persona floor that any search-as-read decision must reuse. `LocalToolSpec` explains that `reads` risk tags do not floor these local tools; the MCP resolver only floors `mutates`/`process` and the default local state is Ask (`Agents/local_tool_provider.py:453-504`). Adding a `reads` tag alone supplies no protection.
- `hub_tool_for(name)` builds the exact `HubTool` used by permission resolution and hashes its description plus input schema (`Agents/local_tool_provider.py:1209-1235`). `pending_gate_for` selects and validates the admitted root before `_resolve_pending_gate` creates an `MCPPendingCall` for Ask (`:1737-1814,1961-2067`). The normal batch hook clears this run's stamps, gathers those pending rows, calls the shared approval bridge once, and stamps name-keyed approvals while returning call-id refusals (`Chat/console_interrupt_rounds.py:5414-5459,5461-5555`; controller wrapper `Chat/console_chat_controller.py:2817-2835`). `invoke_detailed` reselects and guards the root, checks kill switch, re-resolves the permission verdict, and guards again before handler dispatch (`Agents/local_tool_provider.py:2079-2175,2228-2248`). Ask checks a run stamp, then session approval, then single-call callback; session/permanent decisions are persisted by the controller callback (`:3342-3409,3411-3489`; controller `:15762-15774`). Thus search Allowed cannot be treated as permission to read when effective `fs_read` is Deny or Ask.
- The supported ingredients for K4 are `provider.hub_tool_for("fs_read")` plus its injected effective resolver, the existing `MCPPendingCall`/batch review and ordinary `invoke_detailed` gate. Search must resolve both its own tool state and effective `fs_read` state at review and dispatch, take the narrower state, and preserve Ask as a per-call review, including persona/profile and later state changes. The existing hook only asks/stamps by the model tool's name; it does not expose a composed two-tool floor or two separate cards/stamps for one search call. `pending_gate_for("fs_read", search_args)` is not a drop-in: `fs_read` requires a path and its alias preflight/approval payload would describe the wrong operation. K4 therefore needs a small provider-owned composite gate path for search; when Ask comes from `fs_read`, a standing search grant or search session approval cannot satisfy it. Force an `approve_once`-only decision for that floor or equivalent per-call stamp, and recheck it at dispatch; do not write an `fs_read` or search standing grant from the derived floor. This is the material missing contract, not a need for a second permission store.
- Root-target preparation is a separate existing seam: `LocalToolProvider.path_targets` selects and guards the alias (`Agents/local_tool_provider.py:1363-1401`); local `fs_glob`/`fs_grep` report the admitted root as a directory, and local `fs_read` validates an exact path with exclusion context (`:1540-1616`). Search needs the same root directory preflight contract, so project-instruction preparation remains upstream of normal review as documented in `Docs/Architecture/console-file-authority.md:67-87,107-109`. The bridge passes `review_tool_calls` to `AgentService` (`Chat/console_agent_bridge.py:6049-6056,7925-7948`) and keeps run stamp scope (`:7435-7466`). Ordinary run budgets remain in `AgentConfig` and `ToolCatalogRegistry.timeout_for` (`:5083-5090`; provider `Agents/local_tool_provider.py:1289-1325`); K4's ten-hit/16-KiB limits must be lower.

## 2. Production root composition, exclusions, aliases and publication

- Live run calls `capture_execution_roots` and then `_compose_agent_request_providers` before handing the provider to the bridge (`Chat/console_chat_controller.py:26653-26700`). The immediate helper calls `capture_run_admitted_workspace_roots` synchronously (`Chat/console_automatic_submission.py:72-99`). `_compose_local_provider` is also synchronous and explicitly says it runs on the main loop before `asyncio.to_thread` starts the bridge (`Chat/console_chat_controller.py:15658-15664`; review helper repeats that in `Chat/console_interrupt_rounds.py:5440-5445`). This is why K3 must hand K4 a prepared immutable status projection: opening an index store or doing index I/O in this constructor would violate the existing hot path. There is no current off-thread index-snapshot producer in the bounded unchanged source.
- `capture_run_admitted_workspace_roots` returns an immutable tuple ordered by binding ID; Default/global or missing registry gives `()`; selected project-instruction binding narrows to only that selection (`Chat/console_chat_controller.py:1908-1962,1986-2041,2043-2173`). `RunAdmittedWorkspaceRoot` already carries workspace/binding ID, alias, root descriptor, locator fingerprint, root identity, `allow_write`, `guard`, exclusions callback, and optional executor/scope (`Agents/local_tool_provider.py:546-570`). Remote BLOCKED/MISSING roots are excluded at capture; admitted remote roots have a remote executor (`Chat/console_chat_controller.py:2007-2026,2045-2123`). The local/remote split is explicit and remote roots must never be passed to a laptop executor (`Agents/local_tool_provider.py:855-875,1046-1060`). Read-only roots are read-admitted; mutating specs are omitted if none may write and a mixed run refuses mutation on its read-only alias (`:914-947,1120-1134`; `Tests/Agents/test_local_tool_provider.py:263-295`). K4 can include read-only local Ready roots, but neither SSH nor Off/incompatible/unreadable scopes.
- Each root's `exclusions_provider` snapshots binding exclusion rels and accumulates a high-water union with live rels on every read. It yields absolute local `Path`s or relative typed `SensitiveExclusion`s for remote (`Chat/console_chat_controller.py:1584-1649,2053-2058,2124-2136`). Local `path_targets` merges these before card preflight (`Agents/local_tool_provider.py:1564-1589`); the executor receives the callback at per-alias construction (`:855-893`). K4's index authority must capture that exact admitted local root's accumulated absolute floor, convert to relative typed exclusions for K1, and union current restrictions before ranking. A newly removed exclusion must remain hidden to an older run. On an unknown conversion/authority, fail closed; do not take a global-workspace exclusion snapshot or unrestricted status totals.
- The provider sorts admitted aliases, builds per-alias specs, but chooses the first usable root's spec list as `representative_specs`; it injects the entire surviving alias list into each path schema (`Agents/local_tool_provider.py:803-818,855-947`). A conditional index spec on only the first root would be lost in first-root-Off/second-root-Ready; blindly copying it to all aliases would falsely advertise Off/SSH roots. The narrow insertion point is the per-alias `_path_specs_by_alias` construction plus a tool-specific eligible-alias subset at `selected_specs`/schema injection and `_select_admitted_root`/dispatch; advertise `fs_search_index` only when that subset is nonempty. Preserve `HubTool` definition-hash changes when the alias enum changes (`:1209-1235`; `Tests/Agents/test_local_tool_provider.py:205-223`), and retain optional alias for one root / required alias for multiple (`:929-941,1084-1114`; tests `:183-202,226-260`). Existing constructor explicitly rejects custom path specs combined with admitted roots (`:820-827`), so a K4 optional spec cannot be slipped through `specs=`.
- Bridge composition takes `local_provider.list_catalog()` into `local_names`, creates the final allow-list, applies persona advertising and per-run call caps (`Chat/console_agent_bridge.py:4652-4656,4700-4777`), then plugin/goal narrowing and workspace note from finally offered aliases (`:5072-5089,5120-5143`). `_advertised_path_root_aliases` uses final allowed tool names and provider aliases (`:4830-4864`). `PATH_AUTHORITY_TOOL_NAMES` currently identifies fs/git path tools (`Agents/local_tool_provider.py:339-358`); K4 must add the new read/path name to that set and update note eligibility only after final filtering. Existing note tests show aliases match actual `fs_list` reachability, selected binding narrowing, and no exploration promise when read tools are removed (`Tests/Chat/test_console_workspace_folder_note_contract.py:155-175,190-212,283-309`).

## 3. Minimal immutable K3-to-K4 consumer projection

A per-run immutable map keyed by binding ID/alias is sufficient. Each value needs (a) the binding/scope witness that can be matched to `RunAdmittedWorkspaceRoot.workspace_id`, `binding_id`, locator fingerprint/root identity and K1 generation; (b) a distinct Off versus usable Ready/Partial versus unavailable/incompatible status; and (c) immutable status/coverage data only if scoped coverage can later be filtered to the requesting run's admitted exclusions. No open connection, mutable store, global active-workspace authority, cached excerpt, or current-Settings aggregate counter belongs in this projection. `RunAdmittedWorkspaceRoot` already supplies the live guard/executor/exclusion callback, so the projection is an eligibility/status input, not a replacement authority. K4 consumes it after root capture, intersects exact local read-admitted aliases with matching usable entries, and supplies the resulting optional immutable map to `LocalToolProvider`. K1's `ProjectIndexSearchAuthority` is then issued per call from that selected root and its frozen-plus-live exclusion floor, as required by `task-4-brief.md`. If K3 cannot export a matching immutable generation/scope witness, K4 must treat the entry as unavailable rather than infer authority from a path string.

Material gap: the unchanged provider has no composite search-plus-`fs_read` review API and production composition has no off-thread index-snapshot input. Both are narrow K4/K3 interface work. Existing alias/schema and root/exclusion contracts are usable as mapped above. No test or native/runtime verification was performed for this probe.
## Follow-up: exact approve-once-only row and stamp seam

- `MCPPendingCall` already has `options: tuple[str, ...]`, `call_id`, `llm_name`, `server_key`, `tool_name`, `arguments`, `reason`, `effects`, `execution_policy`, `scope_notice`, `rationale`, and `description` (`Agents/mcp_tool_provider.py:349-396`). There is no separate per-call-only/floor boolean. The ordinary local `_resolve_pending_gate` sets `options=("approve_once", "deny")` only for a pair in `ALWAYS_ASK_TOOLS`; otherwise it offers session and permanent choices too (`Agents/local_tool_provider.py:2041-2067`). The latter set is currently just `("local:__local__", "character_save")` (`MCP/permission_store.py:118`), and the shared resolver forces that exact pair to Ask (`:2299-2309`). Adding `fs_search_index` there would force every search to Ask and is therefore not a conditional `fs_read` floor.
- The existing DTO option is enough for accurate presentation: `_build_approval_payload` copies `call.options` into each card row (`Chat/console_interrupt_rounds.py:5116-5168`); `ChatApprovalCard._options_for_row` filters the row's requested values and keeps only recognized options (`Widgets/Chat_Widgets/chat_approval_card.py:143-160`). A row with `("approve_once", "deny")` displays those choices, defaults to approve once, and its scope text says "This call only" (`:77-103,163-168`). Its per-call key is `call_id` first, then `llm_name` (`:1015-1036`); bulk actions choose only a row's legal values (`:1530-1575`); fast buttons can submit only approve once or deny (`:1662-1691`). No new DTO field or UI helper file is required for this presentation.
- The worker-side `request_mcp_approvals` accepts owner-agnostic `MCPPendingCall` rows, builds the payload, and returns an `ApprovalDecisions` map keyed by call ID or name with unresolved-key provenance (`Chat/console_interrupt_rounds.py:3744-3766,3823-3865,3945-3952,3988-4012`). `resolve_pending_approval` checks the round ID and copies submitted strings into the map, but does not validate them against each row's `options` (`:4616-4706`). The card is therefore the presentation constraint; the provider must remain the enforcement constraint.
- The local review hook passes `pending_gate_for` rows to that bridge, makes a name-keyed run stamp (the widest approved choice for that tool), and returns call-id-specific refusal verdicts for denied/unanswered siblings (`Chat/console_interrupt_rounds.py:5453-5555`). `apply_batch_decisions` stores `ApprovalStamp` by `(run_id, tool_name)` (`Agents/local_tool_provider.py:1671-1698`; `Agents/approval_provenance.py:68-100`). At actual dispatch `_verdict_for` checks the stamp/session cache/callback and calls `_persist_approval_safe` for `approve_session` or `always_allow`; the controller maps those to `approve_for_session` or `set_tool_state` (`Agents/local_tool_provider.py:3342-3489,3507-3516`; `Chat/console_chat_controller.py:15762-15774`). Existing `_every_call_decision` rewrites broad verdicts to `approve_once` only for static `ALWAYS_ASK_TOOLS` pairs (`Agents/local_tool_provider.py:3530-3543`). Thus a forged or stale broad decision must also be normalized at the new provider-owned conditional floor before it can reach persistence, including the single-call fallback. Re-resolve the effective `fs_read` floor at dispatch; a preexisting search session grant cannot suppress the card when `fs_read` is Ask.
- Narrow K4 path: in `Agents/local_tool_provider.py`, construct the search `MCPPendingCall` with existing `options=("approve_once", "deny")` whenever combined search/`fs_read` state is Ask because of `fs_read`; keep the row keyed to `fs_search_index` and the actual call ID, and normalize its dispatch verdict to one-call scope before `_persist_approval_safe`. The existing `build_local_review_hook`, `_build_approval_payload`, and `ChatApprovalCard` can pass and display that row unchanged. No extra production file is required solely for approval scope. `scope_notice` is available if the card needs to name the inherited `fs_read` reason, but no new field is necessary (`Agents/mcp_tool_provider.py:383-396`; `Chat/console_interrupt_rounds.py:5156-5162`).
## Final provenance check: exact call identity at dispatch

- `LocalToolProvider.invoke` and `invoke_detailed` accept only `(tool_id, args)`; `_invoke_detailed` currently calls `_verdict_for(name, args, current_run_id())`, and `_verdict_for` reads `_stamp_detail(run_id, name)` (`Agents/local_tool_provider.py:2071-2079,2228-2234,3342-3405`). The current batch stamp is keyed `(run_id, tool_name)`, not call ID (`:1671-1698`). A conditional `fs_read` Ask must not rely on that stamp: another same-name search call could consume it without its own exact review if the floor changes between review and dispatch.
- There IS a supported call-specific dispatch context. `run_context.current_tool_call_id()` reads a `ContextVar`, and `use_tool_call_id()` binds it for a block (`Agents/run_context.py:124-129,152-154,199-206`). `AgentService._make_invoke_tool` enters `use_run_actor(actor), use_tool_call_id(call.call_id)` around `registry.invoke_by_name` (`Agents/agent_service.py:3673-3712`); the registry then invokes the provider with the context intact (`Agents/tool_catalog.py:2309-2315,2390-2396`). The runtime gives every reviewed call a unique correlation ID, including synthesized IDs for originally idless calls, and passes that reviewed ID to the hook (`Agents/agent_runtime.py:2429-2470,2514-2523`). At dispatch it passes the same correlation through `invoke_tool_at_step`, and AgentService replaces an idless ToolCall's ID with that correlation before `_make_invoke_tool` binds it (`Agents/agent_runtime.py:3244-3256`; `Agents/agent_service.py:7754-7764,8786-8792`). Local provider already uses `current_tool_call_id()` for its separate instruction-promotion stamp (`Agents/local_tool_provider.py:2620-2627`), so no core runtime/catalog API is missing.
- The unresolved seam is review-stamp provenance. `build_local_review_hook` receives exact call IDs, gets the exact decisions, then collapses approved scopes by `row.llm_name` before `provider.apply_batch_decisions(run_id, stamps)` (`Chat/console_interrupt_rounds.py:5453-5503`). Its call-ID refusal verdicts stop denied/unanswered siblings in that batch (`:5511-5555`), but cannot constrain a later invocation that sees a changed `fs_read` floor and the surviving same-name approval stamp. K4 needs the narrow extra file `Chat/console_interrupt_rounds.py` along with `Agents/local_tool_provider.py`: pass exact row/decision provenance to a provider API that records/consumes a `(run_id, current_tool_call_id(), fs_search_index)` one-call stamp for the inherited-Ask case. Leave ordinary name-keyed tool approvals and existing UI/DTOs unchanged. An invocation without a matching call-specific stamp must resolve Ask through its single-call fallback or refuse; it must not consume a sibling's name stamp or persist a standing grant. This uses the existing `MCPPendingCall.call_id` and `current_tool_call_id()` seams, with no second permission mechanism.
Clarification: the preceding no-extra-file finding applies only to rendering approve-once-only options. Exact call-specific stamp provenance does require the narrow review-hook change identified in this final section.
