# K3 runtime contract source probe (2026-10-21)

Scope: bounded read of unchanged admission/profile and STT containment sources and selected existing tests. No code or tests were run. This is preflight advice, not proof of a K3 implementation.

## 1. Current data authority

**Admitted scope and pin.** `storage_admission.acquire_storage(path)` returns a `StorageLease` after startup permission, scope resolution, native hold, and post-hold revalidation (`storage_admission.py:1376-1517`). `StorageLease.execution_context(path)` compares the live lease's exact acquisition selection, including PID, bootstrap root, effective config selector, resolved selector and source (`:526-537, :579-595`). A qualified lease's `execution_scope()` returns the held bootstrap root and observed namespace group only while its hold is live (`:559-577`); `close()` retires the participation (`:597-619`). Startup keeps an acquisition in `_startups` through process exit (`:1520-1554`). `activation.execution_scope(..., retained=lease)` consumes that validated context and checks current activation for selected owners (`activation.py:183-221`). This is the supported authority pin, not an identity string.

**Profile/store identity pieces.** `bootstrap._binding` checks the selected config fingerprint, registry mapping, and enrolled roots (`bootstrap.py:473-498`); `storage_admission._scope` uses that binding and refuses paths outside its verified footprint (`storage_admission.py:1302-1373`). `profile_paths.effective_config_path()` selects the actual config selector (`profile_paths.py:25-29`). `config.get_user_data_dir()` yields the secured effective user data directory, but may take locks, restamp the path, or create/harden it (`config.py:11112-11193`), so it cannot run in the short registry fence. The isolated-profile `OpenedReceipt` carries profile ID, generation, operation ID, installation ID, config and data (`profile_open.py:20-30`); `profile_open._expected` gets these from `isolated_restore._launch_state` (`:45-57`), which checks catalog, committed journal, activation witness, and covered data locator (`isolated_restore.py:242-310`). Selection is once per fresh process (`isolated_restore.py:369-390`). For replacement, `activation.replacement_installation_id()` checks the current activation pair and committed/rolled-back journal and returns an installation ID (`activation.py:386-455`), while `isolated_restore.installation_client_id()` supplies that or the ordinary default (`isolated_restore.py:20-29`). Both verified queries are I/O-heavy and unsuitable inside a registry fence.

**Smallest suggested seam.** Outside the registry fence, after obtaining the actual execution lease and resolved data directory, a code-owned producer can form a frozen value such as `DataAuthority(selector, user_data_root, installation_id, activation_generation)`. For isolated launches, use the verified receipt/selection; for replacement/rollback, use the validated activation witness paired with the installation ID; for ordinary history, use the admitted selector and effective user data root with an explicit ordinary generation. Publish its opaque string only after successful admission and refresh it on actual profile selection, data-root change, or committed restore/rollback. Expose `current_data_authority: Callable[[], str]` as a bounded, no-I/O read of that published value; return/refuse on unknown or revoked state. The producer must maintain the lease/authority pin through the effect and publish a different token after a true mapping/generation change. Do not substitute `bootstrap._admission_epoch`: it is invalidated by writes to admission state (`bootstrap.py:89-124`) and is evidence-cache housekeeping. Do not substitute `config.get_runtime_config_generation()` or `get_runtime_config_snapshot`: the former changes on ordinary runtime reload (`config.py:7788-7789, :7955-7962`) and the latter takes locks/copies; a normal preference edit is explicitly allowed to retain bound startup (`Tests/Backup_Recovery/test_startup_readmission_continuity.py:99-115`).

**Gap and qualification.** There is no existing public, cheap, atomic getter containing *both* the admitted private data root/profile identity and restore activation generation. `StorageLease.execution_scope` omits selector/data/generation; `OpenedReceipt` applies only to explicit isolated profile opening; `replacement_installation_id` omits generation; `ProfileCatalog.resolve` explicitly grants no execution (`profile_catalog.py:69-73, :146-153`). A K3 seam must publish the verified tuple outside the fence, define its lifetime and transition ordering, and test stable identity across unrelated config save, changed identity across profile selection and replacement/rollback restore, and refusal on lost/changed admission. Existing patterns to extend: `Tests/Backup_Recovery/test_startup_readmission_continuity.py:99-129`, `test_profile_open.py:85-102`, `test_replacement.py:998`, and `test_activation.py:41,78`.

## 2. Writer and contained worker retirement

**Reusable native proof.** `STT/executor_process_tree.py` is a shared local-worker containment helper despite its directory. Child `enter_worker_containment()` calls `setsid()` on POSIX and reports PID/PGID (`:18-43`). The parent `ExecutorProcessTree` checks reported PID against its owned process (`:225-249`), requires a live process, verifies PGID == PID on POSIX, or creates a kill-on-close Windows Job Object and assigns the child before setting the admission event (`:265-299`). Job API uses `TerminateJobObject`, then `QueryInformationJobObject` until `ActiveProcesses == 0` (`:150-213`). `terminate_tree()` also joins the leader; POSIX signals then probes the **whole process group** until absent (`:301-428`). Failure to prove death quarantines (`:371-378, :407-409`). These guarantees are conditional on every descendant staying in the admitted job/group; an escaped child or externally created writer is outside them.

**Existing integration pattern.** STT child enters containment, sends its identity, and waits on admission before reading a command (`executor_worker.py:892-919`). Parent creates pipe/event/process, receives the typed bootstrap identity, admits containment, and stores process, pipe and tree before its reader starts (`executor.py:742-823`). Retirement detaches the exact generation/process/connection/tree tuple and requires `tree.terminate_tree` or `tree.close` to return proven before deleting scratch; failed proof makes executor unavailable (`:1032-1105`). Existing targeted tests cover admission order, dead leader with live descendants, query/timeout quarantine, POSIX group death and native descendant cleanup (`Tests/STT/test_executor_process_tree.py:310-357, :484-555, :685-797`).

**K3 seam needed.** Retain the exact native writer process object/handle and its claim before first output read, plus any contained worker tree identity and owned pipe/handle. A plain `subprocess.Popen` is not directly compatible with `ExecutorProcessTree`'s `is_alive()/join()` protocol (`executor_process_tree.py:276, :352, :398`); a narrow adapter or equivalent owned native proof is needed if that is K3's writer form. Child bootstrap must establish session/job containment and remain behind the parent admission gate before doing work, as in STT. For explicit restart Resume and configure/revoke -> new Enable, prepare retirement evidence outside all K1 locks: close/stop the exact old writer, establish native exit via retained process identity/handle, close/retire its pipe, prove the contained worker tree empty, and preserve an immutable proof bound to the exact old claim. The bounded `retirement_verifier` under the short registry fence should only inspect that prepared proof and claim identity, with no wait, filesystem access, or process polling. EOF, elapsed time, coroutine completion, or PID-only lookup do not prove the full tree retired. On failed/unknown native proof, keep the old claim unreplaceable and fail closed. Existing STT helper proves a *correctly admitted* tree; no source-visible K3 writer-to-claim retirement receipt or no-I/O verifier seam exists yet.

Source assumptions/cost: POSIX group absence uses bounded polling and Windows job emptiness queries; both are I/O/process work outside registry locks. `ExecutorProcessTree` owns one tree and marks unproven cleanup quarantined; it is not a generic process discovery service. The admission record/profile checks are materially more expensive than a constant-time registry callback.


## 3. Fresh-process Resume after parent death: correction and narrow options

The K3 writer is an **app-owned thread**, not the scanner child. The child is read-only. Therefore the app process's actual death ends that writer thread, but a fresh process has lost all in-memory thread/process/tree objects; it cannot turn a stale PID, elapsed time, or a saved `ExecutorProcessTree` flag into exact retirement proof. The STT dead-leader tests deliberately retain the original parent-owned tree handle and then terminate/query it (`Tests/STT/test_executor_process_tree.py:763-804`); they do **not** test a new process after the parent dies. POSIX `setsid()` permits a child/group to outlive its parent (`STT/executor_process_tree.py:34-43`); Windows kill-on-job-close is configured (`:150-167`), but a fresh process cannot query the lost job handle for `ActiveProcesses == 0` (`:194-213`).

**Normal shutdown:** an exact old-claim retirement receipt could be published durably only after the app writer thread has joined/stopped and the retained tree's `close()/terminate_tree()` positively proves the scanner and contained descendants dead. The existing STT live-parent sequence demonstrates the latter (`STT/executor.py:1032-1105`), and `app_shutdown.py:23-35` explains that even a graceful request can escalate to `os._exit`, skipping `finally` and `atexit`. Thus an intended shutdown or callback completion alone cannot create the receipt. This exact per-claim durable receipt/publication seam is not present in the inspected runtime.

**Abrupt parent death:** existing durable, OS-backed lock patterns can prove a narrower lifetime across processes. `Backup_Recovery/admission.py:1-6, :198-225, :583-752` uses persistent stable lock objects and retained native leases; `Utils/windows_files.py:1190-1215` supplies Windows `LockFileEx`. `Model_Artifacts/leases.py:134-189, :234-307` has a fail-closed keyed `portalocker` lease, with a real killed-process reacquisition test in `Tests/Model_Artifacts/test_provision_crash_recovery.py:1-14, :111-124, :223-225`. These establish that a fresh process can observe lock release by acquiring the *same stable lock*, not that it can identify a missing PID. The app's `Utils/instance_lock.py` is explicitly unusable for this proof: it is advisory, intentionally permits concurrent instances, and reports `acquired=True` on lock-mechanism failure (`:1-12, :45-57, :86-105`).

**Smallest defensible option to qualify:** bind the exact durable K1 claim/generation to stable private lock identity. Hold an app-owner lease continuously from before writer-thread dispatch until after actual thread retirement (or OS process death). Independently, make the read-only scanner child acquire and retain its own claim-keyed native lease before its first read, with parent admission gated on that handshake. After an abrupt app death, a fresh process can acquire both exact old-claim leases *outside* registry locks; a successful fail-closed exclusive acquisition proves the old app writer process/thread and the lock-holding child have ended. The child must be a single process with no descendants, or all contained descendants must participate in a provable shared lifetime; a lock released by only the leader cannot prove a surviving descendant is gone. A claimed normal-shutdown receipt can avoid reacquisition only if published after both positive retirements. Prepare immutable claim-bound proof outside the registry fence, then let `retirement_verifier` compare it under the fence. Lock backend failure, missing/changed claim-to-lock mapping, inherited descriptor ambiguity, or any possible untracked descendant must refuse Resume. This is a **new K3 seam and test obligation**, not a preexisting end-to-end contract.

Recommendation: treat fresh-process Resume as blocked on explicit durable per-claim ownership of both app writer and scanner lifetime (or an equally strong native ownership witness). Use the existing lease primitives as a pattern, not the advisory instance lock or PID check. Qualify at least graceful retirement, hard parent kill while child lives, and parent kill with child already exited on POSIX and Windows; verify no scan begins before its lease is held. No such end-to-end fresh-process worker-retirement test was found in the bounded sources.
