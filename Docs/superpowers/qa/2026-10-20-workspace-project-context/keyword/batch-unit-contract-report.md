# Bounded cross-directory scan/publication unit: frozen-contract assessment

Source-only assessment of frozen HEAD `7d79700e025310e43ab9537ee65bb1792cfe2ba1`. This is an alternative design map, not implementation, benchmark, or K5 review. The observed 12-file/13-directory timing and call counts were supplied by the parent; I did not reproduce or diagnose them.

## Contract ruling

The approved spec says, “Each bounded directory/read unit receives a freshly checked authority revision and exclusions from the parent before admission” ([spec, lines 252–255](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)); ADR-240 says, “Fresh authority is admitted per bounded directory/read unit, not frozen for the whole worker lifetime” ([ADR-240, lines 107–115](../../../../../backlog/decisions/240-workspace-project-context-and-folder-bound-index.md)). These phrases establish a *bounded unit* cadence, but do not unambiguously define whether one unit may contain multiple directories. The approved implementation plan **does** concretize the current unit as one directory page: `admit_unit(directory)` before “every bounded directory/page request, including continuation pages,” with revised exclusions acknowledged before new descent/reads ([plan, lines 156–181](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)). K1 defines a singular-directory `ScanPage` ([plan, lines 104–112](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)). The frozen implementation follows that narrower plan ([scanner, lines 291–345](../../../../../tldw_chatbook/Workspaces/project_index/scanner.py)).

Consequently, **one authority/job preflight for a multi-directory read unit is not an existing supported seam**. Interpreting the spec/ADR's “directory/read unit” to permit it requires an explicit plan/contract ruling or amendment; it cannot silently be presented as an equivalent refactor. Once that ruling is made, admission may be *per bounded read unit* only if the whole multi-directory unit is truly bounded, has one current parent-issued revision/exclusion floor before its first descent/read, and later publication passes its own current fence. If exact current plan language remains binding, retain `admit_unit(directory)` before each directory/page and batch **publication only**; that reduces commit/fence work but not read-preflight work. Neither option authorizes stale authority, longer registry locks, or bypassing active-job/store activation.

The separate publication requirement is explicitly per bounded batch: parent-owned transactional publication and authority/epoch recheck before each committed batch ([ADR-240, lines 107–115](../../../../../backlog/decisions/240-workspace-project-context-and-folder-bound-index.md)); each bounded publication compares live authority/exclusions, captured epoch and durable active-job ownership inside a short registry-then-store fence, held across neither scanning nor joins ([spec, lines 311–322](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)). Additions take effect before the next read-unit *and* publish admission; an in-flight result still needs final admission. Completed-directory receipts alone permit pruning; partial coverage stays truthful ([plan, lines 211–213](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md); [spec, lines 246–278](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)).

## Frozen representation and call path

* `ScanPage` has one `directory`, one identity/completion bit, at most 256 entries/captures, and an authority revision. It checks unique entry paths and capture/entry identity equality ([models, lines 188–250](../../../../../tldw_chatbook/Workspaces/project_index/models.py)). It cannot express several independently completed or empty directories.
* The closed, exact-field **index-only** v1 wire has one `Directory` request and one `Entries` / `DirectoryDone` pair. It rejects unknown fields/types, >256 entries per Entries frame, >2 reads, >4 MiB reported queue, >2 MiB total frame, duplicate JSON keys, and >64 KiB File parts ([protocol, lines 1–50, 93–211, 214–261](../../../../../tldw_chatbook/Tools/project_index_scan_protocol.py)). It is separate from the ordinary one-shot `WorkspaceToolExecutor` contract, which the approved plan preserves ([plan, line 286](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)).
* Scanner `scan` calls `admit_unit(directory)` on *every* page/continuation, sends the current revision/exclusions and verifies acknowledgement, then emits one `ScanPage`; it releases previous page data before the next admission ([scanner, lines 178–253, 254–367](../../../../../tldw_chatbook/Workspaces/project_index/scanner.py)). The worker similarly maintains one `os.scandir` iterator/current directory; it rejects switching directories while an iterator is open, performs up to 256 iterator steps per request, applies exclusions before metadata/read, checks root/descriptor identity, and sends one completion receipt ([worker, lines 309–523](../../../../../tldw_chatbook/Tools/project_index_scan_worker.py)). File captures use bounded descriptor reads and before/opened/after identity checks ([worker, lines 199–276](../../../../../tldw_chatbook/Tools/project_index_scan_worker.py)).
* The store has a durable `directories(path, identity, complete)` frontier, per-job `scan_pages(job_id,digest)`, and `scan_seen` ([store, lines 33–46](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)). `prepare_scan_page` chunks and hashes outside fences ([store, lines 61–92](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py); [plan, line 290](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)). `admit_job` validates Building/exact scope/revision/active owner in the activated private store ([store, lines 457–479](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)). `commit_scan_page` rechecks claim/authority, skips an exact digest replay, publishes entries/text/FTS/frontier, prunes only after a complete directory, and advances one manifest revision in one transaction ([store, lines 598–780](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)).
* Current service has a read-preflight `_admitted` + `admit_job`, then prepares and takes a second `_admitted` + store publication per page ([service, lines 719–757](../../../../../tldw_chatbook/Workspaces/project_index/service.py)). `_admitted` enters the registry fence and reconciles the store ([service, lines 153–163](../../../../../tldw_chatbook/Workspaces/project_index/service.py)). `claim_job` initializes the root frontier; Resume preserves it, whereas restart clears it ([store, lines 399–455, 500–559](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)).

## Smallest coherent cross-directory candidate, conditional on a contract ruling

A new immutable `ScanUnit` would contain one ordered tuple of `DirectoryReceipt(directory, identity, entries, complete/more/issues)`, aggregate captures, and one acknowledged authority revision. It needs **total** `sum(len(receipt.entries)) <= 256`, not 256 per receipt; unique paths globally; each entry an immediate child of its receipt; captures matching the exact file entry; and a separate **<=256 attempted directories/receipts** cap so empty directories cannot create unlimited work. Also cap raw iterator inspections and metadata bytes per unit; current worker limits 256 iterator steps and ~512 KiB metadata *per page* ([worker, lines 425–485](../../../../../tldw_chatbook/Tools/project_index_scan_worker.py)). Parent-before-child receipt order (or equivalent two-phase publish) is necessary: current directory-entry upsert resets a child to incomplete ([store, lines 669–687](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)). Empty directories need explicit completion receipts despite zero entries. Each directory must retain its independent complete/incomplete evidence and identity; a unit-level “complete” bit would be false proof.

K2 wire/worker/scanner would need a new, closed version or explicit new frame types, not a permissive v1 extension: one admitted Unit request/ack, directory-tagged bounded entry/receipt stream, one final unit terminator, aggregate count/resource checks on both ends, and continued root pin/exclusion validation at each descent. The worker must be able to descend newly discovered children *within* the same unit to batch deep chains; merely grouping already durable frontier rows cannot compress a single-file-per-directory chain because children become frontier rows only after the parent commits. Use iterative bounded pending work, never recursion or a tree-sized list. Preserve the index-only pipe and ordinary one-shot executor unchanged ([spec, lines 240–249](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md); [plan, lines 156–162, 286](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)).

K1/K3 would need `PreparedScanUnit` with all chunks/line mappings and a digest of the *whole ordered unit* (revision, directory identities/completion, entries, captures) computed before locking. One short current registry fence followed by one activated store transaction checks exact scope/epoch, live exclusion equality or the permitted narrowing rule, active owner token/job revision/state, and capacity before **any** receipt becomes visible. The transaction inserts all entries/captures/FTS and directory receipts, records the unit digest, and increments the manifest once. Record `scan_seen` for every discovered entry; prune missing immediate children only for each complete directory *after* its entire unit's seen set is durable. Incomplete/unreadable/wide-continuation directories retain old members. A duplicate digest must produce no second FTS/chunk/frontier side effects. A unit whose final fence fails is discarded whole. These are changes to DTO, wire validators, scanner flow, store publisher and service; they are not a call-site-only batching switch ([models, lines 223–250](../../../../../tldw_chatbook/Workspaces/project_index/models.py); [store, lines 61–92, 628–780](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)).

Resource limits remain aggregate: <=256 discovered entries **across** directories, <=256 attempted directories including empty ones, bounded raw `scandir` steps, <=2 simultaneous file reads, <=4 MiB retained/queued extracted text, <=1 MiB strict UTF-8 per file, <=2 MiB each frame, <=64 KiB text parts, 250k discovered entries/job and <=1 GiB cache-owned bytes including sidecars/temp. The current protocol reserves `2*MAX_FILE_BYTES + 64 KiB` scratch and sets retained page text to `4 MiB - reserve`, so a replacement must preserve the combined budget rather than treat 4 MiB as payload plus scratch ([protocol, lines 22–31](../../../../../tldw_chatbook/Tools/project_index_scan_protocol.py); [spec, lines 257–259, 272–278](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)). Retain cancellation/backpressure between short units, and never hold the registry fence over worker I/O or chunking ([spec, lines 311–322](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)).

## Durable frontier, replay and bounded memory

The current `frontier()` has an `attempted = set()` that grows with all visited directories, even though each database read is a 256-row keyset page ([service, lines 701–717](../../../../../tldw_chatbook/Workspaces/project_index/service.py)). That O(visited directories) set conflicts with the intent to avoid tree-sized memory ([spec, lines 246–250](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md)). A monotone path cursor alone is insufficient: a committed parent can insert a child whose path sorts *before* a prefetched/later cursor; resetting the cursor without attempt membership retries incomplete/unreadable directories indefinitely. A bounded candidate is a **single per-run attempt-generation marker on each durable directory row**, set transactionally on a terminal attempted receipt (complete or blocked/incomplete), with an indexed query for incomplete rows not attempted in this run. A new run/Resume uses a new generation, so incomplete rows are again eligible; unattempted newly inserted child rows remain eligible regardless of lexical path. Continuation `more=True` is not terminal: re-admit and continue the same directory with the worker iterator while alive; after crash/new run, re-enumerate it from the start. An attempt marker requires a store schema/version migration (or an equivalently bounded durable membership table); it should not become a generic scheduler. One should profile the eligible-frontier query at scale, as a naive `NOT EXISTS`/scan could trade memory growth for repeated full-table scans. `directories` is currently three columns under schema version 2 ([store, lines 33–46, 440–455](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)).

A unit may traverse a just-discovered child before its row exists durably only because the whole unit commits atomically. On cancellation, worker death, read issue, or failed final admission before commit, no unit receipt is published and the original incomplete frontier remains. After commit, completed receipts suppress requeue, incomplete terminal receipts remain visible as partial coverage, and newly discovered incomplete children are eligible. A replay after uncertain commit uses the unit digest; a changed re-enumeration uses the existing upsert/content-hash path while the frontier remains incomplete. No iterator offset is proof of completion ([spec, lines 246–251](../../../../../Docs/superpowers/specs/2026-10-20-workspace-aware-project-context-design.md); [store, lines 645–649, 669–780](../../../../../tldw_chatbook/DB/Workspace_Project_Index_DB.py)). Care is needed when a later parent replay resets a previously completed child; identity-compatible completed child state should be preserved or requeue handled truthfully, not silently marked complete.

## Expected call reduction and qualification

For the supplied 12-file/13-directory sample, root plus 13 directories are 14 page admissions/publications today: 14 `admit_job`, 14 commits, 28 registry fences, with writer idle 27.56 s and scanner 0.083 s (parent observation, **not** independently reproduced). If all 25 discovered entries, 14 directory receipts, inspected steps, and text fit a single bounded unit, the amended-contract candidate could use 1 read admission, 1 commit, and 2 registry fences. Publication-only batching under the present per-directory preflight would still use 14 read admissions but may use 1 commit: about 15 registry fences, assuming one final publication fence. These are call counts, not latency predictions. For a hypothetical 20k files plus 20k directories, the entry ceiling alone gives `ceil(40,000/256)=157` units as a theoretical floor; text, raw inspection, receipt, exclusion, quota and cancellation boundaries can raise it substantially. A 20k-directory-only chain has an entry-count floor of 79 units plus the separate receipt cap. No timing claim follows from source.

Necessary targeted contract tests, if this alternative is authorized: total-entry and empty-directory attempt caps; deep and wide trees; parent/child completion and stale deletion; excluded subtree before metadata/read; cross-process narrowing between units and revocation between read and publish; removal never widening the running floor; continuation/worker crash/Resume/duplicate digest and partial replay; cancellation/physical worker exit; frame/source-buffer limits including escape-heavy 1 MiB file; quota rollback; durable frontier paths inserted behind prior keysets; no tree-sized parent memory; unchanged ordinary executor frames. Existing scanner barrier tests assume per-directory acknowledgements and must be rewritten around the chosen unit boundary ([plan, lines 173–187, 211–213](../../../../../Docs/superpowers/plans/2026-10-20-workspace-project-keyword-index.md)). No tests were run here.

**Unknown:** whether project owners intend “bounded directory/read unit” to permit several directory descents after one preflight. The frozen plan says no for its concrete K2 interface, so a read-admission reduction requires an explicit contract change and fresh validation. The source alone does not establish the observed SQLite delay's root cause or the candidate's runtime benefit.
