# K5 unchanged UI integration contract probe

Evidence is source-only. I read the K5 brief, named unchanged UI source and direct navigation/controller/test/CSS dependencies, plus `backlog/docs/design-language.md`, `backlog/docs/component-patterns.md`, and the relevant UI architecture documents. I did not inspect changing `project_index` source or run tests.

## Settings per-binding seam

- `tldw_chatbook/UI/Screens/settings_screen.py:21871-22015` renders Workspaces through `_render_workspaces_detail` -> selected workspace card -> `_render_workspace_folder_bindings(registry, record.workspace_id)`. Default and archived workspaces return before folder rows (21957-21986). Selection is `_settings_selected_workspace_id` (21939), set by the row handler at 27335-27349.
- `_render_workspace_folder_bindings` is at 22291-22387. It calls `registry.list_folder_bindings(workspace_id)` at 22311, then has exact `binding.binding_id`, `binding.locator`, access and runtime readiness at 22312-22339. The current toggle/remove buttons stash `binding_id` on the widget (22323-22337), rather than parsing it in handlers. The new card can be yielded once per local-folder binding inside this loop, where row identity and local-only gating already exist. SSH rows are a separate renderer at 22446 onward, so SSH should show unsupported copy there only if desired; it must not acquire local indexing controls.
- The Settings workbench is immediate-apply, not a Save/Revert category (`Tests/UI/test_settings_workspaces_category.py:43-57`). `_refresh_settings_workspaces_pane` at 22706-22740 uses `mutate_reactive(active_category)` to recompose category `SettingsRegion` children, replacing row/card widgets. `SettingsRegion` explains this lifecycle at 3147-3165; the screen's `on_unmount` starts at 5142. A row card's off-thread callback therefore needs its own mounted/visit token plus exact binding/scope/job/epoch checks before display, even if service CAS prevents stale effects. No service I/O belongs in card constructor/compose. The existing SSH advisory probe (`settings_screen.py:22553-22589`) is a limited example of `@work(thread=True)` + `app.call_from_thread` and checking attachment/selected workspace on landing; its single exclusive `settings-ssh-probe` group would coalesce unrelated rows, so it is not a safe worker group to reuse for multiple index cards.
- Scope for the K3 handoff must be carried exactly: the row currently has a binding ID and locator, while K5's stated `ProjectIndexBindingCard(binding_id: str)` alone is insufficient to make a call requiring `project_index_key(app, workspace_id, binding_id, root)` and expected scope. The card needs an immutable row authority snapshot (at least workspace ID/root or an already captured scope) passed as data, or a background capture keyed by the ID that validates the selected binding before actions. Neither a current-workspace guess nor synchronous service lookup in compose meets the brief. This is a narrow constructor/worker handoff within the planned card and `settings_screen.py`, not a new service boundary.
- `settings_screen.py:5326-5375` already refreshes the Workspaces pane on screen resume; `_select_category` clears workspace selection on leaving Workspaces (26012-26017). A status refresh should preserve that lifecycle and avoid republishing into a replaced pane.

## Console modal and navigation

- `tldw_chatbook/Widgets/Console/console_workspace_files_modal.py:123-133` defines the frozen presentation-safe `WorkspaceFilesBinding`: binding ID, label, optional `BindingScope`, availability/access copy, exclusions. `BindingScope` carries workspace ID, binding ID, fingerprint, canonical root, device/inode (`tldw_chatbook/Workspaces/file_inspector.py:129-138`). The modal receives the inspected workspace ID and a captured binding tuple at 272-313; it chooses the first available binding. Binding buttons are index-addressed at 355-362, but `_select_binding` resolves back to `binding.binding_id` and increments `_binding_generation` at 1056-1083. Index status must key to that exact selected binding; `scope=None` is a real unavailable state and cannot be treated as ready.
- The Console owner already captures bindings off the event loop in `tldw_chatbook/UI/Console_Modules/workspace.py:1179-1224,1273-1337`, then opens this modal at 1104-1134. The modal has no index-status field or injected status service. It can request an immutable status in a background operation using its captured workspace/binding/scope, with unavailability copy when scope is absent. If K3 needs root identity for an unavailable binding, the captured DTO lacks it; the smallest extra production scope is `UI/Console_Modules/workspace.py` to enrich the snapshot, rather than reading the registry in modal compose.
- Modal background I/O pattern is `_OperationLane`: `asyncio.to_thread(request.operation)`, then a guarded publish (`console_workspace_files_modal.py:187-251`). Existing guards `_can_publish` at 491-500 and `_can_publish_directory` at 584-605 check mount, generation and selected binding; `_teardown`/on_unmount close lanes and fence updates at 1240-1267. A new status request needs binding-specific generation/epoch, not only modal-wide `_generation`, because selection can change while a request runs.
- The modal currently has Back, Details, Refresh actions at 379-394. Details only updates local copy (`console_workspace_files_modal.py:1212-1222`); there is no Settings navigation action. Safe dismissal is `request_safe_cancel` -> `_perform_safe_cancel` -> `dismiss_safe_once` and visit callback (`1237-1267`). The Console owner currently supplies `on_visit_closed`, not `on_back_to_console` (`workspace.py:1206-1224`). Route after safe dismissal using `NavigateToScreen(TAB_SETTINGS, screen_context=...)` through the app/Console owner, rather than posting navigation while the modal still owns the stack. The production app handles this message off the event pump (`app.py:2915-2945`), and Console already uses the route for Settings (`chat_screen.py:2197-2206`).
- `SettingsScreen.apply_navigation_context` currently accepts category at 24430-24480. A Workspaces context only selects the category; it does not set `_settings_selected_workspace_id` or focus a binding row. For “Settings reachable from Console” a category-only link is supported. For an exact selected binding link, the planned `settings_screen.py` integration must narrowly validate workspace/binding IDs, select the workspace and use `_after_category_panes` (4922-4945) before focusing the row. No change to the app navigation API is needed. `NavigateToScreen` accepts a context dict at `main_navigation.py:153-174`.

## Mounted tests and visual constraints

- Existing mounted Settings harness: `Tests/UI/test_settings_workspaces_category.py:43-57,62-110` uses `DestinationHarness`/`_build_test_app`, opens Workspaces, selects a workspace by button, and waits for mounted selectors. `Tests/UI/test_settings_workspace_folder_journeys.py:15-80,105-117,148-196` exercises dark/light, 80x24/170x48, keyboard focus, painted feedback, and row replacement. This is the closest precedent for the proposed stale-callback and readable-result tests.
- Existing modal harness: `Tests/UI/test_console_workspace_files_modal.py:45-124` uses a narrow service fake and `App.run_test`; `Tests/UI/test_console_workspace_files_integration.py:43-47,107-118,121-141,303-330,461-482` mounts the actual Console with shipped CSS and fingerprints active workspace, draft, pending approval, etc. Its `_wait_for_files_modal` and Console fingerprint are useful for asserting the new Settings route does not activate another workspace or mutate Console state.
- `backlog/docs/component-patterns.md:207-217` and `tldw_chatbook/css/features/_settings.tcss:410-415,963-970,1125-1132` provide token-backed `settings-detail-row`, `settings-input-row`, `settings-status-row`, `settings-focus-card` patterns. Readable error copy uses the existing `$ds-status-error-readable` token (`css/core/_variables.tcss:63`). Modal status/action CSS is in `css/features/_console.tcss:1847-1894`; both status and action strip have fixed heights and status hides overflow. Compact/short constraints at 1980-2020 mean an extra action/status could clip at the 80x24 minimum. First try existing rows/tokens; if a measured mounted check proves a style change necessary, `css/features/_console.tcss` plus bundle rebuild is the smallest extra stylesheet scope. Do not edit the generated bundle directly.

Material gaps: (1) exact Settings binding deep-link is not currently implemented (category-only route exists); (2) card's binding-ID-only constructor must receive or capture immutable authority data off-thread before exact-scope K3 calls; (3) Console captured DTO has no status and no root when scope is unavailable, so a status projection may need the owner file `UI/Console_Modules/workspace.py`; (4) narrow modal layout may require source CSS after mounted evidence. No tests were run and no product files were changed.
