## Token, reasoning, and content interpretations

- The currently saved disposable config has `api_settings.llama_cpp.max_tokens = 512`, `streaming = true`, and `console.reasoning_history = "auto"`. These are current configuration facts, not preserved exact kwargs for each failed request. UI selection can override them. The latest failures' raw `max_tokens`, input estimate, server prompt-token count, completion-token count and finish reason are unavailable.
- Schema loading fits the whole projected next request (`AgentService.load_schemas` and `_project_instruction_request_fits:2500`). Gateway preparation counts schemas/messages, clamps output only to a known provider output cap, and refuses known overflow before dispatch (`console_prepared_request.py:1082`, `:1651`; gateway`:5193`). Adding restore does not itself set output tokens tozero. Successful load means the app estimator admitted it, not that the real server's context capacity was proved: the app log explicitly says the Gemma model has no catalog capability information, and gateway limits may remain unverified.
- A low output budget exhausted entirely in reasoning is a concrete compatible explanation, not a diagnosis. `_structured_local_thinking` (`gateway:2174`) reads llama.cpp `reasoning_content`; `capture_structured` (`:5871`) queues it as thinking and disables the inline splitter, but `emitted_content` is set only by visible text. The no-content native guard at6138 does not count these reasoning events as a final answer. The same outcome can occur with a completed start-anchored `<think>...</think>` block and no visible answer when disposition is displayable (`:6026`, `:6095`). An incomplete thinking block can instead raise `ProviderThinkingCaptureError` at6115.
- `chat_defaults.strip_thinking_tags = true` exists in the scratch config, but its stripping code is in the separate `chat()` consumer (`Chat_Functions.py:1478`, `:2056`), not this Console `chat_api_call` → generic gateway path. Do not attribute the latest failure to that setting. Console-specific structured reasoning and inline splitting are relevant instead.
- `_ToolCallAccumulator` (`gateway:2311`) recognizes OpenAI `choices[0].message.tool_calls` and streaming `choices[0].delta.tool_calls`; it retains only entries with a nonempty function name. A missing name, different tool-call envelope, invalid SSE JSON, or reasoning-only completion can yield no usable native call. `_content_from_provider_mapping` (`:6981`) accepts string content/text, not arbitrary content arrays. These are possible interpretation failures whose actual occurrence is unproved.
- The llama.cpp generic streaming generator (`LLM_API_Calls_Local.py:333`) yields SSE strings and has no `terminal_turn`. `_provider_turn_metadata` (`gateway:2278`) obtains finish reason only from such a `terminal_turn`, so that generic local path does not deliver the SSE finish reason as typed terminal metadata. Existing safe steps cannot show whether the rejected response ended with `length`, `stop`, a tool finish, or an error.
