## Important findings

1. **Retry and Regenerate of a Continue response wrap historical input instead of the continuation instruction.** `Chat/console_chat_controller.py:24656–24659` falls back to the most recent canonical user when no explicit mix-in anchor is supplied. Initial Continue assigns and passes a synthetic anchor (`:18694–18699`, `:18728`), but `_retry_message_body` and `regenerate_message` call `_ensure_user_continuation_instruction` without assigning or passing that new instruction's identity (`:18508`, `:18861`). For Send(user U) → completed assistant A → Continue → failed assistant B → Retry(B), initial Continue sends `[U, A, mixin + Continue]`, while Retry sends `[mixin + U, A, Continue]`. Regenerate(B) makes the same placement error with current choices. This changes semantics and marks historical U as mandatory active input. Factor the synthetic-current-user anchor into the shared continuation construction and pass it through Retry and Regenerate as well. Add controller adapter tests for Continue → failed Retry and Continue → Regenerate, checking that U remains clean and only the synthetic current instruction is wrapped, including capture-off restart.

2. **The new witness grants the replacement exception to ordinary first attempts.** `Chat/console_trace_service.py:3353–3370` checks valid latest ownership, but never establishes that the operational attempt is an accepted replacement of the traced attempt. Every ordinary initial send now has a qualifying record (`Chat/console_native_commit.py:609–623`). Runtime supplies the witness whenever a transformed source and assistant revision exist (`Chat/console_trace_runtime.py:631–641`); its mere presence then bypasses the ordinary response link's `verified_equal`/revision checks (`Chat/console_trace_service.py:3721–3748`). A completed original response edited in place can retain its original valid marker and complete state while acquiring a new latest semantic revision. The helper accepts that original attempt as a replacement, even though no Retry/Regenerate occurred. Focused edit-path check confirms the marker survives and `clear_generation_provenance` clears only thinking and continuation data, not complete lifecycle state (`Chat/console_chat_store.py:12649–12726`; `Chat/chat_persistence_service.py:3458–3469`). This exceeds the explicit ruling that the exception is solely for an accepted replacement and ordinary response-link equality remains. Require a verified relation to the replaced traced attempt/response before issuing or accepting this witness, and bind the witness to the exact result revision settled by that replacement. Merely requiring `retry_of_attempt_id` or a different sibling is insufficient: an actual Retry/Regenerate result can also be edited afterward while retaining its marker and complete state, and the current latest-revision check then accepts the edited revision. Add negative tests for an ordinary transformed first attempt with missing/unequal response link, an in-place edited first response, and an edited accepted replacement; none may obtain authority from a surviving operational marker. Positive tests should retain genuine unedited accepted replacement restoration with every original policy/origin/range/descriptor check intact.
