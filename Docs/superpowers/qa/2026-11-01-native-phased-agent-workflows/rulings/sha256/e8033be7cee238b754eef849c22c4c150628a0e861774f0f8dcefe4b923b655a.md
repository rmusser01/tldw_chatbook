## Important finding

### I1 — Passive accepted MCP context survives revocation of its actual MCP grant

**References:** `tldw_chatbook/Agents/hooks_v2/mcp_executor.py:253`; `tldw_chatbook/Agents/hooks_v2/native_commands.py:282`; `Tests/Chat/test_native_v2_mcp_events.py:1132`.

`MCPHookSelection.check_memory()` compares the captured provider entry, schema, maximum and source object identities, but it does not compare the current MCP permission state. `set_tool_state(..., "deny")` updates the live permission source without replacing that captured catalog tuple. Once native drain is positive, `_CommandEvent.check_memory()` therefore accepts the old selection after registration retirement. The worker's actual permission checker exists (`tldw_chatbook/Agents/mcp_tool_provider.py:1784`), but it is used only by the transient result callback (`tldw_chatbook/Agents/hooks_v2/mcp_executor.py:704`), which `_run` clears at `:867`.

The final permission regression revokes the **hook grant**, not the MCP tool grant. It therefore does not cover this original permission boundary. In one focused reviewer probe using the real configured SessionStart path, actual SQLite/runtime, saved hook approval and connected stdio MCP peer:

1. First Send accepted the hook's runtime context; original custody retired with `_drain_outcome is True`.
2. The real original input registration was retired through `retire_context`.
3. The actual MCP service changed the original tool grant to `deny`; `gate_tool_test(case.tool).state` confirmed `deny`.
4. `source.check_memory()` did not refuse, and a second Send remained accepted. There was exactly one MCP request, so this is stale accepted-context authorization, not a repeated tool dispatch.

**Observed failure:** `task-8d2b2b2-reviewer-permission-configured.log:71`: `{'live_mcp_permission': 'deny', 'second_send_accepted': True, 'source_refused': False}`. The retained probe is `task_8d2b2b2_reviewer_permission_probe.py:52`; result: **1 failed in 5.41s**.

This violates the accepted qualification that passive reuse skips only the spent registration while preserving original permission/source revocation (`task-8d2b-rulings.md:37`). A revoked tool-derived context can continue to authorize later input. Retain the original permission provenance and revalidate its live revocation state for passive result use; keep effectful/read callbacks outside bookkeeping locks and retain a pure final publication check. Add this actual MCP-grant regression alongside the saved-hook-grant test. Do not restore dispatch authority or introduce a caller-selected passive mode.
