### I1. Clean no-run closure permanently retains unused payload slots

- **Location:** `tldw_chatbook/DB/automatic_work.py:1525` and `:1533`; the equivalent proven no-row launch-failure closure is `tldw_chatbook/Agents/agent_service.py:5704`.
- **Problem:** Preparation reserves 131072 bytes per task in `workflow_payload_reservations` (`tldw_chatbook/DB/automatic_work.py:2160`). Clean recovery closes unlaunched attempts and releases their automatic generation/child reservations, but never releases/tombstones their unused payload reservations. The no-row failure path likewise closes the task while leaving this capacity reserved. `WorkflowRunsStore._capacity` counts every payload reservation whose state is not `removed` (`tldw_chatbook/DB/workflow_runs.py:71`). Thus even a prepared phase that performed no work retains all of its result capacity after the code declares it clean. A 12-task prepared phase retains 1.5 MiB without any result; subsequent fresh approvals/replans or other workflows can hit the 4-MiB/128-MiB bounds prematurely.
- **Why this blocks:** The explicit clean-recovery ruling requires releasing unused capacity while preserving completed results and spent accounting. This is a concrete violation of that ruling, not a request to refund consumed work or implement Task 8 continuation early.
- **Smallest fix:** In the same conclusive closure transaction, release the payload slots belonging only to positively closed, unlaunched/no-run attempts. Preserve the existing tombstone/history invariants and archive validation, and leave launched, published and uncertain evidence untouched. Cover prepared recovery, partial quiescence with one real published result and one unused task, and proven no-row launch failure. Assert payload capacity, not only the automatic-work generation/child counters.
