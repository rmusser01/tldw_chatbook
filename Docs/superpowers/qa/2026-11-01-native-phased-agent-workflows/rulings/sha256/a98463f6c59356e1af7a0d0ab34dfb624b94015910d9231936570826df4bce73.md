## Must fix

### 1. [P2 / Important] Planning can leave an unrelated ordinary completion pending after its slot is released

**Locations on final HEAD:**

- `tldw_chatbook/Chat/console_workflow_preparation.py:2513–2526`, `_release_planning_slots`.
- `tldw_chatbook/Chat/console_workflow_preparation.py:2916–2936,3023–3034`, native finalization followed later by planning root/configuration/slot return.
- `tldw_chatbook/Chat/console_workflow_runs.py:2199–2296`, G `_plan` final publication/removal.
- Connected `console_fleet_wake.py:336–341,754–799`, native token release and delivery admission; `console_chat_controller.py:28059,29110–29113`, terminal-state retry.

**What this is:** Native planning occupies the shared automatic-primary token and received-turn claim. An ordinary survivor completion can already be pending in that chat while planning runs, for example when the completion's coalescing timer fires after planning has claimed the slot. That pending ordinary result must become eligible when the planning work and its original custody return, without requiring another user action.

**Problem:** The original wake `_attempt` returns when readiness or the automatic-primary claim is occupied. Once its coalescing deadline has expired, this refusal does not install another timer. Planning does invoke `_finalize_agent_reply`; its terminal `_set_run_state` posts `retry_soon`, but this happens inside the original worker's `run_coroutine_threadsafe(finalize()).result()` interval. The planning intake and token are still held. The posted callback can therefore run and refuse before the later worker/storage/settlement/root return and `_release_planning_slots`.

The actual later `_release_planning_slots` removes the claim/token and has no fleet retry. `release_received_turn` and `release_automatic_primary` themselves only remove their exact entries; neither notifies. G `_plan` subsequently publishes and pops the run without a fleet retry either. If the earlier finalizer retry was the last trigger, the ordinary completion remains pending during the potentially indefinite plan-approval wait despite newly available capacity. The execution-only `_notify_execution_release` at `console_workflow_runs.py:3002–3027` is never reached by planning.

This is a **source-derived interleaving, not a newly executed native reproduction**. It does not assert that every planning run starves a completion: a still-future coalescing timer, another completion, or a later user action can mask the missing edge. Those incidental events do not establish release-driven delivery.

The first-send wake is a different mechanism. `_release_configuration` exits `_first_send_source_scope`, whose finally calls `ConsoleRuntime._wake_first_send` (`console_runtime.py:3094–3111`). That posts only `_first_send_wakeup.set` for the onboarding persistence worker. It does not invoke fleet `retry_soon`, and it may not exist at all for an already-onboarded chat. F configuration and planning-slot release are synchronous with respect to their owning loop, but that ordering cannot turn this separate event into a fleet-delivery notification. F's own token is distinct from G execution's `run.token`; this finding does not falsely describe a G execution token as being released by F.

**Required correction:** First establish this precise boundary with a genuine already-pending unrelated native completion and the original planning/token/received owner. Then notify the existing wake owner only after the appropriate original planning release has positively returned, with the same source, cancellation and post-release-error distinctions required by Q1. Do not add a poller, use a synthetic completion, reset pending state, broadly signal from every token release, or treat a merely completed planner row as physical return. The accepted Q1 ruling deliberately rejected widening the common release method without its own source review; respect that boundary.

**If skipped:** Ordinary survivor results can remain undelivered until an unrelated event, although planning has reached human review and the slot is free. That violates Task8 plan step 4's preservation of unrelated fleet delivery and the spec's ordinary/native composition requirement. The existing execution queued-wake control (`test_original_ordinary_wake_queued_before_workflow_release`) and enabled mixed execution journey do not test F/G planning release.
