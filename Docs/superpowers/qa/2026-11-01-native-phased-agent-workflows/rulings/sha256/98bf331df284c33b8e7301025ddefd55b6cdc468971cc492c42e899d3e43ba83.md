## Actual private API and retained objects

`await bridge._prepare_workflow_reply(*, phase, task_id, binding, resolution, **native_kwargs)` returns `_PreparedWorkflowReply` from `Chat/console_workflow_preparation.py`.

Required inputs are the exact live `WorkflowPhaseAuthorization`, native `RunAdmittedWorkspaceRoot`, original saved task ID and `ConsoleProviderResolution`. It verifies original runtime/controller/bridge/store/session/service identities, session/project selection, current binding and target, original cancellation callback and existing workflow hook refusal. Allowed optional native inputs are MCP/builtin/local/virtual-CLI/raw-shell providers, review/revoke/terminal callbacks, native-tools preference, native budget, project-instruction confirmation/activation/nested budget and narrowing persona rules. It refuses donated parent messages/history/drafts/continuation/primary identity and refuses capture-enabled task mode until the phase snapshot owner exists.

The returned object retains `authorization`, `native`, `phase`, `binding`, `resolution`, `session`, `controller`, `runtime`, original `service` (WorkflowRunService), original cancellation probe, and the suspended original generator `_lifetime`. `native` is `_PreparedNativeReply` containing actual AgentService, first request plan (config/registry/messages/schema), original session/progress-owner IDs, resolution, streaming adapter, unstarted primary lifeline, project-instruction context, review-scope factory, optional native log writer, child change state and `run_primary`. `run_primary` refuses for task mode. The original TaskAuth retains this preparation in its private `_bridge_preparation` list and checks it again at dispatch; closing or losing original source revokes it.

`prepared.native.service.launch_workflow_task(prepared.authorization.task, authorization=prepared.authorization, should_cancel=<same original callback>, ...)` is the existing Task6 child launch. It creates a genuine child with the original requested run/reservation; there is no parent run. The caller binds the actual receipt through existing `WorkflowRunService.bind_native_receipt`, obtains the required Task7 result/checkpoint after actual drain, then calls `await prepared.close()`. Close refuses a launched child without actual drain or required checkpoint, and retires the original generator exactly once. An unlaunched preparation may close its resources; this does NOT settle/complete the accepted phase or invent a task result. The coordinator must quiesce/settle unused reservation custody through existing APIs.

### Changes and ownership contract

1. The gateway retains its real `activation.worker_guard(original ledger)`. Its invocation now has terminal exception transport outside the guard: a pre-body worker admission failure is sent through existing `_QueueItem.adapter_error` and `done`. The stream raises the original exception object, then follows existing native cleanup. No source/activation bypass, dummy provider call or replacement guard. Ordinary worker behavior is unchanged. The existing broad exception transport is explicitly annotated because the exact failure is re-raised by the consumer rather than swallowed.
2. `close()` selects original resource retirement under the existing `WorkflowTaskAuthorization._lock`, shared with the native launch claim. It checks actual launch/receipt/drain and required checkpoint before setting `_closing`. Task source checks reject selected retirement; `launch_workflow_task` revalidates original authorization while holding that same lock immediately before appending the launch claim. Neither child drain nor human consent is waited under the lock; finalizer execution occurs outside it. A child which already won launch remains authorized when premature close is refused, including while that close's finite callback is queued.
3. Self-review found that clearing `_closing` after a finalizer exception would reopen a partly closed frame. Retirement now remains selected if cleanup fails, refusing later launch while leaving `_closed` false (cleanup completion is not asserted). Successful finalization atomically publishes closed and clears the in-flight flag. This is the same retirement/launch blocker, not a new lifecycle framework.

The private API and remaining phase snapshot/launch-freshness/coordinator obligations are unchanged. The two production guard/claim changes are small; the close callback is rearranged around the existing lock, with no new lock/store/executor. Task38531 plan recorded this fix before production; notes record partial fix evidence without completing parent criteria.
