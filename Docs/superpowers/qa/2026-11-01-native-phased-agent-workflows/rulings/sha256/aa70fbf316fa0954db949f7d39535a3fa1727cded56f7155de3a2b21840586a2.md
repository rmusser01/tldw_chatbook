## Important (Should Fix)

### 1. Source loss after registration bypasses the required no-effect refusal protocol

**Locations:** `tldw_chatbook/Workspaces/change_review_finalization.py:784–807,1121–1151,1159–1168`; existing consumer `tldw_chatbook/Chat/console_agent_bridge.py:8643–8674`.

`_admit_pending` turns a failed original-source admission into a ticketless `_OperationResult`, but discovery/baseline process it as a completed worker error before reaching the ticketless/native check. If the source disappears while initial discovery is parked for capacity, no tracker worker enters, yet `baseline_completion` becomes `DISCLOSED_FAILURE`, `completion` stays `PENDING`, and `admission_error` stays empty. That is not the final ruling's UNADMITTED classification for a never-admitted operation.

The E branch correctly sets UNADMITTED and avoids direct publication, but it does so asynchronously after `finalize()` has already returned SCHEDULED. The bridge only appends the existing failure marker for synchronous OVERLOAD_VISIBLE. The handle error is therefore never exposed to the original session: no snapshot row, no visible failure/skipped marker, and no publication revision for a UI consumer to recover the missing disclosure. The existing late-source-loss test (`test_native_change_review_ownership.py:601`) verifies only handle errors and zero publisher calls, so it misses this gap.

**Focused evidence, without rerunning existing suites:** two new temporary probes use the actual `native_review` runtime/SQLite fixture and supported bootstrap-profile opt-in; neither substitutes the native admission implementation or resets a guard.

A real occupied tool slot parks discovery; source loss plus the actual tool release wakes and refuses it. Full output: `/private/tmp/task8d1-review-probes/pending-source.log:35–46,244–255`.

### 2. The new issuer adds unnecessary configuration initialization to bridge construction

**Locations:** `tldw_chatbook/Workspaces/change_review_ownership.py:30–34`; new caller `tldw_chatbook/Chat/console_runtime.py:4552`.

`_NativeSnapshotIssuer.__init__` immediately requests `runtime.execution_capacity`, before even obtaining `runtime.worktree_activity`. On a runtime whose capacity is still lazy, the existing getter calls `RuntimeCapacity.from_settings()` while holding `_execution_capacity_lock` (`console_runtime.py:1863–1871`), which runs `_refresh_limits()` (`execution_capacity.py:84–90,131–143`). `_setting()` then calls `get_cli_setting()` (`Agents/run_log.py:138–152`), whose cold path can read/create the installed config (`config.py:9717,7223–7249,7029–7073`). This constructor runs whenever Git is available, even when no turn has requested capture, so building a nominally inert issuer can now synchronously initialize configuration/storage and allocate the runtime ledger ahead of its previous lazy lifecycle. The new D1 constructor has no finite callback whose lifetime accounts for that extra initialization.

This is a **new body-capable consumer introduced by this diff**, not merely an unchanged getter that can be assigned wholesale to D2. The private app-control config loader has its own existing source/storage admission; this finding does **not** claim that admission is absent, or equate all private control-plane configuration I/O with workspace/evidence-body confinement. The defect is the unnecessary new constructor I/O and lifetime/initialization coupling. The implementation report correctly admits the eager startup path, but its warm bootstrap fixture does not exercise the cold loading branch. I did not force cache/guard resets to manufacture a run; the constructor→getter→loader call chain establishes the added behavior statically. Root's review clarification confirms that this newly introduced eager initialization belongs in the scoped fix, while preserving the distinction from general app I/O.

**Fix:** make construction of the private issuer metadata-only and acquire the same runtime capacity through the appropriate original lazy initialization/operation lifetime when it is actually needed. Preserve the existing private configuration source/storage admission; do not add a second ledger, silently substitute defaults, or impose a blanket workspace claim on all app-control I/O. Add a focused constructor case proving that issuer/bridge construction alone does not invoke the capacity settings loader, plus the relevant real first-use lifetime case. Existing broad startup/source-framework integration remains D2.
