### Implemented behavior and downstream handoff amendment

- `AutomaticWorkLedger.quiesce_workflow_phase(attempt_id, *, owner_id, drained) -> bool` uses the existing FULL transaction to close an interval without changing phase/native acceptance, task claims, result capacity or resource receipts. Only a positive physical-drain observation plus settled dispatched work can close. Unclaimed and reserved-but-unlaunched children do not count as active work. Published results without positive retirement, committed unsettled tokens, unknown usage and other outstanding reservations refuse closure. Reservation inspection includes descendant chains sharing the root allowance. Repeat close returns False.
- `resume_workflow_phase(attempt_id, *, owner_id) -> bool` rechecks exact owner, accepted state, control authority, enabled setting and effective live ceilings, then opens one interval under FULL. It consumes no generation and returns False if already open. `admit_call` and native non-generation `commit` also reopen inside their own dispatch transaction, so later provider/child work cannot bypass clock resumption. Duplicate call/commit receipts do not authorize dispatch or reopen a closed interval. Native Goal/fleet deadline behavior is unchanged. Task5/6/8 must keep using the original task reservation and run identity described above.
- The final tool registry invocation retains its live private-custody/control check and calls `resume_workflow_phase` after definition validation, immediately before the provider effect. This preserves same-session native custody; a read/check/claim alone does not reopen time. The real private-factory test issues custody through `_accept_workflow_phase`, quiesces, verifies a mere `context.check()` keeps the clock closed, and invokes a real registry provider under that same context, proving the interval is reopened before the effect.
- `settle_workflow_phase(..., outcome="completed" | "failed" | "cancelled")` retains `completed` as the default. For planning only, failed/cancelled outcomes require no plan and never publish one or mutate workflow control revision. Existing phase status `failed` means unsuccessful planning, `closed` means confirmed cancelled planning; native state `completed` means settled for all three outcomes. `WorkflowPhaseAttempt.outcome` exposes the durable mapping. A plan supplied with unsuccessful outcome is rejected. Successful planning still publishes with its exact original control-revision CAS; stale publication rolls back the entire settlement.
- Planning failed/cancelled settlement still requires the exact accepted attempt/runtime owner, positive drain and no unsettled/uncertain reservation. It retains generation/model/token charges and releases only the unused reserved planning-result capacity (`result_bytes=0`) after those proofs. A pause/control revision advance does not prevent this non-publication retirement. Wrong owner, unknown usage or persistence failure leaves acceptance, capacity and interval evidence retained. Passive Stop is possible after drained failure/cancellation, without publishing an obsolete plan.
- Task7/8 integration remains explicit: `drained` is the trusted native coordinator's observation input, not a terminal-row inference or user acknowledgment. These SQLite controls exercise the observation; this round does not wire it to ExecutionOwner or add scheduling. The controller positive-origin inventory and fail-closed WORKFLOW_PHASE boundary above remain unchanged.
