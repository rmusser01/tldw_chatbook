## User-facing result

`/workflow new` and its Console palette entry open passive setup for the originating chat. The form shows the workspace's ready local folders, exclusions count, actual existing Change Review capability/consent/root readiness, planner selection, captured preset choices/fallbacks, and finite policy. The user can lower per-run caps within the captured settings, including cumulative **active** seconds. No baseline is claimed in setup. Existing edited files are inputs. `Prepare plan` submits the chosen goal and consumes a planning attempt. `/workflow` opens only this chat's saved headers, fifty at a time. Selecting a row does not start a run, re-audit recovery, enable capture, or consume an unrelated draft/attachment.

The compact workflow button links to the exact chat/workflow needing attention. The review modal binds both IDs, subscribes on attach, explicitly reads current state, and unsubscribes on detach. It shows the exact control/plan revisions, phase and task progress, targets, instructions, modes, tools, read/write footprints, dependencies, inputs, outputs/checks, remaining resources, active-time accounting and recorded Change Review dispositions. It paginates result history, reads the selected immutable checkpoint, and exposes process invocation, verifier digest, exit/cleanup/freshness, manifests and actual stdout/stderr when present. Required result/handoff evidence precedes the plan once results exist. Missing, stale, skipped or failed checks remain visible according to native data; optional logs are unnecessary.

Initial plan approval, later phase approval, remaining-work approval and quality acceptance are separate native decisions. At a multi-phase boundary the user accepts the current phase's quality result and reviews the next phase's fresh decision before authorizing it. `Revise remaining plan` requires explicit instructions; `Pause`, `Stop`, and `Resume` use the displayed control revision. Quality cannot clear unknown physical return. Uncertainty/Recovery and paused/Resume required are distinct. A failed or superseded read disables actions until a fresh authoritative read; Refresh is explicit and there is no UI poller. A failed final metadata publication may be silent to subscribers, so commands also recheck the actual coordinator before execution. Ordinary fleet drilldown/steering and existing tool approval focus remain the owners of those actions. A background link never silently redirects a fleet/approval operation to whichever chat is in front.

Stable action cells prevent a second click at the approval position from becoming Pause or quality acceptance when the state transitions. The primary approval and quality-acceptance buttons have separate positions and identities. The default focus is the objective, Close or another safe control. User guide and concrete implementation decisions are in the Console agent guide, ADR-285, the Task 9 plan clarification and the TASK-38532 implementation note.
