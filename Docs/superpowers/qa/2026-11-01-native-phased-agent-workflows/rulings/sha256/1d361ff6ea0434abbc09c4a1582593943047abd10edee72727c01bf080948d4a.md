### Context at the old and proposed finite return boundary

The current execution `operation.finish` is inside the phase's automatic-work scope, SAME finite `owner.activate`, P's `activate_source`, the source's nested activations, and original outer execution/owned-storage scopes. The extra `with self.activate_source()` around finish adds another actual source activation. The synchronous capacity observer therefore currently sees those bindings, and a newly scheduled asyncio Handle can retain them. The current exception/finally retry has the same issue plus failed-scope ambiguity; it is removed rather than reused.

The proposed single finish call occurs only after these actual original contexts have returned normally. It runs in the SAME original finite worker and restored caller ambient Context, while the common tracked-reader binding/handoff still owns the invoke call. It does not use a fresh Context, clear a variable, revive an old ExecutionState, or adopt another owner. The ambient owner/phase/preparation/tree/guard can be non-None because an actual caller may have its own outer scope; the proposed assertion is identity with the actual pre-P-scope ambient values, never blanket emptiness. Unrelated tracing/custom ContextVars retain their original worker values. Holding `_finite` through the entire native return tail preserves the record of the still-returning operation/root/claim; a notification is not permission to overwrite or close it.

Current execution `retire()` already calls `owner.finish_root` and `claim.settle` after the enclosing P execution/owned-storage contexts have exited; their drain/activity callback context is not being moved inside a new activation. Planning's existing finite finish/root/claim tail is also outside its owning scopes. The proposal does not move planning back into a source scope or add a fresh post-failure check/admission. Actual original-source and outcome validation remains mandatory before the producer tuple is accepted.

Local Python3.12.11 `BaseEventLoop.call_soon_threadsafe` delegates to `_call_soon`, and `events.Handle.__init__` copies the current Context when `context=None`. Consequently G's native release Handle really would copy the restored ambient Context after this change. It invokes only SAME `Event.set`; that method completes existing waiter Futures. The local Python Task/Future implementations explicitly register/reschedule Task wakeups with the Task's retained Context, rather than adopting the Event setter's Context (`tasks.py:352`, `futures.py:161`). The deployed runtime can use C Task/Future implementations, so these local Python sources are the scheduling-contract trace, not an executed proof of C internals. An actual receiving-Task context witness remains in the proposed targeted control below. No change to asyncio, G's callback/context argument, ordinary wake delivery context, common custody scheduling or a new Task is proposed.

### Alternatives and deliberate compatibility cost

Re-entering P's `activate_source` after the original scopes returned is not a harmless context restoration. `_AgentSources.activate` (`Chat/console_agent_sources.py:281`) checks source memory, binds the ordinary tree, enters actual execution and operation-owned database connections, may obtain a scratch lease, and checks storage. It creates new fallible owning exits, can fail under revoked/changed source, and does not recreate the identical previously returned guard. It would make already-owned physical cleanup depend on a fresh activation and reintroduce the same-error exit problem unless another return protocol enclosed it. It is therefore not proposed.

Rebinding only owner/phase values would neither restore the original full source context nor be necessary for either native subscriber; restoring a copied Context containing a returned guard would instead expose stale ownership. Keeping finish inside the original owning scopes would preserve callback context but would still return the tool operation before knowing those scopes returned, contradicting this proposal's retained-operation obligation on failed exits. No such alternative is silently adopted.

Chosen source direction: notify from the restored ambient Context after actual normal P-scope return, retain all original native notification ordering/Exception isolation, and preserve source/producer failure as unknown. Cost: custom subscribers which depended on P's temporary ContextVars no longer receive those temporary bindings at this finite-operation notification. Native subscribers use availability only and already accept out-of-activation limit-change notifications. There is no new subscriber contract promising original context inheritance, fresh activation, immediate dispatch, unique wake causality or performance. A scope/finish/notification BaseException failure still blocks a positive read and original configuration release; any actual earlier physical removal is recorded honestly.
