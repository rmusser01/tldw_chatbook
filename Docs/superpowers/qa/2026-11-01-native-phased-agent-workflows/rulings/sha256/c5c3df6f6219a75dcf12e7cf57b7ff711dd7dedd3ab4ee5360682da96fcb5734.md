### Important

**I1 — Qualify the actual manager and request-building callbacks consumed by the transport.**

Primary changed location: `tldw_chatbook/Chat/console_ssh_custody.py:158` (with capture at `:76` and callback checks at `:179`).

`_RemoteSource` captures and validates `cfg.masters`, plus the identity, methods and grace value of `cfg.transport`. It never captures or verifies the transport's own `_manager`/`master_manager`. These are not interchangeable references: the actual one-shot argv reads `self._manager.ssh_bin` and calls `self._manager.client_options(loc)` (`tldw_chatbook/Tools/remote_workspace_transport.py:1335`), while session startup obtains its manager from `self._transport.master_manager` (`tldw_chatbook/Tools/remote_session_worker.py:295`). Replacing that nested manager after capture leaves every existing `_RemoteSource.check` predicate satisfied. The original `cfg.masters` can be checked/accepted while a different manager supplies the actual binary, options or connection for the request. Native custody then accepts work from a source it did not capture.

The same concrete qualification gap exists for the request-building module aliases: `RemoteWorkspaceTransport.call` uses its own `_bundle_payload` and `_remote_command` (`tldw_chatbook/Tools/remote_workspace_transport.py:1324`, `:1337`), but `_NATIVE_TRANSPORT_FUNCTIONS` only pins the IO/watch/settle/kill functions (`:1598`). Checking `executor._bundle_payload` via `_NATIVE_SSH_FUNCTIONS` (`tldw_chatbook/Tools/remote_workspace_executor.py:1595`) does not check the independent `remote_workspace_transport._bundle_payload` binding. Session startup likewise consumes its module's payload/command builders (`tldw_chatbook/Tools/remote_session_worker.py:293`). A changed builder can run before any refusal while the native source is still treated as stock.

**Why this blocks S:** the accepted contract requires the actual original selected manager/configuration/callback source, and requires changed or unknown implementations to refuse. Exact outer transport type and method identity do not prove the identity of these actual consumed nested sources. This is a source-supported finding, not a claim that a live exploit was reproduced.

**Correction:** capture/check the actual transport-manager relationship and the finite original callback bindings used by one-shot/session request construction before those receiving calls. Preserve the existing configured binary and SSH policy; no binary restriction or new generic trust framework is needed. Add focused real-model replacement negatives for these receiving sources, including a replacement after enqueue, and assert that the replacement callback/peer is never entered. Existing provider/handler/authority/executor replacement tests do not exercise these cases (`Tests/Chat/test_console_ssh_custody.py:298`).

**I2 — An admission frame is currently accepted as remote terminal cleanup proof.**

Primary changed locations: `tldw_chatbook/Chat/console_ssh_custody.py:299` and `:68`.

`response()` calls `WorkspaceToolResponse.from_bytes` and stores its result directly as `request.terminal`. That decoder intentionally accepts all three outcomes, including `admitted` (`tldw_chatbook/Tools/workspace_tool_protocol.py:54`, `:230`). `_Request.proven` subsequently checks only local return and `terminal.cleanup_proven`, not that the frame is terminal. Admission markers legitimately carry `cleanup_proven=True`; the existing complete parser explicitly validates that admission shape and separately rejects a terminal whose outcome is not success/failure (`tldw_chatbook/Tools/workspace_tool_executor.py:918`).

This reaches the real readers: after the first admission marker, a second marker is stored as the purported response rather than consumed as the first marker (`tldw_chatbook/Tools/remote_workspace_transport.py:1160`; `tldw_chatbook/Tools/remote_session_worker.py:578`). With local one-shot retirement, or shared STATUS/write return, the new custody check considers that admission-only response proven. The executor's original `_parse_worker_output` later rejects it as `protocol_failure`, but that exception does not clear the already-populated native proof. Activation therefore finishes the operation even though no valid remote terminal was received.

**Why this blocks S:** a validated frame and a validated terminal are different facts. The exact-operation-ID check and strict boolean are necessary but do not make an admission acknowledgment evidence of remote cleanup. This violates the requirement to retain uncertainty when the original terminal is absent or invalid.

**Correction:** consume the existing stock terminal validation, or enforce its terminal-only outcome contract before recording a positive proof. Invalid/nonterminal frames must leave the original remote obligation unproven while preserving the executor's existing error rendering. Extend the real peer negative controls with a duplicate/admission-only response (and original request ID), checking that the original operation/storage remain retained after local IO/STATUS returns. No protocol change or retry is needed.
