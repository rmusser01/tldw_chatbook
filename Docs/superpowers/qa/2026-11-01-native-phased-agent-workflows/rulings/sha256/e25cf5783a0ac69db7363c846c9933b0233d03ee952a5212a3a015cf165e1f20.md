## Proposed narrow ordering correction, awaiting root ruling

Add one private `RLock` on the existing original `_NativeLegacyHookSource`, named `_workflow_check_lock`. It serializes only concurrent workflow source validation calls on this exact issuer. It introduces no event producer, permission store, source record, capability or runtime owner.

In existing `workflow_task_scope._check_hooks(runtime, session_id)`, retain the configured effectful-definition refusal first. Retain exact engine/issuer type checks before accessing the lock. Under the issuer's private validation lock, retain all current engine/runtime/native-attached, cleanup_pending and published-target checks, then perform the same original `with issuer.capture(session_id): pass` and original RuntimeError refusal. Read the runtime/engine references again in that guarded identity predicate to reject replacement while waiting. Keep v2 definition checks afterward. The lock spans the original source-only capture's actual return, so a concurrent validation checks cleanup only after that source-only admission has physically ended.

The original capture implementation, `_admissions`, `_events`, cleanup_pending, wait_closed, actual hook event admission, native process/required-write/host return, source memory checks, configuration/permission checks and cancelled-native-row guard keep their current logic. An actual event capture or unresolved hook custody still makes workflow validation refuse. No empty-config exemption is introduced. Ordinary fire/notify/prepare_notification never acquire this validation lock and preserve their current behavior.

Use a dedicated issuer-local lock because holding `_EventCustodyRegistry._condition` across recovery/source reads would expand the actual producer/retirement lock, and the runtime `_run_hooks_lock` also protects v2 lifecycle maps with their documented checkpoint lock ordering. The dedicated lock is acquired only by this finite source validator and has no reverse acquisition in event producers or source reads. RLock accommodates same-thread nested acquisition without introducing an exemption from cleanup_pending.
