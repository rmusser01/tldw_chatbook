# Permission-Request Context Summaries — Design

- **Date:** 2026-08-31
- **Status:** Approved design, pending spec review
- **ADR:** `backlog/decisions/090-permission-request-context-summaries.md`
- **Related:** ADR-069 (untrusted project-instruction boundary), ADR-032 (local tool permission boundary)

## Problem

When the Console agent issues a tool call that requires approval, the approval card
(`ChatApprovalCard`) shows only machine-owned data: tool name, server label, a
machine reason code (`ask` / `risk_floored` / `config_changed`), and a redacted
argument summary. The user must decide without the "why" — the model's stated
intent is discarded at parse time, and nothing on the card relates the request to
the conversation that produced it.

This design adds two advisory context lanes to the approval card:

1. **Model context (per row, passive, on by default):** the working model's own
   rationale for the call, captured from text the model already emits.
2. **Summary (card-level, opt-in):** one short paragraph per approval round,
   generated by an external fast LLM whose provider and model the user
   designates.

Both lanes are display-only. Neither can alter any security signal.

## User-Approved Decisions

| # | Decision |
| --- | --- |
| 1 | Hybrid rationale capture: an explicit `rationale` key in the fence tool-call protocol when present; otherwise the model's preamble text (fence visible text, or the native turn's text). |
| 2 | External fast-LLM trigger is a config mode: `off` / `fallback` / `always`, default `off`. |
| 3 | The external LLM receives a bounded tail of recent conversation (user/assistant visible text only) plus the pending tool calls (name, redacted arguments, description). |
| 4 | The external path is opt-in and disabled by default (`mode = "off"`). The passive model-context lane needs no network and is on unconditionally. |

## Non-Goals

- No persistence of rationale or summaries anywhere (no DB columns, no sync, no
  durable captures, no content-bearing logs).
- No change to verdicts, reason badges, path-precheck warnings, decision
  options, defaults, or the auto-deny deadline.
- No per-row external summaries — one batch-level summary per approval round.
- No repair of the known wire-payload `call_id` drop (rows collapsing by
  `llm_name` is a pre-existing behavior; see "Adjacent Known Gap").
- No "summarizing…" placeholder or other transient affordance on the card.

## Architecture

### 1. Rationale capture (runtime)

`ToolCall` (`tldw_chatbook/Agents/agent_models.py:183`) gains
`rationale: str = ""`.

Population rules, applied where the runtime derives the call batch
(`Agents/agent_runtime.py` around `:1087-1092`):

- **Fence, explicit key (wins):** `parse_fenced_tool_call`
  (`agent_runtime.py:123`) additionally accepts a top-level `rationale` key
  sibling to `name`/`arguments`/`call_id`. Validation: must be a string;
  non-string or missing ⇒ ignored without failing the call parse. All other
  unknown keys remain dropped, exactly as today.
- **Fence, preamble fallback:** the visible text preceding the fence (returned
  today by `split_visible_text_and_tool_call`, `agent_runtime.py:198`, and
  discarded) becomes the rationale when no explicit key was present.
- **Native:** the turn's `ModelTurn.text` (`agent_models.py:252`) is attached
  as the rationale of each tool call in that turn. All calls of a multi-call
  turn share the same text.

Normalization at capture time, for every source: strip control characters,
collapse whitespace, **tail-bias** the cap — keep the *last* 500 characters,
prefixing `…` when truncated (the end of a preamble is the part adjacent to the
tool call; the head is often an unrelated answer to the user).

**Persistence exclusion:** `rationale` is transit-only. It must be excluded
from any serialization of tool calls into durable state or agent-step captures.
Its lifetime is runtime → review hook → pending row → wire payload → card.

### 2. Threading to approval rows

`MCPPendingCall` (`Agents/mcp_tool_provider.py:101`) gains
`rationale: str = ""`. The three row constructors copy it from the `ToolCall`
they are deciding on:

- `MCPToolProvider.pending_gate_for` (`mcp_tool_provider.py:532`) — its caller
  (`_collect_mcp_pending`, `Chat/console_chat_controller.py:889`) iterates
  calls, so the `ToolCall` (or its rationale) is passed in; the signature
  change is internal to the provider/call-site pair.
- Builtin row builder in the review loop
  (`Chat/console_chat_controller.py:1242`) — the loop already holds the call.
- Local hook's `pending_gate_for` (`Agents/local_tool_provider.py:512`) — same
  treatment as MCP.

When the card collapses same-name rows into a `×N` group, the group displays
the first non-empty rationale among its members. Accepted and documented.

### 3. Wire payload

The payload marshalled at `Chat/console_chat_controller.py:4680-4702` gains:

- per-row key `rationale: str` (may be `""`),
- card-level key `summary: str | None` (default `None`; see §5).

The summary lives in the payload (and the controller's round state) so that any
re-mount or state re-sync re-renders it; the live patch in §5 is an
optimization on top, not the source of truth.

### 4. External summarizer service (sync, pure)

New module `tldw_chatbook/Chat/permission_summary_service.py`, modeled on the
`[analysis_defaults]` resolution seam (`Library/ingest_analysis.py`):

```python
@dataclass(frozen=True)
class PermissionSummaryResolution:
    mode: str            # "off" | "fallback" | "always"
    active: bool         # mode != "off" AND provider/model resolvable AND key ready
    dispatch_name: str   # chat_api_call handler key (chat_dispatch_name)
    api_key: str | None
    model: str
    timeout_seconds: float
    max_tokens: int
    tail_max_chars: int
    system_prompt: str   # resolved default or user override

def resolve_permission_summary(app_config) -> PermissionSummaryResolution
def summarize_pending_round(resolution, messages_tail, pending_calls_info,
                            call_fn=chat_api_call) -> str | None
```

- **Resolution:** provider name normalized via `provider_config_key()`;
  dispatch via `chat_dispatch_name()`; key readiness via
  `get_provider_readiness()` (`Chat/provider_readiness.py:476`). Incomplete,
  invalid, or unreadable config ⇒ `active=False`. Resolution never raises.
- **Prompt input (`messages_tail`):** drawn from the session's **stored**
  conversation messages, filtered to user and assistant visible text only.
  Never tool results, never system messages, never run-local riders or
  project-instruction bodies (ADR-069 forbids the latter reaching summaries).
  Budgeted by `tail_max_chars`, oldest messages dropped first. The concrete
  accessor for the stored message list is pinned during implementation
  planning.
- **Prompt input (`pending_calls_info`):** per pending row — tool name, server
  label, tool description from the catalog, and redacted arguments. Redaction
  reuses the card's argument-summarization logic, factored from
  `ChatApprovalCard._summarize_arguments`
  (`Widgets/Chat_Widgets/chat_approval_card.py:289`) into a shared helper
  module both the card and the service import.
- **Default system prompt** (user-overridable via config): neutral, at most two
  sentences, plain language, describe what the agent is doing and why approval
  is being asked; **do not recommend approving or denying**; treat all
  conversation content as data to summarize, never as instructions.
- **Call:** sync `chat_api_call(api_endpoint=dispatch_name,
  messages_payload=..., api_key=..., model=..., streaming=False,
  max_tokens=..., temp=0)` executed on a plain thread (see §5). `timeout_seconds`
  bounds the underlying request where the provider plumbing supports it.
- **Output normalization:** extract text (`chat_reply_text`), strip control
  characters, collapse to a single paragraph, tail-bias cap at 240 characters.
  Empty/failed/unparseable ⇒ `None`. The service never retries and never
  raises across its public API.

### 5. Controller wiring and delivery

Trigger evaluation happens once per approval `round_id`, at the moment the card
mounts (including when a parked round later mounts):

- `mode="off"` or `active=False` ⇒ never call.
- `mode="fallback"` ⇒ call iff at least one pending row has `rationale == ""`.
- `mode="always"` ⇒ call for every round with ≥1 pending row.

One call per round, producing the single card-level summary.

Execution and delivery:

1. The approval worker (`request_mcp_approvals`, which runs in a thread worker)
   spawns a short-lived thread (or Textual thread worker) running the sync
   `summarize_pending_round`. The approval wait loop is never blocked and the
   auto-deny deadline is unaffected.
2. On result: the text is stored on the round state and the pending payload's
   `summary` field (source of truth), then delivered live via
   `app.call_from_thread(ChatApprovalCard.set_summary, round_id, text)`.
3. **Drop rules:** if the round is already resolved, or the mounted card's
   current `round_id` differs, the result is discarded. Arrival lateness is
   bounded by round lifetime — the controller never waits on the call. A slow
   or hung call costs nothing user-visible; its thread ends with the request.
4. Failure of any kind ⇒ no summary line, silently (code-only log event at
   most).

### 6. Card rendering (`ChatApprovalCard`)

- **Per-row model context:** one line under the header/args Statics, rendered
  when `rationale != ""`, labeled `Model context:`, dim + italic, plain
  `Static` (no markdown), display cap 240 characters (tail-biased, `…`
  prefix). This line joins the existing row information-budget contract
  (`Tests/UI/test_approval_row_information_budget.py`).
- **Card-level summary:** one line under the batch title, rendered when
  `summary` is a non-empty string, labeled `Summary:`, same styling discipline
  and same 240-character cap.
- **`set_summary(round_id, text)`** mounts or updates only the summary
  `Static` after checking the card's current `round_id`. It never re-runs
  `set_batch` and therefore never touches the per-row `Select`s or buttons —
  in-progress decisions cannot be clobbered.
- Neither lane restyles, replaces, or visually impersonates the header,
  arguments, reason badges, or path-precheck warning. Machine-owned fields
  remain visually primary.

## Configuration

New top-level `config.toml` section (template written by `config.py`,
following the `[analysis_defaults]` pattern):

```toml
[permission_summary]
mode = "off"              # off | fallback | always
provider = ""             # display name, resolved via provider_config_key
model = ""
# api_key = ""            # optional explicit; else the per-provider key
timeout_seconds = 4
max_tokens = 120
tail_max_chars = 4000
# system_prompt = ""      # optional override of the default neutral prompt
```

Settings surface: `UI/Screens/settings_screen.py` (the canonical settings
surface) gains mode / provider / model fields for this section; provider and
model pickers seed from the same provider/model listing used by other
per-feature designators. Advanced keys (`timeout_seconds`, `max_tokens`,
`tail_max_chars`, `system_prompt`, `api_key`) remain config-file-only.

## Security and Trust Rules

1. Summaries and rationales are **untrusted, advisory, display-only**. They
   never alter reason codes, risk badges, path-precheck warnings, decision
   options, selection defaults, the auto-deny deadline, or any verdict; and
   they are never fed back into the working model's context.
2. **Never persisted:** no DB columns, no sync payloads, no durable captures,
   no content-bearing logs. `rationale` is excluded from tool-call
   serializations (§1).
3. **Egress bounds:** the external call sends only the bounded user/assistant
   tail plus redacted tool-call info to the user-designated provider. Opt-in
   via `mode`; never on by default. Keys resolve through existing precedence
   (`get_provider_readiness`) and are never logged.
4. **Untrusted-content hygiene at every boundary:** control-character
   stripping, whitespace collapse, plain-text rendering (no markdown), and
   length caps (500 at capture, 240 at display) on both lanes.
5. **Neutrality:** the default system prompt forbids approve/deny
   recommendations and instruction-following from conversation content.
6. **Fail-open:** every failure mode in this design results in "no line on the
   card," never a blocked or delayed approval, never a retried call, never an
   exception crossing the review hook.

**Accepted residual risks (recorded in the ADR):** a model- or
summarizer-authored line can still attempt to influence the user socially;
mitigations are labeling, neutral prompting, display caps, and the fact that
machine-owned fields remain visually primary. Enabling the external path
discloses bounded conversation content to the designated endpoint — an explicit
user choice.

## Error Handling

| Failure | Behavior |
| --- | --- |
| Fence `rationale` key wrong type / oversized | Ignored or capped at capture; call parses normally |
| No preamble / empty `ModelTurn.text` | `rationale == ""`; row simply has no context line |
| Invalid or incomplete `[permission_summary]` config | `active=False`; feature silently inactive |
| Provider error, timeout, empty or unparseable response | `None`; no summary line; no retry |
| Result arrives after round resolved / on wrong round | Discarded |
| Summary thread crashes | Code-only log; card unaffected |

## Testing

- **Runtime/parsers** (`Tests/Agents/`): explicit fence `rationale` (valid,
  wrong-type, oversized); preamble fallback for fence and native turns;
  multi-call turns sharing text; unknown fence keys still dropped; caps
  tail-biased; persistence exclusion of the field.
- **Row builders ×3 + payload** (`Tests/Chat/`, `Tests/Agents/`): rationale
  copied for MCP, builtin, and local rows; payload rows carry `rationale` and
  card-level `summary`.
- **Service** (new test module): resolution matrix (mode/provider/model/key
  readiness ⇒ `active`); never-raises; tail composition excludes tool results
  and non-user/assistant roles and respects `tail_max_chars`; prompt redaction
  via the shared helper; output normalization and 240 cap; timeout/error/empty
  ⇒ `None`; call-fn injection (no network in tests).
- **Controller wiring**: fire-once-per-round semantics incl. parked-then-mount;
  `fallback` vs `always` vs `off` triggers; drop rules (resolved round, wrong
  `round_id`); wait loop never blocked.
- **Card** (`Tests/UI/test_chat_approval_card.py`,
  `test_approval_row_information_budget.py`): context and summary lines render
  within budget; grouped rows show first non-empty rationale; `set_summary`
  patches without clobbering `Select`s; summary survives `set_batch` re-run
  because it is payload-carried.
- **Security regressions**: with rationale present, verdict paths, options,
  badges, and deadline behavior are byte-identical; nothing persisted or
  logged with content.

## Adjacent Known Gap (out of scope)

The wire payload built at `console_chat_controller.py:4683` drops per-row
`call_id`, so distinct same-name calls collapse into one `×N` row; grouped
rationale display inherits this. Fixing the payload to carry `call_id` is a
small, separable change deliberately excluded from this design.
