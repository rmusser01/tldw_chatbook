The task description's own sketch ("gate-off tools greyed in the matrix with an enable action") is structurally wrong, for three recon-verified reasons: (i) `HubTool` is a frozen dataclass constructed ONLY from registered tools — a gate-off tool has no instance to build a row from; (ii) the Permissions matrix's Space-cycle contract (`action_cycle_state`) treats every non-global row as permission-cyclable, and a gate-off row has no permission state — a new row kind and interaction branch would be needed; (iii) it conflates the REGISTRATION layer into the PERMISSION surface — the exact layer-conflation the owner corrected in this task's own history. The redesign spec's "no registration state to go stale" philosophy points the same direction: keep registration out of the permission matrix.

## Ruling: the affordance lives in Servers mode's source DETAIL panes

The shipped precedent is exact: the `builtin`-source detail already renders config checkboxes (`_builtin_toggle_widgets` — Enabled / Expose tools / Expose resources / Expose prompts) writing `[mcp]` keys via `MCPWorkbench._save_builtin_flag()` (thread-offloaded `save_setting_to_cli_config` + snapshot refresh) with a pinned restart-class note. Registration gates are the same KIND of thing: source-level config, not per-tool permission state.

1. **Unified enumerator** (recon: none exists): `all_tool_gates() -> list[ToolGate]` in `Agents/builtin_tool_gate.py` (beside `builtin_permission_rows` — the settings-time-enumeration precedent lives there). `ToolGate` is a small frozen dataclass: `section` ("tools" | "console"), `key`, `tool_name`, `description` (one line, from the gate table / hand-written for the two odd ones), `enabled` (READ with `coerce_bool_setting(..., False)`), `group` ("builtin" | "local"). Contents: the 7 `_GATEABLE_BUILTINS` rows (group builtin) + web_deep_search (group local) + `("console", "local_tools_enabled")` (group local, the master switch, listed FIRST in its group — an INTENTIONAL extension beyond AC #2's literal "[tools]" wording, declared: the local group's master switch belongs beside the gates it masters; AC #2 is amended in the task file to name it). This enumerator is the single source of truth; `Tools_Settings_Window`'s hand-wiring is NOT extended (that surface stays deprecated and untouched).

**CRITICAL prerequisite (spec review, Critical 1)**: `BuiltinToolProvider.__init__`'s registration read (`Agents/tool_catalog.py:504`) is a RAW `if not get_cli_setting("tools", entry.gate_key, False)` — the last un-coerced gate read in the codebase ([console] local_tools_enabled is loader-normalized; web_deep_search's consumer coerces). Left as-is, a quoted "false" REGISTERS the tool while the new coerced UI shows it OFF — the affordance would lie about a security-relevant gate. This task wraps that read in `coerce_bool_setting(..., False)` FIRST, with a regression test (raw string "false" → tool NOT registered), so the UI and the runtime can never disagree. This is the arc's fifth bool("false") site and the fix closes the class at its origin table.

**Constant relocation (spec review, Important 3)**: `WEB_DEEP_SEARCH_GATE_KEY` moves from `UI/Tools_Settings_Window.py` to `Agents/local_tool_provider.py` (its actual runtime consumer, which today re-types the literal at :1104 — that literal becomes the constant). The enumerator and `Tools_Settings_Window` both import it from there (UI→Agents imports already exist; Agents→UI would be the codebase's first and is forbidden). Tests assert the enumerator entry IS the constant, and the constant IS what `_default_specs` reads.
2. **Builtin-source detail** gains a "Tool gates" checkbox group under the existing `[mcp]` toggles: one `Checkbox` per group-builtin gate (id `mcp-gate-<key>`), current value from the enumerator, plus the adapted note: "Applies on next app restart — tool providers build their catalogs at startup." (NOT the existing "next client launch" wording — these gates affect the in-process agent runtime, no MCP client involved.)
3. **Local-source detail — RESOLVED at spec time (spec review, finding 5): branch (b).** `_collect_snapshots()` never produces a `local:__local__` row (that key exists only in Tools-mode catalog derivation), so ALL gates render in the builtin-source detail under two subheadings ("Agent built-ins" / "Local workspace tools"). Verified reachable with zero preconditions: the builtin snapshot is unconditionally appended regardless of `[mcp] enabled`, the default mode/source is servers/local, and OFF_OPT_IN is a muted display state, not a hidden row. Accepted UX trade-off, stated: the pane is badged as the built-in MCP SERVER while the gate checkboxes control the in-process agent catalog — a different subsystem; the two subheadings plus the adapted note wording are the mitigation, and a future dedicated "Local workspace" rail row is out of scope.
4. **Save path** (amended per spec review, Important 2 — "mirrors exactly" was an understatement): `_save_builtin_flag` hardcodes section "mcp", `BuiltinFlagChanged` carries no section, and `on_checkbox_changed`'s `_BUILTIN_CHECKBOX_KEYS` dict SILENTLY no-ops unknown checkbox ids (a naively-added gate checkbox would visually flip, save nothing, and revert on resync). Required NEW plumbing, stated: a new message type (e.g. `ToolGateChanged(section, key, value)` beside `BuiltinFlagChanged`), a new id→(section, key) table for `mcp-gate-*` ids, a new branch in `mcp_servers_mode.on_checkbox_changed`, and a workbench handler `_save_tool_gate` shaped like `_save_builtin_flag` (`asyncio.to_thread(save_setting_to_cli_config, section, key, value)` + the same snapshot-refresh cycle). Mount-echo needs NO new guard (verified: Textual's Checkbox wraps constructor-initial value in `self.prevent(self.Changed)`, and the rebuild pattern constructs fresh checkboxes — pinned by an existing test). The refresh re-reads via the enumerator (coerced), so a failed write shows the truth.
5. **Discoverability breadcrumbs** (amended per spec review, Important 4): PRIMARY = the Permissions matrix's always-visible legend `Static` (NOT a filterable `PermRow` — the filter hides zero-tool sections exactly when the breadcrumb matters most; and the builtin section's pinned server-default row never vanishes at zero, so the legend is always live). SECONDARY/partial = `_empty_tools_diagnosis` — honestly recorded as blind whenever ANY unrelated local tool source is non-empty (it only runs on a fully-empty catalog). Text: "N tool gate(s) are off — enable them in the built-in server's detail (Servers mode)." Computed from the enumerator; absent when zero are off.
6. **Docs**: CLAUDE.md "New Tool" step 4 rewritten — the manual-row-in-dead-window caveat and the task-3240 tracking line are replaced by: gates surface automatically in the MCP hub via `all_tool_gates()`; a non-`_GATEABLE_BUILTINS` config-gated tool (web_deep_search precedent) needs one entry added to the enumerator's hand-list. `Docs/User_Guide/` MCP page gets the new group + "Verified against" stamp (UI-change rule).

## Testing (MCP module test idioms — widget-mount tests for servers mode / workbench, monkeypatched config seams)

**Seam namespaces, stated (spec review, Minor 6)**: the existing precedent (`test_builtin_flag_toggle_saves_setting_and_reloads_catalog`) patches `get_cli_setting`/`save_setting_to_cli_config` on the `mcp_workbench` MODULE namespace — that does NOT reach the enumerator (`Agents.builtin_tool_gate`) or `BuiltinToolProvider.__init__`'s function-local `from ..config import get_cli_setting`. Tests that need to control what the enumerator/provider read must patch `tldw_chatbook.config.get_cli_setting` directly (or each call site's namespace explicitly); each test states which seam it patches and why.

- Enumerator: all 9 gates present with correct sections/keys/groups; `enabled` honors coerced reads (raw string "false" → False, "true" → True, bool passthrough); the two hand-listed entries don't drift from their source constants (assert `WEB_DEEP_SEARCH_GATE_KEY` equality rather than a re-typed literal).
- Detail pane: gates group renders with current states; restart note present with the ADAPTED wording; checkbox toggle → `save_setting_to_cli_config` called with the right (section, key, value) — both directions (on→true, off→false), persisted-config assertion not widget-value assertion (the 3222 lesson).
- Breadcrumb: N-off → line present with correct count; zero-off → absent.
- Mutation checks at implementation: drop a gate from the enumerator → count/presence test red; break the save routing → round-trip test red; breadcrumb count hardcoded → count test red.
- The pinned catalog/absence-by-default tests (`test_web_deep_search_absent_by_default` etc.) remain UNTOUCHED — this affordance changes discoverability, never registration semantics.
