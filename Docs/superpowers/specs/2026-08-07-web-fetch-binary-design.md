# Binary-file support in web_fetch — design (task-1359)

- Date: 2026-08-07
- Backlog: task-1359 (Support binary file fetching in web_fetch)
- Owner directive: "finish the web-tools arc" — controller rulings recorded below; adversarial spec review replaces the interactive design Q&A.
- Today's behavior (recon-verified): `web_fetch` downloads a binary fully (up to max_bytes), decodes it to throwaway text, then raises `[empty-content] unsupported content type: <type>` — clean fail-closed, but useless, and NO test pins it.

## Rulings

1. **In-memory only, zero disk writes** — supersedes the task description's "bounded temp download" phrasing, and task-1359's AC clause "temp-dir hygiene" is AMENDED in the task file to "zero on-disk persistence (no temp files), guarded by the existing no-persistence-import static test" (spec review, Important 6 — per the repo workflow rule, the AC text changes BEFORE implementation). The PDF path's precedent (`pymupdf.open(stream=body)`, enforced by `test_module_never_imports_persistence`) is the house style; never touching disk satisfies the AC's "temp-dir hygiene" and "never execute downloaded content" clauses structurally — there is nothing on disk to execute. The static no-persistence-import test keeps guarding this.
2. **Allowlist, three tiers by dependency posture** (recon: Pillow is a CORE dep; mutagen is UNDECLARED anywhere; zipfile is stdlib):
   - **Images** (`image/png|jpeg|gif|webp`): Pillow in-memory probe (`Image.open(BytesIO); .verify()`; re-open for `format/size/mode` — precisely (spec review, Minor 9): size/format survive verify() as cached header attributes, it is `.load()` that breaks; the re-open is defensive hygiene that matters for animated GIF/WEBP frame-seeking, and verify() genuinely catches corruption — bad checksums raise SyntaxError, truncation raises OSError — so `[image-error]` has real failure modes) → `[image] {FORMAT} {W}×{H}, {size}` metadata line. `Image.MAX_IMAGE_PIXELS` stays at its default (never raised/disabled) — stated precisely (spec review, Minor 8): it hard-raises `DecompressionBombError` only past 2× the limit; between 1×–2× Pillow merely warns. Acceptable here because this path never decodes pixel data at all (`open()`+header probe only), so declared-dimension abuse costs nothing beyond an honest big-dimensions metadata line. No pixel data, no thumbnail, no EXIF (EXIF can carry location data — privacy refusal by omission, recorded).
   - **ZIP archives** (`application/zip`): stdlib LISTING ONLY — `zipfile.ZipFile(BytesIO)`, never extract, never read member bodies. Output: `[archive] ZIP, {size}, {N} members` + up to `ARCHIVE_LIST_MAX = 20` member lines (spec review, Minor 10: `ARCHIVE_LIST_MAX` bounds DISPLAY only — `zipfile` eagerly parses the whole central directory at construction; the 10 MB byte cap is what bounds a pathological member count, measured ~150k entries ≈ 0.4 s, accepted) (`name — {member size}`), a `… and N more` marker beyond, and member names run through the traversal screen: a member whose name is absolute, contains `..`/`\x00`/backslash, or a Windows drive prefix is listed as `[suspicious name]` with the raw name REPR-escaped, not printed verbatim (screen logic mirrors `chatbook_importer._validated_archive_parts`, but flag-and-show, not reject — we never extract, so listing a hostile name safely is the only duty). Encrypted/corrupt zip → `[archive-error] …` structured refusal.
   - **Audio** (amended per spec review, Important 7 — the original phrasing was ambiguous AND collided with `_extract_text`'s existing `main_type` variable, which holds the FULL type/subtype): the rule is "declared content-type's top-level type — the substring before `/` — equals `audio`", computed by a NEW small helper (e.g. `_top_level_type()`), never by reusing the existing `main_type` splitter. This deliberately accepts real-world variants (`audio/mp3`, `audio/x-wav`, `audio/mpeg`) since audio has no sniff to rescue mislabels. Output: `[audio] {content-type}, {size}` only, metadata WITHOUT new dependencies — mutagen is not a declared dep anywhere in pyproject and does not get added; richer audio metadata is a recorded non-goal.
   - Everything else (`application/x-msdownload`, ELF/PE, video, fonts, …): the existing `[empty-content] unsupported content type: <type>` refusal, UNCHANGED — plus the missing regression test that pins it.
3. **Sniff-wins for magic-bearing types** (PDF precedent): PNG (`\x89PNG\r\n\x1a\n`), JPEG (`\xff\xd8\xff`), GIF (`GIF8`), ZIP (`PK\x03\x04`) are contiguous-prefix magics; **WEBP is NOT a prefix** (spec review, Important 2) — it needs a two-anchor check (`body[0:4] == b"RIFF" and body[8:12] == b"WEBP"`, size field between ignored), so the sniff table must accommodate both matcher shapes, and the minimum bytes-buffered-before-sniff-resolution rises from 5 (`%PDF-`) to 12. **Precedence, stated (Important 3), mirrors PDF exactly**: a declared content-type in the allowlist resolves the kind IMMEDIATELY (cap raised on the declared type's word alone, no byte confirmation — the PDF shortcut's behavior); the sniff exists to OVERRIDE a wrong or absent declared type. Audio has no reliable single magic (ID3/frame-sync ambiguity) → declared-type only, recorded. **Blast radius (Important 4)**: `_fetch_once`'s return tuple is positionally destructured at THREE call sites — `web_fetch`, `_crawl_fetch_page` (every crawled page and every sitemap fetch), and `_fetch_robots_parser` (which has no interest in binary kinds) — the `is_pdf` slot generalizes to a sniffed-kind value and ALL THREE destructurings update together. Side effect, acknowledged: crawl's `html_only` early-abort waits for sniff resolution, so its minimum buffering rises 5→12 bytes — bounded and harmless, but real.
4. **Caps**: one `BINARY_MAX_BYTES = 10 * 1024 * 1024` for the allowlisted binary kinds (raised mid-stream on sniff/declared match, like `pdf_max_bytes`), refusal-not-truncation over cap: `[too-large] {kind} exceeds 10 MB — use media ingestion for large files` (PDF precedent verbatim in shape). Under-cap truncation cannot occur (a body under the raised cap is complete; a body over it is refused). PDF keeps its own 20 MB constant untouched.
5. **No decode of binary bodies**: `_extract_text`'s unconditional `_decode_body` moves BELOW the binary dispatch — binary kinds never round-trip through UTF-8-replace (recon flagged the wasted mojibake decode; fixing it is in scope since the dispatch is being rewritten anyway).
6. **No gate change**: web_fetch already fetches these bytes and throws them away; returning compact metadata instead of a refusal adds no new risk surface (same SSRF/robots/rate/size machinery upstream). Tool description in `local_tool_provider.py` gains one clause ("images/zip/audio return metadata, not contents").
7. **Result size**: metadata output is inherently small (≤ ~25 short lines for a maxed archive listing) — no interaction with the 32 KiB/16,000-char delivery seams; stated, not engineered around.

## Testing (MockTransport idiom; PDF-test patterns as template)

- Image: real in-memory PNG/JPEG bytes (Pillow-generated, like `_make_pdf`) → `[image] PNG {W}×{H}` line; corrupt image bytes → `[image-error]` refusal; PNG served as `text/html` → sniffed, image path (sniff-wins); truncated-at-cap image → `[too-large]` refusal not partial metadata.
- Archive: in-memory zip (zipfile-built) → member listing with sizes; >20 members → `… and N more`; hostile member names (`../../etc/passwd`, absolute, backslash, null) → `[suspicious name]` + repr-escaped, never verbatim-printed control bytes; encrypted zip → `[archive-error]`; zip as `application/octet-stream` → sniffed and listed.
- Audio: `audio/mpeg` body → `[audio] audio/mpeg, {size}`; no Pillow/zipfile involvement.
- Sniff robustness (spec review, Minor 12 — the PDF path's own hard-won precedent): a one-byte-at-a-time dribble test for the 12-byte WEBP magic, and a short-body-under-12-bytes fallback test (tiny text body must still extract as text, not crash the sniff).
- WEBP tests carry a `requires_webp` skip guard probing Pillow's webp write support (Minor 11 — mirrors `requires_pymupdf`), with pre-generated PNG/JPEG bytes needing no guard (Pillow core).
- Regression pins (NEW, closing the recon gap): `application/x-msdownload` → `[empty-content] unsupported content type` unchanged; the static no-persistence-import test still passes (no new imports of ingestion/persistence modules).
- Mutation checks at implementation: break the traversal screen → hostile-name test red; drop the sniff for ZIP → octet-stream listing test red.

## Non-goals (recorded)

Extraction of archive members (listing only — extraction is media ingestion's job); EXIF/metadata dumps for images (privacy); mutagen or any new dependency; tar/7z/rar (zip only — tar's traversal surface is bigger and stdlib tarfile safe-listing is subtler; follow-up if wanted); video; base64 thumbnails (the delivery seam is text and the model can't see images through it today); changing web_crawl's non-HTML marker path (crawl skips binaries by design — a crawl is for page text). Stated plainly (spec review, Important 5): crawl's marker decision consults only `is_pdf` + the DECLARED content-type, so a binary served with a wrong/absent type during a CRAWL keeps today's behavior — mojibake-decoded into a bogus/empty excerpt, NOT rescued by the new sniff. Pre-existing gap, accepted and recorded, not silently implied.
