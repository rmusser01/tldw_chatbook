# TASK-40608 — complete project-index key owner

**Selected approach:** implement a disabled, profile-owned `derive_project_index_key` command as the first storage-process slice. It executes the complete stock `project_index_key` operation: independent data admission, root identity capture, actual Workspace SQLite binding-fence read, `ProjectIndexKey` construction, and positive retirement. The parent receives only the immutable key. Keep status, coverage, approvals and the original run-root guards in their present owners. Measure the entire `prepare_project_index_scopes` callback as well as the command, including first-use initialization and IPC. This selects the disabled vertical slice. Production routing and performance qualification require the controls and complete-call measurements below.

ADR required: **yes**. Existing [ADR126](../../../backlog/decisions/126-complete-local-backup-and-recovery.md) and [ADR230](../../../backlog/decisions/230-console-send-preparation-and-io-ownership.md) are amended before implementation; ADR241 supplies project-index semantics and ADR353 supplies Workspace connection ownership. No schema, dependency, interpreter, generic callable transport or whole application actor is selected.

Task51's source review and scoped caller-custody correction passed before selection. This design is not executable correctness or speed evidence. Implement it under the [sub-five plan](../plans/2026-11-13-task-40608-sub-five.md); the original acceptance gate remains unchanged.

## 1. Why this command, and what it does not cover

Task39 already establishes why moving `ConsoleAgentBridge.run_reply` cannot remove received preparation and durable acceptance, and why live app/controller/store/approval closures cannot be serialized. Task40 establishes expensive callback bodies rather than material executor-start or loop-return delay. Its measured definition-selection `read_sources` took 6.1455/3.4826 seconds, turn-configuration `capture` 0.8236/4.5037, native commit 1.5855/1.3736, postcommit hook admission 4.8552/2.3904, and project-index scope preparation 5.6216/7.6357 (README/edit). These inclusive durations are not additive savings. Definition pre/post currentness was under a millisecond; postcommit guards were below 0.05 ms in that receipt.

Those timings are frozen Gate17 evidence, including its historical compaction/tool-capacity helper overlay. The current worktree has `Chat/console_project_index_preparation.py`; `ConsoleChatController._prepare_project_index_scopes` delegates to it. Preserve the frozen original QA/Trace and replay only a reviewed product diff into the benchmark baseline. Do not transplant an entire current controller or infer new ordering from historical marker names.

Comparison of the actual candidate seams:

| Measured callback | Actual source contract | First-slice decision |
| --- | --- | --- |
| MCP definition `read_sources` | `MCP/console_snapshot.py::_capture_console_definition_selection`: `_CapturedSources.read_permission_payload`, then checked catalog bundle unless kill switch. Permission publication and malformed-input repair already have their own complete process owner. `_CapturedSources` also pins manifest/policy/catalog methods and receivers; inventory and downgrade audit follow the read. | Do not combine this into a supposedly pure read or introduce a second permission owner. A later catalog command can complement the existing permission command. |

Keep its actual parent `current` closure and later split named storage producers from parent-only composition. |
| Project-index scope preparation | `prepare_project_index_scopes` encloses registry ownership; each admitted local root executes its original `guard(False)`, `project_index_key`, status, optional Building coverage, then a second guard before installing a scope. | `project_index_key` is an existing complete synchronous command inside this measured callback, with a small detached result and one fixed registry/data contract. Select this slice. |

**Status is not a read-only command.** `ProjectIndexService._admitted` can revoke/reconcile; `_status_from_store` can suspend an inert Building claim; `_AdmittedStoreFactory.__call__` can create a cache or migrate it; `building_coverage` also calls `_admitted`. Calling these in a child without acknowledging their writes would be incorrect. Restricting selection to a missing index, or falling back to parent status after the child starts partial work, is not this proposal.

The first command works whether the optional project-index cache is absent or present, because key derivation never opens that cache. It returns a domain result after a real SQLite query; it does not return metadata to finish admission in the parent. Both original admissions for key and later status remain, in separate processes for now. There is no claim that all 5.6216/7.6357 seconds move, or that this slice alone can reach five-second journeys.

Task34 supplies only a mechanism proof for interpreter contention, not qualified application dependency/concurrency behavior. Tasks38/41 reject the observation-only process; Task46's completed input-group pairs regressed five of six times. Neither is reintroduced. The new hypothesis is that moving a **complete domain command**, rather than an inner observation or adjacent native call groups, amortizes IPC and removes its Python/native handoffs from the Textual interpreter. Only measurement can establish that.

## 3. Initial selection and explicit parent checkpoints

Selection is an optimization decision **before this command's child launch or storage effects**. Qualify exact ordinary file-backed Windows sources, module/function/default identities, constructor/connection wrappers, parent `LocalWorkspaceRegistryService`, `WorkspaceDB`, `_AdmittedStoreFactory`, service composition and the relevant existing `_console_source_current` checks. Qualify the new fixed helper and wire codec too. Bind the actual selected config module and canonical profile/registry path; require the existing stock `config.get_workspaces_db_path()` selection. Do not assume same pathname means same source.

Custom/subclassed/memory/recovery-selected sources, replaced callbacks, unsupported platform, foreign/borrowed active transactions and unqualified ambient core/raw ownership retain the original path before child effects. An already-selected command whose source subsequently changes refuses; it never retries locally. A parent connection opened by the enclosing registry scope is not itself an active transaction: it may remain under its existing owner. Explicitly reject an outstanding parent transaction that could block the child `BEGIN IMMEDIATE`. Do not strip or transfer the outer parent owner to force eligibility. Record when ambient ownership prevents selection; a benchmark that never selects proves nothing.

The concrete ordinary enclosing scope is **eligible**, not a generic ambient-owner rejection. `ProjectIndexService.registry_connection_scope` installs its own `_Operation` in `service._operation_local`; `project_index_registry_connections` then calls `DB/base_db.py::operation_owned_connection`. That helper records `id(database)` in `_OPERATION_OWNERS.ids` and snapshots the thread-local cached connection; it neither opens SQLite nor establishes `participants.core_operation`, a raw operation, or a transaction. Its `_Operation` is service lifecycle accounting, not `storage_admission._operation_local.operation`. After the original `authority.guard(False)` returns, permit that exact parent service lifecycle record and exact connection owner with no active transaction. Inspect the existing cached connection via `core_cached_connection` without opening another and check `sqlite3.Connection.in_transaction`; the current store kernel has no nested-transaction depth counter to transport. A live idle connection is allowed and remains parent-owned. Refuse a live transaction, a foreign service/connection owner, or an additional ambient core/raw scope rather than misclassifying the ordinary wrapper. Assert this exact nested route selects in the first integration control.

Parent checks run on the original issuing worker, not on a protocol-reader thread pretending to be it. The adapter records `(pid, thread, task)` like `PermissionProcess.call`; each rendezvous validates it and the exact captured callback body/closure bindings. Loop-affine received-intent checks remain on the loop at their existing boundaries. No child message asks the loop to grant a permission.

| Checkpoint | Parent work | Child work and lock rule |
| --- | --- | --- |
| Before queue/selection | Original run-root `guard(False)` remains; capture exact owner/source facts and disposal/admission state. | No child native authority yet. |
| After serialized wait and after first-use Ready | Recheck actual source/config/profile/runtime/session/run ownership, qualified definitions and intake. No stale queued request is issued. | Child independently selects profile and registry DB; Ready supplies source/origin and initialization-retirement evidence. |
| `Check(entry)` before key body | Recheck the parent-only capture; respond Continue/Refuse. | No registry transaction held. After Continue, execute original fresh admission and chain capture, not cached observations from before IPC. |
| Completion adoption | Validate command correlation, child source facts, exact result shape and positive retirement, then parent currentness. | Child has exited the complete helper and released registry transaction/connection and data pin before Settled. |
| Original continuation/publication | Existing status/coverage and compatibility-conditional final `authority.guard(False)` run unchanged; the newly installed shared-handoff worker/loop currentness checks gate adoption after the complete callback retires. | No child lease survives into status, provider/disclosure/approval waits or publication. |

This read needs no rendezvous while holding a SQLite registry transaction. The original stock `binding_authority_fence` acquires `BEGIN IMMEDIATE`, then queries the row and captures current binding root/chain/exclusions inside that fence. Thus replacement while blocked is observed after the wait. Child schema/source checks use the actual current DB; child admission performs its own control/registry/path checks. A parent source change while child SQLite is blocked is detected on parent completion; no key is adopted, even if the read completed. If a later extension introduces a parent wait **inside** a native operation, it must add a fresh child native proof after Continue; a prior admission or parent Continue never serves as that proof.

`authority.guard(False)` can itself read the registry. Never call it while the child holds `BEGIN IMMEDIATE`, and never substitute its serialized boolean for the original guard. The parent-only memory/source rendezvous is separate from this original authority effect.

Reuse `MCP/permission_process.py::write_message`, `read_message`, `_Identity`, `ProtocolError` and the existing isolated launch/`ExecutorProcessTree` containment pattern. Initialize the real WorkspaceDB without schema DDL; check its expected current version and retire the initialization connection positively. Construct the stock factory/service, whose initial `retain()` still admits and retires real data authority. Preserve that initialization cost. Startup enrollment may remain until Shutdown; no command pin/connection/transaction or validated filesystem observation remains idle. The factory's remembered identity is the current original rejection baseline, not a lease: each command still calls `retain` anew.

The command is read-only in **application data**, not literally disk-effect-free. `BEGIN IMMEDIATE`, private SQLite opening, WAL connection setup and admission/startup bookkeeping may acquire locks/create infrastructure sidecars; retain their existing policy. No index cache creation, DDL, repair, revoke, reconcile, default binding repair or status mutation is allowed in this command. Unsupported schema/selection must fail without migration. ## 5. Retirement, errors and uncertainty

Reuse the existing `_Command(None, None)` as the storage-acquisition/lease/raw retirement recorder, as the permission worker already does during initialization. Its `source=None` means no permission publication is poisoned; this worker does not issue permission operations or call permission completion/publication callbacks. `storage_admission._Acquisition` and `StorageLease` already enroll exact births through `_enroll`; `_Command.retirement` checks exact leases/holds, startup baseline, pending operations and non-raising hold errors. Keep the existing creator/thread check and unresolved child record. Do not subclass `_Command` (its exact-type check rejects that), broaden its dispatch, or assume its receipt proves SQLite closure.

The genuinely new supplement is small and domain-specific: retain the exact `WorkspaceDB` participant and every new connection at the existing `store_kernel._get_connection` / `participants.register_core_connection` seam (including configure-failure paths), plus the exact `_DataAuthorityPin` returned by `retain`. Use `project_index_registry_connections`' existing native-and-core closure proof and `core_closing`/`retired_core_connections`, not a second native handle implementation. Verify those actual connections are natively closed and removed from their participant, pins closed, and the service `_Operation` not unresolved before accepting the reused storage receipt. No cursor escapes the fixed helper: its row is fetched and its original transaction exits; native connection closure settles the connection-owned statements. A new per-cursor registry is unnecessary. Wire only small counts/settled booleans.

Unchanged Windows ancestry, ACL, metadata and private-SQLite helper routines retain their existing internal close/failure guarantees and original tests; do **not** add an exhaustive Win32-allocation tracker to this command. The new proof is the join between those existing owners, SQLite/core retirement, pin/lease/hold retirement, and process/pipes/containment. Keep exact failed objects/error records rather than reconstructing them from global counts. Startup leases/holds are separately enumerated and must remain exactly healthy until shutdown. Known errors with positive retirement produce `refused`: fixed kinds `recovery`, `binding_unavailable`, `value`, `io`, `sqlite`. Preserve known exception class/category and relevant errno; do not send traceback/SQL/path secrets or dynamically reconstruct exception classes. `index_binding_unavailable` maps back to the existing `ValueError`; a known recovery refusal maps to `RecoveryRequired`; native/SQLite failures retain their existing optional-unavailable behavior at the enclosing caller. Serialization/result-validation failure is a selected protocol failure, never ordinary no-binding. Retirement uncertainty never uses an ordinary refused result.

Source revocation can discard a positively retired key without poisoning permission publication. Unknown close, transport loss, malformed/unmatched receipt, child death, timeout or broken containment latches this storage owner unresolved; withhold the key, close intake, retain request/source/result/error and exact physical custody, and refuse replacement or local replay. Physical containment may be terminated by the existing deadline owner but does not turn an unknown outcome into successful settlement. The read has no semantic mutation to replay, yet an unproven SQLite/native close must still block maintenance coverage.

The current outer `prepare_project_index_scopes` catches `Exception` and returns `(None, {})`, including retirement exceptions escaping the inner loop. Do not rely on that optional UI result to retain custody. The new app/profile owner remains registered and unresolved independently, so optional tool omission cannot make backup/profile teardown report drained. Preserve caller behavior in the first slice; do not silently change it to an approval or Send failure.

## 7. Smallest correctness controls before timing

Use actual Windows ownership/SQLite fixtures and the installed source paths. Keep existing assertions, not rewritten expectations. Add one focused command suite alongside existing project-index/permission-process controls, covering these causal cases:

1. Stock parity: valid local binding yields the exact same key; missing/detached/archived, wrong workspace/kind, root replacement, ancestor/reparse/ACL and data/profile mismatch refuse identically. Both absent and present index caches are unchanged. Real SQLite query/fence executes in the child, with zero key-body native calls in the parent; count enclosing guard/status work separately.
2. Selection: custom/subclass/memory/recovery/ambient transaction and changed constructors/readers choose the original route before any child launch/admission. Changed definitions after selection refuse without scalar replay. Record exact selected/rejected counts so an accidental fallback cannot pass a performance screen.
3. Wait freshness: hold the real registry write lock externally, mutate/detach the binding or replace root/data ancestry, then release it. Fresh child reads refuse or return the newly valid result according to the original algorithm. Change parent source/session/profile while queued, initializing and blocked; stale results never reach status/publication. Check the parent guard is never called while a child registry transaction is held.
4. Initialization: real isolated child origins, selected interpreter/profile/registry path, schema-validation-only construction, no migration/default creation, initialized connection retired. Wrong schema/missing DB/corrupt selection refuses; no replacement/replay follows selected initialization failure.
5. Custody: exact SQLite native/core closure and hold/pin/lease retirement on success and known error; inject raising and non-raising retirement failures, transport truncation/wrong ordinal and child exit.
