# Response caching for web tools — design (task-2832)

- Date: 2026-08-08
- Backlog: task-2832 (Add response caching for web-tools)
- Owner directive: "finish the web-tools arc" — controller rulings recorded; adversarial spec review replaces the interactive Q&A.
- Sequenced LAST in the arc deliberately: it caches the FINAL behavior of the fetch/search tools after robots (#1427) and binary support (#1442) landed.

## What already exists (scope honesty)

The task text predates this arc's shipping: "the agent-runtime/hub path has none" was true on 2026-08-05, but `web_fetch` has carried `_fetch_cache` since v1 — `(url, max_bytes)` key, 15-min TTL, 256-entry earliest-expiry eviction, SSRF+robots re-checked on hit, and (as of #1442) a deliberate skip for crawl-warmed binary kinds. Its test coverage, named precisely (spec review, Important 5 — the first draft overstated this): hit (`test_fetch_caches_within_ttl`), key-miss (`test_cache_keyed_by_max_bytes`), size-bound eviction (`test_cache_entry_cap_evicts_earliest_expiry`) — but NO TTL-expiry test exists (nothing advances the fake clock past `FETCH_CACHE_TTL_SECONDS`; the robots cache has one, the fetch cache doesn't). **This task adds that one missing `_fetch_cache` expiry test** so the "web_fetch half already shipped and tested" claim becomes true rather than asserted. The remaining implementation gap is `web_search`: every identical query re-bills the provider API within a session. `web_crawl` performs no caching of its own beyond the warm-writes above and gains none here (a crawl is explicitly a fresh traversal).

## Rulings

1. **Cache ONLY the success-blocks path, gated at the single point that produces it** (amended per spec review, Critical 1 — `web_search` has FIVE return shapes, and a startswith("[search-failed]") predicate would mis-cache three of them): (i) exception → `[search-failed] …` string; (ii) non-dict result → UNMARKED "No results found or unexpected response format …"; (iii) error envelope → `[search-failed] … reported an error`; (iv) malformed results list → same unmarked string as (ii); (v) well-formed but EMPTY → "No results found for {query!r} …"; (vi) genuine success → joined result blocks. Only (vi) is cached, by storing at that one code point — never by inferring cacheability from string content. (i)–(iv) are transient-failure shapes that must not pin for the TTL. (v) is DELIBERATELY not cached either: this repo's own history (tavily/searx pass-stub parsers, searx string-shape bug) shows "zero results" is as often a broken parser as a true empty — a transient zero must not be pinned; repeated genuine-empty queries re-billing is the accepted cost. Tests cover (ii) and (iii) not caching, and (v)'s re-invocation.
2. **Key = the tool's post-coercion arguments**: `(engine, normalized_query, count)` where `engine`/`count` are the ALREADY-coerced values the tool computes (garbage degrades to defaults before keying, so `result_count="abc"` and the default share an entry deliberately), and `normalized_query = " ".join(query.split()).casefold()` — whitespace-collapsed, case-folded. Search engines are effectively case-insensitive; two spellings of the same query must not double-bill. Recorded trade-offs (amended per spec review, Important 4 — generalized): **the first populator's RAW text wins** — the backend is queried with the first caller's stripped-but-otherwise-raw query, and every later caller whose spelling normalizes to the same key receives that stored result, not a re-run of its own raw text (internal whitespace and casing differences included; the case-sensitive-query case is one instance of this general rule).
3. **Constants, no config** (v1 precedent — "no config surface until someone asks"): `SEARCH_CACHE_TTL_SECONDS = 900.0` (15 min, parity with the fetch cache), `SEARCH_CACHE_MAX_ENTRIES = 128`, module-level `_search_cache: dict[tuple, tuple[float, str]]`, earliest-expiry eviction mirroring `_cache_put`, registered in `_reset_state_for_tests()`.
4. **The cache lives in the TOOL function (`web_search`), not `perform_websearch`** — `web_deep_search`'s phase-1 fan-out calls `perform_websearch` internally and MUST keep hitting the live pipeline (a research run's sub-queries want fresh, uncached results and their own warnings surface); the two tools' result shapes are different anyway. Recorded.
5. **AC clause "rate limits still apply on misses"**: the search path has NO rate limiter today (the 1 s/domain limiter is fetch-side) — the clause is satisfied vacuously and RECORDED as such, not silently: a cache hit bypasses nothing because there is nothing to bypass; a miss behaves exactly as before. No limiter is added (out of scope; the fetch-side limiter precedent exists if one is wanted later — follow-up territory, not filed absent evidence of need).
6. **AC clause "domain-only logging preserved"** — two honesty notes (spec review, Important 3 + Minor 6): (a) "domain" has no analog for a search query; the clause is READ as "engine-only" here, deliberately. (b) The claim and its test are SCOPED to the `web_search` wrapper's own code, treating `perform_websearch` as opaque: the wrapper's only log line names the engine, and the cache adds no query-content logging (eviction debug may name the engine only) — but Bing and Google's own backend functions inside `WebSearch_APIs` log the FULL query at debug/info (pre-existing, reachable via the same tool, out of this task's scope, and NOT covered by the pinned test, which mocks `perform_websearch` and therefore never reaches them). Pinned by a loguru-sink test (capsys does not observe loguru here — the first draft was proven vacuous by review and rewritten; mutation-verified) asserting the query string never appears for a hit/miss/failure cycle at the wrapper layer. One recorded caveat (review, Minor 5): the wrapper's failure string/log interpolates `{exc}`, and a backend exception whose text embeds the request URL (e.g. raise_for_status on `?q=<query>`) can carry query text through that path — an exception-shape leak, not a cache-added one; accepted and recorded, not covered by the pinned test (whose fake raises a sanitized error).
7. **Cache check placement**: after argument validation/coercion (an invalid query still raises `[invalid-args]` without touching the cache), before the `perform_websearch` import/call.

## Testing (existing seams: monkeypatch `WebSearch_APIs.perform_websearch` at source, fake clock via the module `time` attribute, `_reset_state_for_tests`)

- Hit: two identical calls → ONE `perform_websearch` invocation (call counter), identical output.
- Normalization: `"  Foo   BAR "` and `"foo bar"` share an entry; different engine or count do not.
- Expiry: fake clock past TTL → re-invokes the backend.
- Error results not cached: backend raises → error string returned; next call re-invokes the backend (counter = 2).
- Eviction: fill past `SEARCH_CACHE_MAX_ENTRIES` → earliest-expiry entry evicted (size bound holds).
- Log privacy: capture logs across hit/miss/failure — the query text appears nowhere.
- `web_deep_search` isolation (spec review, Important 2 — this needs a NEW fixture, not `deep_env`, which mocks `generate_and_search` wholesale so `perform_websearch` never runs under it): mock `perform_websearch` at source, let the REAL `generate_and_search` run with `search_enable_subquery=False` (so `all_queries = [question]`, exactly one call), mock `_deep_search_settings`/`analyze_and_aggregate` as usual — then assert the `perform_websearch` counter fires even when a `web_search` cache entry for the same normalized query is pre-warmed.
- `_fetch_cache` TTL expiry (the pre-existing gap named above): advance the fake clock past `FETCH_CACHE_TTL_SECONDS` → the transport is hit again.
- Mutation checks at implementation: bypass the cache store → hit test red (counter 2); drop normalization → normalization test red.

## Non-goals (recorded)

Disk persistence (the old ToolResultCache's disk tier died with ToolExecutor; in-memory per-process matches every other cache in this module); caching `web_crawl` traversals; caching error envelopes; a search-side rate limiter; config keys; sharing the cache with `web_deep_search` (ruling 4); cache invalidation API beyond TTL.
