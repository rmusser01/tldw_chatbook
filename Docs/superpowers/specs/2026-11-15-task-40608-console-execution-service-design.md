# Console execution service boundary — TASK-40608

**Decision: replace the per-helper process direction with one real, profile-bound Console execution service. Its first supported route is the existing stock durable primary Console flow, from received input through preparation, durable acceptance, provider/tool execution and terminal retirement. Extract the composition currently owned by `ConsoleRuntime.ensure_chat_store`, `ensure_agent_bridge` and `ensure_chat_controller`; do not build another App-shaped child or move only `run_reply`.** Keep unrelated screens and their independent repository access in the parent. This is a bounded vertical extraction, not an application-wide storage server or a promise to migrate every Console feature.

Task54's independently accepted result rejects the key-only route. Keep it disabled during this work and remove its unused production implementation when the replacement lands. A whole-index/catalog extension is not selected: it would retain substantial expensive received/configuration/commit/postcommit work in the rendering interpreter and introduce another mutable cross-process boundary before addressing that work. The extraction is the smallest coherent *ownership* boundary covering those phases. It is larger than another command adapter. Its performance is unproven and must pass the rejection screen below before another original journey run.

Status: reviewed design selected for staged implementation on 2026-11-15. Begin with in-process composition factoring that retains original receivers. Detached ownership, process writes and production routing require their later implementation/control gates; design approval is not runtime or performance evidence. ADR required: yes; existing ADR126/230/353 record this boundary. The original README/edit three-pair sub-five requirement remains unmet.

## 1. Cost structure and the limit of the smaller alternative

Use these variables, not a generic “N”: `C` logical foreground commands; `B` selected local bindings; `P(c)` independently admitted source/DB participants in command c; `U(c,p)` unique paths plus their ancestry observed for participant p; `F(c,p)` freshness phases separated by actual waits/effects; and `R(c)` repeated consumers of the same result. Helper nesting can multiply observation of the same `U` within a phase; periodic consumers multiply complete commands. A phase cannot span a lock wait, approval/provider wait, source replacement, repair/write, or publication that requires fresh evidence. Different participants, roots, or source instances cannot be combined merely because a filename matches.

## 4. Fixed operation and projection contract

Add a small versioned codec in `Chat/console_execution_protocol.py`, client/lifecycle owner in `Chat/console_execution_process.py`, and isolated entry in `Chat/console_execution_worker.py`. Reuse the existing bounded framing and contained-process primitives; do not derive a generic RPC framework from `PermissionProcess` or subclass its poison/publication semantics. Messages carry protocol version, profile epoch, service epoch, session ID/incarnation, request ID and strictly increasing per-direction sequence. Reject duplicate/conflicting/out-of-order effects; reconnect is recovery, never replay.

**Receiver scheduling is part of the contract.** Each endpoint has one continuously serviced framed reader and a serialized writer; neither awaits a turn, permission mutation or native worker. The backend reader dispatches onto its running asyncio owner loop. `ReceiveTurn` validates/adopts inputs and creates the existing retained custody task, then returns to dispatch. That task and original worker futures may wait independently. `ResolveDecision`, `CancelTurn`, `CommitPlanAck`, source/config revocation and drain controls are processed while the turn is live. Event/round maps use the original interrupt lock; input adoption uses `_preparation_lock`; transport state uses one short service-control lock over epoch, source revision, pending plan state and admitted finite-effect records. No lock is held during pipe I/O or a native wait. The reader never does DB work; native permission mutations run as retained finite operations while the reader continues servicing controls.

Distinguish `Received(sequence)` (decoded and retained), `Applied(sequence, revision/outcome)` (the named state transition completed), and `Retired(operation)` (its actual physical owners settled). `ReceiveTurn` does not delay consumption of later messages until completion. `UpdateInputs` is applied in channel order before the subsequent pressed `ReceiveTurn`; commands with the same session use the original input lock. Later edits cannot rewrite the accepted pressed snapshot. A decision or Cancel does not queue behind the turn's completion. Cancellation can be applied while a worker is waiting on its Event; the final acknowledgement still waits for physical retirement.

**Revocation/effect ordering:** before changing a parent-owned in-memory source, the stock setter asynchronously requests `FenceSource(expected_revision)`; the backend applies it under the control lock, increments the revision and blocks new effect admissions. Each finite protected effect registers under that same lock against the expected source revision immediately before its existing native preflight: durable commit; hook execution; provider dispatch; tool permission/dispatch; index repair/migration/publication; and terminal/postcommit writes. Registration linearizes the effect versus fencing but grants no native permission. Release the control lock before acquiring native fences; original fresh checks execute, then the effect and its native cleanup. If fencing wins, no new effect starts. If effect registration wins, the change waits for that already-admitted finite effect to retire; it does not declare the old effect rolled back. Fencing never waits for an entire turn, approval or provider response before it can cancel/revoke the next stage. Provider/tool dispatch admission ends at actual dispatch handoff, whose ongoing work remains separately owned and cancellable under existing rules.

After old finite effects drain, the parent applies its original setter and sends `ApplySourceRevision` with the selected values/reference identity stamp; backend installs its domain source change and replies `Applied`. Only then does the parent action report success or permit Send against the new revision. A changed parent object outside a managed setter immediately fences the client locally and requests backend fencing; queued results cannot publish. If the channel fails, close local intake and revoke the association; do not acknowledge the mutation as coordinated. Existing earlier effects remain potentially in flight and drain/recover. No transport wait occurs while holding native/SQLite/permission fences. Backend-owned permission/config changes use the same effect admission order locally and their original fences; they do not need a parent permission object. This orders source replacement with effects without pretending a sequence number is cross-process authority.
