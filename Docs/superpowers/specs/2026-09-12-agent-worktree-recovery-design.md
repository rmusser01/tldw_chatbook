# Agent worktree confirmation and recovery

2026-09-12. Scope: TASK-31210 and TASK-31211. Decision: backlog/decisions/155-agent-worktree-recovery.md. ADR-158 sequences definition caps first (schema18→19); recovery then uses19→20. Recheck actual schema before implementation.

## Product outcome

A primary agent can request Apply, Merge commit, or Discard for its finished isolated child; a visible exact-request confirmation shows source, destination, and the change summary. The Console command palette also offers Recover agent work for previous-turn work owned by this conversation and its currently selected writable repository binding. Opening a list or preview makes no filesystem change. The model's existing tools continue accepting only current-turn handles. Their descriptions direct the user to Console recovery for older work.

Do not create replayed agents, recover old scratch, add settings, or automatically merge/discard work. Only explicit named Workspace bindings are eligible for persisted recovery. ADR-082 scratch is process-local and must never be persisted or rediscovered, even if someone initializes Git inside it.

## Existing APIs that constrain implementation

`Agents/local_tool_provider.py:RunAdmittedWorkspaceRoot` has workspace_id, binding_id, alias, root, locator_fingerprint, root_identity, allow_write, guard(write), optional workspace_executor and authority_scope. `_select_admitted_root(name,args)` honors per-run child routes first and explicit aliases next. `workspace_root` is merely `_root.resolve()` and bypasses admission. `_authority_is_valid` checks write flag/guard; `_authority_scope` is held around dispatched path work. Worktree code must not select authority via private compatibility root or first binding.

`Chat/console_chat_controller.py:capture_run_admitted_workspace_roots` captures actual binding selections. `_workspace_binding_authority_is_current` checks registry ownership, fingerprint, identity and access without consulting viewed workspace. `project_instruction_authority_is_current` checks exact owning session selection. A recovery operation can reuse these guards with a newly captured selection; a persisted record cannot supply a callable guard or authority.

`Tools/workspace_tool_executor.py:WorkspaceToolExecutor.execute` launches the fixed `Tools.workspace_tool_worker` with `-I`, stdin protocol and retained ExecutorProcessTree containment. `_build_request` rechecks the original DirectoryChain. It only allows closed fs and read-only Git operations. `workspace_root_pin.pin_workspace_root` opens O_NOFOLLOW/fchdir on POSIX and verifies/holds cwd on Windows. Never call it in the multithreaded app. Worker Git must inherit cwd (`Path('.')`), not reopen the authorized absolute root or start a new process group. The worker result is only returned after cleanup proof; response/timeout/cleanup failure may occur after a mutation and cannot mean “nothing happened.”

`Workspaces/git_workspace._run_user_git` uses cwd and scrubbed targeting variables but inherits ambient user environment/identity and runs subprocesses without independent process groups. Using it from the existing clean worker changes available ambient config/environment. Decide that explicitly: restore only required user Git identity/config inputs, never PATH executables from the repository, Git targeting/env-injection variables, credentials for network operations, or an arbitrary environment passed by model/UI. No network operation is permitted. Prefer fixed agent identity for generated child commits; parent merge identity can use canonical Git config where supported, otherwise return actionable missing-identity refusal. Do not preserve raw custom GIT_CONFIG_* injection.

## Closed authority/worker boundary

Introduce a public `LocalToolProvider.capture_worktree_authority() -> RunAdmittedWorkspaceRoot | WorktreeRefusal` that returns the exact sole eligible run-admitted writable named binding, after guard(true), or existing reason-coded WorktreeRefusal. Store the intended project selection explicitly in provider construction if multiple admitted roots otherwise make this ambiguous. It must refuse no selection, scratch/default, read-only, ambiguous, stale or disabled authority; do not silently choose from multiple roots. For standalone tests/services, pass an explicit RunAdmittedWorkspaceRoot fixture instead of relying on legacy fallback. Creation, merge and discard all use this seam.

Use the existing one-shot transport/containment, with ADR-155 explicitly allowing these *internal* closed operations (not general git_* tools):

- `agent_worktree_create`: exact generated run UUID, generated branch, app-owned parent DirectoryChain, unpredictable destination basename; no user-supplied Git argv/base. Base is captured by worker from pinned destination repository HEAD.
- `agent_worktree_preview`: source tuple (run ID, exact branch/base, companion DirectoryChain), computes bounded preview plus fingerprint and actual branch HEAD.
- `agent_worktree_apply`: same tuple plus preview fingerprint/expected HEAD; captures child changes and applies exact checked binary patch as uncommitted destination changes.
- `agent_worktree_merge`: same tuple, creates explicit merge commit, aborts only merge state this operation started.
- `agent_worktree_discard`: same tuple and expected HEAD; confirmed destruction only, subject to root deletion limit below.

Add exact argument schemas to workspace_tool_protocol (version bump only if incompatible frame semantics are introduced), `_EXPECTED_INTENTS` (preview read; all others write), and internal worker dispatch in a lazy `Agents/agent_worktree_operations.py`. No arbitrary argv, executable, config map, shell, patch supplied by caller, target ref name, or arbitrary external path. Root and companion identities originate only in admitted app-owned records; protocol validates strict UUID/branch/base/identity shape and bounds. Ordinary fs/read-only-Git callers cannot create these operations through model schemas. Parent-side orchestration still checks normal kill switch, writable binding, exact owning conversation and explicit confirmation.

The worker pins the repository for the entire operation and separately opens/pins the exact child when operating within it; POSIX keeps the destination fd and fchdirs back without reopening the locator. Windows requires both directory handles to deny rename/delete while temporarily switching cwd; the existing helper's share-all handle alone does not provide this two-root guarantee. Use nested existing pin_workspace_root contexts on POSIX, retaining both descriptors and restoring the destination through its descriptor. Refuse all new multi-root operations on Windows or absent required descriptor capabilities before admission; do not add an unqualified Windows retention implementation. Never claim coverage from mocked Windows tests alone.

Match child registration, expected branch, HEAD/base and common Git directory while pinned. The boundary follows ADR-101: it prevents substitution of admitted roots; it is not a hostile-Git-metadata sandbox against arbitrary descendant .git/config edits, hooks, filters, symlinks or privileged mount changes. Disable hooks for generated commits and merges unless product deliberately retains them; keep any accepted attributes/filter behavior documented. Add explicit preflight refusals for unsupported submodules/external Git directories rather than accidentally broadening scope.

### Selected discard policy: discard data; retain baseline checkout

Root adopted the bounded logical-discard policy on 2026-09-12. Discard resets the pinned child to its recorded base, removes untracked child data using no-follow descriptor-relative deletion, detaches HEAD at that base, and deletes the exact agent branch with expected-old-SHA update-ref. Keep the baseline detached checkout as `discarded_cleanup_pending`; receipt and tool descriptions say work discarded and baseline checkout retained. This revises the directory-removal wording; root must update task AC/schema copy before implementation. A failure leaves uncertain state, never a false fully-discarded result.

No production forced pathname root deletion or automatic root-removal GC is authorized by this design. `git worktree remove --force <absolute-child>` reopens the locator and is not safe merely because its previous identity was checked. Keeping harmless residue is the intentional storage cost. Do not build a physical deletion mechanism in these tasks.

## Physical cleanup: reuse ExecutionOwner; no second registry

Current `Agents/execution_capacity.py` already owns positive physical lifetime. `ExecutionOwner.bind_run` records the real run ID; `RuntimeCapacity._owners` only prunes an owner when `_root_finished` and `_operations` is empty. `_call_with_timeout` (:1834) reserves a tool operation before starting; only its actual runner finally calls finish (:1852). Timeout/cancel marks stopping and returns while the operation remains. `_run_owned` binds/activates the owner; `run_child_owned` (:5430) calls child_owner.finish_root only after run_child actually returns. `_settle_fleet` can write terminal DB status but does not finish that owner. Bridge model lifelines reserve_model and release from actual driver-finally (:2353), including delayed client cleanup. This is the needed lifecycle; adding AgentWorktreeOwners would duplicate it.

Concrete minimal extension: `ExecutionOwner.on_drained(callback: Callable[[], None]) -> None`. Store a one-shot callback list on that existing owner. Under capacity lock, `_prune_if_finished` determines the transition, removes owner, and detaches callbacks; `finish_root`/`OwnedOperation.finish` invoke detached callbacks only AFTER releasing the lock. Registration on an already drained owner runs immediately outside the lock. Every callback is attempted independently and exceptions cannot mask cleanup. No callbacks, DB writes or joins under capacity lock. Reserve rejects root_finished, so a drained owner cannot acquire another tool operation later.

At child run precreation, call child_owner.bind_run(child_run_id) before creating/admitting its worktree (the later bind in _run_one remains idempotent). Persist `execution_id` from this actual owner and `writer_state='held'`, then register on_drained to call `AgentRunsDB.mark_worktree_writer_drained(run_id, execution_id)` with an exact conditional update `WHERE writer_state='held'`. This callback also covers normal finish and failed starts. No mapping registry is needed: creation already has both run ID and child_owner. RuntimeCapacity.snapshot supplies current status for explanatory UI; durable `writer_state='drained'` is the positive recovery gate. Failed callback persistence keeps held/unknown and recovery refuses; it never falls back to absence from capacity snapshot. A retry may use the retained exact owner reference while alive; do not infer drain by arbitrary run-ID lookup after pruning.

A helper can raise `WorkspaceToolExecutionError('cleanup_unproven')` and return to the tool runner although descendants might remain. Therefore tool-thread completion is not sufficient on that failure. Add a sticky child-authority error observer at the actual `LocalToolProvider.invoke_detailed` WorkspaceToolExecutionError catch (:1880), before converting it to ToolResult. For admitted agent roots, attach an optional typed `on_cleanup_unproven` callback to RunAdmittedWorkspaceRoot, closing only over run ID/execution ID and the worktree repository. The observer sets `writer_state='uncertain'` (conditional held/drained→uncertain) synchronously before runner-finally can signal drain. The on_drained CAS never overwrites uncertain. If persistence raises, retain that existing owner conservatively (do not release the uncertain tool operation) or set a failure latch that prevents its drain callback from writing drained; do not swallow the failure and mark safe. Easiest owner addition: `mark_cleanup_unproven()` sets a sticky `_cleanup_unproven` flag, exposed to the drained callback outcome; use `on_drained(callback(bool cleanup_proven))` instead of zero-arg callback if this case is supported. That flag survives even if DB persistence fails. Callback writes uncertain when false, drained only when true.

Prefer the latter combined API: `ExecutionOwner.mark_cleanup_unproven()` and `on_drained(callback: Callable[[bool], None])`. The provider's child-root observer marks the exact owner immediately; the owner final callback persists the outcome. Also mark mutation helper cleanup_unproven in recovery's own ExecutionOwner before finish. Ordinary tool exceptions/timeouts with proven process cleanup do not poison ownership forever. Root admission/registration failure before subprocess start remains clean. Read-only operations can launch Git/filter descendants, so observer applies to all child-root workspace calls, not only writes.

Restart behavior is precise: writer_state drained survives and can recover after binding/Git identity validation; held from an earlier process becomes writer_state uncertain on reopen, not drained. Uncertain cleanup is never cleared by reboot/PID/elapsed-time guesses. Runs that finished normally before restart have their durable callback; crash-before-callback retains conservatively. Missing legacy state is non-actionable. This supports normal prior-turn/restarted recovery and honestly limits crashed/unproven owners without inventing cross-process liveness.

For recovered operations, use `runtime_capacity.begin_execution(origin=MANUAL, conversation_id=..., child=False)` as the existing physical owner, reserve_tool around the actual helper, and finish_root when the operation driver exits. Keep its separate cancel event and UI operation record; do not create a fictitious AgentRun or bind it to the child's historical run. Human waiting does not occupy a tool slot; reserve only after consent/authority/CAS admission. This shares actual capacity accounting while preserving distinct domain cancellation.

## Durable metadata/state

AgentRuns v20, after definition-cap v19, adds a local-only `agent_worktrees` table. Fields: run_id PK/FK, workspace_id, binding_id, locator_fingerprint, repo_root, repo_identity_json, git_common_dir, child_path, child_identity_json, branch, base_sha, state, operation_id nullable, expected_source_head nullable, preview_fingerprint nullable, operation_action nullable, created_at, updated_at. State CHECK: `creating`, `unresolved`, `applying`, `merging`, `discarding`, `applied`, `merged`, `discarded_cleanup_pending`, `uncertain`. Add `execution_id TEXT NOT NULL` and `writer_state TEXT CHECK (writer_state IN ('held','drained','uncertain'))`; the existing execution owner's positive drain callback owns this state. Derive conversation and parent from agent_runs; no transcript/task/result blob duplication.

Writing absolute roots to local-only AgentRuns metadata is intentional ADR-155 scope; do not put it in model history, generic diagnostics, export/sync or Console metadata badges. Add repository projection/export exclusions where needed. Never persist ADR-082 scratch.

Creation order: create child run row → insert creating record with intended admitted binding/generated target → invoke pinned create → update exact base/identities/unresolved → admit child provider → start child. Before recorded base/identity success, child never runs. A crash leaves creating/uncertain rows for non-actionable inspection. Failure unwind only touches newly created known-empty material through the same safe boundary.

Recoverable listing joins terminal child run ownership to unresolved records, bounded/paginated and filtered by current selected binding/fingerprint/repo identity. Fresh identity checks and read-only preview happen in workers. Empty/foreign/missing DB rows are not implicitly owned. Legacy agent/* worktrees with no record/base are not adopted or auto-deleted; show a concise legacy limitation where relevant.

Before mutation, CAS unresolved→applying/merging/discarding with a unique operation ID in a transaction. Revalidate exact authority and source fingerprint after Allow; then execute once. Persist success terminal state or `uncertain` on timeout/invalid response/cleanup failure/process interruption/DB finalization failure. On restart, in-flight states become uncertain; never automatically retry apply or clear an uncertain record. Explicit inspection can show current source and destination, but automatic “looks applied” heuristics do not authorize retry. Uncertain rows remain preserved and non-actionable except future explicit reconciliation; this is an honest crash limit.

GC excludes every unresolved/in-flight/uncertain/owner-uncertain record, including clean unmerged work. Unknown branches are preserved. Successful apply/merge may leave harmless source checkout until safe removal; a source state recorded resolved is not recoverable a second time. Disable the old implicit pathname-removal GC in this flow. Retain resolved baseline checkouts and all unknown discovered names; no automatic root-directory deletion is part of this implementation.

## Root decisions resolved (2026-09-12)

Root adopted logical discard with retained baseline checkout, reuse of ExecutionOwner with one-shot outside-lock drain callback and sticky uncertain state, and honest refusal on unqualified platforms. Use writer_state held/drained/uncertain. Register callback before child worker start. A prior-process held row is never guessed drained. No user-data operation has been authorized merely by this planning decision; product operations still require their actual per-call confirmation.

Remaining work is concrete implementation evidence: actual POSIX secondary-root retention and fd-relative cleanup race tests; exact branch-ref CAS; sticky unproven cleanup when DB callback fails; explicit Windows unsupported refusal test. Existing standard linked-worktree Git metadata is a documented trust boundary, not a claim of a hostile repository sandbox. No further ownership-registry design decision remains.

## Logical discard refinement and exact remaining pin limits

The existing POSIX PinnedWorkspaceRoot exposes root_fd and keeps cwd on that inode. Git reset/checkout invoked with cwd='.' therefore restores tracked data in that pinned child rather than a replaced absolute child locator. It does NOT make `git clean` or arbitrary symlink-recursive Python deletion safe by assertion. Implement untracked cleanup by an audited fd-relative traversal (`os.listdir(fd)`, `os.stat(name,dir_fd=fd,follow_symlinks=False)`, O_NOFOLLOW directory opens, `os.unlink`/`os.rmdir` with dir_fd), refuse mount-point traversal, and leave the top-level root alone. Do not delete `.git` administrative linkage. Avoid destructive reset before the prepared source fingerprint is checked. Use `git reset --hard <validated original base>` plus detach HEAD at that same object only after the full Discard approval; protocol fixes commands and object syntax, not caller Git argv. A dedicated implementation may use `git checkout --detach --force <base>` instead if tests establish identical tracked cleanup and branch state. Branch removal is `git update-ref -d refs/heads/agent/<exact run_id> <expected old object>` after checking no other worktree owns it. This is a CAS on the exact ref, not branch -D.

Execution qualification rejected the proposed linked-metadata assumption. A real Git2.39.5 process with both roots pinned advanced a replacement parent repository after its original root moved; no hostile descendant edit was needed. That violates the admitted-root guarantee. Retaining a common metadata directory and passing an ordinary absolute path does not fix it. The tested macOS fd aliases were unsupported, and legacy inode locators resolve through pathnames. Upstream Git startup also canonicalizes and later reopens worktree paths; this is a further source-backed proof obligation, not a reproduced installed-Apple result. Neither standard linked worktrees nor independent child repositories have a qualified complete boundary yet. Keep these new mutation operations unavailable until a separately reviewed execution design has actual original/replacement files, index and ref evidence. Repeated `rev-parse` checks and a safe CREATE-only test do not establish it.

The supported minimal platform is POSIX with descriptor-relative traversal and retained cwd descriptors. Current Windows PinnedWorkspaceRoot's share-all handle and cwd locking do not supply a safe fd-relative clean across multiple roots; logical discard must explicitly refuse there until an equivalent handle-relative primitive and live qualification exist. Apply/merge use nested existing POSIX root pins and fail closed elsewhere. There is no silent fallback to pathname deletion. Remaining concrete implementation proofs: nested-directory replacement/symlink tests for clean, exact Git-ref CAS tests, source fingerprint freshness, and real nested secondary-root pin qualification. These are scoped implementation tasks, not another invented ownership mechanism.

## Implementation rulings

Root reviewed the existing PinnedWorkspaceRoot POSIX descriptor/restore behavior and ExecutionOwner operation-release paths. Reuse nested root pins and the existing owner; do not create another ownership registry or worker daemon. Reuse AgentWorktree/WorktreeRefusal where their structure remains accurate.

Closed worktree Git commands use the worker's existing external-only PATH and containment. Preserve only host-originated HOME/XDG_CONFIG_HOME for these internal worktree operations when absolute and outside the admitted repository; do not add them to unrelated local-tool environments. This allows existing user Git identity/config resolution. Never accept caller/model-supplied environment or GIT_CONFIG_* injection, credentials, SSH or askpass variables. Generated child commits retain the existing fixed tldw-agent identity. Parent merge commits use resolved user Git identity and return an actionable refusal if absent. Disable hooks for generated commits/merges; do not request network operations or credentials. Existing Git attribute/filter behavior remains within the explicit non-hostile-metadata limitation.

Preview is read-only and includes untracked changes. Bound rendered preview to8192characters with a truthful truncation notice. Hash content through bounded chunks and stream binary patches through an owned bounded spool (32MiB cap), refusing oversized operations before changing the destination. A confirmed operation may first capture child changes in a commit so that untracked and tracked content form one exact patch; if that patch exceeds the cap, preserve the child commit, original base and unresolved recovery record, and report that destination changes were refused. Never capture an entire large patch in a Python string. Gate actual root rename/replacement, companion identity drift, nested symlink cleanup, source changes while awaiting consent, dirty destination and existing merge-state cases. Logical discard removes ignored/untracked child data too, without following symlinks, preserving the .git administrative link and tracked baseline. No automatic root-directory cleanup.

Execution order: closed authority/operations, durable ownership/drain fences, visible same-turn card, then retained Console recovery. Do not enable the visible mutation tools until the durable physical-owner prerequisite is reviewed. No current DB terminal status alone grants mutation eligibility.
