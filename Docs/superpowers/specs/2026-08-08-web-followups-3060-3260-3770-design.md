## task-3770 — lock the fetch/robots caches (mechanical)

The `_search_cache` lock shipped in #1444; `_fetch_cache` and `_robots_cache` carry the identical eviction-iteration race (`min()` iterates while a concurrent tool thread mutates). Fix shape, same as #1444: one `threading.Lock` PER cache (`_fetch_cache_lock`, `_robots_cache_lock` — separate locks so a robots fetch never waits on a page-cache scan), wrapping ONLY the short ops:
- `_cache_put` body; `web_fetch`'s cache-hit branch — LOCK SCOPE CARVED PRECISELY (spec review, Important 1): only the dict `.get()`, expiry comparison, and `.pop()` go under the lock; `_validate_hop` (live DNS), the robots re-check (`_robots_allows` — can trigger a full robots fetch + client construction), and the `return text` all execute AFTER release. A literal "wrap the block" reading pulls network calls under the lock and violates this spec's own never-list.
- `_robots_cache_put` body; `_robots_allows`' cache read/expiry check (read the parser reference under the lock; `can_fetch` and the cache-miss FETCH run outside — the accepted cross-call stampede, at most one duplicate robots fetch, is UNCHANGED and `_robots_allows`' docstring must be updated to say "cache bookkeeping locked, fetch not" instead of the now-false "no locks" (Minor 6)).
- `_reset_state_for_tests()`' direct `.clear()` calls stay unguarded — deliberately excluded (test-only, never concurrent with worker threads; Minor 7, recorded).
Behavior unchanged single-threaded; existing cache tests must stay green unmodified. Verification (amended per spec review, Minor 10 — the original "no test" ruling was half lazy): a deterministic race-REPRODUCTION test is still out (flaky by nature), but a barrier-based lock-usage test is cheap and deterministic — thread A blocks inside the critical section on an `Event`, the test asserts `lock.acquire(blocking=False)` fails while A is inside, then releases; one such test per lock (or parametrized across both).

## task-3260 — deep-search scrape path honors robots.txt (design)

Parity gap recorded by the robots spec: a path `web_fetch`/`web_crawl` refuse can still be scraped by `web_deep_search`'s relevance phase. Rulings:

1. **Same toggle, plumbed like the timeouts**: `web_deep_search` reads `respect_robots_txt` from `_webfetch_settings()` and places it into `search_params` (the pydantic-safe channel); `analyze_and_aggregate`/`search_result_relevance` read it from there (default False when absent — the dead-wired research-service caller keeps today's behavior; the TOOL is the only user-facing entry and passes the real setting).
2. **Check site**: in `search_result_relevance`, between the existing SSRF guard and the `scrape_article` call — same offload discipline (the robots check does network I/O: route it through `asyncio.wait_for(loop.run_in_executor(_get_dns_guard_executor(), …), timeout=scrape_timeout_s)` — the dedicated executor exists precisely so guard-class calls can't crowd the LLM offloads; robots fetches are guard-class).
3. **Mechanism reuse, honest UA**: a new small public helper in `Tools/web_tool_impls.py` — `robots_allows_for_scrape(url) -> bool` — builds a short-lived `httpx.Client` on the module `_transport` seam **with `trust_env=False` and a bounded timeout, mirroring `_new_web_fetch_client()` (spec review, Important 2 — httpx defaults `trust_env=True`, and an honored `HTTP(S)_PROXY` does its own DNS and connects on the app's behalf, silently defeating `validate_outbound_url`'s SSRF check on the robots URL)**, delegates to `_robots_allows(client, url, ua=_DEEP_SEARCH_ROBOTS_UA)` (new constant, e.g. `tldw-chatbook-deep-search/1.0`), closes the client. Shares the module robots cache (30-min TTL, negative caching, all #1427 hardening — redirect-following, IPv6 brackets, fail-open — for free). `WebSearch_APIs` imports it FUNCTION-LOCALLY (no module-level cycle: web_tool_impls already imports WebSearch_APIs function-locally in the other direction). UA honesty recorded: `scrape_article` masquerades as Chrome (pre-existing FIXME at `Article_Extractor_Lib.py:192`, out of scope) — the robots check uses a truthful bot identity, which in practice matches sites' `*` groups; checking with the Chrome UA would evade bot-scoped disallows.
4. **Disallowed → snippet fallback, not discard**: a robots-disallowed URL takes the SAME path as an SSRF-refused one — skip the scrape, keep the result with `_build_result_fallback_content` (Title/Snippet/URL). Robots governs FETCHING the page; the snippet came from the search engine, and deep-search's contract is never-discard-paid-work. A `logger.debug` names the host (never the query). No new counter (parity with the SSRF-refusal path, which has none) — RECORDED.
5. **Fail-open, stated unambiguously (spec review, Minor 9)**: on a robots-check error or timeout, treat the URL as ALLOWED and PROCEED to scrape it — matching `_fetch_robots_parser`'s existing fail-open for web_fetch/web_crawl. This deliberately differs from the SSRF guard immediately above, whose own timeout/refusal still refuses; the SSRF guard's semantics are unchanged.

Tests (established seams: `WebSearch_APIs.chat_api_call` + `scrape_article` fakes; `web_tool_impls._transport` for robots bodies; `_reset_state_for_tests`):
- respect on: disallowing robots for a result host → `scrape_article` NOT called for it, result carries fallback content, other hosts scraped normally. **THREE fakes required (spec review, Important 3 — miss one and the test observes the wrong refusal or fail-open): (1) `WebSearch_APIs.is_public_http_url` faked True (the SSRF guard runs FIRST, does real DNS, fails CLOSED — every `.example` host in this test file is refused by it today before any robots check could run); (2) `web_tool_impls._transport` MockTransport serving the robots body; (3) `socket.getaddrinfo` faked to a public IP — `_fetch_robots_parser`'s own `_validate_hop` does a SEPARATE DNS check on the robots URL and fails OPEN on DNS failure, silently bypassing the MockTransport.**
- respect off / key absent from search_params → zero robots fetches (transport counter), scrape proceeds (research-service parity pin).
- robots unreachable → fail-open, scrape proceeds.
- tool-level: `web_deep_search` places the configured `respect_robots_txt` into `search_params` (settings-seam fake).
- Mutation checks: bypass the robots consult in relevance → disallowed-host test red; drop the search_params plumbing in the tool → tool-level test red.
