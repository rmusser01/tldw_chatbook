## Findings

1. **P2 — Reject a stale screen before it replaces the current visit.** `console_execution_process.py`, proposed lines 213–230 (`attach_view`): exact `ChatScreen`/App identities are checked, but current-screen and teardown checks occur only in later `require_view`. A delayed preparation for an older screen belonging to the same App can therefore replace `_view` and increment `_visit` while a different Console screen is current. Its later `require_view` fails, but the valid screen's captured visit has already been invalidated and the stale screen remains attached. Validate the actual current screen and applicable mounted/teardown state before changing either field. A focused control should attach the current screen, attempt attachment of a stale same-App screen, and verify both original attachment fields remain unchanged after refusal.

2. **P2 — Fence superseded saved-target requests within the same visit.** `console_execution_process.py`, proposed lines 284–299 (`prepare_view`): `_resume_view_request` retains the latest `(view, visit, conversation_id, task)`, but a caller awaiting `current[3]` never rechecks that it is still the current tuple. Start saved-target B, then C without leaving the screen; if B's original open finishes after C, B still passes `require_view`, requests its own projection, and can overwrite C. Request sequence checks inside `read_projection` do not solve this: the obsolete B caller issues a newer ReadProjection after its delayed await. Require the same retained request identity after opening and through projection adoption. The initial-target mismatch branch should use equivalent supersession/coalescing ownership. This concerns the implemented preparation helper, not unfinished Compose wiring.

3. **P2 — Preserve a retained first saved session on ordinary navigation return.** `console_execution_process.py`, proposed lines 268–282 (`prepare_view`): open saved conversation A on the first visit, cancel/detach that view after the retained OpenSession has been issued but before any projection is adopted, then return to Console with the default `conversation_id=None`. `_initial_conversation_id != conversation_id` takes the mismatch branch and eventually issues `_retain_open_session(None)`. The backend's original `OpenSession` implementation creates a new blank session when the conversation ID is absent (`console_control_dispatch.py:1327`), so this is a real additional session rather than rejoining A. Treat absent target as reuse of the retained initial result in this case; only an explicitly different saved target should open another session. Retain the original A command and its outcome throughout cancellation.

## Checks without findings

- `ConsoleExecutionClient.__init__` remains inert with `_loop=None`, so the new App holder can be constructed before the running event loop. Startup is retained internally and view observers shield it.
- Retained OpenSession tasks shield both command outcome and physical retirement; an observer's cancellation does not cancel their original receipts. Finished-task exceptions are retrieved, and shutdown joins pending open tasks before closing intake. New prepares that resume after shutdown are rejected by `require_view`.
- The App quit branch passes `deadline=None` through timeout, process wait, pipe-thread joins and monitor join. The existing outer App shutdown loop still retains cleanup across caller cancellation. Negative channel/native outcomes remain negative even after process cleanup; the patch does not equate process absence with successful retirement.
- `acknowledge_plan` requires the exact retained receipt and plan object, canonicalizes through `encode_message`, and submits all original ACK identity/fingerprint fields. Event arrival only wakes observers and does not automatically acknowledge. Actual presentation/paint gating remains an explicitly pending caller responsibility and is not reported as a defect in this slice.
- The selected runtime-construction refusal prevents accidental creation of a parent Console graph. Compose, readiness adoption, full UI reconciliation, Settings and loss-inventory integrations are expressly pending and outside this review verdict.
