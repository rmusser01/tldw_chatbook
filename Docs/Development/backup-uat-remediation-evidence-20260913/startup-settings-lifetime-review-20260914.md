# Startup settings lifetime: bounded independent review

**No additional getter-only grouping is justified in the requested chain.** The inspected code contains repeated live Canvas reads, but they are separated by store/session/view operations rather than a contiguous list of reads like `_global_context_policy_overrides`. No implementation or full-app/local timing run was performed; this is a source/design finding, not a Windows performance result.

The supplied exact86ad profile review records the initial composition stack and 17 cumulative `_read_canvas_enabled` calls. It explicitly cannot assign all 17 calls to one summary invocation or measure equal completed work. Its candidate timeout and the separate four startup failures remain unresolved. Current source also includes intervening upstream session/provider-derivation changes, so historical stack counts cannot substitute for a measurement of this current chain.

Current source evidence (repository `/private/tmp/chatbook-backup-pr-20260912`):

- `UI/Screens/chat_screen.py:8462` `_build_console_settings_summary_state` calls readiness, context estimate and context-control derivation. These are not simple config getters: readiness ensures session settings; context estimate obtains the store and may read messages/workspace context; context-control derivation invokes further live policy/owner work. Enclosing this complete builder would require a broader lifetime/error/owner proof, not the requested nine-read-style change.
- Readiness `:9864` first calls the session controller, then provider selection, fresh app-config resolution and readiness/model-capability logic. Provider selection `:9592` already has its existing per-derivation memo. Its implementation `:9609/:9665` interleaves config projection with `_ensure_console_chat_store`, active-session/settings reads and selection handling. There is no adjacent run of guarded native getters to group without encompassing these operations.
- `UI/Console_Modules/session.py:3515` ensures a store, derives defaults, creates/updates session state and conditionally resolves stale settings. Its blank-default helper `:3499` uses the already supplied app-owned mapping; `Chat/console_session_settings.py:1171/1123/1038` projects that mapping rather than calling repeated guarded CLI getters. Do not count dictionary field access as native acquisition.
- Correction after the current043d Windows review: `_default_console_session_settings` (`session.py:3490`) obtains effective provider/model and fresh app config. Both can reach `_provider_readiness_app_config`. `config.load_settings` is itself decorated with `@_config_participants.guarded` at1747, so even its cache-hit path enters the native config operation. The earlier claim that cache hits avoid acquisition was incorrect and is withdrawn. This nearby two-read helper is absent from the current measured failing startup stack; the actual session ensure uses `_blank_console_session_settings`. No startup fix or safe grouping of the mixed store/session/Canvas path follows from this correction. See `windows-startup-043d-review-20260914.md`.
- `chat_screen.py:9973` `_ensure_console_chat_store` computes workspace context, optionally constructs the store, may update its workspace, and binds Canvas view callbacks. `Chat/console_runtime.py:2877` first creation includes real trace recovery, persistence/media retry and Canvas/store construction. These are different owner/effect boundaries; wrapping this whole path is outside the bounded same-config-read proposal.
- `console_runtime.py:2642` `bind_canvas_native_view` performs one `_canvas_enabled` read before the Canvas lock, then preserves disposal/latch checks and binding/listener/rebind effects inside the lock. `_read_canvas_enabled:2770` calls one supplied reader and fails closed; `_canvas_enabled:2778` applies the restart latch. The default reader (`:1021–1023`) is `config.get_canvas_execution_enabled:398`, which performs one guarded bootstrap load followed by mapping/environment normalization. Grouping this one read cannot reduce multiple acquisitions. Repeated binding calls must retain their existing live gate and custom-reader semantics; do not carry one policy observation across separate callback/effect boundaries.

The already approved `_sync_console_rail_and_controls` (`chat_screen.py:21484`) uses `_run_console_config_sync` for a particular synchronous replayable pass. Initial `compose_content → summary` is a different entry path; copying that scope wholesale would also change native entry-pause handling and which non-config exceptions become persistence failures unless separately designed. The absence of `await` alone does not establish a safe lifetime.

There is therefore no new same-work N→1 reproducer specified for implementation in this chain. Calling the Canvas getter 17 times in an invented loop and wrapping that loop would measure a fabricated boundary, not the actual composition workload. If this chain remains a priority, the next measurement would need one exact current summary invocation with its real session/store/Canvas callbacks, recording original acquisition counts at those callback boundaries and distinguishing warm and first-use paths. It must not replace owner work with stubs and then claim whole-chain equivalence. That would be additional diagnostic scope, not evidence already available here.

No cache, snapshot memo, guard/read removal, different-owner scope, async lifetime, deadline change or speculative startup-wide grouping is recommended. Existing native lock/error/maintenance semantics remain authoritative, and the historical Windows aggregate supplies no new speedup claim.
