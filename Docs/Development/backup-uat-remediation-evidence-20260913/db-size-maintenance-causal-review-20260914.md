# DB-size telemetry maintenance lifecycle review

Bounded source verdict: newly delivered DB-size work is still submitted after other runtime producers close admission. DBStatusManager has no intake gate, tracked worker lifetime, or maintenance hook in RuntimeMaintenance. Existing native/config checks protect storage, but do not prevent this scheduling. This is a concrete omitted producer lifecycle boundary, not proof that it caused any observed Windows30s drain timeout or invalidated a backup.

Exact source path: app's deferred footer initialization schedules an initial update plus DBStatusManager.start_periodic_updates(120). The periodic callback is `lambda: app.call_later(self.update_db_sizes)`; update_db_sizes unconditionally awaits asyncio.to_thread(_collect_db_sizes). Neither that entry nor _collect_db_sizes checks runtime maintenance. app.update_db_sizes simply delegates. Timer.stop is called at ordinary app shutdown, not maintenance. Stopping the timer alone would also leave an already queued call_later delivery possible.

RuntimeMaintenance.settle_producers closes specific _Hook owners and waits each stage. It does not globally pause Textual timers/message delivery or drain the default asyncio executor. Its owner snapshot and producer list omit db_status_manager. Screen navigation admission protects navigation; it is not admission for arbitrary app timer callbacks. Therefore no indirect app/timer gate establishes that a new size worker cannot start in the interval between producer-stage closure and local raw/native retirement.

The distinction between Python work and storage authority matters. Each real DB path getter uses guarded config helpers. Before local pause, an arriving acquisition can perform fresh initialization/permission/registry work and is tracked while doing so; raw scope has final native pause-request checks. After local pause, new _Acquisition refuses storage_locally_paused. Existing leases and pending acquisitions participate in actual drain. The formatter itself only stats main/WAL/SHM sizes; it opens no SQLite connection or content read. No guard bypass or unsafe publishing is demonstrated. However, _get_db_size catches ordinary errors as "Error" and the wrapper may publish that telemetry after failures; an untracked already-started to_thread worker may continue after cancellation of its await. Existing cancellation test confirms no app publication after canceled await, not worker retirement.

Why the previous three-role probe is insufficient: it starts accepted collection before the relevant closure/initialization contention. That proves accepted-work behavior only. It cannot establish behavior of a fresh timer delivery after intake should be closed.

Smallest meaningful native probe proposal (no edits/runs performed here): reuse its fresh private bound profile and actual DBStatusManager/config getters/real native authority. Keep a tiny app scheduling shell only for set_interval/call_later delivery and db_sizes_status; do not boot TldwCli. Record when a real existing runtime producer hook has closed and the native maintenance request is present. Only then deliver the saved real timer callback and drain that actual queued update callable. Gate the collector's entry solely to count a new native thread, then delegate to the original collector; do not replace config getters/admission/formatter results. This proves post-close arrival separately from the prior accepted collector. Repeat at the later actual local-pause point to show the worker is still submitted but its config acquisition refuses before any new storage lease/formatter use. Hold/release a real initialization leader if needed to establish the new worker's pending acquisition rather than infer it from elapsed time. Use bounded Events/deadline and release all gates in finally; do not force retirement.

Record fixed ordering and counts: producer closed, timer delivered, collector entered/thread ID, guarded acquisition entered/refused, no new ordinary native lease after pause, default executor task settlement and whether cached status was published. A control tick after normal resume must collect real sizes. A separate canceled-await variant must retain the existing no-publication assertion while determining whether the actual worker remains live. Use source inspection to establish omission from RuntimeMaintenance; closing only Scheduler in a small probe must not be described as executing the entire app maintenance protocol.

Only after that evidence should a repair be designed: exact manager intake closure plus retained completion of already accepted offloads, registered at the existing runtime producer stage, with reverse resume. No broad timer suspension, new executor/coordinator, retries or native guard changes are justified. An intake check only at timer scheduling would be insufficient because call_later may already be queued; cancellation of asyncio.to_thread alone is insufficient because the native thread survives.

No Windows timing attribution, no code changes, no app boots. Existing tests to preserve: Tests/Utils/test_db_status_manager.py real WAL-inclusive sizes, off-loop collection and canceled-await no-publication; runtime maintenance hook binding/close-drain-resume ordering. This review distinguishes a genuine lifecycle omission from an unproven performance cause.
