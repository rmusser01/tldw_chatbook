# Scheduler initializer probe review

APPROVED as a bounded causal probe of the expected initializer-contention / tracked-worker lifecycle. Both recorded variants exit 0 and retain successful structured receipts. No product change or Windows delay resolution is demonstrated.

Reviewed `/private/tmp/uat-scheduler-initializer-probe.py`, `/private/tmp/uat-scheduler-initializer-results.json`, both referenced child logs, and the current `_Acquisition.initializing`, Scheduler `_offload`/maintenance, and heartbeat source. No new tests, repository edits or remote actions were performed.

The setup uses separate fresh private profiles, confirmed by each log's first configuration creation and native ScheduledTasksDB initialization. `storage.admit_startup()` is the actual gate. No TLDW_TEST_MODE is present. The probe keeps the selected environment unchanged and installs the existing network guard before product imports; zero blocked attempts are asserted. The log identifies current worktree storage source. It does not provide a complete installed-package/source-hash receipt, so this is local worktree evidence.

The sole scheduling intervention wraps `_Acquisition.initializing` and delegates its original context manager exactly once. The leader waits only after the original initialization context has been entered, so its real initializing-root marker remains held. A distinct Scheduler worker reaches the same root at the original context boundary. No permission, registry, path, provenance, cancellation, or native context check is substituted. The scheduling events arrange a possible concurrent ordering; they do not manufacture a successful authority result.

The Scheduler callback is the real `_record_heartbeat` with its default path. Its configuration-backed default-path lookup supplies the relevant guarded acquisition; the probe is not evidence that the heartbeat JSON writer itself uses a raw-file participant. The task is retained in the real `_maintenance_db_tasks` set by `_offload`. Closing Scheduler intake while the initializer remains held gives a false 20ms drain result, rather than cancelling the worker or claiming settlement. Releasing the leader lets the actual worker finish, then drain succeeds and the task set is empty.

In the completion variant, the first heartbeat is read back with the exact tick timestamp. In the pause variant, the real local-pause API intervenes before release: the leader reports RecoveryRequired, no first heartbeat exists, and after pause/Scheduler resume a fresh default-path heartbeat is read back. `_record_heartbeat` intentionally absorbs path-resolution failures, so its successful async completion alone is not evidence of a write. The explicit absence/readback assertions appropriately distinguish those outcomes. The probe records only the leader error class, not the Scheduler worker's exact swallowed reason; do not attribute a specific worker exception beyond this evidence.

Cleanup releases the event, joins the real thread, resumes an owned pause when necessary, restores the exact original initializing method, closes the owned database, and invokes the ordinary storage shutdown. Event waits use 3-second entry bounds and a 5-second leader release bound; heartbeat/join/drain checks use 3-second limits. The 20ms drain observation is a probe deadline, not a product deadline adjustment. No total-process bound is established by the supplied probe/results alone.

Limits: the contender marker is recorded immediately before entering the original context, not from a stack proving time spent inside the wait loop. The source's same-root initialization exclusion and arranged schedule establish expected contention, while these two executions demonstrate retained-worker drain/refusal/recovery behavior. They do not reproduce a 30-second Windows delay, measure normal performance, establish Windows correctness, rule out a different lock cycle, or justify changing any guard or timeout. No further change is recommended from this probe alone.
