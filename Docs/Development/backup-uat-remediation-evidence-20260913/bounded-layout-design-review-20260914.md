# Bounded section owner-layout wait: independent design review

The proposed three-branch change is a coherent minimal candidate. Implementation approval still requires the root's real retained-screen reproduction and focused lifecycle regressions; the Windows CPU observation alone does not establish the geometry predicate at each sampled call. No apps, tests, or repository edits were performed for this review.

Source: `console_bounded_section.py:328–346`, `390–402`, and `414–417` compare actual region heights to selected targets, set styles, then call `request_reconcile`. That schedules another active-screen after-refresh callback even if the owning screen has not reflowed. A same already-selected style cannot make stale geometry current by itself. The previous real tray reproduction establishes that Textual allows this retained-owner lifecycle, but the bounded section has its own wrapper/native sizing branches and must be reproduced independently.

Use one stored owning-screen layout signal for the geometry-mismatch retry, without changing normal external request semantics. Subscribe once after issuing the existing style changes; no await occurs between setting styles and subscribing, so an owner layout publication cannot be lost in that synchronous interval. Immediate signal delivery should unsubscribe/clear that exact stored signal and queue the existing virtual `self._run_scheduled_reconcile` callback. Keep `_reconcile_scheduled=True` throughout the wait AND the queued callback. Do not call `request_reconcile` from signal delivery while that flag is true: it would deliberately coalesce away the only wake. Do not call base `_reconcile` directly: that would bypass `_ContextBoundedSection` allocator handling.

Preserve the current full/scoped contract (`request_reconcile:258`, `request_scoped_reconcile:269`, and `_ContextBoundedSection._run_scheduled_reconcile`, left_rail.py:211–224). Today's three self-retries are full requests, so the wait helper must set `_reconcile_scoped=False` just as those calls currently do. A new full request arriving while pending still demotes scoped ownership; a new scoped request cannot narrow an existing full request. The subclass must continue to snapshot scoped state and prior demand before delegating, and escalate only the same demand changes as before. No allocator algorithm or demand interpretation should change.

Unmount must unsubscribe through the retained signal (not look up `self.screen`) and clear pending flags. The current Signal implementation supports self-unsubscription during publication and drops detached/pruning subscribers; this does not replace explicit cleanup. Register the pending state only after subscription succeeds. Do not add visibility/current-screen guards: transparent/background screen layout is valid, and same-size resume needs a real owner-layout wake even without a widget Resize.

Required native cases: wrapper viewport mismatch, native viewport mismatch, and native total-section-height/hint mismatch; repeated updates while two screens cover the owner stop autonomous callback growth; same-size return restores actual target geometry, hint, focusability and reachable content; hidden ancestor hide/show and removal while waiting retire cleanly. Check that multiple full/scoped requests coalesce without losing a later full request, and exercise the actual `_ContextBoundedSection` override so allocator escalation is not accidentally bypassed. Keep existing `test_console_workspace_tree_cursor_layout.py:317` scoped/demotion test and `test_console_bounded_section.py:182`, `446`, `763`, and width-change tests: they cover native fixed chrome/hint accounting, allocation/clamping, retained offset and responsive remeasurement. Their existing focused logical probes do not substitute for the new unmocked layout reproduction.

This corrects wake ownership only. It does not authorize native admission changes, polling, new deadlines, an allocator refactor, or a claim that every Windows Settings/Library timeout is resolved. Separately, guidance checkpoint stdout may be absent from Windows TimeoutExpired rendering: use the planned bounded fixture log before changing that fixture or attributing its timeout to startup.
